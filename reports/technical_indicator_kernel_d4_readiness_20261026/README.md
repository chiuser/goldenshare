## 需先补齐的三处

### 1. 按现有表格执行，资源验收会超过自己规定的预算

**原文。** LLD §17.1第1880、1891—1907行固定H=200000、10项指标、输出1000；P01一次完整H，P02两次完整H，P03取消一次≤H、完整重试H、最后完整重复H。最多6请求、SQL总预算60000000行。§18.1第2072—2079、2104行再次保留这些上限，禁止借额度或自动重试。

**当前实现依据。** `executor.py:31—37`累计各实际步骤的logical_input_rows；`sources/session.py:111—184`分开计stage、复权、窗口及历史；MACD/KDJ的数学段与追加/状态更新、7个不同均值窗口、BOLL、输出各表检查/关联和尾部保留都会计入。不是把“输出1000根”当成只处理1000行。

按当前源码逐批核算，20万根分为24批8192根和最后3392根，后续批保留249根窗口历史；默认MACD数学段1024、KDJ631。一个完整的20万根/10项请求，**仅已知服务步骤就需12349955行**。五次必须完整执行的请求合计**61749775行**，已超过60000000；取消请求、合成源、因子和基准查询还没有加进去。六次完整等量的已知服务步骤为74099730行。

核算先对保存的D3请求校准：10001根含price结果为608757行，9001根为560880行，均与实际保存统计完全一致。[逐批及分组核算JSON](logical_row_estimate_20261026.json)保留每一步数目、下限及未计工作。这些是整数计量推导，不是20万根耗时或RSS实测。

**影响。** 严格执行原表格会在完成验收前撞预算；开发时临时缩短输入或忽略某些SQL同样违反计划。

**建议。** 先在原两文明确六次请求各自的固定实际输入，把来源生成、因子、失败和最后核对也按当前实现计入，再决定是否保持原总预算。优先在已确认场景和上限内确定可完成目的的输入；若仍保留完整H=200000，则必须提出包含全部步骤的明确预算供review。不能直接把74099730当成新总额，它仍未含来源等额外工作。静态核算的15万根参考仅是复核材料，**本轮没有据此选择或批准新样本**。

**需要review。** 固定验收输入及对应执行预算的修订；产品初始容量、场景数及并发方案不因此改变。

### 2. 方案要求非法参数不排队，LLD却把相关检查放在取得名额之后

**原文。** 组件方案第521行要求“未授权或非法参数不进入等候”；LLD第1283、1285行的库调用和隔离HTTP顺序却是先acquire，工作线程中的calculate再检查参数，没有明确入队前的检查步骤或负责方。HTTP请求“已完成解析”也没有说明已执行指标定义校验。

**当前实现依据。** `contracts.py:80—111`的CalculationRequest构造检查结构和时间；`normalize_request_and_validate_all_instances:114—124`才检查返回数量和条目数量上限；`calculation/dependencies.py:41—50`才用注册定义检查算法、周期及参数，`service.py:85—86`在calculate内调用这两步。

**实际例子。** MA的period=0可以作为一项请求进入execute_library。若直接按LLD的顺序写，两个名额已满时它会先排队，甚至得到繁忙或等待到期，之后才有机会报告参数错误。这与组件方案的入队规则不一致。

**建议。** 在原§12.4同时明确两个入口在acquire前复用现有纯内存检查：请求结构及已知数量限制、算法/支持周期、Definition已有参数规则。不要在App复制一套参数判断，不创建连接、不读来源、不提前执行SQL。calculate仍保留自己的校验，保证直接库调用安全。只要求队前拒绝能纯内存判断的轻量错误；SQL系数可表示性、来源支持及运行资源错误不冒称都能队前判定。将非法MA周期/正常参数对照并入原小型admission清单，不新增长样本或真实控制对象。

**需要review。** 工程调用顺序和复用位置要落回原两文，不需要新增业务规则或调整参数范围。

### 3. 失败后保留原异常，可能同时留下整份结果的引用

**原文。** LLD第1282行要求归还名额前释放body/result和任务返回值引用；第1284行要求保存并重抛同一个原异常对象，不改成ExceptionGroup，只清局部交接容器。没有说明原异常所带的失败栈怎样解除这些引用。

**当前实现依据。** `service.py:136—150`在result已经形成之后做字节计量，失败时保存并重抛原异常；`output/encoding.py:49—95`的失败栈含payload/result与编码器等局部变量。Python异常可以通过这些栈帧继续持有结果。App只是清空自己的result/error交接容器，不能因此证明更下层已结束函数中的大对象引用也解除。

**实际例子。** 结果已经算完，编码时发现超过5MB，服务正确报错并关闭连接。App归还名额后，上层仍保留原异常用于记录错误；如果异常还带着整份结果，就可能在下一请求开始时继续占内存。这里是结果引用问题，不是已证明的连接或SQL资源泄漏。

**建议。** 在原§12.4明确错误移交前的清理顺序：等worker及发送实际结束，保留原错误类型、原因、行号和清理附记，同时清除已结束异常栈及异常链中的结果/输出引用，随后按唯一出口归还名额。Python已有清理栈帧局部变量的方法，可保留异常及失败位置；不要靠GC、RSS下降或删除错误信息代替此要求。把“保留原异常但结果已不再被失败栈持有”的断言并入原错误/清理小例，不新增性能矩阵；确切实现和检查位置先写回LLD。

Python官方说明栈帧引用会延长局部对象寿命，`traceback.clear_frames`可清理失败栈的局部变量，正在执行/挂起的帧另有约束，因此处理时点必须在相关任务真实退出之后：[Python traceback文档](https://docs.python.org/3/library/traceback.html#traceback.clear_frames)、[frame.clear说明](https://docs.python.org/3/reference/datamodel.html#frame.clear)。这些文档经Context7核对；本轮未执行引用或内存实验。

**需要review。** 工程清理合同要补齐，不需要另选计算架构或重新决定原异常优先规则。
