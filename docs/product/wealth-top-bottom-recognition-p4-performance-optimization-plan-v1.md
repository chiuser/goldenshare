## 1. 目标、已有证据与边界

### 1.1 本次要解决什么

60分钟识别首次加载超过现有4秒限制。按8个已讨论方向，先明确每一步为什么存在、是否重复、是否超出本次查询需要，再逐项改动或设计测量。优化目标是减少实际请求总耗时，同时保持同一行情输入下的r4标签、事件编号、结构关系及下一根价格范围一致。

管理员已明确的取舍：

1. 简单、无昂贵操作的重复结构计算先保留，以逻辑简单为先。
2. 重复包装响应应精简。
3. 日历不应固定从1990年开始读取；范围应有实际用途。
4. 缓存看总收益，不看“命中了多少次”；复用检查若比节省的读取/计算更贵，应调整或取消。
5. 同次读取重复的逐文件/目录链接检查应优化。
6. 正常请求不反复验收完整数据集的全部列、顺序和类型。
7. 上证请求不得顺便验收其他指数；原来固定这种行为的测试应同步纠正。
8. 对同一批输入的重复键、对应关系、连续性检查按整条流程统一安排，避免各层重做。
9. 容易、明确能减少多余工作的修改先做完，不以新增计时工具、前后耗时对照或缓存实验作为前置；保留必要的正确性回归。精简完成后，再测剩余耗时和缓存收益，最后决定复杂改造。

## 4. 逐项调查与修改计划

### 4.1 方向1：简单结构复算——保留

**已核实。**`step`先在当前进度副本上推进；`_validate_step`另复制根前进度，再调用`_advance_followed_structures`核对旧结构事件/更新。该方法只遍历TOP/BOTTOM两槽，计算价格和状态，不访问文件/DB、不遍历价格取值范围。`history`每方向最多两个，不能称为不断增长的全历史复制。

**修改计划。**`calculator.py`、`snapshot_validation.py`、`types.py`和`MAIN_SPEC`本方向不改，不另写替代编号/状态校验。测量只观察已有step及校验段，不额外调用一次step获取观测值。若后来证明它实际占主导，再提交独立、保持原子发布和完整事件语义的方案；不能为减少函数调用而先把这里改复杂。

**验收。**原RC/PF人工样本、零柱、同根换远、结构后跟踪及错误不污染原进度等要求全部保留。不得用源码SHA检查代替事实回归；只审计规则和当前代码。此项不虚报“已有性能收益”。

### 4.2 方向2：重复构造、复制及校验

**当前事实。**冷加载时，`_load_series`保留逐根`points/events/structure_records`，先`_validate_entry`，再调用`_response(limit=len(processed))`创建完整内部响应用于校验；`build`随后按窗口调用`_response`。这部分2B仍保留。第一批5084ef939已经删除两个公开投影函数中的直接内部重建；上游完整验证、缓存交接重验及公开debug关联校验仍有效，不能继续把已删除的重建列作当前待改项。

**2A，第一批已完成的实现要求。**

1. 识别`build`同次新建并验证的`InternalXxmResponseDto`，直接交给`project_xxm_response`整理公开字段；删除投影里针对这个新模型的dump后重建。公开模型构造及原HTTP字段、debug投影、显示事件规则不变。
2. 投影入口明确接收完整内部模型，禁止把任意dict或未经验证的对象塞进来。检查实际全部调用方和测试；用正常模型构造代替`model_construct`等绕过办法。不得为适配旧测试增加通用输入兜底。
3. 对来自缓存的预测结果，先在query交接点完成一次完整内部验证；投影不再做第二次同样重建。`get_forecast`独立复制、坏缓存拒绝、出口失败不发布等原要求仍保持。
4. 不把内部模型设成“全都相信”，不取消缓存/恢复等外部交接的检查；仅移除已明确重复的同次对象重建。

**2B，需先测量的完整历史包装。**不能直接删`_load_series`内完整`_response`。当前`_validate_entry`没有覆盖`InternalXxmResponseDto.complete_facts`的全部跨记录条件：事件顺序、同根事件次序、事件/结构双向关联、显示窗口以外坏终态、来源时点、活动结构与最后点一致等。

先分别记录`_validate_entry`、完整历史`_response`、窗口`_response`、公开投影和`cache.put/_deep_size`耗时及处理根数；不得把共享父段与子段相加。若完整包装明显占用时间，才采用下面的代码方案：

- 在原`index_detail_xxm`服务目录增加`result_validation.py`，承接一次完整结果事实检查；对原生记录直接建立时间/事件/结构索引，不先复制成整份HTTP模型。
- 将上述跨记录条件逐条对应到该函数及反例用例；`_validate_entry`调用它，冷加载不再仅为检查而创建全量响应。只优化校验实现，不改变条件。
- 窗口`_response`仍只生成一次本次响应；历史asOf仍只恢复一次实际前缀，不按结构/日期分别回放；编号和被引用的旧结构不因裁窗丢失。
- 对原已通过的公开窗口模型只做该交接所需的检查，不以省时间为由取消schema或返回未经验证dict。

**测试设计。**正常/debug公共字段与编号逐项一致；非法旧结构即使不在当前500根仍被拒绝；一根上的旧结构消失/新钝化/反色多事件次序不变；历史asOf没有未来终态；缓存命中被篡改仍拒绝；输入对象和旧返回对象不被修改。原`test_rc93_window_does_not_hide_invalid_following_or_rebuild_per_record`等保留，不把删除校验后的“能返回”当作成功。

| `SeriesEntry.raw/processed` | 原始输入及已完成输入，源不变时避免重新读、追加时辨别已有前缀 |
| `calculator/points/events/structure_records` | 当前进度、逐根最终标签/事件/结构，避免每次从头识别 |
| `checkpoints` | 内存中的真实历史计算进度副本，用于恢复较早asOf；不是磁盘恢复文件 |
| `signature/open_dates/fingerprints` | 文件变化、相关日历、逐根来源身份及复用判断 |
| `InternalForecastResponseDto` | 已求得的下一根条件结果，避免再次求边界；正常/debug按同份事实投影 |
| `SharedLoads._pending` | 只让同时到达的请求共用正在执行的任务；完成后删除，不是结果长期缓存 |

这些位于后端当前进程的模块全局`_CACHE`及其对象中，不在浏览器、数据库或磁盘；不同进程各有一份，退出即丢失。现总上限64MiB/16条，不是每种各64MiB。当前预测命中前，仍会走历史进度读取、适用前提、EMA校准及未来日历，不能把forecast hit等同于“完全没有其他工作”。

第三轮优化读取轮完成后，后续测量须按计划窗口分清以下情况，不能混成一个“命中/未命中”：

- 文件信息及相关日历、完成时点都未变：复用已有raw和进度，避免重新读完整历史及step，但此前文件/日历检查仍发生。
- 文件被替换、实际内容相同：签名变化会触发重读；`revised`再根据真实行情前缀判断，不一定从头step，却仍有复制、重验和重新发布成本。现有原子替换用例就是同字节文件替换，不能把它全称为业务数据修订。
- 已完成端点或计划起点变化：源key改变，读取并从空重建本次最多N+1000根，即使实际数据尚未满R也不跨key增量。只有同一计划中迟到行情追加、已有前缀及实际首根未变时才只step追加部分；该分支仍有已有结果复制及全段检查，不能称为只做新增工作。
- 同一计划内历史数值真的改变：沿原revised规则重建本窗口进度；旧返回对象保持不变，不能为了省时忽略真实变化。它与上一项因计划首尾变化而重建是两种原因，不是只有数值修订才允许重建。

**为什么查修改时间。**现实现借文件大小、修改时间、设备/文件编号等，发现同名历史文件被替换，避免沿用错误旧结果。字段来自同次`stat`，删掉mtime/ctime元组元素不会自动减少文件检查。真正需要比较的是整段文件变化检查与缓存实际节省的工作。管理员已说明来源不是实时更新、DG按定时范围更新；本方案采纳这个事实，不把每次请求全面验证当成默认正确做法。本轮没有核验精确更新时刻，不据此编造定时失效时间。

**收益口径。**

`不用缓存的请求总耗时 − 使用缓存的请求总耗时 = 缓存的净收益`。

举例：缓存避免500ms工作，但仅为复用它新增2000ms检查，就净慢1500ms；命中率100%也不划算。两种方式共同需要的文件发现等成本不能再重复计入“缓存独有成本”。

**明确项完成后再做的对照设计。**先完成§6第1—3批及§14第三轮优化读取轮并review，A/B均使用相同N/截止及有界窗口下的读取、日历和投影实现；不为测量恢复已删除的检查或旧17年范围。以下“当前缓存流程”指保留本轮后的缓存检查刷新政策，不代表恢复精简前的多余操作。

### 4.8 方向8：顺序、重复、对应和连续性按流程各负其责

**已核实。**当前SQL统计target总数及distinct时间键，Python又建立价格/指标时间tuple比较，`assert_continuous`再做`sorted(set(actual))`及日历端点全量比较。它们并非所有检查都相同：重复时间、两条流错位和缺交易端点是三种不同问题，不能简单全删。

**代码方案。**

1. `_query_rows`删除仅为重复键检查的`count(DISTINCT...)`及不再需要的target_count/聚合空行处理。普通SQL无结果直接[]，不再生成一行全空占位后另行删除。
2. 方向7的`_validate_target_rows`对每次SQL返回的结果按严格降序检查时间键：遇到同键或乱序拒绝，不排序修正、不去重。完整历史保持原`rows.reverse()`后交付升序；分页先按原规则取最近limit根、判断has_more，再沿原`page_rows.reverse()`交付升序，next_cursor仍取本页最早时间。内部SQL检查顺序和调用方收到的顺序必须区分，不得将分页改成降序。对同一份SQL结果不再分别做一次set和一次排序检查；分页因数据不足按原规则扩大分区后产生的新SQL结果仍正常检查，不额外查询来证明检查次数。
