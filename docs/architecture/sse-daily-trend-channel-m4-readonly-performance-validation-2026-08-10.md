标的：`000001.SH`

## 1. 验收结论

以下为 2026-08-10 的原始验收结论。

M4 的数据正确性、金标一致性、纯计算性能、缓存内存、并发单飞和应用侧 API 性能已经通过。

严格的生产 API 性能门禁暂不标记为最终通过：当前代码尚未部署到生产 Web 进程，本机通过公网直连生产 PostgreSQL 时，默认窗口热 API P95 为 `222.314ms`，超过 `<100ms` 门禁；使用同一份 1600 行正式数据在同机数据库快照上执行相同 API，热 P95 为 `6.148ms`，全量 1600 行响应热 P95 为 `13.484ms`。分段结果证明差异来自跨公网数据库往返，不是趋势通道计算、缓存或 JSON 序列化。

当时的最终剩余门禁：代码部署后，在生产 Web 与生产 PostgreSQL 的实际拓扑中复跑冷/热 API 基准。该次验收未执行部署、生产写入、迁移或任务调度。

### 后续关闭记录（2026-09-05）

管理员已完成生产 Web 与生产 PostgreSQL 实际拓扑验证，确认接口运行无问题，并同意关闭本需求。该结论补齐了 2026-08-10 遗留的最终生产拓扑门禁，M4 状态更新为已通过并关闭。

本报告未取得该次验证的原始性能样本，因此不补写具体 P95 数值；下文保留 2026-08-10 的原始测量结果作为历史验收证据。

## 2. 只读边界与方法

正式库查询仅访问：

- `core_serving.index_basic`
- `core_serving.index_daily_serving`

正式 PostgreSQL 连接同时验证：

```text
default_transaction_read_only = on
transaction_read_only = on
```

性能基准使用当前工作区代码和 FastAPI `TestClient` 调用真实 route。正式库模式下，数据库连接强制 `default_transaction_read_only=on`；同机快照模式只将已读取并核验的 1600 行正式数据装入临时 SQLite 文件，接口、Query、calculator、缓存和响应 Schema 均使用生产实现。临时文件在基准结束后删除。

为排除无关成本，性能基准覆盖当前 route 但绕过鉴权依赖；鉴权合同已在 M3 API 测试中单独通过。

统计口径：

- 冷 API：30 次，每次请求前清空进程缓存。
- 热 API：预热一次后连续 100 次，不清缓存。
- 并发：10 个并发请求 × 10 轮，每轮前清缓存。
- P95：nearest-rank。
- 默认窗口：`limit=500`。
- 最大窗口：`limit=2000`，当前返回完整 1600 行。
