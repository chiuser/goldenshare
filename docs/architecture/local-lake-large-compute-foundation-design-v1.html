Local Lake DuckDB 计算执行壳与受控发布方案 v1

本方案定义 Local Lake 后续大体量计算任务的统一安全执行壳。计算内核优先交给 DuckDB； 本方案重点定义“哪些数据喂给 DuckDB、计算前必须检查什么、计算后如何审计、何时允许发布”。它先服务 stk_mins clean_next 前复权 candidate。derived、by-month research、MACD、MA、BOLL 只作为后续可复用方向记录，必须另开专项评审后才能进入开发。目标是：计算交给成熟内核， 正式写入必须受控发布，任何失败都不能污染正式数据。

1. 为什么要先做执行壳

前复权重建、MACD 全量计算、MA/BOLL 指标、by-month 重排，都属于大数据量任务。 真正不应该重复造的是计算内核：排序、过滤、join、列计算、Parquet 扫描和落盘应优先交给 DuckDB。 我们要自己守住的是业务链路：输入冻结、前置门禁、candidate 审计、正式发布、gate、下游重算通知和失败恢复。

已确认方向： 先做“DuckDB 计算内核 + 受控发布执行壳”，再在这个执行壳上实现前复权 qfq candidate。 第一期只做 qfq，不做 MACD、MA、BOLL，也不顺手改 derived/by-month 的现有实现。

执行壳第一版只做必要能力，不追求抽象成万能调度系统。

1.1 选型结论：不自研计算内核

本轮方案收口后，Local Lake 大计算不再以“自己写一套 compute 计算框架”为主线。 DuckDB 擅长本地 Parquet 扫描、join、排序、聚合、列式计算和 larger-than-memory 查询， 所以第一优先级是让 DuckDB 承担计算内核。我们只在 DuckDB 外围管理输入、门禁、候选产物、审计、发布和状态。

层级 由谁负责 原因
Parquet 扫描、join、过滤、列计算、排序、分组 DuckDB 这是 DuckDB 的核心能力，比我们自己写 Python 多进程更稳，也更容易 benchmark。
少量 metadata 读写、manifest、账本、小表 现有 PyArrow / pandas 小数据工具 这些文件体量小，不是主要性能风险；但不能拿小数据工具处理 44 亿行主数据。
输入快照、写锁、candidate 路径、audit、gate、queue、Kopia 备份 lake_console 自己负责 这是 Goldenshare 的业务一致性语义，通用计算框架不知道 clean_next 何时可被下游消费。
Dagster / Prefect / Spark / Dask / Ray 第一版不引入 它们会增加工程复杂度。当前是单机移动盘 Lake，先用 DuckDB 做计算内核更直接。
新的边界： 我们不做通用计算调度框架；我们做的是 DuckDB 计算任务的安全执行壳。 这个壳的职责是：喂对数据、先验门禁、后验审计、可解释状态、受控发布。 第一期落地范围只包含 stk_mins clean_next qfq candidate。

1.3 状态数据结构精确定义

本节是后续开发的字段基线。实现时不得只按字段名临时发挥；新增字段、改字段语义或调整状态流转， 必须先回到本节更新方案。下面的“硬约束”表示不满足时必须拒绝继续执行；“软约束”表示允许记录告警但不能静默吞掉； “可空策略”表示字段什么时候允许为空。

模型 字段 类型/形态 约束级别 含义与可空策略
ComputeRun run_id string 硬约束 一次计算运行的唯一 ID。创建后不可变，不允许为空。
ComputeRun job_type enum string 硬约束 任务类型，例如 stk_mins_qfq_clean_next。UI 不直接展示该枚举，必须映射成人话。
ComputeRun dataset_key string 硬约束 目标数据集，例如 stk_mins。不允许为空。
ComputeRun input_range object 硬约束 本次输入范围，至少包含 start_date、end_date、freqs。全量也必须显式记录范围，禁止用空值表达“全部”。
ComputeRun effective_config object 硬约束 本次实际生效的 DuckDB 与发布配置快照。必须来自 config.local.toml，用于事后解释和复现。
ComputeRun input_snapshot object 硬约束 输入数据快照，记录 raw/adj_factor/security_identity_map 等输入路径、行数或 checksum。发布前必须复核未漂移。
ComputeRun status enum string 硬约束 运行状态。只能按 8.1 状态机流转，不能跳到 published。
ComputeRun created_at, started_at, finished_at timestamp 硬约束 created_at 必填；started_at 在 running 后必填；finished_at 只在终态必填。
ComputeUnit unit_key string 硬约束 单个 DuckDB 执行单元唯一键。必须能从 run_id + continuity_key + publish_partition_key + bucket 稳定生成。
ComputeUnit continuity_key string 硬约束 连续性边界，例如 MACD 是股票代码维度，qfq 可以是目标分区或 bucket。不能破坏递推连续性。
ComputeUnit publish_partition_key string 硬约束 该 unit 最终贡献到哪个正式发布分区。用于失败定位和 candidate 汇总。
ComputeUnit input_paths, output_paths array string 硬约束 输入与候选输出路径。必须是 Lake root 下路径；禁止指向远程 DB 或生产系统路径。
ComputeUnit status, error_code enum string / nullable string 硬约束 status 必填；失败时 error_code 必填，成功时为空。
CandidatePartOutput candidate_part_path string 硬约束 临时候选文件或目录路径。只能位于 _tmp/duckdb_compute/<run_id>/candidate/**。
CandidatePartOutput row_count, byte_count integer 硬约束 候选产物行数和字节数。必须大于等于 0；审计阶段必须与实际 Parquet metadata 对齐。
CandidatePartOutput checksum string 软约束 第一版至少必须使用稳定元数据签名，包含文件列表、文件大小、mtime、row_count、schema fingerprint。内容级 checksum 可后置，但不得记录 checksum_method=not_available 后继续允许发布。
CandidatePartOutput status enum string 硬约束 staged 表示已生成；validated 表示行数/schema/checksum 校验通过；rejected 表示候选产物不可发布。
PublishPartition partition_key string 硬约束 正式发布分区唯一键。对于 clean_next 是 freq=*/trade_date=*；layer cutover 时也必须逐分区展开记录。
PublishPartition source_candidate_parts array string 硬约束 组成该正式分区的全部候选产物。缺一个就不能发布。
PublishPartition target_path string 硬约束 正式目标路径。发布前必须确认不在 _tmp，发布时必须经受控替换。
PublishPartition audit_status, publish_status enum string 硬约束 审计状态和发布状态分开记录。审计没过不能进入发布；发布没完成不能写 formal gate passed。

1.4 FormalGate 精确定义

FormalGate 是正式数据能否被下游读取的唯一门禁。它不是计算状态，也不是审计报告。 它只回答一句话：这个正式分区现在能不能读。

字段 类型/形态 约束级别 含义
partition_key string 硬约束 正式分区唯一键。当前 clean_next 为 freq=*/trade_date=*。
status publishing / passed / blocked 硬约束 passed 是唯一放行状态；其它状态下游必须拒绝读取。
write_revision string 硬约束 上游写入版本。用于解释 gate 对应哪次 raw/clean 写入。
publish_id string 硬约束 正式发布 ID。layer cutover 场景下，目标范围内每个 gate 行都必须写入同一个 publish_id，下游可用它判断 gate 是否对应本次发布。
gate_schema_version string / integer 硬约束 gate 文件结构版本。字段结构或状态语义变化时递增，普通发布不递增。
issue_count integer 硬约束 本分区审计问题数。passed 时必须为 0。
ledger_path string 硬约束 问题账本路径。blocked 时必须能指向可读账本。
message string 软约束 给开发者看的简短原因。UI 不得原样拿它当最终用户提示，必须经过文案映射。
gate 新鲜度红线： 下游不能只看 status=passed。qfq layer cutover 发布时，发布命令必须重写目标范围内所有 gate 行， 并写入本次 publish_id / write_revision。如果发现目标分区仍是旧 publish_id 或缺少 gate 行，必须视为未通过，不能读取。

1.5 问题账本精确定义

问题账本是“问题记录本”，不是 gate。gate 负责阻断或放行，账本负责解释为什么阻断。 同一个问题再次出现时，应更新同一条记录的 last_seen_at、last_seen_run_id 和 seen_count，不得无限制造重复问题行。

字段 约束 说明
ledger_schema_version 硬约束 账本 schema 版本。只有字段结构或状态语义变化时才递增；普通问题新增不改版本。
issue_key 硬约束 问题唯一键。必须由 layer + partition_key + issue_type + ts_code + trade_time 等稳定事实生成。
issue_state 硬约束 open 表示仍存在；resolved 表示本次审计覆盖范围内已消失。
severity 硬约束 严重程度。发布阻断问题必须为阻断级别，不能只写 warning 后继续发布。
issue_type 硬约束 机器可读问题类型。UI 不能直接展示该枚举，必须映射成人话。
expected_value, actual_value 软约束 用于解释问题。例如期望 241 根 1min bar，实际 240 根。没有明确数值时必须写原因。
action, reason 硬约束 给处理者看的建议动作和原因。不得只写异常栈。
first_seen_*, last_seen_*, resolved_* 硬约束 记录问题生命周期。再次发现同一问题只更新 last seen 与 seen count。

1.6 UI 文案映射红线

硬规则： 前端页面、CLI 面向运营的摘要、错误弹窗、状态卡片，不允许直接展示 Python 枚举、内部状态码、异常类名或底层字段名。 底层只能提供稳定 code；展示层必须通过 mapping 表转成人能理解的话。

实现时必须建立独立的文案映射模块或配置表。建议路径为 lake_console/backend/app/presentation/compute_messages.py 和前端等价的只读映射。 后端 API 可以返回 status_code、error_code、stage_code， 但同时必须返回已经映射好的 display_title、display_message、 recommended_action 和 severity_label。

API 展示字段 是否必填 说明
status_code, stage_code, error_code 按场景必填 机器稳定 code。只能用于诊断、筛选和文案映射，不得直接作为主提示展示。
display_title 必填 页面主标题，例如“候选数据审计失败”。
display_message 必填 给运营看的说明，必须说清当前影响，不允许只写异常栈。
recommended_action 必填 下一步建议，例如“查看问题账本后重新审计”。
severity_label 必填 人话严重级别，例如“阻断”“警告”“信息”。
diagnostic_detail 可空 折叠展示的技术细节，可以包含原始 code、路径和异常片段。
底层 code 页面标题 页面说明 建议动作
ComputeRun.planned 计划已生成 系统已经生成计算计划，尚未开始读取和计算数据。 确认输入范围、配置和预计影响后再启动。
ComputeRun.running 正在计算 DuckDB 正在生成候选数据，正式数据尚未被修改。 观察进度；如长时间无输出，查看当前 unit 和日志。
ComputeRun.audit_running 正在审计候选数据 系统正在检查 schema、行数、重复 key、完备性和业务规则。 等待审计完成；审计未通过时不要发布。
ComputeRun.publishing 正在发布正式数据 正式分区处于发布窗口，下游读取已被 gate 阻断。 不要中断进程；如失败，按发布收尾或 Kopia 恢复流程处理。
ComputeRun.published 发布完成 正式数据已经替换完成，门禁已放行。 按下游重建提示执行 derived、research 或 indicator 重建。
ComputeRun.blocked 已阻断 审计或发布条件未通过，系统已阻止正式数据继续被消费。 打开问题账本，先处理阻断问题，再重新审计或发布。
FormalGate.publishing 发布中，暂不可读 该分区正在发布或收尾，下游暂时不能读取。 等待发布完成；不要手工改 gate。
FormalGate.passed 可用 该分区已经通过审计，可以被下游读取。 无须处理。
FormalGate.blocked 不可用，存在阻断问题 该分区审计未通过或发布失败，不能被下游读取。 查看问题账本和推荐动作。
LC_COMPUTE_AUDIT_FAILED 候选数据审计失败 候选数据存在 schema、重复 key、行数、完备性或业务规则问题。 查看 audit ledger，先修复问题，不要发布。
LC_COMPUTE_QUEUE_FAILED 下游通知写入失败 正式数据可能已经变化，但指标或 derived 重建通知没有完整落盘。 保持 gate 阻断，修复 queue/source event 后执行发布收尾。

允许在详情页的“诊断信息”区域展示原始 code，但必须放在次级位置，且旁边要有中文解释。 用户主路径上只能看到人话结论，不允许看到 candidate_ready、LC_COMPUTE_INPUT_CHANGED 这类裸枚举。

2. 当前代码事实

代码审计后，当前已经存在一个非常关键的 gate：

manifest/stk_mins_quality/clean_next_partition_gate.parquet

它由 CleanNextPartitionGateService 管理，粒度是 freq + trade_date。它不是 compute 完成状态，而是正式 clean_next 分区能否被下游消费的放行证。

另外，stk_mins_sync 的 Sync Center 链路已经落地： plan -> Kopia 写前备份 -> raw sync -> clean_next refresh + gate -> 人工确认 -> derived 90/120 -> 人工确认 -> by-month research。 因此本方案不能另起一套与 Sync Center 脱节的锁、备份、gate 或下游重建链路。qfq 是一个改变 clean_next 价格语义的受控维护动作，必须复用或扩展现有 Sync Center 基础设施， 而不是绕过它。

现有能力 当前作用 在 DuckDB 计算执行壳中的定位
LakeJobLockService Sync Center 已使用 manifest/lake_jobs/active_task.lock 做全局运行锁，支持 heartbeat、stale 检测和人工释放 stale。 qfq/DuckDB 写正式 Lake 路径时必须复用或扩展这一把锁；禁止再创建第二套互不感知的全局写锁。
StkMinsPipelineRunState 记录 Sync Center 阶段、人工确认点、用户可读摘要和错误信息。 qfq 相关 UI/CLI 状态也应沿用“后端生成人话摘要”的原则，不能让前端直接展示底层枚举。
CleanNextPartitionGateService 记录正式 clean_next 分区 passed/blocked/publishing。 保留为 clean_next 正式消费门禁，不替换。
CleanNextRefreshService raw affected partition 更新后，重建 clean_next、审计、写 gate、通知 indicator queue。 日常分区刷新链路保留；qfq 发布后，若日常刷新继续写 clean_next，必须调用同一套 qfq 分区构建和受控发布能力，不能绕过 gate。
basic audit 检查 schema、非法价格结构、负数成交量成交额、身份映射、重复 key。 可复用为 clean_next candidate / formal 分区审计。
completeness audit 检查日内 bar 数不足/过多，写问题账本。 可复用为发布前后完备性门禁。
下游 require gate derived、by-month、indicator 读取 clean_next 前检查 gate passed。 必须继续保留。下游只认正式 clean_next gate，不认 compute candidate_part。
边界： 现有 clean_next gate 不是通用大计算 gate。它不记录 compute bucket，不记录 candidate audit，不记录 qfq factor snapshot， 也不表达所有 candidate_part 是否齐全。所以执行壳要补 run/candidate_part/publish manifest，但不能绕开现有 clean_next gate。
禁止双轨： 已实现的 stk_mins_sync 会在人工确认点释放并重新获取 Sync Center 锁；qfq layer cutover 不能照搬这种分段释放方式。 一旦进入正式发布窗口，必须从 gate 置为 publishing 到下游通知落盘和 gate passed 全程保持互斥， 否则会出现 daily sync 与 qfq 发布互相覆盖的窗口。

3. 核心原则

计算交给 DuckDB

优先用 DuckDB SQL 扫描 Parquet、join 因子、生成 candidate。

正式写入必须单点

只有 single writer/coordinator 可以发布正式路径、gate、manifest、state。

连续性优先

分桶不能破坏递推连续性。MACD 按股票分桶，不能按日期切。

3.1 计算分桶与发布分区不是一回事

计算分桶：为了并行和速度，例如 ts_code_bucket=17
发布分区：为了数据资产组织和查询，例如 freq=1/trade_date=2026-05-14

DuckDB 可以按 ts_code_bucket、月份或分区写出中间产物；但正式发布仍必须按目标分区组织。 如果目标分区是 freq + trade_date，最终就必须由 single writer 汇总所有 bucket 后再发布。

4. DuckDB 计算执行壳模型

本章只说明对象之间的关系，字段精确定义以第 1.3 到 1.6 为准。实现时不得只按下面摘要表临时发挥。

模型 含义 必须记录的字段
ComputeRun 一次大计算任务。 run_id, job_type, dataset_key, input_range, duckdb_threads, duckdb_memory_limit, status, created_at, finished_at
ComputeUnit 一个 DuckDB 可执行单元。由 planner 生成。 unit_key, continuity_key, publish_partition_key, input_paths, duckdb_sql_template, expected_output_role
CandidatePartOutput DuckDB 计算后的临时输出，可以是按 bucket、月份或目标分区写出的 candidate 文件。 run_id, unit_key, candidate_part_path, row_count, byte_count, checksum, status
PublishPartition single writer 要发布的正式分区。 partition_key, source_candidate_parts, target_path, audit_status, publish_status
RunManifest 运行账本。用于恢复、审计、解释和 UI 展示。 run.json, units.parquet, candidate_parts.parquet, publish_partitions.parquet, events.jsonl

4.1 全局写锁模型

qfq baseline 是 layer cutover，不允许和 raw sync、clean_next refresh、derived、by-month、indicator 写入并发。 写锁不是性能优化，而是防止正式路径、gate 和下游通知互相踩踏的安全边界。

字段 约束 含义
lock_path 硬约束 复用现有 Sync Center 锁：manifest/lake_jobs/active_task.lock，由 LakeJobLockService 管理。不得新增另一套互不感知的 duckdb_compute 全局锁。
lock_id, run_id, job_type 硬约束 说明谁持有锁，以及锁属于哪次运行。现有锁已记录 run_id / profile_key；qfq 如需 job_type 或 protected_paths，应扩展同一个锁 payload。
owner_pid, host 硬约束 用于人工排查当前进程是否仍然存在。现有实现字段为 owner_pid / owner_host，不得只写 run_id。
started_at, heartbeat_at, stale_after_seconds 硬约束 现有实现字段为 acquired_at / last_heartbeat_at / stale_after_seconds。heartbeat 超过 stale 阈值后只标记 stale 并阻断新写入，不自动释放。
protected_paths 硬约束 本次锁保护的正式路径，例如 research/stk_mins_by_date_clean_next、gate、ledger、downstream queue。
status 硬约束 active、stale、released。只有持锁 run 能释放自己的 active 锁；stale 锁必须人工确认后处理。
禁止自动释放 stale 锁： stale 只能说明进程长时间没有 heartbeat，不能证明正式数据处于安全状态。实现时只能阻断后续写入并提示人工检查。 现有 Sync Center 可以人工 release-stale，qfq 只能复用这种显式人工确认路径，不能后台静默释放。

4.2 输入快照与漂移检查

input snapshot 是“本次 candidate 到底基于哪些输入算出来”的证据。没有 input snapshot，后续无法判断 candidate 是否可发布，也无法复现结果。

字段 约束 含义
snapshot_id 硬约束 输入快照唯一 ID。写入 run.json.input_snapshot.snapshot_id。
source_items 硬约束 数组。每项包含 source_role、path、file_count、row_count、byte_count、schema_fingerprint、metadata_signature。
source_role 硬约束 例如 raw_stk_mins、adj_factor、security_identity_map、config、code_version。
metadata_signature 硬约束 第一版至少由文件相对路径、大小、mtime、row_count、schema fingerprint 生成。内容级 checksum 可后置，但发布前必须可复核元数据未漂移。
code_version, config_hash 硬约束 记录代码版本和生效配置 hash。配置变化时不得复用旧 candidate。
发布前必须复核： publish 命令必须重新计算输入 snapshot 的 metadata signature。任何输入漂移都必须写 LC_COMPUTE_INPUT_CHANGED，本次 candidate 作废，不能继续发布。

6. 分桶规则

本节经过当前代码核验后补细。现有 research/stk_mins_by_symbol_month 使用 stable_bucket(ts_code) 做月度重排；derived 与 indicator 读取 clean_next 前会检查 clean_next_partition_gate。因此 DuckDB 计算执行壳的分桶必须同时满足： 计算连续性不被切断、正式发布分区完整、下游 gate 语义不被绕开。

本期范围提醒： 下表中的 MACD、MA、BOLL、derived、by-month 仅用于说明未来复用执行壳时的分桶原则， 不代表第一期要开发这些任务。第一期只实现 qfq。
任务 连续性约束 推荐计算分桶 正式发布分区
qfq clean_next candidate 逐行变换，不递推；依赖 identity map 与 adj_factor snapshot。 全量用 freq + trade_month + ts_code_bucket；小窗口可用 freq + trade_date + ts_code_bucket。 freq + trade_date
90/120 derived 同一股票同一天的分钟序列不能切碎。 全量用 trade_month + target_freq + ts_code_bucket；小窗口可用 trade_date + target_freq + ts_code_bucket。 target_freq + trade_date
by-month research 不递推，但目标就是按月和 bucket 重排。 freq + trade_month + bucket freq + trade_month + bucket
MACD full / incremental 同一 ts_code + freq 必须按时间递推。 freq + ts_code_bucket freq + trade_date；state 由 single writer 统一推进。
MA / BOLL 滑窗依赖历史窗口，边界必须带 warmup。 freq + ts_code_bucket，并明确 warmup 策略。 freq + trade_date
红线： 递推型指标不能按日期分桶。MACD 如果按日期切，EMA state 会断，结果即使写出来也不可信。

6.1 分桶先看依赖关系，不先看速度

分桶不是为了“切得越碎越快”。正确顺序是：先找连续性依赖，再找发布分区，再决定并行粒度。 如果一个计算单元的依赖被切碎，速度越快，错误越快。

核验项 必须满足的规则 不满足时的后果
continuity_key 同一连续性键必须只归属一个 DuckDB compute unit。MACD 是 ts_code + freq；90/120 是 ts_code + trade_date + source_freq。 递推 state 断裂、K 线聚合跨错边界，结果不可用。
publish_partition_key 同一个正式分区可由多个 candidate_part 贡献，但只能由 single writer 在 candidate_part 全齐后发布。 部分 bucket 先发布会导致正式分区半成品。
bucket_key 股票维度分桶统一使用 canonical/latest ts_code，不能使用旧代码或源代码混分。 同一股票历史被分到多个 bucket，指标连续性与 by-month 查询都会被打碎。
bucket_count 同一层级一旦发布，bucket_count 必须视为 layout 版本的一部分；变更必须创建新 layout 或全量重建。 同一路径下新旧 bucket 混用，查询和增量都无法可靠解释。
输入快照 qfq 必须记录 adj_factor 快照标识或 checksum；identity map 也必须记录版本或文件 checksum。 同一次 run 中前后使用不同因子或身份账本，会出现不可复现结果。

6.2 每类任务的分桶判定

任务类型 允许并行切分 禁止切分 发布完整性判断
qfq 行级变换 全量推荐按 freq + trade_month + ts_code_bucket 切；日常增量可按 freq + trade_date + ts_code_bucket 切。 不允许不同 compute 使用不同 adj_factor 快照或不同 identity map。 同一 freq + trade_date 下所有预期 bucket 完成，且行数、重复 key、schema、完备性审计通过；月级 unit 也必须拆成日级发布分区审计。
90/120 聚合 全量推荐按 trade_month + target_freq + ts_code_bucket 切；日常增量可按 trade_date + target_freq + ts_code_bucket 切。 不允许把同一 ts_code + trade_date 的源分钟序列切到多个 compute。 目标 target_freq + trade_date 所有 bucket 完成，聚合窗口符合交易时段规则；月级 unit 只降低调度开销，不改变日级发布粒度。
by-month 重排 可按 freq + trade_month + bucket 切；这是布局重排，不是计算递推。 不允许跳过源 clean_next gate 或 derived 源完整性检查。 月内所有源分区存在且通过 gate；目标 bucket 行数合计等于源行数。
MACD / EMA 类递推指标 只能按 freq + ts_code_bucket 切；一个股票一个频率的时间序列必须完整有序。 禁止按日期切；禁止多个 compute 同时推进同一 ts_code + freq state。 结果按 freq + trade_date 发布前，state 必须和最后一个已发布时间点一致。
MA / BOLL 滑窗指标 按 freq + ts_code_bucket 切，窗口起点必须带 warmup。 禁止只读目标日期窗口而不读 warmup 历史。 输出日期范围可小于输入日期范围，但必须记录 warmup_start。

6.3 ComputeUnit 必须可解释、可复现、可比对

unit_key = job_type + dataset_key + input_snapshot_key + continuity_key + compute_window_key + bucket_key
publish_partition_key = formal target partition, such as freq=1/trade_date=2026-05-14
write_revision = run_id + unit_key + input_checksum + code_version

unit_key 必须稳定。相同输入、相同代码版本、相同配置生成的 compute units 必须一致。 否则失败后无法解释“到底哪一块算过、哪一块没算、哪一块需要重跑”。

6.4 不要把 compute unit 数量做爆

以全量股票分钟线为例，如果按 freq + trade_date + bucket 直接生成任务， 5 个源频率、约 4,000 多个交易日、32 个 bucket，会产生几十万个 compute units。 这会让调度、manifest、进度、错误处理本身变成负担。

全量任务原则： 计算窗口可以按月或按较大日期窗口组织，正式发布仍按 freq + trade_date 做日级分区。 换句话说：DuckDB 可以一次算一个月内某个 bucket 的数据，但 single writer 必须按每天逐个审计和发布。

7. DuckDB / Coordinator 契约

7.1 DuckDB compute 只能做什么

  1. 读取正式输入或 candidate 输入。
  2. 执行 coordinator 生成的 SQL / compute unit。
  3. 写入 _tmp/duckdb_compute/<run_id>/candidate_parts/<unit_key>/。
  4. 写 candidate_part manifest。
  5. 上报 progress。

7.2 DuckDB compute 禁止做什么

  1. 禁止写正式数据路径。
  2. 禁止写 clean_next_partition_gate。
  3. 禁止推进 indicator state。
  4. 禁止写 downstream queue。
  5. 禁止删除其它 run 或其它 unit 的临时产物。

7.3 single writer 必须做什么

  1. 确认所有 required candidate_part 都完成。
  2. 按目标 publish partition 汇总 candidate_part。
  3. 执行 schema、行数、重复 key、完备性、checksum 审计。
  4. 发布前创建必要 Kopia snapshot。
  5. 写入正式路径。
  6. 写 gate、manifest、downstream queue、state。

8. Gate / Audit 分层

这里必须把名字说清楚，避免后续又混在一起。

层级 文件或模型 用途 是否已有实现
run / candidate_part manifest manifest/duckdb_compute/runs/<run_id>/... 记录 DuckDB 计算运行、compute units、candidate_parts、events。它不是下游消费 gate。 待实现
candidate audit manifest/duckdb_compute/runs/<run_id>/audit_ledger.parquet 发布前检查 candidate 是否可发布。 待实现
formal clean_next gate manifest/stk_mins_quality/clean_next_partition_gate.parquet 正式 clean_next 分区是否允许被 derived / research / indicator 消费。 已有，必须复用
indicator state gate manifest/indicator_state/... 指标 state 只能在结果写入成功后推进。 已有局部实现

8.1 状态模型与错误提示

大计算链路很长，不能只靠命令行最后一句成功或失败。状态要服务三件事： 定位失败点、阻止脏数据发布、给人一个明确的下一步动作。

对象 状态枚举 状态文件 说明
ComputeRun planned, running, compute_completed, audit_running, prewrite_backup, publishing, published, blocked, failed, cancelled manifest/duckdb_compute/runs/<run_id>/run.json 描述整次大计算处于哪个阶段。它是运行状态，不是下游消费 gate。
ComputeUnit pending, running, succeeded, failed, skipped units.parquet 定位具体失败的计算单元，例如某个 freq/trade_date/bucket。
CandidatePartOutput staged, validated, rejected candidate_parts.parquet 记录 DuckDB compute 输出的临时 candidate_part 是否完整、行数与 checksum 是否匹配。
PublishPartition pending, candidate_ready, audit_passed, publishing, published, blocked, failed publish_partitions.parquet 记录正式分区发布状态。只有 published 后才允许写正式 gate passed。
FormalGate publishing, passed, blocked manifest/stk_mins_quality/clean_next_partition_gate.parquet 现有正式消费 gate。下游 derived / research / indicator 只认它。

8.1.1 状态机与状态信息流转图

状态机是开发门禁，不是展示装饰。实现时必须按下面的流转写状态，不能为了“方便收尾”跳状态。 尤其注意：正式 gate 的 passed 必须是最后放行动作，不能早于下游通知和发布记录。

流转 触发条件 必须写入的信息 禁止事项
planned -> running 用户确认执行，获取写锁，输入快照与配置快照已落盘。 run.json.started_at、生效配置、输入快照。 禁止没有 input snapshot 就开始计算。
running -> compute_completed 全部 ComputeUnit 成功，候选产物已写出。 units.parquet、candidate_parts.parquet、行数和 checksum/metadata 签名。 禁止 unit 失败时进入审计。
compute_completed -> audit_running 开始候选层审计。 审计范围、审计规则版本、candidate root。 禁止审计直接修改正式数据。
audit_running -> blocked 发现 schema、重复 key、完备性、qfq 价格或输入漂移问题。 audit_ledger.parquet、errors.parquet、人话处理建议。 禁止带 open 阻断问题继续发布。
audit_running -> prewrite_backup 候选审计通过，准备创建写前备份。 备份范围、目标路径、候选路径、发布计划写入 publish_partitions.parquet。 禁止候选审计未通过就创建发布备份。
prewrite_backup -> publishing Kopia 写前备份成功，拿到 kopia_snapshot_id。 目标分区 gate 写为 publishing，发布记录写入备份 ID。 禁止备份失败后进入 formal replace；禁止还没写 gate publishing 就替换正式路径。
publishing -> gate passed -> published Kopia 备份、正式替换、formal audit、source event / queue 全部成功。 publish record、Kopia snapshot id、downstream queue/source event、final gate。 禁止 queue/source event 之前写 gate=passed。
任意阶段 -> failed/cancelled 计算异常、备份失败、发布失败、用户取消。 错误码、失败阶段、已影响路径、推荐恢复动作。 禁止失败后把状态改成成功；禁止状态失败回滚已完成业务数据。

8.1.2 错误记录必须能直接指导人处理

错误不能只写 Python exception。每条错误至少包含：

error_code
severity
stage
run_id
unit_key
publish_partition_key
source_paths
message_for_human
technical_detail
recommended_action
sample_rows_or_paths
错误码 触发条件 给人的提示
LC_COMPUTE_MISSING_CANDIDATE_PART 某个发布分区缺少预期 candidate_part。 不要发布；检查失败 unit，重跑该 run 或重新生成 candidate。
LC_COMPUTE_INPUT_CHANGED 发布前发现输入 checksum 与 planner 阶段不一致。 输入数据已变化，本次 candidate 作废，需要重新 plan。
LC_COMPUTE_AUDIT_FAILED schema、重复 key、行数、完备性或 qfq 合理性检查失败。 不发布；查看 audit ledger，先处理具体问题。
LC_COMPUTE_BACKUP_FAILED Kopia 写前备份失败。 不进入正式替换；修复备份配置或空间后重试。
LC_COMPUTE_PUBLISH_FAILED atomic replace 失败或正式分区发布后校验失败。 gate 不得 passed；检查 tmp/backup，必要时从 Kopia 恢复。
LC_COMPUTE_QUEUE_FAILED 下游 source event 或 indicator queue 写入失败。 formal gate 保持 publishing/blocked，修复 queue 后重新执行发布收尾。

8.2 下游重建需求模型

当前代码里的 indicator queue 主要服务 MACD，不足以表达 qfq 发布后 derived、by-month、indicator 这几类下游资产的统一失效范围。因此 qfq 发布不能只写 MACD queue，还必须写一份通用 DownstreamRebuildRequirement 账本。它不自动执行重建，只说明哪些下游资产已经失效、应该按什么范围重建。

字段 约束 含义
requirement_id 硬约束 重建需求唯一 ID，由 source_layer + source_publish_id + target_layer + scope 稳定生成。
source_layer, source_publish_id 硬约束 触发失效的上游层与发布 ID，例如 research/stk_mins_by_date_clean_next 与本次 qfq publish_id。
target_layer, target_task 硬约束 需要重建的下游层和任务，例如 derived/stk_mins_by_date、research/stk_mins_by_symbol_month、indicator/macd。
scope_type, freqs, start_date, end_date 硬约束 重建范围。全量 qfq baseline 必须明确写出频率和日期范围，禁止用空值表达“全部”。
status 硬约束 pending、running、done、blocked。本期 qfq 只负责写 pending。
reason_code, human_message 硬约束 机器原因和人话说明。页面展示必须使用 human_message，不得直接显示内部枚举。 
建议路径：
manifest/downstream_rebuild_requirements/stk_mins.parquet

qfq baseline 发布后至少写入：
1. target_layer=derived/stk_mins_by_date, target_task=rebuild_90_120_from_clean_next
2. target_layer=research/stk_mins_by_symbol_month, target_task=rebuild_by_month_from_clean_next_and_derived
3. target_layer=indicator/*, target_task=review_and_recompute_after_qfq
gate passed 前必须完成下游需求落盘： 如果下游重建需求写入失败，formal gate 必须保持 publishing 或 blocked， 不能让下游读到已经变化但没有重建提示的 clean_next。

9. 发布顺序

以 clean_next 正式发布为例，顺序必须固定：

1. candidate_parts 全部完成
2. coordinator 汇总 candidate_part
3. candidate audit passed
4. Kopia snapshot 当前正式 clean_next / gate / ledger / manifest / downstream requirement
5. 写 formal gate = publishing
6. atomic replace 正式分区
7. formal audit passed
8. 写 downstream source event / indicator queue / derived rebuild requirement
9. 写 formal gate = passed
10. 下游才允许消费
为什么 queue 要在 final gate passed 之前： 如果 gate 先 passed，但 queue 或 source event 写失败，下游会看到一个“已通过但没有重算通知”的分区。 所以正式 gate 最终放行必须放在下游通知成功之后。

9.1 容错边界与恢复动作

第一版不做自动 checkpoint / replay。原因是架构规则要求避免重新引入旧式 checkpoint/acquire/replay 语义。 但必须把状态和产物留清楚，让人可以安全判断：哪些没有动正式数据，哪些已经进入发布窗口，下一步该重跑还是该恢复。

阶段 正式数据是否可能变化 必须保留的证据 安全处理方式
planner / compute 阶段 不会。 run.json, units.parquet, events.jsonl, DuckDB compute 日志。 修复问题后新建 run 重算；旧 tmp 可人工清理。
candidate audit 阶段 不会。 audit_ledger.parquet, candidate path, failed partition list。 不发布；先修 audit 问题，再重新生成 candidate。
prewrite backup 阶段 不会。 Kopia snapshot id 或失败原因。 备份失败则停止，不进入 replace。
formal gate = publishing 后 即将变化或正在变化。 旧 gate 行、新 gate publishing 行、backup path、target path、tmp path。 下游会被 publishing 阻断；必须完成发布收尾或从备份恢复后再改 gate。
atomic replace 后、queue 前 已经变化。 发布后行数、checksum、formal audit 结果。 不得直接 gate passed；queue/source event 成功后才能最终放行。
queue 成功后、gate passed 前 已经变化。 source event id、queue id、final gate status。 只差 final gate；如果写 gate 失败，下游仍被阻断，可重新执行发布收尾。

9.1.1 状态写入失败不能污染正式数据

状态和 gate 写入失败时，不能回滚已经成功写入的业务数据，也不能假装成功。 正确做法是让正式 gate 保持 publishing 或 blocked，让下游停止消费，并把错误写入 errors.parquet / events.jsonl。这和生产侧“状态失败不得回滚业务数据”的总原则一致。

9.1.2 UI / CLI 进度必须按阶段说人话

[duckdb_compute] run=... stage=compute unit=12/320 partition=freq=1/trade_date=2026-05-14 bucket=7 rows=1,230,000
[duckdb_compute] run=... stage=audit partition=freq=1/trade_date=2026-05-14 status=passed rows=5,512,000
[duckdb_compute] run=... stage=publishing partition=freq=1/trade_date=2026-05-14 backup=snap-xxx
[duckdb_compute] run=... stage=blocked error_code=LC_COMPUTE_AUDIT_FAILED ledger=...

进度输出必须包含阶段、当前 partition、当前 bucket、已完成数量、总数、关键行数和错误码。 不允许只输出“running”或长时间无输出。

9.2 发布模式：分区发布 vs 层级切换

二次审计后补充：现有 replace_directory_atomically 只能保证单个文件或单个目录替换尽量原子， 不能保证一次大 run 中所有分区“一起成功或一起失败”。因此 DuckDB 计算执行壳必须区分两种发布模式。

发布模式 适用场景 正式 gate 规则 失败影响
partition_publish 日常增量：某个 freq + trade_date raw 更新后刷新对应 clean_next。 只改受影响分区 gate。 单分区失败只阻断该分区，下游其它已通过分区仍可读。
layer_cutover_publish qfq baseline、schema 语义整体切换、全量重建。 先把全量目标分区 gate 标记为 publishing，阻断下游；完整切换和 queue/source event 成功后，再批量写 passed。 失败时全量目标保持 publishing/blocked，不能让下游读到新旧语义混合数据。

9.2.1 qfq baseline 必须走 layer cutover

1. 通过 LakeJobLockService 获取现有 Sync Center 全局 Lake 写入锁，禁止 raw sync / clean_next refresh / derived / indicator 并发写入。
2. 记录 input snapshot：raw partitions、adj_factor、security_identity_map、代码版本、配置。
3. 生成完整 qfq candidate root，例如 _tmp/duckdb_compute/<run_id>/candidate/research/stk_mins_by_date_clean_next。
4. 对 candidate 做全量 audit：schema、行数、duplicate key、完备性、qfq factor coverage、样本价格核验。
5. Kopia 备份正式 clean_next root、gate、quality ledger、downstream requirement、indicator queue/source event。
6. 将所有目标 clean_next gate 批量置为 publishing，阻断下游。
7. 同文件系统内 root-level replace：candidate root -> research/stk_mins_by_date_clean_next。
8. 写下游 queue/source event 与 derived rebuild requirement。
9. 批量写 gate=passed。
10. 释放锁。

如果第 7 步之后、第 9 步之前失败，正式数据可能已经完成替换，但 gate 仍不是 passed， 下游会被阻断。此时只能执行“发布收尾”或“从 Kopia 恢复”，不能直接手改 gate。

10. qfq 作为第一落地场景

qfq clean_next candidate 是最适合验证执行壳的第一场景：数据量大、计算可并行、没有 MACD 那种跨日递推 state， 但又足够重要，能检验临时目录、审计、发布和 gate 设计是否可靠。 

raw_tushare/stk_mins_by_date
+ raw_tushare/adj_factor
+ manifest/security_identity/security_identity_map.parquet
-> DuckDB compute
-> qfq candidate_parts
-> candidate audit
-> publish to research/stk_mins_by_date_clean_next
-> clean_next_partition_gate
-> downstream rebuild requirement（后续 derived / by-month / MACD 专项再处理）

qfq 计算本身继续遵守：

qfq_ratio = adj_factor(ts_code, trade_date) / latest_adj_factor(ts_code)
open/high/low/close/vwap *= qfq_ratio
vol/amount/exchange 不调整
qfq 全量切换不能按分区各自 passed。 qfq 会改变整个 clean_next 的价格语义。如果全量切换过程中一部分分区已经是前复权价，另一部分分区仍是源站除权价， 下游 derived / by-month / indicator 会读到混合价格体系，结果不可解释。因此 qfq baseline 必须采用 layer-level cutover： 先生成完整 candidate，完整审计通过后，再统一进入正式切换。

11. 失败与恢复

失败点 结果 恢复方式
compute 失败 只留下 candidate_part 临时产物，正式路径不变。 重跑失败 unit 或整个 run。
candidate audit 失败 不发布。candidate 保留用于排查。 修复问题后重新 build 或重新 audit。
Kopia snapshot 失败 不进入正式发布。 修复备份配置后重试 publish。
atomic replace 失败 正式路径不得进入半成品。gate 不得 passed。 检查 backup/tmp，必要时从 Kopia 恢复。
downstream queue 失败 formal gate 保持 publishing 或 blocked，不放行。 修复 queue 后重新执行 publish finalization。

12. 定量 sizing 与初始参数

本节把“用几个计算核心、bucket 怎么分、速度怎么估”落到可执行口径。当前本机核验到的硬件基线： Apple M3 Max，14 核（10 性能核 + 4 能效核），内存 36GB；Lake 盘当前约 3.7TiB，总可用约 2.9TiB。 这些数字只用于本地 Lake 计算 sizing，不代表生产部署参数。

12.1 第一版执行拓扑

角色 数量 职责 为什么这样配
coordinator 1 生成计划、维护 run manifest、生成 DuckDB SQL、汇总状态。 必须单点，否则状态解释会混乱。
DuckDB compute connection 默认 1 个 DuckDB 任务；内部线程从 4 起步，压测通过后再试 6，第一版上限 8。 用 DuckDB 扫描 Parquet、join 因子；第一期只计算 qfq candidate，只写 _tmp。derived / indicator 不在本期实现。 DuckDB 自带并行和 out-of-core 能力，比我们自己开多个 Python compute 更可控；并发主要通过 DuckDB threads 和 memory_limit 调整。
single writer 1 合并 candidate_part、审计、备份、正式发布、写 gate、写 queue。 正式路径只能有一个写入者，这是硬约束，不随机器核心数增加。
audit runner 0 或 1 第一版先由 single writer 串行审计；后续如审计成为瓶颈，再单独拆。 先保证正确性，避免审计与发布状态乱序。

12.2 bucket 数量建议

参数 默认值 适用范围 调整规则
bucket_count 32 第一期用于 qfq 计算 bucket；未来若 by-month、indicator 迁入执行壳，也必须沿用稳定分桶原则。 保持和当前配置一致。约 5,500 只股票时，平均每 bucket 约 170 只股票。
duckdb_threads 4 DuckDB 单任务内部并行线程数。 先用 4 跑 2026-03 样本；若 CPU 低于 60%、内存低于 24GB、IO 未打满，再试 6，第一版硬上限 8。
duckdb_memory_limit 24GB DuckDB 查询内存上限。 本机 36GB 内存下，给系统、文件缓存、Python 进程和 UI 留出余量；benchmark 发现 swap 增长时下调。
duckdb_temp_directory _tmp/duckdb DuckDB spill 临时目录。 必须在 Lake 盘上，不能落到本机系统盘；任务结束后由明确 cleanup 流程处理。
target_part_size_mb 256 大文件写入目标大小参考。 正式分区仍以查询布局为主，不为了凑文件大小破坏分区语义。
bucket_count 是布局版本，不是运行参数。 如果一个正式层已经按 32 bucket 发布，不能下一次随手改成 64 并写到同一路径。 真要改，必须新 layout 或全量重建。

12.3 qfq 全量重建的粗略工作量

以当前已清洗出的分钟线规模估算，clean_next 量级约 44 亿行。qfq 是逐行向量计算， 主要成本是读取 raw/clean 输入、查因子、计算 OHLC/VWAP、写出正式 clean_next candidate。

项目 估算值 说明
全量行数 约 44 亿行 按当前 clean_next 全量量级估算。
单日全频行数 约 190 万到 210 万行 取决于股票数量、盘后数据、停牌和历史阶段。
单日单 bucket 行数 约 6 万行 按 32 bucket 粗略均分。
全量 compute units 按月窗口：约 freq_count × month_count × bucket_count 比按日窗口少一个数量级以上；发布仍按日分区。
初始全量耗时目标 DuckDB threads=4：先按 3 到 8 小时量级评估 真实瓶颈可能是外置盘 IO，不是 CPU；必须用样本 benchmark 校准。

12.4 必跑 benchmark，不凭感觉调参

正式全量前必须先跑一个固定样本，得到本机实际吞吐：

样本窗口：2026-03
样本频率：1,5,15,30,60
bucket_count：32
duckdb_threads：4
duckdb_memory_limit：24GB
记录指标：source_rows, output_rows, elapsed_seconds, rows_per_second, peak_memory, tmp_bytes, final_bytes, audit_seconds

调参规则：

  1. 如果 CPU 长期低于 50%，IO 也没打满，可以把 DuckDB threads 从 4 提到 6。
  2. 如果 swap 明显增长或系统卡顿，DuckDB threads 立即降回 2 或 4，并降低 memory_limit。
  3. 如果 IO 等待明显，增加 threads 没用，应降低并发或调整 SQL 写出批次。
  4. 如果 single writer 成为瓶颈，不能增加 writer，只能优化 candidate_part 合并和写入批大小。
  5. 如果某个 bucket 明显倾斜，先记录 bucket skew，不允许临时改 bucket_count 写回同一路径。

12.5 DuckDB 执行模型

第一版不再优先实现 Python 多进程计算框架。大批量列式计算由一个受控 DuckDB 连接执行， 通过 threads、memory_limit、temp_directory 控制资源。 Python 负责构造 SQL、记录状态、触发审计、发布路径和写 gate。 

processes:
  coordinator: 1
  duckdb_compute_connection: 1
  single_writer: 1

duckdb_settings:
  threads: 4
  memory_limit: 24GB
  temp_directory: _tmp/duckdb

memory_budget:
  duckdb_target: <= 24GB
  writer_target: 2GB ~ 4GB
  os_cache_and_margin: >= 12GB

12.6 二次审计补充的硬门槛

下面这些不是优化项，而是进入编码前必须写进实现 checklist 的门槛。少任何一条，后面全量任务都有可能跑很久但产物不可用。

门槛 必须怎么做 原因
流式读写 大计算禁止使用 read_parquet_files() / pandas 全量读入；优先使用 DuckDB 直接扫描 Parquet 并写出 candidate。只有 DuckDB 不适合的局部小环节，才使用 PyArrow batch streaming。 44 亿行级别任务如果全量读内存，必然爆内存或被系统 kill。
输入冻结 run 开始时记录 raw、adj_factor、identity map 的 snapshot/checksum；发布前复核没有变化。 如果 raw 同步或因子更新同时发生，candidate 会混用不同输入版本。
全局写锁 qfq baseline 期间必须占用 Lake 写入锁；禁止 sync center、raw sync、clean_next refresh、derived、indicator 并发写入。 否则正式路径、gate、queue 会互相踩踏。
磁盘预检 全量 qfq candidate 前必须估算 candidate_bytes + tmp_candidate_part_bytes + backup_metadata + safety_margin，空间不足直接拒绝。 candidate 需要接近一份 clean_next 体量的额外空间，不能跑到中途才爆盘。
因子覆盖 每个 ts_code + trade_date 必须能找到有效 adj_factor 和 latest factor；缺失、重复、非正数都进入 block ledger。 前复权价格的正确性完全依赖因子覆盖，不能默认填 1。
数值精度 OHLC/VWAP qfq 结果使用 double，不做两位小数截断；vol/amount/exchange 原样保留。 截断会污染技术指标；成交量和成交额不是复权价格字段。
排序与确定性 正式输出必须稳定排序：ts_code, trade_time；同输入重复运行，输出 row count、key set 和 checksum 必须一致。 便于审计、增量对比、失败恢复和后续指标复算。
候选层保留策略 candidate 失败时保留；candidate 发布成功后保留到人工确认或 Kopia 备份完成，再由明确命令清理。 不能自动删掉唯一可排查现场，也不能让 _tmp 无限膨胀。
运行锁 stale heartbeat 超时只标记 stale，不自动释放、不自动继续发布；必须人工确认后释放或恢复。 防止进程假死时另一个任务误判空闲，造成双写。
测试样本 至少覆盖 2026-03 样本、一个除权因子变化样本、一个北交所/代码映射样本、一个空/停牌分区样本。 只跑顺滑样本无法证明真实边界正确。

13. 配置建议

DuckDB 与发布执行壳相关的所有运行参数，都必须以 lake_console/config.local.toml 为唯一事实源。这里说的不是单个 duckdb_threads，而是包括 DuckDB 资源、compute bucket、 writer 数量、进度节奏、stale heartbeat、重试次数、tmp/spill 路径等所有会影响执行行为的配置。 环境变量不得作为长期配置入口；如后续确实需要临时覆盖，必须在代码和日志里明确记录覆盖来源，并在 ComputeRun 中落下最终生效值。

该配置文件是本地文件，禁止提交到仓库。后续实现时，应同步更新 lake_console/config.local.example.toml，保证示例配置、读取代码和本文档字段一致。

当前实现状态： LakeConsoleSettings 与 lake_console/config.local.example.toml 已加入 DuckDB / compute 执行壳字段。进入后续编码时，执行壳相关参数仍不得散落在命令行参数、 环境变量或硬编码默认值中。 
# lake_console/config.local.toml
duckdb_threads = 4
duckdb_memory_limit = "24GB"
duckdb_temp_directory = "_tmp/duckdb"
compute_bucket_count = 32
compute_max_active_writers = 1
compute_progress_interval_seconds = 2
compute_stale_heartbeat_seconds = 1800
compute_max_unit_retries = 1
配置文件字段 建议默认值 说明
duckdb_threads 4 DuckDB 单任务内部并行线程数。当前 M3 Max + 36GB 内存下从 4 起步；样本 benchmark 通过后最多试 6，第一版硬上限 8。
duckdb_memory_limit 24GB DuckDB 查询内存上限，避免把整机内存打爆。
duckdb_temp_directory _tmp/duckdb DuckDB spill 目录，必须落在 Lake 盘，不允许占用本机系统盘。
compute_bucket_count 32 股票代码稳定分桶数量，保持和现有 research bucket 思路一致；一旦发布就是 layout 版本。
compute_max_active_writers 1 正式发布 writer 数必须固定为 1。
compute_progress_interval_seconds 2 控制进度输出节奏，避免刷屏。
compute_stale_heartbeat_seconds 1800 DuckDB compute 或 coordinator 超过 30 分钟没有 heartbeat，标记为 stale；不自动发布。
compute_max_unit_retries 1 compute unit 最多重试 1 次；重复失败则 run blocked，避免无限重试掩盖数据问题。
配置门禁： 新增任何影响 DuckDB 计算、candidate 写入、正式发布、审计、gate 或 queue 的参数时， 必须先加入 config.local.toml 配置模型和示例文件，再进入实现；禁止在代码里散落硬编码默认值， 也禁止让命令行参数成为长期事实源。

15. 红线

  1. compute 不能写正式路径。
  2. compute 不能写正式 gate。
  3. single writer 不能跳过 candidate audit。
  4. clean_next 正式发布后必须写现有 clean_next_partition_gate。
  5. 第一期只做 qfq，不顺手实现 MACD、MA、BOLL、derived 或 by-month 迁入执行壳。
