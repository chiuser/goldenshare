0. 方案摘要

先打通二级行业真实研究闭环，再从真实闭环中提炼平台能力。

M3 已收口

01提出问题

管理员从受控模板开始，明确研究对象、希望提前发现什么、如何判断成功，以及本轮不测试什么。

02冻结计划

系统把数据范围、交易日边界、公式版本、最终生效参数、样本切分、评价目标和执行预算冻结成可审阅计划。

03验证证据

运行成功不等于研究有效。结果必须通过数据、时间、未来泄漏、预热稳定、样本外和参数敏感性门禁。

04受控发布

通过门禁的结果只成为候选；人工批准后生成不可变版本，生产按同一公式计算，财势乾坤只读取稳定 serving 事实。

架构判断：首版不先建设一套空泛的通用平台，也不拆成独立微服务集群。QTF 作为新的产品子系统进入同一仓库，以“二级行业统一参数研究”为首个垂直切片，继续复用 Foundation 数据契约、Ops TaskRun 运行观测和 App 组合根；平台合同只从真实切片中提炼。

1. 系统定位与产品闭环

QTF 位于数据基础设施与行情产品之间，承担“研究事实转化为生产能力”的责任。

目标架构
数据事实流 研究反馈流 生产发布流 治理能力

2. 首版设计原则

这些原则决定后续实现能否形成平台，而不是堆积新的专项脚本。

架构约束

从用户问题出发

先说清要发现什么、如何判断成功和本轮不做什么，再选择数据和参数；不让用户从底层任务或脚本入口开始。

研究可复现

一次结果必须能追溯到数据指纹、对象池、公式版本、最终生效参数、样本切分、评估口径、代码版本和运行环境。

研究与生产分离

研究允许比较多个候选；生产只允许绑定一个已审批、可回滚、带生效日期的发布版本。

数据直读、质量上游负责

QTF 每次运行直接读取 Data Lake 或 Prod，只对本次 Run 的对象池和日期范围做只读输入门禁；不重新盘点数据源，不清洗、不修复、不回填、不保存输入副本。门禁失败由对应上游修复，失败 Run 保持不可变，修复后以新的 Run 重新直读和计算。

参数受 Schema 约束

支持有限调整周期、阈值和权重，但不是任意键值。类型、范围、步长、依赖、默认值和组合规模必须预先定义。

同核双模式

回测和生产信号共享同一公式实现与参数解释，区别只在输入窗口、执行模式和输出目标。

证据先于排名

运行结束先判断结果是否有效、样本是否充足、样本外是否成立，再比较候选；“成功执行”和“最优参数”都不是科学结论。

先有限探索

先估算组合数、扫描量、耗时和内存，再执行有限次数的研究；不自动扩大搜索空间，不把平台变成无边界调参器。

2.1 开源经验的本地化吸收

只吸收能解决当前问题的设计原则，不复制交易系统，也不引入新的技术栈。

Freqtrade + LEAN
经验来源吸收的设计点结合 Goldenshare 后的落法明确不照搬
Freqtrade类型化参数空间、最终配置留痕、未来数据泄漏分析、预热稳定性分析、后台回测与结果比较。参数只能来自受控 Schema；冻结时保存全部最终生效值；未来泄漏和预热稳定性成为候选门禁；复用 TaskRun 展示进度、失败和取消。不引入交易对、订单、仓位、自动 Hyperopt、TTL 结果缓存；不复制 GPL 代码。
QuantConnect LEAN回测与生产同核、时间前沿、目标与约束分离、样本内/样本外验证、参数敏感性阅读。每个历史点只看当时已发布事实；研究和盘后生产共用公式包；主要目标、硬约束和诊断指标分开；候选必须有未见样本证据。不引入撮合、券商、订单、组合、C# 引擎、云计算节点或自动交易运行时。

不是引入开源框架

首版继续使用现有 Python、PostgreSQL、Lake、DuckDB/Parquet 和 TaskRun。外部项目只用于校准设计，不成为新的运行依赖。

不是复制交易语义

我们的研究对象是行业、概念和地域信号，目标是发现、验证与发布行情事实，不是模拟成交收益或生成交易指令。

明确排除 Qlib

不采用 Qlib 的数据格式、MLflow、Recorder、在线模型或机器学习工作流；本文所有平台合同均从 Goldenshare 现有边界和板块业务需要出发。

4. 系统边界与依赖关系

“复用现有能力”不等于混用领域对象；组合发生在 App，业务事实各归其位。

必须遵守
系统 / 目录在 QTF 闭环中的职责可以依赖禁止承担
src/foundation / Data Lake / Prod保障来源数据的采集、清洗、修复、完整性和正式发布；提供数据集、交易日和访问契约。底层库与基础设施。实验、公式、候选参数或审批语义。
src/ops记录运行意图与 TaskRun 状态，调度 worker，提供进度、失败、取消和审计日志。Foundation 与通用运行协议。量化公式、参数优劣、实验结论和发布决策。
qtf量化领域模型、单次 Run 输入门禁、实验、验证、公式/参数版本和发布。自身领域与明确的 Foundation / Lake / Prod 只读端口。重复开展来源选型或平台级覆盖审计；清洗、修复、回填或复制来源数据；反向依赖 Ops/Biz/App；直接拼装页面。
src/app把 QTF executor、TaskRun、数据库 session、鉴权和 API 路由装配在一起。Foundation、Ops、Biz、QTF。承载量化业务规则或计算公式。
src/biz现有行情模块读取已发布的 serving 指标和信号。Foundation 与已稳定的 serving contract。读取实验草稿、自己选择参数、在查询时重算研究指标。
wealth量化研究工作台和财势乾坤行情展示前端。QTF 业务 API、现有 Wealth API。直接访问 Ops API、数据库或本地实验文件。

复用 TaskRun，不复制运行系统

实验业务状态由 QTF 管，执行进度和错误由 TaskRun 管；两者通过 task_run_id 关联，不再造一套 worker 和任务状态机。

新建实验配置，不复用静态策略配置

现有 StrategyConfig 适合仓库 JSON + 重启生效的静态模块配置；交互式实验草稿、参数冻结和版本比较应由 QTF 自己管理。

Serving 隔离实验域

下游只能读发布后的 compact facts。实验过程表和大结果文件永远不成为财势乾坤页面的直接依赖。

数据责任边界：既有来源与覆盖结论直接复用 板块雷达数据覆盖审计，M1、M2 不再重复审计 Prod。QTF 只在 M3 以后针对某次 Run 的精确对象池和日期范围记录“哪个数据集、哪个日期、哪个字段、哪项运行条件不合格”，并阻止该 Run 继续计算；数据修复、补录、清洗和重新发布必须回到 Data Lake 或 Prod 的正式维护链路。

5. QTF 能力框架

按用户完成一次可信研究所需的八组能力组织，不把内部类和服务直接暴露成产品入口。

模块化单体
能力域用户要完成的事平台内部职责首版核心输出关键边界
01 研究模板与问题定义选择“二级行业转热研究”等模板，说清希望发现什么和如何判断成功。把业务问题映射为对象类别、比较范围、因子族、成功定义和非目标。Research Template、Hypothesis、Evaluation Contract。模板限制可选能力，首版不提供任意脚本入口。
02 本次 Run 输入门禁确认本次研究实际读取哪些行业、哪些交易日，哪些日期不具备研究资格。复用既有来源合同和覆盖审计，只检查本次 Run 的精确范围：必要字段、业务键、缺失、非法数值、历史长度、比较组规模和研究样本要求。Run Input Preflight Record、排除清单。不重新做来源选型或全库覆盖盘点；只检查、不修复，不合格数据回到上游。
03 公式与参数定义理解公式用什么事实、参数有什么含义，并在允许范围内选择候选。注册公式输入输出、回看/预热、时间语义和横截面范围；草稿记录全部显式选择，计划补齐并展示验证合同与预算。Formula Contract、Parameter Schema、Effective Parameter Set。网页不能提交 Python；冻结后不存在隐式配置覆盖或运行时默认值。
04 实验与执行计划在启动前看清组合数、时间范围、样本切分、预计扫描量与停止条件。生成有限参数矩阵、样本内/样本外切分、对照、成本计划和可取消执行单元。Frozen Experiment、Execution Plan、Run Record。超出本次批准范围必须停止并建立新实验版本。
05 回测计算与可信门禁知道任务虽然跑完，但结果是否真的可信，以及为什么无效。直接读取已通过本次输入门禁的上游事实，同核计算逐日因子和信号；执行时间前沿、未来泄漏、预热稳定、覆盖和样本外门禁。逐日事实、信号事件、Validation Report。运行成功不等于研究有效；INVALID 不参加候选比较。
06 结果比较与研究结论比较候选的准确率、覆盖、提前量、样本外表现和参数敏感性。分离主要目标、硬约束和诊断指标，生成对照、敏感性、失败样本和局限说明。Evaluation Report、参数敏感性图、案例明细。不只展示冠军参数；样本不足必须明确为证据不足。
07 候选评审与版本发布把有证据的结果提交评审，确认适用范围、风险和生效日期。绑定数据、公式、参数、验证和审批记录，生成不可变 release。Candidate、Approval、Published Release。不能自动晋升；不能覆盖旧版本或静默改写历史。
08 生产信号与反馈在财势乾坤看到稳定、带日期和解释的信号，并观察后续实际表现。按公共业务交易日和已发布版本运行同一公式，原子写 serving；成熟后回收命中、误报与漂移。Serving Fact、质量状态、release_id、反馈统计。数据延迟按产品降级口径处理；生产不搜索参数。
产品与系统的对应关系：用户看到的是模板、计划、运行、证据、候选和版本；Source Adapter、Formula Kernel、Validator、Artifact Store 和 TaskRun Adapter 是实现这些用户任务的内部模块，不单独成为页面栏目。

6. 三条核心链路

研究、发布和反馈是三条不同的链路，必须通过显式版本连接。

闭环已确认

A. 研究链：从假设到可评审证据

选择模板建立可继续编辑、暂不可运行的研究草稿。
编辑草稿业务问题、成功定义、非目标和全部显式参数选择。
预检并审阅计划对象范围、IS/OOS、组合数、扫描量、执行预算和停止条件。
确认冻结管理员确认 plan hash 后生成完整不可变合同。
执行回测按时间前沿计算因子、信号、未来结果和对照。
可信门禁泄漏、预热、覆盖、样本外和敏感性检查。
阅读证据目标、约束、基线、失败样本和局限。
人工结论候选、待验证或本轮未找到。

B. 发布链：从候选参数到生产信号

候选版本绑定实验、公式、参数、结果与已知风险。
人工评审核对方法、样本、漂移、成本和业务解释。
批准版本生成不可变 release_id 和内容哈希。
指定生效记录生效日期、适用范围和替代版本。
生产计算同一公式包按已批准参数运行。
Serving 发布写入稳定指标/信号契约并附 release_id。
行情消费财势乾坤页面只展示正式结果。

C. 反馈链：从真实表现回到新研究

记录预测信号日、值、版本和当时可见数据。
等待验证窗次日、3日、5日等真实结果成熟。
归因统计命中、误报、漏报、持续性和提前量。
漂移监测样本分布、命中率与数据质量变化。
提出问题定位公式、参数、对象池或市场阶段问题。
派生实验继承来源关系，但创建新的冻结版本。
重新验证任何改进再次经过完整研究与发布门禁。

7. 核心领域对象与状态

平台要管理的是“研究证据链”，不是孤立的一份参数 JSON。

领域模型

ResearchTemplate

业务问题、对象类别、允许的因子/参数、默认比较范围、成功定义和首版非目标；二级行业研究是第一个模板。

FormulaDefinition

公式身份、输入字段、回看与预热、时间语义、横截面范围、空值规则、输出 Schema、实现入口和代码哈希。

ParameterSchema / Set

参数类型、范围、步长、依赖、默认值；冻结集保存全部最终生效值、值来源和参数哈希，而非只保存覆盖项。

UniverseVersion

对象列表、层级关系、比较范围、纳入/排除理由和有效日期。

RunInputPreflightRecord

记录本次 Run 直接读取的上游数据集、字段、业务交易日、as_of、对象池、比较范围、缺口、排除日、行数和内容指纹；这是运行门禁记录，不是新的数据源覆盖审计，也不保存源数据快照或副本。

ExperimentRevision

研究假设、输入门禁记录、公式、有限参数空间、样本切分、主要目标、硬约束、预算和停止条件。

ExperimentRun

冻结实验的一次执行，关联 TaskRun、代码版本、环境和运行记录；运行记录只描述执行条件与结果，不承载上游输入副本。

ValidationReport

数据、时间前沿、未来泄漏、预热稳定、样本覆盖和样本外门禁的逐项状态与证据。

EvaluationReport

主要目标、约束结果、对照、置信信息、样本内/样本外、敏感性、失败样本、局限和候选建议。

PublishedRelease

获批公式与参数、适用对象、生效日、替代关系、审批记录和 release hash。

8. 可信回测框架

把 Freqtrade 的泄漏/预热检查与 LEAN 的时间前沿/样本外原则，落实为板块研究可执行门禁。

候选前硬门禁

8.1 冻结的回测合同

合同部分必须冻结的内容二级行业首个用例
研究问题目标板块、信号含义、成功定义、非目标。在父级直属二级行业中，能否提前发现未来 1/3/5 日继续热的行业；不做个体行业专属参数。
数据范围来源、字段、日期、as_of、对象池、层级、比较范围、排除规则和数据指纹。Prod 既有东财层级、交易日和板块日行情；父级内比较为主，全市场同级只作辅助。
公式与参数公式版本、输入输出、回看/预热、候选维度、候选值、默认值和全部最终生效值。首轮迁移一级行业探索中使用过的价格/成交候选公式，并验证计算语义；其预测有效性和二级行业适用性均未验证。60/120 等具体候选仍须在 R2 计划中逐项批准。
时间切分参数选择区间、校准区间、未见样本外区间，以及每段用途。按交易日顺序切分，不随机打乱；已被查看过的一级行业历史窗口不能伪装成新样本外证据。
评价规则主要目标、硬约束、诊断指标、简单基线和置信方法。进入与留存分开；报告成功率、Lift、覆盖、提前量、样本量、父级分布与简单价格/成交规则。
执行预算组合数、扫描量、执行次数、时间/内存估算、取消点和停止条件。每轮有限尝试，看到结果后不得在同一 Run 追加参数；新假设必须新建实验版本并重新审批。

8.2 六道可信度门禁

门禁平台怎样检查用户看到什么失败后果
单次 Run 输入门禁复用既有来源和覆盖审计结论，只读检查本次 Run 精确对象池与日期范围的可访问性、业务键、重复、缺失、非法数值、历史长度、父级比较组规模和样本要求。不清洗、不修复、不补零、不前向填充。本次 Run 的上游数据集、有效日数、排除日期、缺失原因、各父级可比对象数量和修复归属。本次输入不符合既有上游合同为 BLOCKED，交回 Lake/Prod；仅研究样本不足为 INSUFFICIENT。两者都结束当前 Run，不允许原地恢复。
时间前沿对历史日 t 构造只包含 t 及此前已发布事实的视图；未来标签只能从 t+1 开始。信号日可见数据截止时间、未来结果窗口。INVALID。
未来泄漏差分改变 t 之后的数据并重算，验证 t 及此前因子和信号完全不变；检查公式 lag 与横截面日期。通过/失败、受影响的日期、公式和字段。INVALID，禁止比较和发布。
预热稳定在满足正式回看期的前提下，用不同额外预载长度重算重叠区间；比较因子值、信号日和排名差异。重叠样本差异率、最大偏差、首个稳定日期。超出公式合同阈值则 INVALID；历史不足则 INSUFFICIENT。
样本与覆盖检查事件数、父行业覆盖、时间分布、小同组可比性和是否由少数行业/时段支配。样本数、覆盖父级、最大集中度、排除组。INSUFFICIENT，允许保留研究记录但不得形成候选。
样本外与敏感性冻结参数后只执行一次未见区间；比较样本内/外衰减、简单基线和邻近参数。IS/OOS 对照、衰减、参数敏感性热图、失败样本。门禁不通过则无候选；不得回改参数后继续使用同一 OOS。

8.3 评价结果的阅读顺序

先看有效性数据、时间、泄漏和预热是否通过。
再看硬约束样本、覆盖、稳定性和样本外是否达标。
再看主要目标1/3/5 日成功率、Lift、捕捉率与提前量。
再看敏感性邻近参数是否也合理，避免孤立尖峰。
最后看案例成功、误报、漏报和异常父级样本。
人工结论提名候选、保留观察或本轮未找到。

8.4 最终参数与运行追溯

最终生效参数清单

草稿可以暂不完整但不能运行。单次输入预检根据全部显式参数选择生成可审阅 PLAN，按交易日顺序提出 50%/25%/25% 的 IS/校准/OOS 切分，固定未来 1/3/5 日和 RESET_ONLY 事件语义，并用版本化估算器给出本次预算。管理员确认 plan hash 后，冻结版本保存全部最终值、来源和参数哈希；运行时不再二次补值。

完整运行指纹

每次运行直接读取上游，并记录来源、范围、内容指纹、对象池、公式代码、最终参数、时间切分、评价合同、代码版本和运行环境。上游内容变化后必须产生新 Run，不覆盖旧结果。

已确认口径：不引入自动参数优化，也不自动复用历史计算结果。已完成 Run 可继续查看；每次新建 Run 都重新直读上游并完整计算。平台先提供有限参数矩阵、明确目标/约束、可信门禁和敏感性阅读；是否扩展搜索空间由每轮研究计划单独审批。

9. 上游直读与存储边界

平台直接读取 Data Lake 或 Prod，只保存平台业务状态、单次 Run 输入门禁证据、研究结果和正式输出；大型回测产物的保存方式由具体回测能力按实际规模决定。

不保存输入副本

Data Lake：直接读取正式资产

  • 适合长历史、多对象、大范围列式扫描。
  • 只读取上游正式发布的数据，不复制到 QTF。
  • 使用 DuckDB / Parquet 向量化读取，限定列和分区。

Prod DB：首个切片主来源

  • 二级行业首轮研究直接只读 Prod，不复制数据。
  • 所有研究查询保持只读、显式字段和范围约束。
  • PLAN 先估算扫描量；若可能影响生产热路径，停止并另行批准改为直接读取 Lake。

单次 Run 输入门禁

  • 直接复用已经冻结的数据源与字段合同。
  • 只记录本次 Run 的 source、as_of、范围、数量、缺口与内容指纹。
  • 不重复做全库覆盖审计，不生成输入快照、缓存、副本，不清洗或修复来源数据。
存储区保存内容建议介质写入者消费边界
QTF Platform StateResearch、Revision、Run、公式、参数、单次输入门禁、评估、审批和发布等平台业务状态与关系；它不是来源数据元数据，也不包含来源数据副本。现有 Prod PostgreSQL 的独立 qtf schemaQTF applicationQTF API；不直接给行情页面。
Run Artifacts具体回测能力真正需要保留的派生因子、信号样本、诊断结果、图表数据和运行记录；禁止保存原始输入副本。由该能力的技术方案与 LLD 在 PostgreSQL、受控派生文件或仅保留摘要之间选择对应 QTF capability executor保存粒度、介质、保留期和复现要求均按能力合同冻结。
Serving Facts已发布公式与参数生成的正式指标、信号、质量状态和 release_id。Prod serving 表QTF production runtimeBiz 查询和财势乾坤页面。
TaskRun执行意图、运行状态、进度、失败信息和耗时。现有 Ops 存储Ops runtimeQTF 通过安全视图展示；不是实验结果事实源。
已确认口径：平台不建立输入数据仓、不落输入快照，也不把来源数据复制为 QTF 缓存。开发某项具体回测能力时，只针对派生结果决定保存内容、介质和保留期。若上游数据后来被修订，QTF 可以通过 Run 输入门禁记录识别内容变化，但精确保留和恢复旧版来源数据是 Data Lake / Prod 的责任。

11. 首个垂直需求：行业二级热度参数研究

用真实、边界明确的研究任务检验平台骨架，而不是先造一个空平台。

首个用例

平台必须证明的能力

固定数据类目，灵活调整有限参数；每轮计划执行前可审阅复杂度；输出结果可横向比较并完整复现。

研究原则

先寻找二级行业统一参数，不为每个具体行业单独调参；有限次数、有限范围、每轮先审批，找不到也允许如实结束。

后续延伸

同一框架再研究三级行业、概念和地域；一级/二级/三级联合信号属于后续研究，不提前写死在首版内核。

用户步骤首个用例中的实际内容页面必须回答
选择模板二级行业“逐渐转热 / 高位延续”统一参数研究。研究什么、为什么研究、成功如何定义。

审阅计划交易日范围、样本切分、扫描量、预计耗时、对照和停止条件。这次会算什么、不会算什么、是否超出批准范围。

实现时间前沿、未来泄漏差分、预热稳定、样本覆盖、样本外和参数敏感性；形成明确 VALID/INVALID/INSUFFICIENT 结论。

M5 · R2 真实研究验收

只执行获批的二级行业首轮探索；交付候选、失败样本或“本轮未找到”，验证平台最小闭环确实支持研究判断。

M6 · 提炼通用平台合同

基于 M1～M5 已证明的共同点，收敛研究模板、数据清单、公式、参数、实验、验证和产物接口；不保留专项脚本式旁路。

M7 · 首版量化工作台

落地研究总览、新建研究、运行详情、结果比较、公式参数关系和候选评审，按用户阅读顺序验收。

M8 · 候选与不可变发布

完成人工审批、不可变 release、生效/退役、生产计算同核和 serving 原子切换。

M9 · 财势乾坤接入与反馈

板块雷达/速览消费稳定 serving；验收数据延迟、失败保旧版本、版本追溯和实际表现反馈，不暴露实验结构。

14. 首版门禁与明确非目标

功能范围不打折，但首版不靠增加平台复杂度来制造“高级感”。

禁止越界

首版必须具备

  • 从业务模板开始，冻结研究问题、成功定义和非目标。
  • 每次直接读取 Lake/Prod，来源、字段、业务日期、对象池、比较范围、缺口和内容指纹可追溯。
  • 本次 Run 输入门禁不合格即阻断运行，并明确交由哪个上游修复。
  • 公式有时间语义、回看/预热、输入输出、代码版本；参数有完整最终生效值。
  • 具体回测能力在开发前明确计算范围、资源门禁与派生产物保存策略。
  • 未来泄漏、预热稳定、样本覆盖和样本外验证成为自动门禁。
  • 结果分离主要目标、硬约束和诊断指标，并展示简单基线与参数敏感性。
  • 完整运行记录支持追溯；修订数据后旧结果不得被当作当前结果。
  • 业务审核动作完成后生成不可变 release，生产与回测使用同一公式内核。
  • 生产信号附 release_id、业务交易日和质量状态，可追溯到研究证据。
  • QTF 业务事务与 TaskRun 状态事务隔离。

首版明确不做

  • 不引入 Qlib、Freqtrade 或 LEAN 作为运行依赖；不复制外部平台代码。
  • 不允许用户在网页上传或执行任意 Python 代码。
  • 不建设自动 Hyperopt，不自动扩大参数空间，不自动发布候选。
  • 不为每个具体行业配置独立参数。
  • 不建设机器学习平台、分布式计算集群或实时分钟量化。
  • 不建设订单、撮合、仓位、组合、券商或自动交易系统。
  • 不做申万行业、跨体系映射或相关性研究。
  • 不清洗、修复、回填上游数据，也不保存输入快照、缓存或副本。
  • 不新增 QTF 角色、权限键、数据库账号或角色管理页面。
  • 不复制 Ops TaskRun，也不复用静态 JSON 配置代替实验管理。
  • 不把回测预测表述为交易指令或收益承诺。

身份与业务审核首版只复用现有管理员认证与 require_admin，不新增角色、权限键、数据库账号或角色页面。同一个管理员可以完成全部操作，但候选提交、审核确认、批准版本、发布生效仍是独立业务动作和记录。已确认M0 技术方案与 M7 工作台按此验收。
