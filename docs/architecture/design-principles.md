## 仍值得理解的设计动机

这些是早期设计取舍的摘要，不是对新功能的自动授权；具体方案仍需遵守下表对应的现行规则。

1. **数据事实不随页面拼凑。** 数据基座负责可信事实，页面面向业务任务；不能为一个页面临时发明字段或改写数据含义。
2. **页面与长任务分离。** 关闭页面或 Web 重启不应成为终止后台任务的操作方式。运营通过正式任务入口提交意图、查看进度和取消，不从路由直接跑重任务。
3. **先理解使用者要完成什么。** 页面围绕任务而非数据库表组织；先给状态、结果和可执行动作，技术细节按需展开。中文文案应让使用者理解，不把内部类名或存储字段当作产品语言。
4. **统一体验，不复制业务逻辑。** 共享组件帮助维持交互、状态和格式一致，但运营后台与 Wealth 是两个产品界面，不因此共用 Shell。前端不能重算后端事实或自行拼表。
5. **成功必须可验证。** HTTP 成功、进程存活、任务执行完成、业务结果正确是不同层次；空数据、失败、重试、权限和过期状态都应被真实呈现，不能用示例数据掩盖错误。
6. **借鉴体验，不被外部产品绑住。** 早期反对为兼容外部仓库而改变本仓边界；这不等于禁止比较外部架构。是否采纳某种技术取舍由具体方案说明，不能恢复旧稿“一概禁止架构参考”的泛化规则。
7. **控制首期范围。** 早期先做行情数据与运营入口，避免过早建设通用平台或新角色体系。这是当时范围，不是禁止已经批准的 Wealth、QTF 等后续产品域。
