## 5. 对调度实现的直接结论

1. 源端不是整批原子切换。看到任意新行、使用多数行时间或只看源端最大时间，都不能作为发布条件。
2. 组合通配符是正确请求方式，不需要按市场、按代码或按历史参考集合分片；未来范围治理不得反向制造逐代码源请求。
3. 普通边界在闭合后约 15 秒通常已经完整；五频率共同边界传播和请求耗时明显增加，固定等待 15 或 20 秒不能单独保证完整。
4. 调度必须采用“锚定闭合槽 + 首次等待 + 池覆盖校验 + 非阻塞有界重试”。部分传播结果不得切换 current pointer。
5. 两个交易时段的证据共同支持 `+15s` 首次尝试、部分传播后继续非阻塞有界重试。早盘 `09:30` 在 `+16.394s` 仍缺32只，不能把“等待15秒”误写成“15秒必然完整”。
6. 2026-08-26 下午与 2026-08-28 早盘的 1,395 个历史参考代码最终都完整切换，没有观察到持续旧时间代码。它只能证明该测量集合的传播行为；未来生产就绪集合、槽内冻结和 Health 口径尚未重新基线，不能从本记录直接推导。
7. 普通请求约 `0.5-0.8s`，已观测最大值为早盘 `4.449s`；一分钟槽内具备有界重试空间，但生产请求预算仍必须按滚动60秒模拟，不得只用平均耗时估算。

## 6. 验证后冻结的调度口径

开市源端时序验证已经完成，不需要为了确认源端传播再重复相同请求。`+15/+30/+45s` 尝试和 `+55s` 截止仍可作为未来调度候选证据；但“哪些代码必须完整到达才允许发布”尚未重新基线，因此本文不再冻结生产就绪集合、current pointer 或 Health 的最终合同。

依据本记录，调度口径冻结为：

| 项目 | 冻结值 | 证据与约束 |
| --- | --- | --- |
| 首次尝试 | `expected_bar_time + 15s` | 普通边界通常已经完整；`09:30 +15s` 仍可能不完整，因此必须继续校验和重试。 |
| 后续尝试 | 不早于 `+30s/+45s` | 覆盖 `15:00 +35.571s` 和 `14:00 +45.992s` 才完整的样本。 |
| 完成截止 | `+55s` | 为下一分钟槽保留边界；截止是请求完成时间。 |
| 最大尝试 | 每频率每槽 3 次 | 对应 `+15/+30/+45`。 |
| 源请求 timeout | `8s` 总墙钟时限 | 已观测最大 `4.449s`，保留余量；`now + 8s > +55s` 时不再发起。 |
| lease TTL | `70s` | 从首次尝试前获取，覆盖重试窗口和安全余量。 |
| 独立接口限速 | `20/min` | 五频率共同边界保守上界 `5 x 3 = 15` 次，留 5 次余量；配置校验仍需模拟滚动60秒。 |
| transport retry | 0 | 一次 scheduler attempt 只发一次 HTTP 请求，避免客户端自动重试跨槽。 |
| 频率顺序 | `1MIN,5MIN,15MIN,30MIN,60MIN` | 多频率共同到期时顺序固定，且一次 unified cycle 最多请求一个频率。 |

本验证没有写 Redis，因此不能回答单 snapshot、单 batch 或任何保留批数的实际字节数。只有覆盖范围和 Redis 合同重新拍板后，才允许在隔离 namespace 使用真实字段测量容量；生产启用前仍必须做受控复核。
