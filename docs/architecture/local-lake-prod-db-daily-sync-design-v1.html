Local Lake / Prod DB Daily Sync / Design v1

Local Lake 从远程 DB 每日同步能力设计

本文定义本地 Lake Console 如何从远程 Goldenshare DB 只读拉取生产已沉淀的数据， 写入本地移动盘 Parquet Lake。核心原则是：每次写入前先做 Kopia 备份， UI 不暴露 SQL，一次只允许一个任务运行，默认只做每日更新，并按数据集时间维度生成不同执行参数。

版本：v1 状态：待评审 更新时间：2026-05-14 适用范围：lake_console/ 不进入生产部署

0. 本轮拍板结论

  • 每次执行会写入 Lake 的同步任务前，必须先执行 Kopia 目标范围备份。备份失败，任务不得继续写入。
  • 恢复能力交给 Kopia。Lake Console 只提供快照查看、恢复命令预览和人工执行指引，不自研恢复引擎。
  • 默认 lookback 是每天，工程口径为 lookback_days=1。默认每日任务只处理一个目标日，不做滚动多日补偿。
  • UI 不暴露任何 SQL 输入框、SQL 编辑器、任意表名或任意字段选择能力。
  • 任务一次只能跑一个。需要全局门禁锁，锁未释放前不允许启动第二个写入任务。
  • 每个数据集的更新参数必须按它自己的时间模型生成，不能用一个统一参数模板硬套所有数据集。

1. 目标与边界

要做什么

  • 在 Lake Console 中增加“从远程 DB 更新本地 Lake”的本地写入能力。
  • 以当前已有 prod-raw-db / prod-core-db 只读导出链路为基础，不重复造查询引擎。
  • 提供 CLI 和 UI 两种入口，但 UI 只允许选择数据集/同步 Profile/日期参数，不允许写 SQL。
  • 每次写入前自动创建 Kopia snapshot，并记录本次任务对应的 snapshot id。
  • 任务状态、进度、错误和结果只写本地 manifest，不写远程 DB，不接生产 Ops TaskRun。

不做什么

  • 不把 Lake Console 挂入生产 Web、生产 Ops 或生产 scheduler。
  • 不允许远程 DB 写入、DDL、锁表、状态更新或任意 SQL 查询。
  • 不把生产 ops.task_run、dataset_status_snapshot 当成本地 Lake 事实源。
  • 不做自研备份恢复系统，不做一键 restore apply。
  • 不把 stk_mins raw -> clean_next 链路混入本轮远程 DB 每日同步主线，它仍按独立方案演进。

4. 每日同步流程

1. 解析 Profile 默认 lookback_days=1。根据本地交易日历和数据集日期模型计算目标日期。
2. 获取任务锁 如果已有写入任务运行，直接拒绝启动，提示当前 run_id。
3. 生成写入计划 列出 dataset、source、目标分区、预计写入路径、所需远程 DB 连接。
4. Kopia 备份 对本次会被替换的 dataset root / partition / manifest 做 snapshot。
5. 执行同步 逐数据集调用现有 engine，写入 Parquet，记录本地 run manifest。
6. 校验结果 检查行数、分区文件、空结果策略、异常原因。
7. 写任务结果 记录 success / failed / partial，关联 Kopia snapshot id。
8. 释放锁 正常或异常都要释放；崩溃遗留锁进入 stale 状态。
9. 页面展示 Sync Center 展示任务结果，Recovery 页面展示可恢复快照。
10. 异常恢复 如需回滚，用户按 Kopia restore 命令恢复，不由同步任务自动恢复。

5. Kopia 备份与恢复职责

同步前必须备份

每个会修改本地 Lake 的 profile run，在正式写入前必须先调用 Kopia 创建快照。 这里的备份范围不是默认全湖，而是“本次任务会改动的目标路径 + 关键 manifest”。 这样可以降低每日同步成本，也能覆盖本次写入的恢复需要。

如果 Kopia 备份失败，本次同步必须停止，不能进入写入阶段。

Snapshot 不刷新旧版本

Kopia 的正确模型不是“刷新昨天的备份”，而是“今天再创建一个新的 snapshot”。 snapshot 是不可变的，不能原地更新。这样恢复才可靠：昨天的状态永远指向昨天，今天的状态永远指向今天。

空间节省依赖 Kopia 的内容去重与 retention。没有变化的数据块不会完整再占一份空间； 旧 snapshot 的退出通过 retention policy、unpin 与 maintenance 完成，而不是覆盖旧 snapshot。

恢复不自动执行

Lake Console 只记录 snapshot id、source path、target path 和恢复命令示例。 真正恢复仍由用户人工执行 Kopia restore，并在恢复前确认目标目录。

这避免 UI 误触发大规模覆盖，也避免再造一套恢复系统。

备份保留策略

每次写入前创建新的 prewrite snapshot。普通每日 prewrite snapshot 默认不 pin，按 Kopia retention 自动退出； 只有关键阶段、清洗完成、全量重建完成这类需要长期保留的基线 snapshot 才 pin。

Recovery 页面必须展示 snapshot 是否 pinned、是否 baseline、是否只受 retention 保护，避免用户误以为所有历史点都会永久保留。

6. 单任务门禁机制

本地 Lake 写入任务一次只能跑一个。这个规则要在 CLI、API 和 UI 三层同时生效。

锁文件

manifest/lake_jobs/active_task.lock

启动任务时原子创建。已有锁则拒绝启动。

运行态

manifest/lake_jobs/runs/<run_id>.json

记录 profile、计划、Kopia snapshot、进度、错误。

事件流

manifest/lake_jobs/events/<run_id>.jsonl

页面轮询展示当前 dataset、分区、行数、错误。

状态 含义 允许动作
idle 当前无写入任务 允许启动新任务
running 已有任务持有锁 禁止启动第二个任务；UI 只能查看进度
stale 进程异常退出，锁超过 TTL 只允许进入“人工确认解锁”流程；不得自动覆盖

7. 数据集参数差异与同步 Profile

每个数据集如何更新，必须由数据集自己的时间维度决定。 每日同步 Profile 只负责“今天该跑哪些数据集”，不能把所有数据集都硬塞成同一种参数。

7.1 长期能力入口与本期范围

长期看，Lake Console 的数据资产维护入口分为七类。它们不是一次性全部实现。 本期只实现 prod_db_daily、prod_db_snapshot_refresh、prod_db_manual_backfill、lake_reference_refresh。 stk_mins_sync、index_mins_sync、indicator_compute 保留为后续专项，不能混进本轮开发。

能力入口 用途 默认行为 本期状态
prod_db_daily 每日交易日/锚点数据更新。 lookback_days=1，默认只处理一个目标日；周/月锚点数据只在目标日满足锚点时运行。 本期实现
prod_db_snapshot_refresh 无日期或 current 型基础资料刷新。 不传 trade_date，按数据集 current/snapshot 规则全量替换。 本期实现
prod_db_manual_backfill 人工补数或小范围重跑。 运营选择白名单数据集与日期点/日期区间；后端按数据集模型生成参数。 本期实现

7.2 默认每日 Profile：prod_db_daily

默认 lookback_days=1，也就是“每天只处理一个目标日”。 目标日由本地 trade_cal / 自然日规则解析。若某个数据集是周/月锚点型，只有当目标日满足对应锚点时才运行。

7.3 快照刷新 Profile：prod_db_snapshot_refresh

该 Profile 专门处理无日期 current 型数据集。它可以按需手动执行，也可以后续按较低频率接入本地自动任务。 它与 prod_db_daily 分开，是为了避免把“当前快照”误解成“每日分区数据”。 

lake-console sync-profile prod_db_snapshot_refresh
lake-console sync-profile prod_db_snapshot_refresh --dataset bse_mapping

7.4 本地基础清单 Profile：lake_reference_refresh

该 Profile 专门处理本地 Lake 的基础清单与日历，不属于远程 DB 每日导出。 第一批包含 stock_basic、trade_cal、index_basic。 这些数据会被股票池、交易日展开、指数池和后续同步计划复用，因此要作为独立入口维护。 

lake-console sync-profile lake_reference_refresh
lake-console sync-profile lake_reference_refresh --dataset trade_cal --start-date 2000-01-01 --end-date 2035-12-31

7.5 手动补数 Profile：prod_db_manual_backfill

UI 可以提供“手动补数”入口，但仍不暴露 SQL。手动补数只允许选择： 数据集、来源、日期点或日期区间。底层仍走 LakeSyncPlanner 和数据集白名单。 

lake-console sync-profile prod_db_daily --trade-date 2026-05-14
lake-console sync-profile prod_db_manual_backfill --dataset daily --start-date 2026-05-01 --end-date 2026-05-14

命令名只是方案占位，最终实现前需要与当前 CLI 分组命名保持一致。

8. UI 与 API 设计

Sync Center 页面

  • 显示当前任务锁状态：空闲 / 运行中 / stale。
  • 显示可执行 Profile：每日更新、手动补数、快照刷新。
  • 执行前展示计划预览：数据集、来源、目标日期、目标路径、预计备份范围。
  • 执行时展示进度：当前数据集、当前分区、fetched/written、错误。
  • 执行后展示结果和关联 Kopia snapshot。

UI 禁止项

  • 禁止 SQL 输入框。
  • 禁止任意表名/字段选择。
  • 禁止一键恢复覆盖正式目录。
  • 禁止绕过 Profile 直接拼接远程 DB 查询。
  • 禁止同时启动多个写入任务。

8.1 最小 API

字段级契约以 Local Lake Sync Center API 契约 v1 为准。本节只保留接口总览。为与现有 Lake Console API 风格一致，正式路径统一使用 /api/lake/sync/*。

API 方法 用途 输入 输出
/api/lake/sync/profiles GET 列出可执行同步 Profile。 无 profile_key, display_name, description, default_lookback_days
/api/lake/sync/profiles/{profile_key}/plan POST 生成执行计划，不写入。 target_date?, start_date?, end_date?, dataset_keys? plan_token, datasets、target partitions、backup paths、warnings
/api/lake/sync/runs POST 启动写入任务。 plan_token, confirmed_backup_required run_id, lock_status, started_at
/api/lake/sync/runs/current GET 读取当前运行任务。 无 当前 run 摘要或 idle
/api/lake/sync/runs/{run_id} GET 读取任务详情。 run_id 计划、备份、进度、结果、错误
/api/lake/sync/runs/{run_id}/events GET 读取任务事件流。 cursor? append-only events

9.1 Run Manifest 关键字段

字段 含义 约束
run_id 本地任务唯一 ID。 硬约束，必须唯一。

M1 后端编排骨架 SyncProfileCatalog, SyncProfileRunner, LakeJobLockService, KopiaPrewriteBackupService。 单元测试覆盖锁、备份失败阻断、profile plan。
M2 CLI dry-run / execute lake-console plan-profile, lake-console sync-profile。 dry-run 不写入；execute 前必须产生 Kopia snapshot。
M3 本地任务账本与事件 run manifest、events jsonl、current 状态。 异常退出不丢失可诊断信息；stale lock 可识别。
M4 Sync Center UI Profile 列表、计划预览、启动、进度、结果。 UI 不出现 SQL 能力；不能启动第二个任务。
M5 每日自动执行方式 本地 launchd / cron 示例，只调用 CLI，不接生产 scheduler。 默认 lookback_days=1；日志可追踪。
M6 数据集扩展与回归 按数据集类型逐批纳入 profile。 每批先 dry-run，再小样本 execute，再全量每日任务。

11. 风险与门禁

必须阻断的风险

  • Kopia repository 不可用或备份失败。
  • 已有写入任务运行或锁状态不明。
  • UI/API 出现可输入 SQL 的能力。
  • 远程 DB 查询越过白名单表或字段。
  • 数据集时间参数无法根据 profile 明确生成。
  • 写入目标路径不在 GOLDENSHARE_LAKE_ROOT 下。

每批上线前检查

  • 确认 config.local.toml 中远程 DB URL 只读账号可用。
  • 确认 Kopia repo status 正常，能创建测试 snapshot。
  • dry-run 展示的 dataset、target path、backup path 与预期一致。
  • 小样本执行后，检查 Parquet 文件、run manifest、Kopia snapshot id。
  • 失败路径必须能留下明确错误，不允许静默成功。

11.1 本方案需要后续代码落地时特别注意

  1. 不要把 Profile Runner 做成新的查询层，它只编排已有 planner/engine。
  2. 不要让页面拼接数据事实或 SQL；页面只能消费后端返回的计划对象。
  3. 不要把 Kopia 备份做成可选项。写入前备份是硬门禁。
  4. 不要为了“自动恢复”引入新的覆盖正式数据动作；恢复仍由人工通过 Kopia 执行。
  5. 不要把 stk_mins clean_next 链路的门禁与普通 prod DB daily profile 混在一起。
