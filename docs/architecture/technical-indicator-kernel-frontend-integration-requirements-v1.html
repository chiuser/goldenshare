3.2 成功0根与业务显示分开

内核合法0根只表示本次成功无结果，所有成功结果的msg均为空；它不知道调用方是否首次打开页面或在继续查更早数据。现股票HTTP协议已用HTTP 200、bars=[]、meta.count=0、EMPTY、observedTradeDate=null表达空结果，page-init.quote=null/EMPTY在证券存在而没有行情时也合法。业务后续根据这些已有字段和本次请求用途选择文案，不新增isEmpty、success或msg字段来让内核判断页面状态。

已确定的首屏文案为“暂无行情信息”，历史到底文案为“已经加载全部数据了”。此前拟在StockDetailPage整理显示数据之前处理合法空，页面增加empty状态，不造报价或K线；空历史页保留已加载图表。该页面实现、状态面板及协议对接都后置到产品阶段，当前没有实现，也不影响内核独立开发和验收。

5. 此前提前加载设想（内核完成后再review）

此前设想是在距已加载最早边界还剩100根时，由用户向左查看触发下一页；若每页500，则整页例为第400、900、1400根，1600根短尾合并后可在第1500根触发下一次正常空请求。它是产品何时发请求的候选策略，不是内核的请求频率、分页或验收规则，当前不按此开工。

  • 此前考虑dataKey含证券、day、原首屏日期及forward，历史页endDate不进入key；插入更早K线时按实际日期保持用户视图，原截止日变化再重置。现代码仍是旧key与下标处理，没有完成该改造。
  • 按日期合并、保持指标对齐、保留顶部报价与pageContext、避免迟到响应覆盖新选择，均属于后续业务与图表实现。未传可选通知的指数/分钟调用方怎样保持现状，也在产品阶段核对，不因内核500上限擅自迁移它们。

当前共享图表points变化会清理并重建四图、重画累计点，不能把总渲染成本说成固定500根。若后续保留500/剩100策略，再在产品方案中确定页面常量和加载状态；内核硬上限500不能由这些前端常量代替。本轮不做图表生命周期重构，也不创建跨请求计算缓存。

7. 内核统一合同，以内核原方案和LLD为准

  • 各周期、各调用方统一默认500根、硬输出上限500根；不是仅网页传500，也不是保留旧10000上限后给网页另设约定。超过上限按内核合同处理，产品不能默默截断或拆分来绕过。
  • 动态预热另计。读取及计算可以需要500根以外的历史，最终只返回本次目标；实际不足上限则返回实际数量，合法NULL保留。输入合批和资源限制继续由内核方案定义，不以500当输入上限。
  • 合法0根是中性成功无结果；保留msg字段，所有成功结果均为msg=""。before仍只表达数据时间边界，不让空结果具有“首屏无数据”或“历史到底”的不同内核含义。
  • 内核不关注首屏、屏幕可见范围、提前100根、何时请求下一段或是否继续请求。股票HTTP的bars/count/dataStatus与用户文案由后续业务接入处理，不反向决定core结构。
  • 同次组合使用同一批所需K线及必要复权，预热取必要最大值；来源、公式、输出、取消和清理保持各自职责。页面不是内核独立验收的先决条件。

这些是本轮已明确的内核边界，不代表现代码已实现。具体代码、SQL、调用方及独立验收范围回到内核原方案/LLD核对；本文不再另列一套由前端驱动的内核门禁。
