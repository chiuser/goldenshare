03 · 原请求合同保持不变

GET /api/v1/wealth/market/stock-detail/kline
    ?tsCode=603806.SH&period=day&adjustment=forward
    &endDate=2026-05-29&limit=300
参数保留的当前规则
tsCode必填字符串；原路由继续strip、转大写；未知股票保持404001。不能因为内核只识别规范代码，就改变原接口对未知标的的判定顺序。
period / adjustment默认day / forward；本接口仍只支持这两个值。内部把forward映射为qfq，不对外接受qfq等新值。
tradeDate / endDate保持原日期解析及优先级：先以endDate或tradeDate解析页面日期，查询截止日为endDate或解析出的页面日期。沿用现有A股日期上下文，不引入另一套日历。
startDate可选、包含该日；与endDate均显式传入时，startDate晚于endDate保持原400001。不额外改变现有日期默认行为。
limit接口默认300，合法范围1～2000；页面目前显式传300。不是内核默认1000；本阶段不增加cursor、before、hasMore、nextCursor或额外探测请求。
debug保留0/1，默认0。原有鉴权和请求参数解析错误继续走既有处理。

日线仍返回请求区间内最近limit根，并按交易日期升序排列。历史少于limit时返回实际数量；不补零、不复制日期。合法无数据仍返回原DTO的空bars、count=0及EMPTY状态，不把内核的msg字段加到旧API。

05 · 一次计算十项，同一批日线只准备一次

原API按原规则查询证券、日期和现有K线，确定实际返回日期。
→
一次内核调用stock / day / qfq，七条MA与BOLL、MACD、KDJ一起提交。
→
现有Lake读取按指标需要定位历史，读日线和因子，统一复权并计算。
→
原DTO按日期填入16个指标值，其他行情字段保持原样。

日期范围由现有K线决定

若原查询实际返回300个日期，内部请求使用这些日期的首日和末日，limit=300、before不传；输出必须与这300个日期逐一对应。start只限定对外结果范围，不能裁掉首日之前必需的预热历史。数据库返回0根时，按原空结果处理，不为组织空响应而访问Lake。数据库有K线而Lake没有对应结果，是来源交接失败，不能返回空成功。

例如旧查询截至2026-05-29返回300根：内核返回相同300个日期的指标；按当前默认递推规则，价格计算输入通常为300+500=800根。请求1000根通常计算1500根，请求2000根通常计算2500根。这里的500来自现有参数下的预热规则，不由业务写死；MA250需要249根前置历史，组合采用最大需求，不把十项需求相加。上市历史不足时用实际起点初始化，MA/BOLL保留合法null。

当前8192根合批规则继续有效：上述输入不足8192时，跨日期文件合并后一次交给计算模块，不能一份日线文件就调用一次指标。只读取所需列和候选范围；定位、文件解压及基准读取也计入成本，不能用“返回300根”冒充“只读取300根”。MA20与BOLL20复用均值；同请求复权一次，不增加跨请求状态缓存。

来源与复权必须与页面K线一致

复用现有日线来源合同：silver/quote/stock_daily是不复权输入，由现有来源读取对应复权因子，按既定最新基准转成qfq。Lake根只从现有Settings取得，不在页面、API或脚本中另写根路径。

本阶段最重要的接入核验：页面OHLC来自数据库的*_qfq，新指标将使用Lake复权后的价格。同名“前复权”不保证基准、精度和更新日期一致。冻结LLD并进入编码前，要用一只有除权事件的股票和一只有普通历史的股票作有界对照，记录日期、原始价格、因子、基准以及两边OHLC；先核实输入口径，再谈指标误差。若不一致，停止接入并说明原因，不能暗中改变页面K线、改复权基准或把指标按比例修补。

所选历史范围不改变复权基准；历史请求也沿用当前来源既定基准，不开放任意基准日期。上述有界对照属于接入验收，不是在每次请求中增加全历史质量扫描。内核继续信任外部数据质量，不新增交易日缺口、停牌、退市或数值逐根审计。

2026-10-31单节点续做：管理员已明确要求核清首次SQL错误并完成这项开发前检查。复用保存的数据库42行，不重连数据库；只读取原两股21个日期的21份日线、21份因子和2026-10-30最新因子，共43份文件。先用无行情小例重现并修正汇总SQL的rows别名错误，再核日期/数量/唯一性、原始OHLC、因子、最新基准及168个前复权价格值；同时保存全精度差值和显式五位小数对照，不用舍入掩盖基准或行情差异。执行范围、费用及失败规则见专项LLD第02.1节；本轮不因此进入业务开发。

07 · 生命周期、错误和配置沿用既有约束

  • 明显非法的参数先拒绝；合法请求才等待计算名额。一只股票的十项指标占一个名额。
  • 数据库Session在所属工作线程内完成读取，不在并发任务之间共享；跨线程交接只使用已取出的普通数据及不可变说明。不得把慢SQL放在事件循环中直接执行。
  • 同一请求只有一份截止时间。数据库准备、等待、Lake定位与读取、计算、DTO组装及编码都不能重新获得完整时限；最终发送与清理仍归入原总目标。
  • App通过原TechnicalIndicatorService管理本请求计算连接，实际创建与关闭仍由同一服务完成，App不重复关闭；读取模块管理K线和复权数据，指标管理自己的状态。对外发送的结果必须脱离连接。
  • 仅一个任务观察HTTP断开。取消或停机先通知停止，等待实际工作退出，清理结果、body、交接容器及异常栈帧引用，最后归还名额；不能遗弃线程或提前报告成功。
  • 保留原参数失败400001、未知股票404001、原框架参数校验及鉴权行为。新增来源、计算、繁忙、到期、编码和清理失败保持失败响应，复用既有HTTP 500、internal_error及code/message/request_id结构；不新增业务异常码，具体内部分类保留在有限诊断中。连接已断开时不伪造成功响应。
  • 成功无K线与执行失败严格分开。读取、指标、结果交接或清理错误不返回部分指标、旧指标或空成功。
既有配置本阶段使用方式
同时处理2、等待2、最多等2000ms复用现有Settings及进程内runtime，不建立按指标的等待队列，不另加配置。
总目标8000ms、清理预留2000ms第6000ms停止正常工作；发送已开始时按总目标控制。沿用现有中断和实际退出规则，不承诺底层阻塞必能硬性结束。
