1. 总览判断

先把结论放在最前面，避免后面继续把目标态当成现状。

当前核心模型
不够细

当前最大出入

管理台主要扫描 catalog 登记路径，不能完整表达硬盘上已有的 clean_next、指标资产和治理目录。
开发策略
先定模型
新页面暂停，先评审 Dataset / Node / Partition / PhysicalAsset 的语义边界。

目标模型建议改成 数据集 Dataset -> 内容节点 Node -> 分区 Partition / 文件 File，同时增加 硬盘资产 PhysicalAsset 用来反映真实目录。Layer 只保留“原始层 / 辅助清单层 / 派生层 / 研究层”这种大层级含义，不再混用成具体目录。

A. 目标模型草案

这部分是待评审方案，不代表已经进入代码实现。

待评审 只定模型
数据集 Dataset 业务上可被管理、同步、审计的一组数据。 例：股票历史分钟行情、指数历史分钟行情、分钟指标。
大层级 Layer Lake 里的顶层归属，只回答“数据处在哪一层”。 例：原始层、辅助清单层、派生层、研究层。
内容节点 Node 一个数据集在某个大层级里的具体资产。 例：clean_next_by_date、by_symbol_month、indicators_by_date。
分区 Partition 内容节点下面按日期、月份、频率、指标参数切出来的动态片段。 例：freq=30/trade_date=2026-04-24。

核心关系图

关键约束：Layer 只回答“在哪一层”，Node 才回答“这一层里的哪个具体内容”。例如 research 是大层级，stk_mins_by_date_clean_next 和 stk_mins_by_symbol_month 是两个内容节点，不能再让 research 一个人同时表示这两件事。

Dataset 与 Layer 的关系

关系 是否直接建模 原因 例子
Dataset -> Node 是 数据集拥有多个稳定内容节点，这是业务资产定义的核心关系。 stk_mins 拥有 raw_by_date、clean_next_by_date、by_symbol_month。
Node -> Layer 是 每个内容节点必须说明自己位于哪个湖内大层级。 clean_next_by_date 位于 research 研究层。
Dataset -> Layer 否，只做派生展示 数据集和大层级是通过内容节点间接关联。直接保存会造成“一个 research 到底代表哪个资产”的歧义。 stk_mins 显示有研究层，是因为它有研究层节点，不是因为数据集直接挂了一个 research 目录。

B. Catalog 职责边界

Catalog 不是硬盘目录清单，也不是分区清单；它只登记稳定业务资产。

这里的 Catalog 可以理解成“数据湖资产登记册”。LakeDatasetDefinition 是登记册里的一条数据集定义；LakeNodeDefinition 是这条数据集定义下面的内容节点定义。登记册负责说“应该有什么、在哪里、怎么扫”，硬盘扫描负责说“实际有什么、大小多少、缺不缺”。

应该进入 Catalog

数据集
数据集 key、名称、分组、来源、同步方式、业务角色。
内容节点
节点 key、所属大层级、路径、扫描规则、用途、来源节点。
扫描规则
目录结构如何解析成分区字段，例如交易日期、月份分桶、指标参数。

不应该进入 Catalog

每个具体分区
trade_date=2026-04-24 这类是扫描结果，不是手写定义。
每个具体文件
parquet 文件数量、大小、修改时间来自硬盘扫描，不进静态配置。
临时和治理目录
_tmp、_recovery 应作为硬盘资产展示，默认不是数据集节点。

Catalog 与硬盘扫描的关系

问题 Catalog 回答 硬盘扫描回答 管理台展示方式
这个目录是不是稳定业务资产？ 是 / 否，归属于哪个数据集和节点 目录是否真实存在 已登记 / 未登记 / 治理目录
这个资产怎么读？ 扫描规则和分区维度 实际有哪些目录和文件 节点覆盖范围、大小、文件数、分区数
为什么总览漏账？ 没有登记的节点无法进入数据集摘要 全湖扫描能看到真实占用 总览需要同时展示登记模型和硬盘资产差异

5.0 目标字段关系

对象关键字段人话含义评审重点
LakeDatasetDefinition dataset_key, dataset_name, group_key, source, dataset_role, nodes 定义“这是什么业务数据”。不直接假设只有一个存储根。 是否保留 storage_root，还是改由主内容节点提供。
LakeLayerDefinition layer, layer_name, layer_order, description 定义“处在哪个湖内大层级”。 只做全局大层级，不再保存路径和布局。

6.1 API 硬约束：前端零推断

原则 后端必须负责 前端只能负责 禁止行为
展示事实以后端为准 返回页面所需的完整展示字段，包括名称、状态、大小、覆盖范围、层级、节点、提示文案和排序权重。 按 API 字段直接渲染，不自行补字段。 前端根据 path、layer、layout 猜中文名、状态或业务含义。
聚合计算在后端完成 完成数据集总量、节点总量、全湖占用、漏账差异、登记状态等聚合。 展示后端给出的聚合结果和明细列表。 前端把多个 API 结果拼起来算总数、算差异、判断是否漏账。
语义判断在后端完成 明确返回 registered_state、asset_role、node_name、layer_name、partition_label 等展示语义。 根据后端语义字段控制样式和布局。 前端通过目录名包含 clean、derived、research 来判断资产类型。
页面模型由 API 输出 为总览、数据集列表、节点详情、硬盘资产列表提供稳定 response model。 只做轻量 view rendering，不维护第二套数据模型。 每个页面各自定义一套事实字段，或者私下组装与 API 不一致的 view model。

8. 现状与目标态差异

这张表是后续整理模型时最该盯住的清单。

项目 文档目标态 当前现实 建议处理
Layer / Node 混用 Layer 是大层级，Node 是具体内容节点 LakeLayerDefinition 同时保存 layer、path、layout、purpose 拆出 Node 模型
clean_next 资产 作为 stk_mins 的研究层内容节点 硬盘真实存在，但管理台摘要可能漏账或表达不完整 补 Node 定义和扫描摘要
分钟指标资产 作为 stk_mins_indicators 数据集，指标和参数是分区维度 derived/stk_mins_indicators_by_date 与 research/stk_mins_indicators_by_symbol_month 当前不应继续漏账 新增数据集与扫描规则
全湖硬盘资产 能够展示已登记、未登记、治理目录 当前总览更多依赖 catalog，不能完整解释硬盘真实占用 补 PhysicalAsset 摘要
前端事实拼接 后端提供完整事实，前端只展示 部分页面仍可能按 path、layer、layout 做推断 API 收口后清扫
LakeFileSummary 文件级对象 没有 schema、scanner、API、前端消费 标为目标态
partition_key 分区定位符 当前未返回；且不应继续按单一 key 设计 后续改造成结构化字段
replace_scope 写入安全范围 当前未返回 写能力设计时再落
dataset detail API 独立详情接口 当前前端用 dataset list + partitions list 组合 API 架构阶段评审
row_count 详情或显式刷新可算 字段存在，通用链路未填 保持预留，禁止页面假算
股票基础信息辅助清单 写成独立 dataset 示例 现实是 stock_basic 的辅助清单层 文档需修正

9. 后续开发规则

在模型梳理完成前，新页面开发应暂停。

必须遵守

Storage / Health / Activity 只能在 Dataset -> Node -> Partition 和 PhysicalAsset 这套模型上做页面投影。需要新字段时，先改模型与 API 设计，再开发页面。

必须避免

不要让每个页面自己解析 path、自己发明 layer 结构、自己计算事实字段。前端只做展示 view model，不做事实推断。

9.1 推荐推进顺序

顺序工作产物
1评审本文档目标模型确认 Layer / Node / Partition / PhysicalAsset 是否无语义重叠
2确定 API 契约明确 overview、datasets、partitions、physical-assets 的返回边界
3代码内字段和枚举清扫旧口径清零，前端不再自行拼事实
4恢复页面开发先修数据湖总览真实反映全湖，再进入 Storage / Cost
