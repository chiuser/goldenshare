股票实时日线流架构方案 v1

本文把 V1 范围收敛为“股票实时日线数据”，以 Tushare 0372 `rt_k` 为唯一上游。 它不是离线数据集接入，不走 DatasetDefinition、DatasetExecutionPlan、TaskRun、freshness 或日期审计链路。 服务器侧由 realtime collector 在交易日的 A 股连续竞价时段按固定节奏请求 Tushare，并把结果刷新到 Redis；页面和业务 API 只读取 Redis 快照。

1. V1 方案摘要

先只做股票实时日线快照：服务端采集 Tushare 0372，Redis 保存最新状态，页面/API 读取 Redis。

唯一上游

V1 只接 Tushare 0372 `rt_k`，对应“A股实时日线”。指数、ETF、盘口不进入 V1；WebSocket 作为后续推送能力预留。

服务器刷新 Redis

独立 realtime collector 常驻运行，仅在交易日的 9:30-11:30、13:00-15:00 内每 6 秒发起 1 次 Tushare 全市场请求。

最新状态层

Redis 保存股票最新日线快照、batch stream、delta stream 和 feed 健康状态。V1 不写业务历史库。

最小 API

V1 只定义股票实时日线快照查询 API 和健康观测 API；后续基于 Redis stream 增加 WebSocket 推送。

一句话口径： Redis 不会自己刷新；刷新动作来自服务端 realtime collector。collector 只在交易日的 9:30-11:30、13:00-15:00 请求 Tushare，再把返回的股票实时日线写入 Redis。
2026-06-01 M2 配置收口： 本方案的实时日线 V1 已落地，实时日线与实时分钟的运行配置已统一进入 realtime feed config 单一读取层。collector、CLI、Biz API、Ops API 不得分散读取 Settings 或保留运行配置硬编码；日线 lease TTL 行为保持不变，并从配置对象读取。

2. 与离线链路边界

实时链路必须和当前离线数据维护链路隔离，避免把低延迟服务做成慢任务系统。

维度 离线数据维护 实时行情流 本方案规则
核心目标 可追溯、可重跑、可审计、可落库 低延迟、状态新鲜、读取稳定、失败降级 两条链路独立，不互相复用执行模型
事实模型 DatasetDefinition RealtimeFeedDefinition 0372 不建 DatasetDefinition
执行模型 DatasetExecutionPlan -> IngestionExecutor CollectorPlan -> RealtimeCollector 不进入 TaskRun 主链
状态存储 业务库 raw/core/serving 与 Ops TaskRun 表 Redis 最新快照、batch stream、delta stream、健康状态 V1 不沉淀历史业务库，只保留 Redis 最新快照和短期事件流
质量判断 写入行数、拒绝原因、日期完整性、新鲜度 最后更新时间、延迟、stale 比例、上游错误率 不走 freshness/date audit
用户体验 任务记录、任务详情、手动维护、自动任务 股票实时日线快照、数据是否滞后 V1 页面只消费股票实时日线快照查询 API
硬边界： 实时状态写入 Redis 或 Ops 观测失败，不允许影响离线业务数据表的读写与事务提交；反过来，离线任务失败也不应拖垮实时行情服务。

按现有 foundation / biz / app / ops 边界拆分，Redis 作为实时状态层。

4. Redis 刷新流程

Redis 的数据来自服务端 realtime collector 主动轮询 Tushare，不是由 Redis 自己生成。

4.1 服务端什么时候请求 Tushare

collector 常驻启动

部署一个独立实时采集进程或 systemd service，启动后读取 feed 配置。

判断采集窗口

先判断交易日，再判断 9:30-11:30、13:00-15:00；只有两者同时满足才请求源站，其他时间只更新空闲或休市状态。

请求 Tushare rt_k

调用 0372 `rt_k(ts_code=...)`，字段来自源文档，不自造参数。

标准化快照

把源字段转成股票实时日线快照，记录 `trade_time` 与接收时间。

写入 Redis

写入新 batch 下的股票快照、索引、batch stream、delta stream 和 feed 健康状态。

页面读取

页面/API 只读 Redis；采集时段内超过 stale 阈值才显示数据滞后。

4.2 一次全市场刷新如何走

步骤 动作 请求参数 Redis 写入 说明
1 collector 定时器到点并判断采集窗口 无 无 这个动作发生在服务器端 realtime collector 进程内。非交易日，或不在 9:30-11:30、13:00-15:00 时，不请求 Tushare。
2 请求 Tushare 0372 `rt_k` ts_code=3*.SZ,6*.SH,0*.SZ,9*.BJ 无 源文档明确支持一次提取全市场，单次最大 6000 条；V1 先采用一次拉全市场。
3 标准化返回行 无 暂不写 按 `ts_code` 生成股票实时日线快照，保留 `trade_time` 和服务器接收时间。
4 写入 Redis 新批次快照 无 rt:feed:tushare_stock_rt_k:batch:{batch_id}:snapshot:{ts_code} 先写入新批次空间，暂不覆盖当前可读批次。
5 切换 current pointer，并更新索引、batch stream、delta stream 和健康状态 无 rt:feed:tushare_stock_rt_k:current_batch / rt:feed:tushare_stock_rt_k:stream:batch / rt:feed:tushare_stock_rt_k:stream:delta / rt:feed:tushare_stock_rt_k:health API 和 Ops 页面从 Redis 读取这些状态。采集时段内 6 秒后 collector 再发起下一次全市场请求。
关键解释： Redis 的刷新来源是服务端 collector 的定时轮询。交易日采集时段内每 6 秒，collector 调用一次 Tushare `rt_k(ts_code="3*.SZ,6*.SH,0*.SZ,9*.BJ")`；拿到返回后，写入新的 `batch_id` 空间。全部写完后，最后一步原子切换 `current_batch_id`。页面/API 只读当前批次，避免新旧批次混读。非交易日和非采集时段不请求源站，不应误报为采集失败。

5. Redis 状态层

Redis 是 V1 正式实时状态基础设施，不把最新行情写进业务历史库。

为什么需要 Redis

实时采集进程、Web API、Ops 页面通常不是同一个进程。进程内缓存会导致状态割裂，Redis 能统一最新状态和健康事实。

保存什么

股票实时日线最新快照、短期变化事件、feed 健康、活跃代码索引、最近请求参数。不保存长期历史。

不承担什么

不做离线审计，不做历史 K 线，不替代 raw/core/serving，不作为 TaskRun 事实源。

Key 类型 内容 TTL/保留 用途
rt:feed:{feed_key}:batch:{batch_id}:snapshot:{symbol} Hash 或 JSON 某个批次内单只股票实时日线快照 建议 259200 秒，仅保留最近 3 批 页面和业务 API 通过 current pointer 读取当前批次
rt:feed:{feed_key}:current_batch String 当前可读批次号 不过期或长 TTL 原子切换新批次；读请求先读它，再读对应 batch
rt:feed:{feed_key}:batch:{batch_id}:index Set / ZSet 当前批次有快照的标的集合，可带更新时间分数 建议 259200 秒，仅保留最近 3 批 批量查询、滞后统计
rt:feed:{feed_key}:stream:batch Redis Stream 批次发布事件 `batch_published` 按条数裁剪，默认最近 5000 条 用于 Ops 健康、批次追踪和发布节奏检查
rt:feed:{feed_key}:stream:delta Redis Stream 逐股票变化事件 `quote_changed` 按条数裁剪，默认最近 200000 条 用于后续 WebSocket 推送和变化订阅，不作为历史行情库
rt:feed:{feed_key}:health Hash 上游状态、最后成功、延迟、错误计数、熔断状态 不过期或长 TTL Ops 实时流健康页
rt:feed:{feed_key}:lease String + TTL collector 采集租约 短 TTL，自动过期 避免多个 collector 同时刷新同一个 feed

6. 批次一致性

采用 `batch_id + current pointer`，不对读请求加锁，也不让页面读到新旧批次混杂。

为什么不用读锁

读锁会让页面请求等待写入完成，实时行情高峰期容易放大延迟。Redis 单条写入原子，但多股票逐条覆盖会导致批次混读。

选择的方案

collector 每轮生成新的 `batch_id`，先写完整批次，最后原子切换 `rt:feed:{feed_key}:current_batch`。

读请求语义

API 先读 current batch，再读该批次内的股票快照。请求要么读到上一批，要么读到新一批，不读半新半旧。

步骤 collector 写入动作 读请求可见性 说明
1 生成新 `batch_id`，例如 `20260514T103000.123` 不可见 此时 `current_batch` 仍指向上一批。
2 写入 `rt:feed:tushare_stock_rt_k:batch:{batch_id}:snapshot:{ts_code}` 不可见 即使写了几千只股票，页面仍读上一批，不会混读。
3 写入该批次索引、batch stream、delta stream、health 草稿信息 不可见或仅 Ops 草稿可见 业务 API 不直接读草稿批次。
4 原子执行 `SET rt:feed:tushare_stock_rt_k:current_batch {batch_id}` 新批次可见 这是唯一切换点；切换非常快，不需要锁住读请求。
5 后台清理过期旧批次 不影响当前读 保留最近 2-3 个批次即可，防止读请求跨切换瞬间找不到数据。
接口读取规则： `GET /api/v1/realtime/stock-rt-daily` 必须先读取 `rt:feed:tushare_stock_rt_k:current_batch`，再读取该批次下的股票快照；禁止直接扫描“最新 key”拼装结果。

7. Redis 部署方案

远程服务器当前未安装 Redis。进入代码实现前，必须把 Redis 系统依赖、环境变量、systemd 与发版验收一起纳入。

Redis 系统依赖

生产服务器安装并启用 Redis 服务，建议仅监听 `127.0.0.1`，不对公网开放。

应用配置

`/etc/goldenshare/web.env` 增加 `REDIS_URL=redis://127.0.0.1:6379/0`，Web、Ops、collector 共用。

collector systemd

新增 `goldenshare-realtime-collector.service`，独立于 web、worker、scheduler 重启和观测。

阶段 动作 验收 说明
R1 基础安装 安装 Redis 并设置开机自启 systemctl is-active redis* 与 redis-cli ping 返回正常 服务名可能是 `redis-server.service` 或 `redis.service`，以服务器实际发行版为准。
R2 安全配置 限制 Redis 只监听本机，禁止公网访问 本机可连，外网不可连 V1 不需要 Redis 集群，也不需要远程公网 Redis。
R3 应用 env 通过 `scripts/remote-web-env.sh` 写入 `REDIS_URL` Web/collector 启动时能读取配置 遵守现有远程 env 唯一入口，不手工编辑 `/etc/goldenshare/web.env`。
R4 collector unit 新增 `scripts/goldenshare-realtime-collector.service` systemctl status goldenshare-realtime-collector.service 正常 需要同步更新 deploy 脚本的 unit 同步、重启、状态打印逻辑。
R5 sudoers 把 collector unit 的 install/restart/status 加入 `goldenshare-deploy.sudoers` 部署用户可无密码同步和重启 collector unit 当前 sudoers 只覆盖 web、worker、scheduler、date completeness worker。
R6 发版验收 发版后检查 Redis、collector、Web API、Ops 健康页 Redis 有 current batch；健康 API 显示最近成功刷新 Redis/collector 不健康时，Web 应返回明确 stale/unavailable 状态，而不是内部异常。
部署边界： Redis 安装和系统服务启用是服务器基础设施动作，不应塞进普通应用发版脚本里偷偷执行。应用发版脚本只负责同步和重启 Goldenshare 自己的 realtime collector unit。

9. V1 对外 API

不先设计一堆抽象实时 API。V1 只围绕“股票实时日线快照”定义最小接口。

API 用途 调用时机 返回重点 V1 建议
GET /api/v1/realtime/stock-rt-daily 批量读取股票实时日线最新快照 行情页、股票列表、卡片需要展示当前价/开高低收/成交量时 按 `ts_codes` 返回 Redis 中的最新快照；单次暂定最多 200 个代码；包含 `stale`、`trade_time`、`received_at` 第一期
GET /api/v1/ops/realtime/stock-rt-daily/health 读取股票实时日线采集健康 数据运营后台“实时流监控”菜单打开时 最近请求、最近成功、最近错误、Redis 快照数量、stream 指标、`page_polling_enabled` 和 `recommended_poll_interval_seconds` 第一期
暂不定义 WebSocket 推送 实时行情页需要持续接收价格变化时 后续建议基于 `rt:feed:tushare_stock_rt_k:stream:delta` 读取变化事件，按客户端订阅的股票代码过滤推送 M5 预留
接口原则： 前端和业务调用方只传股票代码列表，单次请求上限暂定 200 个代码；调用方不需要知道 Tushare `rt_k` 的全市场通配符、请求频率或 Redis key。
前端页面 API 已设计： “实时流监控”页面 V1 只调用 `GET /api/v1/ops/realtime/stock-rt-daily/health`。页面进入先读一次；只有 health API 返回 `page_polling_enabled=true` 时，才按 `recommended_poll_interval_seconds=60` 每 1 分钟局部刷新状态区域。页面不得整页刷新，不得自行读 Redis，不得调用 Tushare，也不得自行推导交易日或交易时段。

10. Ops 菜单与观测

在数据运营后台单独规划“实时流监控”一级菜单，不把实时采集伪装成 TaskRun 任务详情。

上游健康

最后请求时间、最后成功时间、最近错误、Tushare 返回行数、最近请求参数。

状态新鲜度

Redis 快照数量、最后刷新耗时、滞后股票数量、最老快照时间。

采集频率

目标 10 次/分钟以内，展示最近一分钟请求次数，避免误触发 Tushare 限流。

菜单建议： 数据运营后台新增“实时流监控”一级菜单，V1 页面只展示“股票实时日线”一个 feed 的采集状态和 Redis 状态。
不要做的事： 不在 TaskRun 里展示实时行情轮询记录；不把实时健康写成离线 freshness；不把 Redis 快照失败当成业务数据表事务失败。

11. Tushare 0372 接入口径

V1 只接股票实时日线 `rt_k`，按源文档要求传 `ts_code`，不落库历史。

项 建议口径 说明
feed_key tushare_stock_rt_k 表达 Tushare 股票实时日线 feed。
源文档依据 docs/sources/tushare/股票数据/行情数据/0372_A股实时日线.md 接口名 `rt_k`；`ts_code` 必填；单次最大 6000 条；支持通配符。
请求方式 ts_code=3*.SZ,6*.SH,0*.SZ,9*.BJ 按源文档示例一次拉全市场；仅在交易日 9:30-11:30、13:00-15:00 内每 6 秒请求一次。
存储 只写 Redis 最新快照、batch stream 与 delta stream 不创建 raw/core 表，不接日期审计。
访问方式 HTTP 快照查询 V1 先做 HTTP 快照；后续 WebSocket 从 Redis stream 读取变化事件并推送。
限流 1 分钟 10 次以内 用户 token 权限为 500 次/分钟以内，但 V1 不需要那么快；按 10 次/分钟作为默认配置。
降级 返回 stale 快照并标记 stale 上游短暂失败时，页面看到“数据已滞后”，而不是空白或误报最新。

12. 推进里程碑

围绕股票实时日线收敛推进，不把未来可能的实时能力混入 V1。

阶段 目标 交付物 不做事项
M1 真实接口探测 验证 0372 `rt_k` 的字段、全市场通配符请求、返回行数和交易时段外行为 探测脚本、样本结果、字段映射确认 不写正式服务代码

M3 股票实时日线快照 API 提供批量读取 Redis 最新快照的业务 API `GET /api/v1/realtime/stock-rt-daily` 不实现 WebSocket，但保留 Redis stream 数据基础
M4 Ops 实时流监控菜单 数据运营后台单独展示股票实时日线采集健康 health API、实时流监控菜单页面 不复用 TaskRun 任务详情
M5 WebSocket 推送 在 V1 快照和 Redis stream 稳定后，增加股票实时日线 WebSocket 推送 `WS /api/v1/realtime/stock-rt-daily/ws`、订阅协议、断线重连、限流策略 不混入指数/ETF/盘口，仍只围绕股票实时日线

13. 已确认与待解决项

这些点会影响后续代码设计，已确认的直接作为实现约束，待解决项进入实现和验收清单。

D1 Redis 部署口径

已确认：V1 生产环境明确要求 Redis；远程服务器需要先安装 Redis 并纳入部署验收，不使用进程内缓存作为生产状态层。

D2 V1 请求方式

已确认：使用 `ts_code=3*.SZ,6*.SH,0*.SZ,9*.BJ` 一次请求全市场，仅在交易日的 9:30-11:30、13:00-15:00 内每 6 秒请求一次。

D3 首期 API 形态

已确认：V1 只做股票实时日线快照查询 API 和 Ops 健康 API；WebSocket 作为 M5 后续阶段，基于 Redis stream 实现。

D3.1 Redis 一致性模型

已确认：采用 `batch_id + current pointer`。collector 写完整个新批次后再原子切换 current pointer；读请求不加锁，只读 current batch。

D4 是否沉淀历史

已确认：V1 不沉淀历史，只保留 Redis 最新快照、batch stream 和 delta stream。历史分钟线或 tick 归档另立题。

D5 stale 阈值

已确认：V1 `stale_after_seconds=20`。仅在采集时段内用于判断滞后；非采集时段显示空闲/非采集时段，不误报失败。

D6 真实请求验证

收盘后初步探测与开市时段验证均已完成，结论支持使用 ts_code=3*.SZ,6*.SH,0*.SZ,9*.BJ 一次请求全市场；开市时段字段完整性与耗时满足 V1 采集口径。

D7 Redis stream 粒度

已确认：V1 同时写 `stream:batch` 的 `batch_published` 批次事件，以及 `stream:delta` 的 `quote_changed` 逐股票变化事件。首批不灌全市场 delta，后续只写与上一可读批次相比发生变化的股票，并用 MAXLEN 裁剪。

D8 Redis TTL

已确认：batch snapshot/index/meta TTL 为 259200 秒（72 小时），同时只保留最近 3 批，覆盖午休、隔夜和周末展示，不沉淀长期历史。

D9 非交易日请求策略

已确认：只有交易日 + 9:30-11:30/13:00-15:00 才请求源站；非交易日显示 `market_closed`。

D10 前端页面轮询

已确认：Ops 页面进入时先请求一次 health API；只有处于交易日交易时段时，才每 1 分钟继续请求 health API，只局部更新状态区域、批次信息、错误信息和指标展示。午休、收盘后、夜间、非交易日、feed disabled 时不持续轮询。不得整页刷新，不得重新挂载整个页面，避免页面闪烁。health API 返回 `page_polling_enabled` 和 `recommended_poll_interval_seconds`，前端按服务端返回决定是否继续轮询，禁止前端自己按本地时间推导交易日或交易时段。

R1 待解决事项

已完成：开市时段真实源接口验证、生产 Redis 与 REDIS_URL 配置、collector + Redis batch pointer 最小闭环、业务 API、Ops health API、实时流监控页面与远程收市 smoke。剩余：下一交易时段端到端验收；WebSocket 推送作为 P1，基于 V1 current batch 和 delta stream 另立实现，不进入 V1 主闭环。
