本轮发现的执行细节遗漏：必须补入LLD

  • 请求并发、框架线程池、SQL线程分开计量。一个请求可含10项指标，仍只占一次同步调用；DuckDB可能在内部用多个线程。框架线程池还服务其他接口，不能把其默认容量当允许40个大计算同时运行，也不能每个Web worker各限2个就声称整个部署只限2个。
  • 连接与实例不能混淆。DuckDB threads和memory_limit是数据库实例范围的设置，不能描述为某条SQL或某个普通cursor的私有配额。无名称的:memory:连接用于本请求独立实例；cursor()仍指向同一实例，不用于冒充请求隔离。首版已确认threads=1；LLD明确配置归属、独立实例与部署预算，实际表现仍须验证，不依赖机器默认CPU核数。
  • 等待也要计入截止。不能进入工作线程才开始计时，漏掉框架线程池已等待的时间。请求到达、获准计算、开始SQL、完成与清理均记录；允许有数量与时间上限的等待已获确认；同时处理2个、等待最多2个且最长2秒的初始值已确认；LLD验证实际执行与超时清理，满载检查不能只放在已经可能排队的工作线程最深处。
  • 取消等待不代表计算停止。AnyIO取消等待或Future.cancel不能替代DuckDB真实中断；页面断开也不自动保证SQL停止。接口侧与本次调用的取消/截止如何交接、运行中的SQL如何interrupt、实际停止后再清理，必须明确。普通SQL仅在工作线程执行；必要取消控制只能针对本请求，连接关闭前撤销并结束监控，验证取消与关闭同时发生时不再操作旧连接。
  • 部署版本要核对。本机Web .venv当前DuckDB=1.5.5，DG .venv=1.5.2；既有能力/数值实验记录是1.5.2，不改写其历史结论。新核LLD明确目标运行版本，按该版本补独立数值、线程/实例隔离、停止和资源样本；不以现有旧实验替代，也不在本轮升级套件。
  • 对其他接口的影响也要测。在既定5项/10项和双请求有界场景中，另列轻量API响应、进程总内存、SQL线程数、等待/拒绝及取消停止；先补新增测试次数和总成本，不扩大成全市场压力测试，不擅自加池或调全局线程数。

算法需要多少输入、产生多少输出：先定义合同，再决定读取

2026-10-21澄清：算法输入/输出需求不是“每批读多少根”的资源配置。指标对象根据公式与参数声明所需字段、每个输出点所需历史、初始化/跨批状态、输出时间对齐及初始空值规则；统一计算服务据此把业务要求的输出范围转换为读取要求，读取模块按要求执行，不自行猜测多读一年或仅读显示区间。

例子算法与读取合同应明确
MA20单个有效输出该点需本根及之前19根收盘价，共20根；输出对应本根时间。不能把该规则误写为任意批量调用都只能20根输入、1根输出。
MA20连续M个有效输出历史充足时需要覆盖这M根及首根之前19根，合计M+19根；请求最近1000个输出时需1019根。前19根是计算所需输入，不属于本次展示结果。若沿用对齐的整段计算接口，也可以每根对应一个位置，初始不足20根的位置为NULL；具体接口须统一说明，不能混淆有效值数量与序列位置数量。
MA250输出最近一个月读取需求为这个月的K线加上首根之前249根日K，而不是只读该月。必须按实际K线根数表达前置要求，不把249根直接改写为249个自然日或固定一年。
MACD/KDJ递推输出最近一个月本版没有跨请求持久状态，按已确认规则从来源约定历史起点递推到截止，再返回目标月份；不能统一声称读一年即可精确恢复全部递推历史。

LLD必须在指标声明、服务给读取模块的内部合同和测试中一致写明：目标输出起止/根数、所需字段与价格口径、首个输出之前需要的K线根数或约定历史起点、截止含义、初始化/跨批状态和初始NULL规则。多个指标按同口径合并所需历史范围，读取模块按该合同读入；实际分成多大批次不改变算法结果和必需历史。

有效历史较短时继续返回实际可用序列并按公式保留初始NULL，不补造K线，不截断必需历史来满足资源预算；数据质量和完整性仍由外部负责，不新增逐根缺口审计。

  seed_ema + alpha * sum(x * power(beta, -i)) OVER (

共用连接指谁共用

只指同一次calculate(request)内部：读取模块通过PyArrow读取当前批，再用该连接注册和物化本批输入，读取模块内的复权对象在该连接执行复权SQL，指标计算模块继续使用该连接中的目标价格表，输出部分读取本次需要返回的结果。同一个统一计算服务负责创建，也负责最终关闭：calculate(request)内部取得本次连接，在同一调用的统一收尾位置关闭。读取、复权、指标与输出只是使用方，不转移连接管理权、不各自close；正常、异常和取消均由该服务保证收尾。

不是多个页面、不同用户或不同股票请求共用同一条可变连接，也不是与DG任务或正式数据库共用连接。首版普通读取/计算步骤在本次工作线程依次执行，不让多个指标线程同时操作它；取消控制可按LLD对本请求执行interrupt，但不得并发执行其他SQL或提前close。这样复权生成的内存表可直接交给指标SQL使用，无须先转成Python全历史行对象，再搬到另一连接；实际缓冲及SQL中间结果仍须计入预算，不能声称全过程没有任何内存复制。

创建与关闭必须落实到同一管理方，不能只写“有人负责”。若改成读取模块创建、计算模块关闭，会出现读取后过早关闭、双方重复关闭或双方都以为对方会关闭的问题。本设计不采用这种交接；完整输出须在关闭前独立，运行中的SQL须先停止。

1. 资源由谁持有

资源创建与持有方使用与释放条件
本次DuckDB连接统一计算服务创建并最终关闭的原则已确认；共用范围限本次调用内的读取、复权、指标与必要结果读取。完整签名和异常关闭步骤在LLD明确。读取模块只释放其数据，不关闭共用连接；计算模块只释放其状态。全部SQL停止且输出已独立后，服务在统一收尾位置关闭一次；不同请求不共享可变连接。
来源游标、文件句柄、注册列数据读取模块管理，并在创建后立即记录归属，覆盖部分初始化失败。最后一次实际使用结束即释放；若DuckDB仍引用注册数据或游标缓冲则不能提前丢弃。正常、失败、取消都走同一清理出口。
实际复权口径与基准读取模块在本次请求准备阶段确定并保持不变。整段历史各批次使用同一实际口径与基准。所需当日因子可按批读取，目标价格生成后无下游使用即可释放；不因此扫描历史或重查来源变化。
原始K线与本批因子读取模块按需读取，不额外形成Python逐行副本。所选目标价格已生成，且本次已确认的指标和价格输出均不再使用原始数据后即可释放。不得因价格生成结束就忽略仍在运行的输入使用方；一次请求只允许一种目标类型，不建立多个目标复权分支。
本批共享目标价格读取模块创建和持有，指标只读使用。全部依赖本批的指标及独立价格输出均完成，必要状态、历史窗口与输出已保存且不再指向本批表，所有引用该表的SQL均已结束，才由读取模块释放。
下一批所需历史窗口计算模块声明需要的历史行数和字段，读取模块按同口径所需最大值保留一份。保留的是独立的小表或列数据，不能只是指向整批原表的视图。下一批使用后更新；没有后续批次则释放。预算包含更新时旧、新保留表短暂同时存在的占用。
EMA、DEA、K/D等指标状态和指标中间表计算模块持有；读取模块不理解或更新指标算法。跨批保存必要状态；同一批内部用完的中间表尽早释放。请求结束、失败或取消后，由计算模块清理。窗口前置行不得再次推进递推状态。
需要返回的价格与指标结果输出组织持有；仅保存展示范围内的结果。最近N根请求每完成一批后只保留最近N根，不全历史INSERT后等最后截取；此结果仍计入同一请求内存预算。关闭连接前转成独立结果对象，不返回仍依赖输入表/连接的视图、游标或未执行查询。读取模块释放不能使返回结果失效；响应交付后的结果不归读取模块继续保管。

2. 一个批次允许释放的明确条件

  1. 服务事先汇总本次固定的指标/价格输出清单、字段及历史要求；首版按固定顺序完成本批使用，不为每个指标另开线程或连接，也不预读下一批。
  2. 读取模块提供本批只读目标价格。输入已经是正确目标口径时直接使用，不重复复权、不读取无用因子。
  3. 全部使用本批的指标和价格输出均已实际完成SQL；不能仅创建一个以后才执行、仍指向输入的查询对象就算完成。
  4. 计算模块保存下一批所需的递推状态，读取模块独立保存必要历史窗口，输出组织保存仍需返回的结果；三者均不得依赖即将释放的输入表或底层注册缓冲。
  5. 服务确认上述条件满足后通知读取模块结束本批。读取模块删除本批表、注销已不用的输入、关闭已不用的来源句柄并移除引用；完成后才推进下一批。
  6. 记录“已释放”指资源不再被本请求使用，可以回收或复用，不承诺进程RSS马上下降或DuckDB立即把全部内存还给操作系统。实际峰值和清理后占用仍须测量。

并发与等待：按整次页面计算说明

并发数量指同一时刻已有处理名额且尚未完成收尾的完整请求数；首版建议把读取、计算、清理及响应发送均计入该名额的持有期，具体API释放位置必须在LLD核对。一个区域一次提交MACD、KDJ、MA、BOLL共4项指标，仍算1个请求；同页另一区域的独立请求另算1个。等待数量是已有请求占满可用计算位置时，最多让多少个尚未开始读取/计算的请求等候。等待时间是这些请求最多等多久；开始执行后的耗时与此前等待分别记录，总截止仍从请求到达计算。

按已确认初始值举例：A、B各一页的组合请求正在处理，C、D依次到达后进入最多2人的等待；E再到达时立即返回繁忙。若A实际结束并归还名额，C先开始；D继续等，自己的等待累计满2秒就结束，不因C开始而重新计时。旧请求只是收到取消信号、SQL却还没停止时，不能提前归还它占用的计算位置。

多个指标不是多个并发请求，DuckDB内部SQL线程数也不是这里的请求数。从行为上这是进程内有数量及时间上限的等待，不是等待整段计算持有的锁，也不需要外部消息队列或新的线程池；初始每进程同时2个、最多等2个且2秒已经确认；LLD核对落点，开发后先按最小场景验证，不等待完整矩阵再定初值。读取、计算、输出/发送各自占用与释放仍按第12节说明，不把等待等同于已开始后台预取。

已确认等待方向；并发控制必须在LLD落实的安排

管理员确认的是效果：空闲立即处理、忙时允许等候、人数与时间有上限、前端整次请求明确失效。下面是落实该效果的工程建议，尚未编码或验收；不改变同步calculate入口、业务进程执行、单次一种目标复权或已有读取/计算资源归属。

  1. 等待的是计算名额，不是整段计算持有的锁。从行为看，是进程内有限的等待队列。优先复用现有AnyIO等运行库的等待/通知能力，接口外只做数量和截止控制；不自建通用任务系统、外部消息队列、数据库任务表或轮询线程。若需要锁，只短暂保护人数及名额变更，不持锁读取K线、执行SQL或等待其他请求。
  2. 同一业务进程的所有相关入口共用一份控制。由App在应用生命周期建立一次，Biz接入层使用；不能在每次请求或每个股票服务实例里新建一份计数。股票、指数和调用同一内核的入口共同计量；Foundation不反向依赖Web框架。非HTTP调用的截止/取消交接另按同一内部合同说明，不默认绕过限制。
  3. 先获得名额，再进入工作线程和读取数据。沿用现有鉴权及轻量请求检查，未授权或非法参数不进入等候；前端总时限仍包含鉴权过程。等待期间只保存有大小限制的请求参数、截止和通知信息，不开DuckDB连接、不读文件、不复权、不占着工作线程睡眠。接口侧用异步等待，获准后通过已有工作线程机制调用同步内核；现有同步def入口不能原样加一把阻塞锁就声称完成。接入层是否修改入口形式须在接入LLD列清，不在本轮修改现行API。
  4. 一次组合请求只申请一次名额。接入层是该次请求名额的唯一申请和归还方。获得名额后，同步calculate、读取/复权对象、各指标及复合依赖都不能再次申请同一名额，否则名额较少时会排队等待自己。当前股票分钟API的_service每次创建查询服务对象，所以不能照此把共享计数放进每次新建的服务实例；App建立的共享控制与每次计算的数据/连接分别管理。直接调用内核的其他入口也必须在自己的接入边界完成一次相同的控制，不以不经HTTP为由绕过资源限制；具体装配列入LLD，不给内核增加Web依赖。
  5. 等待数量不能只靠线程数限制。运行库的并发名额可能有内部等候列表，但不自动提供本业务的最大等待人数。LLD同时限制正在处理与尚未开始的请求；满员后立即拒绝新增等候，不让默认线程池外再堆一层无上限等待。获准后若仍等待框架线程，也计入本次总时限，到期不能后来又启动SQL。
  6. 按到达顺序唤醒，过期和取消请求移除。首版建议先到先开始，不加用户优先级或股票优先级；新请求不能绕过已等候者。等候者取消时释放等候位置，轮到它时还须再次检查截止。取消、超时和“刚好获得名额”同时发生的情况必须逐条验证，防止重复归还或永久少一个名额。
  7. 每次请求只确定一次总截止。服务端用单调时间从到达开始计算，等候、框架线程等待、读数、计算、转换及必要清理的安排都不能靠重新计时延长。最长等待不得超过整次请求剩余时间；初始从到达起总目标8秒，其中最后2秒预留停止/清理；第6秒未完成即取消，LLD核对转换和发送如何计时并记录实际停止耗时。数据查询的业务截止日期与请求失效时间分别说明，不能混用。
  8. 前端也必须有独立的整次失效时间。后端截止无法保证网络一定送达，页面须到期停止加载、取消原请求并忽略迟到结果。已确认后端总目标8秒、前端从发出请求起10秒失效；两端分别计时，预留余量不等于保证所有网络环境都能收到错误响应。当前wealthFetch转交调用方signal，并有401后的登录刷新与一次重发，但本轮所读分钟路径未见统一整次超时；接入时沿用同一截止覆盖刷新/重发、响应体接收和结果转换，不修改全站无关接口，不为繁忙增加无限自动重试。当前parseMinuteResponse在取得Response后还会await response.json，故不能在fetch返回响应头时就清掉定时器。同步JSON解析/图表转换不能靠定时器强行抢断；用输出大小限制和有限测量限定占用，完成后再次检查截止，过期结果不进入展示。
  9. 前端失效不等于SQL已经停止。等待中失效就移除，且不再开始读数；运行中失效就通知内核停止新批次/新指标、中断本请求SQL并清理。未实际停止的SQL和未释放资源继续占原名额；不能通过取消await、返回超时或浏览器断开就归还。正常目标为发起取消后2秒内完成停止与清理，实际SQL停止和资源释放分别记录；若超时仍无法确认停止，标明未停止并阻止继续超额接单，不宣称成功取消，不自动创建新线程或重启进程。Python线程不能被安全强杀的限制仍保留；达不到相应验收条件时不得通过该执行方式的开发验收。
  10. 名额释放必须有唯一负责方和明确时点。首版建议HTTP侧名额覆盖从获准开始，到SQL结束、资源清理及API响应完成或断开；只有这些条件满足才由接入控制归还一次。内核仍由原服务创建/关闭连接，读取和指标分别清理自己的数据；接入层不越权close。慢速发送、DTO/JSON转换失败也受第12节的总资源规则约束，不因SQL结束就无限积存待发送结果。实际释放位置在接入LLD追到框架的响应完成/异常路径，而非只追到函数return。
  11. 多进程的数字分别核算。进程内等待对象不能跨Web进程共用。部署若有P个进程、每进程C个名额，总量最多P×C，等候人数和同时内存同样计入总预算；不能每个进程都配2个后声称全系统只有2个。首版不为统一数字引入分布式锁或外部队列；目标部署进程数和资源分配必须在LLD21明确，不能擅自改部署。
  12. 退出与失败仍要完成收尾。应用关闭时停止接收新计算，移除/结束等候请求，通知运行中计算停止并按归属清理；不保存请求续跑或自动重放。等待人数、处理人数、停止中人数、等待耗时及拒绝/过期原因应能从既有日志和测试记录核对，不新建观测平台，也不因日志失败改变结果。

实现依据与限制：本机Web环境AnyIO为4.13.0，已读CapacityLimiter的OrderedDict等待及取消移除/释放通知代码；它说明已有等待能力，不证明业务最大等待人数、整次超时和SQL中断已经实现。AnyIO官方同步工具说明明确异步工具不能由工作线程直接操作；归还名额等操作须回到其所属的异步执行环境。AnyIO官方线程说明明确取消等待不终止底层线程；Starlette线程池说明确认该容量还供其他接口使用。本次只核对代码与资料，没有安装或升级依赖、建立队列或执行并发测试。

并发控制的有限验证：不靠“加了锁”判断完成

LLD先列12类控制规则验证，每类至多6个轻量请求、固定执行一次，上限72个请求；用可控制的测试替身安排先后，不读正式湖、不算长历史，不随机无限重跑。这部分仅证明控制规则，不作为真实SQL停止、HTTP响应或性能通过的证据。真实SQL取消、响应发送及5项/10项组合仍需最小真实链路；增加的次数、根数、耗时与取消重试开销先写入LLD，不自动包含在现有1226万根预算里。

  • 空闲立即开始，多指标仍只占一个请求名额。
  • 满员后等待，按到达顺序唤醒，新请求不得插队。
  • 等候人数到上限后拒绝，未创建来源或SQL资源。
  • 等待到期移除，之后即使有空位也不开始。
  • 等待取消立即腾出等候位置，不错减正在处理人数。
  • 取得名额与取消/截止同时发生，无名额丢失或重复归还。
  • 计算异常、重复取消及清理异常，其他请求不被误停且收尾归属正确。
  • 框架线程暂不可用时仍受总截止限制，过期不迟启动。
  • 前端失效、登录刷新重发及快速切换沿用总截止，迟到结果不覆盖新选择。
  • SQL未停止或结果仍发送时不提前归还；最终处理/等待/停止中计数可核对。
  • 多个应用进程的总量不误当单进程上限，关闭时不再启动等待请求。
  • 同一时刻5项/10项请求与轻量API并行时，对其他接口的响应影响另用有界真实场景测量，不拿轻量替身的时延作生产依据。

SQL能力实验：输入、公式与独立字面预期

以下是本轮隔离实验，不是正式内核实现。预期值为可手算的固定数值，未调用待测公式生成；Python只提交此SQL并收集结果。最后一列passed的3行均为true。该实验不覆盖长历史与跨段接续。

WITH p AS (
 SELECT 2.0/(2+1) af, 1-2.0/(2+1) bf,
        2.0/(3+1) aslow, 1-2.0/(3+1) bslow,
        2.0/(2+1) ad, 1-2.0/(2+1) bd,
        1.0/3 ak, 1-1.0/3 bk
), bars(i, close, high, low, factor) AS (
 VALUES (1,100.0,101.0,99.0,1.0), (2,101.0,102.0,100.0,2.0),
        (3,102.0,103.0,101.0,2.0)
), base AS (
 SELECT *, max(high) OVER w hhv, min(low) OVER w llv,
   avg(close) OVER w ma, stddev_pop(close) OVER w sd
 FROM bars WINDOW w AS (ORDER BY i ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
), inputs AS (
 SELECT *, CASE WHEN hhv=llv THEN 50.0 ELSE 100.0*(close-llv)/(hhv-llv) END rsv
 FROM base
), stage1 AS (
 SELECT *,
  pow(bf,i)*(100.0+af*sum(close*pow(bf,-i)) OVER w) ef,
  pow(bslow,i)*(100.0+aslow*sum(close*pow(bslow,-i)) OVER w) es,
  pow(bk,i)*(50.0+ak*sum(rsv*pow(bk,-i)) OVER w) k
 FROM inputs CROSS JOIN p
 WINDOW w AS (ORDER BY i ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
), stage2 AS (
 SELECT *, ef-es dif,
  pow(bd,i)*ad*sum((ef-es)*pow(bd,-i)) OVER w dea,
  pow(bk,i)*(50.0+ak*sum(k*pow(bk,-i)) OVER w) d
 FROM stage1
 WINDOW w AS (ORDER BY i ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
), calculated AS (
 SELECT i,dif,dea,2*(dif-dea) hist,k,d,3*k-2*d j,
  close*factor/2 adjusted_close,
  CASE WHEN i>=3 THEN ma END ma3,
  CASE WHEN i>=3 THEN ma+2*sd END boll_upper,
  CASE WHEN i>=3 THEN ma-2*sd END boll_lower
 FROM stage2
), expected(i, dif_e, dea_e, hist_e, k_e, d_e, j_e, adjusted_e) AS (
 VALUES
 (1,0.0,0.0,0.0,50.0,50.0,50.0,50.0),
 (2,0.16666666666666667,0.11111111111111111,0.11111111111111111,
    55.55555555555556,51.85185185185185,62.96296296296296,101.0),
 (3,0.3055555555555556,0.24074074074074073,0.12962962962962962,
    62.03703703703704,55.24691358024691,75.61728395061728,102.0)
)
SELECT c.*, abs(dif-dif_e)<1e-10 AND abs(dea-dea_e)<1e-10
 AND abs(hist-hist_e)<1e-10 AND abs(k-k_e)<1e-10 AND abs(d-d_e)<1e-10
 AND abs(j-j_e)<1e-10 AND adjusted_close=adjusted_e
 AND (i<3 OR (abs(ma3-101.0)<1e-10
  AND abs(boll_upper-102.63299316185545)<1e-10
  AND abs(boll_lower-99.36700683814455)<1e-10)) passed
FROM calculated c JOIN expected USING(i) ORDER BY i
