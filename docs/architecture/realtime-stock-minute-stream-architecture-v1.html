A股实时分钟流架构方案 v1

本文只讨论 Tushare 0374 rt_min 的 A 股实时分钟能力。它不是离线数据集，不落业务历史库，不进入 TaskRun / freshness / date audit。核心目标是：服务端在交易时段内轮询源站，把每个频率的最新分钟 K 线快照写入 Redis，业务 API、Ops 页面和后续 WebSocket 都只消费 Redis。

0. 调研结论

先把容易混淆的事实说清楚，避免方案跑偏。

主接口选择

rt_min 是实时分钟最新快照接口，适合做实时流主链。rt_min_daily 是单只股票当日分钟序列接口，不适合作为全市场实时主采集。

身份字段

实时分钟的一条快照不能只靠 ts_code 识别，必须使用 freq + ts_code。源端显式请求 freq 后会返回该字段。

采集形态

实测 rt_min(ts_code="3*.SZ,6*.SH,0*.SZ,9*.BJ") 支持全市场通配符，周末返回上一交易日最后一分钟快照。

重要修正：第一次调研时因为手写 fields 未包含 freq，误判为接口不返回 freq。复测确认：显式请求 fields=ts_code,freq,time,open,close,high,low,vol,amount 时，单代码、多代码、全市场通配符都返回 freq。后续实现必须把 freq 纳入字段契约和身份键。
2026-05-17 再审计补充：本地源文档 0374_A股实时分钟.md 的输出参数表没有列出 freq，但 tushareMcp 实测 rt_min(ts_code="600000.SH", freq="1MIN", fields=["ts_code","freq","time","open","close","high","low","vol","amount"]) 返回 freq="1MIN"、time="2026-05-15 15:00:00"。因此实现以“当前代码 + 实测行为”校准，测试必须覆盖显式 fields，不能只按本地输出表推断。

1. 已拍板结论

以下结论来自 2026-05-17 评审拍板，后续实现必须按这里执行。

D1：V1 开启哪些频率？

源端支持 1MIN/5MIN/15MIN/30MIN/60MIN。如果全部开启，每轮要请求 5 次源站，每批约 5529 * 5 条快照。

结论：V1 五个频率全部开启：1MIN/5MIN/15MIN/30MIN/60MIN。

D2：Redis feed 如何分层？

方案 A：一个 feed，快照 key 使用 freq:ts_code。方案 B：每个频率一个 feed，例如 tushare_stock_rt_min_1min。

结论：每个频率一个 feed。它和源站请求一一对应，健康状态、stale、失败隔离更清楚，也最少改动现有 realtime store。

D3：采集频率与限速

实时分钟五个频率同时开，会按频率数放大请求量。Tushare 当前权限上限为 500 次/分钟，但 V1 不追求高频刷新。

结论：V1 初始阶段每个 feed 交易时段内每 60 秒采集一次。采集间隔必须做成配置项；V1 可先走服务端配置，后续纳入数据运营后台“实时流配置中心”。

D4：业务 API 是否允许默认频率？

如果 API 不传 freq 默认查 1MIN，调用简单但语义可能不清楚；强制传 freq 更明确。

结论：API 必须显式传 freq，接口层不接受默认值。前端可以默认选中 1MIN，但请求时仍必须带上 freq。

D5：是否接入 rt_min_daily？

rt_min_daily 只适合单只股票当日分钟序列，不支持多代码/通配符。周末实测返回空。

结论：暂时不接入。它可能更适合日内开盘时段获取单股当日分钟序列，等真实场景明确后另立题。

D6：停牌/退市旧时间行如何展示？

全市场返回中少量股票的 time 停在旧日期，这与实时日线一致，不能让 feed 整体失败。

结论：保留行，逐条暴露 quote_time。feed 健康看 collector 成功时间，不看所有股票时间是否等于今天。

D7：Ops 页面形态

实时流监控已有股票实时日线卡片。实时分钟可以作为同一菜单下的第二个 feed group。

结论：必须做。复用“实时流监控”一级菜单，不新增菜单；页面增加“股票实时分钟”分组，按频率展示健康。

D8：开市验证门禁

2026-06-01 开市时段已完成真实验证：五频率全市场均返回 5525 行，身份字段无缺失，freq 与请求一致。

结论：验证记录见 M3 开市真实验证记录；M4 provider / normalizer / 单频发布能力已按该记录落地。

2. 源接口事实

以本地文档、MCP 和真实请求共同校准。

接口 用途 输入 输出 结论
rt_min A 股实时分钟最新 K 线 freq 必填；ts_code 必填；支持多代码；实测支持通配符。 ts_code,freq,time,open,close,high,low,vol,amount。其中 freq 需要显式放入 fields。 V1 主链候选。
rt_min_daily 单只股票当日开盘以来分钟序列 freq 必填；ts_code 必填；文档说明仅单代码。 多行分钟序列，包含 freq。 不做 V1 主链，只作为后续单股分时详情候选。
rt_idx_min 指数实时分钟 类似 rt_min，但指数代码池不同。 类似 rt_min。 不是本轮目标，但架构应能复用 feed 模型。
真实请求摘要：rt_min 全市场通配符在 2026-05-17 周日返回 5529 行；其中 SZ 2898、SH 2317、BJ 314。1MIN/5MIN/15MIN/30MIN/60MIN 均返回 5529 行。limit=10 和 offset=1000 对全市场通配符实测没有改变返回行数，因此 V1 不依赖分页拉全市场。

3. V1 边界

先把不做什么说清楚。

V1 做

实时 collector Redis 最新快照 短期 batch/delta stream 业务 snapshot API Ops health API 实时流监控页面扩展

V1 不做

不落业务历史库 不建 DatasetDefinition 不进 TaskRun 不进 freshness/date audit 不做 rt_min_daily 分时详情 不做 WebSocket 正式推送
实时分钟和离线 stk_mins 是两条系统。离线分钟行情追求可追溯、可重跑、可落库；实时分钟只追求当前最新快照、短期事件流和低延迟读取。不要把离线 ingestion 的 DatasetDefinition / ExecutionPlan / writer 引入实时主链。

4. 架构关系

复用当前 realtime 子系统，但新增股票实时分钟 feed。

Market Clock 交易日 + 采集时段判断
Collector 按频率请求 rt_min
Normalizer 校验 freq/ts_code/time
Redis Store batch + current pointer
Biz API 按 freq + ts_codes 查快照
Ops API 健康、行数、耗时、错误
服务端 collector 是唯一会请求 Tushare 的组件。业务 API、Ops 页面、后续 WebSocket 均不得直接请求 Tushare，也不得自行扫描 Redis 拼装事实，只能读取当前 feed 的 current_batch。

5. Redis 模型

推荐每个频率一个 feed，快照仍保留源端 freq 字段。

推荐 feed_key

tushare_stock_rt_min_1min
tushare_stock_rt_min_5min
tushare_stock_rt_min_15min
tushare_stock_rt_min_30min
tushare_stock_rt_min_60min

快照业务身份

identity = {
  "freq": "1MIN",
  "ts_code": "600000.SH"
}

snapshot_key = ts_code
feed_key 已经表达 freq
Redis key 含义
rt:feed:{feed_key}:current_batch 当前完整批次指针，最后一步切换。
rt:feed:{feed_key}:batch:{batch_id}:snapshot:{ts_code} 某一频率 feed 下，某只股票的最新分钟 K 快照。值中仍保留 freq。
rt:feed:{feed_key}:batch:{batch_id}:meta 批次元信息：行数、源接口耗时、发布时间、请求参数、频率。
rt:feed:{feed_key}:stream:batch 批次发布事件，支撑观测和后续推送。
rt:feed:{feed_key}:stream:delta 变化股票事件，后续 WebSocket 可消费。
rt:feed:{feed_key}:health collector 运行状态、最后请求、错误、当前批次年龄。
如果评审选择“单一 feed + freq:ts_code 复合 snapshot key”，则需要扩展当前 realtime store 的快照读取接口，使它支持通用 identity key，而不是只按 ts_code 读。推荐每频率一个 feed，是为了保持实现边界更稳。

6. Collector 设计

交易时段内采集，非交易时段只写健康空闲状态。

请求参数

api_name = "rt_min"
params = {
  "ts_code": "3*.SZ,6*.SH,0*.SZ,9*.BJ",
  "freq": "1MIN"
}
fields = [
  "ts_code", "freq", "time",
  "open", "close", "high", "low",
  "vol", "amount"
]

交易时段

沿用当前实时日线口径：交易日的 09:30-11:30、13:00-15:00 请求源站。其他时间不请求 Tushare。

采集间隔

V1 初始阶段每个频率 feed 的采集间隔为 60 秒，必须通过服务端配置控制，不允许写死。后续实时流配置中心应统一管理实时日线和实时分钟的启停、频率、间隔与阈值。

字段校验

每行必须有 ts_code、freq、time。若源端返回 freq 与请求频率不一致，该行进入异常统计，不静默覆盖。

批次发布顺序：先完整写入某频率的新 batch snapshot、index、meta 和 stream 事件，再切换 current_batch。读取方永远只读 current pointer 指向的完整批次，避免半批数据。
调度约束：“一个 systemd 服务”不等于“一个串行大循环”。实现时必须按 feed 判断是否到期，逐个 feed 独立执行、独立捕获异常、独立写 health；单个频率超时或失败不能阻塞日线和其他分钟频率。若采用串行实现，必须用配置化 source timeout 与测试证明五频率一轮可以稳定落在采集间隔内；否则应使用有界并发执行，但仍保持同一个 collector service。

7. 配置模型与落地边界

先把“现在如何配置”和“后续配置中心如何接管”分清楚，避免散落到 env、代码常量和页面展示里。

当前日线现状

股票实时日线已经有服务端配置项，例如启停、采集间隔、交易时段、stale 阈值、TTL、保留批次数、stream 裁剪和通配符。它们来自 Settings / env，不是从数据运营后台页面配置。

分钟 V1 落地边界

股票实时分钟 V1 也先走服务端配置，不在本轮实现可编辑配置页面。但实现时必须从配置读取，不允许把 60 秒、五个频率、交易时段、阈值写死在 collector、API 或前端里。

配置审计硬门禁：实时分钟开发前必须把所有新增配置项集中声明在 Settings 的 realtime 区域，并同步写入部署 env 示例、Ops health 返回、测试用例和本文档。V1 的持久化位置是服务端 env 文件（生产为 /etc/goldenshare/web.env），不是页面常量，也不是散落在 collector 内的 Python 常量。后续若建设配置中心，必须先设计单一配置读取服务，再让 collector、API 和 Ops 页面统一消费。
M2 收口结果：实时分钟 collector 开发前置项已明确为 src/foundation/realtime/feed_config.py 单一读取层。该模块从 Settings / env 生成 RealtimeStockRtDailyConfig 与 RealtimeStockRtMinConfig，并集中校验配置关系。日线已有代码消费该配置对象，collector、CLI、Biz API、Ops API 不再分散读取 settings.realtime_stock_rt_daily_*；日线 lease TTL 通过 REALTIME_STOCK_RT_DAILY_LEASE_TTL_SECONDS=30 配置。
配置项 V1 建议值 归属 说明与关联约束
REALTIME_STOCK_RT_MIN_ENABLED false 服务端 env / Settings 控制股票实时分钟 collector 是否启用。默认关闭，部署验收后再打开。
REALTIME_STOCK_RT_MIN_ENABLED_FREQS 1MIN,5MIN,15MIN,30MIN,60MIN 服务端 env / Settings 控制启用哪些频率。V1 拍板为五个频率全开，但仍必须配置化。
REALTIME_STOCK_RT_MIN_POLL_INTERVAL_SECONDS 60 服务端 env / Settings 每个频率 feed 的采集间隔。五频率全开时约等于每 60 秒 5 次源站请求，约 5 次/分钟。它决定源站请求量、stale 阈值和 lease TTL 的下限。
REALTIME_STOCK_RT_MIN_COLLECTION_SESSIONS 09:30-11:30,13:00-15:00 服务端 env / Settings 源站请求窗口。非交易日、非交易时段不请求 Tushare。
REALTIME_STOCK_RT_MIN_STALE_AFTER_SECONDS 90（建议） 服务端 env / Settings 只用于采集时段内判断 Redis 当前批次是否滞后，不用于非采集时段误报。建议至少大于 poll_interval_seconds * 2，避免一次正常抖动就被判 stale。
REALTIME_STOCK_RT_MIN_MAX_CALLS_PER_MINUTE 20（建议） 服务端 env / Settings 用于运行观测和后续硬限流。必须满足 enabled_freq_count * 60 / poll_interval_seconds <= max_calls_per_minute。V1 五频率、60 秒间隔的理论请求量约 5 次/分钟。
REALTIME_STOCK_RT_MIN_LEASE_TTL_SECONDS 90（建议） 服务端 env / Settings 避免多个 collector 同时刷新同一个 feed。必须覆盖单个 feed 的源站请求、归一化、Redis 发布和网络抖动；建议不小于 poll_interval_seconds * 3。
REALTIME_STOCK_RT_MIN_SOURCE_TIMEOUT_SECONDS 20（建议） 服务端 env / Settings 单次请求 Tushare 的超时上限。必须小于 lease TTL，并与 poll interval 匹配；超时只影响对应 feed，不应拖死其他 feed。
REALTIME_STOCK_RT_MIN_SNAPSHOT_TTL_SECONDS 259200 服务端 env / Settings 沿用实时日线 TTL 口径，覆盖午休、隔夜和周末展示。
REALTIME_STOCK_RT_MIN_KEEP_RECENT_BATCHES 3 服务端 env / Settings 每个频率 feed 仅保留最近批次，避免 Redis 长期膨胀。
REALTIME_STOCK_RT_MIN_BATCH_STREAM_MAXLEN 5000（建议） 服务端 env / Settings 批次发布事件 stream 裁剪上限。用于 Ops 观测与后续排障，不用于业务历史沉淀。
REALTIME_STOCK_RT_MIN_DELTA_STREAM_MAXLEN 200000（建议） 服务端 env / Settings 逐股票变化事件 stream 裁剪上限。为后续 WebSocket 预留；若内存压力明显，应先调小该值，而不是改变快照 key 模型。
REALTIME_STOCK_RT_MIN_TS_CODE_PATTERN 3*.SZ,6*.SH,0*.SZ,9*.BJ 服务端 env / Settings 请求全市场通配符。该值属于源站采集配置，只能由 collector 使用；业务 API 和前端不得暴露或传入通配符。
后续配置中心边界：数据运营后台“实时流配置中心”应统一管理实时日线与实时分钟的启停、采集间隔、启用频率、stale 阈值、TTL、stream 裁剪和源站限速。V1 的 Ops 页面只读 health API 展示配置与运行状态，不提供编辑能力；配置编辑能力必须另立需求，避免本轮实现被配置后台拖大。
配置关系基线：配置不是孤立开关。poll_interval_seconds 决定理论请求量；enabled_freqs 放大请求量；max_calls_per_minute 必须覆盖理论请求量；lease_ttl_seconds 必须大于单 feed 最长处理时间；stale_after_seconds 必须大于正常采集间隔加抖动；snapshot_ttl_seconds 和 keep_recent_batches 共同决定 Redis 保留规模。任何改动这些配置的需求，都必须先重新计算关系，不允许只改一个值。
实现约束：前端不得写死 60 秒、五频率或交易时段；业务 API 不得根据页面常量推导配置；Ops API 必须从服务端配置与 Redis health 汇总出展示字段。后续如果切到数据库配置，collector、API、Ops 页面都应通过同一个配置读取服务消费，不允许各自读不同事实源。

8. API 契约草案

只定义读取 Redis 的服务端 API，不暴露 Tushare 参数。

业务快照 API

GET /api/v1/realtime/stock-rt-min
  ?freq=1MIN
  &ts_codes=600000.SH,000001.SZ

返回指定频率、指定股票列表的当前分钟快照。单次 ts_codes 上限建议沿用 200。

Ops 健康 API

GET /api/v1/ops/realtime/stock-rt-min/health
GET /api/v1/ops/realtime/stock-rt-min/health?freq=1MIN

不触发采集，只读 Redis health 和 current batch meta。页面局部刷新。

API 不接受 Tushare 通配符，不接受 limit/offset，不允许缺省 freq，不让调用方理解源站分页。调用方只知道我们的业务概念：频率、股票代码列表、当前快照。

10. 质量与风险

这些点必须在实现和验收里卡住。

字段风险

freq 是关键身份字段。实现必须显式请求并校验；测试要覆盖 connector payload 的 fields，防止再次只看默认字段。

分页风险

文档写有 limit/offset，但全市场通配符实测不受影响。V1 不依赖分页；如果后续发现开市时分页行为变化，再单独评估。

旧行情时间

少量股票可能停在旧日期。不能把这当 feed 失败；业务返回应保留每只股票自己的 time。

写入规模

单频率每批约 5529 条。五频率同时开约 27645 条。Redis TTL 72 小时 + 最近 3 批可控，但 stream delta 需要裁剪。

配置风险

采集间隔、启用频率和 stale 阈值必须来自配置。V1 不做页面配置，但不能把 60 秒、五频率、阈值写死在 collector 逻辑里。

11. 里程碑建议

按小步推进，避免把实时分钟、指数实时、WebSocket 混在一起。

12. 落代码前链路审计

基于当前 realtime 日线代码逐项核验，下面这些是实现时必须遵守的边界。

链路点 当前代码事实 实时分钟实现约束
配置来源 实时日线已经通过 Settings / env 配置启停、采集间隔、交易时段、stale、TTL、保留批次等；不是后台页面配置。 实时分钟 V1 同样走 Settings / env。不得把 60 秒、五频率、交易时段或阈值写死到 collector、API 或前端。
collector 服务拓扑 当前部署脚本和 sudoers 只管理一个 goldenshare-realtime-collector.service。 V1 优先扩展现有 realtime collector 服务，让它同时承载日线和分钟 feed。好处是部署脚本、sudoers、unit 同步、状态检查和远程验收不扩一套；风险是如果循环写成串行大循环，分钟故障可能拖慢日线。因此实现必须做到 feed 级独立 try/catch、独立 lease、独立 health、独立 batch；某个分钟频率失败只能标记该 feed degraded，不能拖死日线。不要擅自新增第二个 systemd 服务；若未来因为耗时、故障隔离或容量压力需要拆服务，必须同步部署脚本、sudoers、unit 同步、监控和运维验收方案。M2 已将 CLI 入口收口为 realtime-collector-serve，并同步 systemd ExecStart。
Tushare 客户端限速 TushareHttpClient 通过 realtime feed config 获取 rt_k 与 rt_min 的实时流限速。 rt_min 必须接入 realtime feed config 的限速口径。由于五个频率都调用同一个源接口 rt_min，客户端限速应按 api_name=rt_min 聚合，控制全体分钟 feed 的总请求量，而不是给每个频率各自一套 20/min。这样才能保证“五频率、60 秒间隔”约 5 次/分钟的总请求量不被代码路径绕开。
Redis 快照键 RealtimeStateStore 的 snapshot key 以 ts_code 为核心，读取接口也是 feed_key + batch_id + ts_codes。 按频率拆 feed 是必要约束：tushare_stock_rt_min_1min 等。Redis key 示例为 rt:feed:tushare_stock_rt_min_1min:batch:{batch_id}:snapshot:600000.SH。该 key 长度在百字节量级，Redis 字典查询主要是 O(1) 哈希查找，V1 每批约数千到数万 key，不是主要性能瓶颈；真正要关注的是源站请求耗时、网络、Redis 写入批量和 stream 裁剪。为避免未来误判，V1 不因 key 较长去改短命名或改复合键；如果未来 Redis 内存或网络成为瓶颈，应先通过 Redis memory、keyspace、pipeline 写入耗时和 API latency 证据判断，而不是凭 key 字符串长度下结论。不要在 V1 改造 store 去支持 freq:ts_code 复合键。
批次发布 当前 store 在 Redis transaction 内写 batch snapshot / meta / current pointer / stream，满足“完整批次后切 current”。 实时分钟必须复用该发布语义。每个频率独立发布 batch，不允许 API 读半批，也不允许页面直接扫 Redis key 拼结果。
lease TTL 实时日线 collector 的 lease TTL 已进入 REALTIME_STOCK_RT_DAILY_LEASE_TTL_SECONDS 配置。 实时分钟不要无脑复制硬编码 TTL。lease TTL 是实时流通用配置，不是分钟线局部参数。它应进入统一配置模型，至少要覆盖单个 feed 一轮请求、归一化、Redis 发布和网络抖动，避免长耗时导致租约提前过期。实现和测试必须覆盖 lease TTL 配置解析与过期边界。
源站请求字段 日线 provider 显式传 fields；本次调研已确认 rt_min 只有显式请求 freq 才能稳定拿到身份字段。 分钟 provider 必须显式请求 ts_code,freq,time,open,close,high,low,vol,amount，并校验返回 freq 与请求频率一致。
业务 API 日线 API 只要求 ts_codes，读取固定日线 feed。 分钟 API 必须同时要求 freq 和 ts_codes；缺任一项都返回 400。API 只能按 freq 映射到对应 feed，禁止默认 1MIN 或扫描全部频率。
Ops health 现有 Ops realtime health API 和前端页面只服务股票实时日线单 feed。 分钟 V1 不能只加一个后端接口就完事。Ops 页面、schema、query key、类型定义要升级为“日线 + 分钟分组”，分钟分组按五个频率展示。
页面轮询 现有页面按 health API 返回的 page_polling_enabled 和 recommended_poll_interval_seconds 局部刷新。 继续保持页面只读 health API；前端不得自己判断交易日/交易时段，不得用页面常量决定 collector 行为。
测试门禁 现有测试覆盖日线 collector、业务 API、Ops health。 分钟 V1 分阶段新增：配置解析、五频率 feed key、provider fields 包含 freq、freq 必传、feed 隔离已在 M2/M4 覆盖；统一 collector 调度、单频率异常隔离、分钟 health、非采集时段不请求源站已在 M5 覆盖；Ops 多频率 health API 和页面分组渲染留到 M6-M7。

13. 验收标准

本节是开发完成判定标准。没有全部满足，不算实时分钟 V1 完成。

验收项 必须满足的标准 建议测试覆盖
Settings 收敛 实时日线与实时分钟所有运行配置必须通过 realtime feed config 单一读取层输出；collector、CLI、Biz API、Ops API 不得分散读取 settings.realtime_stock_rt_daily_* 或 settings.realtime_stock_rt_min_*；不得保留 LEASE_TTL_SECONDS 这类运行配置硬编码。 配置单元测试覆盖默认值、env 覆盖、非法关系拒绝、日线 lease TTL 从配置读取、分钟五频率配置解析。
配置关系校验 enabled_freq_count * 60 / poll_interval_seconds <= max_calls_per_minute 必须被校验；lease_ttl_seconds 必须覆盖采集间隔与源站超时；stale_after_seconds 必须大于正常采集间隔加抖动。 测试非法频率、过低 max calls、过低 lease TTL、过低 stale 阈值时启动配置构建失败。
Collector 全链路 同一个 realtime collector 服务中，日线和分钟 feed 独立运行。任一分钟频率失败只影响该 feed 的 health，不影响日线和其他分钟频率。systemd 仍只管理一个 realtime collector 服务，但启动命令必须从日线专属语义收口为通用 collector 语义。 collector 测试覆盖五频率发布、单频率异常隔离、非采集时段不请求源站、Redis 不可用降级、lease 未获取时跳过；部署脚本检查覆盖通用 collector 命令。
Tushare 限速 rt_min 全频率必须共享同一个源接口限速桶，限速值来自 realtime feed config。五频率全开、60 秒间隔时，实际总请求量应约为 5 次/分钟，不能回落到通用 Tushare 默认限速。 单元测试覆盖 rt_min 限速读取分钟配置；collector 调度测试覆盖五频率一轮请求数与 health 中的 request count。
Redis feed 隔离 五个分钟频率必须写入不同 feed key；同一个 ts_code 在不同频率下不能覆盖；读取 API 必须按 freq 定位 feed。 state store / API 测试覆盖 1MIN 与 5MIN 同股票不同快照、current batch 独立、missing codes 独立。
源接口字段契约 provider 必须显式请求 ts_code,freq,time,open,close,high,low,vol,amount；返回 freq 与请求不一致时不能静默覆盖。 provider 单元测试校验 Tushare 请求 payload 的 fields 和 params；normalizer 测试覆盖缺 freq、缺 ts_code、freq 不一致。
业务 API GET /api/v1/realtime/stock-rt-min 必须显式要求 freq 与 ts_codes；缺参返回 400；不允许默认 1MIN；不接受通配符和源站分页参数。 Web API 测试覆盖成功读取、缺 freq、非法 freq、缺 ts_codes、超过 200 个代码、feed 不可用。
Ops API 与页面 实时流监控页面必须展示日线和分钟分组；分钟按五个频率展示 health。页面只读 Ops health API，不直接调用业务 API、不读 Redis、不自行判断交易时段。 Ops API 测试覆盖多 feed health 聚合；前端测试覆盖分组渲染、五频率状态、错误态、页面局部轮询条件。
部署与环境 env 示例、远程 env 配置说明、systemd collector 启动命令、部署脚本行为必须与单服务承载方案一致。新增配置项必须可在 health API 中观测。 部署脚本静态检查、配置示例检查、health payload schema 测试、远程 smoke 验收。
开市真实验收 生产启用前必须在开市时段记录全频率返回行数、源站耗时、Redis 写入耗时、time 是否推进、异常旧时间样本、Ops 页面状态。 开市 smoke 记录归档；如果任一频率异常，必须定位到源站、配置、collector、Redis 或页面中的具体层级。
