生产后端：四层主系统

当前后端已经收敛为 foundation / ops / biz / app。后续开发不能回流到 platform 或 operations。

foundation

数据基座：源站连接、DAO/model、DatasetDefinition、ingestion 执行计划、数据写入、serving 发布、基础 contracts。

不得依赖 ops/biz/app

ops

运维治理：TaskRun、scheduler/worker、manual actions、freshness、dataset cards、schedule/probe、审查中心、实时流配置。

面向运营后台

biz

业务查询与用户侧 API：行情、quote、realtime、wealth market 各模块 API/query/schema/service。

面向业务消费

app

组合根：FastAPI 路由聚合、auth/admin、依赖注入、异常处理、web/static 运行壳。

装配层，不写业务规则
DatasetDefinition 定义数据集身份、来源、日期模型、输入、存储、规划、事务、观测。
DatasetActionRequest 表达用户或调度意图：维护哪个数据集、时间输入和业务筛选。
DatasetActionResolver 按 Definition 归一化意图，不在 Ops 或前端拼源站参数。
DatasetExecutionPlan 执行器消费的标准计划：source、planning、writing、transaction、units。
IngestionExecutor 执行 source fetch、normalize、write、progress，并按 unit/事务策略提交。
TaskRun 记录运行意图、节点、问题诊断和页面可观测状态。
当前最关键的架构事实： 数据集静态事实源只在 src/foundation/datasets/** 的 DatasetDefinition；数据维护运行投影只在 src/foundation/ingestion/** 的 DatasetExecutionPlan；任务运行与详情观测只走 src/ops/** 的 TaskRun 主链。

源站情况

源站事实和工程实现分层维护。源站文档只记录接口侧事实，数据集实现口径落在 DatasetDefinition 与数据集开发文档。

Tushare

当前主数据源。docs/sources/tushare/ 已按专题沉淀本地接口文档，包含股票、指数、ETF、基金、期货、港美股、债券、新闻语料等分类，并有 docs_index.csv 做索引。

source_key=tushare DatasetDefinition.source_doc_id

BIYING

当前作为另一个源站接入点，代码中有 connector、raw 表和部分数据集测试；docs/sources/biying/ 目前只有 README 摘要，后续新增接口时需要补齐源站文档。

source_key=biying 源文档仍需按接口补充

Biz 自建表

运营后台数据源页存在 biz_tableset 只读展示分支，用于展示业务表来源，不是外部源站，也不进入 DatasetDefinition 手动维护入口。

只读展示 不是 connector
层级 真实位置 职责 常见改动 注意
源站文档 docs/sources/** 记录源接口字段、参数、分页、限速、更新时间和源链接。 新增或修正接口说明。 禁止写本仓落库设计；Tushare 新增/改名需同步 docs_index.csv。
源站注册 src/foundation/datasets/source_registry.py 当前 source selection 暴露 tushare、biying，另有 all、combined 特殊选择。 新增源站 key 或展示名。 改 source key 会影响 Ops/API/前端消费者，必须做全量审计。

数据集事实 src/foundation/datasets/definitions/** 声明 source_key、adapter、api_name、source_fields、request_builder、base_params 等。 新增数据集、修改字段、时间模型、分页、写入目标。 任何 Definition 改动都要审计 manual actions、catalog、workflow、resolver、request builder、freshness、前端和测试。

数据运营后台情况

这里指生产运维系统：后端在 src/ops，前端在 frontend，API 最终挂在 /api/v1/ops/**。

后端 API

src/ops/api/router.py 聚合 overview、freshness、schedules、probes、realtime、catalog、manual_actions、dataset_cards、review_center、date_completeness、codebook、task_runs 等路由。

运行时

任务中心采用队列模型：Web/API 创建 queued TaskRun，独立 scheduler/worker claim 后推进，Web 请求内不直接跑长任务。

前端页面

frontend/ 是 React 19 + TypeScript + Vite + Mantine + TanStack Query/Router；basepath 是 /app。

能力 当前事实源 主要 API / 页面 说明
数据状态总览 ops.dataset_status_snapshot + 轻量重算 GET /api/v1/ops/freshness, GET /api/v1/ops/dataset-cards 页面只能消费统一读模型，不扫描业务表自行推断。
数据源管理 DatasetDefinition projection + freshness /app/ops/v21/datasets/tushare, /app/ops/v21/datasets/biying 展示源下数据集健康度，不承载策略编辑。
手动维护 DatasetDefinition.capabilities + action catalog GET /api/v1/ops/manual-actions, POST /api/v1/ops/manual-actions/{action_key}/task-runs 提交的是任务请求，不是“立即执行长任务”。
任务记录与详情 ops.task_run / task_run_node / task_run_issue GET /api/v1/ops/task-runs*, GET /api/v1/ops/task-runs/{id}/view 完整技术诊断只在 issue 读取；前端不拼旧 steps/events/logs。
自动任务 ops.schedule + probe_rule /api/v1/ops/schedules*, /api/v1/ops/probes* 目标统一用 target_type/target_key 表达。
审查中心 src/ops/api/review_center.py frontend/src/pages/ops-v21-review-*.tsx 一期只读，按领域组织，不按技术对象暴露。
实时流监控与配置 src/ops/api/realtime.py, src/foundation/realtime/** frontend/src/pages/ops-realtime-*.tsx 日线与分钟流已有页面与配置中心基础。
不要恢复旧任务链路： 任务记录、任务详情、重试、停止和手动提交统一消费 /api/v1/ops/task-runs* 与 /api/v1/ops/manual-actions/{action_key}/task-runs。不得恢复已废弃的 executions 路径、旧 steps/events/logs 或历史同步运行日志作为页面事实源。

数据湖情况

lake_console 是本地独立工程，不是生产 Ops 子模块。它管理本地移动盘 Parquet Lake，并逐步承接 Dagster 新湖资产编排。

lake_console/backend

本地 FastAPI + CLI。负责 Lake Root 检查、文件事实扫描、DuckDB sample/query、Sync Center、Tushare 同步、prod-raw/core 只读导出、Kopia Recovery、Parquet 写入与计算。

python3 -m lake_console.backend.app.main lake-console CLI

lake_console/frontend

独立 Vite/React 前端，默认端口 5178。页面数据必须来自 lake backend，不 import 生产 frontend/src/**。

npm run dev 本地管理台，不挂生产 Web

lake_console/orchestrator

正式 Dagster 项目，目标是用 assets、jobs、sensors、asset checks、partitions 管理新数据湖 data_lake/raw|silver|gold。

Dagster 1.13.8 执行命令需用户批准
湖侧对象 当前口径 典型路径或命令 边界

湖侧性能门禁： 涉及 Sync Center、DuckDB 计算、Parquet 写入、prod-db export、Tushare 拉取、历史批量或全市场同步时，编码前必须列性能测算表：对象数、日期数、分区数、请求数、行数、文件数、DuckDB scan/write 量、spill 风险、提交粒度、预计耗时、磁盘与配额影响、拒绝策略和 dry-run/样本验证。无法测算就停下改方案。

用户侧行情前端

wealth/ 是财势乾坤行情系统的独立用户侧前端。它和运营后台 frontend/ 同仓但不是同项目。

工程定位

面向普通用户的行情体验，当前主线是市场总览、股票详情等页面逐步接入真实后端 API。

技术栈

React + TypeScript + Vite + Vitest，另使用 lightweight-charts 承载行情图表。

API 命名空间

用户侧真实 API 统一走 /api/v1/wealth/market/{module}；后端由 src/biz/api/wealth/market/** 接入。

开发边界： wealth 不共享运营后台 Shell、路由、页面结构或视觉体系。做用户侧页面前看 wealth/AGENTS.md 与 wealth/docs/system/**，不要拿 frontend/ 的后台页面模式套过去。

按任务找入口

后续开发者最常见的切入点。先按任务类型找到文档和代码，再用 CodeGraph 看调用链与影响面。

新增或修改生产数据集

  1. 先看 docs/sources/** 源接口事实；Tushare 必须实测。
  2. 写或更新 docs/datasets/*-dataset-development.md。
  3. 落 src/foundation/datasets/definitions/** 的 DatasetDefinition。
  4. 审计 ingestion resolver/unit planner/request builder/writer。
  5. 接 Ops manual actions、dataset cards、freshness、date completeness、前端时间控件。
  6. 补正向和负向测试，特别是“只允许/不得/默认只取”的反例。

改 Ops API 或任务中心

  1. 先读 Ops 当前契约 与 API reference。
  2. 后端看 src/ops/api|schemas|queries|services|runtime。
  3. 任务详情只走 TaskRun view API；问题详情只读 issue。
  4. 前端看 frontend/src/pages/ops-v21-*.tsx 与 frontend/src/shared/api。
  5. 验证至少覆盖 tests/web/test_ops_*.py 和前端 typecheck/test。

改本地 Lake Console

  1. 先读 lake_console/AGENTS.md 与 Local Lake 架构方案。
  2. 涉及数据接口、同步、导出、Parquet 写入时，先列性能测算表。
  3. backend 看 lake_console/backend/app/api|services|sync|catalog。
  4. frontend 看 lake_console/frontend/src，不得 import 生产前端。
  5. 验证用 lake_console/backend/tests 或 tests/lake_console 的定向测试。

改 Dagster 新湖编排

  1. 先读 lake_console/orchestrator/AGENTS.md、编码规范和相关设计。
  2. 先做设计确认，再改 assets/resources/checks/jobs/sensors。
  3. active asset 事实必须登记 LAKE_ASSET_CATALOG。
  4. 正式 DuckDB 连接走 DuckDBResource 或统一 helper。
  5. 未获用户批准，不运行任何会触碰正式 Dagster instance 或正式湖的命令。

改生产运营后台前端

  1. 先读 frontend/AGENTS.md 与前端当前强约束。
  2. 遵守 Mantine 主 UI 基座，不引入第二套组件体系。
  3. 页面消费后端事实字段，不在页面自行推断状态。
  4. 复用 frontend/src/shared/ui 和 shared/api。
  5. 验证顺序：typecheck、check:rules、test、build，必要时 smoke/visual。

改用户侧行情前端

  1. 先读 wealth/AGENTS.md 与 wealth/docs/system/**。
  2. 按模块三件套推进真实 API，不回退旧聚合或 mock 口径。
  3. 后端 API 放 src/biz/api/wealth/market/** 对应模块。
  4. 前端分层遵守 app/pages/features/shared/styles。
  5. 验证用 wealth npm run typecheck/test/build 和相关真实 API smoke。

硬边界

这些边界比“方便实现”优先级更高。遇到冲突先停下来说明，不要靠临时兼容或补丁绕过。

生产子系统依赖方向

foundation 不得依赖 ops/biz/app/platform/operations；ops 不得依赖 biz；biz 不得依赖 ops/operations；app 只做装配。

legacy 冻结

src/platform 与 src/operations 只作为 legacy 占位和清理对象，不承接新主实现，不新增兼容主链。

状态写入不影响业务数据

Ops/TaskRun/freshness/snapshot/schedule 状态写入失败，只能影响观测状态；不得阻塞、回滚或污染 raw/core/core_serving 等业务数据。

配置与迁移不能猜

新增配置项先做审计。新增 Alembic migration 前先查真实 head。涉及生产库、远程服务、Tushare、ClickHouse、Postgres 等命令按本机/审批规则执行。
