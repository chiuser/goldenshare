## 2. 已验证的源接口事实

2026-08-25 至 2026-08-28 的真实请求确认：

```text
api_name=rt_etf_min
ts_code=5*.SH,1*.SZ
freq=1MIN|5MIN|15MIN|30MIN|60MIN
fields=ts_code,freq,time,open,close,high,low,vol,amount
```

请求不需要 `topic`。固定事实：

| 项 | 验证结果 |
| --- | --- |
| 必填参数 | `ts_code`、`freq` |
| 频率 | `1MIN/5MIN/15MIN/30MIN/60MIN` |
| 通配符 | `5*.SH`、`1*.SZ` 和组合值均有效 |
| 返回形态 | 每个代码返回当时最新一根对应频率 K 线，不是全天序列 |
| 身份 | `ts_code/freq/time` |
| 组合规模 | 2026-08-26 下午曾返回 2,325 行；早盘曾为 2,329-2,332 行，不能固化行数 |

本地源文档写“单次最大 1,000 行”，但真实组合请求已经超过该数量。当前证据支持一次沪深组合通配符请求，不支持按代码逐只请求或因旧文档数字强行分片。

## 3. 已验证的闭合与传播事实

源端是“已闭合 K 线逐代码传播”，不是整批原子切换：

1. `1MIN` 同一分钟切换后内容稳定，下一分钟才出现新行。
2. `5/15/30/60MIN` 只在各自窗口闭合后出现新 K 线。
3. `09:30` 是独立一分钟 K 线；`09:35` 的首根五分钟 K 线精确覆盖 `09:31-09:35`。
4. 午休不产生新窗口；下午 `30MIN/60MIN` 网格按交易时段重新计算。
5. 普通请求约 0.5-0.8 秒，已观测最大 4.449 秒。
6. 历史测量参考集合在普通边界通常约 15 秒完整，但共同频率边界和收盘可能到 35-46 秒才完整。

这些证据支持候选调度时点：闭合后 `+15s` 首次尝试，必要时 `+30s/+45s` 重试，`+55s` 截止，每频率每槽最多 3 次，源请求总墙钟 timeout 8 秒，频率顺序 `1MIN,5MIN,15MIN,30MIN,60MIN`。这些是源端时序证据，不是对尚未实现系统的开发授权。

## 4. 仍然有效的架构边界

如果重新基线后批准开发，仍需遵守：

1. 不进入 `DatasetDefinition`、TaskRun、freshness 或 date audit。
2. 不新增第二个 systemd 服务，继续由统一 realtime collector 承载。
3. 源请求保持沪深组合通配符；下游范围不能反向制造逐 ETF 源请求。
4. 不新增普通用户 API 或 WebSocket。
5. 行情批次与 Health 不混入告警业务规则。
6. 请求失败或就绪集合未达到目标分钟时不得发布残缺批次，上一 current pointer 保持有效。
7. Redis 发布成功后的清理失败只能影响维护观测，不能反转已发布事实。

## 5. 必须重新拍板的问题

以下问题没有答案前，LLD 不得恢复为可执行状态：

1. 哪些 ETF 构成每个槽的就绪判断集合；该集合是全市场、Basic 当前资格、运营子集，还是其他明确主数据合同。
2. Redis 保存全市场源端结果还是某个已批准范围；读者和 Health 看到的覆盖口径是什么。
3. 运营是否需要成员管理页面；若需要，其事实源、写入边界和历史可追溯性是什么。
4. 范围变化在同一槽内如何冻结，以及 batch meta 保存什么可复算身份。
5. Redis 容量实测。原方案的 snapshot 数估算依赖旧选择池，已失效；必须用重新基线后的真实范围在隔离 namespace 测量。
6. 配置项的完整审计，包括默认值、持久化位置、所有消费者、发布校验和运维可见性。
