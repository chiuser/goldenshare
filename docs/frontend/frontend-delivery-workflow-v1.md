## 1. 任务产物按规模选择

| 任务 | 最小产物 |
| --- | --- |
| 小任务 | 目标、依据、影响文件、复用组件和验证结果 |
| 中任务 | 用户与场景、主/次任务与非目标、页面状态、技术摘要、测试方案、待决策 |
| 大任务/页面重做 | 完整交付简报：背景目标、用户任务、页面结构、状态设计、API 依赖、共享组件/token、验收、风险与待决策 |

不为小改动复制完整大项目模板；中等及以上任务按下面步骤执行。Phase2–6 已是历史阶段，不作为当前优先级。阶段结果和重入边界见[治理记录](/Users/congming/github/goldenshare/docs/frontend/frontend-governance-rollout-plan-v1.md)。

## 2. 从需求到上线

| 阶段 | 必须说清或验证 |
| --- | --- |
| 0 任务确认 | 修 bug、增量还是重做；谁使用；要完成什么动作；成功标准与影响页面 |
| 1 用户任务 | 场景、主任务、次任务、本轮不做；用使用者动作表达，不照抄内部对象 |
| 2 交互设计 | 首次加载、空、失败、有数据但异常、提交中、提交成功/失败；标题、筛选/操作、主内容、详情/抽屉/Modal、异步反馈 |
| 3 交互评审 | 主操作、首屏重点、筛选/表格层次、术语、完整状态、可复用组件；未通过不进入大规模编码 |
| 4 技术方案 | 文件、组件/子模块、API、URL 与局部状态、测试、写入范围；不把页面私有逻辑塞进共享层 |
| 5 实现 | 必要的 token/共享能力 → 页面骨架 → 数据交互 → 文案反馈；没有新增需要时直接复用，不为遵循顺序强造组件 |
| 6 验收 | 页面可进入、主流程完成、失败反馈、空态可理解、文案可读；测试命令和截图更新条件只维护在[回归流程](/Users/congming/github/goldenshare/docs/frontend/frontend-regression-and-baseline-workflow-v1.md) |
| 7 上线准备 | 影响页面、主要变更、风险、实际验收结果、失败回退；明显交互变化同步页面说明。准备完成不是部署授权 |

复杂页面可以按需求交互、token/组件、页面、测试四条职责协作；这是职责划分，不要求创建四个任务或强制四人并行。各 owner 明确文件范围，未经同步不跨区覆盖；单人也可以顺序承担。

## 3. 评审清单

- 标题、按钮和说明围绕用户任务，首屏能看出主操作；无无意义品牌装饰。
- loading/empty/error/loaded 和提交成败齐全；考虑权限与异常提示。
- 数字、单位、日期格式、表格密度和对齐统一；日期/筛选和状态展示复用共享组件。
- 明确 props 消费者、API 字段与错误、URL/页面状态关系；transport、业务计算、展示职责不混合。
- 不将 page-only 样式升级为全局标准，不继续无边界增厚页面。
- 共享组件变更明确说明、Showcase 和测试影响；没有现成基线也须说明验证缺口。
- 不因赶进度省略错误处理和类型，不以更新截图掩盖逻辑错误。

具体视觉数值与组件规范见[组件目录](/Users/congming/github/goldenshare/docs/frontend/frontend-design-tokens-and-component-catalog-v1.md)，不在本流程复制。

## 4. 简报模板

可将以下信息写进同一份任务说明，不必另建多份重复文档：

1. 背景、目标、用户角色、主/次任务、本轮不做。
2. 页面顶部/主区域/次区域；加载、空、异常、权限、提交中和成败状态。
3. API 与数据依赖、URL 状态、组件与 token、影响文件、协作范围。
4. 验证档位、预期截图变化、实际命令与结果、未覆盖项。
5. 风险、回滚、待决策及不同选项的影响。

## 5. 决策与交付

已有五项设计决定以[组件目录 §12](/Users/congming/github/goldenshare/docs/frontend/frontend-design-tokens-and-component-catalog-v1.md#12-已确认基线)为准；不在每次任务中重新提问。需偏离时列“问题、选项、假设、影响”，明确等待确认，不默认选边。

交付说明写明目标与依据、文件、组件/交互/API 影响、实际验证、截图是否更新及理由、未覆盖风险和下一步。测试命令、CI 状态、历史验收是不同证据，未运行的检查如实列出。
