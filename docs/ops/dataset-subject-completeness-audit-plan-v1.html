数据集日期对象矩阵完整性审计方案 v1

本文定义“日期桶审计”之后的第二阶段能力：在指定日期范围内，检查每个应覆盖对象是否在每个应检查日期桶都有数据。 首个小闭环只接入 adj_factor，用 stock_basic 中已上市且未退市股票作为对象池。

状态：待评审 目录：docs/ops 范围：审查中心 / 数据集审计 不改数据维护主链

1. 问题本质

当前日期完整性审计只判断目标表里是否存在某个日期桶。它适合发现“整天缺数据”，但不能发现“某个日期下少了部分股票、指数或板块对象”的问题。

能力 回答的问题 能否发现 4 只股票缺 2026-03-30/31 典型结论
日期桶审计 这个交易日目标表是否有任意数据 不能 2026-03-30 有 5495 行，所以日期桶已覆盖
日期对象矩阵审计 这个交易日下，每个应覆盖对象是否都有数据 能 2026-03-30 应有 5499 个对象，实际 5495 个，缺 4 个
关键判断 凡是业务语义要求“日期 × 对象”全覆盖的数据集，都不能只依赖日期桶审计。adj_factor 只是第一个暴露问题的样本，不是唯一风险点。

2. 设计目标与非目标

目标

  1. 在现有“数据集审计”中新增矩阵审计类型。
  2. 第一期只让 adj_factor 跑通闭环。
  3. 对象池来自 stock_basic，并按生命周期过滤。
  4. 审计结果写入 ops 自己的审计表，不影响业务数据表。
  5. 页面清楚区分“日期桶通过”和“矩阵通过”。

非目标

  1. 不替代 freshness。
  2. 不做字段值质量校验。
  3. 不做逐字段对账。
  4. 不改数据维护、同步、写入主链。
  5. 不一次性接入所有数据集。

2.1 设计原则与硬约束

原则 硬约束 原因
审计链路独立 审计能力不得复用数据拉取、请求编排、ingestion executor、写入链路或数据补数逻辑；只能消费事实源定义和数据库事实表。 审计不能用同一套可能出错的同步逻辑来证明同步结果正确，否则会失去独立校验意义。
性能优先 矩阵差集必须下推到数据库执行；接入每个数据集前必须做索引审计、小窗口真实耗时验证和大范围成本估算。 矩阵审计天然可能产生大规模检查单元，不能接受一个常规审计任务跑一两个小时。
语义先行 每个数据集接入前必须先写清对象是什么、对象池来源、生命周期规则、缺失是否异常、为什么该口径正确；禁止仅凭字段名或表名猜。 不是所有带 ts_code 的数据集都要求全股票覆盖，事件型和关系型数据集误接入会产生大量误报。
分批推进 第一期只做 adj_factor 小闭环；后续每批必须先评审口径，再编码接入，不允许大干快上。 不同数据集的对象池语义不同，批量套模板会把错误扩散到全平台。
采样完整 概览结果必须展示问题量级；详情样例可以限量，但每条样例必须包含完整判断字段，不能因为采样缺字段、缺值。 运营需要知道问题有多大，也需要通过样例判断“为什么它应该有、为什么判缺失”。
禁止事项 禁止为了省事复用同步 planner / request builder / ingestion executor；禁止在 Python 中构造大规模日期对象矩阵；禁止没有对象池语义评审就接入新数据集。

3. 通用语言

术语 定义 例子
日期桶 按数据集日期模型生成的应检查日期单位。 2026-03-30
对象 某个日期下应被检查的业务主体，可以是股票、基金、指数、板块或成分关系。 920188.BJ
对象池 某个日期桶下，理论上应该有数据的对象集合。 2026-03-30 已上市且未退市股票集合
矩阵单元 一个日期桶和一个对象组成的检查单元。 2026-03-30 + 920188.BJ
缺失单元 对象池里应存在，但目标表实际没有的矩阵单元。 adj_factor 缺 2026-03-30 + 920188.BJ

4. 数据集分层判断

不是所有带 ts_code 的数据集都应该做矩阵审计。必须按业务语义区分。

类型 是否适合矩阵审计 典型数据集 原因
强覆盖行情 / 指标类 适合 adj_factor, daily, daily_basic, stk_limit, stk_factor_pro 业务上通常要求每个应覆盖股票在每个交易日都有数据。
基金 / 指数强覆盖类 适合，但对象池不同 fund_daily, fund_adj, index_daily, index_daily_basic 对象池不是 A 股股票池，必须使用基金池或指数池。
事件 / 榜单类 不适合 limit_list_ths, top_list, limit_step, broker_recommend 不是每个对象每天都应出现，矩阵审计会制造大量误报。
成分关系类 后续专项 dc_member, ths_member, index_weight, kpl_concept_cons 对象不是单字段，而是板块 / 指数与成分的组合关系。

5. 第一阶段小闭环：adj_factor

5.1 已确认口径

对象池口径已确认 adj_factor 使用 stock_basic 中已上市且未退市股票作为 expected universe，并按 list_date / delist_date 对每个交易日做生命周期过滤。
字段 口径
日期桶 沿用 DatasetDefinition.date_model：trade_open_day + every_open_day
对象类型 stock
对象键 ts_code
对象池来源 raw_tushare.stock_basic 或当前代码实际登记的股票主数据表，落地前以代码和 DB 实际表确认。
生命周期过滤 list_date <= trade_date 且 delist_date is null or delist_date > trade_date；若只有当前状态字段，则叠加 list_status='L'。
实际表 core.equity_adj_factor
实际键 trade_date + ts_code

5.2 SQL 形态

with expected_dates as (
  select trade_date
  from core_serving.trade_calendar
  where exchange = :exchange
    and is_open is true
    and trade_date between :start_date and :end_date
),
expected_subjects as (
  select
    d.trade_date,
    s.ts_code,
    s.name
  from expected_dates d
  join raw_tushare.stock_basic s
    on s.list_date <= d.trade_date
   and (s.delist_date is null or s.delist_date > d.trade_date)
   and s.list_status = 'L'
),
actual_subjects as (
  select distinct trade_date, ts_code
  from core.equity_adj_factor
  where trade_date between :start_date and :end_date
)
select
  e.trade_date,
  e.ts_code,
  e.name
from expected_subjects e
left join actual_subjects a
  on a.trade_date = e.trade_date
 and a.ts_code = e.ts_code
where a.ts_code is null;

真实落地时不要求逐字使用这段 SQL，但必须保持同一语义：expected 来自日期桶与对象池的组合，actual 来自目标表去重后的业务键。

6. 建议的数据模型

6.1 DatasetDefinition 新增可选审计模型

不建议把对象池语义塞进 date_model。日期模型只回答“哪些日期桶应检查”，对象矩阵模型回答“每个日期桶下哪些对象应检查”。 

DatasetCompletenessModel
  scope: date_bucket | date_subject_matrix | not_applicable
  subject_kind: stock | fund | index | board | component | null
  subject_key_fields: ["ts_code"]
  actual_key_fields: ["ts_code"]
  universe_strategy: stock_basic_active_lifecycle
  universe_source_table: core_serving.security_serving
  universe_key_field: ts_code
  universe_name_field: name
  lifecycle_start_field: list_date
  lifecycle_end_field: delist_date
  status_field: list_status
  active_status_values: ["L"]

6.2 审计结果表

表 用途 第一期是否新增
ops.dataset_date_completeness_run 继续作为审计 run 主表，新增矩阵审计汇总字段。 是
ops.dataset_date_completeness_gap 保留日期桶缺口区间，不混入对象缺失。 保留
ops.dataset_subject_completeness_gap 按日期桶保存对象缺失摘要和样例。 是
ops.dataset_subject_completeness_gap_detail 保存缺失对象明细，设置单 run 上限，防止异常任务写爆。 建议第一期加上限实现

6.3 run 主表建议新增字段

字段 类型 含义
audit_scope varchar(32) date_bucket 或 date_subject_matrix
subject_kind varchar(32), nullable 对象类型，例如 stock
expected_cell_count bigint 应检查矩阵单元数量。
actual_cell_count bigint 实际覆盖矩阵单元数量。
missing_cell_count bigint 缺失矩阵单元数量。
affected_bucket_count int 存在对象缺失的日期桶数量。
affected_subject_count int 至少缺失一次的对象数量。
detail_truncated boolean 缺失明细是否因安全上限被截断。

7. 执行流程

1. 读取 Definition判断 audit scope 与对象池策略
2. 生成日期桶复用现有 ExpectedBucketPlanner
3. 生成对象池按日期做生命周期过滤
4. SQL 差集expected left join actual
5. 写审计结果run 汇总 + gap 摘要 + detail 上限

7.1 pass / fail 规则

场景 result_status 说明
日期桶无缺失，矩阵无缺失 passed 对象覆盖完整。
日期桶无缺失，矩阵有缺失 failed 本方案的核心场景，例如 adj_factor 缺 4 只股票。
日期桶有缺失 failed 保留现有日期桶缺失语义。
目标表、对象池表、规则不可读 error 审计执行失败，不伪装成数据缺失。

9. 性能与安全边界

  1. 矩阵差集必须在数据库中完成，不允许 Python 生成全量笛卡尔积后逐行比对。
  2. 目标表必须具备 (observed_field, subject_key) 方向索引；落地前逐表确认。
  3. 对象池表必须具备生命周期过滤所需索引。
  4. 缺失明细表必须设置单 run 写入上限，超过后只保留摘要并标记 detail_truncated=true。
  5. 审计只读业务表，只写 ops 审计表；失败不得影响业务数据。
  6. 第一期 UI 可提示长范围审计成本，但不把成本提示做成业务逻辑兼容开关。
  7. 每个数据集接入前必须记录真实性能基线：检查窗口、expected cell 数、actual cell 数、缺失数、SQL 耗时、执行计划摘要。

12. 风险与防护

风险 防护
对象池口径错误导致误报 每个数据集必须显式登记 universe strategy，不允许前端或 SQL 临时猜。
长范围矩阵审计查询慢 数据库差集、索引预检、先小窗口验证，再开放大范围。
缺失明细写爆 ops 表 detail 表设置写入上限，summary 永远完整，detail 可截断。
把事件型数据集误接入矩阵审计 Definition 配置门禁和测试禁止事件型数据集使用股票全覆盖对象池。
与现有日期桶审计结论混淆 API 和页面都显示 audit_scope，列表和详情使用不同统计字段。

13. 编码门禁草案

  1. 新增或修改矩阵审计配置前，必须确认对象池来源、生命周期字段、实际表业务键。
  2. 不得把 ts_code 存在与否作为接入矩阵审计的唯一依据。
  3. 不得复用数据拉取、请求编排、ingestion executor、补数或写入逻辑。
  4. 不得在 Python 内构造大规模矩阵列表。
  5. 不得让矩阵审计写入或修改业务数据表。
  6. 必须有测试证明 adj_factor 能识别指定日期缺失的 4 个代码。
  7. 必须有测试证明事件型数据集不会被误判为适合矩阵审计。
  8. 必须保留现有日期桶审计行为不变。
  9. 必须有性能门禁记录，至少覆盖小窗口真实 SQL 耗时和索引使用情况。
  10. 详情样例字段必须完整，至少包含日期桶、对象键、对象名、生命周期字段、缺失原因码、目标表和实际业务键。

14. 当前代码审计结论

审计点 当前实现 与本方案的关系
审计执行模型 DateCompletenessAuditExecutor 当前只执行日期桶审计：规划 expected buckets、读取 distinct observed date、比较日期集合。 不能直接打补丁扩成对象矩阵；应新增 date_subject_matrix 分支，保留现有日期桶审计行为不变。
实际数据读取 ActualBucketReader 只返回 set[date]，且 SQL 只按 observed_field 去重。 无法识别 adj_factor 某日期下个别 ts_code 缺失；矩阵审计必须新增实际对象矩阵读取器。
结果表结构 M2 后 ops.dataset_date_completeness_run 已具备矩阵汇总字段，并新增 dataset_subject_completeness_gap 与 dataset_subject_completeness_gap_detail ORM/迁移。 存储层已就位；后续仍需独立 executor 写入这些结果表。
API 与前端契约 当前 schema、query service、前端类型均以 bucket count / gap range 为核心。 矩阵审计需要扩展 API 与页面展示，不能把对象缺失塞进现有 sample_values 字符串里。
DatasetDefinition 事实源 M1 后 DatasetDefinition 已新增独立 completeness 配置，当前仅 adj_factor 启用 date_subject_matrix。 后续扩展数据集时仍必须逐个评审对象池语义，不得把对象池语义塞进 date_model 或复用 row_identity_filters。
adj_factor 对象池基础 stock_basic 现行服务表为 core_serving.security_serving，包含 ts_code/list_status/list_date/delist_date/security_type/source。 支持第一期使用股票主数据生命周期池；落地前需确认索引与 SQL 执行计划。
性能风险 core.equity_adj_factor 目前模型只显式定义 trade_date 索引，主键为 (ts_code, trade_date)。 矩阵审计 SQL 应避免 Python 大矩阵；落地前需验证 trade_date + ts_code 差集查询是否走合适索引，必要时单独评审加索引。
实现边界 代码审计未发现必须阻断方案的小前提，但确认本能力不是现有日期桶审计的字段级小改。 正确落地方式是：保留当前日期桶审计，新增对象矩阵审计模型、执行分支、结果表、API 字段与前端展示。
