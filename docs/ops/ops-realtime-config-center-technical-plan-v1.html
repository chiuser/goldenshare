1. 目标与非目标

本轮目标是把实时流配置从散落的 env/Settings 口径，收敛为可查询、可校验、可发布、可审计的运营配置能力。

方案边界
目标

提供实时流对象列表、配置详情、配置校验、发布、修订记录 API；前端复用 showcase 的查看态和编辑态；发布动作留下审计记录。

非目标

不新增 Tushare 请求，不启动 collector，不调整实时行情 Redis key，不做 WebSocket，不把配置中心与实时流监控页面混成同一个页面。

核心原则

Ops 是管理入口，不是运行时底层事实源。collector、实时快照读取服务、Ops health 必须消费同一份实时配置对象；Biz 查询只调用读取服务，禁止自己拼配置。

页面口径

页面直接按 showcase 落地：左侧实时流对象，右侧对象配置；查看态只展示事实；编辑态才展示校验、diff 和发布确认。

2. 总体架构

当前配置事实进入 foundation 实时运行时配置域；Ops 负责管理 API 与 revision；app/CLI 负责把配置装配给 collector。Biz API 不直接读取配置表，而是调用实时快照读取服务。

边界优先
Ops 配置中心页面
展示对象、编辑草稿、提交校验和发布。
Ops Config API
只做权限、管理流程、revision 写入。
foundation.realtime_runtime_config
运行时配置事实源，collector 和读取服务消费。
Realtime Runtime Resolver
统一校验并生成 RealtimeRuntimeConfig。
collector / reader / Ops health
统一配置对象，不再分散读取 env 或拼 Redis key。

架构约束：foundation 不依赖 ops。 因此运行时当前配置表不放在 Ops 模型里；Ops 可以写入配置表并记录 revision，但 collector、实时快照读取服务和 Biz API 不通过 Ops 查询配置。

2.1 命名规则

对象 命名 归属 人话解释
运行时配置事实表 foundation.realtime_runtime_config foundation 保存实时流“应该怎么运行”的当前事实。它不是 Ops 页面私有配置，而是 collector、读取服务、Ops health 都要认的运行时事实。
配置修订历史表 ops.config_revision ops 只记录谁在什么时候把配置从什么改成什么。它不是配置事实源，不能被 collector 或 Biz 当成运行时配置读取。
配置读取模块 src/foundation/realtime/runtime_config.py foundation/realtime M3 已落地。该模块从运行时配置表读取可编辑配置，并结合代码目录中的锁定事实生成统一配置对象。
实时快照读取服务 src/foundation/realtime/snapshot_reader.py foundation/realtime 封装 Redis current batch、feed key、stale、交易时段判断。Biz API 调它，不自己知道底层 key 和刷新逻辑。

2.2 目标文件结构

路径 职责 禁止事项
src/foundation/realtime/runtime_config.py 读取 foundation.realtime_runtime_config，校验配置关系，生成 RealtimeRuntimeConfig、RealtimeStockRtDailyConfig、RealtimeStockRtMinConfig。 不得依赖 Ops；不得读取页面草稿；不得写 revision。
src/foundation/realtime/config_catalog.py 注册实时流对象、显示名、锁定字段、可编辑字段、控件类型、默认展示顺序。 不得放用户草稿；不得放 Token、Redis URL 等部署秘密。
src/foundation/realtime/snapshot_reader.py 统一读取 Redis 快照和 meta，按 runtime config 计算 stale、missing、collection_status，返回业务查询可消费的结果。 不得暴露配置表结构给 Biz；不得请求 Tushare；不得写 Redis。
src/ops/services/realtime_config_service.py 配置中心管理服务：对象列表、详情、validate、publish、revisions。发布时更新 runtime config 表并写 ops.config_revision。 不得启动 collector；不得请求 Tushare；不得直接修改 env。
src/ops/api/realtime_config.py 管理员配置 API 路由，承接页面查看、校验、发布和历史查询。 不得承接行情查询；不得与 realtime monitor health API 混在同一路由里。
src/biz/queries/realtime_stock_rt_*_query_service.py 业务查询服务，只负责参数校验和把 snapshot reader 结果映射成业务 API schema。 目标态不得直接读取 runtime config 表、不得自己拼 feed_key、不得自己计算底层 stale 规则。

2.3 当前代码事实与目标差异

当前实现 问题 配置中心落地目标
src/foundation/realtime/runtime_config.py 从 foundation.realtime_runtime_config 读取可编辑配置，结合 config_catalog.py 锁定事实生成配置对象。 M6 已解决运行时配置来源、Ops 配置 API 和发布审计问题。 后续继续实现前端配置中心页面、文档收口和本地/远程 env 清理。
Biz 查询服务已改为调用 RealtimeSnapshotReader，只保留参数校验和 schema 映射。 M5 已解决 Biz 直读配置、拼 feed key、计算 stale 的边界问题。 后续继续保持该边界：Biz 不直接读取配置表，不知道 Redis key 规则。
Ops health 查询服务通过 runtime resolver 读取配置，并读取 Redis health。 这是合理的，因为 Ops health 的职责就是展示“应该怎么运行”和“实际运行得怎么样”。 保留该方向；后续配置 API 复用同一配置校验口径。

3. 数据模型

V1 不设计持久化 draft 表。前端编辑态在页面内形成草稿，提交 validate，确认后直接 publish；发布成功写当前配置和 revision。

事实与历史分离
表 归属 职责 说明
foundation.realtime_runtime_config foundation 实时流运行时配置事实源 collector、实时快照读取服务、Ops health 读取它。env 只保留部署级秘密和初始化种子，不作为页面编辑目标。
ops.config_revision ops 发布修订历史 复用现有表，object_type=realtime_runtime_config，object_id=object_key，记录 before/after 与操作人。它只做审计，不参与运行时读取。

ops.config_revision 当前已被自动任务、探针规则、标准化规则、发布规则等 Ops 服务复用。 它的字段是 object_type/object_id/action/before_json/after_json/changed_by_user_id/changed_at， 语义是“变更流水”，不是“当前配置”。因此本方案只复用它记录发布历史，不把它扩展成配置表。

3.1 当前配置表建议字段

字段 类型 含义 规则
object_key varchar(64) pk 实时流对象标识，例如 stock_rt_daily、stock_rt_min 由代码目录定义，禁止用户自定义。
object_kind varchar(32) 对象类型 collector_feed、feed_group、on_demand_query。
runtime_config_json json 可编辑配置值 只保存白名单字段；锁定字段不进入可编辑 payload。
version integer 配置版本 发布成功递增，用于并发更新保护。
requires_collector_restart boolean 配置变更是否需要通过 collector 重启生效的策略提示 只能表示“这类配置发布后需要重启才能被 collector 读取”，不能表示“当前是否仍待重启”。页面不得直接把这个字段渲染成待重启事实；待重启必须由配置版本和 collector 上报的已应用版本推导。
updated_by_user_id bigint nullable 最后修改人 Ops API 发布时写入。
created_at / updated_at timestamp with time zone 创建与更新时间 使用数据库时间。

3.2 初始化与缺失策略

初始化

建表迁移只负责表结构；初始化步骤为 stock_rt_daily、stock_rt_min 写入初始行。M4 后初始值来自代码内受控默认模板，不再读取旧 REALTIME_STOCK_RT_* env。

缺失处理

运行时如果缺少已注册对象的配置行，应 fail fast 并在 Ops health / 配置中心显示结构化错误；不要静默回落到散落 env 字段，否则配置中心会失去事实源意义。

3.3 建表流程

步骤 动作 验收点
1. 迁移 head 审计 执行 uv run alembic heads，记录当前真实 head。若出现多个 head，先停下处理分叉，不得继续新增迁移。 新迁移的 down_revision 只能接真实 head，禁止按文件名、日期或印象猜。
2. 新增 ORM 模型 新增 src/foundation/models/meta/realtime_runtime_config.py，模型名建议 RealtimeRuntimeConfigRecord，表名 foundation.realtime_runtime_config。 字段与 3.1 一致；不得把模型放进 src/ops/models/**，避免 collector/reader 依赖 Ops 模型。
3. 注册模型 在 src/foundation/models/all_models.py 导入新模型；确认 src/app/model_registry.py 通过 src.foundation.models.all_models 能加载它。 Alembic metadata 能看到新表；不需要让 foundation 反向依赖 app 或 ops。
4. 新增 Alembic 迁移 新增 alembic/versions/<next>_add_realtime_runtime_config.py，创建 foundation.realtime_runtime_config 表和必要索引。 迁移只做结构变更，不读取 Tushare、不写 Redis、不启动 collector、不清理任何业务表。
5. 初始化配置行 新增受控初始化逻辑或迁移后初始化命令，从代码内默认模板创建缺失的 stock_rt_daily、stock_rt_min 两行。 初始化只执行运行时配置表写入；写入后配置中心详情 API 能读到两行；不得读取旧实时 env 或静默 fallback。
6. 写入修订记录 初始化不写 ops.config_revision。正式页面发布必须写 revision，object_type=realtime_runtime_config。 初始化只是种子动作；发布历史只记录 before/after 与操作人，不作为 runtime config 的读取来源。
7. 迁移验证 执行本地迁移测试，确认表存在、主键存在、JSON 字段可读写、版本字段可并发保护。 配置 resolver 测试能从数据库生成 RealtimeRuntimeConfig；缺行测试必须返回结构化错误。
8. 回滚边界 迁移 downgrade 只删除本次新增表和索引；不得删除 ops.config_revision，不得触碰 Redis 或业务数据表。 符合根规则：开发、迁移、测试脚本不得擅自删除、清空或重建业务数据表。

3.6 旧配置退场后的禁止项

禁止 fallback

runtime config 表缺行或非法时，必须报结构化错误；禁止回退读取旧 env，否则配置中心不是单一事实源。

禁止双写双读

5.4 发布生效闭环 API（M7.1 已落地）

M7.1 已补齐“已发布版本 -> collector 已应用版本 -> 页面状态”的闭环。 requires_collector_restart 仍保留为发布影响策略，但页面当前状态只读取 apply_state。

接口/字段 用途 规则
apply_state 配置详情和对象列表返回的派生状态 由 foundation.realtime_runtime_config.version 与 collector 上报的 applied_version 推导；不是前端自行判断。
restart_pending 页面是否显示“待重启” 仅当对象发布版本大于 collector 已应用版本时为 true。Redis health 不可用或 collector 未上报时返回 unknown，不能假装已生效。
POST /api/v1/ops/realtime/config/collector/restart 管理员在配置中心触发 collector 重启 已落地。接口只允许重启 goldenshare-realtime-collector.service，不请求 Tushare、不写行情 Redis、不修改配置值；本轮不写持久化审计，只写服务日志和返回接口结果。
realtime_config_apply_state collector 启动后上报已读取的配置版本 写入专用 Redis health 记录，包含对象版本、collector_id、process_started_at、applied_at。配置表仍只保存配置事实，不保存运行状态。

6.3 collector 生效

发布配置
runtime config 表版本递增到 N，revision 记录 before/after。

如果 collector 上报的 applied_version 小于 N，显示待重启。

管理员通过页面按钮或受控运维命令重启服务。
collector 上报版本
启动后读取 runtime config，并把已应用对象版本写入 health。
页面显示已应用
配置 API 读取 health，确认 applied_version 等于 N 后显示已应用。
已解决的问题

M7 前页面读取 requires_collector_restart 并显示“需重启”。这个字段只是策略提示：说明这类配置发布后需要重启 collector 才会生效。 M7.1 后页面改为读取 apply_state，不再用静态策略字段证明“现在仍未重启”。

目标口径

页面状态必须由“配置已发布版本”和“collector 已应用版本”推导。 requires_collector_restart 只保留为发布影响说明，不再作为待重启状态事实。

6.3.1 生效状态模型

事实 来源 含义 页面展示
published_version foundation.realtime_runtime_config.version 配置中心最后一次成功发布后的配置版本。 显示当前配置版本。
requires_collector_restart foundation.realtime_runtime_config 这类对象是否需要 collector 重启才能读取新配置；它是策略，不是状态。 发布影响说明：“发布后需要重启 collector 生效”。
applied_version collector 写入的 Redis health 当前 collector 进程启动后实际读取并应用的对象配置版本。 若等于发布版本，显示“已应用”。
restart_pending Ops Config API 派生 requires_collector_restart=true 且 published_version > applied_version 时为 true。 只在 true 时显示“待重启”；unknown 时显示“应用状态未知”。

6.3.2 collector 上报规则

上报时机

collector 启动或每轮调度时，把每个对象的 applied_version、applied_at、collector_id、process_started_at 写入专用 Redis health 记录 realtime_config_apply_state。

上报位置

复用现有 Redis health 语义族，不把运行状态写回 foundation.realtime_runtime_config。配置表只保存配置事实，health 保存运行事实。

失败处理

Redis 不可用、health 缺失或版本缺失时，配置 API 返回 apply_state.status=unknown。页面不得把 unknown 展示成已应用或待重启。

6.3.3 页面重启按钮规则

按钮职责

按钮只负责触发受控重启 goldenshare-realtime-collector.service。它不修改配置值、不请求 Tushare、不读写行情 Redis、不直接把待重启状态改成已应用。

生效确认

按钮成功只表示 systemd restart 命令执行成功。页面必须继续轮询配置详情或 health，直到 collector 上报的 applied_version 等于当前发布版本，才能显示“已应用”。

权限与安全

重启接口必须 admin-only，并限制为单一服务名。若 Web 进程需要调用 systemd，只能配置窄权限 sudoers：允许 status/restart goldenshare-realtime-collector.service，禁止通配命令。

审计

重启操作不是配置发布，不写 ops.config_revision。M7.1 只写应用服务日志并返回接口结果；若后续需要持久化运维操作审计，单独设计 ops.service_operation_log。

6.3.4 版本状态展示规则

条件 页面文案 允许动作
applied_version == published_version 已应用 不显示待重启；重启按钮不强调。
applied_version < published_version 待重启生效 展示“重启 collector”按钮和发布影响说明。
collector health 缺失或 Redis 不可用 应用状态未知 允许查看配置；重启按钮可用但必须提示无法确认当前应用版本。
重启命令成功但 collector 未上报新版本 等待 collector 上报 页面继续轮询；超时后显示重启未确认，不得改成已应用。
