## 1. 当前边界

仓库已经存在 ETF 实时监控池、规则、告警、分钟统计和基于 `etf_rt_daily` 批次的运行链。P6 已把候选、添加/重新启用门禁、ETF 级规则和运行时资格改为 ETF Basic 当前可请求口径：

```text
运行对象 = enabled monitor pool ∩ 当前可请求 ETF
```

这些现行能力不属于本文重构，不因 P8 删除旧激活池而删除、清表或改 schema。

本文原计划用尚未实现的 ETF 实时分钟流重做“成交额异动”的分钟事实与基准。由于实时分钟流的生产覆盖范围尚未重新基线，本文也不能继续给出可执行开发顺序或表迁移。P8 只校准文档，不修改监控代码。

## 2. 仍然有效的业务判断

1. `rt_etf_k.amount` 是盘中累计成交额，只能提供高频采样信号，不能把相邻批次差额冒充完整真实分钟成交额。
2. 真实分钟基准只能来自已发布为 final/valid 的实时分钟事实，或标准 `etf_mins` 历史表。
3. `rt_etf_k` 源请求保持全市场；下游 monitor pool 只决定计算对象，不应反向改变 provider 请求范围。
4. 历史分钟表由独立数据集维护；监控不得补数、修改或写入该表。
5. 告警事实必须先提交，Feishu 发送失败只能影响投递状态，不能回滚采集或告警事实。

## 3. 待重新评审的量化假设

原方案提出 `1/5/15` 分钟窗口：用窗口内 `rt_etf_k` 累计金额差形成盘中保守采样值，再与上一开市日同窗口真实 1 分钟金额曲线比较。该思路可保留为研究假设，但以下合同尚未批准：

```text
事件键、窗口边界、09:30 特例
baseline 缺失处理
observe / alert / strong 阈值
跨窗口 cooldown
final/valid 分钟读取契约
旧表是否删除或重建
delivery 表结构
```

缺失分钟、累计金额下降、采样中断、跨午休或基准不完整都不能按 0 处理。这一质量原则可以继续保留，但必须在新 LLD 中用当前表结构和实际上游 contract 重新落地。

## 4. 已失效内容

1. 任何把旧 ETF 激活池写成实时分钟上游选择范围的设计。
2. 候选列表从旧池读取的页面契约。
3. 以历史 1,395 数量估算监控或 Redis 容量。
4. 在实时分钟范围未定前规划清表、重建规则/告警表或新增 delivery 表。
5. 旧阶段表、文件白名单和迁移顺序。

## 5. 重新开工门禁

重新设计前必须先完成：

1. ETF 实时分钟流范围、就绪、Redis 保存和 reader 契约拍板。
2. 对当前 monitor pool/rule/alert/minute stat、API、页面、Feishu 和归档 CLI 做新一轮 CodeGraph 审计。
3. 明确哪些现有历史数据保留、哪些 schema 真正需要变化，并单独取得清理授权。
4. 用标准 `etf_mins` 的真实覆盖证明上一开市日基准可用。
5. 配置项、请求预算、窗口时序、事务与通知失败隔离全部写入新 LLD 和测试矩阵。

在此之前，不执行 migration、清表、实时分钟开发、Feishu 改造或页面改造。
