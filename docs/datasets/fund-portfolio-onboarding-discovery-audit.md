# 基金持仓（`fund_portfolio`）接入发现审计

状态：发现审计完成，**未进入 LLD、未建表、未写入远程数据**；历史规模盘点与实现门禁尚未关闭
首次审计：2026-08-03；复审：2026-08-05
截图菜单：基金持仓
源文档：[公募基金持仓数据](../sources/tushare/公募基金/0121_公募基金持仓数据.md)

## 结论

`fund_portfolio` 是按季度报告期末披露的基金-证券持仓明细。这个判断不是只看文档：4 个实测基金的 `end_date` 均只落在 3 月 31 日、6 月 30 日、9 月 30 日、12 月 31 日；其中 `000001.OF` 从 2002Q1 到 2026Q2 连续出现 98 个报告期。`period=20250630` 对 O、E 样本均只返回 `end_date=20250630`，并同时包含该报告期的多个 `ann_date`。

`start_date/end_date` 不能作为报告期范围输入：对 O、E 样本传入 `20250101..20251231`，返回的是 `ann_date` 落在 2025 年内的数据，因而包含 `end_date=20241231`，但不含公告发生在 2026 年的 `end_date=20251231`。分页已确认可用：`period=20250630`、8 个显式字段、`limit=2000` 已连续取得 offset `0..660000` 的 662,000 行且仍为满页；随后以 `limit=8000` 只读定位到末段 `offset=1307500` 的 5,298 行，得到该时点全源结果为 **1,312,798** 行。未分页的 8,000 行只是单页，不是报告期总量。

因此，全量接入不受“源端不能分页”阻断；但也**绝不能把一个报告期设计为一次内存累积、一次数据库事务**。当前项目 `DatasetSourceClient` 会累积一个 unit 的全部分页结果。复审已排除两个不可靠的切法：`ts_code` 逗号拼接两个已知基金返回空集，不能假定源端支持代码批量；`period=20250630` 的首个 8,000 行全是同一 `ann_date=20250831`，公告日也不是天然的小数据桶。

## 源端事实与实测

| 项目 | 已核验事实 | 接入含义 |
| --- | --- | --- |
| 无参数 / 只有范围 | 均报“ts_code, ann_date, period 至少输入一个” | 不支持 snapshot 或纯 start/end range。 |
| 单基金历史 | `000001.OF` 6,317 行、98 个连续季度末（2002Q1..2026Q2）；`001753.OF` 43 个（2015Q4..2026Q2）；`015477.OF` 15 个（2022Q4..2026Q2）；`510300.SH` 返回 49 个季度末但总行数正好 8,000，必须按分页继续核验 | `end_date` 在样本中是季度末；无 period 的单基金历史可能触发页上限。 |
| `period` 点过滤 | `period=20250630`：`000001.OF` 187 行（公告日 20250721、20250830），`015477.OF` 274 行（20250721、20250831），`510300.SH` 340 行（20250721、20250830）；三者均只有 `end_date=20250630` | `period` 是报告期末的正确源端点过滤；同一报告期的所有公告版本都必须保存。 |
| 公告日点过滤 | `ann_date=20250721` 分别返回 10、13、15 行；与 `period=20250630` 合传结果相同 | `ann_date` 是披露批次过滤，不是报告期身份，也不能取代 period。 |
| `start_date/end_date` | 对 `000001.OF`、`015477.OF`、`510300.SH` 传 `20250101..20251231`，均返回 `end_date=20241231/20250331/20250630/20250930`，所有返回 `ann_date` 都在 2025 年内 | 实测按公告窗口过滤，与本地源文档“报告期开始/结束”文字不一致；不得把它暴露为报告期回补输入。 |
| 全市场季度分页 | `period=20250630`，offset `0..660000` 每页 2,000；以 `limit=8000` 定位到末段 `offset=1307500` 返回 5,298 行，合计 1,312,798 行 | 源端分页正常且持仓规模很大；按 2,000 行折算至少 657 页。 |
| 身份样本 | 单基金全历史 1,598 行和季度 8,000 行中 `(ts_code,ann_date,end_date,symbol)` 无重复 | 是候选幂等键，不替代跨期修订验证。 |
| 数据质量 | 样本 `stk_float_ratio=95,349,496.79`，与文档“占流通股本比例”不符 | 不能在服务层把它按百分比展示或缩放。 |

| 代码批量 | `ts_code=015477.OF,000001.OF`、`period=20250630` 返回空集；两个代码单独请求均有数据 | 文档未定义代码列表语法，不能把逗号拼接当作源端批量能力。 |
| 公告日分桶 | 同一季度首个 8,000 行的 `ann_date` 均为 `20250831` | 不能因存在 `ann_date` 参数，就假定“一个公告日 = 有界 unit”。 |

## 建议的接入轮廓（非 LLD）

| 维度 | 当前建议 |
| --- | --- |
| 时间输入 | 以报告期 `period` 为一等输入；不能误用“每天”或泛化 `start_date/end_date`。 |
| 完整源范围 | 每次全量以 `fund_basic` 的 E/O 两个市场、无 `status` 过滤的全部源代码为对象池；这不是范围选择，而是“保存全部 Tushare 源记录”的实现前提。当前快照为 O 29,447 + E 2,879 = 32,326 个代码。 |
| 逻辑 unit | 一个源端逻辑 unit 固定为 `(period, ts_code)`；它获取该基金在该报告期的**全部**公告版本，不能用 `ann_date` 只取其中一批。 |
| 分页与事务 | 固定 `limit=2000`，改为共享的 offset-page 流式链路：每页立即归一化、幂等写入、提交；short page（包括“刚好满页后下一页为空”）才标记逻辑 unit 完成。不得再设置任意 `max_pages_per_unit` 造成完整源数据失败或遗漏。 |
| 重试 / 观测 | 页 N 失败时，逻辑 unit 必须记录失败 offset 和已提交行数并失败；重试从 offset 0 重新读取，依赖幂等身份去重，直到取得 short page。页面显示逻辑 unit、当前页/offset、累计读取/提交和失败原因。 |
| 任务切片 | 当前一个报告期至少涉及 32,326 个逻辑 unit。切片只能在本地按稳定排序代码池划分，不能拼多个代码进 Tushare 参数；具体每片代码数必须由 M0 的实际耗时、限流和数据库吞吐确定。 |
| freshness / audit | 季度披露且有公告滞后，先用 `not_applicable`；是否建立季度披露完整性必须有基金池、报告期和发布窗口规则。 |
| 依赖 | `fund_basic` 是持仓全源对象池的上游前置；不得借用 ETF 活跃池，也不得因代码后缀或市场名称排除 Tushare 已返回的记录。 |
| 自动化 | 支持普通定时自动任务；本期不接 probe。 |
| 存储 | 所有 8 源字段保存；业务表、全部叶分区和索引固定 HDD。PostgreSQL 集群共享 WAL 保持当前 SSD，不为本数据集迁移 `pg_wal`。 |

## 完整请求与对账契约（非 LLD）

最终入库的每个源端请求必须固定为：单个 `ts_code`、单个 `period`、`limit=2000`、递增 `offset`，并显式请求全部 8 个 `source_fields`。禁止传 `ann_date`、`start_date/end_date`、`symbol`，也禁止用逗号拼接多个基金代码；前述任一条件都会把“同报告期的全部披露事实”缩小为局部结果或直接返回空集。

分页从 offset 0 开始。每一页必须校验返回行的 `ts_code` 等于请求基金、`end_date` 等于请求报告期；每页立即归一化、幂等写入、提交。只有收到 short page 才能标记 `(period, ts_code)` 成功；若上页恰好 2,000 行，必须继续请求下一页，下一页为空才是正常结束。页面失败时记录失败 offset 与已提交统计，重试从 offset 0 幂等重放，不能把已提交的前几页当作完整成功。

仅用 `fund_basic` 对象池不足以证明“全源没有遗漏”。每个报告期的验收基线为两次不带 `ts_code` 的全源 `period` 分页读取：先取基线 A，再完成逐基金同步，再取基线 B。只有 A/B 的身份集合一致，且逐基金结果的 `(ts_code, ann_date, end_date, symbol)` 并集与它一致，才能判定本次没有系统性遗漏；若 A/B 不同，记录为源端在同步窗口变动并重跑该报告期。源接口未暴露快照 ID，因此不得把跨窗口的源端变化误判成已完成的静态全量。

历史回补也不能根据 `start_date/end_date` 生成区间。先对全对象池做只读历史盘点，取得实际出现的 `end_date` 集合作为离散 `period` 清单；随后按该清单执行上述逐基金请求与全源对账。这个盘点尚未执行，不能用样本基金的最早报告期替代。

## LLD 前仍需验证或决定

1. **完整源范围已定**：保存 Tushare 返回的全部记录，`fund_basic` E/O 全部代码均进入对象池；不允许改成 ETF 池、仅 O、仅 E、代码后缀白名单或 `status` 过滤。
2. **有界写入设计已定**：逻辑 unit 为 `(period, ts_code)`，但物理写入 unit 是一个 offset page（2,000 行）；必须以共享流式分页契约实现，不允许用页数上限停止完整数据。M0 必须以一个完整报告期的全部代码验证 page-merge、short-page、每页提交、重试幂等，以及全源基线 A/B 与逐基金身份键并集的对账。
3. **任务容量门禁**：当前全源代码池为 32,326，一个报告期至少同量的首次请求；按源文档 200/500 请求每分钟，理论下界约为 162/65 分钟，另加分页和重试。源端于 2026-08-05 实测 `period=20250630` 全源结果为 1,312,798 行，若按全局 2,000 行分页折算至少 657 页；这只证明该报告期的当前源端行数，不能替代按 `(period, ts_code)` 执行时的实际请求数与分页次数。完整历史的报告期起点、各期实际代码数和分页次数尚未盘点，禁止再使用“2012Q2–2026Q2 共 57 期”或据此推算的请求量。LLD 前要先以源端盘点建立真实历史工作量。
4. `stk_float_ratio` 的单位与名称以何为准；上线前需要源端说明或多样本验证，数据可先原样保存但不能错误解释。
5. 报告期修订：同 `ts_code/end_date/symbol` 的新公告是否覆盖或保留版本；候选键包含 `ann_date` 的原因须在 LLD 固化。

## 已确认的事实身份边界与待固化项（非 LLD）

1. 持仓源事实的候选逻辑身份为 `(ts_code, ann_date, end_date, symbol)`：同一报告期同一证券在不同公告日披露，必须视为不同披露事实，不能按 `ts_code + end_date + symbol` 覆盖。
2. 同一候选身份出现内容变化时，不得静默覆盖或丢弃；全部 8 个源字段都必须参与内容散列。是否保留观察版本及其表结构尚待 LLD 决定，这不改变“报告期 + 公告日”是业务事实的边界。
3. 同一报告期的 `ann_date` 多版本是完整源事实：`period=20250630` 样本中早期公告仅 10/13/15 行，后续公告补足到 187/274/340 行；任何仅按早期公告日增量的设计都会漏源记录。
4. 当前实现的 `DatasetSourceClient` 先将所有页累积为 `rows_raw`，`IngestionExecutor` 才归一化并在外层逻辑 unit 末尾 commit。流式分页必须改为“页级归一化、页级幂等提交、逻辑 unit 在 short page 后成功”；这会改变共享 source client、executor、事务 lint、进度/TaskRun 对账和相关测试，不能只给 `fund_portfolio` 加特例。
5. 对代码切片而言，计划 admission 必须按**解析后的 unit 集合**判断冲突：不同代码片可并行或排队，重叠的 `(period, ts_code)` 不得重复排队。不得只按 `dataset_key` 一刀切，否则既拦不住同代码重叠，也会错误阻止无交集切片。
