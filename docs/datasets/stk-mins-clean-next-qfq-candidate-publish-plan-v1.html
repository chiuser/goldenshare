Local Lake / stk_mins / clean_next qfq rebuild

stk_mins clean_next 前复权候选层重建与两阶段发布方案 v1

本方案用于修正当前股票历史分钟线 clean 层的价格口径：当前分钟线已通过样本确认更接近除权价， 后续 MACD、MA、BOLL、90/120 分钟线和 by-month research 都不能继续直接使用现有价格。 本方案只定义方案，不执行数据写入。

1. 背景与结论

之前文档中写过“分钟线 Parquet 已按前复权口径保存”。这个判断已经被实际样本推翻。 我们对比了本地 Lake 的 30 分钟线、远程 raw_tushare.adj_factor 和行情软件的前复权价格。

核心结论： 当前 research/stk_mins_by_date_clean_next 中的 open/high/low/close 不能继续被视为前复权价格。正式指标计算前，必须重建 clean_next 的价格口径。
文档收口： 本文是 qfq 专项方案，必须服从 Local Lake DuckDB 计算执行壳与受控发布方案。 candidate 路径、run manifest、publish 顺序、配置来源和 gate 语义均以 DuckDB 执行壳为准； 本文不再单独发明第二套 qfq candidate / manifest / publish 体系。

2. 目标口径

raw 层职责

raw_tushare/stk_mins_by_date 保存源站返回事实。它保留除权价或源站原价，不做物理改写。

raw 是追溯账本，不承担研究连续价格口径。

clean_next 层职责

research/stk_mins_by_date_clean_next 是正式研究基准层。

重建后，它的 open/high/low/close/vwap 必须统一为最新因子基准下的前复权价格。

2.1 为什么不长期新增一个并列正式数据集

如果长期保留 clean_next_qfq，下游会变成双口径： derived、by-month、MACD、MA、BOLL 和研究脚本都要判断到底读哪个路径。 这会重新制造历史包袱。正确做法是：允许施工阶段有 candidate，但正式发布路径仍然是 research/stk_mins_by_date_clean_next。

必须对齐已落地 Sync Center： 当前 stk_mins_sync 已经实现 Kopia 写前备份 -> raw -> clean_next gate -> by-month research 的 backend 分阶段链路。90m/120m 已收敛到 Dagster orchestrator，不再由 Sync Center 写入。qfq 发布不能另起一套锁、备份、gate 或下游重建实现；它是一次改变 clean_next 价格语义的维护动作，必须复用或扩展现有 Sync Center 的 LakeJobLockService、Kopia 备份、clean_next_partition_gate 和下游 derived/by-month 服务。

2.2 是否改行级 schema

不改行级 schema。正式 clean_next 仍保持 11 列：

ts_code
freq
trade_time
open
close
high
low
vol
amount
exchange
vwap

不新增 open_qfq、close_qfq，也不新增 factor_date、adj_factor、source_ts_code 等解释列。 复权基准、factor snapshot、publish 记录写入 manifest 账本。

2.3 前复权计算属于哪个阶段

已拍板： 前复权计算必须发生在 raw_tushare/stk_mins_by_date -> research/stk_mins_by_date_clean_next 的构建阶段。也就是说，它是 clean_next 生成规则的一部分，不是 raw 下载规则、audit 修复规则、 derived 派生规则，也不是 MACD / MA / BOLL 指标内部的临时补偿。

完整链路应表达为：

Tushare 拉源数据
-> 写 raw_tushare/stk_mins_by_date
-> 从 raw 构建 clean_next 时做：
   代码归一、退市过滤、上市日前过滤、非法结构过滤、前复权计算
-> 写 clean_next candidate 或正式 clean_next
-> audit / gate
-> derived / by-month / indicator

这样做的原因很简单：raw 是源站事实，不能改；audit 只负责检查，不能改数据；derived、by-month 和指标都应该消费同一份干净的研究基准， 不能各自临时修价格。否则未来 MACD、MA、BOLL 可能各自用不同的复权逻辑，结果会再次失控。

因此，全量重建与日常增量必须复用同一个计算黑盒： ComputeRequest + transform_key=stk_mins.clean_next.qfq。 两者只允许输入范围不同：全量 baseline 输入完整目标范围，日常增量输入 Adapter 从 affected partitions 翻译出来的分区请求。黑盒内部不能知道它是“全量”“日常同步”“单股票补数”还是“人工修复”触发。 不能出现“全量 candidate 做了前复权，但日常发布仍写除权价”的双口径。

3. 前复权计算规则

本方案采用最新复权因子作为前复权基准。

qfq_ratio(ts_code, trade_date)
  = adj_factor(ts_code, trade_date) / latest_adj_factor(ts_code)

qfq_open  = raw_open  * qfq_ratio
qfq_high  = raw_high  * qfq_ratio
qfq_low   = raw_low   * qfq_ratio
qfq_close = raw_close * qfq_ratio
qfq_vwap  = raw_vwap  * qfq_ratio   -- vwap 是价格字段，也必须同口径调整
字段 处理 原因
open/high/low/close 乘以 qfq_ratio 核心价格字段，必须成为连续前复权价格。
vwap 非空时乘以 qfq_ratio vwap 是成交均价，属于价格口径，不能和 OHLC 口径不一致。
vol 不调整 成交量是实际成交量，不因价格复权改写。
amount 不调整 成交额是实际发生额，不作为前复权价格字段处理。
exchange 不调整 交易所字段是分类字段。
重要： 前复权价格会随最新复权因子变化而变化。每次发布都必须记录本次使用的 factor snapshot， 否则未来无法解释为什么同一历史分钟线在不同时间重建后价格发生变化。

4. 两阶段发布总流程

4.1 路径定义

层 路径 用途 是否给下游读取
raw raw_tushare/stk_mins_by_date/freq=*/trade_date=*/ 源站事实，保留原始价格。 只给 clean 重建使用，不给指标直接读。
candidate _tmp/duckdb_compute/<run_id>/candidate/research/stk_mins_by_date_clean_next/freq=*/trade_date=*/ 施工区，生成前复权 clean 候选；它属于 DuckDB 执行壳的 run 临时产物，不是正式 research 数据集。 禁止给 derived/by-month/indicator 读取。

5. 命令设计

当前实现已经收敛到 DuckDB Compute 执行壳命令组，必须按 prepare / compute / audit / backup / preflight / publish / finalize 分阶段执行； 禁止一个命令从构建直接替换正式层。

实现约束： 命令名以 stk-mins-qfq 为专项语义，底层必须生成 manifest/duckdb_compute/runs/<run_id>/... 的 ComputeRun / ComputeUnit / CandidatePart / PublishPartition 账本。不得再写入 manifest/stk_mins_qfq_candidate 这种独立 qfq manifest 命名空间。

5.1 前置检查与 run manifest

lake-console readiness-stk-mins-qfq \
  --start-date 2009-01-01 \
  --end-date 2026-05-15 \
  --freqs 1,5,15,30,60

lake-console prepare-stk-mins-qfq-run \
  --start-date 2009-01-01 \
  --end-date 2026-05-15 \
  --freqs 1,5,15,30,60

行为：

  1. readiness-stk-mins-qfq 只读检查 clean_next、adj_factor、latest adj_factor、identity map、磁盘空间、历史 run 与 gate。
  2. prepare-stk-mins-qfq-run 写 manifest/duckdb_compute/runs/<run_id>/...，不执行 DuckDB 计算。
  3. run manifest 中的 qfq unit 以 freq + trade_date 为粒度，不再按 bucket 拆碎。

5.2 构建 candidate

lake-console compute-stk-mins-qfq-candidates \
  --run-id <run_id>

行为：

  1. 只写 _tmp/duckdb_compute/<run_id>/candidate_parts/research/stk_mins_by_date_clean_next/freq=*/trade_date=*/part-000.parquet。
  2. 不写正式 research/stk_mins_by_date_clean_next。
  3. 不写 derived、by-month research、indicator。
  4. 写入本次 CandidatePart manifest，并按配置批量 checkpoint，避免逐 unit 重写 manifest。

5.3 审计 candidate

lake-console audit-stk-mins-qfq-candidates \
  --run-id <run_id>

行为：

  1. 只读 candidate。
  2. 检查 schema、重复 key、非法价格、完备性、adj_factor 覆盖、样本前复权对账。
  3. 输出审计报告和问题账本。
  4. 不修改正式 clean_next。

5.4 备份与正式发布

lake-console backup-stk-mins-qfq-prewrite \
  --run-id <run_id>

lake-console preflight-stk-mins-qfq-publish \
  --run-id <run_id>

lake-console prepare-stk-mins-qfq-gate-publish-plan \
  --run-id <run_id>

lake-console stage-stk-mins-qfq-gate-publishing \
  --run-id <run_id>

lake-console publish-stk-mins-qfq-formal \
  --run-id <run_id>

lake-console finalize-stk-mins-qfq-publish \
  --run-id <run_id>

行为：

  1. 检查 candidate 审计状态必须为 passed。
  2. 复核 input snapshot，确认 raw、adj_factor、identity map、配置和代码版本未漂移。
  3. Kopia 备份当前正式 clean_next、gate、quality ledger、downstream requirement、factor snapshot manifest。
  4. 备份成功后，才允许将目标正式 gate 置为 publishing，阻断下游消费。
  5. 按 freq + trade_date 正式分区做原子替换，并执行 formal audit。
  6. 写入 downstream source event / derived rebuild requirement / indicator queue 或对应失效记录。
  7. 写入 publish record。
  8. 只有下游通知和发布记录都成功后，才能将正式 gate 置为 passed。

数据行不新增解释字段，但必须有外部账本记录本次复权基准和发布事实。

文件 建议路径 关键字段 用途

候选审计账本 manifest/duckdb_compute/runs/<run_id>/audit_ledger.parquet ledger_schema_version, issue_key, issue_state, severity, issue_type, freq, trade_date, trade_time, ts_code, expected_value, actual_value, action, reason, first_seen_at, last_seen_at, seen_count 记录候选层问题，未解决不得发布。同一个问题重复出现时更新同一条记录，不无限膨胀。

账本口径： factor snapshot 是本方案的关键资产。以后如果最新复权因子变化，历史前复权价格理论上会变化； 只有记录了本次使用的最新因子快照，才能解释当前 clean_next 的价格版本。
状态与文案口径： 本文不单独发明状态字段和 UI 提示。ComputeRun、ComputeUnit、 CandidatePartOutput、PublishPartition、FormalGate、 audit ledger 和 UI 文案映射，全部以 Local Lake DuckDB 计算执行壳与受控发布方案 v1 中的精确定义为准。前端或 CLI 摘要不得直接显示 publishing、blocked、 LC_COMPUTE_AUDIT_FAILED 等裸枚举，必须映射成人话。

7. 审计门禁

G1 schema 门禁 candidate 每个 parquet 物理列必须严格等于正式 11 列。
G2 adj_factor 覆盖门禁 每个保留行必须按 ts_code + trade_date 找到当日或当日前最近一个有效因子，且每个 ts_code 必须有最新有效因子；缺失、重复、非正数都阻断。
G3 价格变换门禁 随机样本必须能按 qfq_ratio = factor_at_trade_date / latest_factor 复算出 candidate OHLC/vwap；double 计算不截断，审计误差阈值必须在实现前写入配置和报告。
G4 清洗规则门禁 代码归一、上市日前过滤、退市剔除、结构性非法值过滤必须和当前 clean 规则一致。
G5 重复 key 门禁 同一 (ts_code, freq, trade_time) 不允许 payload 冲突。
G6 完备性门禁 qfq 不改变 key set 和行数。候选层必须与输入清洗后 key set 一致，并继续按已确认交易时段和盘后交易口径检查 bar 数；不通过则写账本并阻断发布。
G7 样本对账门禁 002458.SZ、603596.SH 等已确认样本必须接近行情软件前复权显示。
G8 下游隔离门禁 candidate 未发布前，derived、by-month、indicator 不允许读取 candidate。

8. 发布与回滚

8.1 发布前

  1. candidate 审计必须 passed。
  2. 必须复核 input snapshot，确认输入没有漂移。
  3. 必须创建 Kopia snapshot，范围至少包含正式 clean_next、gate、quality ledger、downstream requirement、DuckDB compute manifest。
  4. 必须通过现有 LakeJobLockService 获取 Sync Center 全局写入锁；禁止新建另一套互不感知的 qfq 专用全局锁。
  5. 必须确认当前没有正在运行或等待人工确认的 stk_mins_sync、derived 重建、by-month 重排、indicator 计算。

8.2 发布中

发布动作只做目录替换，不重新计算。若替换失败，正式路径不能进入半成品状态。 实现上应使用 _tmp -> validate -> atomic rename/replace 的目录级发布策略。

8.3 发布后

  1. 重写 clean_next gate，并写入本次 publish_id / write_revision。
  2. 记录正式 90m/120m QFQ 及指标需要全量重建；后续执行必须使用 Dagster orchestrator 的唯一共享窗口合同，不得在 backend 实现第二套 derived builder。
  3. 记录 research/stk_mins_by_symbol_month 需要全量重建；后续执行必须复用现有 StkMinsResearchService，不得再实现第二套 by-month builder。
  4. 记录 indicator 相关结果已失效，但本期不实现 MACD / MA / BOLL 计算与清理。

8.4 回滚

如果发布后发现 candidate 有问题，回滚只允许从 Kopia snapshot 恢复正式 clean_next 与相关 manifest。 不允许手工拼分区，也不允许只恢复部分日期后继续跑指标。

9. 下游重建顺序

clean_next 发布后，下游必须按顺序重建，不能跳步。下列顺序是发布后的后续专项顺序，不属于本期 qfq 实现范围。

1. publish qfq clean_next
2. audit clean_next
3. rebuild 正式 90/120 QFQ（只使用 Dagster orchestrator 共享窗口合同）
4. rebuild stk_mins_by_symbol_month from clean_next + derived（复用现有 StkMinsResearchService）
5. review MACD / MA / BOLL 方案
6. 清理旧 indicator 结果与 state
7. compute indicators full
8. run indicator completeness checks
禁止： 在 clean_next 前复权发布前继续做正式 MACD/MA/BOLL 计算。 任何基于旧除权价 clean_next 的指标结果都不能当作正式资产。
