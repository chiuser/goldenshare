stk_mins clean / audit gates v1

股票分钟线清洗与审计门禁流程图

本文档把 raw_tushare/stk_mins_by_date 到 research/stk_mins_by_date_clean_next、derived、by_month research、后续技术指标输入之间的门禁全部画清楚。 核心目标只有一个：先保证数据干净，再允许下游重建；任何脏数据、口径不明或审计缺口都不能悄悄流进指标计算。

raw 不改写 clean 使用最新 ts_code 退市股整只排除 问题解释进账本 failed 阻断下游
当前口径

raw 是源站事实；clean_next 是当前正式研究事实。clean_next 只保留仍未退市股票的有效分钟线， 并把旧代码归一成最新代码。clean_next、derived、research、indicator 行级数据不得携带 identity_id、source_ts_code、list_date、delist_date。 身份、退市、异常剔除、完备性问题都必须通过独立账本解释。

本文档是 MACD v2 重算与增量可靠性方案 的图形化门禁说明。

1. 总流程图

这张图描述的是运行顺序。绿色节点表示可以继续，黄色表示需要人工复核，红色表示硬失败，必须停下。 下游 derived、by_month research、MACD 只能在 clean 审计通过后启动。

success

门禁通过，可以进入下一步。

needs_review

信息不足或口径不能自动判定，默认阻断。

failed

确认错误，必须修复，不能放行。

explained

缺失有停牌或生命周期依据，不阻断但必须计数。

2. 硬口径

raw 层

raw 只保存源站事实，源站返回什么代码就保存什么代码。raw 不负责研究口径清洗，不因为代码变更或退市而改写历史。

  • 路径：raw_tushare/stk_mins_by_date
  • 保留源站原始 ts_code
  • 每日增量先落 raw

clean 层

clean 是研究事实，只保留可用于研究和指标计算的股票分钟线。

  • 旧代码直接归一为最新 ts_code
  • 未退市股票保留 list_date 起的数据
  • 已退市股票整只排除，不保留退市前历史

下游层

derived、by_month research、MACD 等技术指标只能读取 clean_next 之后的数据。

  • derived 90/120 只读 clean_next 30/60
  • by_month 只读 clean_next/derived
  • 指标 state key 使用最新 ts_code + freq
绝对禁止： clean、derived、research、indicator 行级输出不得包含 identity_id、source_ts_code、list_date、delist_date、identity_version。 这些字段只属于 manifest / audit，不属于分钟线事实行。
账本原则： 如果某条数据为什么被归一、为什么被剔除、为什么缺失可以接受，需要解释，这个解释必须进入账本。 不能为了让下游“看懂原因”就在 clean、derived、research 或 indicator 行级数据里加解释列。

3. 两本账：身份账本与完备性问题账本

clean 行只保存行情事实。所有解释性信息分散到两本账里：G1 身份账本负责“这是谁”，G6 完备性问题账本负责“这里为什么缺、为什么剔除、是否需要修”。

G1 身份账本

manifest/security_identity/security_identity_map.parquet

  • 记录 source_ts_code -> latest_ts_code。
  • 记录代码变更、北交所映射、曾用名证据、退市状态。
  • 记录无法确认的映射，阻断 clean 生成。
  • 退市股票也必须在账本里有记录；clean 根据账本整只排除。

G6 完备性问题账本

manifest/stk_mins_quality/clean_completeness_issue_ledger.parquet

  • 记录交易日缺口、日内 bar 缺口、异常 bar、重复冲突。
  • 记录停牌解释、生命周期解释、需要人工复核的问题。
  • 记录后续处理动作：阻断、修复、剔除、接受已解释。
  • 问题行只有先进入账本，后续 clean 修复或重建才允许剔除。
信息类型 放在哪里 是否进入 clean 行级数据 原因
旧代码、最新代码、代码切换区间 G1 身份账本 否 clean 只输出最新 ts_code，不背历史血缘字段。
退市股票记录 G1 身份账本 否 退市股整只不进 clean，但排除依据必须可追溯。
缺失交易日、缺失 bar、异常时点 G6 完备性问题账本 否 这是质量问题解释，不是行情事实字段。
停牌解释 G6 完备性问题账本，证据指向 suspend_d 否 缺失可以被解释，但 clean 行不需要为缺失添加列。
允许剔除的问题行 G6 完备性问题账本 否 先记账，再剔除；不能静默删数据。

4. 每一步审计什么

G0

事实输入完整性审计

先确认所有判断 clean 的外部事实都在本地 Lake 中存在，并且可读。这里不改任何文件。

  • stock_basic：判断股票是否仍在市场、上市日期、退市日期。
  • trade_cal：判断哪些日期是开市交易日。
  • suspend_d：解释某只未退市股票在某个交易日为什么没有分钟线。
  • namechange / bse_mapping：辅助建立旧代码到最新代码的映射。
  • raw_tushare/stk_mins_by_date：源站分钟线事实。
pass: 全部存在且可读 needs_review: 缺少 trade_cal / suspend_d failed: 文件损坏或 schema 不可解析
G1

security_identity_map 审计

目标是把源站旧代码映射到当前最新代码。它只产出映射表，不把映射字段写入每一行分钟线。

  • 同一个 source_ts_code 只能映射到一个 latest_ts_code。
  • 映射区间不能重叠，不能一行源数据匹配多个最新代码。
  • 北交所 920xxx.BJ、代码改名、曾用名必须能通过本地事实解释。
  • effective_delist_date 非空表示该最新股票已退市，clean 后续整只排除。
  • G1 中出现的所有情况，包括退市股票和无法确认映射，都必须写入身份账本。
pass: 唯一映射 needs_review: 只能靠名称猜测 failed: 冲突映射 / 区间重叠
G2

raw 分区审计

按 freq + trade_date 检查 raw 分区。raw 是源事实，审计只读，不用 downstream 结果反推 raw。

  • 路径必须符合 raw_tushare/stk_mins_by_date/freq=X/trade_date=YYYY-MM-DD。
  • trade_time 可解析，且能落到对应 trade_date。
  • 字段能读、文件非空、Parquet metadata 可解析。
  • raw 分区缺失不等于 clean 错误，但必须在后续完整性审计中说明影响。
pass: raw 分区可读 needs_review: 分区缺失但无法判断原因 failed: Parquet 损坏或字段无法解析
G3

clean dry-run 规则审计

写入 clean 前，先用只读方式模拟 raw -> clean，得到每个分区应保留多少、过滤多少、为什么过滤。

  • source_ts_code -> latest_ts_code：旧代码归一为最新代码。
  • invalid_price：OHLC 非法、全 0 或 high < low。
  • invalid_volume_amount：成交量或成交额为负。
  • invalid_trade_time：时间为空或无法解析。
  • before_list_date：未退市股票上市日前数据。
  • delisted_security：已退市股票整只排除。
  • duplicate_same_payload：同 key 内容一致，可去重并计数。
  • duplicate_conflict_payload：同 key 内容冲突，直接失败。
pass: dry-run 无冲突 needs_review: 身份缺失或事实不足 failed: 同 key 不同内容
G4

clean 写入安全门禁

clean 写入采用 _tmp -> 校验 -> replace。人话讲：先写到临时目录，确认新分区没问题，再替换正式分区。

  • 正式分区不允许半成品写入。
  • 写入字段必须严格等于 clean schema。
  • 写入结果必须和 dry-run 的 kept_rows、过滤原因统计一致。
  • 如果校验失败，临时结果不能提升为正式 clean。
pass: replace 成功且统计一致 failed: 写入后校验不一致
G5

clean schema / row quality 门禁

这是 clean 成品的行级硬门禁。它检查的是 clean 自身是否干净，不再看计算指标。

  • 字段必须等于 ts_code,freq,trade_time,open,close,high,low,vol,amount,trade_date。
  • ts_code + freq + trade_time 必须唯一。
  • trade_time.date == trade_date。
  • OHLC 必须大于 0，high >= low，vol/amount >= 0。
  • 不能出现已退市股票，不能出现上市日前数据。
pass: clean 行级质量通过 failed: 任一硬规则违反
G6

股票级交易日连续性审计

审计对象只包含 clean 中的未退市股票。它不是要求所有股票全历史都有数据，而是要求在该股票应该交易的窗口内，缺失必须有解释。

  • 预期日期：open_trade_dates_between(max(list_date, audit_start_date), audit_end_date)。
  • 如果 raw 中有应保留行但 clean 缺失：failed。
  • 如果 raw 没有行，但 suspend_d.suspend_type='S'：explained_by_suspend。
  • 如果 raw 没有行且停牌事实也缺：missing_source_or_calendar_gap，进入 needs_review。
  • 上市日前缺失：explained_by_lifecycle。
  • G6 暴露的问题必须写入完备性问题账本；需要剔除的问题行，只有先记账后才能在 clean 修复中剔除。
pass: 无未解释缺口 explained_by_suspend: 有停牌依据 needs_review: 事实不足 failed: clean 漏写
G7

日内 bar 完整性审计

对每只股票、每个频度、每个交易日，检查日内 K 线数量和时间点是否符合 A 股常规交易时段。

  • 常规交易时段：09:30~11:30，13:00~15:00。
  • 参考 bar 数：1 分钟 241，5 分钟 49，15 分钟 17，30 分钟 9，60 分钟 5。
  • bar_count == reference_count：通过。
  • 0 < bar_count < reference_count：needs_review，输出缺失时间段。
  • bar_count > reference_count：failed，通常是重复或异常时间点。
pass: bar 完整 needs_review: 少 bar failed: 多 bar / 异常时间
G8

derived / by_month research 门禁

clean 审计通过后，才允许生成 derived 和 by_month research。这里的核心是保证下游没有绕回 raw，也没有重新引入旧 schema。

  • derived 90/120 只能读取 clean_next 30/60。
  • by_month research 只能读取 clean_next/derived。
  • 输出全部使用最新 ts_code。
  • 输出不得包含行级身份字段。
  • by_month 行数必须等于对应 clean/derived 输入行数。
pass: 可以作为指标输入 failed: 读错源或 schema 污染

6. 门禁矩阵

阶段 审计对象 通过口径 阻断口径 下游影响
G0 事实输入 stock_basic、trade_cal、suspend_d、namechange、bse_mapping、raw stk_mins 本地文件存在、字段可读、关键字段不缺失。 关键事实缺失或不可读。 不能生成 clean。
G1 身份映射 security_identity_map 身份账本 每个源代码唯一映射到最新代码，映射区间无冲突；退市记录明确。 同一源代码多重映射、区间重叠、无法确定最新代码、退市状态缺依据。 不能执行 raw -> clean 归一。
G3 dry-run raw 行级规则 能解释每一行保留或过滤原因，且无冲突重复。 duplicate_conflict_payload、identity_conflict、规则无法解释。 不能写 clean。
G5 clean 成品 clean 分区 schema 严格、行级质量合格、唯一键无重复。 字段污染、非法价格、上市日前数据、已退市股票、重复冲突。 不能进入完备性审计和下游重建。
G6 交易日连续性 未退市股票的交易日覆盖与 G6 问题账本 缺失都能被停牌或生命周期解释，问题已记录到账本。 未解释缺口、raw/日历/停牌事实不足、问题未入账。 不能进入 derived/research。
G7 日内 bar 每只股票每个交易日的 bar 数和时点 bar 数符合频度规则，时间点合法。 多 bar、异常时间点、缺失 bar 未解释。 不能作为指标输入。
G8 下游层 derived 90/120、by_month research 只读 clean/derived，行数一致，schema 不污染。 直接读 raw、旧代码断裂、身份字段混入行级数据。 不能开始 MACD/MA/BOLL。

7. 状态如何汇总

单项状态

状态含义
pass明确通过。
failed确认错误，必须修复。
needs_review存在异常信号，现有事实不能自动判定。
duplicate_same_payload同 key 内容一致，可去重，但必须计数。
duplicate_conflict_payload同 key 内容不一致，等同失败。
explained_by_suspend缺失由停牌记录解释。
explained_by_lifecycle上市前缺失或退市股票整只排除。
missing_source_or_calendar_gapraw、交易日历或停复牌事实不足。

全局状态

门禁汇总遵循从严规则，不允许“多数通过就放行”。

  • 任意项 failed 或 duplicate_conflict_payload：全局 failed。
  • 否则任意项 needs_review 或 missing_source_or_calendar_gap：全局 needs_review。
  • 否则：全局 success。
放行条件： 只有全局 success 才允许进入 derived/research/MACD。needs_review 不是警告，它默认也是阻断。

8. 运行时序

从运行角度看，这不是“一边清洗一边算指标”的流程，而是分阶段门禁。上一阶段没有通过，下一个阶段不能启动。

9. 人话版结论

clean 通过前，谁都不能往下跑

如果 clean 里还有已退市股票、旧代码断裂、无效价格、重复冲突、未解释缺口，就不能生成 90/120，也不能重排 by_month，更不能算 MACD。

审计不是“看起来差不多”

每一类异常都必须落到固定枚举和统计上。能解释的写清楚，不能解释的进入 needs_review，确认错误的进入 failed。

退市股不进入研究事实

raw 可以保存退市股源站历史，但 clean 作为研究事实层不保留。退市股必须记录在身份账本里；clean 中出现退市股就是门禁失败。

停牌要靠事实解释

缺数据不能拍脑袋说“可能停牌”。必须用 suspend_d 解释，并记录到完备性问题账本；没有停牌事实，就进入 needs_review。
