stk_mins raw -> clean_next 同步链路详细技术方案 v1

本文承接《stk_mins raw -> clean_next 同步链路方案 v1》的拍板结论，把现有 raw 同步、clean_next 重建、审计、问题账本、下游读取能力整理成一套标准链路。 目标不是再造一套新系统，而是把已经存在的能力串成安全、可阻断、可审计的主链。

1. 拍板结论

编号 结论 工程含义
J1 同步命令最终默认强制刷新 clean_next，不留长期跳过分支。 raw 发布成功后必须进入 clean_next refresh。不能长期提供 --skip-clean-next 这类分叉语义。
J2 clean_next scoped audit 的完整性问题全部视为阻断。 缺 bar、重复 key、结构性非法值等问题写入问题账本后阻断下游，由人工审计修复。
J3 单股票补数后不允许只 patch clean_next 单股票。 只要 raw 的某个 freq + trade_date 分区被改动，clean_next 就按整个 affected partition 从 raw 重建。
J4 下游 derived / by-month / indicator 必须读取 clean_next 通过状态。 没有通过状态的分区不能被派生、重排或计算指标，避免继续吃旧 clean 或 raw。

2. 现有能力盘点：哪些可以复用

这次不是从零写一套。现有代码里已经有 raw 同步、clean_next 重建、审计、问题账本、原子替换等能力， 需要做的是把它们整理成“标准链路”，并补齐中间的连接和门禁。

能力 当前位置 当前作用 本方案如何使用
raw 同步 lake_console/backend/app/services/tushare_stk_mins_sync_service.py 从 Tushare 拉取分钟线，写入 raw_tushare/stk_mins_by_date/freq=*/trade_date=*。 保留请求、分页、限速、分区写入能力；新增标准 affected partitions 输出，并在 raw 发布后强制触发 clean_next refresh。
正式 clean_next 重建 StkMinsCleanService.rebuild_formal_clean_next_from_raw 从 raw 分区生成 research/stk_mins_by_date_clean_next，保留正式 11 列 schema。 作为 clean_next refresh 的核心构建能力复用，但需要沉淀为按 affected partitions 调用的内部服务。
clean_next 基础审计 StkMinsCleanService.audit_formal_clean_next_layer 检查字段、时间、价格结构、成交量额、身份账本、退市、上市日前、重复 key。 作为 refresh 后第一道强门禁。任何 failed 都阻断 clean_next 通过状态。
clean_next 完整性审计 StkMinsCleanService.audit_formal_clean_next_completeness 检查分区内每只股票的日内 bar 数是否满足预期或可解释范围。 按拍板结论升级为强阻断：needs_review 也不能放行下游，必须进入问题账本后人工处理。
问题账本 manifest/stk_mins_quality/clean_next_completeness_issue_ledger.parquet 记录 clean_next 完整性问题。 标准化为 clean_next scoped audit 的问题账本。基础审计与完整性审计都应以同一账本口径输出 issue。
原子替换与临时目录 parquet_writer.replace_directory_atomically、TmpCleanupService 用 _tmp/run_id 写临时分区，校验后替换正式目录。 raw、clean_next、derived、research 继续使用同一写入安全模型，不另造写入器。
source partition 变更记录 IndicatorRecalcQueueService.record_source_partition_replaced 记录分钟线源分区变更，提示指标后续重算。 保留该能力，但触发点应从 raw/derived 变为“下游可用分区已通过 clean_next gate”。
derived / by-month / indicator stk_mins_derived_service.py、stk_mins_research_service.py、indicator_source_reader.py 当前有读取旧 clean 或 raw 的路径。 必须改为读取 clean_next 或 clean_next 派生后的通过状态。这里是本方案明确要收口的缺口。
现有能力不是问题，问题是它们现在还没有形成一条统一的“raw 更新后 clean_next 必须跟进，并阻断下游”的主链。

3. 当前缺口

raw 同步后没有标准 clean_next refresh

现有同步命令可以写 raw，但 clean_next 重建仍主要是独立命令能力。后续必须接成同步后的强制步骤。

affected partitions 还不是一等模型

代码中会触碰分区，但缺少统一对象承载本次影响了哪些 freq + trade_date，导致 clean/audit/downstream 难以稳定串联。

审计结果还没有统一通过状态

问题账本已有，但下游需要一个明确 gate：某个分区到底是 passed、blocked 还是 not_checked。

下游仍可能绕开 clean_next

现有 derived/research/indicator 的读取路径还需要收口，否则 raw 和 clean_next 即便同步了，下游也可能继续读旧路径。

这里不是“可以以后慢慢优化”的问题。只要 derived / by-month / indicator 仍能读旧 clean 或 raw， clean_next 就不是事实入口，链路仍然不可信。M5 必须把这些旧读取路径改为阻断项清零。

4. 标准链路设计

5. 标准模型

5.1 AffectedPartition：通用受影响分区模型

affected partition 不应该只是 stk_mins 的临时结构，而应该是 Lake 写入链路的通用模型。 它表示“某次写入实际改变了哪个数据集、哪个层、哪个物理分区”。stk_mins 只是其中一种特化。

字段 含义 约束
dataset_key 数据集 key。stk_mins 场景固定为 stk_mins。 硬约束。
source_key 数据来源，例如 tushare。 硬约束。
layer 被写入的层，例如 raw_tushare、research、derived。 硬约束。
partition_grain 分区粒度，例如 trade_date、trade_month、snapshot。 用于通用调度和审计。
partition_values 分区键值字典。stk_mins 为 {"freq": "1", "trade_date": "2026-05-10"}。 通用模型的核心字段。
freq 分钟频度，允许 1/5/15/30/60。90/120 是 derived，不由 Tushare raw 同步直接产生。 stk_mins 特化字段，也必须同步写入 partition_values。
trade_date 被改动的交易日分区。 stk_mins 特化字段，也必须同步写入 partition_values。
raw_partition_path 对应 raw 分区路径。 必须存在，否则 refresh 不能开始。
source_run_id 触发这次 raw 改动的同步 run。 用于追踪，不参与业务计算。
write_revision 本次写入修订号，可用 run_id + partition_key 生成。 用于账本与 gate 判断“谁覆盖了谁”。
sync_scope all_market、single_symbol、range 等同步来源。 只做观测；不能改变 clean_next 按完整分区重建的规则。
rows_written / bytes_written 本次写入结果，用于展示和审计。 可为空，但同步命令能拿到时必须填。

5.2 CleanNextRefreshResult

这是 clean_next refresh 的结果单。同步命令最终展示给人的结果也应该来自它。

字段 含义 通过条件
status passed、blocked、failed。 只有 passed 允许下游继续。
raw_rows / clean_rows 本分区 raw 行数与 clean_next 保留行数。 可不相等，因为 clean 会剔除退市、上市日前、结构性非法行。
filter_reasons 清洗阶段过滤原因汇总。 必须能解释过滤行，不允许无理由丢行。
issue_count scoped audit 发现的问题数。 必须为 0 才是 passed。
ledger_path 问题账本路径。 blocked 时必须给出，方便人工审计。

5.3 CleanNextGateStatus

Gate 是给下游看的状态，不是给 raw 同步看的状态。它解决一句话： “这个 freq + trade_date 的 clean_next 分区，能不能被下游使用？” 

manifest/stk_mins_quality/clean_next_partition_gate.parquet

fields:
  gate_schema_version
  dataset_key
  source_key
  freq
  trade_date
  partition_key
  clean_partition_path
  source_run_id
  clean_run_id
  write_revision
  status              # passed / blocked / failed
  issue_count
  raw_rows
  clean_rows
  checked_at
  ledger_path
  message
如果实现阶段不想马上新增独立 gate 文件，也必须用现有问题账本推导出等价语义； 但长期建议沉淀 gate manifest，因为下游不应该每次都重新扫描完整问题账本。

5.4 问题账本版本与结构

问题账本本质上是一个给接口和前端消费的 issue 记录本，不是审计流水日志。 它应该长期保持为唯一文件：manifest/stk_mins_quality/clean_next_completeness_issue_ledger.parquet。 每次 scoped audit 都是“读旧账本 -> 合并本次结果 -> 原子替换写回同一个账本”。 

manifest/stk_mins_quality/clean_next_completeness_issue_ledger.parquet

target fields:
  ledger_schema_version       # 例如 2
  issue_key                   # 问题唯一身份；同一个问题跨多次审计保持不变
  issue_state                 # open / resolved / superseded
  severity                    # block / warning；当前完整性问题统一 block
  dataset_key
  source_key
  layer                       # research/stk_mins_by_date_clean_next
  partition_key               # freq=1/trade_date=2026-05-10
  freq
  trade_date
  trade_time
  latest_ts_code
  issue_type
  severity                    # block / warning；当前完整性问题统一 block
  issue_state                 # open / resolved / superseded
  expected_value
  actual_value
  evidence_dataset
  evidence_ref
  action
  reason
  first_seen_run_id
  last_seen_run_id
  resolved_run_id
  first_seen_at
  last_seen_at
  resolved_at
  seen_count
  superseded_by_issue_key
同一个问题只保留一条记录。再次审计发现同一个 issue_key 时，不新增第二条， 只更新 last_seen_run_id、last_seen_at、seen_count，并保持 issue_state=open。
禁止把账本设计成“每次审计追加一批流水”。那样同一个问题会持续膨胀成很多条， 后续接口和前端会很难判断当前到底还有哪些问题需要处理。

5.5 issue_key 与账本合并规则

issue_key 是问题的稳定身份，不能用随机数，也不能用“文件第几行”。 它应该由能定位同一个问题的稳定字段组合后生成。 

issue_key input:
  dataset_key
  layer
  partition_key
  gate
  issue_type
  latest_ts_code
  trade_time
  expected_value
  evidence_ref
本次审计结果 账本已有记录 处理规则
发现新的 issue_key 不存在 新增一条记录，issue_state=open，写入 first_seen_* 和 last_seen_*，seen_count=1。
再次发现同一个 issue_key 已存在且 issue_state=open 不新增记录，只更新 last_seen_run_id、last_seen_at，seen_count + 1。
本次 affected partition 已审计，但旧问题没再出现 已存在且 issue_state=open 标记为 resolved，写入 resolved_run_id 和 resolved_at。
本次没有审计到某个分区 该分区已有 open 问题 不更新。不能因为只审了 5 月 10 日，就误改 5 月 11 日的问题状态。
规则升级导致旧问题被新问题替代 旧问题已存在 旧问题标记为 superseded，并写入 superseded_by_issue_key。
ledger_schema_version 表示账本结构和字段语义版本，不是数据刷新版本。 只有账本字段变化或字段含义变化时才会变。普通同步、普通审计、问题新增或解决，都不会改变 ledger_schema_version。

6. 详细执行流程

步骤 动作 复用能力 失败处理
1 同步命令从 Tushare 拉取数据，写入 raw 临时目录。 TushareStkMinsSyncService 现有分页、限速、写 parquet 能力。 拉取或 raw 校验失败则本次同步失败，不进入 clean_next。
2 raw 分区原子发布。 replace_directory_atomically。 发布失败时必须回滚到旧分区，或者保留可恢复的 backup；不能留下半新半旧目录。
3 同步服务输出 affected partitions。 当前代码已有 freq/trade_date 维度，需要整理成标准对象。 没有 affected partitions 不能继续刷新 clean_next。
4 clean_next refresh 从 affected raw 分区完整重建 clean_next 候选分区。 rebuild_formal_clean_next_from_raw 的构建规则与 11 列正式 schema。 构建失败则保持旧 clean_next，不发布半成品。
5 执行 scoped audit。 audit_formal_clean_next_layer 与 audit_formal_clean_next_completeness。 任何 issue 都写账本并标记 gate blocked。
6 审计通过后发布 clean_next，并写 gate passed。 现有 clean_next 原子替换能力，加标准 gate manifest。 gate 未写成功时，本分区不得对下游放行。
7 下游 derived / by-month / indicator 读取前检查 gate。 新增 CleanNextGateService.require_passed(...)，集中复用。 未通过则报清楚错误，提示问题账本和修复命令。

6.1 同步与 clean refresh 的触发粒度

第一版不做并行流水线，按串行小批次推进。原则是：一个 raw 分区批次发布成功后， 立刻刷新这批 affected partitions 的 clean_next，而不是等整个超长同步命令全部跑完。

场景 raw 发布粒度 clean_next refresh 粒度 原因
单日全市场，多个 freq 每个 freq + trade_date 完成全市场 raw 后发布。 该 freq + trade_date 发布后立即 refresh。 避免 1min 已经更新但 clean_next 长时间滞后。
区间全市场，按窗口请求 每个 freq + window 会产生多个 trade_date 分区。 该窗口内已发布的 affected partitions 批量 refresh，然后再进入下一窗口。 减少长任务失败时的滞后面，同时避免每只股票触发一次 clean。
单股票补数 raw 层仍可能是单股票 merge 到完整分区。 按完整 freq + trade_date 分区从 raw 重建 clean_next。 不能只 patch clean_next 单股票，否则绕过分区审计。
换句话说：不是“整个 raw 都同步完才清洗”，也不是“每请求一只股票就清洗”。 正确粒度是 raw 分区已经完整发布以后，按 affected partition 批量刷新 clean_next。

6.2 raw 原子发布失败时怎么处理

“不进入半成品状态”的意思是：正式 raw 分区目录里不能出现一半旧文件、一半新文件。 当前工具函数先把旧目录移动到 backup，再把 tmp 目录移动到正式目录。目标实现必须补足失败回滚语义。

失败点 期望状态 处理方式
tmp 写入或校验失败 正式 raw 分区仍是旧版本。 删除本次 tmp 或保留到失败 run 目录；不触碰 final。
旧 final 移到 backup 失败 正式 raw 分区仍是旧版本。 停止发布，报错，不进入 clean_next。
tmp 移到 final 失败 必须恢复旧 final。 把 backup 移回 final；如果自动恢复失败，保留 backup 并阻断命令，提示恢复路径。
新 final 发布成功但 backup 删除失败 正式 raw 分区是新版本。 命令可报清理告警，但不能影响已发布分区；后续 tmp cleanup 清理 backup。

7. scoped audit 标准化

scoped audit 的输入只允许是 affected partitions。它不做全湖扫描，也不接受“顺手审一下别的日期”。

门禁 检查内容 问题状态 是否阻断
Schema clean_next 必须是正式 11 列：ts_code/freq/trade_time/open/close/high/low/vol/amount/exchange/vwap。 schema_violation 阻断。
时间 trade_time 必须可解析，且与分区交易日一致。 invalid_trade_time 阻断。
结构性价格 OHLC 必须可解析，high >= low。单纯 OHLC 为 0 不直接判错。 invalid_price_structure 阻断。
量额 vol、amount 不允许为负。 invalid_volume_amount 阻断。
身份账本 clean_next 里的 ts_code 必须能被 security_identity_map 解释，且已归一到最新代码。 identity_missing / before_list_date / delisted_security 阻断。
重复 key ts_code + freq + trade_time 必须唯一。 duplicate_same_payload / duplicate_conflict_payload 阻断。
完整性 日内 bar 数必须满足该 freq 的交易时段规则，盘后交易可解释范围除外。 missing_intraday_bar / extra_intraday_bar 按本次拍板，全部阻断，进入账本后人工审计修复。
这里的“阻断”不是删除 raw，也不是自动猜修复。意思是：clean_next 不放行，下游不准继续，问题进入账本等人工审计或专项命令处理。

8. 单股票补数的处理规则

单股票补数只是在 raw 层用单股票数据修复某个分区。clean_next 不允许只把这只股票 patch 进去。 因为 clean_next 的质量是按完整分区审计的，只 patch 一只股票会绕过分区级重复、完整性和身份规则。 

单股票补数例子：
  sync-stk-mins-range --ts-code 300114.SZ --freq 1 --start-date 2025-02-17 --end-date 2025-02-17

正确后续：
  raw freq=1/trade_date=2025-02-17 被更新
  affected partition = freq=1/trade_date=2025-02-17
  clean_next 从整个 raw 分区重建
  scoped audit 检查整个分区
  通过后下游才能读

禁止后续：
  只把 300114.SZ 的行塞进 clean_next

9. 下游读取收口

下游 当前风险 收口规则
derived 90/120 当前源码中有读取旧 research/stk_mins_by_date_clean 的路径。 90 只能读 clean_next 的 30 分钟 passed 分区；120 只能读 clean_next 的 60 分钟 passed 分区。
by-month research 当前源码中有读取旧 clean 路径的逻辑。 1/5/15/30/60 必须从 clean_next passed 分区重排；90/120 必须从 derived passed 分区重排。
indicator 当前 source reader 对 raw freq 仍可能读 raw_tushare 或旧 by-month。 指标源必须来自已通过 gate 的 clean_next / derived / by-month research，不允许直接扫 raw 计算。
这一步很关键：只改同步链路还不够。如果下游读取路径不收口，clean_next 再干净也可能没人用。

10. CLI 与输出设计

10.1 同步命令默认行为

lake-console sync-stk-mins-range \
  --all-market \
  --freqs 1,5,15,30,60 \
  --start-date 2026-05-01 \
  --end-date 2026-05-08

默认行为：
  1. 写 raw
  2. 输出 affected partitions
  3. 强制刷新 clean_next
  4. scoped audit
  5. 写 gate
  6. 如果 clean_next blocked，则命令整体以失败状态退出，但 raw 已保留

10.2 独立 refresh 命令

独立命令用于 raw 已经更新、clean_next 未通过或需要人工重跑的场景。它不是绕过主链的长期分支。

lake-console refresh-stk-mins-clean-next \
  --freq 1 \
  --trade-date 2026-05-08

lake-console refresh-stk-mins-clean-next-range \
  --freqs 1,5,15,30,60 \
  --start-date 2026-05-01 \
  --end-date 2026-05-08

10.3 失败输出

[stk_mins_clean_next] blocked affected=3 passed=2 blocked=1
[stk_mins_clean_next] ledger=manifest/stk_mins_quality/clean_next_completeness_issue_ledger.parquet
[stk_mins_clean_next] blocked_partition freq=1 trade_date=2026-05-08 issue_count=4
[stk_mins_clean_next] next: inspect ledger, repair raw or run dedicated repair command, then refresh clean_next again

11. 实施里程碑

本节是后续开发的执行边界。每个 milestone 只完成一个清晰目标，必须按顺序推进； 前一阶段的测试和验收没有通过时，不允许进入下一阶段。这里的拆分不是形式主义， 而是为了防止 raw、clean_next、账本、gate、下游读取一次性混改后无法定位问题。

阶段 目标 改动范围 主要产物 验收门禁 禁止事项
M0 安全底座：先补齐原子发布失败回滚能力。 replace_directory_atomically 及其直接测试。 安全 replace helper；覆盖 tmp 发布失败、backup 恢复、旧目录不丢失的测试。 构造失败场景时，final 分区要么保持旧版本，要么完整切到新版本，不能出现半成品。 不接入 sync 主链；不改 raw/clean 数据口径；不改其他数据集。
M1 沉淀 AffectedPartition 一等模型。 Lake Console 内部模型与 stk_mins raw 写入返回值。 通用 affected partition 结构： dataset_key/source_key/layer/partition_grain/partition_values/partition_path/source_run_id/write_revision/rows_written/bytes_written。 所有 stk_mins raw 写入路径都能返回明确的 freq + trade_date 受影响分区清单。 不触发 clean_next；不改变现有写入行为；不把模型做成 stk_mins 专属字段堆。
M2 重做问题账本为“唯一问题记录本”。 manifest/stk_mins_quality/clean_next_completeness_issue_ledger.parquet 写入逻辑。 ledger_schema_version、issue_key、issue_status、 first_seen_at、last_seen_at、seen_count、resolved_at。 同一问题重复审计只更新同一条记录，不追加膨胀；已消失问题标记 resolved。 不再使用“整文件覆盖当前审计结果”的旧语义；不把账本做成审计日志。
M3 实现 clean_next 分区 gate。 manifest/stk_mins_quality/** 质量元数据。 clean_next_partition_gate.parquet，记录每个 freq + trade_date 的 passed/blocked 状态。 下游可以只读 gate 判断是否允许消费，不需要自己拼账本、扫描文件或重复审计。 不让 derived/by-month/indicator 自行解释问题账本；不允许 gate 与账本状态不一致。
M4 封装 CleanNextRefreshService。 复用 formal clean_next rebuild/audit 能力，新增统一 refresh 编排。 输入 affected partitions 后，按分区从 raw 重建 clean_next，执行 scoped audit， 更新 issue ledger 和 gate，并返回标准结果。 dry-run/apply 都可用；clean_next blocked 时返回明确账本路径和阻断分区。 不做单股票 patch clean_next；单股票补数也必须按完整 affected partition 从 raw 重建。
M5 把 clean_next 强制接入 sync-stk-mins / sync-stk-mins-range。 只改 stk_mins 同步命令与同步服务，不改其他数据集。 raw 发布成功后必须刷新对应 clean_next；命令输出 raw/clean_next/gate/ledger 的结果。 小窗口真实同步后，raw 与 clean_next gate 同步推进；失败时 raw 保留、下游阻断。 不保留长期 --skip-clean-next 分支；不允许 sync 成功但 clean_next 状态沉默失败。
M6 下游读取路径收口到 clean_next。 derived、research by-month、indicator source reader、indicator queue/source metadata。 raw 频率 1/5/15/30/60 的下游统一读 clean_next passed 分区；90/120 仍读 derived。 旧 clean/raw 读取路径清零；未通过 gate 的分区不能被消费。 不把 gate 判断散落到页面或命令拼逻辑；不允许指标继续直接读 raw 生成。
M7 补齐测试门禁。 Lake Console 后端单元测试、服务测试、CLI 冒烟脚本或等价命令说明。 覆盖 successful refresh、blocked refresh、单股票补数触发完整分区 refresh、 ledger 去重更新、gate 阻断下游、原子发布失败回滚。 本节第 12 章列出的门禁必须全部可执行；旧口径测试同步改掉。 不为通过测试降低质量口径；不保留旧 clean/raw 读取断言。
M8 真实小样本验证与文档回写。 小窗口真实 CLI、技术方案文档、必要的开发说明。 选择 1 个单日全市场小样本和 1 个单股票补数样本，验证 raw、clean_next、ledger、gate、downstream 全链路。 真实样本能证明：同步后 clean_next 被强制刷新，下游只消费 passed 分区，blocked 有可读账本。 不做全量长跑；不顺手扩展到其他数据集；不把验证样本当作生产修复动作。
进入开发时必须按 M0 -> M8 顺序推进。尤其是 M0、M2、M3 是安全底座， 不能为了“先看到效果”跳过后直接改同步主链。

12. 测试门禁

单元测试

  • affected partitions 输出完整。
  • single-symbol raw merge 后仍按完整 partition refresh clean_next。
  • clean_next audit 有 issue 时不写 gate passed。
  • gate blocked 时 derived/research/indicator 报错并给出账本路径。

CLI 冒烟

  • 单日小范围同步：raw、clean_next、gate 同步产生。
  • 构造缺 bar 样本：命令失败，账本有记录。
  • 修复后 refresh：gate 从 blocked 变 passed。
  • 下游重建只消费 passed 分区。
