stk_mins MACD 大规模计算稳定性评审 v1

本文记录全市场多年 MACD 计算曾经为什么会被系统 kill，以及当前已经如何收口为可预估、可观测、分段提交、不会把内存打爆的计算链路。

当前状态：MACD 主链已落地 适用范围：lake_console / stk_mins / MACD 优先级：性能优先，其次稳定性与安全性 日期：2026-05-10

1. 已修复的问题与保留边界

已修复一次性读入多年全市场数据

原问题是 full 计算会把目标时间范围内的多年全市场文件攒到内存里。 当前 full 已按 source research 的 trade_month + bucket 流式读取，正式计算不再依赖一次性全量 rows。

已修复长时间无真实进度

原问题是进入大规模读取后没有月、bucket、行数心跳。 当前 full 输出名为 checkpoint 的月级进度日志，包含 month/bucket/source_rows/written； incremental 输出 trade_date/source_rows/symbols/written/state_count。

已修复一次性大提交，失败后有效产出为零

原问题是整段频度最后才统一 commit。 当前 full 按月提交指标分区与 state，incremental 按交易日提交；失败最多影响当前处理窗口，已提交窗口不会被抹掉。

仍禁止不能靠手工按月 full 分段绕过

MACD 是递推指标。每个股票、每个 freq 的 ema_fast、ema_slow、dea 必须从前一段延续。 如果每月都用 full 重算并重置状态，月初指标会失真。

已修复新增上市股票状态语义不完整

当前 all-market incremental 遇到缺 state 股票时，会读取本地 stock_basic。 list_date 落在本次窗口内的新股允许初始化；老股票缺 state 会拒绝并输出 needs_bootstrap。

已修复全市场 incremental 仍是大内存路径

当前 all-market incremental 按 trade_date 遍历 by_date 源分区，每次只读取当天当前 freq 的源文件， 并按交易日独立提交指标分区和 state。

保留边界自动 resume / force 未实现

当前已经做到月级/日级提交和真实进度输出，失败不会抹掉已提交窗口。 但没有实现自动识别上次 run 并续跑，也没有新增 --resume 或 --force 参数。

当前结论： MACD 主链已经从“大范围一次性读写”收口为 full 月级流式、incremental 日级流式、state 后置推进。后续如果要做自动 resume，需要单独评审，不得顺手加参数。

2. 方案原则

优先级 原则 落地要求
1 性能必须先过线 不能把全市场多年数据一次性读入内存；必须按 freq -> trade_month -> bucket 或等价小块流式处理。
2 计算准确性不能让位于分段 分段只是工程执行单位，MACD state 必须跨分段延续；不能每月重置 EMA。
3 失败影响要可控 每个可提交窗口成功后推进正式分区和 state；失败时最多损失当前小窗口，不损失已完成月份。
4 状态推进必须安全 只有指标 by_date 分区写入并校验成功后，才能推进 manifest/indicator_state。
5 进度必须与实际行为一致 读取、计算、写入都要输出当前 freq/month/bucket/symbol/rows，不能只输出“开始了”。

5. 具体改造方案

改造项 方案 解决的问题
源数据读取 新增流式 reader：按 freq -> trade_month -> bucket 逐块 yield；禁止返回全量 batch list。 解决一次性读入多年全市场数据导致 OOM。
计算状态 full 模式在本次计算内部从空 state 起步，但跨月延续工作 state；incremental 模式从 manifest state 继续。 保证分段执行不破坏 MACD 递推准确性。
新上市股票 full 模式下，某股票首次出现在源数据时允许从第一根 bar 初始化；incremental 模式下需要明确判断是“新股首次出现”还是“历史 state 缺失”。 避免历史长区间中新增股票导致全市场任务失败。
写入提交 按月作为最小提交窗口：当月所有 bucket stage 完成后，替换该月涉及的 by_date 分区，再推进 state。 失败最多损失当前月份，已完成月份保留正式结果。
进度输出 每个读取块输出 freq/month/bucket/source_rows/symbol_count/written_rows，并在月提交后输出名为 checkpoint 的月级进度日志。 让用户能判断是否正常推进、耗时是否合理。
incremental 流式化 全市场 incremental 按 freq -> trade_date -> source part 读取 by_date 源分区，逐日 stage、逐日提交并推进 state。 避免把一段时间内所有 by_date 源文件一次性读入内存，同时让日常增量任务具备明确进度。
前置门禁 执行前检查 source research 是否齐全、估算任务规模、检查 lake root 可写；大范围任务必须走流式链路。 把高风险失败提前到启动阶段，并避免重新回到大内存路径。
失败影响控制 full 按月提交，incremental 按交易日提交；已成功提交的窗口会保留正式结果和 state。本方案没有实现自动 resume，也没有新增 --force。 避免失败后有效产出为零；用户仍需按明确范围重跑未完成窗口。
测试门禁 增加月边界 state 延续测试、新股首次出现测试、流式 reader 不返回全量列表测试、失败不污染正式分区测试。 防止以后又把链路写回大内存模式。

6. 全市场 incremental 流式化方案

incremental 和 full 的输入路径不同。full 为了保证多年递推效率，读取 source research； incremental 面向“已有 state 后追加新数据”，应该读取 by_date 源分区，并且按交易日小块推进。

项目 当前实现 目标实现
源读取 一次性收集日期区间内所有 by_date parquet 文件，并拼接成完整 rows。 按 trade_date 遍历源分区；每次只读取当天、当前 freq 的源文件。
计算状态 先检查本次涉及的所有股票是否已有 state，缺一个就整体失败。 每个交易日按股票分组；已有 state 则递推；缺 state 时进入 M7 判定，新股允许初始化，老股拒绝。
写入提交 一个日期区间共用一个 writer session，最后统一 commit。 按交易日提交：当天指标 by_date 分区写入成功后，推进 state 到当天。
内存上限 和日期区间长度线性增长。 和“单个交易日、单个 freq 的源分区大小”相关，不随区间无限增长。
失败影响 区间中途失败时，已 stage 但未 commit 的结果不可用。 失败最多影响当前交易日；之前已完成日期的结果和 state 已经推进。
进度输出 按 symbol 输出，开始前仍可能长时间读数据。 输出 freq/trade_date/source_files/source_rows/symbols/written/state_count。

incremental 的安全规则

  1. 只能在已有 full baseline 的前提下运行全市场 incremental；没有 baseline 时必须提示先跑 full。
  2. 每个交易日独立提交，不能把一段日期区间攒到最后才提交。
  3. 缺 state 股票必须读取本地 stock_basic 股票池，用 list_date/delist_date 判断生命周期。
  4. list_date 落在本次增量窗口内的新上市股票，可以从首次出现的分钟线初始化。
  5. list_date 早于本次增量窗口的老股票缺 state，必须拒绝继续，并输出 needs_bootstrap 和样例原因。
  6. incremental 完成后只重建受影响月份的 indicator research，不重建无关月份。

7. 正确计算流程

  1. 执行 compute-stk-mins-indicator-range 前先做 preflight，列出 freq、月份数、bucket 数、预计输入文件和输出分区。
  2. 每个 freq 单独处理，避免 1 分钟线把其他频度也拖死。
  3. 每个 freq 内按月份顺序处理，确保 MACD 时间顺序正确。
  4. 每个月内按 bucket 读取 research 源文件，一次只把一个 bucket 的一个月数据放进内存。
  5. 每个 bucket 内再按 ts_code 分组，按 trade_time 顺序计算 MACD。
  6. 每只股票计算时读取当前工作 state；没有 state 且属于本轮 full 首次出现，则从第一根 bar 初始化。
  7. 把当月所有 bucket 的指标结果写入 _tmp。
  8. 当月全部 bucket 写完并校验后，替换正式 by_date 分区。
  9. 正式分区替换成功后，才把 state 推进到本月末。
  10. 输出月级进度，再进入下一个月；这里不是自动 resume checkpoint 文件。
  11. 所有月份完成后，重建对应月份的 indicator research 层。

8. 禁止的绕路方案

禁止按月执行 full 命令

这样会让每个月第一根 K 线重新初始化 EMA，结果看似有值，但跨月指标不连续。对于 MACD 来说，这是错误数据。

禁止继续扩大机器内存硬扛

大内存只能推迟事故，不能解决计算链路不可恢复、无进度、无门禁的问题。工程上必须改成流式和分段提交。

禁止只改 progress 文案

如果底层仍然一次性读全量，进度输出只是安慰剂。必须让进度跟真实小块读取、计算和提交绑定。

禁止state 与结果分开随意推进

state 比结果更靠后或更靠前都会造成后续增量计算错位。必须坚持“结果分区成功提交后，state 才能推进”。

9. 实施状态

阶段 目标 验收标准
M1 新增流式 research reader 和 preflight 估算，不改变正式写入。 大范围任务启动前能列出月份、bucket、源文件缺失和预计规模；reader 单测证明不会返回全量列表。
M2 改造 all-market full 为按月提交，state 跨月延续。 跨月样例中，第二个月首根指标不被重置；失败只影响当前月份。
M3 补齐新增上市股票 bootstrap 与 state 缺失保护。 历史区间新增股票可正常开始计算；异常缺 state 能明确报错并给出处理建议。
M4 增加月级提交、日级提交和更清晰进度输出。 失败不再抹掉已提交窗口；进度至少显示 freq、month/trade_date、bucket/part、rows、written。
M5 把 range 命令切到新链路，并禁止旧的大内存路径承接大任务。 全市场多年命令不再被 OS 因内存杀死；小范围 smoke 和长区间 plan 都能通过。
M6 把 all-market incremental 改成按交易日流式读取、按日提交、按日推进 state。 长日期区间 incremental 不再一次性读入所有 by_date 源文件；每日增量和补跑都能看到真实进度。
M7 补 all-market incremental 的 state 缺失判定和新股首次出现处理。 新上市股票能自然进入指标库；老股票异常缺 state 时拒绝继续，避免算出中途初始化的假 MACD。
M8 落地源数据修复后的人工重算队列。 源分区替换后可记录待重算项，用户可查看建议命令并在人工重算后标记完成；不自动消费队列。
后续 自动 resume、MA、BOLL 等能力单独评审。 不得在 MACD 主链收口文档里把这些未实现能力写成当前代码事实。

10. 评审结论

推荐决策： 不再尝试给用户一组“手工分段命令”来绕过问题。当前 MACD 全市场计算链路已经改成流式、分段提交、state 连续的实现；自动 resume 仍需另行设计。

这样做以后，用户可以继续使用一条高层命令表达目标区间和频度，系统内部负责拆成安全的小计算窗口。 用户不应该被迫理解 bucket、月提交、state 延续这些内部细节；这些是工程系统必须自己承担的能力。

full 和 incremental 都必须满足同一条底线：不能因为用户传入较长日期区间，就把所有源文件一次性读入内存。 full 按 source research 的月/bucket 流式处理；incremental 按 by_date 的交易日分区流式处理。

事实依据：当前代码读取链路见 lake_console/backend/app/services/indicators/indicator_source_reader.py、 indicator_compute_service.py、 indicator_by_date_writer.py。 本文随当前实现维护，用于说明已落地机制、当前边界和后续需要单独评审的能力。
