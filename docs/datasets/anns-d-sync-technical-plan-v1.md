## 1. 目标、依据与范围

目标：保留有独有信息的公告；完整记录覆盖无独有信息的残缺记录；可观测、可取消、可恢复地同步历史范围。

依据为用户对缺 rec_time、缺 URL 和冗余案例的决定、Tushare doc_id=176 的[本地源文档](/Users/congming/github/goldenshare/docs/sources/tushare/大模型语料/0176_上市公司全量公告.md)、当前 Definition、转换器、Raw/view 模型、DAO、执行器和 TaskRun，以及[开发模板](/Users/congming/github/goldenshare/docs/templates/dataset-development-template.md)。实现细节与硬要求追溯只在[LLD](/Users/congming/github/goldenshare/docs/datasets/anns-d-sync-low-level-design-v1.md)维护。

范围：anns_d 的缺值处理、身份、完整性覆盖、持久化、按日规划、分页进度与恢复；既有公告维护入口和日期范围输入继续使用。修改消费者读取合同，适配 PDF CLI。没有 OCR、全文检索、调度新功能、Worker/lane、新数据源、Lake 写入或安装依赖。

用户已明确的业务决定与工程设计分开：允许缺值、消除该案例冗余是用户决定；下文冲突保留、原始证据留存、预算、表结构和执行方案是本次具体设计。P0 文档交付不包含生产执行授权。

## 3. 公告保存与覆盖原则

必填：ann_date、ts_code、title；可空：name、url、rec_time。缺值不拒绝、不补造。URL 是否可下载由下载工具判断。可选时间解析失败保存 NULL 和原文证据、计质量告警；不让可选属性格式错误丢掉整条公告。

候选组 G=(ann_date, ts_code, title)，日期必不可少；标题只沿用必要字符清理，不截断、不模糊匹配。源代码不限定上市证券代码正则或当前股票池，S1649.SZ、债券公告等源端样本不因类型被过滤。

组内比较属性 V=(name, url, rec_time)。B 覆盖 A，当且仅当 A 每个非空属性与 B 对应属性相同，且 B 至少多一个非空属性。六字段相同是完全重复。有效公告集合等于组内所有不被其他记录覆盖的版本。这是信息包含关系，不是非空数排名或最后写入覆盖。

| 输入情况（日期、代码、标题相同） | 有效结果 | 分类 |
| --- | --- | --- |
| 六字段相同 | 一条 | 完全重复 |
| URL 空 / U，时间都空，名称相同 | U 一条 | 残缺被完整覆盖 |
| URL 都 U，时间空 / T，其余兼容 | U+T 一条 | 时间补齐 |
| 所有版本 URL、时间都空，名称相同 | 一条残缺公告 | 正常保存 |
| 两个不同非空 URL | 两条 | 信息冲突保留 |
| 同 URL、两个不同非空时间 | 两条 | 信息冲突保留 |
| 两个不同非空名称 | 两条 | 信息冲突保留 |
| A=(U,NULL)，B=(NULL,T) | 两条 | 不凭兼容关系合成源端不存在的完整记录 |
| 上例之后出现 C=(U,T)，名称兼容 | 只显示 C | C 覆盖 A、B |
| 两个不同 URL 完整版与一条无独有属性的空 URL 版 | 两个完整版 | 空版本冗余 |
| 空 URL 版有其他完整版均没有或不一致的时间/名称 | 保留该版本 | 有独有信息 |
| 日期不同，代码标题相同 | 不同组分别保存 | 不跨日期合并 |

用户于2026-10-02明确拍板：物理上只保存最终有效集合，不保留被覆盖的残缺版本；非空冲突按上述保守规则分别保留。Raw和有效公告读取出口都没有被覆盖冗余。质量告警只保留有限样本及统计，不另建长期源版本历史库，也不把被覆盖载荷藏进raw_payload。迁移恢复资料是获准执行期间的恢复用途，不成为日常公告版本存储。

## 4. 身份与持久化方向

raw_tushare.anns_d 直接保存组内不被覆盖的记录，core_serving_light.anns_d 继续提供同名普通视图。每批将同组现存记录与本批新记录合并计算有效集合；忽略新输入中被覆盖的残缺版本，物理删除库内被完整版本覆盖的行，只插入尚不存在的有效版本，全部在同一短事务内完成。先完整后残缺、先残缺后完整、跨页、跨运行以及重放都必须得到相同的六字段业务集合。到达顺序造成的自增id、fetched_at差异不属于业务集合一致性口径。

六字段指纹只识别规范化记录内容，不作为唯一公告实体永久ID。已存在且仍有效的同指纹行保持id；完整版本替代旧残缺版时旧id可被删除、新版获得新id，不承诺代表id永不变化。PDF文件身份仍为日期、代码、URL，消费者不得用Raw id作为永久公告实体键。新增group_key索引支持跨批匹配，不新增is_current、covered_by_id或冗余版本表。

不改写非空冲突、不把互补残缺记录拼成不存在的源行。每条保留记录的raw_payload来自该保留源版本，不能为物理删除留一份冗余公告全文。

新增业务完成凭证 anns_d_sync_unit，仅服务本需求的持久化完成边界，不成为第二套 TaskRun。凭证与 unit 最后一批业务结果同事务提交；Ops 状态写入单独事务。理由：现行 Ops 节点更新允许失败，不能作为可靠跳过数据的唯一依据。字段与恢复规则见 LLD，P0 未创建表。

## 5. 长任务方向、预算和成本

point 为一个自然日；range 由 resolver 按自然日拆分，builder 仅格式化 start_date=end_date。仍然 bucket_rule=not_applicable、observed_field=ann_date，不要求连续日期有数据。六字段显式请求，单线程、每页 2,000、每次写入最多 500；每批提交，组内候选查询有硬上限，禁止整日或完整范围常驻内存。

已完成日期从业务凭证恢复；未完成日期从 offset=0 重放，原来提交的数据保留。offset 只用于一次尝试内分页。重复执行同范围进行新观察，不能永久跳过可能更新的日期；只有明确继续同一冻结执行计划才复用完成凭证。显式续跑关联输入已在 P2 同步 Ops API/手动表单，CLI/自动 workflow 显式省略，详见 LLD §12，不隐式猜测“最近一次同范围任务”。

2020—2024 共 1,827 天。若源端总返回量仍为 10,098,550，每天以短页/空页终止，请求量为 sum(floor(N_day/2000)+1)，包含空日；仅在该固定数据分布假设下约 5,050—6,876 次，不含重试。不能把请求数量当成已证明完整性的源端总量。按每页 8 秒估计串行拉取约 11.2—15.3 小时，另加写库和限流等待；这是情景估算，非 ETA 或配额承诺。大 offset 不再跨五年增长，但日内深分页与限流仍须实测。

工程预算集中写入 Definition 的具名执行策略，具体配置审计见 LLD：计划最多 3,660 天；每天最多 500 请求页、1,000,000 源行；每执行含重试最多 15,000 请求；响应体最多 64 MiB；候选组最多 128 个不同源版本。超限安全停止并保留已提交事实，不截断后报成功。源请求和数据库不可分割调用目标不超过 25 秒，取消响应门禁 30 秒。数值是设计预算，P1/P2 测量如需调整须同步本文及 LLD，不在脚本另设默认。
