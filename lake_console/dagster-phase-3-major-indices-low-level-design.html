Dagster Phase 3 主要指数 Low Level Design

本文严格承接 Phase 3 主要指数方案设计，描述下一步编码落地需要遵守的文件结构、资产实现、字段契约、 PostgreSQL metadata、Tushare 请求、历史回补、jobs、sensors、checks、验证与风险门禁。

设计输入Phase 3 主要指数方案设计
模板依据Dagster 数据集资产接入综合模板
本地 Dagster1.13.6，已验证存在 BackfillPolicy.single_run
源站审计2026-05-23 已用 tushareMCP 与本地 SDK 校准字段和分页

Dagster 官方依据： Asset jobs、 Automation condition sensors、 Backfilling data。

1. 范围与硬边界

最终目标

主要指数 gold 日表

gold_market_major_indices_daily[trade_date] 输出首页主要指数 10 个卡片事实。

中间事实

active 指数日线

silver_index_daily[trade_date] 是经过 active 池过滤后的指数日线标准事实。

源站镜像

Tushare 重新拉取

index_basic 与 index_daily 都从 Tushare 拉取，不从旧湖 bootstrap。

不做事项： 本 LLD 不设计 ClickHouse serving，不改财富端 API，不发布 prod，不改页面 UI，不把 active pool 或主要指数名单放进 YAML。 历史回补进入 Dagster，但不挂 sensor、不进入日常生产自动化。

2. 代码文件结构

文件命名按数据集和职责拆开，避免宽泛文件爆炸。新增文件应遵守“jobs 只做 selection，assets 做生产逻辑，checks 做质量判断”的门禁。

目录 职责 禁止事项
assets/** 拉取 Tushare、读取或维护本地 metadata 表、写 raw/silver/gold Parquet、返回 materialization metadata。字段常量和数据集专属 helper 第一版也放在对应 asset 文件内。 不得把下游 job 的流程判断塞进 asset；不得手改其它资产。
jobs/** 只定义 define_asset_job 名称、selection、checks selection、description。 不得写 Tushare、SQL、Parquet、路径拼接或质量判断。
sensors/** 读取 Dagster instance 状态，判断 ready，提交 RunRequest 或 SkipReason。 不得在 sensor 中写数据湖、写 metadata 表或直接修复上游。
resources.py 集中放外部系统连接资源，例如 TushareResource、LakeRootResource、DuckDBResource，以及本地 metadata PostgreSQL 连接。 只提供连接能力，不写具体业务表逻辑。
目录收敛口径： 第一版不新增 contracts/ 或 metadata/ 顶层目录。字段契约跟随对应资产文件； 本地 PostgreSQL 连接放 resources.py；active pool / 主要指数名单的具体表读写 helper 跟随对应 asset 文件。 后续只有当复用范围明确扩大时，才讨论单独抽目录。

4. 本地 PostgreSQL Metadata

active pool 与主要指数名单是配置型数据资产。它们不使用 YAML 作为长期事实源，唯一事实源是本地 PostgreSQL metadata 表， 通过 Dagster update job 修改并 materialize 为 Parquet asset。

5. Asset 实现细节

Asset 实现要点 Materialization metadata
raw_tushare_index_basic 调用 index_basic，不传 market，显式传 13 字段，limit/offset 分页。 写 raw/tushare/index_basic/full/part-000.parquet。 path,row_count,columns,page_count,market_distribution,source_method=tushare_api_full_snapshot
silver_index_basic 读取 raw；日期字段转 DATE；按 ready_for_trade_date 过滤终止指数： exp_date is null OR exp_date > ready_for_trade_date。 ready_for_trade_date,source_row_count,kept_row_count,terminated_removed_count,market_distribution
silver_index_daily_active_pool 根据 run config 初始化或维护当前 active 指数列表；写本地 PostgreSQL 当前表和 history 后，读取当前表写 silver Parquet。 校验所有 code 存在于 silver_index_basic 且未终止。 path,row_count,active_count,added_count,removed_count,history_ids
raw_tushare_index_daily 分区资产。单日运行按 ts_code + trade_date 请求；历史 range backfill 按 ts_code + start_date/end_date 请求，先写 staging，再按日期一次性生成完整 raw 分区。 path,row_count,requested_code_count,returned_code_count,page_count,source_method,empty_code_samples
silver_index_daily 读取 raw、silver_index_basic 和 active pool；只保留 active pool 内指数； trade_date 转 DATE，change 改为 change_amount。 path,row_count,raw_row_count,active_pool_count,missing_active_count,coverage_rate
gold_market_major_indices 根据 run config 初始化或维护当前首页主要指数 10 个名单；写本地 PostgreSQL 当前表和 history 后 materialize 当前名单。 path,row_count,item_count,added_count,removed_count,reordered_count,history_id
gold_market_major_indices_daily 读取 silver_index_daily、silver_index_basic 和主要指数名单； 输出固定 10 行，字段面向 API。 path,row_count,major_indices_count,missing_code_samples

6. 历史回补设计

禁止低效回补： 不允许按 ts_code × trade_date 请求历史数据。历史回补必须按 ts_code + start_date/end_date 拉时间序列。

优先技术路线

raw_tushare_index_daily 与 silver_index_daily 从第一版开始设计为可支持单分区运行和 range backfill。 历史回补 job 仍使用 define_asset_job 做 asset selection，不写 op 逻辑。 

raw_tushare_index_daily(
  partitions_def=cn_a_trade_days,
  backfill_policy=dg.BackfillPolicy.single_run(),
)

silver_index_daily(
  partitions_def=cn_a_trade_days,
  backfill_policy=dg.BackfillPolicy.single_run(),
)

index_daily_history_backfill_job = dg.define_asset_job(
  name="index_daily_history_backfill_job",
  selection=AssetSelection.assets(raw_tushare_index_daily, silver_index_daily)
            | AssetSelection.checks_for_assets(raw_tushare_index_daily, silver_index_daily),
)

range backfill 执行流程

读取 partition range -> 得到 start_date/end_date
读取 silver_index_basic 有效指数列表
for ts_code in effective_codes:
  调用 index_daily(ts_code, start_date, end_date, fields, limit, offset)
  将结果写入 staging chunk

DuckDB 读取 staging chunks
按 trade_date 分组
for trade_date in target_dates:
  生成 raw/tushare/index_daily/trade_date=YYYY-MM-DD/part-000.parquet.tmp
  os.replace 到 part-000.parquet

silver_index_daily 对同一 range 读取 raw 分区
按 active pool 生成 silver 分区
实现前验证门禁： Slice 3.0.0 已使用临时 /private/tmp Dagster instance 验证本地 Dagster 1.13.6 的 BackfillPolicy.single_run() 行为，没有污染正式 Dagster instance 或正式湖。

Slice 3.0.0 验证结论

  • BackfillPolicy.single_run() 可用于 index daily 历史回补：dg launch --partition-range 对 3 个测试日期只生成 1 个 run。
  • asset 代码必须使用 context.partition_keys 或 context.partition_key_range 处理分区集合；不能把 context.partition_key 作为 range backfill 主逻辑。
  • range run 会为每个分区写入 materialization 记录，get_materialized_partitions() 与 get_status_by_partition() 都能看到分区状态。
  • blocking check 可执行，但验证中 check 成功记录是 range 级别一次 evaluation，metadata 中包含本次检查覆盖的 partition keys；不是每个分区单独一条 SUCCEEDED check 记录。
  • 如果 job selection 中混入未声明 BackfillPolicy.single_run() 的 partitioned asset，CLI 会拒绝 --partition-range，要求改用 UI/daemon backfill 或让所有 selected assets 统一声明 single-run policy。
  • 因此 index_daily_history_backfill_job 选择的 raw/silver index daily 资产及对应代码必须统一 range-aware；checks 设计必须接受 range 级别评价，并在 metadata 中清晰列出覆盖分区。

staging 目录

data_lake/raw/tushare/index_daily/_staging/run_id=<run_id>/chunks/{ts_code}-{page}.parquet

staging 不是正式资产，不参与 asset graph，不被下游读取。它的生命周期只属于本次历史回补 run： run 开始时创建；拉取分页数据时写入 chunks；目标 raw 分区全部写入并验证通过后删除； run 失败时短期保留用于排错，metadata 必须记录 staging 路径和失败 code 样本，排错完成后人工清理。 后续重跑必须使用新的 run_id 目录，不复用旧 staging。

7. Jobs 与 Selection

Job selection run config 说明
index_basic_update_job raw_tushare_index_basic、silver_index_basic 与 checks ready_for_trade_date 日更 full snapshot。job 不写逻辑，asset 使用 config 标记服务到哪个交易日。
index_daily_active_pool_initialize_job silver_index_daily_active_pool 与 checks 无人工输入；只读远程 prod ops.index_series_active resource='index_daily' 一次性初始化 active pool；初始化完成后不再同步远程。
index_daily_active_pool_update_job silver_index_daily_active_pool 与 checks items 人工维护入口，提交当前完整 active 指数列表，不自动跟远程同步。
index_daily_update_job raw_tushare_index_daily、silver_index_daily 与 checks partition key 日频单分区更新；只读依赖 silver_index_basic 和 active pool。
index_daily_history_backfill_job raw_tushare_index_daily、silver_index_daily 与 checks partition range 手动历史回补；不挂 sensor；优先走 BackfillPolicy.single_run()。
market_major_indices_initialize_job gold_market_major_indices 与 checks 无人工输入；只读远程 prod major_indices.cn_a.v1.json 一次性初始化当前首页主要指数 10 个名单；初始化完成后不再同步远程。
market_major_indices_update_job gold_market_major_indices 与 checks items 人工维护当前 10 个首页主要指数名单。
market_major_indices_daily_job gold_market_major_indices_daily 与 checks partition key 只生产最终 gold；不 selection index basic / index daily 上游。

8. Sensors 与自动化

Sensor 输入状态 触发条件 RunRequest

12. 风险与待确认项

风险 影响 处理口径
BackfillPolicy.single_run() 行为不满足 UI/check 可观测要求。 已验证可用于历史回补，但 checks 是 range 级别成功评价，不是每个分区单独一条成功评价。 后续 index daily 历史回补继续采用该路线；raw/silver assets 必须统一 single-run，checks metadata 必须列出覆盖分区。
有效指数数量过大。 日频同步和历史回补请求量过高。 在 silver_index_basic 完成后先输出有效指数数量和请求量测算，再决定回补批次。
prod active pool 初始化必须严格受控。 如果泛化读取远程 ops 表，会破坏 lake console 的远程隔离边界。 lake_console/AGENTS.md 已白名单化：仅 index_daily_active_pool_initialize_job 可一次性只读 ops.index_series_active resource='index_daily'，初始化后不再同步。
prod 主要指数 JSON 初始化必须严格受控。 如果长期读取远程 JSON，会形成第二事实源和远程运行依赖。 lake_console/AGENTS.md 已白名单化：仅 market_major_indices_initialize_job 可一次性只读该 JSON，初始化后本地 metadata 表是唯一事实源。
index_daily 源站 ready 时间未知。 sensor 可能过早探测导致 skip 或错过更新。 先用 preview 和单日真实探测验证，默认 STOPPED，不长期开启。
metadata 表人工维护入口设计过复杂。 运营维护困难，history 不可审计。 第一版只支持初始化和全量替换当前表；复杂差异编辑后续再讨论。
