Dagster Phase 3 主要指数 Low Level Design

本文严格承接 Phase 3 主要指数方案设计，描述下一步编码落地需要遵守的文件结构、资产实现、字段契约、 PostgreSQL metadata、Tushare 请求、历史回补、jobs、sensors、checks、验证与风险门禁。

设计输入Phase 3 主要指数方案设计
模板依据Dagster 数据集资产接入综合模板
本地 Dagster1.13.6，已验证存在 BackfillPolicy.single_run
源站审计2026-05-23 已用 tushareMCP 与本地 SDK 校准字段和分页

Dagster 官方依据： Asset jobs、 Automation condition sensors、 Backfilling data。

1. 范围与硬边界

最终目标

主要指数 gold 日表

gold_market_major_indices_daily[trade_date] 输出首页主要指数 10 个卡片事实。

中间事实

active 指数日线

silver_index_daily[trade_date] 是经过 active 池过滤后的指数日线标准事实。

源站镜像

Tushare 重新拉取

index_basic 与 index_daily 都从 Tushare 拉取，不从旧湖 bootstrap。

不做事项： 本 LLD 不设计 ClickHouse serving，不改财富端 API，不发布 prod，不改页面 UI，不把 active pool 或主要指数名单放进 YAML。 历史回补进入 Dagster，但不挂 sensor、不进入日常生产自动化。

2. 代码文件结构

文件命名按数据集和职责拆开，避免宽泛文件爆炸。新增文件应遵守“jobs 只做入口，assets 做生产逻辑，checks 做质量判断”的门禁。下面按当前代码事实区分“已实现”和“待新增”，避免把规划文件误读为已存在文件。

目录 职责 禁止事项
assets/** 拉取 Tushare、读取或维护本地 metadata 表、写 raw/silver/gold Parquet、返回 materialization metadata。字段常量和数据集专属 helper 第一版也放在对应 asset 文件内。 不得把下游 job 的流程判断塞进 asset；不得手改其它资产。
jobs/** 定义 asset job 的名称、selection、checks selection、description；受控手动回补 job 也只能做薄入口组合，不能承接具体数据生产逻辑。 不得写 Tushare、SQL、Parquet、路径拼接或质量判断。
backfills/** 放受控历史回补流程编排，例如读取 run config、生成目标交易日列表、调用已复用的拉取/写入/check evaluator，并显式记录 materialization/check evaluation。 不得挂 sensor/schedule/automation；不得绕开正式路径、字段契约和 checks。
sensors/** 读取 Dagster instance 状态，判断 ready，提交 RunRequest 或 SkipReason。 不得在 sensor 中写数据湖、写 metadata 表或直接修复上游。
resources.py 集中放外部系统连接资源，例如 TushareResource、LakeRootResource、DuckDBResource，以及本地 metadata PostgreSQL 连接。 只提供连接能力，不写具体业务表逻辑。
目录收敛口径： 第一版不新增 contracts/ 或 metadata/ 顶层目录。字段契约跟随对应资产文件； 本地 PostgreSQL 连接放 resources.py；active pool / 主要指数名单的具体表读写 helper 跟随对应 asset 文件。 后续只有当复用范围明确扩大时，才讨论单独抽目录。

4. 本地 PostgreSQL Metadata

active pool 与主要指数名单是配置型数据资产。它们不使用 YAML 作为长期事实源，唯一事实源是本地 PostgreSQL metadata 表， 通过 Dagster update job 修改并 materialize 为 Parquet asset。

配置审计

配置项 建议值 / 来源 消费者 缺失行为
TUSHARE_TOKEN 既有环境变量；继续通过 dg.EnvVar("TUSHARE_TOKEN") 注入。 TushareResource code location 不崩；实际调用 Tushare 时失败并给清晰错误。

5. Asset 实现细节

Asset 实现要点 Materialization metadata
raw_tushare_index_basic 调用 index_basic，不传 market，显式传 13 字段，limit/offset 分页。 写 raw/tushare/index_basic/full/part-000.parquet。 path,row_count,columns,page_count,market_distribution,source_method=tushare_api
silver_index_basic 读取 raw；日期字段转 DATE；按 ready_for_trade_date 过滤终止指数： exp_date is null OR exp_date > ready_for_trade_date。 ready_for_trade_date,source_row_count,kept_row_count,filtered_out_row_count,source_terminated_index_count,market_distribution
silver_index_daily_active_pool 默认从本地 PostgreSQL 当前表读取并写 silver Parquet；update job 通过 source_mode=local_replacement 和完整 items 列表替换本地当前表并写 history。 校验所有 code 存在于 silver_index_basic 且未终止。 path,row_count,active_count,source_mode,history_count,added_count,removed_count,updated_count,unchanged_count
raw_tushare_index_daily 分区资产。请求列表来自 silver_index_daily_active_pool；单日运行按 ts_code + trade_date 请求；历史回补按 ts_code + start_date/end_date 请求，先写 staging，再按日期一次性生成完整 raw 分区。 row_count,active_pool_count,page_count,request_count,partition_row_counts,source_method,empty_index_code_count
silver_index_daily 读取 raw 和 active pool；只保留 active pool 内指数； trade_date 转 DATE，change 改为 change_amount。 path,row_count,raw_row_count,active_pool_count,missing_active_count,coverage_rate
gold_market_major_indices 默认从本地 PostgreSQL 当前表读取并 materialize 当前首页主要指数 10 个名单；初始化 job 通过 source_mode=prod_initialization 一次性读取 prod JSON 并写本地当前表/history。当前 update job 只重新 materialize，不接收 items，不写表。 path,row_count,item_count,source_mode,history_count；新增/移除/排序变化摘要留给后续本地维护写表入口实现。
gold_market_major_indices_daily 读取 silver_index_daily、silver_index_basic 和主要指数名单； 输出固定 10 行，字段面向 API。 path,row_count,major_indices_count,missing_code_samples

6. 历史回补设计

禁止低效回补： 不允许按 ts_code × trade_date 请求历史数据。历史回补必须按 ts_code + start_date/end_date 拉时间序列。

正式技术路线

raw_tushare_index_daily 与 silver_index_daily 继续使用 dynamic partitions，服务单日更新、sensor 和 UI 分区观测。 Slice 3.2.2 后，指数资产族使用专属的 cn_a_index_trade_days； 全局 cn_a_trade_days 只保留为全量备份和对照分区集合。 但历史回补不再使用 Dagster 原生 --partition-range。 正式入口仍命名为 index_daily_history_backfill_job，其职责是接收 start_date/end_date/dry_run/force，从 silver_trade_calendar 生成按日期排序的目标交易日列表，并校验这些日期已注册到 cn_a_index_trade_days，再执行受控历史回补。 

index_daily_history_backfill_job(config)
  config:
    start_date: "YYYY-MM-DD"
    end_date: "YYYY-MM-DD"
    dry_run: true | false
    force: true | false

  execution:
    read silver_trade_calendar
    select SSE open days between start_date and end_date
    sort by trade_date
    ensure target dates are registered in cn_a_index_trade_days
    read silver_index_daily_active_pool
    fetch index_daily by ts_code + start_date/end_date + limit/offset
    write staging
    rebuild raw partitions by trade_date
    rebuild silver partitions by trade_date
    emit materialization/check metadata
替换旧实现： 当前 index_daily_history_backfill_job 已替换为普通 Dagster job， 通过 run config 接收 start_date/end_date/dry_run/force。 它不再是 define_asset_job，也不再拥有 PartitionsDefinition； 误用原生 --partition-range 会报 Job has no PartitionsDefinition， 不会进入资产执行。

受控历史回补执行流程

请求范围： Slice 3.2 使用 silver_index_daily_active_pool 作为 index_daily 请求列表。 当前 active pool 约 1,130 个 code；禁止在本链路中默认改回 silver_index_basic 全部有效指数。
请求节流： Tushare index_daily 当前会限制 500次/分钟。正式 helper 必须在逐 code 请求之间加入最小间隔， 并在 materialization metadata 中输出 min_request_interval_seconds、request_count 和 page_count，避免 active pool 单日更新撞限。
stdout 观测： orchestrator/utils/dg_log_helper.py 提供 DgStdoutLogger， 只通过 print(..., flush=True) 写入 Dagster Run 页面 step stdout。 index_daily 拉取和历史回补必须输出 fetch_start、逐 code fetch_progress、staging_split_start、raw_partition_written、 raw_partitions_completed、staging_cleaned、silver_partition_written 和 silver_partitions_completed。stdout 仅用于运行过程观测，不替代 materialization metadata 或 asset check metadata。 
读取 run config -> start_date/end_date/dry_run/force
读取 silver_trade_calendar -> SSE open days
生成 target_trade_dates 并按日期排序
校验 target_trade_dates 已注册到 cn_a_index_trade_days
读取 silver_index_daily_active_pool 指数列表
for ts_code in active_pool_codes:
  调用 index_daily(ts_code, start_date, end_date, fields, limit=8000, offset=0/8000/...)
  将结果写入 staging

DuckDB 读取 staging
按 trade_date 分组
for trade_date in target_dates:
  生成 raw/tushare/index_daily/trade_date=YYYY-MM-DD/part-000.parquet.tmp
  os.replace 到 part-000.parquet

按 active pool 生成 silver 分区

按指数代码修复入口

已新增 index_daily_repair_by_codes_job，用于修复少量指数代码的漏拉或断档。 它是手动维护入口，不挂 sensor/schedule，不维护 active pool，不替代日频更新和历史全量回补。 

index_daily_repair_by_codes_job(config)
  config:
    ts_codes: ["399803.SZ"]
    start_date: "YYYY-MM-DD"
    end_date: "YYYY-MM-DD"
    dry_run: true | false
    force: true | false

  steps:
    validate ts_codes are non-empty, unique, and in silver_index_daily_active_pool
    load SSE open trade dates from silver_trade_calendar
    ensure target dates are registered in cn_a_index_trade_days
    fetch Tushare index_daily by ts_code + start_date/end_date + limit=8000 + offset
    group fetched rows by trade_date
    for each affected trade_date:

      merge fetched rows

不能覆盖整天分区为单 code 数据： raw_tushare_index_daily[trade_date] 和 silver_index_daily[trade_date] 都是按交易日聚合多个指数的分区文件。按 code 修复时必须合并到既有分区， 只能替换指定 ts_code 的行，禁止删除同日其它 active pool 指数行。
  • dry_run=true 只输出目标 code、目标交易日、预计请求数、已有分区状态和影响路径；不访问 Tushare、不写湖。
  • force=false 遇到目标日期范围内已有同 code 行时直接失败；需要替换旧行时必须显式设置 force=true。
  • force=true 才允许替换指定 code 旧行。
  • metadata 必须包含 requested_ts_codes、returned_ts_codes、affected_partition_count、returned_row_count、inserted_row_count、replaced_row_count、still_missing_trade_dates_by_code。
  • 本入口不执行已暂停的 silver_index_daily_active_pool_coverage；coverage 口径后续单独重设。
实现前验证门禁： Slice 3.0.0 已使用临时 /private/tmp Dagster instance 验证本地 Dagster 1.13.6 的 BackfillPolicy.single_run() 行为，没有污染正式 Dagster instance 或正式湖。

Slice 3.0.0 验证结论

  • BackfillPolicy.single_run() 可让一个 run 处理多个分区：临时验证中 dg launch --partition-range 对 3 个测试日期只生成 1 个 run。
  • 多分区运行代码必须使用 context.partition_keys 或 context.partition_key_range 处理分区集合；不能把 context.partition_key 作为多分区主逻辑。
  • range run 会为每个分区写入 materialization 记录，get_materialized_partitions() 与 get_status_by_partition() 都能看到分区状态。
  • blocking check 可执行，但验证中 check 成功记录是 range 级别一次 evaluation，metadata 中包含本次检查覆盖的 partition keys；不是每个分区单独一条 SUCCEEDED check 记录。
  • 如果 job selection 中混入未声明 BackfillPolicy.single_run() 的 partitioned asset，CLI 会拒绝 --partition-range，要求改用 UI/daemon backfill 或让所有 selected assets 统一声明 single-run policy。
  • Slice 3.2 正式验证发现：named dynamic partitions 的 --partition-range 会按 Dagster instance 中 partition key 的注册顺序展开，不一定等同自然日期连续区间。
  • 结论修正：BackfillPolicy.single_run() 可复用“一次 run 处理多个分区”的能力，但不能继续用原生 --partition-range 选择目标日期。正式 history job 必须自己从 silver_trade_calendar 生成有序目标交易日。
  • Slice 3.2 已完成正式替换：raw_tushare_index_daily 与 silver_index_daily 不再声明 BackfillPolicy.single_run()，历史入口由普通 job 负责；误用 --partition-range 会在 CLI 层失败。
  • Slice 3.2.2 已修正分区事实源：股票资产族使用 cn_a_stock_trade_days，指数资产族使用 cn_a_index_trade_days，全局 cn_a_trade_days 只保留为备份和对照。

分页与请求量口径

  • 不人为拆小批次。历史回补默认使用完整 start_date/end_date 区间请求，避免请求次数膨胀。
  • index_daily 单次请求上限按 limit=8000 设计；只有某个 ts_code 在目标区间返回超过 8000 行时，才继续请求 offset=8000/16000/...。
  • 请求数按 active_pool_count × 每个指数分页数 估算，不按 active_pool_count × trade_date_count 估算。
  • 正式代码保留通用 Tushare 默认 limit=6000，但 index_daily 专用路径已使用 limit=8000，并在 metadata 中记录。

staging 目录

data_lake/raw/tushare/index_daily/_staging/run_id=<run_id>/{ts_code}-{page}.parquet

staging 不是正式资产，不参与 asset graph，不被下游读取。它的生命周期只属于本次历史回补 run： run 开始时创建；拉取分页数据时写入 staging；目标 raw 分区全部写入并验证通过后删除； run 失败时短期保留用于排错，metadata 必须记录 staging 路径和失败 code 样本，排错完成后人工清理。 后续重跑必须使用新的 run_id 目录，不复用旧 staging。
