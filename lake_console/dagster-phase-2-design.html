Dagster 第二期方案设计：自动化执行链路与停复牌校验

本文是第二期开发前置设计文档。目标不是扩大业务范围，而是把第一期手动执行的资产链路收敛成可重复、可观测、可回填的 Dagster 流程， 并把 Tushare raw 拉取纳入 Dagster 资产链路，让 daily、suspend_d、trade_cal、stock_basic 都有明确的接入口径。

1. 第二期目标和边界

第一期已经有资产图、分区和 checks，但没有自动化触发，也没有形成“历史 raw 拉齐 + Tushare 续更新”的完整数据来源链路。 第二期的核心是先把旧湖已经拉过的历史数据按 Tushare 字段契约 bootstrap 到新湖 raw，再用 Dagster 接入 Tushare 拉取新数据，由 quote 日频链路执行 raw checks 和 silver 生产，再由下游业务链路在 readiness 通过后生成 gold 和下游 checks。
事项 第二期口径
自动化链路 新增明确命名的 asset jobs：quote_daily_job 负责同一个 trade_date 的 raw 拉取、raw checks、silver 生成和 silver checks；daily_market_breadth_job 只负责 gold 生成和 gold checks。下游触发优先使用 declarative automation 表达 market_breadth_upstream_readiness；若 Slice 2.2.2 小样本验证不通过，必须停下来讨论 asset sensor 后备方案。
历史 bootstrap 新增 Slice 2.0：从旧湖读取已有历史数据，按 Tushare 源站字段契约投影、类型纠偏并写入新湖 raw。它是一次性节省时间和接口成本的历史拉齐步骤，不改变长期数据来源口径。
数据拉取 第二期纳入 TushareResource。历史日期优先由旧湖 bootstrap 拉齐；bootstrap 之后的新日期由 daily 与 suspend_d 按已完成交易日拉取；trade_cal 与 stock_basic 按低频基础数据更新，不混进日频 quote / breadth 链路反复跑。
触发方式 cn_a_trade_day_sensor 负责注册已完成交易日并触发 quote 日频链路；下游业务资产优先使用 declarative automation 等待 market_breadth_upstream_readiness，不默认用 asset sensor 触发生产。asset sensor 只作为验证不通后的后备方案或通知/告警用途。
schedule 可作为第二步接入，用于固定时间触发“检查最近应跑交易日”。但不能绕过 dynamic partitions 注册，也不能直接假设自然日就是交易日。
新增数据集 引入 suspend_d 每日停复牌信息：raw_tushare_suspend_d[trade_date] 与 silver_stock_suspend_daily[trade_date]。
数据来源 新湖 raw 的正式字段口径永远对齐 Tushare 源站。旧湖可以作为历史 bootstrap 来源，但写入新湖前必须纠偏成 Tushare 源站镜像；bootstrap 完成后，新数据由 Tushare API 续更新。
不做内容 不引入 ClickHouse serving、不做 prod release、不迁移更多业务页面资产、不把旧 lake_jobs 或旧运行账本带回来。

2. Dagster 官方依据

本节只记录会影响第二期技术方案的 Dagster 事实依据，不靠猜。

主题 官方依据 对本项目的设计影响
Asset job Dagster Asset jobs：job 是 assets 执行和监控的主要单元，可手动、schedule 或 sensor 触发。 第二期必须定义正式 asset job，不能继续只靠临时脚本或 UI 手点。
Partitioned job Partitioning assets：同分区 assets 的图可以按同一个 partition key 发起运行；官方示例也展示了 partitioned asset job 与 schedule/sensor 的组合。 raw_tushare_stock_daily、raw_tushare_suspend_d、silver_stock_daily、silver_stock_suspend_daily、gold_market_breadth_daily 应共享 cn_a_trade_days。
Dynamic partitions Partitioning assets 中 dynamic partitions 示例使用 sensor 返回 SensorResult，同时包含 RunRequest(partition_key=...) 和 build_add_request(...)。 第二期优先把“注册已完成交易日 + 发起对应分区运行”收敛到 sensor，而不是保留一个纯手动 partition 注册 job。
Backfill Backfilling data：backfill 用于运行不存在或需要更新的历史 partitions；默认覆盖 N 个 partitions 时会发起 N 个独立 runs。 本项目第一版 backfill 采用“一个交易日一个 run”。落后 5 个交易日时，是一次性提交 5 个 partition runs，而不是一个 run 内部拉区间并拆分。
Schedule Dagster Schedules：schedule 用于按固定间隔自动执行 job，默认时区为 UTC，可显式设置 execution_timezone。 本地 A 股每日任务如果上 schedule，必须显式设置 Asia/Shanghai，并且目标 partition 必须来自交易日事实，不是自然日。
Sensor Dagster Sensors：sensor 根据外部状态变化发起 RunRequest，run key 可避免重复运行，cursor 可管理高频状态。 本项目可以用 sensor 观察 silver_trade_calendar、raw 文件是否就绪或 Tushare 同步状态，再按“已完成交易日”发起 asset job。
Asset sensors Dagster Asset sensors：asset sensor 可以监听资产 materialization，并在条件满足时触发下游 job；不满足时可以返回 SkipReason。 第二期不把 asset sensor 作为默认下游生产触发方案；优先留给通知、审计告警或 declarative automation 难以表达的复杂自定义触发。
Declarative Automation Declarative Automation：AutomationCondition.eager() 和 on_missing() 可基于上游资产状态请求下游资产；官方说明上游 partition 未 materialized 或仍在运行时，下游不会被请求。 第二期优先用 declarative automation 表达“上游没好，下游先不请求；上游好了，再触发下游”。Slice 2.2.2 需要重点验证如何把 blocking checks 纳入 readiness 判断。
Asset check 依赖 Asset checks API：additional_deps 可声明 check 依赖的其他资产；blocking=True 且 ERROR 失败时会阻断下游。 silver_stock_daily 的完整性 check 读取 silver_stock_basic 和 silver_stock_suspend_daily，必须用 additional_deps 明确告诉 Dagster。

4. 第二期 Slice 拆分

为避免一次贪多，第二期按三个 slice 推进。Slice 2.0 先用旧湖把历史 raw 拉齐到新湖；Slice 2.1 再让 Tushare 日频续更新和 quote 日频链路跑通；Slice 2.2 最后把低频基础数据更新、下游 readiness gate 和自动化触发收口。

Slice 目标 包含内容 不包含内容 验收结果
Slice 2.0 旧湖历史数据 bootstrap 到新湖 raw。 读取旧湖 daily、suspend_d、trade_cal、stock_basic，按 Tushare 字段契约投影和类型纠偏，写入新湖 raw 目标路径，并执行 raw checks。先按 2026-04 小范围验证，再用 Slice 2.0.6 从 2014-01-01 起做 quote 日频全历史 bootstrap 收口；raw 保持源镜像，silver 才定义标准事实边界。 不调用 Tushare API，不生成新的业务口径，不把旧湖路径写入 Dagster 正式 asset path。 新湖 raw 历史数据字段看起来与 Tushare 直接拉取结果一致；后续 silver、gold 和 checks 不需要知道 raw 来自旧湖 bootstrap 还是 Tushare API。全历史 quote bootstrap 完成后，才能把日常 raw asset 切到 Tushare API。
Slice 2.1 跑通 Tushare 日频 raw 拉取到 quote 日频行情资产的单日链路。 TushareResource、quote_daily_job、raw_tushare_stock_daily 从 daily 拉取、raw_tushare_suspend_d 从 suspend_d 拉取、raw checks、silver checks、单日/全月验证。 不让下游业务 job 主动补上游，不启用长期自动 sensor，不做 ClickHouse/prod release，不改线上 API。 手动触发 quote_daily_job，能从 Tushare 拉取指定已完成交易日的新 raw，并生成 quote 日频 silver/check metadata。
Slice 2.2 补齐低频基础数据更新、下游 readiness gate 和自动化触发。 trade_cal 区间更新、stock_basic 全量快照更新、cn_a_trade_day_sensor、daily_market_breadth_job、readiness gate 条件（优先 declarative automation）、可选 schedule 兜底、latest completed trade date 规则。 不引入更多业务数据集，不做大范围历史回填自动开启。 Dagster UI 能看到 quote_daily_job、breadth job 和自动化条件；上游未就绪时下游不启动 run，上游就绪后下游才被触发。

4.1 Job 拆分原则

原则： 禁止设计一个全局大 daily_foundation_job 来囊括所有日频数据集。 日频资产必须按数据域、资产族和下游依赖边界拆成可并行的小 job，避免下游被无关数据集卡住。
job 类型 边界 说明
quote_daily_job stock_daily、suspend_d 这类 quote 日频行情资产族。 第二期先落这个 job，服务 market breadth 的最小闭环。
basic_update_job stock_basic 这类低频基础快照资产。 不跟 quote 日频 run 反复跑；下游只检查它是否已就绪。
calendar_update_job trade_calendar 这类交易日历资产。 负责维护交易日事实和 dynamic partitions 的依据。
未来其它日频 job 例如 fundflow_daily_job、limit_daily_job、factor_daily_job。 后续单独讨论如何把基础数据集装进若干可并行的合理 job。

下游 readiness 必须从下游视角定义依赖集合。 例如 market_breadth_upstream_readiness 只等待 market breadth 真正需要的 quote 日频资产、stock basic 和交易日历，不等待无关的资金流、涨停、因子等其它资产族。

4.3 开发顺序和前后依赖

第二期内容很多，开发时必须按依赖顺序推进。不能先做下游 gold，也不能先打开自动化触发。 每一步只解决一个边界清晰的问题，完成验证后再进入下一步。

顺序 开发目标 为什么必须在这个位置 完成门禁
0 自动化安全门禁先定：cn_a_trade_day_sensor 默认 STOPPED，下游 readiness gate 不先打开大范围自动生产。 避免一启动 daemon 就扫描交易日、注册大量 partitions、触发大量 quote 日频 runs。 文档和配置口径明确，开发验证阶段只手动触发或小范围 backfill。
1 实现 bootstrap 历史迁移通用引擎：BootstrapDatasetSpec、old_lake_executor、bootstrap/specs/**、统一 raw 写入、metadata 和 raw contract checks。 旧湖进入新湖不是日常生产链路，但后续很多数据集都需要复用这套“读旧湖、投影字段、纠偏类型、写新 raw、跑 raw checks”的迁移工具链。 至少能用一个小样本证明：旧湖读取、字段投影、类型纠偏、新湖 raw 写入、raw checks 全链路可重复；同时确认 bootstrap 不被 sensor、schedule 或 declarative automation 触发。
2 先让 suspend_d 作为 bootstrap 引擎第一个使用者。 suspend_d 字段少但能覆盖 partition bootstrap、suspend_timing 类型漂移、nullable string cast、allow_empty 和 raw checks，适合作为迁移引擎首个验证对象。 单日历史迁移能写入新 raw 并生成 silver；raw/silver checks 通过；不触发 quote/breadth 自动化。
3 做 calendar_update_job 和 basic_update_job 的历史迁移准备：trade_calendar、stock_basic 从旧湖拉齐到新湖 raw/silver。 cn_a_trade_days dynamic partitions 的事实依据来自 silver_trade_calendar；市场宽度完整性 checks 需要 silver_stock_basic。 交易日历和 stock_basic raw/silver checks 通过；能得到 2026-04 已完成交易日集合；未来 open day 不会被立即运行。
4 做 stock_daily 历史迁移和完整性 checks 改造。 先用 suspend_d 跑稳 bootstrap 引擎，再处理数据量更大、重复/冲突/完整性逻辑更多的 stock_daily，避免把引擎问题和数据质量问题搅在一起。 单日和 2026-04 的 raw/silver_stock_daily 跑通；raw/silver blocking checks 通过；验证新口径：raw 不过滤，silver 执行当前上市、上市日后、BJ 开市日和 2014 起始日过滤；完整性 metadata 可解释差异。
5 新增 Slice 2.0.6：用 bootstrap_quote_daily_job 做 quote 日频全历史 bootstrap 收口。 当前 bootstrap_quote_daily_job 仍绑定旧湖 bootstrap 实现。必须趁日常 raw asset 尚未切到 Tushare API 前，把旧湖 quote 日频历史债务尽量迁完；否则进入 2.1 后，同名 job 会跟随 asset 当前实现变成 API 拉取，不再代表旧湖迁移。 已完成：2014-01-02 至 2026-05-15 共 3004 个交易日均有成功 run；新湖 quote raw/silver 分区缺失为 0，完整性 missing/extra 为 0/0。
6 接入 Tushare API 续更新：TushareResource、daily、suspend_d 的新交易日 raw 写入。 先有历史 bootstrap 和 checks，再接 API 续更新，才能证明两种来源写入同一契约、同一 raw path、同一 checks。 任选一个已完成新交易日，Tushare API 写入 raw，和 bootstrap raw 共享字段契约与 checks；source_method=tushare_api 只进入 metadata。
7 小范围启用 cn_a_trade_day_sensor，只注册/触发已完成交易日的 quote_daily_job。 只有历史 bootstrap、Tushare raw 拉取、raw/silver checks 都跑通后，sensor 才有稳定的上游 job 可以触发。 传感器默认 STOPPED；人工小范围验证后确认不会注册或运行未来 open day。
8 实现 market_breadth_upstream_readiness 和 daily_market_breadth_job，并验证下游自动化门禁。 只有上游 job、checks、readiness 都稳定后，自动化才有意义。 readiness 明确包含 materialization + blocking checks；前置条件不满足时不请求下游；满足后只生产 gold_market_breadth_daily。优先验证 declarative automation；若验证不通，停下讨论 asset sensor 后备。
9 全链路验收和收口。 最后再做 2026-04 全月和最近已完成交易日的小范围自动化验证，避免前面问题被批量 run 放大。 落后多个交易日时按一个交易日一个 partition run 补齐；下游只在 readiness 通过后触发；无多余生成物。

4.4 Slice 2.0.6：quote 日频全历史 bootstrap 收口

增加 Slice 2.0.6 的原因是：bootstrap_quote_daily_job 当前选中的仍是走旧湖 bootstrap 的正式 raw/silver assets。 这正好提供了一个窗口，可以把旧湖中已经存在的 quote 日频历史数据迁到新湖。 一旦进入 Slice 2.1，raw_tushare_stock_daily 和 raw_tushare_suspend_d 会改成 Tushare API 日常写入； 同一个 selection job 再运行时会跟随 asset 当前实现变成 API 拉取，不再代表旧湖 bootstrap。 因此必须先把历史迁移债务尽量还完，再切换日常生产实现。

当前已知事实也必须写进门禁：旧湖 raw_tushare/daily 覆盖范围大于 raw_tushare/suspend_d。 所以 2.0.6 的第一步不是直接大批量运行，而是先审计两个旧湖来源的分区覆盖，并用 silver_trade_calendar 的 SSE open day 做交易日门禁。 如果某个 daily 日期没有对应 suspend_d 源文件，不能静默写一个空停复牌文件，因为“源文件缺失”不等于“当日没有停复牌记录”。 如果某个旧湖日期不是 silver_trade_calendar 中的 SSE 开市日，也不能注册为 cn_a_trade_days 或运行 quote 日频 job。

当前最新迁移口径以 dagster-stock-daily-migration.html 为准： quote 历史迁移从 2014-01-01 起，实际首个交易日是 2014-01-02； 旧湖 daily 与 suspend_d 当前共同最新日期为 2026-05-15； 可迁移 SSE 开市日为 3004 个。raw_tushare_stock_daily 保持源镜像，不按股票池过滤； silver_stock_daily 才执行当前上市、上市日后、BJ 自 2021-11-15 起、2014-01-01 起四类过滤。 silver_stock_basic 正式只保留 list_status='L'，当前上市股票数为 5517。

5.2 交易日历超前时的硬门禁

关键口径： silver_trade_calendar 可能提前包含全年交易日历。例如当前真实日期是 2026-05-19， 但日历里可能已经有 2026-12-31 open=true。这些未来 open day 只是“日历事实”，不是“数据已经发生”。 sensor 禁止把未来 open day 注册后立即触发运行。 
sensor 必须区分两件事：

1. 日历中存在的 open day
   silver_trade_calendar 里 open=true 的日期，可能包含未来日期。

2. 已完成交易日 eligible day
   open=true
   且 trade_date <= latest_completed_trade_date
   且该交易日的数据理论上已经可以产生。

只允许 eligible day 进入：
  cn_a_trade_days.build_add_request(...)
  RunRequest(partition_key=...)

禁止：
  把全年 open days 一次性注册后全部运行
  把未来 open day 注册后立即运行
  用自然日 today 直接替代 latest_completed_trade_date

latest_completed_trade_date 的第一版可按保守规则确定：只取小于当前自然日的最近 open day。 如果后续希望在收盘后运行当天数据，必须再引入明确的“数据源已完成更新”判断，例如固定收盘后安全时间、raw 文件就绪检查或 Tushare 同步完成状态。

5.3 为什么不是继续手动 job

第一期曾经有一个 sync_cn_a_trade_day_partitions 手动 job，职责只有注册 2026-04 POC partitions；该临时入口已经退役删除。 第二期如果继续沿用这类手动 POC 链路，就没有解决“资产从上游到下游自动生成”的问题。 因此第二期应把 partition 注册和 partition run 发起连接起来。

5.5 运行顺序

Slice 2.0 的旧湖 bootstrap 是一次性历史拉齐动作，不由 sensor 反复触发。 下面的每日自动化顺序适用于 bootstrap 完成后的新增交易日续更新。 

quote 日频资产更新顺序：
1. 确认 LakeRootResource 可用
2. 计算 latest_completed_trade_date
3. 从 silver_trade_calendar 找到 eligible trade_date
4. sensor 注册 eligible trade_date 到 cn_a_trade_days
5. sensor 发起 quote_daily_job[trade_date]
6. quote_daily_job materialize raw_tushare_stock_daily[trade_date]：调用 Tushare daily 并写 raw
7. quote_daily_job 执行 raw_stock_daily checks；失败则阻断 silver_stock_daily
8. quote_daily_job materialize raw_tushare_suspend_d[trade_date]：调用 Tushare suspend_d 并写 raw
9. quote_daily_job 执行 raw_suspend_d checks；失败则阻断 silver_stock_suspend_daily
10. quote_daily_job materialize silver_stock_daily[trade_date]
11. quote_daily_job materialize silver_stock_suspend_daily[trade_date]
12. quote_daily_job 执行 silver_stock_daily / silver_stock_suspend_daily 相关 checks

下游业务资产生产顺序：
13. readiness gate（优先 declarative automation）评估 market_breadth_upstream_readiness
14. 如果前置条件通过，请求 gold_market_breadth_daily[trade_date] 或发起 daily_market_breadth_job[trade_date]
15. breadth job materialize gold_market_breadth_daily[trade_date]
16. breadth job 执行 gold_market_breadth_daily checks
17. 如果前置条件不通过，不请求下游 run，等待下一次 automation evaluation 或上游 materialization 事件
门禁： raw checks 是 raw 写入后的入厂质检，必须发生在 silver 加工前。 blocking=True 的 raw check 失败时，不允许继续生成 silver，更不允许继续生成 gold。

5.6 下游 job 前置条件

daily_market_breadth_job 的职责只限于 gold_market_breadth_daily 和 gold checks。 它的前置条件必须优先由 declarative automation 在启动下游 run 前判断；不满足时不启动下游 run。 asset sensor 只作为通知、告警或复杂自定义触发的后备方案。

硬门禁： ready 不等于只看 silver_stock_daily[date] 是否 materialized。 LLD 和实现必须专门设计 market_breadth_upstream_readiness 状态：quote 日频链路完成且 raw/silver 层阻断 checks 全部通过，stock_basic 和 trade_calendar 这些低频基础资产也已就绪后，下游才允许触发。 仅靠 “silver materialized” 判断会漏掉质量门禁，不能作为下游生产依据。
前置条件 判断口径 不满足时行为
partition 已注册 trade_date 已存在于 cn_a_trade_days dynamic partitions。 不发起 breadth run，等待 cn_a_trade_day_sensor 注册。
交易日已完成 trade_date <= latest_completed_trade_date，不能用未来 open day 触发下游。 declarative automation 不请求下游；若使用 sensor 后备，则返回 SkipReason。
基础行情 silver 已就绪 silver_stock_daily[trade_date] 已 materialized，且 raw_tushare_stock_daily / silver_stock_daily 相关 blocking checks 全部通过。 等待 quote_daily_job，不主动调用 Tushare。
停复牌 silver 已就绪 silver_stock_suspend_daily[trade_date] 已 materialized，且 raw_tushare_suspend_d / silver_stock_suspend_daily 相关 blocking checks 全部通过；0 行停复牌也必须有空 parquet 和 metadata。 等待 quote_daily_job，不主动补 raw。

第二期目标是通过 Dagster 自动化层表达这种“等待”能力，但这里的等待不是一个已经启动的 run 卡在 RUNNING 状态。 推荐做法是：declarative automation 暂不请求下游资产，等待下一次条件评估； 如果后续 LLD 证明必须使用 asset sensor，则由 sensor 返回 SkipReason，不发起下游 RunRequest。 一旦上游 materialization 和 checks 满足，再发起下游 job。

5.7 一个交易日一个交易日生产

“一个交易日一个交易日生产”不是说操作上只能手动点一天，而是说 Dagster 的最小运行和观测单元是一个 trade_date partition。 如果日线落后 5 个交易日，可以一次发起一个 backfill 或 sensor 批量提交 5 个 RunRequest；但每个 quote_daily run 只负责一个交易日的 raw、checks、silver 链路。 下游 gold run 只在对应交易日的 market breadth 上游前置条件满足后再启动。

6. Tushare 数据源拉取接入方案

本节把 tushare-data 技能理解、本地源文档、现有 request builder、tushareMCP 实测和旧湖/新湖 parquet 字段审计合并成第二期接入口径。 第二期的数据来源分两步：历史日期先从旧湖 bootstrap 到新湖 raw；bootstrap 之后的新日期再由 Tushare API 续更新。

6.1 历史 bootstrap 口径

旧湖已经拉取过大量历史数据，第二期没有必要为了旧日期重新消耗 Tushare 接口和时间。 但旧湖文件不能原样复制：新湖 raw 必须看起来像 Tushare 源站直接返回的数据，所以 bootstrap 必须做字段投影和类型纠偏。 
旧湖 parquet
  ↓  DuckDB 读取、字段投影、类型纠偏
新湖 raw/tushare/.../part-000.parquet
  ↓  raw checks
silver / gold / checks
规则 口径
旧湖角色 只作为历史 bootstrap 来源，用来节约旧日期重复拉取成本；不是 Dagster 长期正式数据路径，也不是新湖 raw 字段契约来源。
字段口径 写入新湖 raw 前，必须按 Tushare 源站字段白名单投影；旧湖多余字段不进入新湖 raw，缺少字段必须失败或显式记录为阻断问题。
类型口径 新湖 raw 保持源站镜像：例如 daily.trade_date 和 suspend_d.trade_date 为 YYYYMMDD 字符串，trade_cal.is_open 为 0/1。
路径口径 正式 asset path 只写新湖路径，例如 raw/tushare/stock_daily/trade_date=YYYY-MM-DD/part-000.parquet；旧湖路径只允许出现在 bootstrap spec / migration entrypoint 参数和文档说明中。
metadata 口径 数据文件本身不增加 source_method 这类系统字段；Dagster materialization metadata 可以记录 source_method=old_lake_bootstrap、行数、字段列表和类型纠偏摘要。旧湖路径只在文档和 bootstrap spec / migration entrypoint 参数中出现，不写入正式资产字段。
下游口径 后续 silver、gold 和 checks 不区分 raw 来自旧湖 bootstrap 还是 Tushare API，只认新湖 raw 字段契约和路径。

6.5 TushareResource 边界

Tushare token 已拍定使用环境变量 TUSHARE_TOKEN，由本机 ~/.bash_profile 提供。 Dagster 侧必须通过 dg.EnvVar("TUSHARE_TOKEN") 注入 TushareResource。 文档只记录变量名和读取方式，不记录 token 值；禁止硬编码，禁止写入 dagster.yaml、.env 或散落 env 文件。 
TushareResource 职责：
1. 通过 dg.EnvVar("TUSHARE_TOKEN") 获取 token，不把 token 写入 dagster.yaml、代码常量、文档或日志。
2. 提供按 api_name 调用的薄封装，例如 call("daily", params, fields)。
3. 记录 request metadata：api_name、params、fields、fetched_at、row_count。
4. 对参数错误、权限错误、空结果、网络错误分层抛错。
5. 不负责 silver/gold 计算，不负责业务口径判断。

TushareResource 不应做：
1. 不在 dg dev 启动时因为 token 缺失让整个 code location 崩掉。
2. 不自行决定交易日。
3. 不把局部 ts_code/suspend_type 查询结果写成正式全市场 raw 分区。
4. 不吞掉异常后写半成品 parquet。

6.6 raw 写入策略

raw asset materialize 的职责从第一期“确认已有 raw 文件”升级为“写入符合 Tushare 契约的 raw parquet、记录 metadata”。 日常生产写入来源是 Tushare API；旧湖 bootstrap 是历史迁移入口，可以写入同一套新湖 raw 路径，但不作为每日 raw asset 的长期分支。 写入必须使用临时文件加原子替换，避免失败时污染正式分区。

6.7 旧湖 / 新湖字段风险

旧湖只能作为历史 bootstrap 和对照来源，不能作为第二期 raw 字段契约来源。 新 raw 必须以 Tushare 源站输出字段为准，尤其是日期和空字符串类型。
数据集 已发现风险 第二期处理
daily 旧湖 daily.trade_date 是 Parquet DATE，Tushare 源站返回 YYYYMMDD 字符串。 新 raw 保持字符串，silver 再标准化为 DATE。第一期新湖 stock_daily 已按此口径纠偏。
suspend_d 旧湖 trade_date 是 DATE；suspend_timing 有分区类型推断差异，空分区可能被推成 INTEGER/NULL。 新 raw 写入时显式投影为字符串；批量审计旧湖时使用 union_by_name=true 或显式 cast。
trade_cal 旧湖 is_open 是 boolean；Tushare 源站返回 0/1。 新 raw 保持 0/1，silver 再标准化为 boolean。
stock_basic 接口会返回未来 list_date；全量快照不能直接当任意历史日期股票池。 raw 保留全状态；silver basic 只保留当前 L；silver_stock_daily 必须继续用 trade_date >= list_date 过滤上市日前日线。

suspend_timing 类型漂移处理

旧湖 suspend_d 的 suspend_timing 类型不可信：部分分区全空时 DuckDB 可能推断为 INTEGER/NULL， 有实际日内停牌时间的分区才会是 VARCHAR。这个问题只允许存在于旧湖读取阶段，不能带进新湖 raw。 

旧湖读取和 bootstrap 写新湖时必须显式投影：

select
  cast(ts_code as varchar) as ts_code,
  strftime(cast(trade_date as date), '%Y%m%d') as trade_date,
  cast(suspend_timing as varchar) as suspend_timing,
  cast(suspend_type as varchar) as suspend_type
from read_parquet(
  '/旧湖/raw_tushare/suspend_d/trade_date=*/part-000.parquet',
  union_by_name=true
)

新湖 raw 契约：
suspend_timing string，可为空

禁止：
1. 直接 cp 旧湖 suspend_d parquet 到新湖 raw
2. 依赖 DuckDB 自动推断 suspend_timing 类型
3. 把 INTEGER/NULL 类型继续传播到新湖 raw
新湖 raw_tushare_suspend_d 写入后必须做 schema check： suspend_timing 只能是字符串列或空值，不能保留旧湖分区推断出来的整数类型。

bootstrap 通用机制

对某一个具体数据集来说，bootstrap 通常只执行一次，用来把旧湖历史数据拉齐到新湖 raw。 但 bootstrap 这套“读旧湖、字段投影、类型纠偏、写新 raw、跑 raw checks”的工具链会被后续大量数据集复用。 因此 bootstrap 入口、spec 和通用执行逻辑长期保留，用作迁移审计记录和后续类似数据集接入的复用基础。 后续每个数据集只应该补充自己的 bootstrap spec，不应该重新发明一套 copy/cast/check 流程，也不应该把 bootstrap 做成日常生产链路。

口径拆清楚：bootstrap 通用引擎只负责“旧湖 → 新湖 raw”的历史迁移；bootstrap migration job 可以在同一次验证里继续 materialize 对应 silver 和 checks， 但 silver 仍由正式 silver asset 生成，不由 bootstrap 引擎单独生成另一套结果。

10.2 suspend_d 修正与完整性观测

日内停牌不能直接当成无日线解释。 只有 suspend_type='S' 且 suspend_timing 为空才是全日停牌。 如果 suspend_timing 不为空，应作为盘中停牌观测上报，不能从 silver daily 标准事实集合中剔除。

13. 已确认口径与开发跟进项

问题 已确认口径 原因
旧湖历史数据是否先 bootstrap 到新湖？ 已确认纳入第二期 Slice 2.0。旧湖只用于节约历史日期重复拉取成本，写入新湖前必须纠偏到 Tushare 源站字段契约。 这样既节约时间，又不破坏新湖 raw “源站镜像”的长期定义。
第二期是否实现 TushareResource 拉取 raw？ 已确认纳入第二期。daily 与 suspend_d 进入 quote_daily_job 的日常更新；trade_cal 与 stock_basic 分别进入 calendar_update_job 和 basic_update_job 的低频更新。 如果不接入 raw 拉取，新交易日没有 raw 数据，自动化链路只能调度但无法真正生产新分区。
下游 job 是否可以主动补上游？ 不可以。daily_market_breadth_job 只负责 gold；上游缺失时等待 quote_daily_job 或上游 backfill，不在下游内部调用 Tushare。 避免多个下游 job 重复拉取、覆盖 raw、污染 metadata 和触发限流。
上游未就绪时如何“等待”？ 等待优先发生在 declarative automation 层：不请求下游资产，等待下一次条件评估。若 Slice 2.2.2 验证证明需要 asset sensor 后备，则 sensor 返回 SkipReason，不发起下游 RunRequest。不是启动一个下游 run 后卡住。 这符合 Dagster 的自动化模型，也更容易观测和重试。
ready 是否只等于 silver materialized？ 不等于。ready 必须表示 market breadth 的上游依赖整体通过质量门禁：silver_stock_daily materialized + stock daily raw/silver blocking checks passed + silver_stock_suspend_daily materialized + suspend raw/silver blocking checks passed + silver_stock_basic ready + silver_trade_calendar ready。 如果只看 materialized，可能绕过质量门禁，导致下游消费不合格数据。
suspend_d 0 行交易日是否写空 parquet？ 要求写空 parquet。 这样可以区分“已确认无停复牌记录”和“raw 未准备好”。
新完整性 check 是否 blocking？ 第二期先 WARN，完成 2026-04 全月验证后再决定是否升级 blocking。 check 是在定义数据边界，不能在业务语义未完全沉淀前直接阻断。
cn_a_trade_day_sensor 是否默认 RUNNING？ 第二期先默认 STOPPED。代码中可以定义 sensor，但本地启动 Dagster daemon 时不让它自动扫描交易日、注册分区并触发 quote_daily_job。 必须先人工验证 latest_completed_trade_date、旧湖 bootstrap、Tushare 拉取、raw/silver checks 和 readiness gate。否则一启动就可能自动注册大量 partitions、触发大量 quote 日频 runs。
cn_a_trade_day_sensor 长期是否应该直接触发 quote？ 短期可以触发 quote_daily_job，且 quote_daily_job 同时包含 stock_daily 和 suspend_d。长期更优雅方向是 sensor 只注册已完成交易日 partition，各资产族通过 declarative automation / on-missing 响应缺失分区。 短期方案简单好验收；长期方案能让交易日发现和数据域生产解耦，但必须先验证 Dagster 当前版本对 dynamic partitions + declarative automation 的组合行为。
Tushare token 配置如何管理？ 使用 TUSHARE_TOKEN 环境变量，由本机 ~/.bash_profile 提供；Dagster 侧通过 dg.EnvVar("TUSHARE_TOKEN") 注入 TushareResource。 token 是敏感配置，禁止硬编码，禁止写入 dagster.yaml、.env、设计文档、metadata 或日志。
