Dagster Phase 3 主要指数数据生产链路设计

本文用于设计“财势乾坤首页市场总览 - 主要指数”模块在本地 Dagster 数据湖中的数据生产链路。 设计方式遵循数据集接入模板：从最终页面/API 反推 gold，再拆 raw / silver、checks、jobs、sensor 和初始化维护方式。

参考： Dagster 数据集资产接入综合模板、 Phase 2 设计、 Phase 2 LLD、 主要指数需求文档、 主要指数实施方案。

1. 目标与边界

目标产出

首页主要指数 10 卡片事实

最终 gold 资产服务 GET /api/v1/wealth/market/major-indices，输出固定 10 个主要指数的点位、涨跌点、涨跌幅和方向。

标准事实

active 指数日线

silver_index_daily 表达经过 active 指数池筛选后的指数日线标准事实，不再把 active 过滤留到 serving 层。

源数据

Tushare 重新拉取

raw_tushare_index_basic 和 raw_tushare_index_daily 均从 Tushare 拉取，不从旧湖 bootstrap。

本阶段不做： 不迁移旧湖 index daily，不接 ClickHouse serving，不发布 prod，不改财富端 API 契约，不改页面 UI，不引入整页聚合接口。

Tushare 源站字段审计结果

审计时间： 2026-05-23。审计依据为本地 Tushare 文档、tushare-data 技能口径、tushareMCP 实测和本地 Tushare SDK 实测。
接口 结论 实现门禁
index_basic 不传 fields 时，实测只返回 ts_code,name,market,publisher,category,base_date,base_point,list_date。 fullname,index_type,weight_rule,desc,exp_date 需要显式请求才返回。 raw_tushare_index_basic 必须显式请求完整 13 字段，不允许依赖默认返回字段。
index_basic 全量分页 实测 fields=完整字段, limit=8000, offset=0 返回 8000 行， offset=8000 继续返回 5538 行，全量 13538 行。 市场值包含 CNI、NH 等当前文档 market 表未列出的值。 全量快照必须分页拉取；第一版不按文档枚举写死 market 白名单，不传 market，以源站返回为准。
index_daily 显式请求字段与文档一致： ts_code,trade_date,open,high,low,close,pre_close,change,pct_chg,vol,amount。 不传 fields 虽能返回完整字段，但字段顺序不同。 raw_tushare_index_daily 必须显式请求完整 11 字段，并固定字段顺序。
index_daily 分页 实测 000001.SH 从 19900101 到 20260521 返回 8644 行， 超过单页上限，需要 limit/offset 分页。 历史回补和日频同步都必须复用分页 helper；任何返回行数等于 limit 的请求都必须继续请求下一页。

6. 本地维护模型

active 池和主要指数名单不使用 YAML 作为长期事实源，避免外部文件和 Dagster asset 出现双事实源。初始化后，本地 PostgreSQL metadata 表是唯一事实源，Dagster update job 是唯一修改入口。

active pool

本地表建议

goldenshare_lake_meta.index_daily_active_pool
goldenshare_lake_meta.index_daily_active_pool_history

记录当前 active 指数列表。被移除的指数直接从当前表删除，变更留在 history。

major indices

本地表建议

goldenshare_lake_meta.market_major_indices
goldenshare_lake_meta.market_major_indices_change_history

记录当前首页主要指数 10 个指数及顺序。变更前后快照留在 history。

维护入口

维护动作 入口 规则
初始化 active 池 index_daily_active_pool_initialize_job Slice 3.0.2 执行。只读远程 prod PostgreSQL ops.index_series_active，过滤 resource='index_daily'，写入本地 index_daily_active_pool 和 history，再 materialize silver_index_daily_active_pool；不得自动同步。初始化阶段 display_name 先留空。
维护 active 池 index_daily_active_pool_update_job 通过 Dagster Launchpad run config 提交当前 active 指数列表，校验后覆盖当前表并写 history。
初始化主要指数名单 market_major_indices_initialize_job Slice 3.0.2 执行。从远程 prod 的 major_indices.cn_a.v1.json 初始化一次，只读取 10 个指数代码并按顺序生成 rank，写入本地 market_major_indices 和 history，再 materialize gold_market_major_indices；不得自动同步。初始化阶段 display_name 先留空。
维护主要指数名单 market_major_indices_update_job 通过 Dagster Launchpad run config 提交当前 10 个指数和 rank，校验后覆盖当前表并写 history。
禁止绕过 Dagster： 不允许直接手改本地 metadata 表后让下游使用。所有变更必须通过 Dagster update job 写表、写 history、materialize asset、跑 checks。

10. 触发与自动化策略

触发器 职责 安全口径
index_basic_sensor 以 cn_a_trade_days 已注册 partition key 作为业务日期来源。 对候选 trade_date，若 silver_index_basic 最近一次成功 materialization 没有声明 ready_for_trade_date >= trade_date， 或对应 blocking checks 未全部通过， 则触发 index_basic_update_job。 默认 STOPPED；正式启用前先 preview；不触发 index daily，不自动维护 active pool。
index_daily_sensor 交易日分区已注册、silver_index_basic 和 active pool ready，且 Tushare index daily 源站可用后，触发 index_daily_update_job[trade_date]。 不触发 basic 或 active pool；上游未 ready 只 skip。
market_major_indices_automation_sensor 当 gold_market_major_indices_daily[trade_date] 缺失且直接上游 checks 通过时，触发 gold 生成。 默认 STOPPED；避免一次性吞历史缺口。
full snapshot freshness 口径： silver_index_basic 本身不分区，不能天然知道“哪一天 ready”。因此 index_basic_update_job materialize silver_index_basic 时，必须在 metadata 中记录 ready_for_trade_date。 sensor 用 cn_a_trade_days 的 partition key 作为要生产的交易日，再用 ready_for_trade_date 和 blocking checks 判断该 full snapshot 是否能服务这个交易日。

active pool 和主要指数名单属于人工维护资产，默认不需要 sensor 自动修改；维护动作通过手动 Dagster update job 发起。

11. Tushare 拉取与性能门禁

性能风险： Tushare index_daily 是按 ts_code 拉时间序列的接口，不是按交易日拉全市场截面的接口。 历史回补禁止按“有效指数数 × 交易日数”逐日逐指数请求，否则请求量会爆炸。

日常更新

日频同步只处理一个已注册交易日，因此可以按有效指数逐个请求当天数据。它属于常规生产链路，由 sensor / job 触发。 

index_daily_update_job[trade_date]
  -> 读取 silver_index_basic 中有效 ts_code
  -> 对每个 ts_code 调用 index_daily(ts_code, trade_date=YYYYMMDD)
  -> 合并写 raw_tushare_index_daily[trade_date]
  -> silver_index_daily[trade_date] 再按 active pool 过滤

历史补齐

历史补齐必须进入 Dagster，但不能混入日常生产链路。建议单独定义 index_daily_history_backfill_job，只允许手动触发，不被 sensor、schedule 或 declarative automation 调用。 

index_daily_history_backfill_job[start_date, end_date]
  -> 读取 silver_index_basic 中有效 ts_code
  -> 对每个 ts_code 调用 index_daily(ts_code, start_date, end_date)
  -> 分页拉取完整时间序列
  -> 写入本次 backfill 专用 staging 目录
  -> DuckDB 读取 staging
  -> 按 trade_date 分组
  -> 每个 trade_date 只生成一次完整 raw 分区 part-000.parquet
  -> silver_index_daily[trade_date] 再按 active pool 过滤
文件写入原则： 历史回补不能“每拉一个 ts_code 就覆盖一次目标日期 parquet”。Parquet 分区文件必须按目标交易日一次性重建： 先写 .tmp，再用 os.replace 原子替换 part-000.parquet。

历史补齐的请求和写入模型：

  • 请求次数按 有效指数数量 × 每个指数分页数 计算，不按 有效指数数量 × 交易日数量 计算。
  • 最终写文件次数按目标交易日数计算，每个 trade_date 分区只写一次完整 part-000.parquet。
  • staging 数据只服务本次回补 run，不作为正式 raw/silver/gold 资产，不允许下游直接读取；成功后删除，失败时短期保留用于排错，不承诺长期存在。
  • 历史回补 metadata 必须记录 source_method=tushare_api_range_backfill、请求 code 数、分页数、staging 路径、目标交易日数、写入行数和失败 code 样本。
  • 日频同步 metadata 使用 source_method=tushare_api_daily，与历史回补区分。
  • 全量历史开始前，必须先输出有效指数数量、交易日数量、预计请求数、预计耗时和 Tushare 配额影响。

14. 已拍板项

  1. Phase 3 从“财势乾坤首页市场总览 - 主要指数”下游 API 反推资产图。

  5. silver_index_daily_active_pool 作为 silver asset，决定哪些指数进入 silver_index_daily。
  6. silver_index_daily_active_pool 由 prod PostgreSQL ops.index_series_active 中 resource='index_daily' 一次性初始化；初始化后只本地维护，不再与 prod 同步。
  7. gold_market_major_indices 作为 gold 业务名单 asset，决定首页主要指数展示哪 10 个和顺序。
  8. gold_market_major_indices 由 prod major_indices.cn_a.v1.json 一次性初始化；初始化后只本地维护，不再与 prod 同步。
  9. active pool 和主要指数名单不使用 YAML 作为长期事实源，避免 YAML 与 Dagster asset 双事实源。
  10. active pool 和主要指数名单使用本地 PostgreSQL metadata 表作为唯一事实源，所有人工变更必须通过 Dagster update job。
  11. 下游对上游是 deps，不是 selection；下游 job 不主动补上游。
  12. index_basic 和 index_daily 请求都必须显式指定完整 fields，禁止依赖 Tushare 默认返回字段。
  13. index_daily 历史回补按 ts_code + start_date/end_date 拉区间，不按 ts_code × trade_date 逐日请求。
  14. index_daily 历史回补先写 staging，再按 trade_date 一次性生成完整 raw 分区文件；禁止每拉一个 code 就重复覆盖目标 parquet。

15. 待评审风险点

  • 历史 index daily 全量补齐的请求量可能较大，LLD 前必须先测算有效指数数量、每个指数分页数、目标交易日数量、预计耗时和配额影响。
  • 一次性读取 prod DB / prod JSON 需要明确只读连接方式、权限、字段白名单和审计记录。
  • 本地 PostgreSQL metadata 表结构需要在 LLD 中细化，包括当前表、change history、Dagster run id 和回滚方式。
  • Tushare index_daily 的真实 ready 时间和空结果行为还需要结合日频 sensor 小样本验证；分页行为已完成源站实测。
  • 历史回补 staging 只作为临时运行目录，成功后删除；失败恢复方式、重复运行覆盖策略需要在 LLD 中细化。
