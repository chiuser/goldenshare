Dagster Phase 3 主要指数数据生产链路设计

本文用于设计“财势乾坤首页市场总览 - 主要指数”模块在本地 Dagster 数据湖中的数据生产链路。 设计方式遵循数据集接入模板：从最终页面/API 反推 gold，再拆 raw / silver、checks、jobs、sensor 和初始化维护方式。

参考： Dagster 数据集资产接入综合模板、 Phase 2 设计、 Phase 2 LLD、 主要指数需求文档、 主要指数实施方案。

1. 目标与边界

目标产出

首页主要指数 10 卡片事实

最终 gold 资产服务 GET /api/v1/wealth/market/major-indices，输出固定 10 个主要指数的点位、涨跌点、涨跌幅和方向。

标准事实

active 指数日线

silver_index_daily 表达经过 active 指数池筛选后的指数日线标准事实，不再把 active 过滤留到 serving 层。

源数据

Tushare 重新拉取

raw_tushare_index_basic 和 raw_tushare_index_daily 均从 Tushare 拉取，不从旧湖 bootstrap。

本阶段不做： 不迁移旧湖 index daily，不接 ClickHouse serving，不发布 prod，不改财富端 API 契约，不改页面 UI，不引入整页聚合接口。

图中要点：

  • raw_tushare_index_daily 依赖 silver_index_daily_active_pool，因为 Tushare index_daily 必须按 ts_code 逐个请求，第一版只拉 active 池内指数。
  • silver_index_daily 继续依赖 active 池，active 池决定哪些指数进入标准事实层。
  • silver_index_daily_active_pool 与 gold_market_major_indices 都来自本地 metadata 当前表；它们与 silver_index_basic 的一致性通过 cross-asset checks 校验，不伪造直接数据血缘。
  • gold_market_major_indices 是首页主要指数名单资产，决定展示哪 10 个指数和顺序；它不依赖 silver_index_daily。
  • gold_market_major_indices_daily 是最终页面/API 可消费的业务结果资产。

审计时间： 2026-05-23 首次审计，2026-05-24 Slice 3.1 开发前复核。审计依据为本地 Tushare 文档、tushare-data 技能口径、tushareMCP 实测和本地 Tushare SDK 实测。
接口 结论 实现门禁
index_basic 不传 fields 时，实测只返回 ts_code,name,market,publisher,category,base_date,base_point,list_date。 fullname,index_type,weight_rule,desc,exp_date 需要显式请求才返回。 raw_tushare_index_basic 必须显式请求完整 13 字段，不允许依赖默认返回字段。

6. 本地维护模型

active 池和主要指数名单不使用 YAML 作为长期事实源，避免外部文件和 Dagster asset 出现双事实源。初始化后，本地 PostgreSQL metadata 表是唯一事实源。Slice 3.2.1 已为 active 池补齐完整列表替换维护入口；主要指数名单的本地维护写表入口仍未实现，后续必须单独设计。

active pool

本地表建议

goldenshare_lake_meta.index_daily_active_pool
goldenshare_lake_meta.index_daily_active_pool_history

记录当前 active 指数列表。被移除的指数直接从当前表删除，变更留在 history。

major indices

本地表建议

goldenshare_lake_meta.market_major_indices
goldenshare_lake_meta.market_major_indices_change_history

记录当前首页主要指数 10 个指数及顺序。变更前后快照留在 history。

维护入口

维护动作 入口 规则
初始化 active 池 index_daily_active_pool_initialize_job Slice 3.0.2 执行。只读远程 prod PostgreSQL ops.index_series_active，过滤 resource='index_daily'，写入本地 index_daily_active_pool 和 history，再 materialize silver_index_daily_active_pool；不得自动同步。初始化阶段 display_name 先留空。
维护 active 池 index_daily_active_pool_update_job Slice 3.2.1 执行。通过 source_mode=local_replacement 和完整 items 列表替换本地当前表，写入新增/删除/更新 history，再 materialize silver_index_daily_active_pool 并运行 checks。它是完整替换，不是增量更新。
初始化主要指数名单 market_major_indices_initialize_job Slice 3.0.2 执行。从远程 prod 的 major_indices.cn_a.v1.json 初始化一次，只读取 10 个指数代码并按顺序生成 rank，写入本地 market_major_indices 和 history，再 materialize gold_market_major_indices；不得自动同步。初始化阶段 display_name 先留空。
维护主要指数名单 market_major_indices_update_job 当前代码只读取本地 market_major_indices 当前表，重新生成 gold_market_major_indices 并运行 checks；不接收 items run config，不写当前表，不写 history。真正的本地维护写表入口是后续任务。
禁止绕过 Dagster： active 池不允许直接手改本地 metadata 表后让下游使用；必须通过 index_daily_active_pool_update_job 的完整替换配置写表、写 history、materialize asset、跑 checks。主要指数名单在正式维护写表入口实现前仍不得手改表后让下游使用。
Launchpad 口径： Dagster 原生 Launchpad 不会自动把当前 active pool 的 1130 行预填到配置输入框。完整替换时，items 需要由用户准备并粘贴；本 Slice 不提供导出 YAML 模板工具。

10. 触发与自动化策略

本节是后续 Slice 3.4 规划。当前代码尚未实现 Phase 3 指数类 sensors，也尚未实现 source_readiness/tushare/index_daily.py；现有 Phase 2 sensors 不承担主要指数链路。

Slice 3.2.2 前置门禁： 当前 cn_a_trade_days 曾被股票链路和指数链路共用，但两个资产族的历史范围不同。 股票日线当前从 2014 年开始，指数日线需要更早历史。继续共用同一个 dynamic partition 集合，会让指数早期日期污染股票 suspend_d、stock_daily、market_breadth 的 sensor 和待补判断。 因此指数历史全量回填前，必须先完成资产族交易日分区拆分；原 cn_a_trade_days 保留为全量备份分区集合，不再作为正式生产资产的 partitions 定义。
分区定义 资产族 起点口径 负责资产 / 触发器
cn_a_trade_days 全量备份 / 对照分区集合 扩展后的 silver_trade_calendar 中全部 SSE open day，起点随交易日历扩到 19900101，实际首个 open day 为 1990-12-19。 cn_a_trade_day_sensor 只负责注册该备份集合，不触发任何数据更新；正式生产资产不再依赖它。
cn_a_stock_trade_days 股票行情资产族 2014-01-01 起且不晚于当前自然日的 SSE open day，实际首个交易日为 2014-01-02。 raw_tushare_stock_daily、silver_stock_daily、raw_tushare_suspend_d、silver_stock_suspend_daily、gold_market_breadth_daily 及股票相关 sensors。
cn_a_index_trade_days 指数行情资产族 以扩展后的 silver_trade_calendar 为事实源，支持 1990-12-19 起且不晚于当前自然日的指数交易日。 raw_tushare_index_daily、silver_index_daily、gold_market_major_indices_daily、index_basic freshness 判断、指数相关 sensors 和 index_daily_history_backfill_job。
原则： silver_trade_calendar 是完整交易日事实表；dynamic partitions 是“某个资产族允许 Dagster 管理和生产的 key 集合”。 每个日频资产族必须有自己的 partition definition，不得默认共用一个全局 cn_a_trade_days；全局 cn_a_trade_days 只做备份、排障和对照。
触发器 职责 安全口径
index_basic_sensor 以 cn_a_index_trade_days 已注册 partition key 作为业务日期来源。 对候选 trade_date，若 silver_index_basic 最近一次成功 materialization 没有声明 ready_for_trade_date >= trade_date， 或对应 blocking checks 未全部通过， 则触发 index_basic_update_job。 默认 STOPPED；正式启用前先 preview；不触发 index daily，不自动维护 active pool。
index_daily_sensor 交易日分区已注册、silver_index_basic 和 active pool ready，且 Tushare index daily 源站可用后，触发 index_daily_update_job[trade_date]。 不触发 basic 或 active pool；上游未 ready 只 skip。
market_major_indices_automation_sensor 当 gold_market_major_indices_daily[trade_date] 缺失且直接上游 checks 通过时，触发 gold 生成。 默认 STOPPED；避免一次性吞历史缺口。
full snapshot freshness 口径： silver_index_basic 本身不分区，不能天然知道“哪一天 ready”。因此 index_basic_update_job materialize silver_index_basic 时，必须在 metadata 中记录 ready_for_trade_date。 sensor 用 cn_a_index_trade_days 的 partition key 作为要生产的交易日，再用 ready_for_trade_date 和 blocking checks 判断该 full snapshot 是否能服务这个交易日。

active pool 和主要指数名单属于人工维护资产，默认不需要 sensor 自动修改。active pool 已支持通过 index_daily_active_pool_update_job 完整替换维护；主要指数名单的正式人工维护写表入口后续单独设计。

11. Tushare 拉取与性能门禁

性能风险： Tushare index_daily 是按 ts_code 拉时间序列的接口，不是按交易日拉全市场截面的接口。 历史回补禁止按“有效指数数 × 交易日数”逐日逐指数请求，否则请求量会爆炸。
Slice 3.2 请求范围纠偏： 日常更新和历史回补都以 silver_index_daily_active_pool 为请求列表。当前 active pool 约 1,130 个 code； 若按 silver_index_basic 全部有效指数拉取，会达到约 12,598 个 code，日频请求量不可接受。 后续实现不得退回全量有效指数作为默认请求范围。
Tushare 频率限制： 正式单日验证时已触发 index_daily 的 500次/分钟 限制。 因此 index_daily 拉取 helper 必须内置节流，metadata 必须记录最小请求间隔和实际请求数；禁止无节流循环打接口。

日常更新

日频同步只处理一个已注册交易日，按 active 池指数逐个请求当天数据。它属于常规生产链路，由 sensor / job 触发。 

index_daily_update_job[trade_date]
  -> 读取 silver_index_daily_active_pool 中 ts_code
  -> 对每个 ts_code 调用 index_daily(ts_code, trade_date=YYYYMMDD)
  -> 合并写 raw_tushare_index_daily[trade_date]
  -> silver_index_daily[trade_date] 校验并保留 active pool 内指数

历史补齐

历史补齐必须进入 Dagster，但不能混入日常生产链路。正式入口仍命名为 index_daily_history_backfill_job，但它不能再使用 Dagster 原生 --partition-range。该 job 必须通过 run config 显式接收 start_date/end_date/dry_run/force，再从 silver_trade_calendar 读取 SSE 开市日，按 trade_date 自然顺序生成目标交易日列表，并校验这些日期已经注册到 cn_a_index_trade_days。 

index_daily_history_backfill_job(config: start_date, end_date, dry_run, force)
  -> 读取 silver_trade_calendar 中 SSE is_open=true 的交易日
  -> 截取 start_date/end_date 内的目标交易日并按日期排序
  -> 校验目标交易日已注册到 cn_a_index_trade_days
  -> 读取 silver_index_daily_active_pool 中 ts_code
  -> 对每个 ts_code 调用 index_daily(ts_code, start_date, end_date, limit=8000, offset=...)
  -> 分页拉取完整时间序列，并只保留目标交易日
  -> 写入本次 backfill 专用 staging 目录
  -> DuckDB 读取 staging
  -> 按 trade_date 分组
  -> 每个 trade_date 只生成一次完整 raw 分区 part-000.parquet
  -> silver_index_daily[trade_date] 校验并保留 active pool 内指数
原生 range 禁用： named dynamic partitions 的原生 --partition-range 会按 partition key 的注册顺序展开，不保证等同自然日期顺序。 因此历史回补禁止使用 dg launch --partition-range 作为正式入口。 当前 index_daily_history_backfill_job 已改为普通 Dagster job，不再拥有 PartitionsDefinition；误用 --partition-range 会直接失败，不会进入资产执行。
文件写入原则： 历史回补不能“每拉一个 ts_code 就覆盖一次目标日期 parquet”。Parquet 分区文件必须按目标交易日一次性重建： 先写 .tmp，再用 os.replace 原子替换 part-000.parquet。

历史补齐的请求和写入模型：

  • 请求次数按 active pool 数量 × 每个指数分页数 计算，不按 active pool 数量 × 交易日数量 计算。
  • index_daily 单次请求上限按 limit=8000 设计；只有单个指数在目标区间返回超过 8000 行时，才通过 offset=8000/16000/... 继续分页。
  • 不再人为拆小批次。历史回补默认用完整 start_date/end_date 区间请求，分页只由 Tushare limit/offset 决定，避免请求次数膨胀。
  • 最终写文件次数按目标交易日数计算，每个 trade_date 分区只写一次完整 part-000.parquet。
  • staging 数据只服务本次回补 run，不作为正式 raw/silver/gold 资产，不允许下游直接读取；成功后删除，失败时短期保留用于排错，不承诺长期存在。
  • 历史回补 metadata 必须记录 source_method=tushare_api、请求 code 数、分页数、staging 路径、目标交易日数、写入行数和失败 code 样本；是否为历史回补由 run config 中的 start_date/end_date 与目标交易日列表判断。
  • 日频同步 metadata 同样使用 source_method=tushare_api，并通过 use_trade_date=true 表明它是单日请求。
  • dynamic partition 的 range 展开不再作为历史回补依据；正式历史回补只能使用 silver_trade_calendar 生成的有序目标交易日列表。
  • Slice 3.2.2 已拆分资产族分区。执行指数全量历史回补前，仍必须确认目标日期已注册到 cn_a_index_trade_days。
  • Slice 3.2 已完成受控历史回补入口：dry_run=true 只输出计划，不访问 Tushare、不写湖；force=false 遇到既有 raw/silver 文件会失败；只有 force=true 才允许原子替换。
  • 全量历史开始前，必须先输出 active pool 数量、交易日数量、预计请求数、预计耗时和 Tushare 配额影响。
