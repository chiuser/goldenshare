# 大火箭

## 记录目的

本文记录本地数据湖引入 Dagster 的早期讨论结论。

当前阶段不是正式方案设计，也不是实施清单。重点是先把方向、边界和仓库归属想清楚，避免过早开工导致架构走偏。

## 已确认结论

1. Dagster 不需要把 `dagster-io/dagster` 源码下载到工程里运行。
2. 正常使用方式是把 Dagster 作为 Python 依赖安装，然后在自己的工程里写 assets、jobs、resources、schedules、checks 等编排代码。
3. Dagster 适合作为本地数据湖控制面，负责资产、依赖、分区、检查、调度、回填、日志和运行状态。
4. Goldenshare 仍然专注业务规则、数据口径、同步逻辑、DuckDB 计算、发布规则和本地 lake 文件事实。
5. 当前讨论范围仅限本地数据湖，不替换生产 Ops 运营后台，也不接生产 TaskRun、scheduler、worker 或状态表。

## 仓库归属结论

阶段性决定：Dagster 先放在 `goldenshare` 仓库内，归属于 `lake_console` 本地工程，而不是立即新建独立仓库。

原因：

1. 当前还处于学习和讨论阶段，Codex 需要持续读取 `goldenshare` 现有上下文、文档、边界规则和 `lake_console` 代码。
2. 如果立即分仓，会导致新的 Codex 项目缺少当前仓库上下文，讨论和实现都会变得费劲。
3. `lake_console` 本来就是本地数据湖独立工程，适合作为 Dagster 本地控制面的承载位置。
4. 现阶段更重要的是上下文连续性，而不是过早追求仓库物理隔离。

推荐理解：

```text
物理上同仓：goldenshare/lake_console
逻辑上独立：本地 Dagster 控制面，不进入生产主系统
```

未来如果 Dagster 控制面稳定、边界清晰、可以作为独立产品存在，再评估是否拆成独立仓库。

## 隔离原则

即使放在同仓，也必须保持运行和边界隔离：

1. 依赖隔离：Dagster 可以使用独立虚拟环境或独立依赖入口。
2. 运行隔离：使用独立 `DAGSTER_HOME`，不混入生产运行目录。
3. 位置隔离：Dagster 运行目录和本地 PostgreSQL 必须安装并存放在本机固定磁盘，不放在移动 SSD 上。
4. 数据库隔离：本地 PostgreSQL 中区分 Dagster 内部状态库和业务 metadata 库。
5. 系统隔离：不接生产 `src/ops`、TaskRun、scheduler、worker 或状态快照。
6. 部署隔离：生产部署脚本不启动 Dagster，不把 Dagster 纳入生产服务。
7. 环境隔离：本地 lake 仍然通过显式配置指定，不允许隐式写入仓库目录、用户 home 或系统临时目录。

## 本机磁盘与移动 SSD 边界

阶段性决定：Dagster 和本地 PostgreSQL 都应安装、运行并持久化在本机固定磁盘上，而不是移动 SSD 上。

原因：

1. Dagster 保存 run、event、schedule、asset materialization 等控制面状态，运行时对这些状态有持续读写。
2. PostgreSQL 承载 Dagster 管理状态和本地业务 metadata，属于事务型状态，不适合放在可能被拔掉的移动盘上。
3. 如果移动 SSD 被随意拔掉，最多应该影响 Parquet Lake 文件访问，不应该破坏 Dagster 或 PostgreSQL 的管理状态。
4. 移动 SSD 的定位是承载本地数据湖资产文件，不承载控制面数据库和服务运行态。

推荐理解：

```text
本机固定磁盘
  Dagster 代码依赖 / DAGSTER_HOME / 本地 PostgreSQL / ClickHouse 服务数据

移动 SSD
  Parquet Lake：raw / silver / gold / manifest / research / derived 等文件资产
```

后续设计必须显式处理移动 SSD 不可用的情况：Dagster 和 PostgreSQL 可以正常启动，但相关 lake assets 显示为不可访问、不可执行或需要重新挂载，而不是让控制面自身崩坏。

## 当前倾向的职责分工

```text
本地 Parquet 数据湖
  存 raw / silver / gold 文件

DuckDB
  负责从 raw 计算 silver / gold

Dagster
  负责定义资产、依赖、分区、检查、调度、回填、日志和状态

本地 PostgreSQL
  一部分承载 Dagster run/event/schedule 等管理状态
  一部分承载业务 metadata，如数据源、schema、发布包、同步记录

本地 ClickHouse
  存 serving 表，供本地 API 调试

生产 PostgreSQL
  接收轻量发布结果

未来生产 ClickHouse
  替代部分生产 PostgreSQL 查询
```

## 暂不决定的事情

以下问题后续继续讨论，不在本文定案：

1. Dagster 目录最终命名为 `dagster`、`orchestrator` 还是其他名称。
2. Dagster 是否使用独立 `pyproject.toml`。
3. Dagster metadata 和业务 metadata 是分库、分 schema，还是同库不同 schema。
4. 哪些现有 `lake_console` 命令先被包装为 Dagster asset。
5. Dagster asset partition 粒度如何设计，尤其是 `stk_mins` 这类大规模数据集。
6. 本地 ClickHouse serving 表与发布包的第一版边界。
