1. 设计硬边界

本 LLD 的底线： 第二期不是扩大业务资产范围，也不是重写第一期。第二期只围绕四件事展开： 旧湖历史数据按 Tushare raw 契约 bootstrap 到新湖；TushareResource 拉取新增 raw；股票行情日频链路自动化；market breadth 下游只在上游质量门禁通过后生产。
边界 LLD 口径
数据湖路径 正式 asset path 只允许 data_lake/raw、data_lake/silver、data_lake/gold。旧湖只作为 bootstrap 输入，不出现在新 Dagster asset 的正式 path 中。
raw 定义 新湖 raw 是 Tushare 源站镜像。旧湖 bootstrap 写入 raw 前必须投影字段、纠偏类型，写出来的 parquet 要看起来像 Tushare API 直接返回。
job 拆分 禁止设计一个全局 daily_foundation_job。第二期按 calendar、basic、quote、breadth 拆 job，避免下游被无关资产卡住。
下游行为 daily_market_breadth_job 永远不主动补上游、不调用 Tushare、不修 raw。上游未就绪时，不启动下游 run，等待 declarative automation 下一次评估。
ready 定义 ready 不等于 silver materialized。ready 必须包含 materialization + raw/silver blocking checks passed + 必要共享基础资产就绪。
自动化安全 cn_a_trade_day_sensor 第二期默认 STOPPED，人工小范围验证后再考虑打开。
配置新增 新增 Tushare token、旧湖 root、自动化开关等配置前，必须先做配置项审计。禁止新增临时 env 文件或散落配置。

6. Bootstrap 低层设计

Bootstrap 是历史迁移工具链，不是长期生产链路。对某一个具体数据集来说，bootstrap 通常只执行一次：把旧湖历史数据按 Tushare raw 契约写入新湖 raw。 但这套“读旧湖、字段投影、类型纠偏、写新 raw、跑 raw checks”的通用机制后续会被很多数据集复用，所以它不能退化成散落的手工 cp 命令。 Bootstrap 入口、spec 和通用执行逻辑长期保留，用作迁移审计记录和后续类似数据集接入的复用基础。

边界要拆开：bootstrap 通用引擎只负责把旧湖历史数据写成符合 Tushare 契约的新湖 raw。 bootstrap migration job 可以为了验收继续选择对应 silver assets 和 checks，但 silver 仍由正式 silver asset 生成，不由 bootstrap 引擎生成一套旁路结果。

硬边界： bootstrap 不参与每日自动化，不被 cn_a_trade_day_sensor、schedule 或 declarative automation 触发。 具体数据集 bootstrap 完成并验收后，日常更新只走 TushareResource 和对应的 calendar/basic/quote jobs。

6.3 suspend_timing 类型漂移固定处理

旧湖里不同交易日的 suspend_d parquet 文件不一定有完全一致的字段类型。 最典型的是 suspend_timing：有的日期有类似 14:51-14:57 的日内停牌时间，DuckDB 会把它看成字符串； 有的日期这一列全是空，DuckDB 可能把它推断成 INTEGER/NULL。这就是“类型漂移”。

如果 bootstrap 批量读取这些旧湖分区，不做处理就可能出现两类问题： 一类是直接读取失败；另一类更危险，是 DuckDB 自动推断出一个不符合 Tushare 源站契约的类型，然后悄悄写进新湖 raw。 所以这里必须先按字段名合并，再强制 cast 成新湖 raw 要求的类型。 

select
  cast(ts_code as varchar) as ts_code,
  strftime(cast(trade_date as date), '%Y%m%d') as trade_date,
  cast(suspend_timing as varchar) as suspend_timing,
  cast(suspend_type as varchar) as suspend_type
from read_parquet(
  old_path,
  hive_partitioning=false,
  union_by_name=true
)
union_by_name=true 的意思是：多个 parquet 文件合并时按字段名对齐，不按字段位置瞎拼。 cast(suspend_timing as varchar) 的意思是：不管旧湖里 DuckDB 把它猜成什么，新湖 raw 都统一写成 nullable string。 写完后还要做 raw schema check，如果新湖 raw 里的 suspend_timing 不是字符串列，直接失败，不能继续生成 silver。

6.5 第一个使用者：suspend_d

suspend_d 作为 bootstrap 引擎的第一个使用者。它字段少、业务逻辑相对单纯，但能覆盖 bootstrap 最关键的能力： 按 trade_date 分区迁移、旧湖字段类型纠偏、nullable string cast、允许 0 行结果、写入新 raw 后复用 raw checks。

不建议第一个使用者选择 stock_daily。它数据量更大，重复行、冲突行、完整性 WARN 和业务检查更多， 容易把 bootstrap 引擎问题和数据质量问题搅在一起。先用 suspend_d 把迁移引擎跑稳，再扩到 calendar/basic/stock_daily。

8. Asset 实现设计

8.1 raw asset 日常职责与 bootstrap 边界

第二期的长期生产口径是：raw asset 日常更新由 TushareResource 写入。 bootstrap 只是历史迁移入口，它可以写入同一套新湖 raw 路径，并记录 source_method=old_lake_bootstrap 的 materialization metadata； 但不应该把 old_lake_bootstrap 做成每日 raw asset 的长期分支。 

long-term raw asset execution:
  use TushareResource
  write Tushare source-mirror raw parquet
  emit MaterializeResult metadata:
    source_method = "tushare_api"

one-time bootstrap execution:
  use BootstrapDatasetSpec + old_lake_executor
  write the same raw parquet contract
  emit migration metadata:
    source_method = "old_lake_bootstrap"

shared contract:
  same asset key
  same physical path
  same raw fields
  same raw checks
  same downstream silver/gold code
source_method 是运行 metadata，不是业务字段，也不是下游判断逻辑。 任何 sensor、schedule、declarative automation 都不能选择或触发 old_lake_bootstrap。

  partitions_def=cn_a_trade_days,

def raw_tushare_suspend_d(context, lake_root, duckdb, tushare):

    source_method="tushare_api",
    data_contract="source_mirror",
  })

  keys_to_add = first 2 eligible_open_days not in existing_keys
  return SensorResult(
    dynamic_partitions_requests=[
      cn_a_trade_days.build_add_request(keys_to_add)
    ]
  )

suspend_d_sensor:
  pending = registered partitions not materialized by both raw_tushare_suspend_d and silver_stock_suspend_daily
  request suspend_update_job[trade_date] for first 2 pending partitions

stock_basic_sensor:
  target_trade_date = latest registered partition
  request basic_update_job if stock_basic full snapshot is not fresh or blocking checks are not green

stock_daily_sensor:
  pending = registered partitions not materialized by both raw_tushare_stock_daily and silver_stock_daily
  for first 2 pending partitions:

    require suspend_d[trade_date] materialized + blocking checks passed
    require Tushare daily(trade_date) source readiness

11.1a 设计解释：partition 注册不是同步调用其它 sensor

当前实现已经把“交易日发现”和“资产族生产”拆开。Dagster sensor 是轮询机制，不是消息队列推送； 因此 partition 注册后，不是立刻同步调用其它 sensor，而是等待各资产族 sensor 在下一次 tick 中读取正式 instance 状态并判断是否需要触发。 

target sensors:
  cn_a_trade_day_sensor:
    input:
      silver_trade_calendar
      current time
    output:
      cn_a_trade_days dynamic partition keys
    no RunRequest for data production jobs

  suspend_d_sensor:
    input:
      cn_a_trade_days
      raw_tushare_suspend_d materialized partitions
      silver_stock_suspend_daily materialized partitions
      suspend_d blocking check status
    output:
      suspend_update_job[trade_date]

  stock_basic_sensor:
    input:
      latest silver_stock_basic materialization
      stock_basic blocking check status
      stock_basic freshness policy
    output:
      basic_update_job

  stock_daily_sensor:
    input:
      cn_a_trade_days
      stock_daily raw/silver materialized partitions
      stock_daily blocking check status
      stock_basic readiness
      suspend_d[trade_date] readiness
      Tushare daily source readiness
    output:
      stock_daily_update_job[trade_date]
Readiness 硬门禁： 下游 sensor 判断上游 ready 时，不能只看文件存在，也不能只看 asset 是否 materialized。 ready 必须包含：目标上游 asset 已 materialized、对应 blocking checks 全部通过；如果是 full snapshot，还必须满足 freshness；如果是 partitioned asset，必须按同一个 partition_key 判断。 WARN checks 不阻断生产，但 WARN metadata 必须可见。
多 sensor 方案已落地，迁移成本验证符合预期：asset key、物理路径、partition 定义不变；主要改动是把 cn_a_trade_day_sensor 中的 stock daily 触发逻辑迁出，新增资产族 sensor，并为每个 sensor 明确 run key、cursor、最大单 tick 请求数和失败重跑策略。
防重复判断口径： 第一版不能用“quote_daily_job 是否成功运行过”判断某个历史分区是否待补。 历史 quote 分区已经由 bootstrap_quote_daily_job materialize 到正式 quote assets， 因此 sensor 必须以股票日线 raw/silver 两个资产的 materialized partitions 交集判断是否已完成。 cn_a_trade_days 只表示这个日期是否注册为 Dagster partition key，不等于股票日线 raw/silver 已生产完成。
第一版安全阈值： cn_a_trade_day_sensor 每 tick 最多注册 2 个 partition key；suspend_d_sensor 与 stock_daily_sensor 每 tick 最多提交 2 个 run request。 这些阈值用于防止配置错误或日历误判时一次性触发大量 runs。stock_basic_sensor 是 full snapshot，每 tick 最多提交 1 个 basic_update_job。
历史踩坑记录： Slice 2.2.1 第一轮只验证到 sensor 发现/注册/提交 run request，不能在当时宣称端到端链路已通。已验证内容包括： dg check defs 通过；dagster sensor preview 返回 2 个 run request； sensor decision 明细只选择 2026-05-18、2026-05-19； 正式 daemon tick 成功注册这两个 dynamic partition keys，并创建两个 quote_daily_job runs。未验证通过的内容是：这两个 run 没有成功执行 asset 生产和 checks。 它们在出队阶段因当时存在多个 daemon heartbeat 冲突失败，属于运行环境/daemon 使用问题，不是 raw_tushare_stock_daily、raw_tushare_suspend_d 或 silver 资产内部失败。 后续 2026-05-21 已由 sensor 触发 quote_daily_job 并成功完成端到端生产； Slice 2.2.1d 后同类验收目标应切换为 stock_daily_update_job。
run_key 失败重跑坑： 历史 quote_daily_job 入口曾使用 run_key=f"quote_daily:{key}" 作为防重复门禁。 Slice 2.2.1d 后正式入口使用 run_key=f"stock_daily_update:{key}"。 Dagster 会认为同一个 sensor run key 已经提交过，即使对应 run 最终失败，后续 sensor tick 也会跳过同一 run key。 本次重启 sensor 后，tick 被标记为 SKIPPED，日志为 “already completed with run keys: quote_daily:2026-05-18, quote_daily:2026-05-19”。 因此不要为了补跑而修改 run key 规则；需要补跑时应使用 Dagster UI、手动 partition run 或后续明确设计的重试流程。 新 job 使用 stock_daily_update:{trade_date} 作为稳定 run key 前缀； 历史 quote_daily:{trade_date} 只作为旧入口的事实记录保留。
silver_trade_calendar 可能包含全年未来交易日。sensor 必须使用 latest_completed_trade_date 截断，只允许已完成交易日进入 build_add_request 和 RunRequest。
第二期第一版 latest_completed_trade_date 使用保守口径：取小于当前自然日的最近 open day。 如果未来要收盘后跑当天，需要新增“数据源已完成更新”的依据，不能直接用自然日 today。

11.1.1 Slice 2.2.1b：stock daily source readiness 与当天交易日

新需求来自日常使用口径：Tushare 源站的当日日线发布时间不精确，可能在当晚 19:00 或 20:00 左右才可用。本地新湖期望在 Tushare 源站当天数据可用后尽快拉取，而不是固定等到第二天。 因此第一版“只取小于当前自然日的最近 open day”的实现，只能作为安全保守版本，不能作为最终日常更新口径。 

new stock daily source readiness requirement:
  candidate_day = today if today is SSE open day
                  else latest open day before today

  if candidate_day == today:
    if local time < 16:00 Asia/Shanghai:
      skip without probing Tushare
    poll Tushare source readiness about every 10 minutes after 16:00
    only trigger stock_daily_update_job[today] after daily(trade_date=today), stock_basic, and suspend_d are ready

  if source is not ready:
    return Chinese SkipReason / no RunRequest
    keep sensor alive for next tick

  if source is ready:
    register cn_a_trade_days partition key if needed
    emit RunRequest(partition_key=today)
设计边界： 这里的 readiness 是“源站 readiness”，表示 Tushare 当天 raw 数据是否已经可拉取； 它不同于后面的 market_breadth_upstream_readiness。 源站 readiness 与上游基础资产 readiness 共同决定 stock_daily_update_job 能不能跑； market breadth readiness 决定 quote raw/silver 和 checks 通过后，下游 gold 能不能跑。

第一版 ready 判定只以 daily(trade_date=YYYYMMDD) 为准。suspend_d 不参与 ready 判断， 因为它在真实业务上可能合法返回 0 行，不能单独区分“确实无停复牌”和“源站未更新”。 stock_daily_update_job 真正运行时只选择 daily 对应 assets；suspend_d 由 suspend_update_job 先行准备，并作为只读前置条件。

实现落点不得放在 defs/tushare_readiness.py 这类宽泛文件中。 源站可用性探测不是 Dagster Definitions 本身，应放在独立业务 helper 包： lake_console/orchestrator/src/orchestrator/source_readiness/tushare/stock_daily.py。 Slice 2.2.1e 后，defs/sensors/stock_daily_sensor.py 负责调用该 helper 并决定是否发起 stock_daily_update_job； defs/sensors/cn_a_trade_day_sensor.py 只负责注册 partition。

跳过场景 中文说明 行为
没有可用交易日 没有从交易日历中找到符合条件的已完成上交所开市日。 不注册分区，不发起运行。
没有待补数据 当前所有符合条件的行情日频分区都已经生成完成，没有待补数据。 不发起运行。
当天未到探测窗口 今天是交易日，但还没到 16:00，不开始探测 Tushare 日线。 不调用 Tushare，不发起运行。
当天源站未就绪 今天是交易日，也已经进入探测窗口，但 Tushare 日线还没有返回有效数据。 不写 raw，不占用 run_key，等待下一次 sensor tick。

传感器间隔调整为 minimum_interval_seconds=600。这是 Dagster sensor 的最小评估间隔， 不是严格 cron；实际效果是 daemon 正常运行时，16:00 之后大约每 10 分钟探测一次源站。

11.1.2 防未来交易日误跑流程

silver_trade_calendar 是“交易日计划表”，它可能提前保存全年日历。 例如今天是 2026-05-20，日历里可能已经有 2026-12-31 open=true。 这个未来日期在日历上是正确的，但未来行情、未来停复牌、未来市场宽度还没有真实发生，不能注册后立刻运行。

latest_completed_trade_date 是 sensor 的安全边界，意思是“目前最晚哪个交易日已经真实结束，理论上可以拉数据”。 第二期第一版采用保守规则：只取小于当前自然日的最近 open day。这样即使今天是交易日，也不会在当天盘中误跑当天数据。 

example:
  current_date = 2026-05-20
  silver_trade_calendar contains:
    2026-05-18 open=true
    2026-05-19 open=true
    2026-05-20 open=true
    2026-05-21 open=true
    2026-12-31 open=true

  latest_completed_trade_date = 2026-05-19

  allowed to register / run:
    2026-05-18
    2026-05-19

  forbidden to register / run:
    2026-05-20
    2026-05-21
    2026-12-31

所以 sensor 的完整判断流程是：先读取交易日历，再计算 latest_completed_trade_date， 然后只保留 trade_date <= latest_completed_trade_date 的 open days。 这些日期才允许注册为 Dagster dynamic partition keys，也才允许在上游 ready 后触发股票日线 job；Slice 2.2.1d 后该 job 为 stock_daily_update_job。

默认 STOPPED 是为了防止验证阶段一启动 daemon 就自动扫描全年日历、注册未来分区、触发大量无意义失败 run。 第二期必须先人工小范围验证 2026-04 和最近几个已完成交易日，确认不会误跑未来日期后，再讨论是否开启 RUNNING。

11.2 长期方案：sensor 只注册交易日分区

更优雅的长期方向是让 cn_a_trade_day_sensor 退回到“交易日分区注册器”的角色： 它只负责把已完成交易日注册到 cn_a_trade_days，不直接决定触发哪个数据域 job。 后续 stock_daily_update_job、未来的 fundflow_daily_job、limit_daily_job、factor_daily_job 等资产族， 由各自的 declarative automation / on-missing 条件响应缺失分区。 

long-term cn_a_trade_day_sensor:
  latest_completed_trade_date = resolve_latest_completed_trade_date(now)
  eligible_open_days = open days <= latest_completed_trade_date
  new_keys = eligible_open_days - existing cn_a_trade_days

  return SensorResult(
    dynamic_partitions_requests=[
      cn_a_trade_days.build_add_request(new_keys)
    ],
    run_requests=[]
  )

stock daily assets:
  automation condition:
    when partition exists
    and stock daily assets are missing
    and stock_basic / suspend_d prerequisites are ready
    request stock_daily_update_job[trade_date]
长期方案不能直接拍脑袋落地。进入长期方案前必须用当前 Dagster 版本验证： dynamic partition key 新增后，declarative automation 是否能稳定发现 missing partition 并请求对应资产族； 同时不能绕过 raw/silver blocking checks 和 market breadth readiness gate。

11.3 从短期到长期的迁移成本评估

迁移项 变化内容 成本 风险与控制
资产 key / 物理路径 不变。raw_tushare_stock_daily、raw_tushare_suspend_d、silver/gold 路径都不需要迁移。 低 无数据迁移成本，这是推荐先走短期方案的原因。
partition 定义 不变。继续使用 cn_a_trade_days dynamic partitions。 低 只改变谁触发 run，不改变 partition key 语义。
cn_a_trade_day_sensor 从“注册 partition + 返回 quote_daily RunRequest”改成“只返回 dynamic partition add request”。 低 需要删除或关闭 run_requests 生成逻辑，避免与 declarative automation 双重触发。
stock_daily_update_job 触发方式 从 sensor 显式触发，迁移为 quote 资产族自己的 automation condition / on-missing 触发。 中 必须验证 Dagster 当前版本对 dynamic partitions + declarative automation 的组合行为；不能靠猜。
重复运行防护 短期靠 sensor run_key=f"stock_daily_update:{key}" 防重复；长期要依赖 automation 的 missing 状态和 Dagster run 状态。 中 迁移时要先小范围验证同一天不会被 sensor 和 automation 同时提交 run。
未来更多日频资产族 长期方案下，新增 fundflow_daily_job 等不需要改 cn_a_trade_day_sensor。 收益高 这是长期方案的主要收益：交易日发现和数据域生产解耦。
上线切换 先保持 sensor 默认 STOPPED 或小范围运行；验证 automation 后，再关闭 sensor 的 run 触发职责。 中 建议分两步切：先让 automation 只在测试分区生效，再切正式 2026-04 或最新交易日。
总体评估：从短期方案迁移到长期方案的成本是低到中等，主要改的是调度/自动化层，不涉及数据文件迁移、asset key 迁移或路径迁移。 真正需要谨慎验证的是 Dagster 当前版本的 declarative automation 行为，以及它和 dynamic partitions、checks readiness 的组合方式。

12. Market Breadth 自动化门禁

daily_market_breadth_job 是下游业务生产 job，只负责 gold。它不等待成 RUNNING，不轮询上游，不调用 Tushare。 “等待”发生在 declarative automation 不请求下游 run 这一层。

12.1 ready 条件

market_breadth_upstream_readiness[trade_date]:
  partition exists in cn_a_trade_days
  trade_date <= latest_completed_trade_date
  silver_stock_daily[trade_date] materialized
  raw_tushare_stock_daily[trade_date] blocking checks passed
  silver_stock_daily[trade_date] blocking checks passed
  silver_stock_suspend_daily[trade_date] materialized
  raw_tushare_suspend_d[trade_date] blocking checks passed
  silver_stock_suspend_daily[trade_date] blocking checks passed
  silver_stock_basic materialized and blocking checks passed
  silver_stock_basic freshness satisfies current trade_date
  stock_basic update is not selected by daily_market_breadth_job
  silver_trade_calendar materialized and blocking checks passed

12.2 实现优先级

优先级 方案 使用条件
1 Declarative automation + upstream blocking checks。 当前 Dagster 版本验证通过，能表达上游缺失不请求、上游 checks 失败不继续。

3 通知/审计 sensor。 不作为生产触发入口，只用于提示上游缺失、checks 失败或连续未跑。
