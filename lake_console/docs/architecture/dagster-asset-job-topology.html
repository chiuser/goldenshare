Dagster 资产与 Job 拓扑梳理

本文用于把当前 Dagster orchestrator 中的 asset 层级、依赖关系、资产归属、job selection、更新频率和触发方式放到一张研发地图里。 它同时区分“当前代码事实”和“后续应遵守的研发模式”，避免业务 job 偷偷写共享基础资产，也避免 full snapshot 并发写入变成隐性坑。

Job 的职责是“这次跑哪些资产”，不是“这些资产怎么生成”。因此同一个 asset 可以被不同 job 选中，但必须有清晰目的，不能让多个业务 job 随意写共享基础资产。

5. 触发方式与日内时序

后续研发模式应把“基础资产准备”和“业务资产生产”分层：基础资产先更新并通过 checks；股票 / 指数日线分区再按交易日生产；gold 业务资产最后在 readiness 通过后生产。

基础资产准备 stock_basic 是日更 full snapshot，suspend_d 是日频停复牌事实。二者都应在 stock_daily 生产前完成。
Stock Daily 生产 后续 stock_daily_update_job 只写日线 raw/silver；它只读校验 silver_stock_basic 和 silver_stock_suspend_daily。
业务 Gold 生产 breadth gold jobs 只生产各自 gold 资产，直接输入 silver_stock_daily 未通过质量门禁就不请求。

6.1 推荐研发模式

一个资产，一个清晰归属 每个 asset 必须归属到一个资产族：calendar、basic、quote、breadth。资产族决定它的 job 入口、更新频率和 checks 口径。
共享基础资产单独写 stock_basic、trade_calendar 只能由自己的 update job 写。业务 job 只能只读依赖。
Job 是入口，不是逻辑容器 job 文件只写 define_asset_job 和 selection。拉取、写文件、SQL、质量判断都不进 job。
Checks 是边界，不是装饰 blocking check 定义能不能继续生产；WARN check 定义可观测差异。readiness 必须读 checks 状态，上游 checks 不全绿就不能触发下游。
Sensor 按资产族拆分 cn_a_trade_day_sensor 只注册交易日；index_trade_day_sensor 只注册指数交易日；index_daily_sensor、suspend_d_sensor、stock_basic_sensor、stock_daily_sensor 分别判断本资产族是否 missing、fresh、checks passed 或源站 ready，并提交对应 run request。
Sensor 门禁必须轻量 silver_index_daily_sensor 的门禁只读 raw-by-code 文件事实：全部注册指数代码的 raw parquet 文件都存在，且都包含目标交易日数据；不在 evaluation 中读取 raw run tags/config 或 raw check history，重检查放在 asset run 和 checks 中。
告警不参与生产 feishu_run_status_sensor.py 只发送 run started/succeeded/failed 通知，默认停止；发送失败只能影响告警可观测日志，不能阻断、重试或回滚任何 asset 写入。
并发保护作为保险丝 先通过 job selection 设计避免重复写；再用 Dagster concurrency 保护 full snapshot 写入。
