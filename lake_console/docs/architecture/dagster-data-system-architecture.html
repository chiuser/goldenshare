Goldenshare 本地数据系统与 Dagster 资产架构

本文按当前讨论目标梳理：本地 Parquet 数据湖、DuckDB、Dagster、本地 PostgreSQL、本地 ClickHouse、生产 PostgreSQL 与未来生产 ClickHouse 的关系；并把当前 `lake_console` 的数据集、节点、服务映射到 Dagster assets 与 resources。

文档性质早期架构 review 文档；下方旧湖映射仍是设计参考，已实现清单以 Phase 2 / Phase 3 文档为准。
当前 Dagster 项目lake_console/orchestrator 已包含正式 assets、resources、jobs、checks、sensors，不再是脚手架空项目。
当前数据集事实源Dagster active definitions 以 lake_console/orchestrator/src/orchestrator/defs 为准；旧 Lake Console catalog 只作迁移参考。
当前 PostgreSQLgoldenshare_dagster 承载 Dagster 状态；当前 orchestrator 代码不注册 goldenshare_lake_meta resource。
长期方向如果 Dagster 能承接主要治理能力，lake_console 产品形态将逐步退场。
新 Lake 根路径Dagster 新资产只使用 data_lake/raw、data_lake/silver、data_lake/gold。

0. 长期演进口径

长期而言，如果 Dagster 能胜任当前数据湖控制台承担的大部分工作，lake_console 将逐步废弃、退场，直到最终移除相关产品代码。Dagster 将成为本地数据湖资产管理、依赖、分区、检查、调度、回填、日志和状态观测的主控制面。

但这不意味着现有 lake_console 的代码和模型没有价值。相反，当前已经定义的数据结构、类别体系、catalog、同步策略、数据生成服务、文件路径口径、质量检查经验，是迁移到 Dagster 时最重要的参考资产。后续应逐步吸收、借鉴、重构进 Dagster assets/resources/checks/schedules，而不是凭空重写一套未知口径。

当前 lake_console 内容 长期处理方式 迁移到 Dagster 的方向
前端数据湖控制台页面、同步中心页面、控制台交互壳 若 Dagster UI 能覆盖主要观测和操作能力，逐步退场。 用 Dagster asset graph、runs、asset checks、backfills、schedules 替代。
LakeDatasetDefinition、LakeNodeDefinition、catalog 分类与路径定义 保留为迁移依据，逐步吸收到 Dagster asset metadata。 以 LakeNodeDefinition 粒度生成或定义 Dagster assets。
同步、导出、清洗、DuckDB 计算、指标生成相关服务 保留算法和业务口径，重构执行入口。 迁移为 Dagster assets、resources、ops 内部函数或 asset checks。
lake_jobs/*、duckdb_compute/runs/*、_tmp 运行账本 逐步退场。 由 Dagster run/event/log/backfill/check 状态接管。
本地配置、路径规则、Lake Root 可用性检查 保留安全口径，收敛实现方式。 迁移为 Dagster resources 和执行前检查。

0.1 Dagster 新数据湖迁移原则

接下来不会大批迁移旧数据湖资产到 Dagster，而是理清楚一个数据集、设计一个数据集、迁移一个数据集。每次迁移前，必须先明确层级、路径、分区、依赖、检查、resource、回填和验证口径，再进入实现。

raw data_lake/raw

只放 Dagster 新数据湖的原始事实资产。旧 raw_tushare 目录不再作为 Dagster asset path。

silver data_lake/silver

放清洗、规范化、身份映射、质量门禁后的稳定中间资产。比如 qfq 前的 stk_mins_by_date_clean_next。

gold data_lake/gold

放成品资产、研究资产、serving 候选和发布来源。比如 qfq 后的分钟线资产、成品股票池、交易日历等。

原则 门禁口径 原因
新旧路径隔离 任何新的 Dagster asset path 不得出现旧数据湖路径，例如 raw_tushare、旧 manifest、旧 derived、旧 research。 避免新 Dagster 资产图继续绑定历史 Lake Console 目录语义。
旧数据湖不是废弃数据 旧数据湖只作为迁移来源。迁移某个数据集时，按确认后的新层级复制或重建到 data_lake/raw|silver|gold。 保留历史数据价值，但不让旧路径污染新资产定义。
单数据集迁移 禁止批量迁移。每个数据集必须先有迁移设计、检查清单和验证结果，再进入下一个数据集。 每个数据集的时间语义、分区、质量门禁、上下游依赖都不同，不能套模板硬搬。
Asset 声明门禁 声明 Dagster asset 前，必须列清 asset key、layer、new path、old source path、partitions、upstream assets、resources、checks、backfill 方式、验证 SQL/脚本。 保证资产图、物理文件和质量检查是一套口径。
Resource 声明门禁 新增或迁移 resource 前，必须列清职责、配置来源、持久化位置、失败时机、消费者、测试替身和是否允许阻断 dg dev。 resource 是外部能力边界，不能随手创建导致配置散落。
Dagster 用法门禁 任何 Dagster assets/resources/partitions/checks/backfills/schedules 设计或操作，必须先查 Dagster 官方文档或本地 --help，讨论确认后再动手。 避免靠猜使用 Dagster，防止重复之前“先干后查”的时间浪费。

这条原则优先级高于旧目录惯性：旧 Lake Console 路径可以被读取、审计、复制、对比，但不能成为新 Dagster asset 的正式 path。

这张图把“数据流”和“控制/元数据流”分开。Parquet、ClickHouse、生产库承载数据；Dagster 和本地 PostgreSQL 承载运行、状态、发布账本与治理信息。

2. 数据分层定义

raw 原始事实层

保存源站或批准只读来源的原始业务事实。字段口径尽量贴近源端，但必须去掉 Goldenshare 内部系统字段。写入策略以 current file 或 replace partition 为主。

silver 清洗规范层

从 raw 计算得到，处理字段标准化、去重、身份映射、生命周期过滤、质量门禁。它是后续 gold 和 serving 的稳定输入。

gold 服务与研究层

面向查询、研究、发布或本地 API 调试的成品资产。可以仍是 Parquet，也可以被同步到本地 ClickHouse serving 表。

path 物理目录不参与资产分类

manifest 是当前实现里的历史物理目录名，不是资产层级。资产分类只认 raw / silver / gold；具体文件放在哪个目录，不能决定它的资产层级。

4.1 已确认的资产口径修正

  • 资产分层只认 raw / silver / gold，不再引入 support、reference 这类额外资产分类。
  • manifest 只是当前实现里的历史物理目录名，不参与资产分类。后续如果需要更清晰的目录结构，可以把成品资产迁移到 gold/*。
  • daily、adj_factor、security_universe、trading_calendar 都是正常数据资产；是否参与其他资产计算，只是依赖关系，不改变它们的层级。
  • lake_jobs/*、duckdb_compute/runs/*、duckdb_compute/_tmp/* 属于历史运行账本和临时状态，未来应逐步退场，由 Dagster 的 run/event/schedule/backfill/log/check 机制接管。
  • research/stk_mins_by_date_clean_next 在 qfq 计算前是 silver；qfq 计算后的结果应该是独立 gold asset。当前原地替换会让同一路径同时代表两个语义状态，后续需要拆出稳定的 gold 路径和 asset key。

5. 本地 PostgreSQL 两个库的职责关系

本地 PostgreSQL 不是存行情明细的地方。行情明细仍在 Parquet Lake 和 ClickHouse serving。PostgreSQL 的定位是“事务型控制面和治理账本”。

这份文档不建议在 dg dev 启动时阻断式检查移动 SSD。更合理的方式是：Dagster 正常启动，lake 相关 asset 执行前检查 Lake Root；不可用时记录为 run/check 失败。

7. 当前决策

  • Dagster 新数据湖路径统一为 data_lake/raw、data_lake/silver、data_lake/gold。
  • 旧数据湖路径只作为迁移来源，不得出现在任何新的 Dagster asset path 中。
  • 迁移节奏是理清楚一个数据集、设计一个数据集、迁移一个数据集，禁止批量迁移。
  • 资产分类只使用 raw / silver / gold。
  • manifest 是历史物理目录，不是资产层级；不要围绕它创造资产分类。
  • research/stk_mins_by_date_clean_next 在 qfq 前是 silver；qfq 后结果应拆成独立 gold asset，避免原地替换造成语义混乱。
  • 当前 derived 默认按 gold 处理。
  • Dagster asset 以 LakeNodeDefinition 为粒度，而不是以 LakeDatasetDefinition 为粒度。
  • goldenshare_lake_meta 只在明确业务账本需要时接入；当前 active orchestrator 代码不注册它作为 resource，旧 active pool / 主要指数 metadata 表不再是生产依赖。
