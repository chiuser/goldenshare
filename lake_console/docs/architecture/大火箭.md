# 大火箭

## 记录目的

本文记录本地数据湖引入 Dagster 的早期讨论结论。

当前阶段不是正式方案设计，也不是实施清单。重点是先把方向、边界和仓库归属想清楚，避免过早开工导致架构走偏。

## 已确认结论

1. Dagster 不需要把 `dagster-io/dagster` 源码下载到工程里运行。
2. 正常使用方式是把 Dagster 作为 Python 依赖安装，然后在自己的工程里写 assets、jobs、resources、schedules、checks 等编排代码。
3. Dagster 适合作为本地数据湖控制面，负责资产、依赖、分区、检查、调度、回填、日志和运行状态。
4. Goldenshare 仍然专注业务规则、数据口径、同步逻辑、DuckDB 计算、发布规则和本地 lake 文件事实。
5. 当前讨论范围仅限本地数据湖，不替换生产 Ops 运营后台，也不接生产 TaskRun、scheduler、worker 或状态表。

## 仓库归属结论

阶段性决定：Dagster 先放在 `goldenshare` 仓库内，归属于 `lake_console` 本地工程，而不是立即新建独立仓库。

原因：

1. 当前还处于学习和讨论阶段，Codex 需要持续读取 `goldenshare` 现有上下文、文档、边界规则和 `lake_console` 代码。
2. 如果立即分仓，会导致新的 Codex 项目缺少当前仓库上下文，讨论和实现都会变得费劲。
3. `lake_console` 本来就是本地数据湖独立工程，适合作为 Dagster 本地控制面的承载位置。
4. 现阶段更重要的是上下文连续性，而不是过早追求仓库物理隔离。

推荐理解：

```text
物理上同仓：goldenshare/lake_console
逻辑上独立：本地 Dagster 控制面，不进入生产主系统
```

未来如果 Dagster 控制面稳定、边界清晰、可以作为独立产品存在，再评估是否拆成独立仓库。

## 隔离原则

即使放在同仓，也必须保持运行和边界隔离：

1. 依赖隔离：Dagster 可以使用独立虚拟环境或独立依赖入口。
2. 运行隔离：使用独立 `DAGSTER_HOME`，不混入生产运行目录。
3. 位置隔离：Dagster 运行目录和本地 PostgreSQL 必须安装并存放在本机固定磁盘，不放在移动 SSD 上。
4. 数据库隔离：本地 PostgreSQL 中区分 Dagster 内部状态库和业务 metadata 库。
5. 系统隔离：不接生产 `src/ops`、TaskRun、scheduler、worker 或状态快照。
6. 部署隔离：生产部署脚本不启动 Dagster，不把 Dagster 纳入生产服务。
7. 环境隔离：本地 lake 仍然通过显式配置指定，不允许隐式写入仓库目录、用户 home 或系统临时目录。

## 本机磁盘与移动 SSD 边界

阶段性决定：Dagster 和本地 PostgreSQL 都应安装、运行并持久化在本机固定磁盘上，而不是移动 SSD 上。

原因：

1. Dagster 保存 run、event、schedule、asset materialization 等控制面状态，运行时对这些状态有持续读写。
2. PostgreSQL 承载 Dagster 管理状态和本地业务 metadata，属于事务型状态，不适合放在可能被拔掉的移动盘上。
3. 如果移动 SSD 被随意拔掉，最多应该影响 Parquet Lake 文件访问，不应该破坏 Dagster 或 PostgreSQL 的管理状态。
4. 移动 SSD 的定位是承载本地数据湖资产文件，不承载控制面数据库和服务运行态。

推荐理解：

```text
本机固定磁盘
  Dagster 代码依赖 / DAGSTER_HOME / 本地 PostgreSQL / ClickHouse 服务数据

移动 SSD
  Parquet Lake：raw / silver / gold / manifest / research / derived 等文件资产
```

后续设计必须显式处理移动 SSD 不可用的情况：Dagster 和 PostgreSQL 可以正常启动，但相关 lake assets 显示为不可访问、不可执行或需要重新挂载，而不是让控制面自身崩坏。

## 第一阶段安装流程

第一阶段目标只是把本地控制面地基铺好，不接任何业务资产。

验收目标：

1. 本机 PostgreSQL 能稳定启动。
2. `goldenshare_dagster` 数据库可连接。
3. `DAGSTER_HOME` 位于本机固定磁盘。
4. Dagster UI 能启动。
5. Dagster 的 run / event / schedule 等状态写入本机 PostgreSQL。
6. 移动 SSD 不挂载时，Dagster 和 PostgreSQL 仍能正常启动。

### 1. 安装 PostgreSQL

第一版推荐用 Homebrew 安装本机 PostgreSQL，不使用 Docker，不放移动 SSD。

```bash
brew install postgresql@18
brew services start postgresql@18
```

如果本机已有其他 PostgreSQL 版本，先确认端口和服务状态，避免多个实例同时抢 `5432`。

```bash
brew services list
```

Homebrew 的 PostgreSQL 数据目录默认在本机固定磁盘，例如 Apple Silicon 常见路径：

```text
/opt/homebrew/var/postgresql@18
```

这个目录不得移动到移动 SSD。

### 2. 创建本地数据库

本机正式环境不单独创建业务用户，先按当前决定直接使用本地 PostgreSQL 超级用户或默认用户。

仍然创建两个数据库，把 Dagster 内部状态和我们自己的 lake metadata 分开：

```bash
PG_BIN="$(brew --prefix postgresql@18)/bin"

"$PG_BIN/createdb" goldenshare_dagster
"$PG_BIN/createdb" goldenshare_lake_meta
```

Dagster 官方要求 Postgres storage 使用的数据库配置 UTC timezone。第一版先把两个本地库都设为 UTC，展示层后续再处理本地时区：

```bash
"$PG_BIN/psql" -d goldenshare_dagster -c "ALTER DATABASE goldenshare_dagster SET timezone TO 'UTC';"
"$PG_BIN/psql" -d goldenshare_lake_meta -c "ALTER DATABASE goldenshare_lake_meta SET timezone TO 'UTC';"
```

连接串第一版使用本机默认用户，不写入仓库：

```bash
export DAGSTER_POSTGRES_URL="postgresql://$(whoami)@localhost:5432/goldenshare_dagster"
export LAKE_META_POSTGRES_URL="postgresql://$(whoami)@localhost:5432/goldenshare_lake_meta"
```

### 3. 准备 Dagster 本机目录

Dagster 的配置、运行日志和本地 artifact 都放在本机固定磁盘。

```bash
mkdir -p ~/.goldenshare/dagster_home
mkdir -p ~/.goldenshare/dagster_logs
mkdir -p ~/.goldenshare/dagster_artifacts
```

本地环境变量：

```bash
export DAGSTER_HOME="$HOME/.goldenshare/dagster_home"
export DAGSTER_COMPUTE_LOG_DIR="$HOME/.goldenshare/dagster_logs"
export DAGSTER_ARTIFACT_DIR="$HOME/.goldenshare/dagster_artifacts"
```

这些路径不得指向移动 SSD。

本机环境变量统一写入 shell profile，当前使用 `~/.bash_profile`，不再额外维护散落的临时 env 文件。

### 4. 编写 `dagster.yaml`

`dagster.yaml` 放在：

```text
~/.goldenshare/dagster_home/dagster.yaml
```

第一版配置思路：

1. Dagster run / event / schedule / tick / asset 状态写入本机 PostgreSQL。
2. compute logs 写入本机固定磁盘。
3. local artifacts 写入本机固定磁盘。
4. 本地并发先限制为 `1`，避免多个数据湖任务同时抢 DuckDB、磁盘和外部接口额度。

示例：

```yaml
storage:
  postgres:
    postgres_url:
      env: DAGSTER_POSTGRES_URL

compute_logs:
  module: dagster.core.storage.local_compute_log_manager
  class: LocalComputeLogManager
  config:
    base_dir:
      env: DAGSTER_COMPUTE_LOG_DIR

local_artifact_storage:
  module: dagster.core.storage.root
  class: LocalArtifactStorage
  config:
    base_dir:
      env: DAGSTER_ARTIFACT_DIR

run_coordinator:
  module: dagster.core.run_coordinator
  class: QueuedRunCoordinator
  config:
    max_concurrent_runs: 1
```

### 5. 创建 Dagster 项目脚手架

官方脚手架创建命令：

```bash
cd /Users/congming/github/goldenshare/lake_console
uvx create-dagster@latest project orchestrator
```

命令语义：在当前目录下创建一个名为 `orchestrator` 的新目录，因此目标路径是：

```text
/Users/congming/github/goldenshare/lake_console/orchestrator
```

当前脚手架已创建，且 `uv sync` 已执行。

脚手架已生成：

```text

lake_console/orchestrator/README.md

lake_console/orchestrator/src/orchestrator/__init__.py
lake_console/orchestrator/src/orchestrator/definitions.py

```

当前已执行 `uv sync`。`uv sync` 已根据 `pyproject.toml` 创建项目自己的 `.venv`，并生成 `uv.lock`。

### 6. 启动验证

启动前先确认环境变量已设置：

```bash
echo "$DAGSTER_HOME"
echo "$DAGSTER_POSTGRES_URL"
```

第一阶段不创建 Dagster 项目，不接业务资产。若需要验证 webserver，可用空 workspace：

```bash
dagster-webserver --empty-workspace -h 127.0.0.1 -p 3000
```

验证点：

1. 浏览器能打开 Dagster UI。
2. Dagster UI 的 instance 配置能看到当前 `dagster.yaml`。
3. PostgreSQL 中能看到 Dagster 创建的内部表。
4. 关闭 Dagster 再启动，历史运行状态不会丢。
5. 移动 SSD 不挂载时，Dagster 仍能启动。

注意：不要从仓库根目录长期直接启动 Dagster webserver。实测从仓库根目录启动时，Dagster 会自动读取当前目录的 `.env`，可能把生产或业务环境变量带入本地控制面。正式启动方式后续必须单独讨论并确认。

第一阶段不做以下事情：

2. 不定义正式 lake assets。

## 当前倾向的职责分工

```text
本地 Parquet 数据湖
  存 raw / silver / gold 文件

DuckDB
  负责从 raw 计算 silver / gold

Dagster
  负责定义资产、依赖、分区、检查、调度、回填、日志和状态

本地 PostgreSQL
  一部分承载 Dagster run/event/schedule 等管理状态
  一部分承载业务 metadata，如数据源、schema、发布包、同步记录

本地 ClickHouse
  存 serving 表，供本地 API 调试

生产 PostgreSQL
  接收轻量发布结果

未来生产 ClickHouse
  替代部分生产 PostgreSQL 查询
```

## 暂不决定的事情

以下问题后续继续讨论，不在本文定案：

1. Dagster 目录最终命名。
2. Dagster 是否使用独立 `pyproject.toml`。
3. Dagster metadata 和业务 metadata 是分库、分 schema，还是同库不同 schema。
4. 哪些现有 `lake_console` 命令先被包装为 Dagster asset。
5. Dagster asset partition 粒度如何设计，尤其是 `stk_mins` 这类大规模数据集。
6. 本地 ClickHouse serving 表与发布包的第一版边界。
