1. 目标、范围和最新决定

下载器由业务进程像SDK一样独立创建和调用。每个实例只负责自己的下载，不管理其它实例、线程或进程。

2026-10-20管理员最新决定取代前版进程控制设计：撤销组件的跨线程/跨进程限频、下载名额、配置协调及其锁。限频和并发调度由业务保证，不由组件判断业务身份或检查DG是否只有一个任务。

管理员已确认：下载器在调用它的业务线程中同步执行，同一实例的创建、使用、回调和关闭均在同一进程、同一线程；组件不创建线程、请求子进程或后台服务。DG独立任务执行进程内可直接调用；需要响应页面的业务另开下载线程。业务可注册标准回调，成功页、安排重试和完整unit完成时通知；后续线程间或进程间传递归业务。详见第4、14和21.9～21.10节。

四单元、六种模式全部建设。业务只传完整契约名、模式和范围；组件完成一个unit的全部分页、有限重试和时间排序后交付一次内存结果。业务决定存在哪里、怎么存，并负责归一化、业务校验及提交。

每活动unit工作空间2GiB的已确认初始值保留，不预分配、不测量。原“同机同时最多2个unit”撤销，既不是下载器的进程数，也不再是任何跨进程限制。一个实例同一时刻只执行一个session、一个unit；不同实例互不统计，总内存和总请求频率由业务控制。

load()通过所在工程既有读取办法取得token/地址及组件技术默认，返回独立实例。业务不传token、地址、字段、分页或请求方式。download创建session但不发网；__enter__完成契约、输入和mapping检查并占用本实例；首次next才下载。

同一实例的load、download、with、next、poll、cancel和close必须在拥有实例的同一进程、同一调用线程中执行。DG可在执行该资产的线程直接调用；需要持续响应页面的业务另开下载线程，页面线程不直接操作该实例。每实例同一时刻一个session，unit/页串行；第二session未等前一个关闭便进入时报INPUT，不排队、不加锁。同一实例不得跨线程/进程使用，不实现fork继承修复或跨线程cancel/poll；多个业务线程/进程各建独立实例，合计频率/并发/内存由业务负责。组件不检测是否主线程、不自动换线程或替业务创建线程；在独立任务进程的主线程调用不属于错误。

不提供reload()：旧实例保持创建时配置，新实例调用所在工程读取入口，遵守其既有缓存/生效规则。不同实例即便同token、不同配置也不相互检查或报“配置冲突”。改配置不影响正在执行的对象；同token整体使用是否合理由业务/运营保证。

DownloadControl是不可变输入，只含业务的is_cancelled: Callable[[], bool] | None，默认None；它本身不保存停止状态。每个session独立建立内部SessionControl，合并自己的cancel标志与该业务检查，分页、退避、接收和排序都使用这同一个内部对象。检查须快速返回严格bool；非bool为INPUT，不按真假值猜。普通业务异常原样结束且不重试；在__next__中意外抛StopIteration的特殊转换见第23.9节。该接口不建线程或通信；外部停止要求由业务传入，session.cancel只设置本session标志。

业务应使用with。若确需try/finally，须先显式调用session.__enter__()完成相同准备，再遍历并在finally close；只for或只finally close不等于已完成初始化。CREATED状态的__iter__/__next__报INPUT且不发网；会话不能重复进入。__enter__失败自行清理仅本session已取得的资源，因为此时with不会调用__exit__。实例用当前session引用标记使用者，只在该引用就是自己时清除；第二session因已有活动session而失败，不能清除第一个session的标记。此处不加锁、不支持并发调用。__exit__始终不吞业务异常。

标准回调的注册与使用期

on_progress在创建本次DownloadSession时注册，类型为Callable[[DownloadProgress], None] | None，只接收组件定义的一个不可变进度对象，返回None。省略或None表示业务不需要通知，组件不调用任何外部通知方法；非None且不可调用、为异步函数或异步__call__时，在准备阶段报INPUT，不发网、不试运行回调，也不创建事件循环。回调只归本session，运行中不替换、不全局登记，不影响下一次任务。

回调普通异常由通知实现单独处理；返回值不作为取消、重试、业务提交或限频指令。回调不能重入next、关闭当前会话或修改内部状态。若需停止，使用既有取消检查或同线程session.cancel；通知顺序见第14～15节。其它线程/进程不得直接读取活动下载器；需要其收到信息时，由业务回调主动传递摘要。拥有实例的业务线程可以直接处理摘要，没有必须转交另一线程的要求。

回调期间允许和禁止的调用

session用普通的_in_next及ProgressReporter.in_callback标志防止同线程递归进入，不使用锁。回调期间允许cancel、poll_progress和读取summary；再次next、enter、close或显式__exit__在修改状态前报INPUT，不请求、不关闭资源、不清除活动标记。这个INPUT由普通通知异常分支处理，当前下载仍继续。业务保存/遍历逻辑中的正常break/异常则由with正常收尾。跨线程使用仍不受支持，不能把同线程检查当线程安全承诺。

7. 实例使用范围：各实例独立，不管理进程

一个unit是什么，与进程数是什么关系

unit仍是第9节由契约与模式确定的一份完整交付范围：例如某一天的全部股票，或某只股票的整段指定历史。一个unit可以有多页，但组件在当前业务进程中同步请求，没有“每页创建一个进程”。一个任务可以有100个unit，不限制为2个。

当前实例只处理一个活动unit，属于顺序调用，不是对其它实例的数量限制。两业务进程分别创建实例可以各处理一个unit；三个进程各建实例也不会因组件名额被拦住。组件不检查有几个进程、哪个账户、同token是否正在别处下载；合计频率和内存由业务负责。

原进程间运行状态全部撤销

不创建进程间状态目录、状态文件、锁文件、任务/请求登记、token摘要、进程心跳或配置代次。不使用fcntl、threading锁、共享内存或进程间通信。不注册fork前后回调，不清理其它进程资源；业务在本进程创建并使用对象，不继承正在使用的父对象。

发送与限频的归属

完成输入检查后即可按当前任务顺序发送，不预约发送时间，不记录别的实例发送时间。业务负责整体限频，包括分页、尾页、重试及SDK实际调用可能增加的请求；组件不让业务逐页接收或批准。业务在unit之间等待只能调慢unit之间的请求，不能精确控制一个unit内部页间间隔；按已确认决定，组件仍不补逐页批准、主动限频或每实例频率配置。

收到429仍按标准错误和有限退避处理，这是失败后的恢复，不是主动限频。组件不因为“业务已保证限频”就把429伪装成成功或删除重试。

对象A结束只关闭A的资源

每次请求由其当前session拥有连接和响应；finally明确关闭，session退出释放自身buffer和活动标记。没有“释放两个名额”、跨实例配置冲突或等其它实例退出。已交付结果归业务持有，关闭A不改A的结果，更不操作B的连接或结果。

每个使用组件的进程在实际调用线程中创建、使用并关闭自己的实例；DG式独立任务进程不强制另开线程。需要响应页面的业务由业务另开下载线程。同进程多个调用线程各持有独立实例，回调始终在拥有该实例的线程执行。组件不提供跨实例协调、线程创建、进程创建、锁、通知队列或进程间通信。

枚举按契约声明的维度和值顺序展开；省略时只使用该契约明示默认，没有默认就要求输入。契约明确枚举组合是否各自为unit；若多个枚举属于同一unit，执行单元按固定顺序完成所有组合再交付一次。组合按需生成，不构造完整笛卡尔积。枚举选择同样进入unit身份，不能借此新建字段子契约。

用本任务的板块例子说明：按管理员澄清，概念、地域、行业使用同一个接口和同一份完整业务契约，变化的是分类标签值。本地文档362对dc_index同时列有请求/输出字段idx_type；它是理解该边界的资料，不是本轮真实源验收。若某天三类共同构成契约的一份完整unit，内部按该契约完成各类及其分页后交付一次；它们不是三个不同契约。若契约规定各分类分别为unit，Planner也须把分类组数计入total_units、unit_id和顺序，任务汇总使用同一计数；不能到执行时临时改变unit粒度。模式表中的基础数量按固定分类/过滤范围理解，分类是否进一步展开只能由同一契约明示。

多个枚举组合属于同一unit时，还必须保留“这条记录由哪组输入取得”。采用§13的独立请求输入说明和行索引；不得往源fields/values中补分类列。例如源未返回分类字段，两组输入各返回相同的代码和时间，也保留两条记录及各自输入索引，业务仍能分辨来源；这不是主键去重或业务校验。

unit_id选用SHA-256，内容是完整契约名称/版本/摘要、模式、对象、点或完整区间、固定过滤和本unit枚举选择的规范表示；不含PID、随机任务ID、分页位置或运行时钟。跨进程重启相同意图身份保持，范围/契约变化身份变化。task_id另用UUID，表示本次执行，不能拿unit_id充当业务已提交证明。

UnitPlanner对输入集合只保存冻结的小型索引，O(对象数+时间点数+枚举输入数)，不保存业务数据和全组合。每次next生成DownloadUnit（ordinal、unit_id、完整范围、固定参数），再由RequestBuilder生成不含凭据的PageRequest。凭据只在本实例的网络发送前附加。输入冻结表示超过1MiB时明确容量不足，不能截短对象/日期以通过。

10. 执行单元：业务进程内同步请求

10.1 单次请求接口与执行顺序

PageDownloader确定当前页，由SourceTransport同步返回AttemptOutcome；成功分支携带SourcePage，失败分支只携带受控AttemptFailure。HTTP先解析根协议，SDK按第17节解析正常返回对象，之后才进入同一SourcePage结构。一次尝试按“检查取消→准备请求及容量→执行网络→取得完整响应→解析实际fields/items→finally关闭本次连接/响应”进行。下一页或重试只在本次资源明确关闭后开始；不能把任何异常当空列表。

普通Pro的HttpProTransport采用标准库http.client.HTTPConnection/HTTPSConnection。按已核验binding和http_endpoint发送api_name/token/params/fields JSON，不自动重定向、隐藏重试或TLS降级。URL是否带api_name路径由固定mapping说明，不由业务拼接。

源请求Decimal用精确JSON number表示，不先转float或改为字符串；字符串转义复用标准库JSON规则。参数仅接受契约允许的有限类型，禁止NaN/Infinity/任意对象。内部不再需要带类型标记的进程传输编码，HTTP请求和业务结果分别保留各自已定义表示。

10.2 超时与取消：同步调用的实际保证

HTTP连接默认5秒、单次读取30秒；进入本次源调用时记录45秒请求期限，在每次I/O前后及接收块间检查，已建立socket的等待取当前阶段超时与剩余期限的较小值。完整响应取得后，本地解析或排序不因该网络期限触发重新下载。不得把45秒扩为整个任务或业务处理总时长。

没有额外线程/进程可以强行打断同步函数。操作系统DNS解析、SDK内部未暴露的阻塞等不一定受这些检查立即控制，不能承诺任意调用到45秒必退。取消同样在安全位置生效：进入unit/页/尝试、退避分段等待、HTTP接收块间、排序块间和交付前后。正在阻塞的I/O要等返回或网络超时；SDK必须提供明确超时和取消检查位置，不能把其不支持的能力写成已支持。

例如请求刚进入30秒读取等待，5秒时业务提出取消，组件可能还要等该次读取返回或超时，再停止；不再承诺2秒内强制终止。业务框架直接使调用栈抛出中断异常时也执行finally，保留原异常；业务进程被系统强制杀死时组件不承诺运行收尾，资源交操作系统回收，不存在需另外杀掉的组件请求子进程。

按下载过程解释停止

以下载某一天全部股票为例：需要两页，第一页6000行，第二页100行。

  1. 10:00:00，下载器发出第一页请求，正在等Tushare回复。
  2. 10:00:03，业务收到“停止本次任务”，记录停止要求。请求已经发出，下载器此刻还没有从等回复的那一步返回。
  3. 如果10:00:07收到回复，下载器回到自己的处理步骤，检查到停止要求，关闭本次连接，丢弃尚未交付的unit，不请求第二页，也不进入重试。
  4. 如果一直没有回复，则按已经设置的网络等待超时结束这次等待，再检查停止要求并结束；不能把取消当普通网络失败继续重试。此前已交付且由业务保存的数据不受影响。

所以“停止”可以表示收到要求后不再继续下载；它不保证把已经发出去、正在等回复的这一次请求立刻打断。如果业务直接结束自己的进程，下载器也随这个进程结束，不会另留下一个下载子进程。此同步停止方式已由管理员2026-10-21确认；例子不是已运行验收。

10.3 删除进程及通信设计

原RequestSupervisor/worker、匿名管道、分帧/ACK、父进程存活通道、FD传递、TERM/KILL/wait、进程启动/传递超时及父子RSS统计全部撤销。源响应不经过跨进程序列化。SDK若正常返回DataFrame，允许按原API接收，再转成统一记录；这不是额外制造的无用表格。SDK返回对象、转换中的统一记录和临时引用重叠期均计入当前unit，转换完成后释放返回对象；不得在组件另外造一份无用途的DataFrame。

10.4 响应解析，区别于业务检查

统一SourceResponseParser检查明确协议：HTTP状态、整数且非bool的code、data、非空且不重复的实际fields及items行列表；每行值数必须与实际fields对应。HTTP429/5xx先分类，错误HTML不当成功JSON。无有效响应字段有限重试；确定列值数量矛盾按SOURCE_PROTOCOL失败。

源成功少业务列但字段和值可以对应时仍交业务；不补列、改值或对比主键。合法空响应必须有明确成功、有效fields及items=[]。重复JSON键、非法JSON、NaN/Infinity和不能表达为SourceScalar的嵌套单元格明确失败，不静默转字符串、补NULL或丢值。多余根层执行信息不混进业务记录。SDK约束见第17节。

10.5 页与重试通知的位置

成功响应完成协议解析、容量检查和本次网络资源关闭后，先检查取消；通过后PageDownloader确定是否采纳，更新unit条数并发布PAGE_COMPLETED；父探测也按一次成功响应通知，但page_accepted=False且不计入unit条数。通知后再检查取消，再推进下一页或排序。若请求返回时已取消，不再发页成功通知或安排重试；已经发生的请求和成功响应事实仍计入统计，不把观察通知是否发生当成请求是否发生。通知不放进网络尝试的异常捕获中，不能因通知失败重发成功页。

可重试源失败且仍有下一次尝试时，先完成本次资源关闭并检查取消，再固定同页参数与下次尝试号/最早重试时刻，发布RETRY_SCHEDULED；随后再检查取消并按剩余退避时间等待。若关闭失败则不通知已安排重试、不重发。回调耗时不重置退避时刻，不计入45秒网络期限；真正开始重试才增加retry_count。取消、不可重试错误或尝试耗尽不伪造“已安排重试”通知，最终错误照常抛给业务下载线程处理。

11.1 普通分页的逐步规则

  1. 固定本unit过滤、完整fields和本接口有效页大小。offset初始值来自契约，不从业务请求读取。
  2. 成功响应按原记录数判断页长；少业务列、重复键、相同页内容均不能改变这次计数。业务排序发生在全部下载结束后。
  3. 失败仅重试原页参数；成功才推进。可靠total/next_offset由契约明确对应字段、含义和校验规则；没有可靠依据不自行猜下一页标记。
  4. 到终点后停止：满页后空页、多个满页后短页都支持。不能因为页数、请求总数或任务耗时到某个旧阈值就失败。
  5. 来源变化导致翻页间不是一致快照时保留来源事实，不跨页去重或声称数据版本一致；业务自行判断覆盖和复权业务。

11.2 时间拆分的连续性

日级闭区间示例：[start,end]按mid=start+floor((end-start)/2)分为[start,mid]和[mid+1日,end]。只有契约明确的日级闭区间才用这个公式；其它粒度/开闭范围由对应已登记策略提供相邻边界函数，必须证明无重叠或遗漏。不能按主键去重补救错误边界。

用显式栈维护未完成子范围，先压右再压左，避免递归栈随长历史增加。一个范围的首请求满页且能拆时释放父响应，再处理子范围；不能同时保留父范围6000条和两份子范围重复记录。最小范围首次满页转正常分页，沿用首响应，不重新发第一页，也不改变unit身份。取消在每个范围/页/重试及合并前后检查。

通用机制的最小范围满页继续分页及代码测试属于本组件；namechange专项真实源验证依管理员决定仅留TODO，本LLD不另设它的验证安排。

accepted_page_count / empty_page_count最终采纳的叶范围/正常分页页数，以及其中的0行页数。确认终点的空页计入采纳页与空页，但row_count增0。
row_count最终交付的全部记录数，不去重；父探测和失败尝试的部分记录不重复计入。父6000仅探测，左右4800和4700，最终9500；不是15500。
split_count / terminal_summary发生拆分数、正常终点方式、范围全部完成标记和必要末位置。只保留汇总/当前范围，不保留全任务每次请求明细。
delivered_units / total_units完整返回的unit数和按输入计算的总数。只表示下载交付，不表示业务入库或发布。0个unit总数/完成量均0，不伪造100%有数据。

所有计数是事实，不是账户额度/请求预算。累计计数可随任务增长，明细存储不随历史请求次数无限增长。最后错误仅保留当前页有限尝试详情；进度只保留最新状态，终点摘要保留必要计数和最后位置。

页通知只报告请求事实，不交付该页数据。父探测被弃用时page_row_count仍报告收到的条数，page_accepted=False且unit_row_count不增加；采纳叶页/普通页标记True，包括尾部空页。时间二分动作不单独发布通知；由它产生的实际成功响应或重试仍按统一事件通知。首满页转offset时不重发该页通知，记录也不重复计入。

通知方法抛普通异常，不进入上述错误分类或网络重试；仅在本session保留回调失败次数和最后一次异常类型，不能附原异常消息、traceback、token或原始响应，不新建回调错误码。通知不重试、不补发。PAGE/RETRY回调抛DownloadCancelled按取消传播；UNIT完成回调抛它则按§21.8先交当前完整结果再停止，不记普通通知故障。KeyboardInterrupt/SystemExit/GeneratorExit仍按原中断传播。通知方法的慢执行由业务负责，组件不承诺强行中断它。

本次编码审计补齐的错误来源和关闭优先级

SourceTransport把其实际I/O或已核验SDK调用产生的已知失败转换为AttemptOutcome.failure，只保存标准数字码、可选HTTP/源状态、Retry-After和脱敏原因类型。业务is_cancelled、回调、解析后的本地实现及写入异常不经过这种转换。RetryPolicy检查返回值，不使用包住整条下载的except Exception来推断错误来源。

关闭失败禁止重发：即使主失败是本可重试的网络错误，只要本次response/connection/SDK资源关闭也失败，仍保留主错误并附cleanup_errors，但本次重试资格关闭，直接结束；成功响应伴随关闭失败则CLEANUP，不能先发页成功通知。关闭每一个自己拥有的句柄都要尝试，不能第一个关闭报错后跳过其它句柄；也不能让关闭错误盖掉业务/取消/源主异常。

实际字段和值，及分类请求说明

SourceRecord/UnitResult为frozen/slots模型；集合冻结，同样的实际fields在unit内引用同一tuple。不以完整契约补NULL，不构造全列并集；缺某字段和字段存在但值None可区分。record.as_mapping()只按需生成该条实际字段和值，不事先为全unit另建dict副本。

多个分类组合仍属同一完整契约时，request_inputs按固定展开顺序保存非凭据的业务过滤说明，request_input_index指向它；各页/内部子范围沿用对应索引，排序也保留。没有枚举也有一份说明，空响应保留已完成的组合说明。不把token/URL/页号/内部时间拆分边界加入该说明，也不替源数据补分类列。不能混入不同接口或不同契约的记录。

HTTP原始JSON用parse_int=int、parse_float=Decimal解析，null→None；字符串、负数、布尔及日期源字符串不变。Decimal不经过float。只要实际值能按SourceScalar正确表达，即便与业务期望类型不同仍交业务；非法JSON数值或结构按协议错误处理。SDK必须满足同等保真；其正常返回对象允许存在并计入容量，但不能把已丢精度的DataFrame再转回Decimal并宣称恢复原值。无法证明某方法满足源值/NULL规则时，该方法不能登记为支持，不能为它改写SDK或默默放宽统一输出。

2GiB保留，但只核对本实例当前unit

UnitMemory只登记当前unit拥有的源响应bytes/文本、解码临时dict/list、已采纳记录、待采纳页、字段形状、请求输入说明、行索引、排序键/引用容器及容量记录自身；没有父子两份副本、管道帧、ACK或进程内存汇总。宿主业务已有对象、只读契约、解释器固定依赖及已交付结果不归本unit。业务保留多个结果的占用由业务管理。

继续采用前稿的功能检查办法：分配前核对“已持有对象+预计本次分配+预留”≤2147483648；不预分配2GiB、不采样进程RSS、不开展内存测量。采用sys.getsizeof及明确有限类型递归成员计数，同进程共享引用按对象身份只算一次，memoryview和底层缓冲分别计；字段/说明/登记表本身也计数。登记表不沿自身引用再次重扫所有历史记录；每页增量登记，丢弃和移交时撤销，不形成逐页重扫的平方成本。最新通知摘要占固定小空间；业务自行保留的摘要/结果及回调内部对象由业务负责，不在组件建立通知历史。

直接HTTP单次响应最多64MiB，按64KiB块接收，接收前检查容量；完整解码前沿用原始长度64倍的保守预留估算，并把128MiB工作预留包含在2GiB内。解码后以实际对象计数替代估算。64倍是前稿估算，未经测量，不是解释器硬保证；空unit也可能在约30MiB源JSON时提前拒绝，不能承诺64MiB响应一定可用。错误详情区分预计不足和实际超限，但共用CAPACITY。

排序前为键、引用容器和最终tuple重叠期预留；容量不足在交付前失败，不丢字段/股票、不缩unit、不改文件输出、不重新请求。MemoryError同样为本地CAPACITY。检查不是操作系统隔离，宿主保留结果和库内部不可控分配仍可能造成额外压力；SDK内部接收/生成返回对象不受本组件逐块检查控制，须按第17节逐方法核验，不把HTTP的64MiB接收保证套给SDK；各实例合计没有4GiB或两个unit的保证。后续真的遇到容量问题再按授权调整，不先压测。

14. 输出单元：排序、一次交付和进度

时间顺序

按点模式的unit由输入阶段时间升序；历史范围unit内部按契约指定源时间字段稳定升序。时间比较只产生排序键，不改原记录的日期/时间值；同时间保留来源到达次序。缺时间、NULL或无法比较的记录保留原内容和相对顺序放unit末尾。无时间维度保持来源及枚举拼接顺序，不造时间或业务排序。

每4096条建立排序块，块间检查取消，以稳定合并完成整unit排序；键、引用块和最后tuple均计入容量。取消或排序失败不返回部分结果。不同对象各自为unit时，不把它们打散成全任务时间排序。

结果使用期

完整unit下载和排序/冻结完成并通过最后一次取消检查后，先更新completed_units/completed_row_count并发布UNIT_COMPLETED，再更新实际交付计数并返回结果；不等待业务保存确认。普通通知异常不阻止返回；通知中直接取消/中断的处理见下文。交付后的取消不能撤销已返回的结果或计数。组件撤销对该明细的额外持有并移交业务；不等待业务确认保存，也不预取下一unit。业务持有的结果在close后仍可读，不清空或改写。只有再次next才开始下一unit。业务保存报错或主动break时，with关闭当前session，停止后续下载；不重试业务或回滚之前已保存的unit。

14.2 三种通知的准确时点

通知触发时点数量与边界
PAGE_COMPLETED一次成功响应已完整解析、网络资源关闭，且已确定是否采纳后成功普通页、叶页、尾空页和父探测各尝试通知一次；失败的请求不发成功页通知，首次页复用不再通知。

不单独设置时间拆分通知，不增加任务开始/结束、心跳或每秒回调。零unit任务没有上述事件，以会话摘要确认0个unit结束。已注册时所有三种事件按顺序通知，不合并、抽样或节流掉unit完成通知；未注册则只维护最新摘要，不调用业务、不存历史队列。

14.3 通知执行、异常与停止

DownloadSession为本次会话建立一个ProgressReporter，持有回调引用、sequence、最新快照、通知失败计数及最后一次异常类型；它是download_progress.py内的普通对象，与公开不可变DownloadProgress模型分开，不新增单元或后台执行。会话把同一Reporter传给PageDownloader；RetryPolicy只决定重试和可取消等待，不直接通知业务；SourceTransport只返回源响应，不调用业务回调。页采纳事实更新后由PageDownloader发布页事件；RetryPolicy决定同页重试后，由PageDownloader发布重试事件；UnitOutput返回冻结的完整结果后，由DownloadSession更新完成量并发布unit事件，再返回业务。publish先按这些执行事实生成含下一个序号的冻结快照，生成成功后才更新序号并替换最新一份，再可选调用业务；回调失败不回退序号或计数；通知故障记录自身也不调用通知或重发源请求。poll直接读取该最新快照；初始化时为None。关闭会话释放回调引用，不清空业务已收到的不可变对象或summary；不保留通知历史。

download_progress.py中的ProgressReporter在当前调用线程中先更新最新快照，再直接调用on_progress(snapshot)；不创建线程、锁或通知队列，不等待业务保存确认。快照生成/更新及回调中的普通Exception只影响观测：生成失败保留上一份可用快照，回调失败保留本次已生成快照；在可记录时增加progress_error_count及保存last_progress_error_type；既不重发源页，也不重试通知或丢弃已完成结果；原中断和PAGE/RETRY明确取消继续传播；UNIT完成回调取消按§21.8转停止意图并交付当前完整结果。业务必须让回调快速返回，避免在其中写库、做慢网络操作、等待其它线程/进程或直接更新页面。组件无法强制中断慢回调。

PAGE_COMPLETED/RETRY_SCHEDULED回调结束后检查取消；若已停止，不再发下一页或重试，未完成unit不交付。UNIT_COMPLETED时完整结果已准备好，普通回调异常不阻止返回；该回调调用session.cancel()或抛DownloadCancelled，均按§21.8已确认规则先交当前完整结果，再停止后续unit。若当前已是最后unit，正常耗尽/退出按SUCCEEDED，不再检查取消。KeyboardInterrupt/SystemExit/GeneratorExit继续保留原中断，不为了交付而吞掉。

14.4 最新摘要与接收进度的业务代码

只在三种规定事件发生时生成并替换进度快照，不额外每秒通知。session.poll_progress只供拥有实例的调用线程读取最后事件快照，不供其它线程/进程直接读取；快照保留事件发生时的值，不在返回结果后改写delivered_units，当前实际交付数以summary为准。回调、结果处理和异常处理都在调用线程，业务可以就地处理摘要；若其它线程或进程需要它，由业务通过已有办法传递。组件不写业务状态表、文件或TaskRun，不建通知历史。每次回调的耗时在finally累加到summary.callback_elapsed_seconds，包含失败/完成回调；不反写已冻结UnitStatistics。会话elapsed包含两次next之间的业务等待，不作为源网络期限。

摘要大小与事件事实

4KiB以固定字段的无空白UTF-8 JSON表示字节数计，IntEnum编码为数字、只读定位模型编码为固定字段；它是快照生成检查，不是结果保存或业务日期转换。超限只使本次通知生成失败并记脱敏观测错误，不能截断业务输入、修改源值或中断下载。未注册回调也不保存历史。page位置、attempt_number等在UNIT事件必须为None；current_scope切回原unit完整范围，不能拿最后子范围冒充整个unit。

UNIT回调发生在返回前，completed_units已包含当前unit，delivered_units还不包含它；完成回调中的summary同样只显示已发生交付。回调结束、符合最终交付规则后，在return前增加实际交付量；poll仍保留原事件时点的不可变值，不原地改成新计数。completed_row_count只在完整结果准备好时增加一次，采纳页只增加unit_row_count，重试/父探测都不得重复计入。

15. 串联、停止、关闭与重启续跑

session状态允许动作和终态明确边界
CREATED进入with完成静态校验→READY；未进入直接close且未取消→STOPPED，已cancel则CANCELLED。创建时不发网，失败不缓存活动标记。
READY / RUNNING仅READY可next；调用期间RUNNING，完成后返回并READY；全部已交付时标记download_complete，正常退出为SUCCEEDED。RUNNING中重入next报INPUT且不启动另一请求；0个unit不伪造结果。
STOPPED / CANCELLED未交完时正常break/close→STOPPED；取消检查确认→CANCELLED。不开始下一请求或unit；未完成buffer丢弃；全部已交付后正常close不误记提前停止。
FAILED来源最终失败、本地处理失败或尚未关闭时with接收到业务异常→FAILED；已关闭则保留首次终态并传播新异常。保留原错误；下载结束与业务提交分开。
已关闭上述终态和close幂等；保留summary与已交付结果。该session不可再次进入；同实例可创建下一个session。

关闭顺序与异常

停止新请求→当前调用可返回时退出执行→finally关闭本请求响应/连接和SDK实例资源→释放未交付buffer/排序对象→清除本实例活动标记→形成摘要。close重复调用无副作用，不关其它实例或宿主业务连接；本地资源关闭不触发网络重试。

已有业务/源/取消异常时保留主异常，附有界脱敏cleanup_errors，不让清理异常覆盖它；无原异常但关闭失败则CLEANUP，不能报成功。业务直接中断调用栈时也执行finally；强制杀进程不承诺Python收尾。没有SIGALRM、进程级信号更改、fork钩子或强制结束请求进程的方案。

取消检查不得包在来源重试捕获里。外部业务取消检查本身失败时保留原业务异常，不把它当暂时网络错误；进度和业务结果处理仍分开。源请求正在同步阻塞时遵守第10节等待边界，不能用close伪装已立即停止底层调用。

恢复边界

运行中临时失败重试当前页；业务进程重启后，未完成unit从第一页重新下载。组件无页缓存、恢复文件或业务提交记录。业务依据正式持久化事实排除已保存unit；不能把delivered_units当提交清单。示例D1已保存、D2第2页失败：D1不回滚，D2重启从第1页，D3本次不开始；D2交付但业务未保存也不能当已完成。

初始化、最后一个unit和关闭的具体口径

实例只保留自己的当前session引用。进入第二session失败，只释放第二session自己的准备资源，原活动引用不变；第一个仍能顺序继续。来源失败、取消、自然耗尽和close都按所有者清除引用，随后同实例可开新任务。终态再次next仅结束迭代，不重复请求；已关闭session不能再次进入。

total_units在静态准备完成时按冻结输入计算。最后一个完整unit实际返回时即将download_complete置True，不要求业务额外next一次才能知道全部下载完成；零unit在合法输入检查完成后同样为True。无主异常和关闭失败时，正常退出/close按全部已交付→SUCCEEDED、未交完且已cancel→CANCELLED、其余提前退出→STOPPED排序；不再把已提出取消的退出写成STOPPED。summary不把任何一次交付算成业务提交。

下载完成事实与退出原因分别保存：若最后一份已返回后业务保存抛错，with仍原样传播业务异常，session状态FAILED，但download_complete=True，已交付计数和结果不清空；若第二份unit下载失败则download_complete=False。清理失败且没有主异常时按CLEANUP失败，不能把“下载完成”冒充“关闭成功”。cancel()只记停止意图，检查确认前不宣称底层调用已经终止；安全检查一旦确认取消，不再继续页或unit；完整unit通知中设置停止标志或抛DownloadCancelled，均按第14.3节返回当前已完成结果后停止后续领取；最后unit已交付则正常完成。

非with显式__enter__后直接finally close只能管理资源；若业务处理失败，组件无法由close推断业务异常，调用方不能把该session摘要当业务任务成功。需要组件在退出时记录业务异常，应使用with。该区别不增加业务提交回调或持久化记录。

业务下载线程与回调的收尾要求

拥有实例的调用线程负责它的完整生命周期，业务负责选择执行位置。DG在执行资产的线程直接捕获结果/异常；页面场景由业务创建B，并接收B传来的摘要/错误，不能假定线程异常自动抛到页面线程A，也不能在页面响应路径join整个任务。业务另起进程时在该进程内创建实例和回调，业务负责消息、退出及异常接收。组件finally只关闭自己拥有的资源，不管理业务线程/进程或通信。

PAGE_COMPLETED及RETRY_SCHEDULED通知不改变完成unit数；UNIT_COMPLETED只把已经完整准备好的unit计入completed_units及completed_row_count，在return语句前的最后交付步骤计入delivered_units和原summary交付行数；不是尝试在return之后写不可达代码。通知成功不意味着业务保存成功。普通通知异常保持运行；PAGE/RETRY回调抛DownloadCancelled时停止，保留已发生计数和既有业务结果；UNIT两种取消按§21.8先交当前完整结果再停后续unit，最后unit已交付则成功。KeyboardInterrupt/SystemExit/GeneratorExit原样传播。其它线程/进程提出的停止要求，由业务传递后供调用线程内is_cancelled读取；不能跨线程/进程调用活动session.cancel/close。

关闭的编码约束

准备前summary.total_units=None、download_complete=False；合法输入准备完成后才设置明确总量，0个unit单独确认完成。_closed是资源收尾事实，与SUCCEEDED/FAILED/STOPPED/CANCELLED原因分开，不能用一个CLOSED值覆盖原因。close在READY/CREATED或终态执行；next/回调仍在执行时的外部close及显式__exit__先报INPUT，内部异常收尾调用独立的_finalize，不从内部绕入公开close。

_finalize按句柄所有权逐项关闭、释放未交付对象、清除自己持有的实例引用并生成摘要；重复调用不重复关闭或改变首次终态。若for已自然耗尽并完成关闭，随后with内部其它业务代码抛错，仍原样向外传播，摘要保留此前下载终态；若业务保存错误发生在最后unit返回后、下一次next耗尽前，则按既定FAILED且download_complete=True记录。已有主异常时只记录关闭错误并让原异常继续；源失败附关闭错误不再重试。__exit__返回False，不能因关闭错误替换业务原异常，也不把原异常序列化进summary。完成回调两种取消的分支按§21.8已确认规则；无主异常时，完整交付优先于取消标志：全部已交付为SUCCEEDED，尚有unit且已提出取消为CANCELLED，其余正常提前退出为STOPPED；关闭失败仍报CLEANUP。

16. 完整例子：业务下载线程、分页重试通知和两次unit交付

daily的11字段、trade_date与6000条说明沿用本地源文档27。以下日期/页数及通知为可手算人工示例，不是本轮源实测或已经运行的组件；正式登记仍需对应契约/mapping与有界源证据。

# 页面场景业务示意，未运行；通知通信/保存方法由业务自己实现。
from threading import Thread

def on_progress(progress: DownloadProgress) -> None:
    post_progress_to_main_thread(progress)  # 快速返回，不在这里刷新页面或等待A

def run_download():  # 业务下载线程B
    try:
        downloader = TushareDownloader.load()
        task = DownloadTask(contract_name="tushare.daily@1", mode=DownloadMode.BY_POINT,
                            points=("2026-10-13", "2026-10-12"))
        with downloader.download(task, on_progress=on_progress) as download:
            for result in download:
                verify_and_save(result)  # 业务自己的归一化、校验、事务与保存
    except DownloadCancelled:
        post_cancelled_to_main_thread()  # 业务传回取消结果
    except Exception as error:
        post_failure_to_main_thread(error)  # 业务接收B的失败，不等待自动传播到A

# 业务主线程A负责启动；页面更新代码继续在A运行。
download_thread = Thread(target=run_download, name="tushare-download")
download_thread.start()
# 不在页面响应路径join等待全任务；线程退出管理由业务负责。
顺序组件事件/业务动作条数与完成量
1. 业务线程启动A创建B；B中load并注册on_progress，创建两个日期unit，先12日后13日。初始化不发通知；总unit数2。
2. 12日第一页offset=0成功6000，关闭网络资源并采纳，回调PAGE_COMPLETED。page_row_count=6000，page_accepted=True；unit_row_count=6000，completed_units=0，completed_row_count=0，progress_percent=0。
3. 12日第二页首次失败offset=6000收到503；关闭资源后回调RETRY_SCHEDULED，再按剩余1秒退避。error_code=1203，attempt_number=1，next_attempt_number=2；request_count=2，retry_count=0；unit条数仍6000。
4. 原第二页重试成功同样offset=6000、全字段，实际重发后得到100；回调PAGE_COMPLETED。request_count=3，retry_count=1；page_row_count=100，unit_row_count=6100；完成unit数仍0。
5. 12日完整unit准备好全部页到终点并排序/冻结；回调UNIT_COMPLETED，随后一次返回6100行。通知中completed_units=1，delivered_units=0，completed_row_count=6100，unit_row_count=6100，progress_percent=50；实际返回后delivered_units=1。
6. 业务处理B内verify_and_save；业务保存后再次next才开始13日，组件不预取。业务保存失败则异常由B接收并传回A；不能触发来源重试或回滚12日已保存事实。
7. 13日合法空页有效fields且items=[]；回调PAGE_COMPLETED，再完成排序/冻结后回调UNIT_COMPLETED。页条数/当前unit条数为0；完成通知中completed_units=2，delivered_units=1，completed_row_count=6100，progress_percent=100；随后返回一个0行unit。
8. 正常退出B中关闭会话，业务负责线程退出与页面状态传递。delivered_units=2，summary.row_count=6100，request_count=4，retry_count=1；这些不代表两天均已业务保存。

注册时事件序列为PAGE_COMPLETED → RETRY_SCHEDULED → PAGE_COMPLETED → UNIT_COMPLETED → PAGE_COMPLETED → UNIT_COMPLETED，共6次回调尝试、2次完整数据交付。普通回调异常也不改变这4次来源请求和两个结果；该通知不补发。业务不注册on_progress时，来源请求与两个结果相同，外部回调调用次数为0。时间拆分无单独事件。

另一个业务进程在其实际调用线程内创建自己的实例；无需一律另开下载线程。同进程多个调用线程也各用独立实例，组件不控制数量或整体频率，关闭一个不动另一个。以上A/B示例仅用于页面场景；本轮没有启动线程或实现业务通信。

17. SDK：每个业务进程正常创建和调用自己的客户端

正常用法是各业务进程创建自己的下载对象，下载对象按固定mapping使用HTTP或创建本进程的SDK客户端。当前已读源码的DataApi构造函数把显式token、timeout保存在客户端实例中；DG现有TushareResource.call也是每次创建客户端再调用。没有依据为这种各进程独立调用额外设计进程锁，也不由“不需要额外加锁”推导同一个客户端可任意多线程同时使用。

澄清前版错误表述：“SDK全局修改”指我在旧LLD中拟议的SdkRawProBinding：为了拦住SDK生成DataFrame，临时替换SDK模块引用的requests对象。这是我提出、尚未实现的做法，不是Tushare SDK正常使用所要求的步骤，也不是现有DG已经实施的改动。该做法撤销，不再把它列作SDK自身的安全问题或待管理员拍板事项。

代码mapping选择普通Pro的HTTP实现或已核验的具体SDK方法，业务不选方式、失败不自动切换。用SDK就按其正常入口显式传入本实例token/超时及方法支持的参数，不调用set_token改变默认凭据，不临时替换requests、不改SDK模块/类的行为，不加锁包装这类改写。

适配接口职责明确边界

23.3.1 同一session如何让全部步骤读到停止要求

内部SessionControl位于download_session.py，不作为公开业务接口；每个session在创建时各建一份。它保存requested:bool、业务检查函数引用，以及contract_name/version、task_id、stage、unit_id、DownloadScope、PagePosition和attempt_number等当前错误定位字段。cancel()只将这份对象的requested置True；原DownloadControl不被修改，所以两session即使使用同一个只读业务控制输入也不会互相取消。分页/RetryPolicy/HTTP或SDK/UnitOutput收到的是该session同一个SessionControl，内部参数用Protocol标注，明确声明raise_if_cancelled() → None、set_location(stage, unit_id, position, attempt_number) → None及error_location() → ErrorDetails；PageDownloader的同页重试直接调用第三个方法，不能在接口声明中遗漏。set_unit(unit)只由会话对具体SessionControl调用；底层不反向import具体session类。

raise_if_cancelled先检查requested，已置位便抛当前定位的1401，不再调用业务检查；否则调用业务is_cancelled，返回值必须严格bool。True时保存requested并抛1401，False继续；None、数字、字符串或awaitable为INPUT。检查本身抛普通业务异常原样结束，__next__中意外StopIteration按§23.9处理；这些都不进入来源分类。准备时检查control类型、检查函数和on_progress是否同步可调用，不试运行它们，不await、不建线程。

set_location仅更新本session的固定定位：会话开始PREPARE；每次尝试前SOURCE及当前页/1～4次尝试；安排退避前BACKOFF；排序前ORDERING；完整unit通知前UNIT_READY并清page/attempt；关闭时CLOSE但不改已经冻结的原错误定位。cancel在CREATED/READY/RUNNING均可置位，进入with不清空预先提出的要求；closed后cancel不操作、不覆盖终态。全部结果已交付时，__next__/正常关闭先处理完成事实，不再调用取消检查，保持§21.8决定。

close和显式__exit__在_in_next或Reporter.in_callback时都先拒绝，且不改任何资源或状态；正常with的__exit__发生在next已经返回/抛出并完成finally之后。内部异常只走_finalize，不借公开__exit__/close绕过检查。_finalize清业务检查函数、回调及原始task/control输入引用，保留小型定位/计数和最新不可变摘要；它不修改业务提供的对象或已交付结果。

set_unit从当前DownloadUnit生成小型DownloadScope，不保存记录或完整输入；error_location()每次返回新的不可变ErrorDetails定位值，尚未解析契约/生成unit时对应字段为None。RetryPolicy.to_download_error(failure, attempt_number, *, location)只把受控失败合入这份定位，再生成标准错误；不持有全局会话、不反查unit_id、不从最后进度通知猜当前范围。SOURCE时source_position是实际页/子范围，current_scope仍表明原业务unit对象/点/范围；UNIT_READY清页位置/尝试号。即使首请求失败、尚未产生回调，业务也能知道哪个对象/日期出错。

六模式基础数量分别为1、points数、objects数、points数×objects数、objects/object_ranges数、1；枚举被契约规定独立为unit时再乘组数，组内多请求则不乘。对象范围模式的每个对象/范围始终一份，时间拆分不修改这个总量。重复枚举值也在发网前拒绝；省略使用契约默认，显式空仅按对应空输入规则处理。

内容摘要与unit_id的编码在contract_registry.py定义唯一函数。源契约名称/版本、字段顺序/类型/含义、参数、模式、分页、时间/排序规则全部参与规范内容；本地证据路径/存储映射和运行配置作为附件，不进入源内容比较或摘要。映射键按字符序，序列保持有语义的顺序；源标量用类型标记表示，例如字符串[1,value]、整数[2,十进制字符串]、Decimal[3,sign,digits,exponent]、布尔[4,value]、空[0]，不经float。规范JSON用UTF-8、无空白、不允许NaN后SHA-256；这仅用于稳定身份，不是网络请求格式。unit_id只包括本unit执行范围和契约摘要，不含其它unit、ordinal、PID、页位置或仅用于检查的外层日期区间。业务输入字典排列变化不改身份；源契约/真实范围变化必须改身份。

23.5.1 每次尝试的持有范围与事实计数

prepare只验证并保存binding、配置/契约引用和SDK方法依赖；每次fetch_page再创建本次连接/响应或正常SDK客户端。SDK构造必须已经核验不暗中发网；构造失败不计请求。HTTP发送方法或已核验SDK方法调用前，仅调用一次counters.mark_sent(attempt_number)。完整协议解析、容量检查及SourcePage构造成功后，调用一次mark_response_success；再执行finally关闭。关闭失败、其后取消或父探测弃用都不撤销已经发生的成功响应计数；原响应不完整、无有效字段或协议失败时不加。successful_response_count现在同时保存在unit统计和DownloadSummary，失败/取消后也可读。

只有本次资源关闭成功的SourcePage才返回成功Outcome供采纳；有关闭失败时按原规则生成failure，但不回滚已发生计数。SDK客户端不跨尝试复用，依原正常API释放；无close方法不虚构close。session末尾的transport.close只处理仍由自己拥有且未关闭的句柄，不再次关闭已完成尝试，不关闭别的实例。last_cleanup_errors每次尝试起点清空，累计摘要不重复登记同一次关闭失败。

内部计时统一使用同一clock.monotonic，UTC更新时间另取clock.utc_now。request期限只覆盖本次网络调用，receive_seconds计实际网络接收/已核验SDK调用段，waiting_seconds只计退避等待且不含通知，sort_seconds只计排序，unit.elapsed_seconds从本unit开始到冻结；会话elapsed_seconds从创建session到当前/首次关闭，含两次next间的业务等待，关闭后冻结。callback_elapsed_seconds在回调finally中独立累计，取消/原中断也计入；不反写已冻结UnitStatistics。

23.5.2 HTTP异常与既有重试规则的对应

当前classify_tushare_error针对requests异常，不能把它的类判断原样搬到http.client后就宣称可靠性不变。仅在真正HTTP I/O捕获范围使用下表；取消检查、解析/容量、业务回调和关闭仍在各自范围处理。先按具体异常再按基类判断，不使用错误文字中的429/timeout提升本地错误。

发生的事情及具体异常固定处理独立反例与验收
实际连接/读取超时TimeoutError；连接重置/拒绝/中断等ConnectionError；对端未返回响应即断开RemoteDisconnected；接收不完整IncompleteRead1203，同一PageRequest有限重试。RemoteDisconnected同时继承BadStatusLine，必须优先识别为连接中断。丢弃本次不完整字节；关闭成功且未取消才可安排重试。T06/T14分别构造真实socket中断和明确异常替身；成功后仍只采纳完整页一次，次数按实际发送计。
有效Content-Length声明尚有数据，read1却提前返回空字节；或分块传输抛IncompleteRead前者显式识别1203，后者按上一行；不能直接把半份body送JSON解析并误报确定协议错误。分块传输按实际传输规则处理，不混用被其覆盖的Content-Length；合法无长度响应仍以正常EOF结束。T14用合法JSON前缀但少于声明长度的响应，证明不会把截断当成功或1205；不会保留半页。
非RemoteDisconnected的BadStatusLine、LineTooLong或已收到的确定HTTP/JSON协议错误1205，不重试；先分清没有收到完整响应与完整响应自身错误。其它HTTPException不一律当临时错误，未登记的来源错误按1501结束。T04/T06/T14覆盖坏状态行与连接提前断开的相反结果，不只按异常基类判断。
ImproperConnectionState（含CannotSendRequest/ResponseNotReady）、本地PermissionError/FileNotFoundError/ValueError前者为本地调用次序错误；后者按真实发生位置处理，原异常结束，不包装来源失败、不重发。SDK异常继续使用其单独核验的分类，不拿HTTP类反推。T06/T11证明本地异常带timeout或429文字也不重试；业务检查抛同名网络异常仍不是源失败。

socket.gaierror仅EAI_AGAIN表示已识别的暂时解析失败，按1203；其它未登记原因及证书校验失败不猜成临时故障，按1501不重试。仍遵守现有未知错误不盲重试的原则，不增加错误码、请求预算或自动更换地址。该对应表的异常继承依据为Python最低支持版本官方文档和本地标准库；是否正确执行必须由T04/T06/T14验证。

23.8 回调生成、序号、异常与计数

def publish(self, event, facts):
    try:
        candidate = freeze_progress(event, facts, sequence=self.sequence + 1)
        check_progress_json_size(candidate, max_bytes=4096)
    except Exception as error:
        self.record_observation_error(type(error).__name__)
        return
    self.sequence = candidate.sequence
    self.latest = candidate
    if self.on_progress is None:
        return
    started = self.clock.monotonic()
    self.in_callback = True
    try:
        returned = self.on_progress(candidate)
        self.reject_unexecuted_awaitable(returned)  # 只记录类型错误；不await或另开线程
    except DownloadCancelled:
        raise  # PAGE/RETRY传播；UNIT完成处转为本session停止意图
    except Exception as error:
        self.record_observation_error(type(error).__name__)
    finally:
        self.counters.callback_elapsed_seconds += self.clock.monotonic() - started
        self.in_callback = False

异常类型之外的原消息/traceback不记录；record_observation_error自身不调用通知，记录失败也不能改变数据行为。KeyboardInterrupt/SystemExit/GeneratorExit不是普通Exception，直接传播。源网络、业务取消检查与业务保存不放进publish的普通通知捕获中。合法回调返回None，任何其它返回值均不作为取消/重试/提交指令；不增加通知确认、补发或历史队列。

publish的候选快照生成失败不增加sequence；回调失败则序号已产生且不回退。UNIT前更新completed，UNIT回调后才在最后交付步骤更新delivered，因此两个完成量有明确差一语义。PAGE/RETRY不增加completed；snapshot不可修改，poll不隐式刷新已交付数。总量0时无事件且比例为None；最终源错误直接抛给调用方业务代码，不额外新造任务结束事件。

准备阶段用inspect检查回调和取消检查的异步函数/异步__call__，它们不满足同步契约，报INPUT且不发网。已注册同步回调若意外返回awaitable，Reporter不运行它；普通coroutine对象仅close以释放，再记TypeError观测故障，不改源请求/数据交付。其它返回值仍不作为控制指令。record_observation_error只保存计数/最后类型，自己不得调用外部日志或业务代码，内部记录失败也不得盖掉原异常。内部快照生成失败、回调普通异常各算一次对应观测失败，不增加源重试或事件补发。

回调准备检查只判断同步可调用及可取得的签名，不试运行业务代码：inspect.signature可用时，按一个位置参数绑定以检查on_progress，按零参数绑定以检查is_cancelled；参数绑定不成立为INPUT。没有可读取签名的内置可调用对象，不凭猜测拒绝，首次调用的普通异常按各自既定归属处理。已知异步函数/异步__call__仍准备阶段拒绝；意外返回的awaitable只记错误，不运行或切线程，仅关闭确认尚未启动的普通coroutine对象，不操作业务自己管理的Future/Task。

所有事件始终保留任务累计request_count/retry_count、total/completed/delivered、unit_row_count/completed_row_count及时间字段；不因为UNIT无本页信息就把累计重试次数置None。freeze_progress按表构造同一DownloadProgress并校验有限数值、不可变定位和事件字段组合，再做4KiB检查；内部生成失败仍只影响观测。RETRY的retry_delay_seconds为该次安排时最早重试时刻与当前单调时刻之差，不在回调结束后改写原快照；实际只等待余下时间。

23.9 next、取消和finally的串联

def __next__(self):
    self._require_next_allowed()  # CREATED/重入拒绝；终态StopIteration在工作try之外
    self._in_next = True
    self._status = DownloadStatus.RUNNING
    buffer = result = None
    try:
        if self.download_complete:  # 合法0unit或最后unit已交付：不再查取消
            unit = None
        else:
            self._control.raise_if_cancelled()
            unit = self._planner.next_unit()
            if unit is None:  # 静态总量仍有剩余，不能默默结束
                raise RuntimeError("下载计划数量与实际单元不一致")
        if unit is not None:
            self._current_unit = unit
            self._control.set_unit(unit)  # 只留小型对象/时间范围定位，不保留结果数据
            self._control.set_location(DownloadStage.SOURCE, unit.unit_id, None, None)
            buffer = self._pages.download_unit(unit, self._contract, self._control, self._progress)
            self._control.set_location(DownloadStage.ORDERING, unit.unit_id, None, None)
            result = self._output.finish_unit(buffer, self._contract, self._memory, self._control)
            self._control.set_location(DownloadStage.UNIT_READY, unit.unit_id, None, None)
            self._control.raise_if_cancelled()  # 完成通知前最后检查
            self._mark_completed(unit, result.statistics.row_count)
            try:
                self._notify_completed_unit(result)
            except DownloadCancelled:
                self.cancel()  # 唯一转换位置；当前完整结果仍交付
            self._detach_unit_from_component(result)
            self._status = DownloadStatus.READY
            self._mark_delivered(unit, result.statistics.row_count)
            return result
    except StopIteration as error:
        failure = RuntimeError("下载步骤意外结束，任务未正常完成")
        self._finalize(primary=failure)
        raise failure from error  # 保留原因，不能让for把业务检查错误当作正常耗尽
    except BaseException as error:
        self._finalize(primary=error)
        raise
    finally:
        buffer = result = None
        self._in_next = False
    self._finalize(normal_exit=True)
    raise StopIteration

notify_completed_unit传的只有摘要，不把result放进回调对象。普通通知异常已隔离；该回调中session.cancel()和DownloadCancelled统一留下本session停止意图，当前完整结果仍交付一次。尚有unit时，下一次next领取前确认取消并抛DownloadCancelled；先退出with/close也按CANCELLED收尾。已全部交付时先确认耗尽，不再调用is_cancelled，不抛新的DownloadCancelled；其它原中断和业务保存抛的取消不吞。detach只撤销组件引用，不修改公开结果或业务保存。最后一个结果返回前即确认download_complete，不要求额外next；进入with后合法0unit也可正常耗尽。

_finalize的固定顺序：确定主异常/停止原因 → 不再领取工作 → 逐项关闭实际拥有资源并收集有限CleanupIssue → 清未交付buffer/临时对象/容量登记 → Reporter释放回调 → 仅清自己的活动引用 → _closed=True并保存原因和不可变摘要。出现任何关闭错误仍继续后续关闭；有原异常保持原对象/traceback，没原异常但有关闭错误才抛CLEANUP。重复close不重做步骤、不擦掉计数；业务finally与源finally分层，不能重复发网络或重复交付。

23.10 错误脱敏、测试文件与开发顺序

AttemptFailure是无原Exception引用的数据，源端分类在对应catch中完成后离开catch，再创建/抛公开DownloadError，避免保留原__cause__/__context__；不能只写raise from None就声称对象链已清。源异常消息和完整响应不作为错误字段。普通业务原异常不修改，不给它塞源字段；__next__内意外StopIteration仅按§23.9作迭代器必要转换并保留原因，不作为来源错误；关闭问题存本会话summary.cleanup_errors。该实现兼容Python3.10，不依赖3.11的add_note。
