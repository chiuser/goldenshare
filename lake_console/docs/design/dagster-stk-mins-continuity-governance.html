Dagster 股票分钟线连续性治理专项方案

本文用于治理股票分钟线动态分区缺口导致的下游跳空问题。目标是让 raw、silver、qfq、qfq factor repair、前复权分钟线 MACD/KDJ daily 和 repair 都遵守同一个连续性契约：只要权威交易日历中存在未处理缺口，后续日期不得继续推进。

2. 事故复盘：6 月 15 日空洞如何放大

1. 交易日未注册 2026-06-15 是交易日，但 dg 未启动，股票分钟线交易日分区未注册。
2. 次日注册成功 2026-06-16 注册后，下游 sensor 选择“最新 registered date”。
3. raw/silver/qfq 跳过缺口 6 月 16 日继续推进，6 月 15 日空洞没有被当成 blocker。
4. MACD/KDJ 状态跳日 6 月 16 日把 6 月 13 日当上一状态日，技术指标递推被污染。
5. 后续 repair 才恢复 后续通过手工补注册、补数据、重算 qfq 和 MACD/KDJ 才恢复一致。
关键结论： 这不是单日运维缺口，而是系统契约问题。当前链路允许“权威交易日历存在应处理日期，但 dynamic partition 缺失”时继续处理后续日期。

4. 根因定义

根因一：DynamicPartitions 被误当成权威日历

dynamic partition 只是 Dagster 操作状态，表示“这个分区已注册”。它不能证明市场没有其它应处理交易日。

根因二：目标选择是 latest-driven

多个 sensor 都选择最新 registered date。这种策略适合只关心最新快照的资产，不适合有连续性约束的分钟线链路。

根因三：状态递推没有校验上一 expected day

MACD/KDJ 是状态递推资产，必须从上一真实交易日 state 递推。当前代码允许使用任意更早 state。

根因四：repair 范围从 registered set 推导

qfq factor repair 和 MACD/KDJ repair 都应覆盖 expected date range，不能只覆盖 registered date range。

5. 目标契约

最终口径： 股票分钟线链路以权威交易日历为 expected date source，以 dynamic partition 和 readiness 作为运行状态。 任何环节发现 expected open day 缺口时，必须停在最早问题日期，不能继续推进后续日期。

硬规则

  1. expected stock mins trade dates 只能来自 silver_trade_calendar 的 SSE 开市日，并受同日运行窗口和历史起点约束。
  2. cn_a_stock_mins_trade_days 和 cn_a_stock_mins_silver_trade_days 只表示 Dagster 已注册，不表示权威日历。
  3. 日常 sensor 目标选择必须改为 earliest actionable date / first not ready，不得再用 latest registered date 作为正式目标。
  4. 如果 expected date 未注册、未 ready 或 blocking checks 不通过，后续日期必须 skip。
  5. MACD/KDJ daily 必须要求上一 expected trade date 的 state ready；不得从更早 state 自动跳日递推。
  6. qfq factor repair 的 previous trade date 和 selected partition range 必须来自 expected calendar，并校验对应 silver/qfq 事实完整。
  7. MACD/KDJ repair 的 target dates 必须来自 expected calendar range；range 内任一日期缺失或不 ready 时 fail closed。
  8. run key 治理口径不变：不得解析 run key 反推 config，不引入 storage id，不新增散装手工 repair。
当前落地边界： 截至 2026-06-17，raw/silver/qfq 日常 sensor、MACD/KDJ daily run-status sensor、qfq factor repair op/helper 已按上述连续性契约改造。 MACD/KDJ daily asset write 与 MACD/KDJ repair op 仍未完成 exact previous expected state / expected range 改造，不能在文档中视为专项已全部收口。

6. 设计方案

6.1 新增连续性 gate/helper

已拍板新增一个股票分钟线连续性 gate/helper 模块。它不是 sensor、asset、op、check 或 run contract，而是被 sensor、run-status sensor 和 repair op 共同调用的生产门禁判断组件。

lake_console/orchestrator/src/orchestrator/defs/asset_guards/stk_mins_continuity.py

职责：

  • 从 silver_trade_calendar 加载 expected open trade dates。
  • 比较 expected dates 与 raw/silver dynamic partitions。
  • 返回 earliest missing registered date、first not ready date、previous expected date、contiguous ready frontier 等连续性判断结果。
  • 生成小而结构化的 cursor details，避免 cursor 存大数组。

放在 defs/asset_guards 的原因：它会被多个 sensor 使用，也会被 qfq factor repair op 和 MACD/KDJ repair op 使用。放在 defs/sensors 会让 op 反向依赖 sensor 包；放在 run_contracts 又不合适，因为它不是纯 run/cursor/metadata 契约，会读取交易日历、dynamic partitions 和 readiness 状态。asset_guards 当前已经承载 stock daily freshness guard、qfq factor repair status、MACD/KDJ repair gate 等同类“能不能继续生产”的判断能力。

6.1.1 连续性术语说明

这些术语不是新的业务 ID，也不是要写进 run key 的字段。它们是 continuity helper 给 sensor、run-status sensor 和 repair op 使用的判断结果，用来回答四个白话问题：日历上有没有该处理但没注册的日期、哪个日期最早没处理好、目标日期真正的上一交易日是谁，以及当前连续安全推进到了哪一天。

术语 白话含义 怎么计算 主要用途
earliest missing registered date
first_missing_registered_date		 交易日历里应该有这一天，但对应的 Dagster dynamic partition 还没注册。它是最早的注册缺口。 从 expected open trade dates 里，找第一个不在目标 partition set 里的日期。例如 expected 是 06-13, 06-15, 06-16，registered 是 06-13, 06-16，结果就是 06-15。 阻止后续 sensor 直接跑 06-16；分区注册 sensor 应优先补这个日期；cursor 和 skip reason 要把它写清楚，方便运营知道缺在哪里。
first not ready date
first_not_ready_trade_date		 这一天已经进入应处理范围，但对应资产还没 ready，或者已 materialized 但 blocking checks 没全绿。它是最早的数据处理问题点。 按 expected dates 从早到晚检查 readiness。第一个 materialization 缺失、check 缺失、check failed 或上游门禁不满足的日期，就是 first not ready date。 决定 sensor 的目标日期。raw/silver/qfq 不再找“最新日期”，而是找这个最早未完成日期；如果这一天是失败状态，后续日期全部停止，避免跳洞。
previous expected date
previous_expected_trade_date		 目标日期在权威交易日历里的上一交易日，不是 dynamic partition 里碰巧存在的上一天。 在 expected open trade dates 中找到小于 target 的最后一个日期。例如 target 是 06-16，交易日历里上一交易日是 06-15，即使 06-15 没注册，也不能退回 06-13。 给状态递推和 repair 使用。MACD/KDJ daily 必须要求上一 expected date 的 state ready；qfq factor repair 比较上一日复权因子时也必须用它，不能用上一 registered date 代替。
contiguous ready frontier
ready_through_trade_date		 从治理起点开始，所有应处理交易日都已经注册且 ready，连续安全推进到的最后一天。 从 expected dates 起点开始向后扫描，只要每一天都 registered 且 readiness 通过，就推进 frontier；遇到第一个缺注册、缺数据或 checks 不绿的日期就停止。 告诉下游“最多只能基于哪一天继续”。例如 frontier 是 06-13，说明 06-16 之前还有缺口，下游不能把 06-16 当成安全目标。
例子： 假设交易日历里最近三天是 2026-06-13、2026-06-15、2026-06-16， 但 cn_a_stock_mins_silver_trade_days 只有 2026-06-13 和 2026-06-16。 那么 first_missing_registered_date 是 2026-06-15， previous_expected_trade_date(2026-06-16) 仍然是 2026-06-15， ready_through_trade_date 最多只能是 2026-06-13。 这时任何 qfq、MACD/KDJ 或 repair 都不能继续把 2026-06-16 当作安全目标。

建议数据结构：

StockMinsContinuityStatus
  expected_start_date: str
  expected_end_date: str
  expected_count: int
  registered_count: int
  missing_registered_dates: tuple[str, ...]
  first_missing_registered_date: str | None
  first_not_ready_trade_date: str | None
  next_actionable_trade_date: str | None
  previous_expected_trade_date: str | None
  ready_through_trade_date: str | None
  blocked_reason: str | None

6.2 交易日注册：从当天注册改为补偿式注册

对象 现状 目标
cn_a_stock_mins_trade_days 18:00 后只注册今天。 按 silver_trade_calendar 补齐从起点到 latest completed open day 的缺失分区；同日交易日仍需 18:00 后才注册。
cn_a_stock_mins_silver_trade_days 19:45 后只看最新 raw registered date。 只注册最早 raw ready 且所有前置门禁 ready 的 missing silver partition；前面有缺口时不注册后续日期。

raw trade day 注册优先复用 build_trade_day_partition_registration_result(...) 的思想：交易日历驱动、单 tick 小批量补齐、cursor 可观测。已拍板分区 catch-up 可以小批量补，单 tick 上限按现有口径取 2；股票分钟线需要保留 18:00 窗口，不允许提前注册当日分钟线分区。

6.3 日常 sensor：全部改为 frontier-driven

Sensor 目标选择新口径 遇到缺口时
stock_mins_raw_sensor 从 expected raw trade dates 中找最早 registered 但 raw 未 ready 的日期。 如果 expected date 未注册，skip 并报告 first_missing_registered_date。
stock_mins_silver_trade_day_sensor 从 raw registered dates 中找最早 raw ready 但 silver 未注册的日期。 如果更早 raw date 未 ready，不注册后续 silver partition。
stock_mins_silver_sensor 从 silver registered dates 中找最早 silver 未 ready 的日期。 如果更早 silver materialized 但 checks 未绿，停止自动重跑，要求人工处理。
stock_mins_qfq_daily_sensor 从 silver contiguous ready frontier 中找最早 qfq 未 ready 日期。 如果 silver 或 adj factor 前置门禁缺失，停止在该日期。
stock_mins_qfq_factor_repair_sensor 从 qfq contiguous ready frontier 中找最早 factor repair status 未完成日期。 如果 qfq 未 ready 或已有 materialized check problem，停止。

6.4 MACD/KDJ daily：上一日必须是上一 expected trade date

run-status sensor 继续监听同日 stock_mins_qfq_daily_update_job 与 stock_mins_qfq_factor_repair_job 成功，但在提交 MACD/KDJ daily 前必须新增连续性门禁：

  • 从交易日历获取 previous_expected_trade_date(target_trade_date)。
  • 如果 target 是 baseline 之后第一个日常分区，可按既有 baseline 口径处理。
  • 否则必须检查上一 expected date 的 MACD/KDJ state readiness。
  • 如果上一 expected state 不存在，返回 SkipReason，不得回退到更早 state。
禁止行为： 不允许把 discover_latest_macd_kdj_state_path_before_trade_date(...) 的“任意更早 state”当作日常递推的上一状态。 该函数可以保留为低层文件发现能力，但正式 daily/repair 门禁必须先证明上一 expected state 存在。

6.5 qfq factor repair：上一日与范围必须来自 expected calendar

execute_gold_stk_mins_qfq_factor_repair(...) 已在 M8 改为接收 expected dates，previous date 和 selected range 不再从 registered partitions 推导。正式口径：

  • previous_trade_date 改为上一 expected open trade date。
  • selected_partition_keys 必须等于 expected range 内已注册且 ready 的完整集合。
  • 如果 expected range 中有日期未注册，直接失败且不生成 repair metadata；source qfq/silver 不满足既有事实检查时继续 fail closed。
  • repair metadata 中仍使用已完成的 upstream_batch_id 口径，不引入 event storage id。

6.6 MACD/KDJ repair：修复区间不能跳过 expected date

repair op 当前从 registered silver dates 得到 target dates。目标口径：

  • target dates 来自 expected_trade_dates[start_trade_date, repair_end_trade_date]。
  • range 内每个 expected date 都必须有对应 qfq source ready。
  • 上一 state 必须是 previous_expected_trade_date(start_trade_date) 的 state；没有则 fail closed，除非是正式 baseline 起点。
  • completion metadata 继续只写 source_upstream_batch_id。

6.7 Cursor 与可观测性

Dagster sensor cursor 应保持小而结构化。连续性状态建议只写摘要和样本：

{
  "target_date": "2026-06-15",
  "decision": "skip",
  "selected_count": 0,
  "blocked_count": 1,
  "details": {
    "expected_start_date": "2026-06-13",
    "expected_end_date": "2026-06-16",
    "first_missing_registered_date": "2026-06-15",
    "missing_registered_date_samples": ["2026-06-15"],
    "ready_through_trade_date": "2026-06-13",
    "next_actionable_trade_date": null
  }
}

这能让 UI 和 tick history 直接说明为什么没有提交后续 run，而不是只显示“最新日期已 ready”。

8. 测试与验收计划

必须新增或调整的测试

以下测试清单中，raw/silver/qfq/qfq factor repair/MACD run-status/qfq factor repair op 相关项已随 M1-M8 落地；MACD/KDJ asset write、MACD/KDJ repair op 和最终全量回归仍待后续阶段完成。

  • 交易日注册测试：停机错过 2026-06-15 后，下一 tick 先补 2026-06-15，而不是只注册 2026-06-16。
  • raw sensor 测试：registered set 缺 2026-06-15 时，不提交 2026-06-16 run。
  • 顺序保护测试：2026-06-15 run 未完成时，即使 2026-06-16 已经通过 catch-up 注册，也不得提交 2026-06-16 的下游 run。
  • silver trade day sensor 测试：raw 2026-06-15 未 ready 时，不注册 2026-06-16 silver partition。
  • silver/qfq/factor repair sensor 测试：选择第一个未 ready / 未完成日期，不选择最新日期。
  • MACD/KDJ daily 测试：target 2026-06-16 必须要求 2026-06-15 state ready；只有 2026-06-13 state 时 skip。
  • qfq factor repair 测试：上一 expected trade date 缺失时，不允许用上一 registered date 代替。
  • MACD/KDJ repair op 测试：expected range 内缺日期或 qfq source 缺失时失败，不写 completion metadata。

9. 停手机制

实现阶段遇到以下情况必须停下汇报，不得靠补丁绕过：

  1. 发现某个股票分钟线下游必须允许越过 expected trade date 缺口才能生产。
  2. 发现 silver_trade_calendar 对股票分钟线 expected date 的定义不可靠。
  3. 发现需要新增数据库表、summary asset、readiness asset 或正式配置项才能推进。
  4. 发现必须读取正式 Dagster instance 才能判断代码契约。
  5. 发现 qfq factor repair 或 MACD/KDJ repair 必须恢复无上游 batch 的散装修复路径。
  6. 发现实现会改变 run key 治理已完成的五条最终验收口径。

10. 与既有治理成果的关系

既有专项 关系 不得破坏的口径
Run key 治理 本专项只改目标日期选择、连续性 gate 和 repair date range，不改 run key identity。 所有正式 run key 仍经统一 builder；禁止解析 run key 生成 config。
upstream batch id MACD/KDJ repair 仍只能消费真实 qfq factor repair upstream batch。 不恢复 event storage id completion identity，不恢复散装手工 repair。
Asset schema contract 本专项不改资产字段契约。 不得把连续性状态塞进正式 parquet 字段；应通过 sensor cursor、metadata 或 checks 表达。
Index daily gap audit 可借鉴 first-not-ready 与 gap audit 思路。 不能直接套用指数 code-by-code 语义到股票分钟线五/七频度和 stateful 指标。

11. 已拍板事项

编号 事项 已拍板口径 影响
D1 本专项是否只覆盖股票分钟线链路，还是同时治理 cn_a_stock_current_trade_days 等 current trade day 专用分区。 先只覆盖股票分钟线链路；current trade day 单独审计。 避免扩大到复权因子、股票基础等资产族，保持一轮一个清晰目标。
D2 cn_a_stock_mins_trade_days 的补偿式注册是否直接复用 build_trade_day_partition_registration_result(...)。 复用其 calendar-backed catch-up 口径，但保留股票分钟线 18:00 同日窗口和独立 partition set。 减少重复实现；需要补足股票分钟线专属测试。
D3 股票分钟线连续性 helper 放置位置与命名。 新增 orchestrator.defs.asset_guards.stk_mins_continuity。它是股票分钟线连续性 gate/helper，不是 sensor；先服务 sensor、run-status sensor 与 repair op gate。 避免 op 反向依赖 defs/sensors；同类生产门禁能力收敛到 asset_guards，名称稳定表达业务对象，避免 utils/common。
D4 每个 sensor tick 最多补/提交多少个日期。 partition catch-up 可以小批量补，单 tick 上限取 2；run 提交永远只按 first not ready / ready frontier 推进；writer pool 和 run key 继续兜住同一资产族并发。 注册可以提前知道日期存在，但执行必须等连续 ready；测试必须覆盖 2026-06-15 run 未完成时，即使 2026-06-16 已注册，也不会提交 2026-06-16 的下游 run。
D5 MACD/KDJ baseline 起点如何定义。 沿用现有正式 baseline cutoff；只有 baseline 之后的日常日期必须要求上一 expected state。 避免误判历史初始化之前没有上一 state 的正常情况。
D6 缺口 audit 是否做成正式 asset check。 第一阶段不做正式 asset check，先做 continuity gate + cursor 可观测；是否新增 blocking asset check 作为后续增强单独设计。 避免未经确认新增 Dagster definitions；先把“不能跳洞执行”根问题解决。若未来需要 Dagster UI 长期红绿灯，再单独设计正式 continuity asset check。
D7 遇到中间日期已 materialized 但 blocking checks 未绿时是否自动重跑。 不自动重跑；继续沿用现有“已生成但 checks 未绿时人工处理”的安全口径。 降低覆盖写风险，保持已有运维语义。
