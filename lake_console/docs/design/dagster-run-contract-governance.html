Dagster Run Contract 治理方案

本文档定义 Goldenshare Lake Dagster 项目中 tags、run config、metadata 与 sensor cursor 的语义边界、命名空间、字段准入规则和第一版最小字段集合。它是后续代码审计和逐项整改的依据，不直接修改任何 asset、job、sensor 或正式 Dagster instance。

1. 背景与问题

当前项目已经出现 tags、run config、metadata 与 cursor 语义混杂的问题。典型表现是：sensor 手写 RunRequest，不同文件各自发明 tag key；下游 readiness 反向解析历史 run config；automation sensor 与普通 sensor 使用不同触发标签；materialization metadata 中也混入部分本应属于定义层或运行层的信息。

这不是代码风格问题，而是运行契约问题。如果不先定义边界，后续 asset、job、sensor 数量增加后，每个新增入口都会继续扩散一组临时 tags/config，通知、readiness、并发、审计都会被这些局部口径拖住。

治理原则：先定义契约，再审计现状，再逐项修正。禁止为了当前一个通知噪音或一个 sensor 门禁，继续新增未经定义的 tag、config 字段或 cursor 字段。

2. 外部依据与可借鉴边界

来源 相关口径 对本项目的约束
Dagster Asset metadata and tags Asset tags 用于资产过滤、搜索和组织；metadata 用于更丰富的资产描述或运行产物事实。 Asset tags 只能放低基数、静态、对 UI 过滤有实际价值的信息；行数、路径、样本、schema 等事实进入 metadata。
Dagster RunRequest API RunRequest 明确区分 run_key、run_config、tags。 执行参数进入 run_config；本项目第一版不新增自定义 run tags，只读取 Dagster 系统 tags。日期、代码、批次数量这类动态信息不能借 run tags 传递。
Dagster Jobs API Job 定义支持 tags、run_tags、metadata，三者作用不同。 Job 定义层 tags 只服务定义分类；run_tags 不作为默认扩展点。只有出现明确调度策略或外部系统契约，并先更新本文档，才允许讨论自定义 run tags。
Dagster Run configuration Run config 是运行时配置，供 asset/op/resource 消费并由 schema 校验。 Run config 只能放会改变本次执行行为的参数，不能放通知、UI 分类、批次统计或下游观测状态。
Dagster Managing concurrency Dagster 并发控制可以使用 pools 或 run tag limits。 Run tags 未来可能参与调度控制，因此必须稳定、受控、可审计，不能随意新增高歧义 key。
dbt tags / dbt meta dbt tags 常用于选择和组织资源；meta 承载结构化自定义元数据。 标签应服务选择和治理，不应承载复杂结构；结构化描述进入 metadata。
DataHub Tags / Domains Tags 是轻量分类；Domains 是更正式的业务域归属。 不要用大量自由 tags 模拟业务模型；本项目第一版只保留确实会用于过滤、审计或自动化的最小标签。
OpenLineage Spec Job、Run、Dataset 有不同实体边界，运行事实和数据集事实通过不同 facets 表达。 本项目必须区分 asset 定义事实、run 执行事实、materialization 产物事实和 sensor 私有状态。

3. 四类信息的边界定义

类别 定义 应该放什么 禁止放什么
tags 低成本、低基数或可索引的字符串标签，用于过滤、查询和资产组织。Run records 上第一版只读取 Dagster 系统 tags。 资产静态分类；Dagster 系统生成的 partition、backfill、sensor、schedule、from_ui 等运行事实。 行数、样本行、文件路径、错误详情、完整 schema、复杂 JSON。
run_config 本次 run 的执行输入，会被 asset/op/resource 读取并改变执行行为。 源接口查询窗口、写入模式、明确的执行参数。 通知策略、UI 分类、batch 统计、owner、行数、ready 状态。
metadata 资产定义、materialization、asset check 或 event 上的结构化说明和事实。 路径、行数、schema、源接口、数据契约、质量检查统计、样本。 触发来源、sensor 私有 offset、通知开关、会影响执行的参数。
cursor 某个 sensor 自己的私有进度和上次评估摘要。 上次评估时间、目标日期、offset、决策摘要、少量诊断样本。 跨 sensor 契约、下游 readiness 唯一事实源、业务数据事实、长期审计口径。
一句话规则：run_config 改变执行，asset tags 只做资产分类，run records 第一版只读 Dagster 系统 tags，asset/materialization metadata 描述资产与产物事实，cursor 只服务 sensor 自己。

4. 命名空间规则

命名空间 归属 规则 原因
dagster/* Dagster 系统 只读，不自造，不覆盖，不把自定义语义塞进该命名空间。 Dagster 会生成 dagster/partition、dagster/backfill、dagster/sensor_name 等系统 tags；伪造会污染 UI、查询和后续升级。
goldenshare/* 本项目自定义 asset tags 和 metadata 所有跨模块可见的自定义 key 必须使用该前缀，并在本文档或后续契约文档登记；第一版不用于 run tags。 避免与 Dagster、第三方插件和未来系统 key 冲突；也便于静态扫描。
无前缀 config 字段 具体 asset/op 的 typed config Config 字段使用 Python config model 的局部业务名，不加 goldenshare/ 前缀。 Run config 是代码消费的结构化输入，不是全局标签字典；命名应贴近 asset 业务参数。
无前缀 cursor 字段 具体 sensor 私有 JSON Cursor 顶层字段遵守本文档最小规范，sensor-specific 信息放入 details。 Cursor 不对外共享，不需要全局前缀；但需要基本结构方便排错和迁移。

5. Asset Tags 第一版字段

Asset tags 第一版只定义两个字段：层级和数据域。标签只服务 UI 过滤、资产组织和低基数分类，不承载具体数据集名称、运行日期、批次状态或质量统计。数据域取值学习 docs/sources/tushare/** 的目录语言，但在 UI 中做简化展示；具体 Tushare 来源目录和文档路径进入 metadata，不进入 tag。

字段 是否必填 允许值 适用对象 定义原因
goldenshare/layer 是，正式数据资产必填 原始层、标准层、正式层 所有落到 data_lake/raw|silver|gold 的 asset Lake 三层是本项目硬边界，且在 UI、文档、路径、checks 中反复使用。值使用中文是为了让 Dagster UI 中的资产过滤更直观；代码内部路径仍然使用 raw、silver、gold。
goldenshare/data_domain 是，正式数据资产必填 基础数据、行情数据、指数专题、项目配置、衍生指标 所有正式数据资产 该字段用于少量稳定的数据域过滤。基础数据、行情数据、指数专题 来自 Tushare 本地文档目录；项目配置 和 衍生指标 用于非 Tushare 源资产。

5.1 当前数据域归类

数据域 当前覆盖数据集 定义原因
基础数据 stock_basic、trade_cal 本地 Tushare 文档把股票基础信息和交易日历放在 股票数据 / 基础数据 下。UI tag 保留二级目录名，具体上级目录和文档路径由 metadata 记录。
行情数据 daily、suspend_d 本地 Tushare 文档把 A 股日线行情和每日停复牌信息都放在 股票数据 / 行情数据 下。停复牌不单独造新分类，避免偏离既有文档目录体系。
指数专题 index_basic、index_daily 本地 Tushare 文档把指数基本信息和指数日线行情放在 指数专题 下。该目录本身已经是稳定一级分类。
项目配置 market_major_indices 主要指数名单来自项目 seed/config，不是 Tushare API 目录中的数据集。单独归为项目配置，便于和源站数据区分。
衍生指标 market_breadth、stock_return_distribution 市场宽度和股票涨跌幅分布由湖内标准层资产计算得到，不直接对应 Tushare 源目录。归为衍生指标，表达其作为正式层分析产物的性质。
明确不定义 goldenshare/data_family：具体数据集身份由 asset key 和中文名映射表达，不再把 stock_daily、index_daily 这类数据集名搬进 tag。否则未来 500 个资产会变成 500 个 family，失去分类价值。
暂不定义的 asset tags：owner、sensitivity、source_system、freshness_class 第一版不进入 asset tags。原因分别是：当前没有多 owner 运维流程；本地 lake 目前没有分级隐私治理；source 更适合作为 definition metadata；freshness 已由 checks/readiness 表达，提前做 tag 会形成重复口径。

7. Run Tags 第一版口径

Run tags 第一版不定义任何自定义字段。Tags 只适合做分类和过滤，不适合传递日期、批次成员、完成数量、通知策略等动态信息。当前已有自定义 run tags 是待迁移债务，不能继续扩展。

系统 tag 使用方式 原因
dagster/backfill 只读，用于识别 UI backfill 或 Dagster automation backfill 的子 run。 Dagster 已有原生 backfill 总任务语义，不需要自定义 batch tag 模拟。
dagster/partition 只读，用于理解本次 run 的 Dagster partition key。 分区 key 是 Dagster 系统事实，不能用自定义 tag 重复维护。
dagster/sensor_name 只读，用于识别 run 是否由 sensor 发起。 触发来源已有系统 tag，删除 triggered_by 这类重复字段。
dagster/schedule_name 只读，用于识别 run 是否由 schedule 发起。 触发来源已有系统 tag，不再自定义 trigger 字段。
dagster/from_ui 只读，用于识别人工 UI 发起。 人工触发来源属于 Dagster 系统事实，不需要自定义 tag。

7.1 明确删除的自定义 run tags

现有或曾讨论字段 最终口径 原因
triggered_by、trigger 删除；改读 Dagster 系统 trigger tags。 触发来源是 Dagster 已有系统事实，自定义字段会形成重复口径。
asset_family 删除；资产分类使用 asset tags 和 asset key。 资产分类不是单次 run 的动态事实，放 run tags 会重复。
trade_date 删除；不替换为 goldenshare/logical_date。 日期是运行输入或资产分区语义，不适合作为自定义 tag 传递给下游。
index_ts_code 删除；指数代码由 Dagster partition key 表达。 partition key 已经是指数代码，自定义 tag 是重复信息。
goldenshare/batch_type、goldenshare/batch_member_type、goldenshare/batch_key、goldenshare/batch_member_key、goldenshare/batch_expected_count 不定义。 这些字段是在用 tag 传递批次信息，不是分类过滤项。批量总状态应使用 Dagster backfill 或正式批次状态事实，不能把 run tags 当临时数据库。
goldenshare/notify_scope、goldenshare/concurrency_group 不定义。 当前没有正式通知路由和并发 tag 策略，不预留会影响调度或形成重复事实的字段。

7.2 指数 Silver 触发安全设计

删除自定义 run tags 前，必须先保证 silver_index_daily_sensor 不误判。当前 sensor 依赖 asset_family、trade_date、index_ts_code 查询 raw run 成功状态；直接删 tags 会让 sensor 退化为解析 run config，风险不可接受。

设计点 最终口径 原因
Silver 门禁事实源 改为 raw 文件事实：所有注册指数代码的 raw 文件必须存在，并且都包含目标 trade_date 数据。 Silver 真正消费的是 raw 文件，不是 run 记录。run 成功不能证明文件仍存在，也不能证明文件里有目标日期。
禁止误判 任何 raw 文件缺失、目标日期缺失、扫描异常、扫描超时或扫描不完整，都只能 SkipReason，不得触发 silver run。 门禁宁可保守 skip，也不能在上游不完整时生成 silver。
性能边界 禁止在 sensor hot path 中查询大量 asset check history 或大量 run records；raw readiness 检查必须是轻量文件事实检查。 此前 sensor 侧重 IO 和大量历史查询曾导致 gRPC deadline exceeded，不能重复。
Cursor 用途 Cursor 只记录诊断摘要，例如目标日期、注册代码数、ready 数、缺失样本和评估耗时；不能把 cursor 当作跨 tick 的正向 ready 事实。 跨 tick 缓存 ready 状态可能被外部文件变化污染。触发 silver 必须来自本次完整检查结果。
整改顺序 先迁移 silver_index_daily_sensor 到 raw 文件事实门禁；静态确认不再依赖旧 run tags/config；再删除 index_daily_sensor 里的自定义 run tags。 顺序错误会直接影响 silver 自动触发，属于数据安全风险。

8. Run Config 使用规范与 Launchpad UX

Run config 是执行输入，不是观测标签。最终态必须同时满足两层要求：底层 asset/op 使用 typed config 保证校验；面向 Dagster UI 的 job 暴露简化 config，让 Launchpad 不是空白深层 YAML，而是可 scaffold、可理解、只需要填写关键字段的表单。

规范 原因 落地要求
每个 asset/op 的 config 必须由 dg.Config typed model 定义。 typed config 可以让 Dagster 做 schema 展示和校验，避免裸 dict 在 sensor 中失控。 这是底层执行契约，不能因为增加 UI 简化 config 而取消。
有手动 UI 运行需求的入口必须提供简化 config schema。 用户在 Launchpad 点击 Add config 时，不应该面对空白页面或深层 ops/.../config/... 结构。 优先用 Dagster 原生 dg.Config schema 表达业务动作输入；带分区定义的 asset job 不得未经验证直接挂 ConfigMapping。
Config 不携带通知、batch、trigger、owner、UI 分类。 这些字段不改变 asset 执行，放入 config 会污染 Launchpad 和运行契约。 通知与批量总状态另行设计；owner 或分类用 asset tags/metadata。
Config 字段变更必须做消费者审计。 Config 是执行契约，改名或改语义会影响 UI 手动 run、sensor run、backfill repair 和历史文档。 变更前列出所有 run_config 构造点、Launchpad 使用方式、sensor readiness 读取点和文档。

8.1 指数日线 UI Config 最终态

index_daily_update_job 的 UI 配置最终态只暴露简化字段。这里不是“UI 好看”问题，而是 run config 在资产族变多后是否可维护、可审计、可被运营正确使用的问题。手动运行不能要求运营记忆深层 YAML 和隐藏不变量。

M3B 已把 raw_tushare_index_daily_by_code 的正式 UI config 从 start_date/end_date/write_mode 收敛为 trade_date/write_mode。asset 内部把 trade_date 映射成 start_date = end_date = trade_date，底层 Tushare 请求窗口不再暴露给运营。

trade_date 必须有字段说明但不设置危险默认日期；write_mode 可以默认 replace。如果 Launchpad 中 Add config 或 Scaffold Missing Config 后仍然只能得到空白编辑器，或仍要求用户手写 start_date/end_date，则该 job 尚未达到本节定义的最终态。

M3 静态验证发现：当前 Dagster 版本不允许给带分区定义的 asset job 直接挂 ConfigMapping，否则 job config schema 解析会失败。因此 index_daily_update_job 在保持“指数代码是分区语义”的前提下，本轮不能把 Launchpad 外部配置改成顶层 trade_date/write_mode。M3 只清理 sensor 自定义 run tags，并把 sensor 侧配置生成收敛到 builder；UI 手动配置治理需要单独设计，不得用破坏分区 job 的方式硬接。 

# Launchpad 展示目标
trade_date: "2026-05-26"
write_mode: "replace"
UI 字段 底层映射 允许值 定义原因
trade_date start_date = trade_date，end_date = trade_date YYYY-MM-DD 手动补某一天指数 raw-by-code 时，用户只关心业务日期，不应填写两个相同的日期字段。
write_mode write_mode replace 当前只允许替换写入。保留字段是为了让写入行为显式，但默认值应由 config schema 提供。

8.2 M3B Launchpad Config 契约治理计划

依据 Dagster 官方 run config 口径，配置由 asset / op / resource 的 schema 驱动，Launchpad 负责按 schema 做校验、展示说明并支持 Scaffold Missing Config；asset job 是资产执行入口，不能为了手动配置体验绕开 asset、partition 和 checks 体系。 参考： Run Configuration、 Asset jobs、 Advanced Config Types。

治理点 M3B 口径 原因
问题定性 Add config 空白或深层 YAML 是运行契约可维护性问题，不是视觉问题。 资产族和 job 变多后，手填结构不可记忆、不可审计，也容易误填导致错误运行。
实现方向 在 Dagster 原生 dg.Config schema 内降低认知负担，主入口只暴露 trade_date/write_mode。 让 UI、sensor 和文档共享同一个业务动作语义，避免三套配置口径分裂。
不采用路径 不使用 ConfigMapping 强接顶层 config，不新增二维 partitions，不新增 op job 绕过 asset job。 这些路径要么被当前 Dagster 分区 asset job 限制挡住，要么破坏分区规模、资产血缘或 checks 体系。
区间修复 不把 start_date/end_date 区间修复保留为主入口能力；未来需要时单独设计 repair 入口。 当前日常和缺口修复都是“指数代码 + 单个交易日”，低频区间能力不应污染主入口。
M3B 验证口径：代码实现阶段必须补充编译、纯函数测试、in-memory Definitions + dg.validate_run_config(...) 验证、旧 start_date/end_date 拒绝验证、sensor 静态扫描、git diff --check 和文档完整性检查；UI 验证只允许打开 Launchpad / Scaffold Missing Config，不启动 run，且读取正式 Dagster UI 前必须单独获批。

8.3 M3B 目标 Typed Config 字段

Config model 字段 允许值 定义原因
IndexDailyRawByCodeConfig（M3B 目标） trade_date YYYY-MM-DD 主入口只表达“补哪一个交易日”。该字段由 asset 内部映射为 Tushare start_date=end_date，避免运营手填两个必须相等的日期。
write_mode replace 当前 raw-by-code 文件写入只允许替换模式。保留字段是为了让写入行为显式，并由 schema 给出默认值和说明。

8.4 不采用二维分区

Dagster 支持 MultiPartitionsDefinition，可以表达“指数代码 x 日期”的笛卡尔积分区；本地 Dagster 1.13.6 也存在 MultiPartitionsDefinition、MultiPartitionKey 和 MultiToSingleDimensionPartitionMapping。但当前指数交易日约 6393 个、指数代码约 946 个，笛卡尔积约 604 万 partitions，远超 Dagster 官方建议单 asset 控制在 100,000 partitions 以内的量级。

最终口径：不采用“指数代码 x 日期”二维分区作为指数日线 raw 主模型。raw 继续按指数代码分区，日期通过 asset typed config 的 trade_date 输入；silver 继续按交易日分区。
后续审计要求：如果发现其它 asset 需要 config，必须先补充到本节，说明字段消费者、执行影响、允许值、失败行为和为什么不能由 partition key 或 resource 配置表达。

9. Metadata 使用规范

Metadata 分为三类：asset definition metadata、materialization metadata、asset check metadata。它们都可以承载结构化信息，但语义不同。第一版优先使用 Dagster 标准 metadata key；只有标准 key 无法表达时，才使用 goldenshare/*。

9.1 Asset Definition Metadata

字段 是否必填 格式 定义原因
goldenshare/source_system 正式数据资产必填 见 9.1.1 source system 枚举 source system 是资产定义事实，不是每次运行事实。放在 metadata 中可以表达 raw、seed、derived 等来源，不污染 asset tags。
goldenshare/source_api 源站 API asset 必填，其它资产为空 源接口稳定名称，例如 daily、index_daily 源接口名用于追溯 Tushare 文档、字段契约和请求参数。它比 source_system 更细，但不是 UI 过滤主轴。
goldenshare/source_category_path Tushare 源站 API asset 必填，其它资产为空 本地 Tushare 目录路径，例如 股票数据 / 行情数据 asset tag 中的 data_domain 是简化中文分类；完整 Tushare 目录路径需要保留在 metadata 中，方便后续核对源文档而不污染 tag 枚举。
goldenshare/source_doc 源站 API asset 必填，其它资产可选 仓库内文档路径或官方文档 URL 仓库规则要求涉及 Tushare 参数和字段时先查文档。把源文档挂到定义 metadata，能减少后续无依据改接口。
goldenshare/data_contract 正式数据资产必填 资产设计文档中定义的契约 id，不做全局枚举 数据契约会随资产族设计演进，不适合做全局固定枚举；但每个资产必须明确自己遵守哪份契约。
goldenshare/path_template 有湖文件产物的 asset 必填 不含具体 run id 的路径模板 定义层应说明资产长期写到哪里；具体本次文件 URI 放 materialization metadata。

9.1.1 Source System 枚举

枚举值 定义原因
tushare 源数据直接来自 Tushare API，需要追溯 Tushare 文档、字段和请求参数。
derived 资产由湖内上游资产计算得到，不直接调用外部源站。
seed 资产来自仓库维护的静态 seed 文件，治理口径不同于外部 API。
old_lake_bootstrap 只用于一次性迁移来源或 bootstrap 记录，提醒维护者该来源不是长期正式写入口。

9.2 Materialization Metadata

字段 是否必填 格式 定义原因
dagster/uri 有单一主产物路径时必填 实际文件或目录 URI Dagster 标准 metadata key，适合表达本次 materialization 的实际产物位置。
dagster/row_count 表格型产物必填 非负整数 Dagster 标准 metadata key，行数是排错、质量检查和历史对比的核心事实。
dagster/column_schema 正式表格型产物推荐 Dagster column schema metadata schema 是资产产物事实，适合放 metadata；不适合用 tag 表达。
goldenshare/source_row_count 发生源到目标转换时必填 非负整数 用于核对源端行数与目标行数，支撑 reject、dedupe 和质量排查。
goldenshare/duplicate_removed_count 执行去重时必填 非负整数 去重会影响行数，必须显式暴露，不能只在日志中出现。
goldenshare/rejected_row_count 存在 reject 流程时必填 非负整数 仓库规则要求任何 reject 都必须解释到 reason code 和样本，不能静默跳过。
goldenshare/reject_reason_counts 存在 reject 流程时必填 JSON object，key 为 reason code，value 为数量 单个 reject 总数不足以排查原因；需要知道每类拒绝原因的规模。
goldenshare/sample_rows 只有排错必要时可选 最多 10 行脱敏样本 样本对排错有价值，但可能让 metadata 过重；只在失败、冲突或 reject 时使用。

9.3 Asset Check Metadata

字段 是否必填 格式 定义原因
goldenshare/check_scope 推荐 schema、row_count、key_uniqueness、partition_alignment、value_sanity、freshness 检查名往往较长且资产特定；scope 提供低基数分类，便于后续汇总质量风险。
goldenshare/checked_row_count 检查扫描行集时推荐 非负整数 说明检查覆盖了多少行，避免只知道 pass/fail 而不知道检查范围。
goldenshare/failed_row_count 检查能定位失败行时推荐 非负整数 失败规模影响处置优先级；必须区别单行异常和大规模质量事故。
goldenshare/failure_samples 失败时可选 最多 10 行样本 提供人工排错入口，但避免在 check metadata 中堆积大量数据。

10. Sensor Cursor 使用规范

Cursor 是 sensor 私有状态，不是跨 sensor 契约。它可以帮助诊断最近一次 tick 为什么 skip 或 request，但不能作为下游资产 ready 的唯一事实源。

字段 是否必填 格式或枚举 定义原因
schema_version 必填 1 Cursor 结构会随 sensor 演进。显式版本可以安全读取旧 cursor，而不是靠 try/except 猜结构。
evaluated_at 必填 ISO 8601 datetime，使用项目传感器时区 排查 sensor tick 时必须知道这份 cursor 对应的评估时间。
decision 必填 见 10.1 decision 枚举 人看 cursor 时应先知道这次 tick 做了什么，而不是从多组计数字段推断。
target_date 有目标日期时必填 YYYY-MM-DD 或 null 大多数日频 sensor 都围绕某个业务日期评估；该字段只用于 sensor 私有诊断，不进入 run tags，也不作为下游 ready 事实。
selected_count 有 run 或 partition request 时必填 非负整数 展示本次 tick 实际选择了多少个请求，避免只看样本列表。
blocked_count 有门禁判断时推荐 非负整数 展示门禁挡住了多少候选项，帮助判断是全部 ready、全部 blocked，还是只是没有候选。
sample_keys 有大量候选或缺失项时推荐 最多 20 个字符串 样本有助于排错，但 cursor 不能变成大列表仓库；必须限制数量。
details 可选 sensor 私有 JSON object 保留各 sensor 的诊断空间，但所有跨 sensor 通用字段必须放在顶层。

10.1 Cursor Decision 枚举

枚举值 定义原因
skip 本次 tick 没有提交任何请求。需要和“提交了 0 个但有错误”区分。
request_runs 本次 tick 提交了一个或多个 RunRequest。
register_partitions 本次 tick 只注册 dynamic partitions，不触发数据生产 run。
notify 本次 tick 只发送外部通知，不提交生产 run，也不注册 partitions。

Sensor 禁止直接手写自定义 tags={...} 和深层 run_config={...}。 裸 dict 是当前口径扩散的主要来源。 新增静态检查脚本或扩展 docs/code integrity 检查。第一版 RunRequest.tags 不允许出现自定义 tags；需要 tags 时必须先更新本文档。

新增字段必须先改本文档。 字段一旦进入 asset tags、run records、materialization metadata 或 cursor，就可能被下游依赖。 PR/提交前检查文档是否同步；未登记字段不得进入正式代码。

13. 本轮代码审计结论

本节按“文档中要求删除或清理的 run tags / run config 口径”回读当前代码后形成。结论是：这些字段不能一刀切删除，必须先拆清写入点、读取点和数据安全影响。

defs/assets/**/*.py、defs/checks/**/*.py 当前正式 asset definition 基本只设置 group_name，尚未系统接入 goldenshare/layer、goldenshare/data_domain；materialization/check metadata 已有大量行数、路径、样本、契约字段。 不是本轮“删除 run tags”风险点，但后续接入 asset tags / metadata helper 时必须逐资产核对，不能批量猜。 按资产族分批迁移 metadata 和 asset tags；每批迁移前先核对对应 asset/check 现有 metadata 字段，不做全仓一次性替换。
安全结论：指数链路必须先改 silver_index_daily_sensor，再删 index_daily_sensor 的 asset_family/trade_date/index_ts_code。其它 triggered_by/trigger/asset_family 多数只是展示或筛选噪音，但也要同步飞书展示逻辑，不能留下“旧 tag 仍是新契约”的错觉。
