Dagster 平台观测人类可读治理 LLD

本文是 dagster-dataset-human-readable-governance-rollout-plan.html 中 Wave 5 的代码级低阶设计。范围只有 lake_root_health， 目标是让平台健康失败能直接看出是路径、权限、磁盘空间还是 DuckDB temp 问题。

Wave 5：平台观测 状态：已落地 只改表达层 不改健康判断 不新增 sensor 不写业务 lake 数据

1. 目标

lake_root_health 是平台健康检查，不是行情业务数据集。 它应该回答：lake root 是否可用、必要目录是否齐、canary 是否能读写、磁盘空间是否够、 DuckDB temp 是否可用，以及失败后先修哪里。

2. 硬边界

边界执行口径
健康判断 不改 evaluate_lake_root_health(...) 的 required paths、canary、free space、DuckDB temp 判断。
Definitions 不改 asset/job/schedule/check 名称；不新增 sensor；不新增 check。
数据写入 不写 Parquet，不写 Dagster DB，不写业务数据库；保留现有 canary 临时文件写读删行为。
表达方式 metadata 用平台语言，不写上游行情、下游消费、source asset 等业务数据集词汇。
测试 只跑单元测试、静态门禁、文档检查和 git diff --check；不运行 dg。

3. 性能与副作用

入口新增读取/写入预算
Asset / check 0 新增业务读取。继续沿用现有目录存在性、canary 和磁盘空间检查。 metadata 只追加短中文、组件状态和下一步，不扩大文件扫描。
Job / schedule 0。job 仍只 selection lake_root_health 与 checks；schedule 仍默认 STOPPED。 不改变执行频率、default status 或 selection。

4. 代码级改动

文件改动
defs/health/lake_root.py 在 LakeRootHealthStatus.metadata() 里追加 summary、next_action、result_status、 component_status、diagnostic_ref。 不改 healthy、run_available 和评估函数。
defs/assets/lake_root_health.py description 改成平台可读说明，materialization 继续使用现有 metadata builder。
defs/checks/lake_root_health_checks.py 在聚合 check metadata 中追加 rule_summary，让失败项能直接看出哪个组件不绿。
tests/test_lake_root_health_asset.py 补 asset/check metadata 可读字段断言，确认不写 Parquet。
tests/test_run_contract_static_gates.py 补静态门禁：平台健康入口必须保留人类可读字段，且不得被 sensor 或业务资产依赖。

5. 实际落地状态

对象结果
LakeRootHealthStatus.metadata() 已追加 summary、next_action、 result_status、component_status 和 diagnostic_ref；原有路径、canary、空间和失败原因字段保留。
lake_root_health asset 已改成平台健康检查说明；成功仍只写 materialization metadata， 失败仍抛 dg.Failure 并携带同一份 health metadata。
lake_root_health_ready check 已保留 rule_passed 和 failed_rule_names， 并追加 rule_summary；没有新增细碎 check。
行为边界 已确认不改健康判断、job selection、schedule default status、sensor 依赖、 平台门禁调用和数据写入行为。
