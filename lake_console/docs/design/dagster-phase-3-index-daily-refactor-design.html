Dagster Phase 3 Index Daily 重构设计

本文是指数日线 index_daily 的新方案设计文档。它不是当前代码事实说明， 而是后续重构落地前的准口径草案。本文只描述设计，不表示已经修改代码或执行迁移。

目标起点：2000-01-01 Raw 分区：cn_a_index_ts_codes Raw 粒度：ts_code Silver 粒度：trade_date 初始化来源：外部 CSV

1. 设计结论

新方案把 index_daily 从“按交易日拉全部指数”改成“按指数代码拉一段时间窗口”。 Raw 层使用 cn_a_index_ts_codes dynamic partitions 承载指数代码；Silver 层继续按交易日分区， 保持下游业务查询和现有 silver_index_daily 事实口径稳定。

层级 目标资产 分区 职责
Raw raw_tushare_index_daily_by_code[ts_code] cn_a_index_ts_codes 按单个指数代码和单个 trade_date 向 Tushare 拉取日线数据，内部使用 start_date=end_date=trade_date，写入该代码自己的 raw parquet。
Silver silver_index_daily[trade_date] cn_a_index_trade_days 从 raw-by-code 文件中按交易日抽取、标准化、去重、校验，产出按交易日组织的标准事实表。
Sensor index_daily_sensor 读取 cn_a_index_ts_codes 判断交易日和 Tushare 源站 ready 后，为每个指数代码发起 raw 更新 run。

这套方案的核心取舍是：Raw 层更适合“按代码拉取与修复”，Silver 层更适合“按交易日服务下游”。 两者不再强行使用同一个分区维度。

2. 当前代码事实与问题

本轮设计前已阅读当前 lake_console/orchestrator 下相关代码与文档。Slice E 后，旧 active pool / raw-by-trade-date 链路已经从 active Definitions 和代码生产入口退场，当前事实如下。

当前实现 代码事实 重构原因
Active pool silver_index_daily_active_pool asset、active pool checks 和 index_daily_active_pool_update_job 已从 active Definitions 删除。 PostgreSQL 中已有 index_daily_active_pool / history 表未 drop、未 truncate。 指数池来源已经切到 cn_a_index_ts_codes dynamic partitions，由外部 CSV 初始化；旧 PG 表只保留为后续单独清理对象。
Raw 按交易日 旧 raw_tushare_index_daily[trade_date] asset 和旧 raw-by-date checks 已删除。 旧物理文件 raw/tushare/index_daily/trade_date=YYYY-MM-DD/part-000.parquet 已按用户确认删除，避免 UI 和物理湖路径继续误导新链路。 单指数补数时必须按交易日改很多文件；按代码维护 raw 更自然，也更适合 Tushare index_daily(ts_code,start_date,end_date) 的请求方式。
Silver 按交易日 当前 silver_index_daily[trade_date] 写入 silver/index_daily/trade_date=YYYY-MM-DD/part-000.parquet。 这个口径适合下游按日查询，保留不变；变化只发生在上游 raw 组织方式和生成方式。
历史回填 index_daily_history_backfill_job 已从 active Definitions 删除。 新方案应优先使用 partitioned asset job，让 UI 能按 ts_code 选择分区；历史大批量可以接受 run 数较多，但分区状态更清晰。
按代码修复 index_daily_repair_by_codes_job 已从 active Definitions 删除。 新 raw-by-code 布局天然支持单代码重跑，修复入口应退化为普通的分区重跑，不再需要专门 repair job。

3. 目标架构

外部 CSV
  └─ 初始化 Dynamic Partitions: cn_a_index_ts_codes
       ├─ 000001.SH
       ├─ 399001.SZ
       └─ ...

index_daily_sensor
  ├─ 判断今天是否交易日
  ├─ 判断 Tushare index_daily 是否 ready
  ├─ 读取 cn_a_index_ts_codes
  └─ 为每个 ts_code 发 RunRequest

index_daily_update_job[ts_code]
  └─ raw_tushare_index_daily_by_code[ts_code]
       └─ raw/tushare/index_daily_by_code/ts_code=<TS_CODE>/part-000.parquet

silver_index_daily_update_job[trade_date]
  └─ silver_index_daily[trade_date]
       └─ silver/index_daily/trade_date=YYYY-MM-DD/part-000.parquet

关键约束：Raw asset 使用 cn_a_index_ts_codes 分区，Silver asset 使用 cn_a_index_trade_days 分区。两者分区维度不同，因此不应该强行塞进同一个 partitioned asset job。否则 UI 的 partition selection 会变得含混，后续 backfill 和排错也容易乱。

3.1 Asset / Check / Partition / Job / Sensor / Run 关系总图

Partitions

cn_a_index_ts_codes 指数代码动态分区。由外部 CSV 初始化，例：000001.SH、399001.SZ。
cn_a_index_trade_days 指数日线 silver 的交易日分区，例：2026-05-22。
→ 读取/选择

Sensors / Jobs / Runs

index_daily_sensor 判断交易日 + 源站 ready，读取 cn_a_index_ts_codes，为每个指数代码发起一个 raw 更新请求。
index_daily_update_job[ts_code] partitioned asset job。每个 Dagster run 对应一个 ts_code，run config 提供 trade_date/write_mode。
silver_index_daily_update_job[trade_date] 建议新增的 trade_date partitioned job。它只负责把 raw-by-code 汇总为某个交易日的 silver。
→ materialize

Assets / Checks / Files

raw_tushare_index_daily_by_code[ts_code] Raw 源镜像资产，按指数代码保存一段时间窗口的数据。
Raw checks 文件存在、字段契约、partition key 匹配、ts_code + trade_date 唯一。
Raw file raw/tushare/index_daily_by_code/ts_code=<TS_CODE>/part-000.parquet
silver_index_daily[trade_date] Silver 标准事实资产，按交易日读取 raw-by-code 结果并标准化。
Silver checks 分区日期匹配、唯一性、字段契约、价格合理性、覆盖率观测。
Silver file silver/index_daily/trade_date=YYYY-MM-DD/part-000.parquet

3.2 日更触发时序图

1. Sensor tick index_daily_sensor 被 Dagster daemon 轮询评估。
2. 交易日判断 只处理已完成或已进入探测窗口的 A 股交易日。
3. 源站 ready 对 Tushare index_daily 做只读探测，不写 parquet。
4. 读取代码分区 从 cn_a_index_ts_codes 读取全部待更新指数代码。
5. 判断 raw 缺口 扫描 raw-by-code 文件，找出还没有目标 trade_date 的 ts_code。
6. 发起 raw runs 只为缺失的 ts_code 发 index_daily_update_job RunRequest。
7. Silver 刷新 raw 完成后，再按 trade_date 触发或手工执行 silver 更新。

从这张图看，run 不是单独的数据资产，而是 Dagster 对一次执行的记录： raw 日更阶段的一个 run 对应一个 ts_code 分区； silver 刷新阶段的一个 run 对应一个 trade_date 分区。 Checks 绑定在对应 asset 上，用来判定本次 materialization 是否满足质量门禁。

4. Dynamic Partitions 设计

4.1 分区定义

名称 类型 含义 初始化方式
cn_a_index_ts_codes DynamicPartitionsDefinition 指数日线 raw 层允许更新的指数代码集合。 从外部 CSV 一次性导入，不新增正式 Dagster job。

4.2 CSV 初始化口径

第一版初始化来源使用： /Users/congming/github/goldenshare/lake_console/reports/index_daily_continuous_since_list_date_after_20000101.csv。 这份 CSV 是按“从 2000-01-01 观察，且从指数上市日之后连续性满足要求”的口径生成的候选指数集合。

初始化不是生产 job，只是一次性注册 dynamic partition key。建议实现为受控命令或一次性脚本，执行后删除临时脚本，保留导入审计结果。

操作 口径 注意事项
新增 从 CSV 读取 ts_code，调用 cn_a_index_ts_codes.build_add_request(keys) 或 Dagster instance API 注册。 必须使用正式 DAGSTER_HOME=/Users/congming/.goldenshare/dagster_home；未经用户确认不得执行。
删除 原则上先退役，不优先物理删除 partition key。 删除 key 不会自动删除 raw parquet 或历史 materialization；误删会造成 UI 状态和文件状态脱节。
修改 Dynamic partition key 不做 rename；改代码等同于新增新 key、退役旧 key。 必须记录旧 key 对应 raw 文件是否保留、迁移或废弃。
查询 通过 Dagster UI 或 instance API 查看当前 cn_a_index_ts_codes keys。 实现前应确认 UI 是否满足日常增删查需求；批量导入仍建议命令化。

5. Asset 设计

5.1 Raw asset

Asset key raw_tushare_index_daily_by_code
Partitions cn_a_index_ts_codes
Partition key ts_code，例如 000001.SH
物理路径 raw/tushare/index_daily_by_code/ts_code=<TS_CODE>/part-000.parquet
源接口 index_daily(ts_code, start_date, end_date, limit, offset)
字段口径 Raw 保持 Tushare 源镜像；日期字段保持源站字符串口径，不在 raw 层标准化为 DATE。
Materialization metadata 记录本次运行事实：分区代码、由 trade_date 派生的源接口窗口 start_date/end_date、write_mode、分页数、请求参数、字段列表、产物 URI、行数和列结构。metadata key 以当前 M6 治理后的实现为准，使用 dagster/uri、dagster/row_count、dagster/column_schema 与 goldenshare/*，不再写旧的 top-level path、row_count 或 source_method。

Raw asset 不再读取 silver_index_daily_active_pool，也不再读本地 PostgreSQL active pool。 它只相信自己的 dynamic partition key，即 cn_a_index_ts_codes。

5.2 Silver asset

Asset key silver_index_daily
Partitions cn_a_index_trade_days
Partition key trade_date，例如 2026-05-22
物理路径 silver/index_daily/trade_date=YYYY-MM-DD/part-000.parquet
读取来源 读取 raw-by-code 文件集合，抽取目标 trade_date 对应行。
字段口径 Silver 日期字段统一标准化为 DATE；数值字段做类型标准化；主键为 ts_code + trade_date。

silver_index_daily 的 asset key 建议保留，因为它的业务含义没有变：按交易日产出的指数日线标准事实表。 变化的是它的上游 raw 组织方式，不是下游语义。

6. Job 设计

6.1 Raw 更新 job

Job index_daily_update_job
类型 Partitioned asset job
Partition set cn_a_index_ts_codes
Selection raw_tushare_index_daily_by_code 及 raw checks。
Config trade_date、write_mode

这个 job 的 UI 行为应该类似当前用户截图里的 partitioned asset job：启动时选择一个或多个 ts_code 分区。 但 sensor 自动触发时会为每个 ts_code 发独立 RunRequest，因此日常自动化会产生较多 run；这点已接受。

6.2 Silver 更新 job

Job silver_index_daily_update_job（建议新增）
类型 Partitioned asset job
Partition set cn_a_index_trade_days
Selection silver_index_daily 及 silver checks。

不建议让 index_daily_update_job 同时 selection raw-by-code 和 silver-by-date。 因为两个 asset 的 partition key 语义完全不同，一个是指数代码，一个是交易日。 分开两个 job，可以避免 UI 选择分区时出现“到底选的是代码还是日期”的歧义。

7. Run Config 契约

Raw 更新 job 的 config 只表达目标交易日和写入方式，不再表达指数代码。指数代码来自 partition key；底层 Tushare 请求窗口由 asset 内部映射为 start_date=end_date=trade_date。

ops 或 asset config:
  trade_date: "2026-05-22"
  write_mode: "replace"
字段 类型 含义 校验
trade_date string 本次 raw-by-code 更新的目标交易日，配置中使用 YYYY-MM-DD，请求 Tushare 前转换为 YYYYMMDD。 必须不早于 2000-01-01；主入口不接受日期区间。
write_mode enum 写入模式，第一版只支持 replace。 必须显式传入；sensor 日更默认使用 replace。

7.1 write_mode 语义

模式 语义 适用场景
replace 把当前 ts_code 文件中目标 trade_date 的旧行删除，再写入本次 Tushare 返回行；其它日期历史保留。 日更单日、单日缺口修复。区间修复不是主入口能力，如需支持必须单独设计 repair 入口。
merge 第一版暂不实现。 后续只有在明确需要补充性 upsert，且不会削弱数据覆盖校验时再单独设计。

8. Sensor 设计

8.1 index_daily_sensor

步骤 行为 失败/跳过口径
判断交易日 读取 silver_trade_calendar 或既有交易日 partition，只处理已完成交易日。 非交易日直接 Skip，不发 run。
判断源站 ready 使用 source_readiness/tushare/index_daily.py 对 Tushare index_daily 做只读探测，不写文件。 源站未 ready 时 Skip，不占用 run key。
读取代码集合 从 formal Dagster instance 读取 cn_a_index_ts_codes dynamic partition keys。 没有可用代码时 Skip，并输出中文原因。
判断 raw 缺口 读取 raw-by-code 文件，确认每个 ts_code 是否已经包含目标 trade_date。 已有目标日期的代码不再触发；缺失代码才进入本 tick 候选。
触发 raw 更新 为每个 ts_code 通过 build_run_request(...) 提交 raw 更新请求，config 使用当天 trade_date。 run_key 使用 index_daily:<trade_date>:<ts_code> 防重复。
单 tick 限流 每次 sensor tick 最多提交 500 个 RunRequest。 sensor 默认 STOPPED；首次启用前必须 preview，已完成单 tick 限制为 1 的小样本真实触发验证。
cursor 使用 v1 cursor 顶层记录 target_date、decision、selected_count、blocked_count 和样本；下一批缺口偏移量只保存在 details.next_pending_offset。 cursor 只推进同一个 sensor 的批次；是否缺数据仍以 raw 文件里是否已有目标 trade_date 为准。 
RunRequest 示例:
  job_name: index_daily_update_job
  partition_key: "000001.SH"
  run_key: "index_daily:2026-05-22:000001.SH"
  run_config:
    ops:
      raw_tushare_index_daily_by_code:
        config:
          trade_date: "2026-05-22"
          write_mode: "replace"
  tags: {}

Sensor 触发多代码时会产生多个 run。之前讨论已经接受这类 runs 展示较多的问题。 第一版不通过 GraphQL 或私有 API 强行创建 UI 聚合 backfill，避免引入更难维护的机制。

8.2 Silver 更新触发

由于 raw 和 silver 分区维度不同，Silver 更新建议作为单独阶段处理： 日更时在全部注册指数代码的 raw-by-code 文件都存在且包含目标日期数据后，由 silver_index_daily_sensor 自动触发 silver_index_daily_update_job[trade_date]；历史迁移时则先跑 raw code backfill，再跑 silver trade_date backfill。

当前代码已实现 silver_index_daily_sensor。它只触发 silver，不补 raw、不调用 Tushare、不读取 raw run tags/config。

设计项 silver_index_daily_sensor 口径
职责 只判断某个 trade_date 的 raw-by-code 是否已经足以生成 silver，并触发 silver_index_daily_update_job[trade_date]。
不做什么 不调用 Tushare，不补 raw，不注册 cn_a_index_ts_codes，不注册 cn_a_index_trade_days，不做历史批量回填。
候选日期 只考虑已经注册到 cn_a_index_trade_days 的交易日。第一版日常自动化只处理最新一个待生成 silver 的交易日；历史日期仍通过 UI/backfill 人工分批处理。
Ready 条件 读取 cn_a_index_ts_codes，计算目标日期应参与的指数代码集合；每个代码的 raw_tushare_index_daily_by_code[ts_code] 文件必须包含目标 trade_date。 该 sensor 不扫描 raw check history；真正的数据质量由 raw/silver asset checks 暴露。
缺口处理 任一应参与代码缺 raw 文件或缺目标日期，则返回中文 skip reason，并在 cursor/log metadata 中输出缺口统计和样本；不触发 silver。
触发方式 通过 build_run_request(...) 提交 silver_index_daily_update_job[trade_date]。
run key silver_index_daily:<trade_date>，避免同一个交易日重复提交。
单 tick 数量 第一版最多触发 1 个 trade_date 的 silver run，因为 silver 是按交易日聚合资产，不需要像 raw-by-code 一样每个代码一个 run。
cursor 使用 v1 cursor 顶层记录 target_date、decision、selected_count、blocked_count 和缺失样本；raw ready 数、缺文件数、缺目标日期数、selected_trade_date 放入 details。cursor 只做观测，不替代文件判断。

9. Checks 与质量门禁

9.1 Raw checks

  • raw_index_daily_by_code_file_exists：目标 raw 文件存在。
  • raw_index_daily_by_code_required_columns：字段集合符合 Tushare index_daily 显式字段契约。
  • raw_index_daily_by_code_partition_matches：文件内 ts_code 必须等于 partition key。
  • raw_index_daily_by_code_unique_key：ts_code + trade_date 唯一。
  • raw_index_daily_by_code_date_range_observed：metadata 中上报实际最小/最大 trade_date，不一定阻断。

9.2 Silver checks

  • silver_index_daily_file_exists：目标 silver 分区文件存在。
  • silver_index_daily_partition_date_matches：文件内 trade_date 必须等于分区日期。
  • silver_index_daily_unique_key：ts_code + trade_date 唯一。
  • silver_index_daily_required_columns：字段契约完整。
  • silver_index_daily_price_sanity：价格字段非负，且 high/low/open/close 关系合理。
  • silver_index_daily_coverage_observed：按 cn_a_index_ts_codes 与上市日期口径输出覆盖率、缺失代码样本；第一版建议先 WARN/metadata，避免误阻断。

10. 旧实现安全退场

旧实现退场不能一次性硬删。要先停写、再切新链路、再做引用审计、最后才清理定义和表。 目标是：不误触发旧任务，不让 UI 出现明显错误入口，不破坏历史 run/event 可追溯性。

10.1 退场对象清单

对象 当前状态 退场策略
silver_index_daily_active_pool 旧指数日线 active pool 文件资产，Slice E 已删除 active definition。 新链路不再依赖；当前代码不再消费该 asset。
index_daily_active_pool_update_job 旧维护 active pool 的 job，Slice E 已删除 active definition。 不再作为 UI 可执行生产入口出现，避免误点执行。
goldenshare_lake_meta.index_daily_active_pool 旧 active pool PG 表，当前不再由代码创建或写入。 停止写入，导出审计 CSV，引用清零后再由用户明确批准是否 drop。
goldenshare_lake_meta.index_daily_active_pool_history 旧 active pool 历史表，当前不再由代码创建或写入。 同上。不要误删同 schema 下其它 metadata 表。
raw_tushare_index_daily 旧 trade_date raw asset。 旧 definition 已删除。旧 raw-by-date parquet 已按用户确认物理删除；Dagster 历史 run/event 继续保留为审计记录。

10.3 Dagster 历史执行记录口径

旧 Dagster run/event/backfill 记录不做物理删除。删除 Dagster PostgreSQL 事件记录会破坏审计链路，也容易造成 UI 历史页面异常。 正确做法是让旧 job 从 active Definitions 退场，让新 job 使用新名称和新 tags，从时间线和名称上区分新旧链路。

11. 迁移实施顺序

12. 风险与避坑

混合分区 job 风险

不要把 cn_a_index_ts_codes 和 cn_a_index_trade_days 两套分区的 assets 放进同一个 partitioned asset job。UI 会很难表达“这个 partition 到底是什么”。

Active pool 退场风险

PG 表不能先 drop。必须先停止写入、导出审计、清零引用，再由用户明确批准退场。

历史 UI 链接风险

旧 active Definitions 已提前退场，避免 UI 误点旧入口；历史 run/event 保留审计，不物理清理。

Sensor run 爆炸

每天为每个 ts_code 发 run 会增加 run 数量。第一版接受这个代价，用 tags、run_key、限流降低排查成本。

write_mode 误解

replace 是替换指定日期窗口，不是默认删除整份代码文件。实现和 UI 文案必须写清楚。

日志口径

之前 stdout 方案存在 UI/命令行落点混淆。新链路如需进度日志，应单独设计 Dagster UI 可观测方式，不在本方案里顺手扩展。

14. 验收标准

  • 新 raw asset 可以按单个 ts_code 和指定时间窗口从 Tushare 拉取并原子写入。
  • cn_a_index_ts_codes 可由 CSV 初始化，且 UI/API 可查询。
  • 不再需要 index_daily_active_pool PG 表驱动日常指数池。
  • Silver 仍按 trade_date 产出，并保持下游查询口径稳定。
  • 旧 jobs 不再出现在 active 生产入口里，避免 UI 误点。
  • 旧 Dagster run/event 记录保留可审计，不做危险清理。
  • 任何 PG 表退场都有导出备份、引用审计和用户明确批准。
