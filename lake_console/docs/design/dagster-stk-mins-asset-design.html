Dagster stk_mins 资产落地设计

本文定义股票分钟线 stk_mins 在新 Dagster lake 中的正式分层、分区、资产拆分、历史导入和后续增量路线。 已拍板口径：按交易日分区，按分钟频度拆不同资产；raw 保存 backup 中的原始 clean_next，silver 做代码与停复牌口径标准化，gold 存前复权后的分钟线。

3. 已拍板设计

分区

新增并独立使用 cn_a_stock_mins_trade_days。

它服务 stk_mins 资产族，不污染 cn_a_stock_trade_days、cn_a_stock_current_trade_days。

频度

freq 不进入 Dagster partition key。

五个固定频度拆成 sibling assets：1m、5m、15m、30m、60m。

raw

保存 backup 中的原始 clean_next 数据，作为新湖的历史 raw 基线。

历史导入方法参考 adj factor：bootstrap 文件、注册分区、补录 runless events。

silver / gold

silver 对 raw 做标准化，统一代码与停复牌口径。

gold 保存基于 silver_adj_factor 计算后的 qfq 分钟线。

身份映射

silver_stock_identity_map 是正式业务资产，不是临时 manifest。

它负责把历史源代码映射到标准股票代码，后续由基础数据事实重建。

为什么不使用 MultiPartitionsDefinition(date x freq)： date x freq 的规模本身可以接受，但本项目已确认 freq 是质量边界和运维边界。 拆成不同 asset 后，UI、checks、backfill、历史修复和失败定位更直接；日期仍是调度和回填边界。

4. Partition 设计

cn_a_stock_mins_trade_days = dg.DynamicPartitionsDefinition(
    name="cn_a_stock_mins_trade_days"
)
项目口径
分区键YYYY-MM-DD 股票交易日。
历史起点按 backup clean_next 当前事实，从 2009-01-05 起步；正式开发前需再次只读复核。
历史终点按 backup clean_next 当前事实，到 backup 最新交易日；历史导入执行前需重新只读确认。
日常注册后续新增 stk_mins 专用分区注册 sensor，不能复用或污染股票日频分区。
不做不按股票代码分区，不按分钟时间分区，不做 date x stock x freq。
边界： cn_a_stock_trade_days 当前服务 stock daily 链路，实际数据从 2014-01-02 开始。 stk_mins 历史从 2009-01-05 开始，因此必须独立分区，不能共用股票日频分区。

6. Stock Identity Map 资产设计

silver_stock_identity_map 是股票代码身份归一资产。它解决“同一只股票历史上可能出现过多个交易代码”的问题， 让分钟线、日线、停复牌、复权因子在 silver/gold 层使用同一套标准代码口径。

6.1 业务职责

  • 把旧代码、北交所旧代码、名称变更导致的历史代码统一映射到当前标准代码。
  • 解释 stk_mins 与 silver_stock_daily 的股票集合差异，区分真实缺失和代码变更。
  • 支持 silver_stk_mins_* 标准化，以及 gold_stk_mins_qfq_* 与 silver_adj_factor 的代码对齐。
  • 保留映射来源、置信度和原因，方便后续排查“为什么这条分钟线被归到这个股票代码”。

6.2 字段契约

字段类型说明原因
latest_ts_codeVARCHAR标准股票代码。silver/gold 层最终使用的股票代码。
source_ts_codeVARCHAR源代码或历史代码。raw clean_next 中出现的代码，用于 join 映射。
valid_fromDATE映射有效起始日期。为后续审计映射区间和历史追溯保留时间边界。
valid_toDATE映射有效结束日期，可为空。退市或历史区间结束时需要明确边界。
effective_list_dateDATE标准股票上市日期。支持过滤上市日前分钟线和解释覆盖范围。
effective_delist_dateDATE标准股票退市日期，可为空。当前主口径不服务退市股票，但保留字段便于审计历史来源。
identity_sourceVARCHAR映射来源枚举。允许值为 stock_basic、bse_mapping、namechange。
confidenceVARCHAR置信度枚举。stock_basic 与 bse_mapping 为 confirmed；namechange 推断映射为 inferred。
reasonVARCHAR映射原因。排查和审计时需要看到可读原因。
created_atTIMESTAMP WITH TIME ZONE本次生成时间。full snapshot 每次重建后需要知道生成批次时间。

6.3 初始 bootstrap 来源

阶段来源目标说明
M1-M3 /Volumes/datasource/goldenshare-tushare-lake/manifest/security_identity/security_identity_map.parquet data_lake/silver/basic/stock_identity_map/part-000.parquet 作为初始化来源，一次性 bootstrap 到新湖；不是长期运行时 fallback。

初始 bootstrap 必须只读复核旧湖文件 schema、行数、source_ts_code 唯一性、枚举值和日期字段。 写入新湖后必须补录 runless materialization 与 blocking check events，否则 Dagster UI/readiness 无法识别该基础资产已经可用。

6.4 长期生成逻辑

长期口径不是继续读取旧湖 manifest，而是由新湖基础事实重建 full snapshot。

输入用途状态边界
silver_stock_basic 生成 source_ts_code = latest_ts_code 的基础身份行，并提供上市/退市日期。 当前 Dagster 已有正式资产；按当前业务口径只服务当前上市股票池。
bse_mapping 生成北交所旧代码到新代码映射，置信度为 confirmed。 后续需在 Dagster 中接成正式基础资产，不能长期读旧 lake_console manifest。
namechange 根据曾用名历史推断少量历史代码到当前代码的映射，置信度为 inferred。 后续需在 Dagster 中接成正式基础资产；推断规则必须有专项测试和冲突检查。

生成规则保持 full snapshot：每次上游基础事实更新后重新生成整张 silver_stock_identity_map。 当前数据规模只有几千行，重建比增量维护更稳，更容易审计，也避免历史窗口被局部补丁污染。

6.5 更新入口与触发机制

  • 正式资产：silver_stock_identity_map。
  • 正式 job：后续单独设计 stock_identity_map_update_job，selection 只包含该 asset 及其 checks，不顺手更新分钟线。
  • 触发条件：silver_stock_basic、bse_mapping、namechange 任一上游更新并通过 blocking checks 后，允许重建身份映射。
  • 消费门禁：silver_stk_mins_* 只读依赖该 asset，必须确认 materialized 且 blocking checks passed 后才允许生成。
  • 历史初始化：M1-M3 只做 bootstrap 和事件补录；不把旧湖 manifest 做成日常依赖。

6.6 Blocking checks

  • 文件存在且行数大于 0。
  • schema 与字段契约完全一致。
  • source_ts_code 非空且唯一。
  • latest_ts_code 非空。
  • identity_source 只能为 stock_basic、bse_mapping、namechange。
  • confidence 只能为 confirmed、inferred。
  • valid_to 若非空，必须不早于 valid_from。
  • 同一 source_ts_code 不允许映射到多个不同 latest_ts_code。
  • namechange 推断映射如果与已确认映射冲突，必须 fail，不允许静默覆盖。

7. Raw 层导入设计

raw 层保存 backup 中的原始 clean_next 数据，作为新湖历史分钟线基线。

项目口径
读取来源/Volumes/datasource/backup/research/stk_mins_by_date_clean_next/freq=*/trade_date=*/*.parquet，正式执行前重新只读复核路径和文件名。
写入目标/Volumes/datasource/data_lake/raw/tushare/stk_mins/freq=*/trade_date=*/part-000.parquet。
迁移方式复用 adj factor 已验证的方式：先实现 bootstrap spec/helper，再 dry-run、小样本、全量执行。

M2 已落地的 bootstrap helper

  • stk_mins_bootstrap_spec(freq, lake_root, backup_root) 固定五个 raw dataset key：raw_stk_mins_1m、raw_stk_mins_5m、raw_stk_mins_15m、raw_stk_mins_30m、raw_stk_mins_60m。

  • bootstrap_stk_mins_partition_to_raw(...) 写新湖 raw 时始终输出 part-000.parquet，默认拒绝覆盖已有目标文件。
  • stock_identity_map_bootstrap_spec(...) 与 bootstrap_stock_identity_map_to_silver(...) 只服务 silver_stock_identity_map 初始 full snapshot，默认拒绝覆盖已有目标文件。
  • M2 不新增 active Dagster asset/job/sensor/check，不注册分区，不补录 events，不执行正式迁移。

Raw checks

  • 文件存在。
  • schema 与 raw contract 一致。
  • 文件内 freq 与 asset 频度一致。
  • 文件内日期或分区日期与 partition_key 一致。
  • ts_code + trade_time 唯一。
  • 价格、成交量、成交额字段满足 backup clean_next 的历史容忍口径：raw 只拦截空值、负值和空代码；历史 low=0、vwap=0、停牌结构行全 0、个别 OHLC 区间残留不在 raw 层拦截，后续 silver 标准化再治理。
  • 分区 key 已注册到 cn_a_stock_mins_trade_days。
待开发前只读复核： backup clean_next 的历史 schema、文件名、全量分区范围、五个频度文件覆盖率必须在 M0 再审计一次，不把此前聊天中的结果当成实时事实。

8. Silver 标准化设计

silver 层目标不是简单复制 raw，而是把 raw clean_next 调整为新 Dagster lake 中可长期消费的标准事实。 标准化重点是代码口径、交易日口径、停复牌口径和字段契约。

8.1 代码口径

  • 使用 silver_stock_identity_map 把旧代码归一到当前标准代码，例如 000022.SZ -> 001872.SZ、北交所旧代码到 920xxx.BJ。
  • silver 分钟线不得直接读取旧湖 manifest；只能依赖新湖正式 asset silver_stock_identity_map。
  • 同一 trade_time + latest_ts_code 如果同时出现旧代码和新代码行，必须先审计价格是否完全一致；一致时按新代码保留一行，不一致时 fail check，不静默择优。

8.2 停复牌口径

  • 不能要求 silver stk_mins 与 silver_stock_daily 每日股票集合完全相等。
  • 预期股票集合应按以下口径判断：silver_stock_daily[trade_date] 中有行情的股票，加上 silver_stock_suspend_daily[trade_date] 中可解释停牌的股票。
  • raw clean_next 中可由停牌表解释的结构行允许进入 silver，不作为缺失或脏数据。
  • 不在 stock daily 中、也不在 suspend_d 中、且无法被身份映射解释的股票，进入待审计差异，不直接写成 green。

8.3 字段契约

字段类型说明
ts_codeVARCHAR标准化后的股票代码。
freqINTEGER分钟频度，取值为 1、5、15、30、60。
trade_dateDATE交易日。
trade_timeTIMESTAMP分钟 bar 时间。
open / high / low / closeDOUBLE未复权价格。
volDOUBLE成交量；历史 raw 可能是整数，silver 统一为数值契约。
amountDOUBLE成交额。
exchangeVARCHAR交易所。
vwapDOUBLE成交均价。
追溯字段： 是否在 silver 物理字段中保留 source_ts_code 需要在 schema 开发前单独拍板。 默认建议不放入正式主字段，避免破坏 clean_next 面向计算的简洁 schema；映射统计和样本写入 materialization/check metadata。

8.4 Silver checks

  • schema 与字段类型一致。
  • freq、trade_date、trade_time 与分区一致。
  • ts_code + trade_time 唯一。
  • 标准代码必须存在于 silver_stock_basic 当前上市股票池，或被设计文档明确允许。
  • 代码集合差异必须能被 stock_daily、suspend_d、identity map 三类口径解释。
  • 不可解释差异必须作为 blocking check failure，不能静默落入 silver。

9. Gold qfq 设计

gold 层保存前复权后的分钟线，输入为标准化后的 silver stk_mins 与 silver_adj_factor。 gold 是计算结果，不回写 raw/silver，也不覆盖原始 clean_next。

9.1 计算口径

qfq_price = original_price * adj_factor(trade_date) / latest_adj_factor(ts_code)
  • adj_factor(trade_date) 来自同一股票同一交易日的 silver_adj_factor。
  • latest_adj_factor(ts_code) 使用当前最新可用复权因子作为前复权基准。
  • 若某只股票最新复权因子发生变化，需要从该股票最早可用分钟线日期向后重算 gold qfq。
  • gold qfq 不记录历史版本；它表达当前最新复权口径下的分钟线结果。

9.2 Gold checks

  • gold 行数与对应 silver 分区一致。
  • ts_code + trade_time 唯一。
  • qfq 后价格非负；停牌结构行按 silver 允许口径处理。
  • 每个 ts_code + trade_date 都能找到 silver_adj_factor。
  • 抽样复算 qfq 公式，确认 open/high/low/close 一致。

10. Jobs 与 Sensors 初步边界

本节只定义边界，不提前锁死最终 job/sensor 名称。编码前需按 sensor tags、readiness、run request/cursor 门禁再出详细方案。

对象职责边界
历史 raw bootstrap helper 从 backup 导入 raw 文件，注册 cn_a_stock_mins_trade_days 历史分区。 不运行正式 asset job；执行前必须 dry-run、小样本、全量三步审批。
raw event 补录 helper 补录 raw materialization 与 raw checks。 只追加 event log，不写文件，不产生 Runs 页面记录。
历史 silver/gold 生成 helper 批量生成历史 silver 和 gold 文件。 不重新请求 Tushare，不通过日常 job 覆盖 raw。
日常 update jobs 按单日分区更新五个频度 raw/silver/gold。 job 只做 asset selection，不写业务逻辑。
日常 sensors 注册分钟线交易日分区，并在上游 ready 后提交 run。 sensor 只做门禁，不在下游 job 内补上游。

12. 风险与处理原则

风险处理原则
backup clean_next 与旧湖正式 clean_next 文件名/范围不一致 M0 必须只读复核，bootstrap 不靠历史印象拼路径。
silver 标准化时旧代码和新代码同日冲突 同值可去重；不同值必须 fail check，不能静默选择。
身份映射从 bootstrap 来源变成长期生成来源时口径漂移 silver_stock_identity_map 字段契约和 checks 先固定；长期生成逻辑必须生成同一契约，不允许消费者改读旧湖 manifest。
停牌结构行被误判为 daily 缺失 expected universe 使用 stock_daily + suspend_d，不使用 stock daily strict equality。
qfq 最新因子变化导致历史需重算 gold qfq 明确是当前复权口径结果；因子变化后按受影响股票回刷历史 gold。
历史批量补录 event 过慢 必须用聚合审计和样本 readiness，不允许上千分区逐个深扫 event history。

13. 非目标

  • 不把 freq 放入 run config。
  • 不使用 date x stock x freq 分区。
  • 不把 backup/legacy 写入正式 asset key。
  • 不把旧湖 security_identity_map 作为长期运行时依赖；它只作为初始化 bootstrap 来源。
  • 不把 qfq 结果原地覆盖 raw 或 silver。
  • 不在本设计中接入 90/120 分钟派生、by-symbol-month 重排或 MACD 等指标资产。
  • 不把旧 lake_console 运行账本作为 Dagster 正式运行状态。

15. 验证口径

开发阶段只做静态和临时目录测试，不运行正式 Dagster，不读写正式 instance。

  • gold 阶段：临时 DuckDB 文件覆盖 qfq 公式、因子缺失、行数一致、字段类型。
