分区

raw 独立使用 cn_a_stock_mins_trade_days，承载 2009 年以来全量分钟线日期。

silver 独立使用 cn_a_stock_mins_silver_trade_days，只承载 2014 年以后可被 stock daily / suspend / namechange 等依赖解释的日期。

频度

freq 不进入 Dagster partition key。

五个固定频度拆成 sibling assets：1m、5m、15m、30m、60m。

raw

历史基线保存 backup 中的原始 clean_next 数据；默认日常增量从 prod DB raw_tushare.stk_mins 只读抽取；Tushare stk_mins 保留为人工备用入口。

历史导入方法参考 adj factor：bootstrap 文件、注册分区、补录 runless events。三个来源写入同一套 raw asset key、路径、schema 和 checks。

silver / gold

silver 对 raw 做标准化，统一代码与停复牌口径。

gold 保存基于 silver_adj_factor 计算后的 qfq 分钟线。

身份映射

silver_stock_identity_map 是正式业务资产，不是临时 manifest。

它负责把历史源代码映射到标准股票代码，后续由基础数据事实重建。

为什么不使用 MultiPartitionsDefinition(date x freq)： date x freq 的规模本身可以接受，但本项目已确认 freq 是质量边界和运维边界。 拆成不同 asset 后，UI、checks、backfill、历史修复和失败定位更直接；日期仍是调度和回填边界。

6. Stock Identity Map 资产设计

silver_stock_identity_map 是股票代码身份归一资产。它解决“同一只股票历史上可能出现过多个交易代码”的问题， 让分钟线、日线、停复牌、复权因子在 silver/gold 层使用同一套标准代码口径。

6.1 业务职责

6.4 长期生成逻辑

长期口径不是继续读取旧湖 manifest，而是由新湖基础事实重建 full snapshot。

输入用途状态边界
silver_stock_basic 生成 source_ts_code = latest_ts_code 的基础身份行，并提供上市/退市日期。 当前 Dagster 已有正式资产；按当前业务口径只服务当前上市股票池。
bse_mapping 生成北交所旧代码到新代码映射，置信度为 confirmed。 后续需在 Dagster 中接成正式基础资产，不能长期读旧 lake_console manifest。
namechange 根据曾用名历史推断少量历史代码到当前代码的映射，置信度为 inferred。 后续需在 Dagster 中接成正式基础资产；推断规则必须有专项测试和冲突检查。

生成规则保持 full snapshot：每次上游基础事实更新后重新生成整张 silver_stock_identity_map。 当前数据规模只有几千行，重建比增量维护更稳，更容易审计，也避免历史窗口被局部补丁污染。

6.5 更新入口与触发机制

  • 正式资产：silver_stock_identity_map。
  • 正式 job：stock_identity_map_update_job 已实现，selection 只包含该 asset 及其 checks，不顺手更新分钟线。
  • 触发条件：silver_stock_basic、bse_mapping、namechange 任一上游更新并通过 blocking checks 后，允许重建身份映射。
  • 消费门禁：silver_stk_mins_* 只读依赖该 asset，必须确认 materialized 且 blocking checks passed 后才允许生成。
  • 历史初始化：M1-M3 只做 bootstrap 和事件补录；不把旧湖 manifest 做成日常依赖。

6.6 Blocking checks

  • 文件存在且行数大于 0。
  • schema 与字段契约完全一致。
  • source_ts_code 非空且唯一。
  • latest_ts_code 非空。
  • identity_source 只能为 stock_basic、bse_mapping、namechange。
  • confidence 只能为 confirmed、inferred。
  • valid_to 若非空，必须不早于 valid_from。
  • 同一 source_ts_code 不允许映射到多个不同 latest_ts_code。
  • namechange 推断映射如果与已确认映射冲突，必须 fail，不允许静默覆盖。

M4C 已实现的 Tushare merge_repair 受控修复模式

M4/M4B 的默认写入策略是为了日常安全：目标 raw 分区文件已存在且 checks 通过时直接复用，不重复请求源站，不覆盖历史 baseline。 这个策略不能作为唯一能力，否则少量历史坏行无法通过 Dagster 正式链路修复。 M4C 已在同一套 raw_stk_mins_* assets 内增加受控 merge_repair 模式，不新增平行 asset，不另起临时 job 分支，不绕开 raw checks。

Config schema 与 Launchpad Scaffold 口径

write_mode 必须设计为 Dagster Selector，而不是简单字符串。 目的不是让运营记住一堆散落 key，而是让 Launchpad schema 明确知道 merge_repair 分支下面有哪些字段。 用户在 UI 中选择或编辑为 merge_repair 分支后，Scaffold / schema panel 必须能展示并补齐 stock_codes、start_time、end_time 结构；如果后续只读 UI 验证发现本地 Dagster 1.13.6 做不到这一点，不得执行正式 repair，必须先重新设计。 

# 日常安全模式：只选择 reuse_existing 分支，不需要额外参数。
ops:
  raw_stk_mins_1m:
    config:
      source: tushare
      write_mode:
        reuse_existing: {}

# 人工修复模式：只选择 merge_repair 分支，修复参数写在该分支下面。
ops:
  raw_stk_mins_1m:
    config:
      source: tushare
      write_mode:
        merge_repair:
          stock_codes:
            - 000030.SZ
          start_time: "09:00:00"
          end_time: "19:00:00"
  • write_mode 同一时间只能选择一个分支；reuse_existing 与 merge_repair 不能同时出现。
  • reuse_existing: {} 表示日常安全模式：已有合格文件直接复用，目标不存在才按正常来源生成。
  • merge_repair 表示人工修复模式：只修指定股票、当前 asset 频度、当前 partition 日期和指定时间窗口。
  • stock_codes 必须是非空列表；禁止把全市场股票池塞进 repair 分支。
  • start_time、end_time 使用 HH:MM:SS，日期来自 asset partition key，不允许在 config 里另填一个会与 partition 冲突的 trade date。
  • 第一版 merge_repair 只允许 source=tushare；prod DB 近期补数继续走 stock_mins_raw_update_from_prod_job 的日常/缺口口径，不与 Tushare repair 在同一次 run 中混用。

修复写入算法

  1. 根据当前 asset 名称确定频度，例如 raw_stk_mins_1m 只能修 1min，不得通过 config 越权修其它频度。
  2. 根据 partition key 和 start_time/end_time 生成 Tushare 请求窗口，例如 2016-12-19 09:00:00 至 2016-12-19 19:00:00。
  3. 对 stock_codes 中每个代码调用 Tushare stk_mins，字段固定为 ts_code,trade_time,open,close,high,low,vol,amount,freq,exchange,vwap。
  4. 若任一指定股票返回 0 行，repair run 必须失败；不能静默认为“修好了”。
  5. 读取现有目标文件 raw/tushare/stk_mins/freq={freq}/trade_date={partition_key}/part-000.parquet；repair 目标文件必须已存在且能通过基础 schema 校验，缺文件场景走正常历史迁移或正常 raw 更新，不用 repair 模式临时造整日文件。
  6. 把 Tushare 返回行归一到 raw schema，并校验所有返回行都属于指定 stock_codes、当前 asset 频度、当前 partition 日期和请求时间窗口。
  7. 合并时只替换返回结果覆盖到的 ts_code + trade_time 键；如果原文件没有这些键，则追加新行。不得删除同股票同窗口内 Tushare 未返回的其它已有行，避免一次不完整源站响应扩大损坏范围。
  8. 合并后按 ts_code, trade_time 排序，写入临时 parquet，再用原子替换更新 part-000.parquet。
  9. 修复 run 必须产生正常 Dagster materialization 和 blocking check events；不得使用 runless event 伪装本次修复，也不得只写文件不让 UI/readiness 更新。
  10. 本次修复事实写入 materialization metadata，并经治理 helper 自动使用 goldenshare/* 命名空间：source_method=tushare_merge_repair、write_mode=merge_repair、repair_stock_code_count、repair_start_time、repair_end_time、repair_returned_row_count、repair_replaced_row_count、repair_appended_row_count。

禁止事项与安全边界

  • 禁止用 merge_repair 覆盖整个交易日分区、整频度分区或全市场股票池。
  • 禁止在 sensor、schedule、automation 中自动生成 merge_repair run；该模式只允许人工明确指定。
  • 禁止把 merge_repair 用作历史缺口 backfill 主路径；历史缺口仍需单独列范围、请求量、耗时和回滚方式。
  • 禁止在 repair 中同时读取 Tushare 与 prod DB；一次 run 只能有一个来源。
  • 禁止 repair 绕过 raw checks；合并后七个 raw blocking checks 必须继续执行，失败时该分区不能被视为 ready。
  • 禁止把 repair 专用的股票代码、时间窗口、返回行数写成 run tags；它们属于 run config 或 materialization/check metadata，不属于分类 tag。

8. Silver 标准化设计

silver 层目标不是复制 raw，而是把 raw clean_next 标准化成可以长期消费、可以继续生成 qfq gold 的分钟线事实。 raw 保留历史原貌；silver 负责代码归一、停牌结构删除、价格修复、成交量/成交额归一、exchange 归一和 blocking checks。 本节是后续 silver 开发的正式口径，代码实现不得只参考旧审计脚本或临时报告。

8.1 范围与边界

  • silver assets 规划为五个 sibling assets：silver_stk_mins_1m、silver_stk_mins_5m、silver_stk_mins_15m、silver_stk_mins_30m、silver_stk_mins_60m。
  • partition 改为 cn_a_stock_mins_silver_trade_days，不再复用 raw 全量分钟线分区；freq 继续由 asset 名称表达，不进入 partition key。
  • 第一轮严格审计和 silver 历史验收范围从 2014-01-01 起；若未来要生成更早历史，必须先按同一口径补做只读审计。
  • silver 不回写 raw，不修改 backup clean_next，不修改 M3 历史 raw baseline；所有修复都发生在 silver 生成链路。
  • silver 不做 qfq；前复权只在 gold 层用 silver_adj_factor 计算。
  • silver 不把临时报表当运行依赖；审计报表只能作为设计证据，真正运行时依赖必须是正式 asset、仓库 seed 或明确 helper。

8.3 标准化执行顺序

  1. 读取目标 freq/trade_date raw 文件；若是粗频度，还读取同日 1m raw 文件。
  2. 对 1m 数据先应用仓库价格修正 catalog，得到“可用于 silver 和粗频度重算的标准 1m 输入”。catalog 由版本化 seed 在进程内一次性加载和校验，分区生成阶段只做内存查表，不允许每个分区重复读取 CSV。
  3. 用 silver_stock_identity_map 将 source_ts_code 归一为 latest_ts_code，silver 主字段写标准代码。
  4. 删除可由 silver_stock_suspend_daily 解释的全日停牌结构行；这些行不写入 silver，也不作为异常。
  5. 对粗频度中的非停牌全 0、局部价格 0、价格关系异常，优先用同股票同日期的标准 1m 输入重算对应 bar。
  6. 按用户确认的成交量口径修正 vol/amount：vol=0 时 amount=0；0 < vol < 100 的历史小额异常按 0 处理。
  7. 按股票代码后缀生成标准 exchange，不继承 raw 既有 exchange。
  8. 输出前执行 silver checks；无法解释或无法修正的差异必须 fail，不能静默写入 silver。

  • 使用 silver_stock_identity_map 把旧代码归一到当前标准代码，例如 000022.SZ -> 001872.SZ、北交所旧代码到 920xxx.BJ。
  • silver 分钟线不得直接读取旧湖 manifest；只能依赖新湖正式 asset silver_stock_identity_map。
  • silver_stock_identity_map 当前复核结果：旧 565 条频度-日期-代码记录、113 个股票-日期组合全部 ok；当前 active 身份映射为 5,775 行，source_ts_code 唯一、枚举和 latest_ts_code 参照均通过。
  • 同一 trade_time + latest_ts_code 如果同时出现旧代码和新代码行，必须先审计价格是否完全一致；一致时按新代码保留一行，不一致时 fail check，不静默择优。
  • silver 物理字段不保留 source_ts_code，以保持分钟线事实表面向计算消费的简洁契约；映射前后代码、去重统计和样本进入 materialization/check metadata。若未来要改变这个口径，必须作为 schema 变更单独设计，不能在 M5 编码中临场添加字段。

8.5 停复牌与 universe 口径

  • 不能要求 silver stk_mins 与 silver_stock_daily 每日股票集合完全相等。
  • silver 输出股票集合以 silver_stock_daily[trade_date] 中有行情的股票为主；全日停牌日期的数据不进入 silver 分钟线。
  • silver_stock_suspend_daily[trade_date] 只用于解释 raw 中为什么会出现停牌结构行，或解释为什么某只上市股票当天没有日线和分钟线；它不是 silver 输出行的保留依据。
  • raw clean_next 中可由停牌表解释的全日停牌股票分钟行，silver 生成时全部删除，不只限于 OHLC 全 0 结构行。
  • 不在 stock daily 中、也不在 suspend_d 中、且无法被身份映射解释的股票，进入待审计差异，不直接写成 green。

8.6 价格修复与重算口径

  • silver 层不允许 open/high/low/close 出现 0、负数或空值；这比 raw 层更严格。
  • 1m 是 silver 的基础修复事实源；在使用 1m 之前必须先应用版本化价格修正 catalog。
  • 价格修正 seed 字段固定为：freq,trade_date,ts_code,trade_time,open,high,low,close,reason。第一版只允许 freq=1，且必须由 check 确认修正后的 OHLC 为正且满足价格关系。

8.7 成交量、成交额与 vwap 口径

  • vol、amount 不允许为负。
  • 若 vol=0，silver 将 amount 归一为 0；这是用户确认的历史修复口径。
  • 若 0 < vol < 100，按历史小额异常处理，silver 将 vol 和 amount 归一为 0。
  • 除上述两类外，vol >= 100 且 amount <= 0，或其它无法解释的成交量/成交额矛盾必须 fail。
  • vwap 不进入 silver 主字段，不作为 silver blocking 对象；raw 中 vwap 只保留为源事实。
  • 最新复核结果：197 行真正不依赖 vwap 的 vol/amount 矛盾，在 vol=0 和 vol<100 两条规则下剩余阻塞为 0。

8.8 Exchange 与时间口径

  • silver 不继承 raw exchange，统一按股票代码后缀归一：.SH -> SSE，.SZ -> SZSE，.BJ -> BSE。
  • 未知后缀、空代码、无法归一 exchange 必须 fail。
  • trade_date 来自 partition key，trade_time 必须落在该交易日；不使用固定分钟时间网格做 blocking 检查。
  • 审计结果显示 null_trade_time_count=0、partition_date_mismatch_count=0、suffix_unmapped_count=0。

9. Gold qfq 设计

gold 层保存前复权后的分钟线，输入为标准化后的 silver stk_mins 与 silver_adj_factor。 gold 是计算结果，不回写 raw/silver，也不覆盖原始 clean_next。 本节是进入 M7 后的正式设计方案；M7A 性能验证工具、M7B 主表契约基础、M7C 纯计算 helper、M8A gold assets 和 M8B blocking checks 已实现。 已拍板：下一步先按命令方式生成历史 gold qfq 物理文件并补录 runless events，不先接日常 job/sensor。 正式 gold jobs/sensors 后移到历史 baseline 和 event 事实对齐之后再开发。 任何正式写湖、Dagster job、sensor、backfill 或 event 补录仍需单独审批。

已废弃的实体设计： 不保留 gold_stk_mins_qfq_daily_summary，也不保留 gold_stk_mins_qfq_factor_repair_summary。 日常完成状态由五个 gold_stk_mins_qfq_* 的 materialization 和 blocking checks 表达； repair 是否需要执行、影响哪些股票、为什么成功或跳过，由 repair job 内的 DuckDB 检测和 repair check metadata 表达。 后续代码、schema、path、catalog、job selection、sensor 门禁和文档都不得重新引入这两个实体。

9.1 计算口径

qfq_price = original_price * adj_factor(trade_date) / latest_adj_factor(ts_code)
  • adj_factor(trade_date) 来自同一股票同一交易日的 silver_adj_factor。
  • latest_adj_factor(ts_code) 是按股票取当前最新可用 silver_adj_factor 后得到的计算基准，不是一个必须长期落盘的新资产；M7 首选在 DuckDB SQL 中用 CTE/临时表生成。
  • 当 trade_date 正好等于最新因子日期时，adj_factor(trade_date) 与 latest_adj_factor(ts_code) 的数值通常相同；历史日期则通常不同。两者不能在设计上合并成一个概念。
  • 若某只股票最新复权因子发生变化，需要从该股票最早可用分钟线日期向后重算 gold qfq。
  • gold qfq 不记录历史版本；它表达当前最新复权口径下的分钟线结果。

9.3 日常单日生成链路（历史 baseline 完成后）

日常链路只做一个交易日的五频度 qfq 生成，不在同一个 job 里顺手做历史 repair。 正常顺序为 raw → silver → gold qfq。 该链路不是当前下一步；必须等历史 gold qfq 文件和 runless events 补齐、UI/readiness 对齐后再落地。

对象职责边界
stock_mins_qfq_daily_update_job 选择五个 gold_stk_mins_qfq_* assets 及其 blocking checks。 不触发 raw/silver，不做历史 repair，不访问 prod DB/Tushare，不写 gold_stk_mins_qfq_daily_summary。
stock_mins_qfq_daily_sensor 在最新 silver 分区 ready、silver_adj_factor[trade_date] ready 后触发单日 gold job。 sensor 只看当前目标日期的轻量 readiness，不逐历史分区深扫；目标是否完成以五个 gold assets 的当日 materialization + blocking checks 为准。

日常 qfq 必须强依赖 silver_adj_factor[trade_date]。 如果当天分钟线已完成但当天复权因子未 ready，gold qfq 必须 skip 或失败，不能退回上一交易日因子继续计算。 禁止为了状态观测新增 gold_stk_mins_qfq_daily_summary；状态由正式 gold asset materialization、blocking checks 和 check metadata 表达。

9.4 历史 baseline 生成与 runless event 补录

历史 gold qfq baseline 不走 Dagster job/backfill。它采用与 silver 历史生成相同的执行口径： 先用命令式 helper 直接生成正式 gold qfq 物理文件，再通过 runless asset events 补齐 Dagster UI/readiness 需要的 materialization 和 check 事实。 这条链路只用于历史 baseline，不替代后续日常 Dagster job/sensor。 M8C 已实现 plan-gold-qfq-history 与 generate-gold-qfq-history CLI，并已按 freq/year 批量生成正式历史 gold qfq 物理文件。 M8D 已实现并正式执行 plan-gold-qfq-events、report-gold-qfq-events、audit-gold-qfq-final CLI：按 freq/year “审一年、写一年”完成全量 Dagster runless materialization/check event 补录。

阶段口径原因
文件生成 按 dry-run、小样本、全量三步执行；历史批次粒度为 freq -> year。每批用 DuckDB 从该频度该年份的 silver 分区和 silver_adj_factor 批量计算 qfq，再按 ts_code/year 写出 data_lake/gold/quote/stk_mins_qfq/freq=*/ts_code=*/year=*/part-000.parquet。 避免复制第二套 qfq 公式；避免按日期反复读写同一个股票年份文件；命令式批处理比 Dagster 大量历史 run/backfill 更可控。
写入顺序 历史生成按 freq -> year 批量生成，并对目标 freq/ts_code/year 文件做互斥写入：同一个目标文件在一次历史 baseline 中只写一次。若某一年数据量实测过大，才允许退化为 freq -> year -> stock_code batch，但仍不得按日期反复改同一个年份文件。 gold 物理文件按股票年份组织；不同交易日属于同一个股票年份文件。按日期循环会让同一个文件被重复重写几百次，并发写还会出现后完成任务覆盖先完成任务的风险。
目标已存在 第一版默认目标 gold 文件已存在即失败；只有后续显式设计并通过审计的 --skip-existing-valid 或覆盖模式才允许跳过或重写。 历史 baseline 是正式资产初始化，不应默默覆盖已有正式文件；出现已存在文件时先停下来解释来源和一致性。
历史范围 以 cn_a_stock_mins_silver_trade_days registered partitions 为逻辑事实源，并与 silver 文件集合做交叉审计；只有“已注册且 silver 文件存在”的日期进入 gold 历史生成。 gold 只能从已验收的 silver 日期派生，不能把未注册或不该进入 silver/gold 的日期写入历史 baseline。
事件补录 文件生成和只读审计通过后，再补录 gold_stk_mins_qfq_* 的 runless materialization 与 8 个 blocking check events。M8D helper/CLI 使用年度批量审计：每批 freq/year 只用 DuckDB 聚合扫描一次 gold、silver 与 adj factor 文件，再按日期拆出 materialization/check events；正式执行是“审一年、写一年”：某个 freq/year 审计通过后立即补录这一年 events，再进入下一年。文件审计或 gold check 不通过时，禁止补绿 event，必须先停下来修正文件事实。不再整频度一次性补录，也不得退回按日期重复深扫同一批股票年份文件。 Dagster UI 和 readiness 看 event log，不扫描文件目录；event 一旦补录是追加事实，必须在文件审计之后执行。
规模估算 当前 2014+ silver 分区约 3014 个交易日，五频度共 15070 个 asset partitions；每个 partition 补 1 materialization + 8 checks，预计约 135630 条 runless events。 该量级低于此前 raw 分钟线补录事件量，可按 dry-run、小样本、全量执行；但不得在 dry-run 里逐分区深扫 event history。
最终审计 用聚合口径确认文件分区集合、registered partition 集合、materialization partition 集合和 check succeeded/failed 计数一致，并抽样验证 readiness。 历史批量审计必须用集合与计数，不用日常 sensor 的逐分区 readiness 主循环。
2025 年只读估算： 以正式 silver 湖 data_lake/silver/quote/stk_mins 为输入，只读统计 2025 年 243 个交易日。 五频度合计约 422,372,516 行、约 6,838.5 MiB（约 6.68 GiB）silver parquet。 最大频度为 1m：约 317,132,552 行、4,751.2 MiB（约 4.64 GiB）；按 ts_code/year 拆分后，估算最大单个 1m 股票年份文件约 0.97 MiB。 这说明历史 baseline 应按 freq -> year 批量写文件，而不是按交易日循环重写同一批股票年份文件。

9.5 因子变化 repair 链路

前复权基准发生变化时，历史 qfq 必须回刷受影响股票。repair 不并入日常 qfq job 的关键路径，而是在日常 gold qfq 当日五频度全部 ready 后单独触发。 是否需要 repair、哪些股票需要 repair，必须在 repair job 启动后用 DuckDB 检测，不放进 sensor。

步骤口径原因
监听信号 stock_mins_qfq_factor_repair_sensor 监听当日五个 gold_stk_mins_qfq_* 分区全部 materialized 且 blocking checks 全绿。 只看当前目标日期五个 gold assets 的 ready 状态，不扫描历史明细；不引入 gold_stk_mins_qfq_daily_summary。
变化检测 repair job 内用 DuckDB 比较 silver_adj_factor[trade_date] 与上一股票交易日的 silver_adj_factor[previous_trade_date]，筛出因子变化股票。 几千只股票的因子差异比较很轻；没有变化时 job 直接成功，并由 repair check metadata 写明 reason=no_factor_changed 和 changed_code_count=0。
历史回刷 若存在变化股票，按股票逐个循环处理，重算该股票从最早可用 silver 分钟线日期到当前日期的 qfq，并重写该股票相关年份文件。 物理文件按 freq + ts_code + year 组织，repair 不再需要重写大量全市场 date-partition 文件。
完成记录 不新增 gold_stk_mins_qfq_factor_repair_summary。repair job 成功、跳过或失败原因写入正式 repair check metadata。 避免把“运行状态说明”升级成长期业务资产；状态事实由 run、check result 和 metadata 承载即可。
重要并发边界： 日常日期分区写入与 repair 股票历史回刷都会写同一个 freq/ts_code/year 文件。 后续 job/backfill 必须串行，或用 Dagster concurrency 限制保护同一 gold qfq 文件族，禁止多个日期分区并发写同一股票年份文件。

12. 风险与处理原则

风险处理原则
backup clean_next 与旧湖正式 clean_next 文件名/范围不一致 M0 必须只读复核，bootstrap 不靠历史印象拼路径。
silver 标准化时旧代码和新代码同日冲突 同值可去重；不同值必须 fail check，不能静默选择。
身份映射从 bootstrap 来源变成长期生成来源时口径漂移 silver_stock_identity_map 字段契约和 checks 先固定；长期生成逻辑必须生成同一契约，不允许消费者改读旧湖 manifest。
停牌结构行被误判为 daily 缺失 expected universe 使用 stock_daily + suspend_d，不使用 stock daily strict equality。
qfq 最新因子变化导致历史需重算 gold qfq 明确是当前复权口径结果；因子变化后先由 repair job 用 DuckDB 检测受影响股票，无变化直接成功，有变化再按股票逐个回刷历史 gold。
按日期物理分区的 qfq 文件不适合原地修单只股票 Parquet 不能原地改几行；单股历史 repair 若按日期物理分区会重写大量全市场文件。正式口径已改为 freq + ts_code + year，repair 只重写受影响股票的年份文件。
gold sensor 门禁过重导致超时 日常 sensor 只看目标日期五个 gold assets 的 readiness，不做历史分区深扫；必要的文件事实校验放到 asset/check 内用 DuckDB 聚合完成。
历史批量补录 event 过慢 必须用聚合审计和样本 readiness，不允许上千分区逐个深扫 event history。

开发阶段只做静态和临时目录测试，不运行正式 Dagster，不读写正式 instance。

  • 契约阶段：编译路径、schema、partition、metadata helper；静态门禁确认没有新增 active asset/job/sensor。
  • bootstrap 阶段：临时目录小样本迁移，验证字段、路径、分区 key 和 event 补录 helper。
  • raw 日常阶段：临时目录与 fake Tushare resource 覆盖分页、freq 字符串归一、已存在目标复用、坏目标拒绝覆盖、七个 raw checks、job selection 与两个 sensors 的时间门禁。

  • silver 阶段：临时 DuckDB 文件覆盖 1m 标准化、代码映射、停牌结构行删除、价格修正 seed、粗频度按 1m 重算、成交量/成交额归一、exchange 归一、重复键冲突和 10 个 silver checks 的 pass/fail。
