Dagster 股票分钟线 Prod DB Raw 导出稳定性治理方案

本文档只用于准备后续代码开发。当前不直接开发、不写数据湖、不写 prod DB、不写 Dagster instance。目标是把 stock_mins_raw_update_from_prod_job 在 raw_stk_mins_1m 步骤长时间无进展的问题拆清楚，并形成可 review 的落地方案。

状态：待 review 日期：2026-06-29 范围：stk_mins raw prod_db source 原则：先方案，后开发

1. 当前结论

下一步不是直接开发。 需要先确认本文档的技术口径，尤其是批次大小、超时策略、临时文件路径和恢复流程。确认后才进入代码实现。

这次卡住不是普通的“1m 数据量大所以慢”。已审计到的现象是：prod PostgreSQL 端没有持续运行的 raw_tushare.stk_mins 查询，本地 Dagster step 进程 CPU 接近 0，仍持有 prod PG 连接， 目标 1m 目录为空。这更像是 DuckDB postgres scanner 在一次性大批量远程读取时进入了不可观测的等待状态。

因此治理重点不是加一句日志或延长等待，而是把当前“一整天全市场一次性拉取”的实现改成“有批次、有超时、有进度、有清理”的实现。

3. 当前代码链路

这次问题所在的代码路径是： 

_materialize_raw_stk_mins_partition
  -> write_raw_stk_mins_partition_from_prod_db
    -> build_prod_stk_mins_duckdb_source_sql
    -> _write_raw_stk_mins_rows_from_prod_db_source

当前 prod_db 分支的关键行为：

  • build_prod_stk_mins_remote_query 对当日、单个频度、全部当前上市代码构造一条远程 SQL。
  • build_prod_stk_mins_duckdb_source_sql 用 DuckDB postgres_query(...) 读取 prod PG。
  • _write_raw_stk_mins_rows_from_prod_db_source 用一条 CREATE TEMP TABLE prod_stk_mins_source AS SELECT * FROM (...) 把所有行读进 DuckDB 临时表。
  • 只有这一步完成后，才会做行数校验、scope 校验、COPY parquet 和 os.replace。
人话解释：现在像是让一个搬运工一次性把全市场 1 分钟数据全搬完，中途没有分批、没有超时、没有“搬到第几车”的进度。一旦卡住，外面只能看到“开始了”，看不到卡在哪里。

4. 改造目标和硬边界

目标

  • 让 stock_mins_raw_update_from_prod_job 的 prod_db raw 导出在 1m 大分区下可控、可观测、可失败退出。
  • 保持最终数据湖产物不变：每个 freq/trade_date 仍只有一个正式 part-000.parquet。
  • 保持数据 schema、字段顺序、路径、asset 名、job 名、sensor 名、partition 口径不变。
  • 失败时不得留下半成品正式文件；不得写绿色 Dagster 状态。

硬边界

  • 不改 raw_stk_mins_* asset 名称、job selection、sensor 触发逻辑、run key、run config。
  • 不改 prod 表结构，不写 prod DB，只读 raw_tushare.stk_mins。
  • 不引入逐行 Python 写 parquet；批处理也必须用 DuckDB set-based SQL 写 parquet。
  • 不增加细碎 Dagster asset check，不扩大 Dagster DB 状态量。
  • 不把 Tushare fallback 混进 prod_db 日更主链路。Tushare repair 仍走现有 repair 机制。

5. 拟采用方案

5.1 按股票代码批次读取 prod DB

将当前“全部代码一次查询”改为“稳定排序后的代码批次查询”。推荐默认批次大小为 500 个代码： 当前约 5,530 个股票代码时，1 个频度约 12 个批次。1m 每批大约十万行级别，不再把 1,331,766 行压到单次 DuckDB postgres scanner 调用里。

策略 当前 改造后
远程查询次数 每个频度 1 次 每个频度约 12 次，数量随代码数线性变化
单次数据量 1m 单次约 133 万行 1m 单次约十万行级别
进度观测 只有 started / completed 每批有 started / completed / elapsed / row_count
失败处理 卡住时没有中间边界 批次超时或失败，清理 staging，asset 失败退出

5.2 staging 文件再合并成正式 part

每个批次先写入临时 staging parquet。所有批次完成后，再用 DuckDB 读取 staging parquet，做统一 schema casting、scope 校验、去重校验和排序，最后写入临时 part-000.parquet.tmp，通过 os.replace 原子替换正式文件。 

raw/tushare/stk_mins/freq=1/trade_date=YYYY-MM-DD/
  .prod_db_staging/run_id=<run-id-or-uuid>/batch=00001.parquet
  .prod_db_staging/run_id=<run-id-or-uuid>/batch=00002.parquet
  part-000.parquet.tmp
  part-000.parquet

staging 目录只存在于本次写入过程中。成功或失败都应在 finally 中清理；如果进程被强杀，下一次运行开始前也要清理本资产自己的过期 staging 目录。

5.3 超时和连接生命周期

每个批次都必须有明确超时。优先方案是在 DuckDB Postgres attach 的连接信息中注入 PostgreSQL statement_timeout 和连接超时配置；开发时必须先用单元测试和最小只读验证确认 DuckDB postgres extension 支持该 conninfo 口径。

推荐初始值：

  • 单批次 statement_timeout：180s
  • 连接超时：沿用现有 connect_timeout，但不能把密码、host、user 写进 SQL 字符串。
  • 超过单批次超时即失败退出，不自动无限重试。
如果开发验证发现 DuckDB postgres extension 无法稳定支持 statement timeout，本方案不允许硬凑。 需要停下，单独评估 psycopg server-side cursor / COPY streaming 方案，而不是继续扩大当前不可控实现。

5.4 运行日志和 metadata

使用现有 DgStdoutLogger("stk_mins")。日志只写阶段、数量和耗时，不打印完整 SQL、完整代码列表、连接串或样本数据。

  • raw_stk_mins_prod_extract_started：记录 partition、freq、code_count、batch_size、batch_count。
  • raw_stk_mins_prod_extract_batch_started：记录 batch_index、batch_count、batch_code_count。
  • raw_stk_mins_prod_extract_batch_completed：记录 batch_index、row_count、returned_code_count、elapsed_ms。
  • raw_stk_mins_prod_extract_merge_started：记录 staging_file_count、source_row_count。
  • raw_stk_mins_prod_extract_merge_completed：记录 output_row_count、returned_stock_code_count、elapsed_ms。

materialization metadata 在保留现有字段基础上追加批处理摘要：batch_size、 batch_count、query_count、max_batch_elapsed_ms、 source_row_count、extract_strategy=prod_db_code_batches。

7. 测试和门禁

单元测试

  • 批次规划：输入 5,530 个代码时，按稳定排序和默认 500 大小切成确定批次。
  • SQL contract：每个 batch 仍有显式字段、freq/date/code 过滤、ORDER BY ts_code, trade_time，无 select *。
  • 写入成功：多个 batch parquet 合并后，最终 part-000.parquet schema、字段顺序、scope 和行数正确。
  • 失败清理：任一 batch 失败时，不产生正式 part-000.parquet，staging 目录被清理。
  • 空结果失败：全部 batch 总行数为 0 时失败；部分代码无数据仍沿用当前 empty_stock_code_count 口径。
  • 日志门禁：stdout 不包含完整 SQL、完整代码列表、连接串、密码或 DataFrame。

静态门禁

  • 禁止 prod_db raw helper 再出现单块 CREATE TEMP TABLE prod_stk_mins_source AS SELECT * FROM ({source_sql})。
  • 禁止 production helper 对全部代码只生成一个 postgres_query。
  • 禁止修改 stock_mins_raw_update_from_prod_job、sensor 名称、run key 和 partition 口径。
  • 禁止新增细碎 asset check 或扩大 Dagster DB 状态量。

8. 实施顺序

  1. 你确认本文档口径，尤其是批次大小、超时、staging 路径和是否包含连接生命周期治理。
  2. 进入代码实现：先改 prod SQL/batch helper 和 tests，不动 sensor 开关，不跑正式 Dagster。
  3. 跑本地单元测试和静态门禁。
  4. 只读验证 prod 单批次 source probe，确认 timeout 和批次 SQL 能正常返回。
  5. 在 sensor 仍关闭的前提下，审批手动运行 stock_mins_raw_update_from_prod_job 的目标日期。
  6. 成功后再评估是否开启 sensor。

10. 风险和停止条件

  • 如果 DuckDB postgres extension 无法对 batch 查询设置可靠超时，停止，不进入正式运行。
  • 如果 batch 写入后 source/target 行数或 scope 校验不一致，停止，不写正式文件。
  • 如果实现需要改 job/sensor 行为、湖路径、schema 或新增状态实体，停止，重新评审方案。
  • 如果真实 1m 手动运行仍出现长时间无进展，保留日志和 batch 边界证据，再决定是否切换提取技术路线。
本方案的核心收益是：即使未来再失败，也应该失败在一个可解释的批次上，而不是只有一句 raw_stk_mins_started 后沉默几十分钟。
