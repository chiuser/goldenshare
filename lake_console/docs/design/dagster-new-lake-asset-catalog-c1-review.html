Dagster 新湖 Asset Catalog C1 开发方案

本文档记录 C1 开发方案与落地口径。目标是把当前新湖 Dagster assets、checks、paths、metadata、schema、source 和补录事实收敛到一个只读 registry， 通过静态治理防止漂移，不改变任何 asset/job/sensor/check 运行语义。

状态 C1 已按代码口径落地为只读 registry + static gates。
更新时间 2026-06-07
目标目录 lake_console/orchestrator/src/orchestrator/defs/catalog/
核心边界 只读 registry + static gates；不生成资产，不触发 Dagster，不写 lake。

1. 拍板结论

事项 结论 原因
C1 覆盖范围 覆盖 lake_console/orchestrator 当前所有正式 active assets，包括 lake_root_health。 避免产生“哪些正式 asset 不进 catalog”的新漂移点。
非表类 asset 允许 column_schema=None，当前主要用于 lake_root_health。 health asset 不写 parquet，不应伪造表字段契约。
测试事实源 替换 test_asset_governance_contracts.py 中的隐形 ASSET_CONTRACTS。 Catalog 写完后必须成为治理测试事实源，否则只是多一份文档化列表。
业务代码消费 C1 不让 asset/check/job/sensor/bootstrap 运行逻辑消费 catalog。 先把事实源立起来，降低运行风险。C3 再选择性消费。
命名 模型名为 LakeAssetCatalogEntry，不使用 V1/V2 命名。 这是新湖 Dagster asset catalog，不是旧湖 backend catalog，也不是数据基座 DatasetDefinition。

2. 当前事实依据

C1 落地前，当前代码已经存在一张隐形 catalog，集中在治理测试和 run contracts 中。C1 的目标不是创造新事实，而是把已经散落的事实移入正式 registry。 C1 落地后，治理测试只保留 active Dagster definitions 作为 live spec 读取入口，dataset/path/schema/check 事实由 registry 提供。

事实类型 当前位置 C1 处理方式
资产身份、layer、domain、dataset id/name 历史上在 tests/test_asset_governance_contracts.py::ASSET_CONTRACTS 已迁入 LakeAssetCatalogEntry。
字段契约 defs/run_contracts/asset_column_schemas.py Catalog entry 直接引用 tuple[ColumnContract, ...] | None。
metadata keys defs/run_contracts/metadata.py Catalog static gates 对账 dataset_id、dataset_name、source_system、data_contract、path_template。
layer/domain tags defs/run_contracts/asset_tags.py Catalog entry 使用现有 AssetLayer、DataDomain 枚举。
路径模板 defs/paths.py 与历史治理测试里的 ASSET_PATH_TEMPLATES 已迁入 catalog；非文件型/serving asset 可为 None。
blocking checks defs/checks/**，目前由测试和人工维护 Catalog 记录 check name 集合，static gate 对账 active checks。
source 语义 SourceSystem metadata、Tushare/prod DB/helper/bootstrap 文档 拆成字段契约来源、实际摄取来源、默认日常来源、bootstrap 来源。
当前数量口径 治理测试当前登记 40 个正式 active assets。C1 覆盖这 40 个；其中 lake_root_health 是 platform health asset，可无表字段 schema。

3. C1 硬约束

约束 落点 验收
必须覆盖所有 active assets。 list_lake_asset_catalog_entries() 与 active definitions 对账。 缺登记、多登记均测试失败。
必须覆盖所有当前治理事实。 dataset id/name、tags、source_system、data_contract、path_template、column_schema、blocking checks。 metadata/tag/schema/check drift 均 static gate 失败。
禁止改变生产语义。 不改 asset function、job selection、sensor、check 计算、bootstrap helper。 本轮只新增 registry 和测试，不触碰运行代码。
禁止引入旧湖 backend 或数据基座运行时依赖。 orchestrator.defs.catalog.lake_assets 只依赖 orchestrator 内部 run contracts。 static gate 禁止 import src.foundation 或 lake_console.backend。
禁止 V1/V2 命名。 文件、类、函数、文档命名。 代码搜索无 LakeAssetDefinitionV1 / V2 这类命名。
默认不做业务代码消费。 asset/check/job/sensor/bootstrap 不从 catalog 读取。 C1 后行为与之前一致。

4. 数据模型定义

C1 的模型必须足够表达当前 active assets 的事实，同时避免变成过度抽象的生成器。模型是只读定义卡，不做 IO，不访问 Dagster instance，不扫描 lake。

4.3 字段说明

字段 类型 是否必填 来源/对账 说明
asset_key str 是 asset.key.to_user_string() Dagster asset key。C1 使用字符串，避免 registry 直接持有 asset definition 对象。
dataset_id str 是 goldenshare/dataset_id 稳定数据集 ID。多个频度 asset 可共享同一个 dataset id，例如 stk_mins_qfq。
dataset_name str 是 goldenshare/dataset_name、DATASET_CHINESE_NAMES 中文显示名。不是 asset key，也不是旧湖节点名。
layer AssetLayer 是 goldenshare/layer 使用现有枚举：raw、silver、gold、serving、platform。
data_domain DataDomain 是 goldenshare/data_domain 使用现有枚举：basic_data、quote_data、index_topic、project_config、derived_metric、platform_observability。
group_name str 是 asset definition group_name Dagster UI 分组事实，用于 static gate 对账。
source_system SourceSystem 是 goldenshare/source_system 保留现有 metadata 口径，用于兼容当前 definition metadata 对账；不再单独承担实际摄取来源语义。
data_contract str 是 goldenshare/data_contract 资产字段/质量契约名。必须与 definition metadata 一致。
data_contract_source DataContractSource 是 catalog 新事实 字段契约来源。用来解决“字段契约来自 Tushare，但日常数据可来自 prod DB”的歧义。
column_schema tuple[ColumnContract, ...] | None 表类 asset 必填；非表类可空 dagster/column_schema 直接引用稳定字段契约对象。C1 不再用 column_schema_name 字符串做主事实，减少二次映射漂移。
path_template str | None 文件型 asset 必填；serving/health 可空 goldenshare/path_template 正式 lake 物理路径模板。ClickHouse serving 和 health asset 没有 parquet path 时为 None。
partition_model PartitionModel 是 asset partitions_def、路径模板、PartitionModelDefinition 具体 leaf 分区模型。命名采用“分区维度 + layer + 资产名/资产簇”，例如 trade_date_partition_raw_stock_mins。
source_api str | None 有源 API 时必填 goldenshare/source_api Tushare API 名或其它源接口名。derived/seed/platform asset 可为 None。
source_doc str | None Tushare/prod 源契约建议必填 goldenshare/source_doc 本地源文档或契约文档 ID。
ingestion_sources tuple[IngestionSource, ...] 是 catalog 新事实 该 asset 允许的实际摄取来源集合。可包含 Tushare API、prod DB 只读、旧湖 bootstrap、派生计算等。
default_daily_ingestion_source IngestionSource | None 日常生产 asset 必填；非日常可空 job/sensor/asset 设计口径 日常更新默认来源。历史 bootstrap 来源不得伪装成默认日常来源。
bootstrap_sources tuple[IngestionSource, ...] 可为空 tuple bootstrap / runless event 文档和 helper 允许用于历史初始化、旧湖迁移、直写补录的来源。
blocking_check_names tuple[str, ...] 可为空 tuple，但必须显式 defs/checks/** 正式 blocking checks 名称。C1 static gate 对账 check definition。
write_policy WritePolicy 是 asset/helper 写入代码 表达写入粒度和原子替换口径，例如 stock-year、partition file、single file、ClickHouse sync。
event_policy EventPolicy 是 Dagster run / runless event 设计口径 表达是否支持 runless event backfill。日常增量仍必须走正式 Dagster run。
performance_contract LakeAssetPerformanceContract 是 catalog 新事实 记录批次维度、计算引擎、Python 职责和源请求策略。C1 只登记和静态检查，不生成 planner。
notes str 否，默认空字符串 人工说明 只放必要说明，不承载机器门禁。

5. 枚举取值口径

5.1 DataContractSource

枚举值 含义 例子
tushare_raw_contract 字段契约来自 Tushare 源接口白名单。 raw_tushare_stock_daily、raw_stk_mins_1m
prod_serving_contract 字段契约来自已审计的 prod serving/core 白名单。 后续 prod DB 最佳事实源接入。
derived_contract 字段契约来自新湖派生计算。 gold_stk_mins_qfq_90m、gold_market_breadth_daily
seed_contract 字段契约来自项目 seed 或固定配置。 主要指数名单相关资产。
platform_contract 平台健康或观测资产契约。 lake_root_health

5.2 PartitionModel 分层命名

PartitionModel 采用两层结构：上层 PartitionModelFamily 表达人的分类视角， 例如 trade_date_partition；下层 PartitionModel 表达具体资产簇 leaf model。 leaf 命名规则固定为： 

分区维度 + layer + 资产名/资产簇

示例：
trade_date_partition_raw_stock_mins
trade_date_partition_silver_stock_mins
trade_date_partition_gold_stock_mins_qfq_stock_year_file

qfq 保留特例 trade_date_partition_gold_stock_mins_qfq_stock_year_file： 它的 Dagster asset 按 trade_date 分区，但物理文件按 freq/ts_code/year 存储。 后缀 stock_year_file 用来保留这个最关键的物理写入事实。

10. 性能门禁

C1 本身不跑数据、不扫 lake、不访问正式 Dagster instance，因此运行性能风险来自测试和代码加载，而不是数据处理。 但 catalog 必须提前承载后续 C2/C3 的性能事实。

项 C1 口径
对象数 当前 40 个 active assets。
日期/分区数 C1 不枚举分区。
源请求数 0。不访问 Tushare、prod DB、旧湖、ClickHouse。
DuckDB 扫描/写入 0。不创建 DuckDB 连接。
正式 lake 写入 0。不写 /Volumes/datasource/data_lake。
Dagster instance 读写 0。不运行 dg，不读取正式 event log。
测试复杂度 集合对账和 definition metadata 读取，规模固定在 active definitions 数量级。
不可接受阈值 任何 C1 测试需要访问 lake、Dagster instance、prod DB、Tushare，均视为设计错误。

11. 非目标项

C1 不做以下事情
  • 不自动生成 Dagster assets、checks、jobs、sensors。
  • 不改变任何 asset 的 @dg.asset(...) 参数。
  • 不改变 qfq daily/repair sensor readiness。
  • 不改变 bootstrap、repair、runless event CLI 行为。
  • 不接旧湖 backend UI，不新增数据库表，不新增配置项。
  • 不 import src.foundation 运行时。

13. Review 关注点

字段类型是否足够明确 当前模型用枚举约束 source、partition、write、event、compute engine，避免后续自由字符串乱飞。
是否过度抽象 C1 不生成资产、不消费 catalog，只做 registry 和 static gates。抽象风险可控。
是否能支撑后续数据接入 Tushare、prod DB、旧湖 bootstrap、derived assets 已有独立来源字段，不再压进一个 source_system。
是否保护性能口径 每个 entry 有 performance contract，后续 C2/C3 可用来禁止 per-stock Python 明细循环。
