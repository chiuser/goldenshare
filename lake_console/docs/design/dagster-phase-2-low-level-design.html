0. Phase 3 分区口径修正

Phase 3 Slice 3.2.2 后，股票日频资产族的正式生产分区统一为 cn_a_stock_trade_days； cn_a_trade_days 只保留为全量 SSE open day 备份和对照分区集合，不再作为股票生产资产、股票 sensors 或 market breadth 自动化的正式分区来源。 本 LLD 涉及股票日频生产、停复牌、股票日线和市场宽度的分区口径，均按 cn_a_stock_trade_days 理解。 股票资产族分区合法性通过正式 blocking asset checks 表达；业务 asset 写入函数不保留定制化写前 guard，避免把质量门禁混入数据写入逻辑。

1. 设计硬边界

本 LLD 的底线： 第二期不是扩大业务资产范围，也不是重写第一期。第二期只围绕四件事展开： 旧湖历史数据按 Tushare raw 契约 bootstrap 到新湖；TushareResource 拉取新增 raw；股票行情日频链路自动化；market breadth 下游只在上游质量门禁通过后生产。
边界 LLD 口径
数据湖路径 正式 asset path 只允许 data_lake/raw、data_lake/silver、data_lake/gold。旧湖只作为 bootstrap 输入，不出现在新 Dagster asset 的正式 path 中。
raw 定义 新湖 raw 是 Tushare 源站镜像。旧湖 bootstrap 写入 raw 前必须投影字段、纠偏类型，写出来的 parquet 要看起来像 Tushare API 直接返回。
job 拆分 禁止设计一个全局 daily_foundation_job。第二期按 calendar、basic、quote、breadth 拆 job，避免下游被无关资产卡住。
下游行为 daily_market_breadth_job 永远不主动补上游、不调用 Tushare、不修 raw。上游未就绪时，不启动下游 run，等待 declarative automation 下一次评估。
ready 定义 ready 不等于 silver materialized。ready 必须包含 materialization + raw/silver blocking checks passed + 必要共享基础资产就绪。
自动化安全 stock_trade_day_sensor、suspend_d_sensor、stock_basic_sensor、stock_daily_sensor 第二期默认 STOPPED，人工小范围验证后再逐个打开。
配置新增 新增 Tushare token、旧湖 root、自动化开关等配置前，必须先做配置项审计。禁止新增临时 env 文件或散落配置。

6. Bootstrap 低层设计

Bootstrap 是历史迁移工具链，不是长期生产链路。对某一个具体数据集来说，bootstrap 通常只执行一次：把旧湖历史数据按 Tushare raw 契约写入新湖 raw。 但这套“读旧湖、字段投影、类型纠偏、写新 raw、跑 raw checks”的通用机制后续会被很多数据集复用，所以它不能退化成散落的手工 cp 命令。 Bootstrap 入口、spec 和通用执行逻辑长期保留，用作迁移审计记录和后续类似数据集接入的复用基础。

边界要拆开：bootstrap 通用引擎只负责把旧湖历史数据写成符合 Tushare 契约的新湖 raw。 bootstrap migration job 可以为了验收继续选择对应 silver assets 和 checks，但 silver 仍由正式 silver asset 生成，不由 bootstrap 引擎生成一套旁路结果。

硬边界： bootstrap 不参与每日自动化，不被 stock_trade_day_sensor、schedule 或 declarative automation 触发。 具体数据集 bootstrap 完成并验收后，日常更新只走 TushareResource 和对应的 calendar/basic/quote jobs。

6.3 suspend_timing 类型漂移固定处理

旧湖里不同交易日的 suspend_d parquet 文件不一定有完全一致的字段类型。 最典型的是 suspend_timing：有的日期有类似 14:51-14:57 的日内停牌时间，DuckDB 会把它看成字符串； 有的日期这一列全是空，DuckDB 可能把它推断成 INTEGER/NULL。这就是“类型漂移”。

如果 bootstrap 批量读取这些旧湖分区，不做处理就可能出现两类问题： 一类是直接读取失败；另一类更危险，是 DuckDB 自动推断出一个不符合 Tushare 源站契约的类型，然后悄悄写进新湖 raw。 所以这里必须先按字段名合并，再强制 cast 成新湖 raw 要求的类型。 

select
  cast(ts_code as varchar) as ts_code,
  strftime(cast(trade_date as date), '%Y%m%d') as trade_date,
  cast(suspend_timing as varchar) as suspend_timing,
  cast(suspend_type as varchar) as suspend_type
from read_parquet(
  old_path,
  hive_partitioning=false,
  union_by_name=true
)
union_by_name=true 的意思是：多个 parquet 文件合并时按字段名对齐，不按字段位置瞎拼。 cast(suspend_timing as varchar) 的意思是：不管旧湖里 DuckDB 把它猜成什么，新湖 raw 都统一写成 nullable string。 写完后还要做 raw schema check，如果新湖 raw 里的 suspend_timing 不是字符串列，直接失败，不能继续生成 silver。

6.5 第一个使用者：suspend_d

suspend_d 作为 bootstrap 引擎的第一个使用者。它字段少、业务逻辑相对单纯，但能覆盖 bootstrap 最关键的能力： 按 trade_date 分区迁移、旧湖字段类型纠偏、nullable string cast、允许 0 行结果、写入新 raw 后复用 raw checks。

不建议第一个使用者选择 stock_daily。它数据量更大，重复行、冲突行、完整性 WARN 和业务检查更多， 容易把 bootstrap 引擎问题和数据质量问题搅在一起。先用 suspend_d 把迁移引擎跑稳，再扩到 calendar/basic/stock_daily。

8. Asset 实现设计

8.1 raw asset 日常职责与 bootstrap 边界

第二期的长期生产口径是：raw asset 日常更新由 TushareResource 写入。 bootstrap 只是历史迁移入口，它可以写入同一套新湖 raw 路径，并记录 source_method=old_lake_bootstrap 的 materialization metadata； 但不应该把 old_lake_bootstrap 做成每日 raw asset 的长期分支。 

long-term raw asset execution:
  use TushareResource
  write Tushare source-mirror raw parquet
  emit MaterializeResult metadata:
    source_method = "tushare_api"

one-time bootstrap execution:
  use BootstrapDatasetSpec + old_lake_executor
  write the same raw parquet contract
  emit migration metadata:
    source_method = "old_lake_bootstrap"

shared contract:
  same asset key
  same physical path
  same raw fields
  same raw checks
  same downstream silver/gold code
source_method 是运行 metadata，不是业务字段，也不是下游判断逻辑。 任何 sensor、schedule、declarative automation 都不能选择或触发 old_lake_bootstrap。

    evaluation = record.event.dagster_event.event_specific_data
    target = evaluation.target_materialization_data

# 正确口径
for record in get_asset_check_execution_history(...):
    if record.status.value not in {"SUCCEEDED", "FAILED"}:
        continue
    evaluation = record.event.dagster_event.event_specific_data
    target = getattr(evaluation, "target_materialization_data", None)
    if not target or target.storage_id != materialization_storage_id:
        continue

11.1.1 Slice 2.2.1b：stock daily source readiness 与当天交易日

新需求来自日常使用口径：Tushare 源站的当日日线发布时间不精确，可能在当晚 19:00 或 20:00 左右才可用。本地新湖期望在 Tushare 源站当天数据可用后尽快拉取，而不是固定等到第二天。 因此第一版“只取小于当前自然日的最近 open day”的实现，只能作为安全保守版本，不能作为最终日常更新口径。

  candidate_day = today if today is SSE open day
                  else latest open day before today

  if candidate_day == today:
    if local time < 16:00 Asia/Shanghai:
      skip without probing Tushare
    poll Tushare source readiness about every 10 minutes after 16:00

11.1.2 防未来交易日误跑流程

silver_trade_calendar 是“交易日计划表”，它可能提前保存全年日历。 例如今天是 2026-05-20，日历里可能已经有 2026-12-31 open=true。 这个未来日期在日历上是正确的，但未来行情、未来停复牌、未来市场宽度还没有真实发生，不能注册后立刻运行。

latest_completed_trade_date 是 sensor 的安全边界，意思是“目前最晚哪个交易日已经真实结束，理论上可以拉数据”。 当前实现采用两段规则：小于当前自然日的 open day 可以注册；如果今天本身是 SSE 开市日，则只有本地时间 16:00 后才允许注册今天 partition。 但注册 partition 不等于运行数据生产；股票日线生产仍由 stock_daily_sensor 在 Tushare 源站 ready 且上游 checks 通过后触发。

    allowed to register:
      2026-05-18

partition 定义 不变。继续使用 cn_a_stock_trade_days dynamic partitions。 低 只改变谁触发 run，不改变 partition key 语义。
stock_trade_day_sensor 已从“注册 partition + 返回股票日线 RunRequest”改成“只返回 dynamic partition add request”。 低 已通过 Slice 2.2.1e 完成，避免与资产族 sensor 双重触发。
stock_daily_update_job 触发方式 从早期交易日 sensor 显式触发，迁移为 stock_daily_sensor 触发；当前 stock_trade_day_sensor 只注册分区。 中 已验证当前 sensor 方案；若未来再迁移 declarative automation，必须重新小样本验证。
重复运行防护 短期靠 sensor run_key=f"stock_daily_update:{key}" 防重复；长期要依赖 automation 的 missing 状态和 Dagster run 状态。 中 迁移时要先小范围验证同一天不会被 sensor 和 automation 同时提交 run。
未来更多日频资产族 当前多 sensor 方案下，新增 fundflow_daily_job 等不需要改 stock_trade_day_sensor。 收益高 这是当前方案的主要收益：交易日发现和数据域生产解耦。
上线切换 当前保持四个 sensors 默认 STOPPED 或小范围运行；需要生产化时再逐个开启。 中 建议继续按资产族分步打开：先确认 partition 注册，再确认基础资产，再确认日线，不一次性打开全部自动化。
总体评估：从短期方案迁移到当前多 sensor 方案的成本已经验证为低到中等，主要改的是调度/自动化层，不涉及数据文件迁移、asset key 迁移或路径迁移。 后续若要进一步迁移 declarative automation，真正需要谨慎验证的是 Dagster 当前版本的 automation 行为，以及它和 dynamic partitions、checks readiness 的组合方式。

12. Market Breadth 自动化门禁

daily_market_breadth_job 是下游业务生产 job，只负责 gold。它不等待成 RUNNING，不轮询上游，不调用 Tushare。 “等待”发生在 declarative automation 不请求下游 run 这一层。

12.1 ready 条件

  trade_date is not a future open day

12.2 实现优先级

2.2.2a 验证结果： declarative automation 可以可靠读取直接上游 blocking checks； 正式 instance 只读检查也确认 2026-05-22 的 stock_basic、suspend_d、stock_daily readiness 状态均可读取且为 ready。 gold_market_breadth_daily 当前直接依赖只有 silver_stock_daily，这与业务口径一致； 因此下一轮应直接给 gold asset 加 automation 条件，而不是新增中间 readiness asset。
优先级 方案 使用条件
1 自定义 AutomationConditionSensorDefinition + upstream blocking checks。 当前 Dagster 版本验证通过，适用于 breadth gold 这种只依赖直接标准事实资产的下游生产。正式入口不使用全局默认 sensor，而是使用每个 gold asset 自己的 automation sensor，只 target 单个目标资产。
2 Asset sensor 后备，只负责查询 readiness 后发起下游 run 或返回 SkipReason。 只有 declarative automation 无法表达 checks readiness，或必须强控单 tick 分区数量、复杂中文 skip reason、复杂业务窗口时使用。
3 通知/审计 sensor。 不作为生产触发入口，只用于提示上游缺失、checks 失败或连续未跑。
如果必须使用 asset sensor 后备，它也不能主动补上游。它只能返回 SkipReason 或触发 daily_market_breadth_job。
短窗口 automation 验证结论： dagster sensor preview default_automation_condition_sensor 和自定义 market_breadth_automation_sensor 都不能像普通 sensor 一样预览，当前版本会返回 NotImplementedError；automation condition 的安全验证应使用 dg.evaluate_automation_conditions(...) 做只读评估。 2026-05-23 正式 instance 只读评估结果显示，从空 cursor 评估 gold_market_breadth_daily 会请求 2975 个缺失分区，范围从 2014-01-02 到 2026-03-31。 连续第二次 tick 模拟仍请求同一批缺失分区，因此在历史 gold 大量缺失时，不能短暂开启 default_automation_condition_sensor 做小窗口验证；否则可能触发大范围历史 runs。 后续不把默认 automation sensor 作为正式触发入口；历史缺失分区通过 UI 分批 backfill，日常触发改为自定义 breadth automation sensors。

控制目标： 自定义 automation sensor 的目的不是解决历史 2975 个缺失分区。 历史分区补齐仍通过 Dagster UI 分批 backfill。 这个 sensor 的职责是把日常 market breadth 自动触发从全局默认 sensor 中收敛出来，明确控制 target、默认状态、评估频率、run tags、description 和启用策略。
控制项 第一版口径 原因
target 只选择 gold_market_breadth_daily。 避免默认全局 sensor 扫描其它未来带 automation condition 的资产。
default_status STOPPED。 上线前必须先做只读评估；历史 gold 补齐前不得自动开启。
minimum_interval_seconds 建议第一版 600 秒。 market breadth 不需要高频评估；Dagster sensor interval 是最小间隔，不是精确 cron。
run_tags 至少包含 trigger=automation_condition 和 asset_family=market_breadth。 方便 Dagster UI 中区分人工 run、UI backfill 和 automation run。
非交易日 不在本 sensor 里重复判断自然日。 stock_trade_day_sensor 控制 cn_a_stock_trade_days partition 注册；非交易日没有 partition key，即使评估也不会生成非交易日分区。
历史缺失 不靠 sensor 限流解决。 历史补齐应由 UI backfill 分批执行；sensor 启用前必须用 dg.evaluate_automation_conditions(...) 确认请求范围。
use_user_code_server 第一版不启用。 当前只使用 Dagster 内置 condition；未来若写自定义业务 condition，例如最近 N 个 A 股交易日、业务冻结标记或复杂窗口，再单独验证。
