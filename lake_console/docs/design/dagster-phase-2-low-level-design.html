0. Phase 3 分区口径修正

Phase 3 Slice 3.2.2 后，股票日频资产族的正式生产分区统一为 cn_a_stock_trade_days； cn_a_trade_days 只保留为全量 SSE open day 备份和对照分区集合，不再作为股票生产资产、股票 sensors 或 market breadth 自动化的正式分区来源。 本 LLD 涉及股票日频生产、停复牌、股票日线和市场宽度的分区口径，均按 cn_a_stock_trade_days 理解。 股票资产族分区合法性通过正式 blocking asset checks 表达；业务 asset 写入函数不保留定制化写前 guard，避免把质量门禁混入数据写入逻辑。生产前置事实门禁单独处理：silver_stock_daily 依赖 silver_stock_basic 当前上市股票池，已在写入前校验 stock basic freshness，防止人工运行绕过 sensor 后静默过滤新股。

1. 设计硬边界

本 LLD 的底线： 第二期不是扩大业务资产范围，也不是重写第一期。第二期只围绕四件事展开： 当时旧湖历史初始化已结束，相关执行器现已清退；保留 TushareResource 拉取新增 raw、股票行情日频链路自动化、market breadth 上游质量门禁三项设计。
边界 LLD 口径
数据湖路径 正式 asset path 只允许 data_lake/raw、data_lake/silver、data_lake/gold。当前禁止旧湖作为读取或 bootstrap 输入；候选使用独立正式 staging 根。
raw 定义 新湖 raw 保持当前 Tushare 源字段契约。当时旧湖初始化做过字段投影和类型纠偏；该执行路径已删除，不构成当前接入方式。
job 拆分 禁止设计一个全局 全局日更 job。第二期按 calendar、basic、quote、breadth 拆 job，避免下游被无关资产卡住。
下游行为 daily_market_breadth_job 永远不主动补上游、不调用 Tushare、不修 raw。上游未就绪时，不启动下游 run，等待 declarative automation 下一次评估。
ready 定义 ready 不等于 silver materialized。ready 必须包含 materialization + raw/silver blocking checks passed + 必要共享基础资产就绪。
自动化安全 stock_trade_day_sensor、raw_suspend_d_update_job_sensor / silver_suspend_d_update_job_sensor、raw_stock_basic_update_job_sensor / silver_stock_basic_update_job_sensor、raw_stock_daily_update_job_sensor / silver_stock_daily_update_job_sensor 第二期默认 STOPPED，人工小范围验证后再逐个打开。
配置新增 新增 Tushare token、自动化开关等配置前，必须先做配置项审计。禁止恢复旧湖 root 配置，禁止新增临时 env 文件或散落配置。

Slice 2.2.2a 历史验证结论，已被后续事故修正： 当前 Dagster 1.13.6 中，AutomationCondition.on_missing() 与 AutomationCondition.all_deps_blocking_checks_passed() 曾被用来表达“直接上游同分区可用且 blocking checks 通过时，请求缺失下游”。 后续 19aa0df9-01a9-4c36-afc7-b95a20298b25 证明这个口径不适合 breadth gold 的日常跟进触发： 它更偏“补新 missing”，不等价于“直接上游更新完成后推动下游”。当前正式口径已经改为 eager() + all_deps_blocking_checks_passed()，且只看直接 asset deps；如果某个下游确实需要多个非直接前置条件，必须另行显式设计。
stock daily 不切换实现： missing() + all_deps_blocking_checks_passed() 不适合作为现有股票日线链路的完整替代。 raw_tushare_stock_daily 没有直接上游 asset，需要的是 Tushare 源站 ready 判断； silver_stock_daily 可以受益于直接上游 checks 判断，但仍额外需要 silver_stock_basic 当日 freshness 和 silver_stock_suspend_daily[trade_date] 分区 ready。 所以当前实现继续使用 raw_stock_daily_update_job_sensor / silver_stock_daily_update_job_sensor 汇总这些门禁，不迁移到 declarative automation。

# 正确口径

    if record.status.value not in {"SUCCEEDED", "FAILED"}:

11.1.2 防未来交易日误跑流程

silver_trade_calendar 是“交易日计划表”，它可能提前保存全年日历。 例如今天是 2026-05-20，日历里可能已经有 2026-12-31 open=true。 这个未来日期在日历上是正确的，但未来行情、未来停复牌、未来市场宽度还没有真实发生，不能注册后立刻运行。

latest_completed_trade_date 是 sensor 的安全边界，意思是“目前最晚哪个交易日已经真实结束，理论上可以拉数据”。 当前实现采用两段规则：小于当前自然日的 open day 可以注册；如果今天本身是 SSE 开市日，则只有本地时间 17:00 后才允许注册今天 partition。 但注册 partition 不等于运行数据生产；股票日线生产仍由 raw_stock_daily_update_job_sensor / silver_stock_daily_update_job_sensor 在 Tushare 源站 ready 且上游 checks 通过后触发。

    2026-05-19 open=true
    2026-05-20 open=true
    2026-05-21 open=true
    2026-12-31 open=true

  before 17:00:
    allowed to register:
      2026-05-18
      2026-05-19

所以 stock_trade_day_sensor 的完整判断流程是：先读取交易日历，再计算 latest_completed_trade_date， 然后只保留合法 open days 作为可注册分区。 这些日期只允许注册为 Dagster dynamic partition keys；是否触发股票日线生产，由 raw_stock_daily_update_job_sensor / silver_stock_daily_update_job_sensor 在上游 ready 和 Tushare 源站 ready 后单独判断。

默认 STOPPED 是为了防止验证阶段一启动 daemon 就自动扫描全年日历、注册未来分区、触发大量无意义失败 run。 第二期必须先人工小范围验证 2026-04 和最近几个已完成交易日，确认不会误跑未来日期后，再讨论是否开启 RUNNING。

1 自定义 AutomationConditionSensorDefinition + upstream blocking checks。 当前 Dagster 版本验证通过，适用于 breadth gold 这种只依赖直接标准事实资产的下游生产。正式入口不使用全局默认 sensor，而是使用每个 gold asset 自己的 automation sensor，只 target 单个目标资产。
2 Asset sensor 后备，只负责查询 readiness 后发起下游 run 或返回 SkipReason。 只有 declarative automation 无法表达 checks readiness，或必须强控单 tick 分区数量、复杂中文 skip reason、复杂业务窗口时使用。
3 通知/审计 sensor。 不作为生产触发入口，只用于提示上游缺失、checks 失败或连续未跑。
如果必须使用 asset sensor 后备，它也不能主动补上游。它只能返回 SkipReason 或触发 daily_market_breadth_job。
短窗口 automation 验证结论： dagster sensor preview default_automation_condition_sensor 和自定义 market_breadth_automation_sensor 都不能像普通 sensor 一样预览，当前版本会返回 NotImplementedError；automation condition 的安全验证应使用 dg.evaluate_automation_conditions(...) 做只读评估。 2026-05-23 正式 instance 只读评估结果显示，从空 cursor 评估 gold_market_breadth_daily 会请求 2975 个缺失分区，范围从 2014-01-02 到 2026-03-31。 连续第二次 tick 模拟仍请求同一批缺失分区，因此在历史 gold 大量缺失时，不能短暂开启 default_automation_condition_sensor 做小窗口验证；否则可能触发大范围历史 runs。 后续不把默认 automation sensor 作为正式触发入口；历史缺失分区通过 UI 分批 backfill，日常触发改为自定义 breadth automation sensors。

defs/sensors/market_breadth_automation_sensor.py

    dg.AutomationConditionSensorDefinition(

      emit_backfills=True,

defs/sensors/stock_return_distribution_automation_sensor.py
  stock_return_distribution_automation_sensor =
    dg.AutomationConditionSensorDefinition(
      name="stock_return_distribution_automation_sensor",
      target=dg.AssetSelection.assets(gold_stock_return_distribution),
      default_status=dg.DefaultSensorStatus.STOPPED,
      minimum_interval_seconds=600,
      description="Evaluate stock return distribution declarative automation only.",
      emit_backfills=True,
      use_user_code_server=False,
    )
控制目标： 自定义 automation sensor 的目的不是解决历史 2975 个缺失分区。 历史分区补齐仍通过 Dagster UI 分批 backfill。 这个 sensor 的职责是把日常 market breadth 自动触发从全局默认 sensor 中收敛出来，明确控制 target、默认状态、评估频率、description 和启用策略；run tag 口径遵守治理专项，不再写项目自定义 tags。
控制项 第一版口径 原因
target 只选择 gold_market_breadth_daily。 避免默认全局 sensor 扫描其它未来带 automation condition 的资产。
default_status STOPPED。 上线前必须先做只读评估；历史 gold 补齐前不得自动开启。
minimum_interval_seconds 建议第一版 600 秒。 market breadth 不需要高频评估；Dagster sensor interval 是最小间隔，不是精确 cron。
run_tags 不写项目自定义 run_tags。 触发来源由 Dagster 系统 tag / sensor tick 表达；治理专项 M4 已删除 trigger/asset_family 这类自定义 run tags。
非交易日 不在本 sensor 里重复判断自然日。 stock_trade_day_sensor 控制 cn_a_stock_trade_days partition 注册；非交易日没有 partition key，即使评估也不会生成非交易日分区。
历史缺失 不靠 sensor 限流解决。 历史补齐应由 UI backfill 分批执行；sensor 启用前必须用 dg.evaluate_automation_conditions(...) 确认请求范围。
use_user_code_server 第一版不启用。 当前只使用 Dagster 内置 condition；未来若写自定义业务 condition，例如最近 N 个 A 股交易日、业务冻结标记或复杂窗口，再单独验证。

15. 持续跟进项与开发前停点

本节列出的事项不是可忽略备注，而是第二期后续开发需要持续跟进的开放项。 每个事项都必须在对应 Slice 中更新状态，直到满足关闭条件；如果验证失败，必须停下来讨论替代方案，不能绕过或静默降级。

事项 所属阶段 当前状态 处理方式 / 关闭条件
Tushare token 是敏感配置，容易被误写进代码、文档或 Dagster 配置文件。 2.0.1 已实现。 当前 TushareResource 使用 dg.EnvVar("TUSHARE_TOKEN") 注入；禁止硬编码、禁止写入 dagster.yaml 或散落 env 文件。缺 token 时由依赖 Tushare 的 asset run 给出清晰错误，不把敏感值写入代码、文档、metadata 或日志。
Declarative automation 与 blocking checks 的组合行为需要本地版本验证。 2.2.2 已完成 2.2.2a 小样本验证；2.2.2b 已落地实现；19aa0df9 后已修正触发条件。 结论：直接上游 checks passed 可以用 declarative automation 表达，但 on_missing() 更偏补新 missing，不适合表达“直接上游更新后推动下游”。breadth gold 资产已改用 eager() + all_deps_blocking_checks_passed()，对应 gold job 只在 silver_stock_daily 直接质量门禁通过且同分区可用后运行。历史缺失分区走 UI 分批 backfill，并使用自定义 automation sensor 作为正式触发入口。
stock_trade_day_sensor 已从 quote 调度职责中解耦。 2.2.1e 已完成。 stock_trade_day_sensor 当前只注册合法交易日 partition，不再发数据生产 RunRequest；raw_suspend_d_update_job_sensor / silver_suspend_d_update_job_sensor、raw_stock_basic_update_job_sensor / silver_stock_basic_update_job_sensor、raw_stock_daily_update_job_sensor / silver_stock_daily_update_job_sensor 分别接管资产族触发。迁移没有改变 asset key、物理路径、partition 定义或历史数据；后续新增其它日频资产族时，不应再扩大 stock_trade_day_sensor 职责。
bootstrap 历史迁移和 Tushare 日常生产容易写成两套 raw 契约。 2.0.2 起持续 历史迁移口径已收口；新生产链路不得复用 bootstrap 作为日常入口。 字段常量、路径函数、raw checks 必须共用；source_method 只作为迁移审计 metadata，不作为业务字段或下游判断逻辑。关闭条件：bootstrap raw 与 Tushare API raw 能共用同一套 checks，下游 silver/gold 不区分来源。
旧湖 suspend_d 不同日期分区里，同一个字段可能被 DuckDB 推断成不同类型。 2.0.3 已完成历史迁移验证。 典型例子是 suspend_timing：有值的分区像字符串，全空分区可能被推断成 INTEGER/NULL。bootstrap 读取旧湖时使用 union_by_name=true 按字段名合并，并显式 cast(suspend_timing as varchar)；写入新 raw 后，schema check 确认它是 nullable string，否则阻断后续 silver。suspend_d 单日和 2026-04 全月 bootstrap 验证已完成。
未来 open day 被误注册并运行。 2.2.1 实现、安全验证与端到端生产验收已完成。 silver_trade_calendar 是全年交易日计划表，不代表未来数据已经发生。stock_trade_day_sensor 必须先计算 latest_completed_trade_date，只允许 trade_date >= 2014-01-01 的合法 open days 注册；今天是开市日时，只有本地时间 17:00 后才允许注册今天 partition。该 sensor 不再运行任何数据生产 job。已确认不会注册未来 open day，也不会误把 bootstrap 已完成历史分区当成待补。
Tushare 当天日线发布时间不确定，sensor 不能只靠交易日历判断当天能跑。 2.2.1b 已实现，小样本、正式 instance preview 和真实 sensor run 已验证。 已新增 StockDailySourceReadiness：在今天是 SSE 开市日时，raw_stock_daily_update_job_sensor / silver_stock_daily_update_job_sensor 16:00 前不探测；16:00 后约每 10 分钟探测 Tushare daily(trade_date=YYYYMMDD) 是否已经可用。源站未 ready 时只返回中文跳过原因或不发 run request，不写 raw 文件，不占用 run_key。历史 2026-05-21 曾由早期 sensor 入口完成端到端验证；当前同类触发职责已迁入 raw_stock_daily_update_job_sensor / silver_stock_daily_update_job_sensor。
最新交易日口径需要支持“今天交易且源站已发布”时取今天，而不是固定取昨天。 2.2.1b 已实现。 代码已把候选交易日和源站 ready 拆开：小于当前自然日的已完成交易日仍按历史缺口逻辑处理；如果今天是交易日且 16:00 后 Tushare 已发布当天 daily，则今天会进入可生产候选。第一版不使用 suspend_d 判断源站 ready，但 raw_stock_daily_update_job / silver_stock_daily_update_job 触发前必须等待 suspend 分区 ready。2026-05-21 已验证 sensor 触发历史 quote run 端到端成功；2026-05-22 已验证当前 raw_stock_daily_update_job / silver_stock_daily_update_job 单日成功。
sensor run_key 去重会阻止失败 run 自动二次提交。 2.2.1 已踩坑并记录。 如果 sensor 已经用某个稳定 run_key 提交过 run，即使该 run 因 daemon/launcher 问题失败，后续 tick 也会跳过同一 run key。Slice 2.2.1d 后新 key 使用 stock_daily_update:{trade_date}，同时历史 quote_daily:{trade_date} / stock_quote_daily:{trade_date} run key 记录只作为旧入口事实保留。这个行为保护了防重复语义，不能通过改随机 run key 绕开。关闭条件：后续明确失败 run 的补跑流程，例如 UI retry、手动 partition run 或专门的重试策略。
