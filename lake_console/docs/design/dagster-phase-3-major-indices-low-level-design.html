8.2 取数范围和首刷验证

  1. 从 Tushare index_basic（doc_id=94） 请求现行 Raw 合同的 13 列。业务参数为空。limit=6000，offset 从 0 每次加 6000，末页少于 6000 条时结束。检查页字段、每页条数、总体非空及跨页主键唯一。重复键或请求失败保留诊断并停止，禁止通过静默去重得到候选。
  2. 首刷在同一个取数窗口，用支持 limit/offset 的请求按已知 8 类市场分别分页，将各市场唯一代码集合与不传 market 的结果对账。已知范围是 BSE、CI、CNI、CSI、NH、SSE、SW、SZSE。每组都须取完，尤其是上次已有 9,079 条的 CSI。若全量请求出现新的市场，核实后保留。独立取数与主请求无法对齐时先定位是漏页、源端在两次请求间变化，还是接口筛选行为不同，再决定能否发布。当前没有覆盖所有潜在市场取值的独立名单。
  3. 保存请求时间、各页 offset 和返回行数、每市场唯一代码数及差异。候选 Raw 的代码和 13 列值与同批主请求对账，按现行合同转换空值和类型。与旧 Raw 比较得到新增、移除和业务字段变化，用于解释替换内容。旧代码本次重新出现时照常保留。

同一个 Job 使用可选的类型化运行配置。首刷手动启用 verify_source_market_coverage，在本次发布前验证市场覆盖。日更使用空业务请求参数和例行校验，Sensor 另外传入 scheduled_trade_date 作为取数前的日期校验。普通手动运行仍可用空配置，由 Job 自行选择最新已登记交易日。配置沿统一构造入口进入 Job，两个选项均不会传给 Tushare。

8.3 候选、发布与恢复

  1. 固定本批输入。 Job 在开始时解析并记录实际采用的指数交易日 D。Raw 候选以本次分页结果生成，Silver 候选只读该 Raw 候选，用固定的 D 应用现行 exp_date IS NULL OR exp_date > D。现行日期归一化及字段类型继续生效。没有可用 D 时，本批不能完成两层发布。
  2. 先核候选。 两份 Parquet 和逐文件记录留在 /Volumes/datasource/data_lake_staging/index_basic/ 的本次执行目录。记录执行身份、取数时间、适用交易日、源和候选的行数与摘要、正式目标原身份。验证两份文件可读、列类型、主键和日期。用本批 Raw 及 D 生成 Silver 应有结果，双向核对代码和终止日期，分别记录应有、实际、缺码、多码和终止日期不符的数量与样例。两层候选都通过且同一文件系统才开始替换正式文件。此步骤由全链 Job 的 Raw 阶段执行。单资产运行只准备和发布所选层。单跑 Silver 时，以本次实际读取的正式 Raw 版本为输入，同样先对账再发布。单层发布不能计为全链日更成功。
  3. 逐文件发布并检查。 目标仍是 /Volumes/datasource/data_lake/raw/tushare/index_basic/full/part-000.parquet 和 /Volumes/datasource/data_lake/silver/index_basic/full/part-000.parquet。先发布 Raw 并读回，Raw 阻断 Check 通过后，Silver 阶段校验正式 Raw 仍是当前执行的输入，发布同批 Silver 候选并读回。每次替换用同文件系统的 os.replace()，发布前后记录摘要和完成状态。启动前确认两个目标无其他写入任务。当两层发布并取得对应 Check 后，才记全链当天成功。
  4. 中断按事实续跑。 候选校验失败时原正式文件继续使用。已完成一层替换时保留该层的结果和本批记录，核对目标摘要后继续未完成层。Dagster 重执行通过原始 run ID 找到同一批次，复用固定 D 和有效候选。实际目标、候选或源文件与记录不符时停止续跑并报告变化。若文件已替换但 Dagster 记录缺失，先对齐正式文件和本批记录，再由获准的 Dagster 重执行补齐该层证据。两份文件是各自原子替换，分层发布期间按各层实际状态呈现。

参考指数日线候选写入和续跑设计。该 writer 的日期列校验及路径适用于日线分区。指数基础信息候选沿用快照路径和字段合同。

8.4 日更触发与审计读取

  • 把候选验证结果绑定到正式产出。 通过发布读回确认正式文件摘要等于本次已核验的候选摘要。Raw 物化记录本批源请求和 Raw 覆盖结果，Silver 物化记录实际使用的 Raw 版本、ready_for_trade_date 和本批对账结果。现有的 Raw 文件合同 Check 和 Silver 生命周期 Check 读取各自目标物化的覆盖结果并写入明细，保留原有 passed 判定。发布后的 Check 及页面无需重做源端或两层对账。
  • 按版本复用证据。 审计按业务日期找到各层产出，再以物化记录 ID 和 run ID 匹配 Check，核对其中的覆盖证据属于同一产出。后来单跑 Raw 导致当前 Raw 版本变化时，旧 Silver 的对账证据仍只对应它原来使用的 Raw。旧版缺证据或关联不上时，齐备显示「待确认」。重跑旧文件 Check 不构成当日更新，也不能用当前 Raw 给旧 Silver 补造证据。
  • 分开显示结果。 更新状态读取各层实际交付。若 Raw 已发布、Silver 未完成，分别呈现，整个日更 Job 仍未完成。齐备状态结合各层对应的正式 Check 和覆盖证据。对账失败发生在发布前，差异记在该次运行明细，不能把未发布候选的缺口归给仍在使用的旧快照。

8.4.1 Sensor 定义与启用

新增 defs/sensors/index_basic_update_job_sensor.py，定义 index_basic_update_job_sensor，目标是既有 index_basic_update_job。通过 build_sensor_tags 构造三项定义标签。goldenshare/sensor_domain=index_topic，goldenshare/sensor_target_layer=raw_silver，goldenshare/sensor_role=asset_update。编写时同步运行合同治理、资产与任务拓扑和Sensor 静态门禁，将分类作为定义标签注册。

默认 STOPPED，部署并核对定义后单独启用。最短轮询间隔沿用股票基础信息 Sensor的 600 秒。每天在北京时间 [18:00, 次日 00:00) 按 daemon 实际轮询决定是否提交。D 只取北京时间当天，在 cn_a_index_trade_days 核对该日是否已登记。读取交易日登记使用现有 index_trade_day_sensor 的结果，更新 Job 和两个资产仍为无分区快照。

8.4.2 每轮判断与查询上限

先用只读路径检查确认正式 Lake 挂载与 staging 根存在，再判断本地时间。此阶段不写探针文件。任一条件不满足就跳过，Dagster 数据查询为 0。符合窗口时按下表顺序读取，能作出决定时提前结束。

顺序查询与范围处理
1has_dynamic_partition 查 cn_a_index_trade_days 的当天 D，1 次。未登记就跳过。休市和本机离线漏跑日都不补拉历史快照。
2按目标 Job、Dagster 原生 Sensor 名称标签及当日 run key 查提交记录，get_run_records(limit=1)，1 次。当日自动任务已提交则跳过。失败或取消显示原因，由人工按原批次重执行。
3按目标 Job 和状态 NOT_STARTED、QUEUED、STARTING、STARTED、CANCELING 查询，get_run_records(limit=1)，1 次。同一 Job 正在排队或执行时等下一轮。其他作业继续使用现有 Dagster 队列规则。
4get_asset_records 一次读取 Raw、Silver 两个资产的最新物化记录，最多 2 条。核对同批发布、时间及适用日。缺少当前产出或两个版本并非同批时，都不能作为当晚完整交付。
5按资产目录登记的 6 个阻断 Check 键批量读取最新执行结果，get_latest_asset_check_execution_by_key，1 次，最多 6 条。分别用目标物化 ID 和 run ID 关联两层产出。只核对本次交付证据，正式阻断条件保持原样。
6仅按上两步收集的物化及 Check 执行 run ID 批量读取运行记录，get_run_records，1 次，去重后最多 8 条。确认该批 index_basic_update_job 有成功的完成记录。可由同批的恢复运行完成。

每轮最多调用 6 次 Dagster 查询 API，由上表六项各一次相加。每轮最多返回 18 条记录，由两条运行筛选记录、两条物化记录、六条 Check 记录和最多八条关联运行记录相加。单轮最多提交 1 个 RunRequest。DuckDB 查询、Parquet 扫描及 Tushare 请求各为 0。查询报错或超出次数、记录数预算时中止本轮、记录原因、不提交。部署前用隔离测试断言上限并记录满足条件路径和早退路径的实际耗时，首次启用验收记录正式轮询的耗时。600 秒是两轮的最短间隔，耗时预算以测试实测为依据。

8.4.3 交付、去重和游标

  1. 当晚交付证据。 当前两层的 goldenshare/index_basic_coverage 均包含通过结果和相同的 batch_id，且 Silver 记录的 raw_sha256 等于本批 Raw 的 sha256。Raw 的 fetched_at 换算到北京时间后须落在 D 当晚窗口。Silver 的 goldenshare/ready_for_trade_date 须等于 D。6 项 Check 均通过并绑定各自物化；两份带覆盖明细的 Check 同时核对其中的批次和目标物化 ID。成功的 Job 或恢复运行须属于 index_basic_update_job，其原始 run ID（无父运行时为自身 run ID）与批次相同，结束时间不早于两层中较晚的物化。两层可以来自同一批次的不同运行。独立重跑 Check 不能补出相同批次的成功交付。
  2. 提交方式。 当日有登记、当前两层尚未构成当晚完整交付且未提交自动任务时，用 build_asset_update_run_key 生成 subject=index_basic_update_job, unit_id=D 的 run key，由 Dagster 对同一个 Sensor 去重。用 build_run_request 提交，partition_key=None。在 run_contracts/configs.py 增加 build_index_basic_update_job_run_config，只构造 ops.raw_tushare_index_basic.config.scheduled_trade_date=D。首刷专用的 verify_source_market_coverage 保持默认 false。运行日期从配置传入 Job。
  3. 日期及失败边界。 18:00 前的手动首刷不满足当晚时点。当晚手动运行相同 Job 并产生完整交付时跳过自动提交。如果当前只发布了一层，且当天还没有自动提交，则按日更规则补一次两层更新；当天已有自动提交时保留实际状态，依原批次人工恢复。任务排到次日才开始取数时，现有 Job 用 scheduled_trade_date 拦截。冻结候选已存在的续跑仍按其固定输入继续。
  4. 游标与诊断。 通过 build_sensor_cursor 保留 schema_version、evaluated_at、decision、target_date、selected_count、blocked_count 和最多一个日期样本。details 由 build_cursor_details 构造，只含 sensor_name、job_name、asset_family、partition_set、reason_code、blocked_component、summary、next_action 和本轮总耗时 performance_ms.total。游标用于解释当轮决定。去重与交付以前述正式运行和 Check 记录为准。
