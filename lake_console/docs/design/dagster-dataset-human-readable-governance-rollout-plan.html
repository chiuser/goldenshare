Dagster 数据集人类可读治理滚动方案

本文把股票日线 Raw/Silver 标杆专项的做法，推广成其他数据集后续治理的路线图。 这不是一次功能改造方案，而是一份“怎么把 Dagster UI 里的信息写给人看”的滚动治理计划。

范围：lake_console/orchestrator 当前 catalog 数据集 只落文档 不改更新逻辑 不改触发逻辑 不改数据湖数据

依据： dagster-dataset-human-readable-governance-recommendations.html、 dagster-stock-daily-human-readable-governance.html、 dagster-sensor-cursor-governance-plan.html、 dagster-data-pipeline-performance-governance.md、 当前 LAKE_ASSET_CATALOG 静态审计结果。

1. 总结

统一目标是：一个接手的人打开 Dagster UI 后，可以快速回答四个问题： 这个数据集是什么、本次为什么触发或没触发、卡在哪里、下一步该做什么。

后续治理只改“表达层”：asset description、run stdout、materialization metadata、check metadata、sensor cursor 和对应测试。 不改变任何数据生产决策，不重写 SQL，不改变 lake 路径，不新增历史 backfill，不启停 sensor。

2. 已拍板实施口径

以下口径已经确认，后续每个数据集的人类可读治理都按这里执行；如需偏离，必须在对应资产族 LLD 中单独说明并重新确认。

事项 已确认口径 执行含义
推进顺序 按 Wave 1 基础事实、Wave 2 日频行情、Wave 3 Gold/Serving、Wave 4 分钟线高频、Wave 5 平台观测 推进。 先做低风险、低体量资产族，把表达样式和测试模式稳定后，再碰分钟线高频链路。
实施粒度 每次只治理一个资产族，必须先写该资产族 LLD，再改代码，再跑测试，再同步文档。 禁止一次性横扫全仓库改 cursor、metadata 或日志，避免误伤触发逻辑和状态机。
Check 策略 默认不新增细碎 check，只增强现有 check metadata 的人类可读表达。 失败原因、规则摘要和下一步动作放进现有聚合 check；除非后续单独拍板，否则不扩大 Dagster DB 状态量。
Cursor 统一硬口径 所有后续 cursor 使用短中文 summary / next_action，保留机器可读 reason_code，明确 blocked_component，只放小型 evidence。 cursor 是调度路标，不是 readiness 报告；禁止完整报告型 to_cursor_details()、status_samples、批量状态、完整路径列表、完整 code 列表。
分钟线专项 分钟线、qfq、MACD/KDJ、state 必须放到独立 LLD，不能和日频资产混改。 这些链路体量最大、性能最敏感，任何新增扫描、日志、metadata 或 cursor 字段都要单独做性能门禁。
Serving 同步资产 默认只增强 materialization metadata 和 stdout，不新增 prod sync check。 prod 同步成功与失败先在事务内校验和 materialization metadata 中表达；除非后续某条 serving 链路确实需要 blocking check，否则不新增状态实体。
总入口 本文作为后续数据集人类可读治理的总入口。 每个资产族治理前先引用本文，再写资产族自己的 LLD；原则不反复讨论，开发只对账当前资产族的具体实现。

本轮通过当前代码中的 list_lake_asset_catalog_entries() 只读导入审计到 57 个 catalog 资产： raw=13、silver=15、gold=25、serving=3、platform=1。

分类 数据集 / 资产 治理重点
基础事实与全量快照 trade_cal、stock_basic、stock_lifecycle、 namechange、stock_identity_map、index_basic Wave 1 已完成：description、stdout、materialization metadata、check metadata、 stock_basic/namechange/identity_map cursor 与静态门禁已落地。
日频行情 Raw/Silver suspend_d、daily、adj_factor、 index_daily 按交易日说明触发原因、阻断组件、文件覆盖和下游消费。股票日线已经作为标杆完成。 market_major_indices_daily 是相邻 gold 消费者，放到 Wave 3 治理，本组只做影响面防误伤。
分钟线 Raw/Silver stk_mins 的 1m/5m/15m/30m/60m raw 与 silver 资产。 按频度和交易日聚合表达，不把 code 列表、路径列表、批量状态塞进 cursor 或 stdout。
分钟线复权与指标 stk_mins_qfq、stk_mins_qfq_macd_kdj、 stk_mins_qfq_macd_kdj_state 区分复权产物、指标产物和状态连续性产物；重点说清上游频度、状态承接和失败修复方向。

Serving / Prod 同步 ch_share_fact_market_breadth_daily、 prod_ch_share_fact_market_breadth_daily、 prod_core_wealth_market_turnover 强调事务写入、源产物、目标表、写前写后核对和失败后的人工边界。
平台观测 lake_root_health 保持为平台健康检查，不套业务资产语言。

4. 全局硬边界

禁止项 原因
不改 asset/job/sensor/check 名称。 避免破坏 Dagster 历史、自动化引用、治理文档和测试契约。
不改 job selection、run key、run config、partition、sensor tick 顺序。 本专项只改可读性，不改变触发和调度语义。
不改 Tushare 请求参数、prod DB SQL、DuckDB SQL、lake path、Parquet schema。 避免把表达治理变成数据生产改造。
不把完整 readiness 报告、路径列表、code 列表、schema 明细塞进 cursor。 cursor 是调度路标，不是诊断报告。完整证据留在 check metadata、materialization metadata 和只读审计报告。
不新增细碎 check。 减少 Dagster DB 状态膨胀。必要时在现有聚合 check metadata 里补人类可读摘要。
不写 Dagster DB，不运行正式 job/sensor/materialize/backfill。 每个后续数据集治理需要单独 LLD 和验证命令，本方案本身只定路线。

5. 统一改动包

每个数据集后续治理时，都按同一组改动包审计和落地。没有对应对象的资产可以跳过，但跳过要在 LLD 里说明。

对象 改什么 验收标准
Asset description 用一句话说明来源、分区口径、产物用途和主要下游。 不写“selection/partition mapping”这类实现堆砌；运营能看懂它在业务链路里的位置。
Run stdout 用 DgStdoutLogger 记录阶段事件和关键数量。 只打印阶段名、分区、频度、row count、file count、attempt 等小字段；禁止完整 SQL、DataFrame、全量样本。
Materialization metadata 追加 goldenshare/summary、goldenshare/next_action、goldenshare/result_status、goldenshare/input_summary、goldenshare/diagnostic_ref。 成功时说明“写成了什么、等谁消费”；失败或跳过时说明“先修什么”。原有机器字段保留。
Asset check metadata 在现有聚合 check 中补 summary、next_action、rule_summary 和稳定的 failed_rule_names。 不新增碎 check；失败样本有上限；缺文件、缺 code、重复 key、上游未 ready 都能直接看出下一步。
Sensor cursor 保留 v1 顶层结构，新增或规范短中文 summary、next_action、blocked_component 和极小 evidence。 普通 request/skip 目标小于 2KB，复杂 repair/backoff 目标小于 3KB，硬上限 8KB；不得写 status_samples、*_batch_status、报告型 to_cursor_details()。
测试和静态门禁 为每个资产族增加或更新人类可读 contract 测试。 锁住 cursor 长度、禁写字段、stdout 事件名、metadata 字段和“旧触发逻辑不变”。

6. 分类治理方案

6.1 基础事实与全量快照

资产族 建议改动 特别注意
trade_cal 说明它是所有交易日分区的根事实；stdout 记录拉取范围、交易日数、注册分区增量；check metadata 说明缺失或异常交易日该怎么处理。 不能把“日历刷新失败”误写成某个下游日频资产失败；下游只是被阻断。
stock_basic / stock_lifecycle / stock_identity_map 说明当前股票池、生命周期、身份映射分别回答什么问题；metadata 记录源行数、过滤行数、当前可交易股票数、退市历史数。 这些资产是很多行情资产的门禁，cursor 里要显示“基础事实未 ready”，不要复制完整基础事实报告。
namechange 说明它是股票曾用名事件线；metadata 记录去重前后行数、时间线覆盖范围、异常事件样本上限。 不要把全量历史样本塞进 metadata 或 stdout。
index_basic 说明它是指数身份和上市属性事实；metadata 记录指数数量、市场分布、active pool 相关提示。 不要重新设计 index daily 的 active pool 口径；只补人类可读表达。

6.2 日频行情 Raw/Silver

资产族 建议改动 特别注意
daily 股票日线 Raw/Silver 已完成标杆专项，作为后续日频行情治理的参考。 后续不要回退 cursor 和 metadata 表达；新增日频资产优先对齐这个样式。
suspend_d Wave 2A 已完成：raw/silver sensor cursor 已改为“交易日、阻断组件、分区门禁、raw/silver 是否 ready、下一步”；check metadata 已解释停复牌文件为空、缺文件和规则失败的区别。 停牌数据天然可能为空，已保持“空 raw 文件可以通过”的原有 check 语义；后续不要回退为把空文件说成失败。
adj_factor Wave 2B 已完成：raw/silver description、stdout、materialization metadata、check metadata 和 cursor 已能说明复权因子对 qfq 分钟线和指标链路的影响；cursor 可直接看出是 stock_basic、stock_lifecycle、raw、silver 还是运行窗口阻断。 已保持当前 freshness、readiness、运行窗口和 batch 选择语义；未新增按 code 的碎 check。
index_daily Wave 2C 已完成：沿用已瘦身的 raw by-date cursor 原则；raw/silver materialization metadata 强调 DG code count/hash、prod source 覆盖和 raw/silver 同日关系；checks metadata 先给摘要和下一步，再保留诊断字段。 已保持 by-date prod source、raw/silver readiness、run key、job/sensor 和数据湖路径不变；没有恢复旧 by-code 叙事，也没有把 prod source probe 的完整缺口列表写入 cursor。
market_major_indices_daily 它是主要指数日线 gold 派生产物，不并入 Wave 2；Wave 2 只审计 index_daily 改造不会误伤它。 实际人类可读治理放到 Wave 3。它是下游消费者，不应该重新扫描旧 index daily by-code 路径。

6.3 分钟线 Raw/Silver

资产族 建议改动 特别注意
stk_mins raw 1m/5m/15m/30m/60m Wave 4A 已完成：raw materialization metadata 已补 summary、next_action、input_summary、filter_summary；stdout 只记录开始/完成、频度、分区和聚合数量；cursor 能直接说明已触发、运行窗口、分区缺口、stock_basic 或 raw 自身阻断。 已保持 prod DB/Tushare source 选择、run key、job selection、写湖路径和 DuckDB SQL 不变；仍严禁 stdout/cursor 打印全量 code、路径列表或每个文件状态。
stk_mins silver 1m/5m/15m/30m/60m Wave 4A 已完成：silver materialization metadata 已说明 raw、identity map、stock daily、suspend 等输入和标准化过滤计数；聚合 checks 已补 summary、next_action、rule_summary；sensor cursor 能直接说明 raw、stock_daily、suspend_d、stock_identity_map 或 silver 自身阻断。 已保持 raw/silver 同日同频依赖、热路径读取上限、check 数量和阻断语义不变。

6.4 分钟线复权、指标和状态

资产族 建议改动 特别注意
stk_mins_qfq Wave 4B 已完成：native/derived materialization metadata 已说明 silver/qfq source、复权因子、source freq、输出文件数、替换行数和窗口生成统计；qfq checks 已补 summary、next_action、rule_summary；qfq daily / factor repair cursor 能直接说明 silver、adj_factor、gold qfq、repair 状态或运行窗口阻断。 已保持 qfq 计算 SQL、factor repair runtime state、防重复提交逻辑、run key、job selection、写湖路径和 check 数量不变；cursor 仍不保存 code list，只保存已有聚合证据。
stk_mins_qfq_macd_kdj Wave 4C/4D 已完成：indicator materialization metadata 已说明 qfq source、previous state、输出文件/行数和下一步；check metadata 已用 summary、next_action、rule_summary、failed_rule_names 表达 source coverage、公式抽样和 schema 问题；daily 与 repair run-status SkipReason 会直接说明下一步；scoped repair completion metadata 已说明 upstream batch、code count/hash、覆盖范围和后续处理。 已保持 MACD/KDJ 参数、计算 SQL、expected calendar、previous state gate、job selection、run key、触发顺序、repair upstream batch、completion gate 和 check 数量不变；metadata 值已用测试防止 tuple 等不可序列化值回流，repair stdout 不打印 code list。
stk_mins_qfq_macd_kdj_state Wave 4C 已完成：state materialization metadata 已说明承接的 previous state、是否首日初始化、state 行数和下一 expected 交易日用途；state checks metadata 已说明文件契约和最新覆盖失败时该修什么。 已保持 state 文件内容和每个 code 的递推明细不进入 Dagster event；stdout 只记录 freq、partition、state 行数和 previous state 摘要。

6.5 派生指标与业务 Gold

资产族 建议改动 特别注意
market_breadth 用业务语言说明市场宽度是什么，输入来自哪些 gold/silver 资产；cursor 保持最近已瘦身的 continuity 路标风格。 ClickHouse serving 的完整 row/path 诊断不回到 cursor；保留在检查或只读审计报告。
stock_return_distribution 说明收益分布的分组口径和输入 silver_stock_daily；metadata 记录样本股票数、分桶数量、异常或空结果的下一步。 不能把分桶明细全量写进 cursor。
wealth_market_turnover 说明财富端市场成交额快照来自 silver 分钟线；metadata 记录 5 个频度是否齐备、points_json 行数、prod sync 状态。 如果上游频度不全，仍按已拍板口径全失败；治理只改说明，不改变失败策略。

6.6 Serving / Prod 同步

资产族 建议改动 特别注意
ch_share_fact_market_breadth_daily / prod_ch_share_fact_market_breadth_daily metadata 说明同步目标、源分区、删除行数、写入行数、写后核对；cursor 只讲本 tick 是否需要同步和卡在哪个 upstream。 不要新增 serving check 来放大 Dagster DB 状态，除非后续单独拍板。
prod_core_wealth_market_turnover 说明它是 gold lake 产物到 prod core serving 的事务同步；失败 next_action 要区分 env 缺失、权限失败、源 gold 未 ready、写后核对失败。 不改变 prod 写库账号、事务边界或历史回灌策略。

6.7 平台观测

资产族 建议改动 特别注意
lake_root_health description 和 metadata 聚焦“根目录是否可用、可写、空间是否足够、临时目录是否正常”。 它不是业务数据集，不要套用“源站、silver、下游指标”的语言。

8. 每个 Wave 的交付模板

  1. 先读根 AGENTS.md、lake_console/orchestrator/AGENTS.md、CODING_STANDARDS.md 和本方案。
  2. 审计目标资产族的真实 asset、job、sensor、check、readiness、tests 和 catalog entry。
  3. 列出硬边界：哪些触发逻辑、run key、路径、SQL、source 参数不能碰。
  4. 写该资产族 LLD，落到代码级改动点和测试点。
  5. 只做表达层代码修改和测试，不写 lake，不写 DB，不运行正式 Dagster。
  6. 跑目标单测、静态门禁和 git diff --check。
  7. 把最终口径同步回对应设计文档或新增专项文档。

9. 后续 LLD 必须审计的依赖

这份滚动方案只给分类和方向。真正动代码前，每个资产族必须重新审计当前代码，因为 sensor cursor、runtime state、readiness helper 和 check metadata 往往有上下游依赖。

依赖类型 审计要求
cursor runtime state 凡用于去重、repair attempt、backoff、run-status 追踪的字段必须保留；只能改展示信息，不能改状态机。
readiness helper 可以取摘要，不能改变 readiness 判断；禁止为了 cursor 好看而调整 ready/skip/fail 语义。
asset check 优先改 metadata，不拆碎 check；若确实要新增 check，必须单独说明 Dagster DB 状态成本。
serving 写入 prod sync 的事务、权限、目标表、写后核对不在本治理中改变。
高频分钟线 任何增加扫描、路径枚举、per-code 明细的改动都必须做性能门禁。

10. 不做事项

  • 不把这份方案当成代码变更授权。
  • 不清理历史 Dagster event、run、cursor 或 lake 物理目录。
  • 不启用或停止任何 sensor。
  • 不触发历史 backfill 或 runless event 补录。
  • 不因为可读性治理新增状态表、summary asset 或额外 serving 表。
