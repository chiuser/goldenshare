Dagster Sensor Cursor 治理专项方案

本文解决一个具体问题：现在很多 sensor cursor 写得像机器诊断报告，字段混乱、内容重复、很难一眼看出为什么触发或为什么跳过。 治理目标是把 cursor 统一成“调度路标”，让运维人员打开 cursor 后先看到结论，再看到最少证据。

适用范围：lake_console/orchestrator sensors 不改数据湖 不写 Dagster DB 先设计后实施

一句话结论

Cursor 不应该回答“这个数据集完整诊断结果是什么”，只应该回答 “这次 sensor tick 为什么触发、为什么跳过、卡在哪个组件、下一步该看哪里”。

完整诊断应放在 asset check metadata、materialization metadata、readiness helper 输出或只读审计报告里，而不是塞进 cursor。

官方建议怎么用 Cursor

Dagster 官方文档把 cursor 定义为 sensor 的跨 tick 状态。它会在下一次 sensor evaluation 时通过 context.cursor 传回来，也可以通过 context.update_cursor(...) 或 SensorResult(cursor=...) 更新。

官方口径 人话解释 对本项目的含义
cursor 用来记录进度，避免重复处理 记住“上次处理到哪里了” 可以存 frontier、last observed id、已提交目标日期等小状态
cursor 是字符串，示例中常用时间戳、etag 或 JSON Dagster 不规定业务字段 字段模板要由 Goldenshare 自己定义，不能等官方给标准表
cursor 存在 Dagster storage 中 它不是日志文件，也不是报告文件 必须小、稳定、可读，不能存大列表和完整诊断
SkipReason 用于说明为什么不提交 run 给人看的句子可以放 SkipReason cursor 里用机器码；人话原因由模板字段表达，不直接塞长中文段落

参考：Dagster 官方 Sensors 文档、Testing Sensors 文档、Schedules and Sensors API 中 update_cursor 说明。 Sensors / Testing sensors / Schedules and sensors API

当前问题审计

当前仓库已经有统一入口 build_sensor_cursor(...)，顶层字段相对稳定： schema_version、evaluated_at、decision、 target_date、selected_count、blocked_count、 sample_keys、details。 真正混乱的是 details。

问题 代码证据 为什么伤人
字段名不统一 selected_trade_date、selected_keys、target_trade_date、pending_keys 混用 看 cursor 时要先猜这个 sensor 的方言
同一含义重复表达 顶层有 target_date，details 里又放 selected_trade_date、batch status 里又放 selected date 信息不再是结论，而是多份互相可能不一致的状态片段
把报告型对象塞进 cursor 多个 sensor 调用 to_cursor_details()，该 helper 会带 status_samples、missing_file_paths、summary cursor 变长，而且读者被迫从报告里找结论
阻断原因不总是第一眼可见 部分 cursor 依赖 status 顺序推断 blocked_component，容易把“待生产目标缺失”误写成“阻断点” 会误导处理方向，比如应先修上游，却以为目标资产自己坏了
历史/repair 状态过重 stock_daily_sensor 把 repair state、selected/blocked 列表、readiness_details 一起写入 cursor 变成内部数据结构转储，不像给人看的调度说明

治理原则

1. 先结论，后证据

打开 cursor 的前 10 行，必须能看出：本 tick 是触发、跳过还是注册分区；目标日期是什么；如果跳过，卡在哪。

2. Cursor 是路标，不是报告

cursor 存最小状态和最小证据。完整 readiness 报告、SQL 结果、样本行、路径清单，去 check metadata 或审计报告看。

3. 人话要标准化

cursor 不写长中文段落，但要有清晰字段：summary、next_action、blocked_component。

4. 字段固定，方言消失

所有 sensor 的 details 采用同一套字段；数据集差异只能放在 context 和 evidence 的小字段里。

统一 Cursor 模板

明确保留当前顶层字段，同时把 details 收敛为下面的标准结构。 其中 summary 和 next_action 是给人看的短句； reason_code 是机器码；evidence 是最少证据。

字段定义

字段 必填 说明 禁止内容
sensor_name / job_name 是 定位入口，避免只看文件名 动态日期、错误明细
asset_family 是 数据集或资产族，例如 stock_daily、index_daily 长业务描述
reason_code 是 稳定机器码，例如 request_run、run_window_not_started 中文句子、动态拼接大段文本
blocked_component 是 真实阻断点。没有阻断时写 none 把“待生产目标缺失”误写成阻断点
summary 是 一句人话，说明触发或跳过原因 超过 80 个中文字符的长报告
next_action 是 下一步该做什么，或等待什么 多步骤 runbook、SQL、路径清单
frontier 按需 窗口边界和推进进度，例如 ready through、first not ready status_samples、每个日期完整状态
evidence 按需 最少证据，例如 count、首个缺失 check、少量 sample 全量路径、全量 code list、sample rows、完整 schema map
diagnostic_ref 按需 告诉人去哪里看完整诊断 把完整诊断复制进 cursor

长度预算已确认：普通 skip / request cursor 小于 2KB；复杂上游阻断小于 3KB；超过 4KB 必须解释并加测试。 任何 cursor 不允许超过 8KB。这个阈值不是为了省几个字节，而是为了强迫信息设计保持克制。

Reason Code 标准

明确口径：本轮不新增单独的 reason-code 枚举文件；先由统一 builder、compact helper 和静态门禁收敛。 新增 reason_code 必须是 ASCII snake_case，禁止写中文和长句。若后续出现跨 sensor 大量复用混乱，再单独抽常量或枚举。

场景 reason_code summary 示例 blocked_component
提交 run request_run 已触发：目标分区缺失且上游门禁通过。 none
全部 ready all_ready 未触发：最近窗口内目标资产已经 ready。 none
运行窗口未到 run_window_not_started 未触发：还没到日常运行窗口。 run_window
交易日分区缺失 missing_registered_partition 未触发：交易日分区还没注册。 对应 partition set
上游未 ready upstream_not_ready 或具体门禁码 未触发：上游 silver 分钟线还未 ready。 上游 asset family
blocking check failed blocking_check_failed 未触发：目标分区已生成但 blocking check 未通过。 失败 check 所属 asset
已提交过本阶段 already_submitted 未触发：本阶段已经提交过 run，等待结果。 none
源系统未 ready source_not_ready 未触发：prod core DB 尚未覆盖目标日期。 源系统名，例如 prod_core_db

逐数据集治理方案

这里的“逐数据集”按资产族处理。治理时不改变 sensor 决策行为，只换 cursor 写法和测试门禁。 表中的“当前风险”指治理启动前的审计基线；已落地后以 LLD 的“已落地口径”为准。

实施路线

  1. C0 审计冻结。 只读列出所有 sensor 的 cursor 字段、长度样本、是否写 to_cursor_details()、是否有 status_samples。
  2. C1 建统一 contract。 继续使用 schema_version=1，但收紧 details 字段规范、长度预算和禁止字段校验； 不另起 v2，避免把本次治理变成 schema 迁移。
  3. C2 一次性治理所有 active sensor。 所有数据集 sensor 同一轮改完，不保留新旧两种 cursor 方言；改动必须只改变 cursor payload，不改变触发逻辑。
  4. C3 全量测试和静态门禁。 对每个 active sensor 覆盖 request、all ready、window not started、upstream blocked、check failed 等主要分支； 静态门禁禁止报告型字段回流。
  5. C4 静态门禁收口。 禁止 sensor cursor 写 to_cursor_details()、status_samples、sample_rows、完整路径列表、中文 reason。
  6. C5 文档和运维口径固化。 更新 run contract governance、performance governance、coding standards。

测试与门禁

测试类型 要证明什么
单元测试 每个 sensor 的 request、all ready、window not started、upstream blocked、check failed 分支都输出正确 reason_code 和 blocked_component
长度预算测试 典型 cursor 小于 2KB；复杂阻断小于 3KB；任何 cursor 硬上限 8KB，超过直接失败
静态门禁 sensor cursor 不得调用报告型 to_cursor_details()；不得写 status_samples、sample_rows、missing_file_paths 全量列表
文档对账 每个资产族的 cursor 模板和实际字段一致

已确认拍板项

  1. 引入统一 cursor 模板，但继续使用 schema_version=1。
  2. 允许 cursor 写短中文 summary / next_action，但必须确保 JSON 编码后在 Dagster UI 和审计工具中正确显示。 reason_code 仍保持 ASCII 机器码，SkipReason 仍保留完整人话。
  3. 长度预算采用：普通 2KB、复杂 3KB、硬上限 8KB。少数 repair sensor 如需超过 3KB，必须单独解释。
  4. 禁止 sensor cursor 直接调用报告型 to_cursor_details()。 若某 helper 未来只返回 compact 结构，必须改名，例如 to_cursor_frontier()。
  5. 所有 active sensor 一次性改完，不分批保留新旧两种 cursor 口径。
  6. 每个 sensor 必须有 summary 和 next_action。它们是“说人话”的核心字段。

不做什么

  • 本专项不改变 sensor 的触发逻辑、run key、run config、job selection。
  • 本专项不清理正式 Dagster DB 中已有旧 cursor；部署后由下一次 tick 自然覆盖。
  • 本专项不新增 readiness asset、status manifest 或数据库表。
  • 本专项不把 cursor 当成事实源；事实仍来自 run、asset event、asset check、lake 文件和正式 source probe。
