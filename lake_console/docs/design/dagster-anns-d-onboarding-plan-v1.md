## 1. 目标、范围与确认口径

DG保存Tushare `anns_d` 公告元数据。日常直接从Tushare获取，不依赖Prod日更任务；Prod仅作为既有历史初始化的只读来源。本轮不修改Prod、PDF下载器、数据中心页面，也不增加Silver、Gold、搜索索引或公告业务数据库。

管理员已确认：

1. 每日08:00，时区Asia/Shanghai，schedule只提交一个 `raw_anns_d_update_job` 运行；同一运行内部按日期从早到晚处理九天。
2. 以计划触发日为D，范围为D−7至D+1，包含过去七天、当天和次日。2026-10-26对应固定列表19、20、21、22、23、24、25、26、27日；不是截至当天的最近九天。
3. 取消整批总时间期限。晚启动、排队、跨午夜或运行超过一小时，均不构成拒绝执行的理由；不改成从实际启动后重新限时。
4. 每个日期仍完整分页、合并已有记录、逐文件提交并形成按日检查结果。一个job不等于一次Tushare接口请求。
5. 单日源数据问题应记录该日失败，继续尝试其他日期；公共资源故障，或需要新请求但共享次数已耗尽时，停止并报告未执行日期。已有完整capture/交付只需文件或事件恢复时，不因无需使用的请求额度已满而拒绝。九个任务请求已创建不代表九天已更新成功。
6. 已提交文件不因后续失败回滚。恢复同一次执行时，核对证据后复用已提交日；新一天的正常调度必须重新观察九天来源，不因分区曾经成功而跳过。
7. 保留现有单次请求30秒超时、每页最多三次尝试和默认五秒请求间隔。现有单日100次、整批350次请求上限继续生效，含重试和中断后已消耗请求；它们是内部控制值，不宣称是源站硬限。
8. 保留一个公告资产、九个日分区及原有两项检查的身份，不用额外摘要资产或永久状态表替代它们。

## 3. 数据及时间合同

### 3.1 三层时间语义

| 层次 | 口径 |
| --- | --- |
| 时间输入 | 自动按计划日D冻结九日；手工历史点/闭区间保留已结束日期边界 |
| 执行单位 | 一次job处理九日；Tushare仍逐日分页；候选及正式提交仍逐日 |
| 完整性判断 | 文件、完整分页交付证据及按日检查共同证明本次观察；不要求每天非零，不证明源端永久完整 |

公告按自然日 `ann_date` 归档，不使用A股交易日历、股票池或上市状态过滤。`rec_time` 是发布时间，不能替代公告日期。已有真实样本证明次日公告可提前发布，因此D和D+1继续保留；本次没有重新请求源验证。

### 3.2 字段、合并和路径

固定六字段及顺序：`ann_date, ts_code, name, title, url, rec_time`。Raw均为nullable VARCHAR，保留源字符串、NULL、空字符串、空白和版本；只还原SDK缺失值，不修饰业务值。路径日期为YYYY-MM-DD，文件内 `ann_date` 保留源YYYYMMDD。

只删除六字段完全相同的重复，按 `DISTINCT(existing UNION ALL incoming)` 合并。NULL与空字符串不同；本次源未返回的旧记录保留；同标题、同URL或同代码不能作为去重键。缺URL、发布时间等合法；无法归属请求日期、缺列或错误类型阻止该日提交，不静默删行。

正式文件：

~~~text
/Volumes/datasource/data_lake/raw/tushare/anns_d/ann_date=<YYYY-MM-DD>/part-000.parquet
~~~

分页文件、候选、spill及执行checkpoint只位于：

~~~text
/Volumes/datasource/data_lake_staging/anns_d/
~~~

保留现有专属自然日分区，自2020-01-01开始、Asia/Shanghai、`end_offset=2`。资产与两项检查共用同一分区定义。文件schema检查必须使用 `hive_partitioning=false`。合法空日写完整六字段零行文件，空页仍须有正确schema及分页结束证据。

## 4. 一个job的运行方式

schedule根据计划触发时间冻结范围，只生成一个请求；不取源、不读Lake、不执行checks。保留job、asset、schedule及两个check的现有名称，去重键按整个日期范围构造，不能再按单个目标日生成九份。

运行顺序：

1. 核验固定范围、执行身份及正式卷，读取本次执行checkpoint。
2. asset按九个日期顺序调用既有单日执行器；单日完整capture后构建候选、验证并原子提交。每次仅处理一日文件，不把九天明细累计在Python内存。
3. 保存每一天独立的文件路径、行数、来源页及交付checkpoint引用，并输出“文件已完成x/9”。
4. 文件阶段有单日失败时，其他可执行日期仍尝试；全部尝试后汇总报错。已提交日文件及checkpoint保留，不能给失败分区补成功物化。
5. 九日文件阶段全部完成后，asset只返回一次结果，由Dagster产生九条各自带日元数据的物化。
6. 同一job内两个检查节点各自遍历九日，正常产生18条明确绑定日期及本次物化的检查。某日规则返回未通过且节点可继续时，仍记录其余日期结果，最终job失败；取消、公共故障和未处理异常停止相应检查节点，不假称未执行日期已检查，也不假设框架会立即取消已并发运行的兄弟检查。

此实现的正式物化和检查发生在文件阶段完成之后，不是每提交一个文件就立即完成该日的两项正式检查。文件阶段失败时，不得把“文件已完成8/9”写成“DG已通过8/9”。续跑复用这八日的有效文件与证据，完成缺日后再形成物化和正式检查。

进度必须区分文件提交量与检查完成量；检查失败不回滚文件。不得调用历史CLI或runless补录工具代替这条正式日更链。

本次只改自动schedule的运行组织。保留资产原有backfill policy，不额外设置`BackfillPolicy.single_run()`；schedule直接提交范围run已通过隔离验证，无需借此改变手工UI默认逐分区回填，也不新增Dagster CLI的partition-range入口。

## 5. 失败、取消、续跑和跨天

| 情况 | 行为 |
| --- | --- |
| 当日源调用重试耗尽、响应缺列/错日期/重复页 | 该日失败，保留现场；其余日期继续尝试 |
| 磁盘不可用、执行身份冲突、共享请求预算耗尽、事件服务故障 | 停止相应阶段，明确失败和未执行日期；不伪造完成 |
| 取消或进程退出 | 停止领取新页/新日，释放调用子进程；已提交文件保留 |
| 不完整capture | 同日用新attempt重新完整capture，不拼接不同观察时刻的offset页 |
| 完整capture/已提交日 | 指纹与checkpoint核对后复用，不重复请求或覆盖 |
| 文件提交后物化尚不完整 | 显式重跑asset，复用已核验文件，形成九条新物化及相应检查；不重拉已提交来源 |
| 九条物化已完整，仅checks失败 | 支持仅重跑实际失败的检查节点，目标绑定原执行的对应日物化；不要求新run重做物化，不重拉来源 |
| 同日100次或整批350次请求已用尽 | 原执行不能再领取相应请求，续跑不重置；仅新的明确获准补拉意图可重新获得预算，不自动换身份绕过 |
| 正式文件已被另一批更新 | 不用旧候选覆盖，不伪造旧交付；明确冲突，由新的获准执行重新观察 |

跨午夜保持原定九日，不按恢复当天重算。下一日08:00仍生成下一批自己的九日范围；当前全局单并发配置不改，不增加并行源请求或新sensor。若发生积压，显示实际阶段和等待状态，不以整批超时丢弃任务。

完成的一批重放可复用本批证据；下一天的新批必须重新请求重叠日期，以纳入晚发布公告。七天回刷不是源端迟到SLA，超范围历史缺口另行明确补拉，不扩大日常范围。

CLI同一`--window-id`及手工UI重新执行，都先读取已冻结的时间、范围和配置；手工UI以Dagster原生root_run_id保持执行身份，独立新run不能误复用旧观察。恢复某日成功后，替换其旧失败状态并清除旧reason，再由各日最新状态汇总本批结果。

正常全流程新run验收是9条物化、18项检查；仅重跑一个或两个检查节点的新run分别是0条物化加9或18项检查。收尾按实际执行步骤计数，并核对同一冻结执行、同日物化与未重跑检查的已有有效结果，不能一律要求恢复run重新产生9/18，也不能仅凭所选步骤成功就宣布整个九日已通过。

旧已结束运行、文件、事件、checkpoint及报告保持原样。新执行不自动续用旧未完成窗口；历史证据读取与当前执行配置解耦，具体迁移见LLD第8节，不增加按旧设计执行的长期分支。

## 6. 写入、检查及状态边界

- 完整分页、候选集合对账、同文件系统逐文件 `os.replace()`、fsync及checkpoint保留。
- 不新增备份或Kopia，不把候选放入正式Lake；不声称九文件整体事务。
- 两项原check名称、blocking语义、分区定义及检查内容保持；只改为支持范围运行下的逐日记录。
- catalog的历史事件能力继续为`SUPPORTS_RUNLESS_EVENT_BACKFILL`，只用于原有历史补报；不能因日更禁止runless就把历史能力一并移除。
- 日常事件由当前job原生执行产生；不得顺手使用历史runless模式。
- checkpoint只用于执行与续跑，不成为第二份readiness、源数据或永久公告状态。
- 原始文件提交不依赖后续观测写入成功；状态写入失败不删除或回滚已提交数据。

## 7. 性能、读取范围与不变的控制项

| 项目 | 范围与预算 |
| --- | --- |
| 调度热路径 | 每tick一个RunRequest；零Lake扫描、零源请求、零业务数据库查询 |
| 执行数量 | 一run、九日期、最多九次正式日文件提交；正常完成9条物化及18条检查 |
| 请求 | 每日基础页数 `floor(N_i/2000)+1`；满页继续，空日也请求一页；总次数含重试≤350、单日≤100 |
| 调用控制 | 单次30秒、每页最多三次尝试、默认结束后间隔五秒；保留取消；无整批总期限 |
| 计算 | DuckDB列式合并/COPY；2GB内存、2线程、20GB spill配置保持，临时目录在本次staging |
| 读写 | 只读目标九日的既有文件及本批来源页、候选和交付证据，不扫描全历史；保守次数模型见LLD第10节 |
| 失败恢复 | 已提交且证据未变的日期不重拉；不完整日重拉开销计入原请求上限，不自动重置 |
| 收尾 | 正常使用本run 9条物化/18项检查；仅检查恢复使用实际新增结果与同目标的已有检查，范围仍限九日，不另加全局审计或性能压测 |

最近30天已有10个成功九日批次，原执行方式的整批耗时约139—166秒，仅作为历史规模参考，不是新实现性能承诺或超时门槛。单日历史最大约69,498行/35页是2026-10-03审计时点，不把315页场景当成当前真实请求量。

现有writer及checks会多次引用单日文件，不能写成“旧文件只读一次”。本次不顺带重写其校验算法或新增重复全量对账。完整开销须包含源页JSON/Parquet、候选、校验、事件、一次中断续跑及收尾。

## 8. 既有历史初始化的边界

历史初始化范围仍为2020-01-01至2026-09-30，不因本次改造重跑。Prod只读白名单仍是 `raw_tushare.anns_d`：按月快照、服务端游标、fetchmany=10,000，服务器内从payload投影六字段；id只用于排序/恢复，不进入Raw，不输出完整payload或系统列。

保留月200万行、月30分钟、SQL60秒的既有历史读取保护；它们与本次取消的日常整批期限无关。历史文件生成与runless事件补录继续分开；原历史工具的有界执行及批准范围不扩大，也不能替代正式日更。

本轮仅为配置移除解除历史证据解析耦合，不改变Prod SQL、字段、表、索引、数据或历史初始化范围。

## 9. 开发与验收顺序

1. 按LLD先统一证据读取，移除总期限配置与全部消费者，防止历史检查因配置删除失效。
2. 实现稳定范围身份、单请求schedule及逐日文件执行，覆盖单日失败继续、取消、手工/CLI续跑；移除前日成功门禁。

4. 完成固定日期、迟到/跨午夜、失败/取消/恢复、旧证据读取及事件分区/目标绑定测试；正反样本依据源合同与真实生产者结构。

6. 后续获准正式执行时，仅运行一次明确九日范围的job并核对原有检查；失败停止，不自动重试整批，不重复全局审计。
