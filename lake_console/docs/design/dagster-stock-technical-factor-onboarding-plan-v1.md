## 1. 目标与已确认要求

将 Prod 已有的股票技术因子历史数据 bootstrap 到正式 DG Lake；初始化完成并验收后，由 DG 自动从 Tushare 下载后续交易日数据、处理并发布 Raw/Silver，不继续每日从 Prod 导出本数据集。DG 同时监控复权因子变化，从 Tushare 重新获取受影响股票的历史技术因子。直接使用已完成的下载器及语义适用的既有读写能力，不把抽取其他公共模块或迁移旧数据集作为前置条件。这里描述的是接入后的运行方式，当前尚未开发或启用该自动更新。

当前顺序为：补齐并确认本方案和本数据集 LLD → 完成对应步骤代码影响面审计 → 调整契约名校验并登记完整契约与固定请求方式 → 实现并隔离验收 DG 接入 → 分别批准正式初始化、事件补记及自动更新。组件已有六种模式，不重做组件建设；本数据集按具体用途选择模式。本轮只更新设计和编写 LLD 草案，不开发。

已确认要求：

1. 历史 bootstrap 来源是 Prod；日常来源是 Tushare。不能把初始化改成从 Tushare 重拉全部历史。
2. 复权因子监控及受影响股票的历史更新是本次接入的组成部分，不能只有当天追加。
3. Tushare 请求使用已完成的下载器；复用 DG 现有 DuckDB、日历、运行合同以及可直接适用的写入与恢复能力。旧数据集迁移、其他公共模块抽取均不在本次范围。
4. 按 DG 接入模板设计 Raw、Silver、Catalog、checks、job、sensor、初始化、恢复、性能与人的排障路径。
5. 正式 Lake 只使用 `/Volumes/datasource/data_lake`；候选文件只使用 `/Volumes/datasource/data_lake_staging`。不使用旧 Lake、旧 Console、Kopia 或已经清退的一次性修复入口。
6. tushare数据下载组件每下载完整一个unit，就向业务交付一次源数据；分页不逐页回传，也不等整批结束才返回。业务按本工程规则决定正式存到哪里、怎么写入，复用现有写入与发布能力。下载完成、正式写入和数据集完成分别确认；业务校验或写入失败不进入源请求自动重试。
7. 历史下载默认每股从可信最早已有日期至目标T，按该股完整范围形成unit，不为配合20日本地合并批次而切成20日网络请求。请求量/分页和实际容量按完整契约处理；范围未获准或容量不够时说明原因，不截短历史。处理旧日期只发布d<T。

保留 Raw/Silver 两个资产，Silver 本期沿用原规则，后续新增清洗另行明确。日常只检查今天及上一个交易日。上一个交易日未补齐时，先安排一次补采；同一执行日期内，进入该次下载流程后就不再自动补第二次。补后仍缺、日下载/日发布失败且无法确认已齐、或覆盖未知时，不推进今天，交管理员判断与修复。上个交易日本来已齐，或这一次已补齐后，才允许安排今天；只有历史阶段失败而日覆盖已确认齐全，不当成日数据缺口。完整的前置检查、排队及重启处理见 §8.3 和 LLD §3。

只在执行日为开市日时自动运行：北京时间 19:00 开始，之后 19:30～23:30 每半小时安排今天的新一轮；午夜不再新开任务，已实际运行任务可正常结束，排队任务实际开跑时须再查截止时间。已有排队或运行任务就跳过该次，不累积待跑任务。19:00～23:30 共 10 个计划时点，不是要求无论是否补齐都运行 10 次，也不是允许把前日的一次机会变成每半小时一次。

每轮取得并按既定规则处理好的数据即可发布给业务使用，不等全市场股票全部补齐，不设最低数量或覆盖比例。按当天非停牌上市股票的代码集合判断缺失，用于继续补采、历史回刷前置和说明覆盖情况；不拿这份集合删掉来源其他合法行。要分开记录“本轮已发布”“当天股票已补齐”“复权历史已更新”。完整下载 unit 指已取完本次接口查询的全部页，不表示全市场应有股票都已在源端发布。

下载阶段不建设逐页、逐股票断点续传。**任务在任何阶段失败、异常退出或取消后，获准重执行一律重新下载，不复用该失败任务保存的源候选或尚未发布的合并候选。**日更重执行重新取得原目标T的完整日源；历史失败的全部原股票及原窗口重新取得历史源，不逐股、逐页或按已完成20日接续。失败前已经发布的正式文件保留，作为新请求合并的基础，不删除、不回滚；完整变化名单、批准范围及失败证据保留。其他此前整批成功且仍有效的历史不并入本次失败范围重刷。同一个仍正常运行的任务取全源后继续发布，不是失败重试。下载器同页有限重试及bootstrap原恢复规则不变。

一个自动日更 job 承载每轮更新和必要复权历史处理，另提供管理员手动历史repair job；Raw、Silver 各一个综合 blocking check。股票复权因子数据集的目标日及前一交易日Raw已就绪，才允许提交自动技术因子 job；job 开始再次核实，并在下载技术因子前生成、保存或复用目标日的完整变化名单。自动job先发布有效日Raw/Silver并通过必要检查，再核对原目标T已发布Raw按应有代码集合确认齐备，才允许下载、合并或发布历史。手动repair不执行T日阶段，按§8.5先核原T Raw齐备及原历史前置，不要求执行或补齐T日Silver。Raw不齐或覆盖未知时自动历史等待，repair直接报“原日期数据缺失”。确认全天停牌仍从应有集合扣除，不要求补造停牌日行；技术因子同名adj_factor值不一致仅作诊断。日数据可以部分发布，历史必须满足覆盖前置；历史未完成不撤销已有日数据，job失败也不意味着已发布文件被回滚。

分区由独立 sensor 根据日历注册今天（若开市）及上一个交易日；bootstrap 先注册获准范围。注册不表示来源、上游因子或业务数据已就绪，不等待 Tushare 发布，也不删除更早的历史键。复权因子前置与技术因子Raw覆盖是两种判断；日数据可部分发布，历史必须等Raw覆盖齐备。

本次接入只在 DG 内维护 `stk_factor_pro` 的一份完整源契约及其消费者。Prod 定义只作参考、Prod Raw 只作获准 bootstrap 来源，不修改 Prod 契约、DatasetDefinition、执行器或消费者；财势乾坤接入、三工程契约统一、契约平台和跨工程 import 均不在本次范围。不新增本地 MACD/KDJ 计算，不修改 Wealth、ClickHouse、Redis 或其他数据集的调用方式。

```python
daily_task = DownloadTask(
    contract_name="stk_factor_pro",
    mode=DownloadMode.BY_POINT,
    points=("2026-10-21",),
)

history_task = DownloadTask(
    contract_name="stk_factor_pro",   # 同一份完整契约
    mode=DownloadMode.BY_OBJECT_RANGE,
    objects=("000001.SZ",),          # 业务确定的受影响股票
    time_range=TimeRange("2026-10-19", "2026-10-21"),
)


def download_and_save(task, save_unit, *, expected_unit_count,
                      control=None, on_progress=None):
    downloader = TushareDownloader.load()
    session = downloader.download(task, control=control, on_progress=on_progress)
    with session:
        for result in session:
            save_unit(result)        # 仅业务校验、源候选落盘/读回，不发布正式文件
            del result
    summary = session.summary       # 正常退出with，关闭成功后才判断阶段完整
    if (summary.status != DownloadStatus.SUCCEEDED
            or not summary.download_complete
            or summary.total_units != expected_unit_count
            or summary.completed_units != expected_unit_count
            or summary.delivered_units != expected_unit_count):
        raise ValueError("下载会话未成功完成，不能记录源完整或发布正式文件")
    return summary
```

`expected_unit_count`由本次已核验任务范围得出，不是运营配置；上述两个例子均为1。下载期间只保存完整unit源候选，正常退出with后再核最终summary及源清单/行数，才保存source-complete并进入正式发布。关闭失败、STOPPED/CANCELLED/FAILED不能因unit已全部交付就放行；阶段失败仍按§9重新下载。日期传给下载器时统一使用ISO字符串，业务记录中的日期类型按本地合同转换。

无分类展开时，daily_task 的一个 unit 是该交易日全市场完整结果；history_task 的一个 unit 是该股票在所给整个窗口的完整结果，不是每天一次。示例短窗口仅说明输入，实际历史更新仍须覆盖 §8 确认的全部历史，由业务安排连续、有界且不遗漏的窗口。

窗口由业务在调用前确定，下载器不会根据内存余量自动缩小 BY_OBJECT_RANGE 的范围。一只股票的完整历史可以是一个经过确认可承载的窗口，也可以分为多个连续窗口，具体划分在 LLD 明确。同一股票的多个窗口须分次构造任务，不能把重复代码的多个 object_ranges 放进同一个 DownloadTask；当前输入校验会以 1102 拒绝重复对象。

**股票代码的扇开由下载器完成，不要求业务逐只股票调用。**DG 业务确定变化股票清单及各股票的历史范围；同一窗口可一次传入多个 objects，各股票范围不同时可一次传入每个代码一项的 object_ranges。下载器现有 UnitPlanner 按代码生成 unit，串行下载并逐个完整交付。例如同一窗口传入 3 个代码，一个任务就会生成 3 个 unit。业务安排多个时间窗口时按窗口分次提交，可在每个任务中继续传入多个代码；“多窗口分次调用”不是“业务按代码扇开”。日常 BY_POINT 则直接按交易日取得全市场结果，无需逐个代码请求。

### 6.6 已有组件边界及接入要求

组件同步调用，业务在 DG 独立任务进程的执行线程中创建、使用和关闭实例即可；需要持续响应页面时由业务另开下载线程。组件不创建线程/子进程，不管理业务通信、全机并发、同 token 合计频率或账号额度。

业务可注册标准 PAGE_COMPLETED、RETRY_SCHEDULED、UNIT_COMPLETED 回调；回调在下载调用线程同步执行，只传摘要，不传分页数据。业务负责把摘要交给页面或其他进程，并在结束/异常后转发最终 summary；不能等待下载器另发结束事件。普通回调异常只影响观测，业务保存异常必须从结果循环抛出，不进入源重试。

完成一个完整 unit 后才交付不可变内存结果，不预取下一 unit；当前默认 2 GiB 是单 unit 工作空间约束，不是进程总内存保证，不重新引入文件交付或并发名额。业务及时消费并释放结果，完整 unit 交付后要及时形成可读回的候选事实，避免把所有历史留在内存最后才写。

分页或重试阶段取消丢弃未完成 unit。完成回调中 cancel 或 DownloadCancelled 都先交当前完整 unit，再停后续；若已是最后一个则正常下载完成。使用 with 确保正常、提前退出、取消和业务异常均关闭自身资源，网络取消受当前同步调用返回/超时约束。进程重启后未完成 unit 从第一页开始；哪些结果已形成候选或正式提交由业务记录，不能用进度 100% 或下载完成代替数据集完成。

以上描述组件行为；本数据集采用更简单的业务重执行方式：正常运行中完整unit及时落盘，整个历史约定范围取全后才进入20日合并发布；但任务一旦失败、异常退出或取消，重新执行不读取旧下载候选继续发布，而是重新下载原目标日和需要重试的原历史完整范围。仅执行历史repair时不请求T日数据；它先检查原T Raw是否齐备，不齐或未知直接报错“原日期数据缺失”，交管理员处理。旧正式文件、完整名单、原范围和排障证据保留，失败候选不复用并不授权物理删除。今天新轮同样重新请求T；前日一次限制不因人工重执行而恢复。此前整批历史成功且仍有效的记录可用于避免无关重复回刷，失败范围内已发布一部分不能据此缩小本次重新下载范围。详见§8～9；bootstrap恢复规则独立不变。

本节复用已完成组件，不重复列出全部错误码、超时及内部单元设计；以组件 LLD 和业务使用文档为准。

## 7. 历史 bootstrap

### 7.1 范围与来源

只从 `raw_tushare.stk_factor_pro` 导出已批准范围内的 261 个业务字段，不读 Serving 视图补字段，不带入三列系统字段，不读生产任务状态充当 Lake 数据事实。明确登记该表为此次只读导出的来源白名单；不因此开放其他表。

执行前冻结起止日期、按日计数、已知缺日及来源截止条件，并解释 §3.2 的数量差异。Prod 首尾范围内是否需要补缺、补哪些日期，须基于实际证据在本方案记录并评审；不能以 bootstrap 名义默认从 Tushare 补齐全部历史。

历史因子结果可能已经被 Prod 按较新的复权基准更新。初始化前还须核对 Prod 因子与 DG 同一截止日期的复权基准，选取发生过复权变化的股票和历史日期做有界对照；不能用单个当日价格相等证明全部历史已正确刷新。若发现未解释的不一致，先处理范围和来源结论，再执行正式初始化。

截止日期也不能阻止 Prod 在导出期间更新旧日期。正式导出须事先协调来源维护窗口，确认批准范围内没有并发历史重刷，并按窗口记录来源内容核验依据；发现来源已变就停止并重新确认受影响范围。不能通过锁住生产表或长期持有全历史事务换取一致性；续跑和最后来源复核的开销纳入预算。

### 7.2 导出、候选、发布

1. 用日期索引按自然月规划有界导出窗口，显式排序、261业务字段投影、SQL 超时和窗口总行数上界；使用“上限加一行”发现截断，不把上限内的结果冒充全部结果。每次从数据库读取5,000行是内存批次，不是窗口总行数上限；具体月份范围、总行数上界和超时仍须按批准范围确认。
2. 复用`ProdPostgresResource.connect_readonly_transaction()`，使用服务端named cursor，`itersize`及`fetchmany`均取同一个5,000行常量；普通cursor即使分次fetchmany也可能已把整月结果传入客户端，不能当作流式。按`trade_date, ts_code`稳定排序，当前批转为staging分片后释放；同一日期可以跨多个读取批次，见到下一日期或游标EOF才确认该日源完整，再形成一次该日期候选，不每5,000行覆盖一次正式文件，也不要求整月都读完才保存完整日期。按当前代码的2个身份/日期字段和259个Float(53)估算，5,000行净字段约9.94MiB，含协议传输约15～35MiB、Python基本行对象约40MiB；连同缓冲/转换按128MiB工作空间、256MiB余量考虑。这是已接受的估算，不是实测峰值或新增硬限制；字段类型、批次/副本变化时须重核。bootstrap不经过Tushare下载器，其64MiB HTTP及2GiB unit限制不适用于此数据库批次。月窗口保持有界只读事务，不能启用覆盖全部历史的数据库长事务。
3. Raw 候选与 Silver 候选分别校验。每个已完成独立文件形成可读回事实，从 staging 通过同文件系统 `os.replace()` 到正式目录。
4. 逐文件记录来源范围、候选/目标指纹、校验结果和完成情况；已有目标只在内容等价或已批准更新理由下继续。意外目标变化、候选变化或来源范围改变必须停止。
5. Raw 和 Silver 的多个文件不是整体原子提交。中断后保留已完成文件，续跑识别“已提升但 checkpoint 未完成”等情况，读回核验后推进；不能因状态记录失败撤销已提交业务文件。
6. 全部物理验收完成后，再单独设计和审批 Dagster 历史事件补记。Direct Lake bootstrap 不等于逐日 Dagster backfill，事件不能代替文件验收。

bootstrap的批准输入、字段类型、单月行数上界R、事务内SQL超时、受控SQL与日期数组、来源身份和逐日期完整记录现已在LLD§10.2～10.4细化；实际生产值仍执行前获批。R+1仅为截断检测，收到超限行先停止，不能拿它当下一日期到达的证明；跨日片段须显式按日期过滤并核计数/摘要，完整日才发布。

5,000行只控制一次接收和转换的规模，不成为SQL总LIMIT。中断时未收齐日期的分片不可发布；已经完整保存或提升的日期按逐文件记录核对复用，未完成日期在其批准月窗口内重新读取，不按数据库offset/第几批断点续传，也不新增整月完整才可恢复的门槛。源维护窗口、原日期/字段和目标身份仍必须有效；不能拿旧来源记录覆盖后来合法更新。

正式导出属于数据集全局明细读取，必须先获得明确批准；正式 Lake 写入、事件补记分别授权。小样本或代码开发授权均不替代这些授权。

## 8. 每日更新与复权变化后的历史更新

bootstrap 只读 Prod 的批准历史；完成初始化验收及另行启用批准后，DG 直接从 Tushare 下载。一个自动日更 job 承载所选目标日的更新和必要复权历史处理；管理员另可使用手动历史repair job处理保存的原目标日范围；sensor 只检查、选择目标日和提交，不计算完整变化名单，不写 Parquet，不拉历史。新 sensor 默认 STOPPED。

本节使用三个不同日期：执行日期 D 是当前北京时间日期；目标日 T 是本次实际要更新的交易日；P 是 T 的前一交易日。先补上一个交易日时，T 不是执行日期，P 也不是执行日期的“昨天”。例如周一补周五，比较周五与周四因子，不能比较周一与周五。

### 8.1 当日应有股票、可发布数据与复权前置

这里的股票复权因子数据集是现有 Tushare `adj_factor`，在 DG 对应 Raw 资产 `raw_tushare_adj_factor`。`stk_factor_pro` 自身也返回一列 `adj_factor`；两者名称相同但分别来自两个接口。以前者的T/P值比较变化、生成回刷名单；后者同名字段按源保存并记录差异，不作为否定前者的依据，没有新增另一种因子或数据集。下文直接用现有数据集名称。

覆盖以 T 日上市 A 股减去全天停牌的代码集合为准，盘中停牌仍列应有；这是已确认规则。按目标日读取现有 `silver_stock_lifecycle` 与最终 `silver_stock_suspend_daily`，不能用当前上市清单回推历史。生命周期采用 `list_date <= T AND (delist_date IS NULL OR T < delist_date)`；最终停牌中 `suspend_type='S' AND suspend_timing IS NULL` 表示全天。参考 [现有日线覆盖检查](/Users/congming/github/goldenshare/lake_console/orchestrator/src/orchestrator/defs/checks/stock_daily_checks.py:882) 的语义，不照搬它的日线起点或其他限制。

“确认全天停牌”必须有具体依据：复用现行 `suspend_d_ready_for_trade_date(instance, T)` 核对Raw与最终Silver的最新物化及关联检查，再读取T日最终Silver，核对日期、必需字段及文件身份。历史前置和覆盖计算共用这一次已核验输入，不各自叠加固定修正源。检查事件就绪不等于实际文件已经核实；输入未知或被改写时，覆盖不能宣告已齐，整个历史阶段不得启动；本轮有效日数据仍可发布。具体读取和失效判断见LLD§5.2、§9。

比较“应有代码减去合并后已发布代码”，不只比行数，也不只看本轮源响应。股票覆盖用于继续补采、是否启动历史及说明，不是本轮日数据发布门槛；覆盖输入暂不可用时不能宣告已齐，但已经取得的有效数据仍可使用。应有集合不是下载过滤器或清洗规则，来源其他合法行不能据此从 Raw 删除。每轮记录应有、本轮返回、合并后已发布集合的输入身份、数量与完整缺失清单位置；依据变更就重新核对，不沿用过期的 100%。本期 Silver 不额外过滤行，成功生成后与 Raw 的主键/行数对应；两层处理是否成功与源缺股票分别记录。后续新增清洗不作为当前前置。

**股票复权因子数据集就绪是提交技术因子 job 的前置条件。**更新 sensor 在日期已注册且运行窗口允许之后，检查股票复权因子Raw资产 `raw_tushare_adj_factor` 的 T 和 P；任一未就绪就不提交 job，也不消耗前日补采机会。job 开始再次核对，不能把“日期已登记”“文件存在”或“有一条因子”当成已更新好。

现有 [raw_tushare_adj_factor_ready_for_trade_date](/Users/congming/github/goldenshare/lake_console/orchestrator/src/orchestrator/defs/sensors/readiness.py:1024) 关联该分区最新 materialization 及其既有三个 blocking checks：`raw_adj_factor_contract_check`、`raw_adj_factor_key_value_integrity_check`、`raw_adj_factor_partition_allowed_check`。这些检查不证明全市场股票覆盖；本方案复用其就绪语义，不新增一个要求全市场因子齐全的检查。job 再验证实际文件日期、主键及有效正数值，与已就绪的输入对应。Raw 避免 Silver 当前上市筛选漏掉历史对象，不改现有因子资产和消费者。

任一需要比较的旧股缺 T/P 值，记录“无法判断”及代码，不能内连接静默丢掉或写成无变化；生命周期能证明的真正新上市股票不补造上市前历史。整体输入资产未就绪时不启动；输入已就绪但个别股票不能比较时，保留未判定范围，不能伪称全部历史判断完成。它不等于技术因子本轮股票缺行，也不恢复股票覆盖发布门槛。

### 8.2 一个 job 内完整时序

1. 开始时核对目标日T、执行日期D、计划时点、截止时间、注册日期及唯一写入条件；再次确认股票复权因子Raw T/P已就绪，读取实际比较输入。
2. **在任何技术因子请求前**生成并完整保存目标T的变化名单、对应T/P值、各股原历史范围、无法判断范围及输入依据。同T输入未变可以核验后使用已有完整名单；输入变更则保存新依据，并保留以前尚未完成的原范围。名单是业务依据，不属于重试时弃用的下载候选。
3. 每轮以及失败后的日更重执行，都以BY_POINT重新请求原T的全部网络页。完整unit才交业务；业务错误不触发组件源重试。仅源候选在循环内保存；正常退出下载with、会话最终成功且本轮全部unit/行数对账通过后才记源完整、进入发布。每次执行只使用本run新下载源构建候选。自动入口五字段、准确层级、parent/root核对及截止规则见LLD§2.4。
4. 检查字段、日期、主键、类型及源/保存对账。将新源按主键合入当前T Raw，未返回旧行保留；校验、发布并读回Raw T。直接从这份合并后的Raw全部业务行生成Silver T，日期转DATE，校验并发布Silver T。这里“完整Raw”指合并后的文件，股票是否齐备另算；日数据没有最低股票数、比例或全历史完成门槛。
5. **以已发布Raw T计算历史前置。**应有集合为T上市A股扣除确认全天停牌股票；必须有真实覆盖依据且缺失代码集合为空。Raw不齐或覆盖未知时，记录缺失及历史待处理，结束本轮历史步骤：不下载、不合并、不提升任何历史文件，也不先处理名单中已到的股票。Raw齐备且日Silver必要检查通过后，才进入下一步。全天停牌缺T行不会造成应有集合缺失，仍可处理原名单内该股d<T历史；盘中停牌不扣除。
6. 核对完整变化名单内本次尚待处理的原范围，以及相应当前T/P输入；个股缺比较值仍明确待处理，不伪造无变化。同股票、基准、范围、契约及处理规则此前**整批成功发布并读回有效**的历史可排除；某失败批次即使已发布一部分，其原完整范围仍作为整体重试，不据中间文件缩小范围。技术源同名adj_factor不同只记录差异，不阻断，也不改源业务值。
7. 对本次确定的全部股票及原窗口重新下载完整历史源，整个约定范围取全、保存并校验后，按升序每批20个交易日合并。每个d<T先合并并发布Raw d，再从其全部业务行生成并发布Silver d；当前T不由历史阶段覆盖。同一正常运行内从完整源进入发布是正常流程；任何阶段失败后再次执行，都重新下载本次失败的原完整范围，不读取失败run候选继续提升。
8. 历史下载前、首次历史提升前、整个范围完成记录前，核对本次T/P输入仍有效，并核原T Raw、生命周期及最终停牌输入的文件身份。因子输入变化则停止；覆盖依据变化时只重新计算原T覆盖，不能确认齐备则停止后续历史步骤，保留正式文件和待处理依据。输入未变复用本run核验结果，分页和每个历史文件不重复扫描整份因子或全市场覆盖，不在同job无限重算。
9. 分别记录本轮日发布、T日Raw覆盖和历史完成/待处理。历史失败不撤销日文件或此前历史正式文件，执行异常如实失败。业务从已正式提交文件读当前结果；Raw/Silver多文件不是整体原子事务，不新增全Lake版本目录或整体切换服务。

例如名单A/B/C在19:00请求前已保存，19:00日Raw仍缺非全天停牌B，则日Raw/Silver照常发布，A/B/C历史都不启动。19:30用新请求补齐Raw且日Silver通过后，才处理三股尚未成功完成的原历史；若B确认全天停牌，它不属于应有缺失集合，可以没有T行。若历史下载完整后发布到第10日失败，重试重新下载该失败范围全部历史，已发布前10日保留作当前合并基础，不从第11日接旧候选。

最终合并按旧B行、新U个唯一键、交集K核对`B-K+U`；例如旧4,000、本轮4,800唯一键且漏回旧50个，最终4,850行，数字不是门槛。合法空响应不删除旧行；首次无有效行不伪造可用文件。每个阶段按日期/层合并，不逐股重写全市场文件。

历史下载按股票组织，正式文件按交易日组织，因此在回刷或repair发布时需合入该日全市场文件，保留其他股票。历史本地合并固定每批20个交易日，按有效SSE日历及原范围形成升序d<T清单，末批不足20日照常处理；不凑日、越界、造空文件或自动注册旧分区。每批最多40个日期/层文件，仍逐文件校验、提升和记录。20日不是网络页、下载unit、独立修复范围、失败后可跳过下载的边界或整个历史成功标记；批次变化本身不改变业务内容身份。

### 8.3 前一交易日只补一次与今天的半小时轮次

前日发起记录只按本数据集job、执行日期、前日目标和运行用途精确查询，最多11条用于发现超过十时点的异常；不扫描全run历史。每时点最多发起一次；旧run未终结就占位。旧run明确记为预检终止且未下载（`PRECHECK_NO_DOWNLOAD`），才允许下一时点使用新的提交序号；仅run失败、找不到记录或cursor为空都不能证明未下载。持久开始事实在首次下载前写入并读回确认，写不成功不联网，写后进程退出保守算已用；不追求证明网络报文实际发出的瞬间。LLD规定具体字段、统一run_key builder调用及异常测试，不另建调度状态表或下载器锁。

一次限制是自动调度保护，不取消管理员明确处理问题后手动重入的能力。手动仍须指定目标、范围、原轮次或新轮次及来源，不能悄悄恢复自动重试；日更重执行及历史失败范围都重新下载，不复用失败任务候选；正式已提交文件保留。前日 day coverage 已补齐与全部历史已完成分别记录，前者允许按规则推进今天；本期 Silver 与 Raw 行/主键对应；两层必要检查未通过不能标为处理完成，未来新增清洗不阻塞本期。

永久输入/契约/权限错误、确定目标冲突需人工；今天临时源错误可在后续时点重试，前日则仍受一次限制。cursor 只存日期、轮次和小型状态，完整范围在业务文件；常态目标2 KiB、复杂目标3 KiB、UTF-8硬上限8 KiB。持久 run 和开始记录用于防重，重启不清除；不能因 cursor 缺失把次数默认为0，也不能无界遍历全部 run/event。

自动multi_asset的op固定为`stk_factor_pro`，RunRequest配置只允许`ops.stk_factor_pro.config`下的`execution_day/target_trade_date/purpose/scheduled_slot/submission_no`五字段；today的提交序号为null，前日为1～10，attempt由用途派生。分区必须等于T，D/T/用途/slot须符合真实日历；不增加token、fields、分页或路径覆盖项。重新执行来源只从Dagster原生parent/root及已验证引用定位，不扫描目录或猜最新成功，准确schema、样例和接口见LLD§2.4。

因活动任务跳过当前slot的决定使用现有SensorResult cursor保存到Dagster原生持久tick；当前cursor被清空时读取同sensor、当天、最近一条已完成tick恢复小型closed_slots集合，不新增文件、表或锁。上游未就绪但未占用slot不提前关闭；真正首次启动仍可在当前slot发起。查询与保留期异常时保守跳过当前slot，不追补旧slot，具体原生接口/边界见LLD§3.5。

永久输入/契约/权限、结构、目标冲突、本地读写和未分类失败停止对应T/阶段自动重试；临时源错误仅允许按原时点及前日一次边界继续。sensor必须读取STEP_FAILURE的固定阶段/目标/retryable metadata，不能仅因缺股票再次提交。管理员修复并明确重新执行、取得同T/阶段真实成功事实后解除；清cursor、仅标run SUCCESS或未执行该阶段不能解除，已用前日机会不恢复。历史失败不清除日完成，也不阻止Q日已齐后推进今天；细化矩阵及有界读取见LLD§6.1。

### 8.4 变化名单的输入、持久化与分区注册

1. 名单归属于目标 T，包括前一交易日 P、完整变化代码/因子值、无法比较代码、最早已有日期至 T 的范围、源契约及处理版本、输入和范围依据。业务在 job 开始、技术下载前完整保存到本轮 staging；后续步骤读回，不靠 metadata 样本或 cursor 拼名单。
2. 每次同 T 自动job开始都重新核对股票复权因子数据集输入；手动repair先按§8.5检查原T Raw齐备，再核T/P。输入相同则复用完整名单，补入或修订则重新核对并保存新记录。不是每下载一页就重算，也不另建监控进程。新记录必须保留同T旧名单尚未完成的范围；即使当前T/P重新相等，也不能把尚未完成的历史静默删掉，须按当前有效依据完成回刷，或有生命周期证据说明本来没有该段历史并留下具体原因。以前目标日的未完成名单保留且可追溯，不因今天建新名单而覆盖或丢弃。
3. 名单复用与历史已完成复用分开。历史只从**此前整批已完整发布且读回有效**的完成记录推导，比较股票、该股 T/P 值、历史范围、契约与处理规则；不能把下载到第9股但整批第10股失败当作逐股续传。补入新股改变整份因子摘要，不能无条件推翻其他股票相同基准下的完成依据。
4. T 日正常增行不使已完成的 `d<T` 历史自动失效；目标被外部改写、股票因子/范围或规则变化则复核，不盲目复用。当前 run_id 是轮次身份，不是历史数据需要重下的理由。日期更早的待处理历史不在 sensor 中扫描/自动另起任务，管理员通过手动repair job引用其原完整名单/范围处理；不借今天的新名单覆盖旧待处理，不增加跨日自动任务。正常自动任务的前日保护与午夜截止不变。
5. 变化股有历史时更新已有最早日期至 T 的全部约定窗口，不缩成30/90日，不只改 adj_factor、不按比例缩指标、不本地重算。多个股票/范围交组件按代码扇开，多个窗口分次调用，完整 unit 立即保存并释放。最早日期从可信初始化记录或有界聚合取得，不在每 tick 扫全历史。
6. 独立动态分区 `cn_a_stock_factor_pro_trade_days` 由 Raw、Silver、job/check 共用。bootstrap 在批准范围及日历核实后先注册；日常注册今天（若开市）和上一个交易日，不等因子或 Tushare 发布，不注册未来、不删旧键。用于比较的 P 若更早，只读已存在的股票复权因子数据集分区，不因此自动安排技术因子补采。
7. 借鉴分钟线完整清单、范围和执行前复核，不照搬500只上限、截断清单或新增跨 job 触发链。两个综合 check 不增加；覆盖或两接口同名因子值不一致不进入其失败条件。历史分区事件需明确实际分区和开销，不能以当日一条事件代表全部历史。

### 8.5 管理员手动历史repair job

**必须提供`raw_tushare_stk_factor_pro_repair_job`。**它只处理保存的原目标T及原历史名单/范围，不嵌套日更新、不发布T，不增加自动repair sensor。沿原历史窗口的BY_OBJECT_RANGE若包含T可完整保存源返回，但正式只发布d<T。

管理员从原日更或repair run的metadata复制完整配置。输入固定为四个必填字段：`target_trade_date`、`source_run_id`、`expected_history_plan_digest`、`expected_history_ranges_digest`。不再有控制旧源复用的开关，不暴露任意股票、日期窗口、fields、路径或凭据。`source_run_id`仅定位原完整名单、原范围、批准依据和失败证据，不表示从该run读取下载候选。引用run须属于本数据集和原T；repair引用repair时保留可核对的原始完整名单/范围出处，不改原run，不扫描历史任务或staging目录猜最新候选。

执行顺序固定如下：

1. 校验四项输入、run身份、原T、原完整名单/范围摘要、契约/规则及允许的staging位置；不匹配即停止。
2. **检查原T已经发布的Raw是否按当日应有股票集合齐备。**使用原T的生命周期和已核实最终停牌数据，不能拿今天覆盖替代。缺股票、Raw不存在、覆盖依据未知或无法确认齐备，直接失败，固定提示**“原日期数据缺失”**，附原T、缺失代码数量/证据位置及“请管理员先处理原日期日数据”。此分支零Tushare请求、零正式文件提升，不启动日更新，不以对象T单日窄查询确认资格，不自动补日，不擅自改分区。Raw齐备是手动repair与自动历史共同的硬前置。
3. 检查原T/P的股票复权因子输入、原历史分区、当前目标及唯一写入条件。仅T/P值后来修订且股票/范围/契约/规则仍在原授权内时，本run保存新因子依据和差异；不要求管理员另起准备任务，也不因当前T/P重比相等删除原待刷范围。缺权威值或其他身份变化明确停止说明。
4. 根据原完整范围及可核对的**此前整批成功**记录确定本次尚待处理的原失败范围；此前独立成功的其他范围不混入。失败范围即使部分日期或股票已正式写入，也不从中间恢复下载；先保存本次完整名单及范围，再重新下载该范围全部历史源。空待处理范围核对后如实返回无待处理历史，不为产生网络请求重复刷成功结果。
5. 全部约定历史源取全并校验后，按20交易日/批、逐d先Raw后Silver发布d<T；核对并记录整个本次范围是否完成。源完整后进入发布属于本次正常流程，不是在失败任务之间复用源。
6. 任一阶段失败、异常退出或取消后，完整名单、原范围、失败证据及已提交正式文件保留；下一次获准repair仍从原名单定位失败完整范围，重新下载全部源，不读取本次失败候选续发。新记录写本run，不改原run；原完整名单/范围摘要用来限制授权，而非允许旧源复用。

repair、日更、bootstrap及其他同数据集写入互斥，复用DG既有调度约束及入口预检，不新增下载器锁、线程、进程或共享额度。人工入口不受19:00～午夜自动排程限制，但正式范围及执行仍需批准；不会消耗、重置或恢复前日的一次自动机会。缺应写历史分区或唯一写入条件就停止，不边修边扩大范围。

历史源网络完整但合法空、或少回原已存在且应刷新的键时，合法返回行可以合并，旧缺行保留并记录未刷新范围，不假报整批成功。例如原100条只返回99条，发布合法99条并保留旧1条，整范围仍待处理；后续再试重新下载该失败/未完成完整范围，不按缺1条续传。技术源同名adj_factor差异只排障，不要求历史值全部等于T日权威值，不新增blocking check。

[Dagster RunRequest / SensorResult](https://docs.dagster.io/api/dagster/schedules-sensors)对同一sensor已用run_key去重，清cursor不能恢复机会；最短评估间隔不等于精确准点。本规则仅在本数据集业务合同中落实，不改下载组件或其他数据集。

## 9. 发布安全、失败与恢复

bootstrap、正常日发布及历史发布都使用候选校验、原目标核对、提升意图、同文件系统`os.replace()`和读回；多个Raw/Silver文件不是整体事务，不新增备份、快照、共享锁或下载器进程管理。bootstrap自身中断恢复按§7独立执行；本节失败候选弃用规则只规定Tushare日更及历史repair，不改写已批准的bootstrap规则。

日源与历史源分别保存`source/day/source-complete.json`、`source/history/source-complete.json`，记录本run、阶段、D/T/P、原名单/范围摘要、全部约定unit和文件摘要。记录只证明**本次仍正常运行的阶段**源已取全，允许随后校验和发布，不代表股票已齐或整个范围已发布；任务一旦失败、退出或取消，下次不得因为这个完整记录存在而复用源。完整记录和旧候选可以保留作证据，但不再是跨失败run的发布输入。

| 情况 | 行为 |
| --- | --- |
| 日源完整但合并后Raw仍缺应有股票 | 发布有效日Raw/Silver，报告覆盖；历史不启动。今天等下一固定时点，前日一次后仍缺则停止当天自动推进并交管理员。 |
| 日源合法空 | 保留旧正式行，按当前合并Raw真实计算覆盖；首次无有效行不伪造可用文件。 |
| 任何阶段失败、超时终止、异常退出或取消 | 获准重执行一律新下载。日更重新取得原T日源；历史重新取得该失败原股票/窗口全部源，不按页、股票或20日批次继续。下载器同页有限重试不受此条改变。 |
| 源已完整但清洗/合并/发布失败 | 不复用该失败任务的源或未发布候选；下次重新下载，当前正式文件作为新合并基础。 |
| 已提交部分正式文件 | 保留、不删除、不回滚；旧源弃用不等于删除正式文件。重新下载后从当前正式文件合并，未返回旧行保留。 |
| schema、主键、日期、转换或目标冲突 | 保留原因及小样本，阻止错误候选继续发布；不让业务错误进入组件源重试，人工修正后重执行仍新下载。 |
| 正式替换成功但记录失败 | 当前文件尽力完成同步、读回及证据；仍失败则保留提升意图和真实文件，下一次先认清已提交事实用于排障，再新下载。不能用认清事实作为续发旧候选的入口。 |
| Raw覆盖不齐或未知 | 日数据仍可发布；自动历史不启动。手动repair直接报错“原日期数据缺失”，零网络、零正式写入，交管理员处理，不嵌套补日。 |
| 日数据已发布而历史失败 | 日文件可用，历史待处理；手动repair只处理原历史，不重新日更。历史失败前已提交的正式文件也保留，但整个失败历史范围下次重新下载。 |
| 观察或事件记录失败 | 不回滚业务文件；缺必要证据时不能假报整批成功，不因界面状态缺失自动把正式文件删除。 |

取消在网络请求、校验、提升前检查；当前文件已经替换时，尽力完成同步、读回及记录，再停止下一文件。候选失效仅表示后续不得使用，不授权本轮物理清理。旧完整名单、授权范围和失败记录继续限制新请求，不能据失败重执行扩大历史。

### 9.1 本run逐文件核对与成功历史完成依据

每次实际提升前，从**当前正式文件**生成候选并保存本run提升意图：阶段、原T、实际日期/层、原名单及范围、当前目标指纹、候选/预期发布指纹和必要检查结果。替换前再核目标没有在候选生成后被其他写入改变；不一致就停止，不能覆盖未知改写。正常流程只提升本run新源生成的候选。替换成功后读回并写本run完成记录；源/候选/意图/完成记录身份明确，不能只比文件个数。

任务已经失败后，提升意图仅帮助认清哪些正式文件已经提交，不授权继续提升旧候选。新run按本run新下载源与当前正式文件重新合并；来源本身可能修订，不能承诺来源数值永远不变。

此前**整批已成功且仍有效**的历史完成事实仍用于避免无关重复：必须整范围发布、读回及必要事件通过，且产生该结果的run最终成功；全部物理文件写完但事件或收尾失败，仍按失败任务重新下载。按股票、当前T/P、范围、契约、规则及该范围正式完整业务内容核验；其他股票改变同一整日文件，不自动推翻本批成功结果，可对原范围做有界内容核对。失败批次里的部分写入不等于整批成功，不用于从中间跳过重试范围。成功依据与失败候选严格区分，前者保留，后者任何阶段失败后都不能续发。

sensor 不遍历全 Lake、不读取无界事件历史；批量检查须一次读取明确文件集合，避免包一层 Python 循环仍逐分区扫描。超过 100 个历史分区或 `分区数×blocking checks数>1000` 时，按性能治理规范做批量聚合与分层验证，不逐分区全深扫。

| bootstrap | 与批准来源范围逐窗口/日期汇总对账，并记录缺日与覆盖限制；不能仅凭估计总行数验收。 |
| Raw→Silver | 本期完整保留261业务字段及对应行，trade_date归一化为DATE，其余合法值保留；核对主键、行数及字段映射。未来新增清洗另行确认，不影响本期按此验收。 |
| 股票覆盖（不阻断日发布，阻止未齐时回刷） | 按目标日非停牌上市代码集合与合并后已发布代码求差，缺失决定补采并阻止历史启动；依据未知不宣告补齐，也不阻止有效数据使用。 |
| 复权更新 | 变化集合和范围完整、应更新文件读回、未变化行保持相同；“无变化”须能证明比较过。历史完成与当轮日数据发布结果分开，日阶段先提交，历史异常不回滚日文件；缺前因子不记0变化。 |
| 发布/恢复 | 文件指纹、批次、checkpoint 和最新物理结果一致；旧事件不能证明新文件仍有效。 |

计算、合并和恢复正确性主要由独立金样本及离线有界验证证明；正式checks检查必要数据合同，不把全市场股票覆盖当作失败条件。覆盖另作有界集合计算；不新增按股票的常驻check、不为判断覆盖重拉全源或重算历史。物理文件可用判断与正式checks共用纯校验及聚合语义，股票补齐和历史完成另有明确事实，不能把三者压成一个ready。

**已确认：Raw、Silver 每层只设一个综合 blocking check，共两个检查定义。**Raw 检查合并文件可读、字段/主键/日期及本次来源保存范围与计数；Silver 检查合并文件可读、归一化/清洗后的合同及与本批输入的对应关系，本期按完整业务字段、仅日期归一化及与Raw逐行对账检查；后续新增清洗另行变更。不为每个字段、每只股票或每个历史窗口分别新增 check。发布前候选校验、文件检查及整批完成判断尽量复用同次聚合结果，不能在三个位置重复扫描同一批历史。两个检查定义不代表任意历史范围只产生两条检查事件；本批涉及哪些分区、需要多少事件及其读写成本在 LLD 列清，并须在隔离 instance 核验分区及事件关联，不把样本 metadata 充当完整核对。

缺股票不使上述两个check失败，未补齐时本轮仍可发布成功；检查成功也不能令sensor误以为全天已经补齐而停止。历史分区及当日检查依赖按LLD的分阶段编码设计落实，不能继续以全部历史已绿作为不加说明的当日发布门槛。只计十个实际执行的目标日发布阶段，共20个物化及20个检查结果（可能含一次前日，不能额外加一次前日而仍称20）；历史阶段、同日重复发布和重执行另计，不能按不同日期去重估算，也不声称整晚只有两个事件。内容未变时是否省略重复写入/事件须在LLD技术设计明确。

复权变化清单和应发布文件的完成核对仍是必要业务条件，但不因此增加一个扫描全部历史的常驻 blocking check。初始化完整性审计与日常检查分开。检查名称、分区绑定、读取范围、SQL/文件读取次数及正常/重入验收耗时必须在 LLD 明确并验证；本次 Prod 审计不是这些尚未实现检查的性能验收，没有秒数承诺，也不能在缺少开销上界时进入开发。

Raw/Silver 分区 checks 必须显式使用与资产相同的 `partitions_def`；隔离 instance 中核对实际产生的 check event 分区，不能只看函数返回成功。开始实现后按代码约束运行必要单元、契约、隔离集成及最小真实验收；本轮没有运行数据管道测试，也不声称接入已通过。

源到本地及两层对账按LLD§9.1～9.2的确定规则实现：HTTP允许int/Decimal/NULL，Prod数值按已核实Float(53)取得float/NULL，统一显式转换为有限DOUBLE；不接受bool/字符串数字，不用TRY_CAST吞错，不加任意容差。HTTP日期严格YYYYMMDD，Prod DATE显式格式化，Silver再形成DATE；完整字段按名称对应并投影为契约顺序。先核唯一主键，再以NULL-aware双向键差和全部数值字段比较核对，合法NULL/负数正常；合并后保留旧行不能误当历史已经全部刷新。schema、函数签名、检查结果结构和独立样本均在上述LLD章节。

### 12.3 可见信息和排障顺序

资产、check、job、sensor 均使用中文说明，讲明数据是什么、读取什么、何时可执行、会改哪些文件以及失败后如何处理。metadata 先展示 `summary`、`next_action`、结果、输入和过滤范围、诊断位置，再展示机器字段。

长任务展示阶段、当前日期/股票窗口、已完成/总量、页数、来源/目标行数、耗时和最后更新时间；业务将标准页/重试/unit通知接到现有任务观测，并在退出或异常后报告最终结果；下载器没有固定间隔心跳，不能承诺阻塞网络调用期间持续发回调。进度随已完成工作推进，不能伪造完成量，ETA 无依据时明确暂无法估算。

多个下载任务组成一个历史批次时，组件 total_units 和百分比只覆盖各自会话，不会自动累计成整批进度。业务依据已确定的股票×窗口范围及实际完成事实汇总批次状态，并分别展示下载、业务保存、合并和发布阶段；某个会话 100% 不能显示成整批完成。

每轮展示目标日、计划日期/时点、本轮源代码数、合并后可用代码数、应有/缺失代码数、覆盖依据和历史状态；完整清单放业务文件，metadata仅引用位置和摘要。午夜结束仍缺股票时如实显示缺失，不把窗口截止显示成成功补齐；前日一次仍缺则停止当日推进并明确提示管理员；更早旧洞不自动扩展补采，不在午夜开启新一晚重试。
