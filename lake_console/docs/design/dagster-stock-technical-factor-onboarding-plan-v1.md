## 1. 目标与已确认要求

将 Prod 已有的股票技术因子历史数据 bootstrap 到正式 DG Lake；初始化完成并验收后，由 DG 自动从 Tushare 下载后续交易日数据、处理并发布 Raw/Silver，不继续每日从 Prod 导出本数据集。DG 同时监控复权因子变化，从 Tushare 重新获取受影响股票的历史技术因子。直接使用已完成的下载器及语义适用的既有读写能力，不把抽取其他公共模块或迁移旧数据集作为前置条件。这里描述的是接入后的运行方式，当前尚未开发或启用该自动更新。

当前顺序为：确认本方案 → 完成本数据集各步骤 LLD 和代码影响面审计 → 调整契约名校验并登记完整契约与固定请求方式 → 实现并隔离验收 DG 接入 → 分别批准正式初始化、事件补记及自动更新。组件已有六种模式，不重做组件建设；本数据集按具体用途选择模式。每一步先完成对应 LLD 再开发，本轮不编写本数据集 LLD。

已确认要求：

1. 历史 bootstrap 来源是 Prod；日常来源是 Tushare。不能把初始化改成从 Tushare 重拉全部历史。
2. 复权因子监控及受影响股票的历史更新是本次接入的组成部分，不能只有当天追加。
3. Tushare 请求使用已完成的下载器；复用 DG 现有 DuckDB、日历、运行合同以及可直接适用的写入与恢复能力。旧数据集迁移、其他公共模块抽取均不在本次范围。
4. 按 DG 接入模板设计 Raw、Silver、Catalog、checks、job、sensor、初始化、恢复、性能与人的排障路径。
5. 正式 Lake 只使用 `/Volumes/datasource/data_lake`；候选文件只使用 `/Volumes/datasource/data_lake_staging`。不使用旧 Lake、旧 Console、Kopia 或已经清退的一次性修复入口。
6. tushare数据下载组件每下载完整一个unit，就向业务交付一次源数据；分页不逐页回传，也不等整批结束才返回。业务按本工程规则决定正式存到哪里、怎么写入，复用现有写入与发布能力。下载完成、正式写入和数据集完成分别确认；业务校验或写入失败不进入源请求自动重试。

本次接入只在 DG 内维护 `stk_factor_pro` 的一份完整源契约及其消费者。Prod 定义只作参考、Prod Raw 只作获准 bootstrap 来源，不修改 Prod 契约、DatasetDefinition、执行器或消费者；财势乾坤接入、三工程契约统一、契约平台和跨工程 import 均不在本次范围。不新增本地 MACD/KDJ 计算，不修改 Wealth、ClickHouse、Redis 或其他数据集的调用方式。

| 项目 | 方案 |

| 时间输入 | 正常更新为一个交易日；历史更新为明确股票集合及起止日期。接口可传区间，不代表每日每只股票都必须有一行。 |
| 执行单元 | 下载 unit 为一个交易日的全市场完整结果，或一只股票在一个明确窗口内的完整结果；网络分页不是 unit。发布单元是一个日期的一层文件，与下载 unit 不相同。历史任务按有界日期窗口组织，完整 unit 交付后及时形成业务候选事实。 |
| 完整性 | 按 SSE 日历确定应检查的交易日；股票行覆盖结合该日来源结果及已核实的上市、退市、停牌事实解释。不能用当前上市股票数要求每个历史日都相同。 |
| 数据含义 | 保存源端当前可取得的因子结果。历史会随复权更新，不构成“历史当时所见”的版本档案。 |

### 4.2 Raw 与 Silver

建议采用两个资产，名称在后续 LLD 和全消费者核验中冻结：

| 层 | 建议资产 | 职责及路径 |
| --- | --- | --- |
| Raw | `raw_tushare_stk_factor_pro` | 显式保存全部 261 个源业务字段；建议按 `raw/tushare/stk_factor_pro/trade_date=YYYY-MM-DD/data.parquet` 组织。`trade_date` 保留源 `YYYYMMDD` 字符串；Prod DATE 导出时按合同转换。 |
| Silver | `silver_stock_factor_pro` | 保留相同业务字段和主键，将 `trade_date` 标准化为 DATE；建议按 `silver/stock_factor_pro/trade_date=YYYY-MM-DD/data.parquet` 组织。 |

以上路径均由 `defs/paths.py` 统一提供，不在脚本、页面和 Catalog 分别拼装。具体文件名须与该目录的现行规范一起核定。数值采用 DOUBLE，保留合法 NULL；指标可负，不设统一“全部非负”或“全部非空”规则。主键、日期解析错误、重复主键和数值转换失败必须阻止发布，并给出原因及样本，不能静默丢弃。

Raw 和 Silver 均保留来源返回的业务行，包括历史退市股票；本方案不额外按“当前上市”筛掉它们。来源存在非预期证券类型时先解释合同与真实样本，不能依靠隐含过滤消除行数差异。Silver 在这里提供标准日期和可复用事实，不增加重新计算的技术指标，因此不需要新增 Gold。

建议独立使用 `cn_a_stock_factor_pro_trade_days` 分区定义，Raw、Silver 和其分区 checks 共用，避免借用分钟线历史起点或当前上市因子分区范围。初始范围建议以 Prod 实际来源 `2020-01-02` 至经确认的截止日为准；准确范围、缺日清单及截止日冻结后才能执行。不默认拉取 2020 年以前的数据。

以下是完成上述登记后的调用形式，当前代码尚不能按此名称执行；日期示例不表示本轮请求已发出。

```python
from orchestrator.tushare_download import (
    DownloadMode, DownloadTask, TimeRange, TushareDownloader,
)

daily_task = DownloadTask(
    contract_name="stk_factor_pro",
    mode=DownloadMode.BY_POINT,
    points=("2026-10-21",),
)

history_task = DownloadTask(
    contract_name="stk_factor_pro",   # 同一份完整契约
    mode=DownloadMode.BY_OBJECT_RANGE,
    objects=("000001.SZ",),          # 业务确定的受影响股票
    time_range=TimeRange("2026-10-19", "2026-10-21"),
)


def download_and_save(task, save_unit, *, control=None, on_progress=None):
    downloader = TushareDownloader.load()
    session = downloader.download(task, control=control, on_progress=on_progress)
    with session:
        for result in session:
            save_unit(result)        # 业务校验、候选落盘及提交，不放进进度回调
            del result
    return session.summary
```

无分类展开时，daily_task 的一个 unit 是该交易日全市场完整结果；history_task 的一个 unit 是该股票在所给整个窗口的完整结果，不是每天一次。示例短窗口仅说明输入，实际历史更新仍须覆盖 §8 确认的全部历史，由业务安排连续、有界且不遗漏的窗口。

窗口由业务在调用前确定，下载器不会根据内存余量自动缩小 BY_OBJECT_RANGE 的范围。一只股票的完整历史可以是一个经过确认可承载的窗口，也可以分为多个连续窗口，具体划分在 LLD 明确。同一股票的多个窗口须分次构造任务，不能把重复代码的多个 object_ranges 放进同一个 DownloadTask；当前输入校验会以 1102 拒绝重复对象。

**股票代码的扇开由下载器完成，不要求业务逐只股票调用。**DG 业务确定变化股票清单及各股票的历史范围；同一窗口可一次传入多个 objects，各股票范围不同时可一次传入每个代码一项的 object_ranges。下载器现有 UnitPlanner 按代码生成 unit，串行下载并逐个完整交付。例如同一窗口传入 3 个代码，一个任务就会生成 3 个 unit。业务安排多个时间窗口时按窗口分次提交，可在每个任务中继续传入多个代码；“多窗口分次调用”不是“业务按代码扇开”。日常 BY_POINT 则直接按交易日取得全市场结果，无需逐个代码请求。

### 6.6 已有组件边界及接入要求

组件同步调用，业务在 DG 独立任务进程的执行线程中创建、使用和关闭实例即可；需要持续响应页面时由业务另开下载线程。组件不创建线程/子进程，不管理业务通信、全机并发、同 token 合计频率或账号额度。

业务可注册标准 PAGE_COMPLETED、RETRY_SCHEDULED、UNIT_COMPLETED 回调；回调在下载调用线程同步执行，只传摘要，不传分页数据。业务负责把摘要交给页面或其他进程，并在结束/异常后转发最终 summary；不能等待下载器另发结束事件。普通回调异常只影响观测，业务保存异常必须从结果循环抛出，不进入源重试。

完成一个完整 unit 后才交付不可变内存结果，不预取下一 unit；当前默认 2 GiB 是单 unit 工作空间约束，不是进程总内存保证，不重新引入文件交付或并发名额。业务及时消费并释放结果，完整 unit 交付后要及时形成可读回的候选事实，避免把所有历史留在内存最后才写。

分页或重试阶段取消丢弃未完成 unit。完成回调中 cancel 或 DownloadCancelled 都先交当前完整 unit，再停后续；若已是最后一个则正常下载完成。使用 with 确保正常、提前退出、取消和业务异常均关闭自身资源，网络取消受当前同步调用返回/超时约束。进程重启后未完成 unit 从第一页开始；哪些结果已形成候选或正式提交由业务记录，不能用进度 100% 或下载完成代替数据集完成。

### 7.1 范围与来源

历史因子结果可能已经被 Prod 按较新的复权基准更新。初始化前还须核对 Prod 因子与 DG 同一截止日期的复权基准，选取发生过复权变化的股票和历史日期做有界对照；不能用单个当日价格相等证明全部历史已正确刷新。若发现未解释的不一致，先处理范围和来源结论，再执行正式初始化。

截止日期也不能阻止 Prod 在导出期间更新旧日期。正式导出须事先协调来源维护窗口，确认批准范围内没有并发历史重刷，并按窗口记录来源内容核验依据；发现来源已变就停止并重新确认受影响范围。不能通过锁住生产表或长期持有全历史事务换取一致性；续跑和最后来源复核的开销纳入预算。

### 7.2 导出、候选、发布

1. 用日期索引组织有界窗口，显式排序、字段投影、SQL 超时、单次行上限；使用“上限加一行”发现截断，不把上限内的结果冒充全部结果。窗口大小、连接次数和单窗口预算由代表性样本确定。
2. 业务在有界只读事务中流式读入，按完整契约与本地映射做 schema 和主键验证，用 DuckDB 形成日期候选。不能在 Python 中累计整个历史后首次落盘，也不启用覆盖全部历史的数据库长事务。
3. Raw 候选与 Silver 候选分别校验。每个已完成独立文件形成可读回事实，从 staging 通过同文件系统 `os.replace()` 到正式目录。
4. 逐文件记录来源范围、候选/目标指纹、校验结果和完成情况；已有目标只在内容等价或已批准更新理由下继续。意外目标变化、候选变化或来源范围改变必须停止。
5. Raw 和 Silver 的多个文件不是整体原子提交。中断后保留已完成文件，续跑识别“已提升但 checkpoint 未完成”等情况，读回核验后推进；不能因状态记录失败撤销已提交业务文件。
6. 全部物理验收完成后，再单独设计和审批 Dagster 历史事件补记。Direct Lake bootstrap 不等于逐日 Dagster backfill，事件不能代替文件验收。

## 8. 每日更新与复权变化后的历史更新

历史与日常来源明确分开：bootstrap 从 Prod 的 raw_tushare.stk_factor_pro 读取已批准历史；完成初始化验收并另行批准启用后，DG sensor 自动判断待处理交易日及源可用性，发起 DG job，由业务调用下载器直接请求 Tushare，再校验、合并、发布本数据集 Raw/Silver，并处理必要的复权历史更新。本数据集日更不继续从 Prod 导出，也不新增 Prod 任务完成状态作为触发条件。

初始化记录最后已验收交易日 B，后续从 B 之后的待处理交易日衔接，不能直接跳到“今天”而遗漏交接期间的数据。待处理日期仍服从 §8.3 的有界连续性规则；交接间隔超出常态窗口时走经确认的专项恢复，不悄悄扩大 sensor 扫描或重做全历史 bootstrap。新 sensor 默认 STOPPED，完成开发、真实验收及启用批准后才进入自动运行。

### 8.1 复权因子的使用范围

交易日 T 的前一交易日 P 由已验证的 SSE 日历确定，不用自然日减一。新数据集建议从已有 `raw_tushare_adj_factor` 的 T/P 分区规范化读数，再与本数据集需要监控的股票范围对齐；这样不会因为当前上市 Silver 的筛选而漏掉来源仍返回的股票。先验证 Raw 的字段、日期、唯一性和范围，文件存在不足以进入比较。

本数据集在业务侧读取并对齐相邻交易日因子，不以先抽取公共因子模块为前置；现有消费者保持原来源及原判断。不修改 `silver_adj_factor` 的上市筛选，不另建重复因子资产，也不直接依赖分钟线 repair job 的成功状态。

新数据集的变化判断采用源复权因子值变化，不给合法变化加未经证明的阈值。旧股票缺少 P 的值不能当作“没有变化”；生命周期能证明的新上市股票不因没有上市前因子而自动补造历史。范围内股票在 T 缺值、生命周期不足或 Raw 覆盖不明时，输出具体原因并阻止该次完整性通过。退市且来源不再提供新日因子的股票保留已有历史，不要求退市后继续每日产生记录。

目前尚无本数据集所需的 DG 物理因子覆盖核验结论。对应 LLD 必须写清这一核验及代表性对照，相关执行前补齐；不能因 Raw 文件存在就宣称全市场覆盖已经通过。

### 8.2 日常流程

1. 在源端已发布完成、T/P 因子及日历可用后，以日期 T 形成一个 unit，下载组件取得全市场完整 261 字段的全部页后交业务一次。业务校验并在 staging 保存当天基础候选；此时尚未正式发布，不逐页调用业务写入。
2. 读取 T/P 因子并识别变化股票；将该股票集合、输入因子指纹、日历、来源日期及历史范围纳入同一可追溯批次。执行时重新核对输入，不能用已经变化的输入继续旧批次。
3. 对发生变化且本数据集已有历史的股票，确定从其最早已有日期到 T 的完整更新范围，再按已确认的业务窗口构造 BY_OBJECT_RANGE 任务。每个 unit 是一只股票在本次窗口内的全部 261 字段，完整交付后，业务校验、写入 staging 并记录可读回事实，再领取下一个 unit；不将所有股票结果一直留在内存。所有窗口合起来必须覆盖完整历史，不能仅修改 `adj_factor`、按比例缩放价格或本地重算部分 MACD/KDJ。
4. 等本批次所需下载结果完整并通过业务检查后，按日期汇总合并。日期 T 使用第 1 步的全市场基础候选，历史日期使用对应正式旧文件；受影响股票的新结果按主键替换或加入，未受影响行保持相同。T 的历史更新结果如与基础候选同键，核对来源及因子基准一致后使用本批历史更新结果，不能追加出重复行。每个受影响日期每层只形成并正式提升一次最终候选，不先发布当天文件再因历史更新重写一次，也不每处理一只股票就重写全市场全年文件。
5. T 当天最终候选与历史最终候选采用同一套发布、逐文件 checkpoint、取消和恢复规则。没有变化股票时，当天基础候选通过检查后即可作为最终候选。正式文件的提升顺序和同日写入互斥方式由 LLD 明确；bootstrap、日更、历史更新不能同时写同一目标。
6. 物理读回、范围与 checks 完成后，才记录该批次完成。没有变化也要有“已检查、无需历史更新”的完成结论；0 只变化、源请求失败、空数据和因子缺失必须是不同结果。

历史范围不能用固定 30/90 日截断。新上市且没有本数据集既有历史的股票通过正常日数据接入；其他无历史对象先解释原因，不能由最早日期查询为空直接推导“无需处理”。

须核对 T 日股票因子返回的 `adj_factor` 与本批次 T 日独立因子输入一致，并对历史结果按对应日期做有界抽样核验；不能要求所有历史行的因子等于 T 日因子。源发布尚未一致时先等待或报错，不能把两个不同时点的结果拼成成功批次。历史请求过程中基准再次变化时，保留已取得证据但不继续按旧基准完成整批，先重新确认范围。

行数对账分开计算：每个下载 unit 的源返回、业务归一化及 staging 保存行数一致；最终日期文件按旧数据与本批新结果的合并关系核对，不能要求只含变化股票的源结果行数等于全市场目标行数。设基础文件有 B 行，本批该日新结果有 U 个唯一主键，与基础重合 K 个，则合并后应为 B−K+U 行，并验证未更新行保持相同。例如原文件 5,566 行，更新其中 3 只股票仍应是 5,566 行，不能要求最终文件只有 3 行；bootstrap 则按批准来源范围直接对账。

源端新结果缺少原有主键时先解释停牌、数据修正或读取不完整，不能默认按源返回删除旧行。超出已批准历史范围、缺失来源、资源承载不足时保留未完成状态，不静默缩短区间。

### 8.3 Job、Sensor 与日常完成条件

按“源可用性判断、日更、受影响历史更新、完成校验”划清职责。sensor 只做有界判断和请求编排，不写 Parquet、不拉全历史。具体 job 拆分在 LLD 确定，但必须能独立展示日数据和历史更新的进度、失败及重试。

日常连续性复用默认最近 10 个 expected trade dates 的有界窗口，优先推进最早可行动日期；长停机与窗口外缺洞走专项恢复，不能不断扩大 sensor 扫描范围。上一批需更新的历史没有完成时，不能把后续日期标成整个数据集已就绪。

单文件检查通过只证明该文件有效；本数据集日常完成还要求所有应发布 Raw/Silver 文件读回、约定 blocking checks 通过，以及该批次所需历史更新或“无需更新”结论匹配完整范围。业务对外报告的数据集 ready 必须包含这些条件，不能用单文件通过、run SUCCESS、单条 materialization 或一段样本股票列表代替。失败或 checks 未过时给出下一动作，不无限自动重试。

使用完整变化股票范围及其指纹核验批次，不只保存前若干只股票冒充范围；大量列表存诊断文件，cursor 只保留定位与少量状态。cursor 常态目标不超过 2 KiB，复杂情况控制在 3 KiB 内，硬上限 8 KiB。新 sensor 默认 STOPPED；源发布时间和执行窗口经实测再定，不套用分钟线 19:40 或 MACD 的自动股票数上限。

## 9. 发布安全、失败与恢复

bootstrap、日更和历史更新使用一致的发布步骤：先校验完整候选，记录提升意图，检查正式目标仍与预期相同，再原子提升并读回完成。已有 publisher 的业务等价比较使用集合差异，因此必须先保证主键唯一，不能将集合相等误当成重复行也被验证。

| 情况 | 必须达到的行为 |
| --- | --- |
| 请求卡住、超时、取消、业务进程退出 | 本数据集按固定 HTTP 方式和同步请求边界处理，不因取消强制杀下载线程或切换 SDK。业务进程退出不等于正常关闭或完成业务提交。 |
| 已收到源数据，业务校验或写入失败 | 停止后续下载，保留业务错误原因；不触发源请求重试，不重做业务提交。业务依据完整unit接收、已提交结果及checkpoint处理续跑，组件不清理业务文件。 |
| 下载 unit 已返回，业务 staging 尚未完整保存 | 不把回调或 download_complete 当作可续跑事实；下次从该 unit 的第一请求重新下载。 |
| 全部下载结束，正式发布或目标读回失败 | 保留下载完成事实，业务写入及整批任务仍未完成；由业务检查目标和恢复，不能把下载完成显示成数据集ready。 |
| 数据缺列、错日期、重复键、转换错误 | 阻止发布，保存原因及小样本，不跳过后继续宣称完整。 |
| 业务候选完整保存、正式文件未变 | 核对候选内容、契约版本、范围及本批输入仍匹配后复用；候选和记录不一致时先读回确认，不能只凭“下载成功”跳过源 unit。不重新下载仍然有效且已完整保存的来源单元。 |
| 正式文件已提升、完成记录未写成 | 用候选与目标指纹及读回结果确认实际情况，再补齐本次续跑状态；不重复覆盖。 |
| 正式文件被其他任务改变 | 停止并展示冲突，不能覆盖新的合法数据。 |
| 一部分 Raw 或 Silver 已完成 | 保留已完成文件，整批继续未就绪；续跑处理未完成文件，不重新扫描并重算全部历史。 |
| 状态或事件记录失败 | 业务文件不回滚、不删除；保留明确的待核验状态，按物理事实恢复。 |

写前检查正式挂载、staging 与正式目录所在文件系统、空间、目标冲突及维护窗口。取消在请求、导出、校验、提升前后检查；已完成单元保留，取消后不领取新单元。不会宣称多文件整体原子性，也不新增文件备份或快照。

## 10. 性能测算与停止条件

### 10.1 已有样本规模及暂定请求量模型

| 场景 | 当前可以测算的量 | 需要补的实测 |
| --- | --- | --- |
| 日更 | 既有样本 N=5,566 行、F=261 字段，按暂定 p=10,000 和不足页结束规则，预计 `floor(N/p)+1=1` 次请求；不是新的实测请求数。 | 有界核对分页、完整字段响应字节及耗时、业务调度频率；恰好满页仍须后续请求确认结束。 |
| bootstrap | 2026-10-18 的 R 估计约 832 万行；仅 259 个 DOUBLE 的未压缩数值量约 17.25 GB/层，Raw+Silver 约 34.50 GB，尚未计字符串、NULL、压缩、索引或 spill。 | 当前准确范围、Parquet 压缩率、日期数、单窗口行数/字节、连接数、读写速度与空间峰值。旧 Prod 23.55 GB 不能直接当作 Lake 空间预算。 |
| 复权历史更新 | 以实际股票×窗口 unit 计算：第 i 个 unit 预期 H_i 行，按暂定页大小 p=10,000，首次分页请求合计 `Q=sum(floor(H_i/p)+1)`；如发生可重试错误，最多 3Q 次额外尝试，实际可更少。受影响 D 个日期的文件每层至多合并发布一次。 | 变化股票数、每个窗口行数、源请求量、业务 staging 大小、整日旧文件读取量及最终候选空间。没有变化股票时历史 Q=0；划分更多窗口可能增加空尾页或首请求次数。 |
| 恢复和最终验收 | 续跑校验已完成文件与 checkpoint，最终检查所有本次发布文件、分区范围及来源对账。 | 指纹/业务比较、读回、最终聚合审计开销，以及中断后不重复下载和重算的证据。 |

历史导出不用每个日期分别新建数据库连接作为未经测量的默认方案，也不能为了减少连接改成无上限全历史事务。先按索引和样本确定有界窗口与连接复用方式，完成后及时结束只读事务。

### 10.2 开发前必须明确的资源约束与性能测量

后续 LLD 先按已有证据和明确标注的分页假设写清本步范围与开销；对应开发或正式执行前按该步骤要求补齐必要的有界核验。至少记录对象、日期、页数、预计请求数、SQL/连接数、单页/窗口行和字节限制、耗时、DuckDB 内存/线程、spill、staging 空间、文件读取/合并/提升次数、取消响应、续跑和最终验收开销。下载器既定 2 GiB 初始值不要求重新测量选值；业务侧候选写入和文件合并仍须有界。

下载器当前默认连接/读取/请求时间为 5/30/45 秒，同页最多 4 次尝试、默认 1/2/4 秒退避，HTTP 响应上限 64 MiB，并受单 unit 解析/排序工作空间限制；具体边界见组件文档。组件没有频率配置，业务调度负责总频率，不另建额度管理或整个任务的请求数/时长硬截断。记录请求规模和耗时用于性能评估与排障，不把旧 transport 的其他数值带入本数据集，也不据既有样本承诺吞吐。

物理内存、单页字节或磁盘承载不足、执行超出已批准的数据读写范围时，停止领取新单元并保留已完成结果，输出剩余范围和原因；不得丢股票、减少字段、缩短历史或推进完成状态来规避问题。不把请求总数或整个任务耗时作为下载组件的人为截断条件。需要扩大范围时先更新本方案及对应 LLD，再申请执行。

sensor 不遍历全 Lake、不读取无界事件历史；批量检查须一次读取明确文件集合，避免包一层 Python 循环仍逐分区扫描。超过 100 个历史分区或 `分区数×blocking checks数>1000` 时，按性能治理规范做批量聚合与分层验证，不逐分区全深扫。

## 12. Checks、真实验收与人的排障

### 12.1 数据验收

| 检查 | 主要内容 |
| --- | --- |
| schema | 261 个显式业务字段、类型、日期格式和可空数值；Prod 辅助列不进入源投影。本地辅助列按本地存储定义另行检查，不混入接口契约。 |
| 主键及日期 | 主键非空、唯一、日期在执行范围并与分区一致；不把休市空结果当作成功交易日数据。 |
| 行数与拒绝 | 下载 unit 的源行数、归一化和 staging 保存行数对账；最终文件按 B−K+U 的合并关系核对，不能与部分股票的源行数直接相比；任何拒绝都有原因和小样本。 |
| bootstrap | 与批准来源范围逐窗口/日期汇总对账，并记录缺日与覆盖限制；不能仅凭估计总行数验收。 |
| Raw→Silver | 日期转换以外业务字段及主键一致，不暗中过滤当前非上市股票。 |
| 复权更新 | 变化集合和起止范围完整、所有应更新文件读回、未变化股票保持相同；“无变化”也能证明已检查。 |
| 发布/恢复 | 文件指纹、批次、checkpoint 和最新物理结果一致；旧事件不能证明新文件仍有效。 |

计算、合并和恢复正确性主要由独立金样本及离线有界验证证明；日常生产 checks 做轻量合同与覆盖检查，不重复拉全源或重算全历史。readiness 与正式 checks 使用相同的纯判断和聚合语义，避免两套口径。

Raw/Silver 分区 checks 必须显式使用与资产相同的 `partitions_def`；隔离 instance 中核对实际产生的 check event 分区，不能只看函数返回成功。开始实现后按代码约束运行必要单元、契约、隔离集成及最小真实验收；本轮没有运行数据管道测试，也不声称接入已通过。

### 12.2 测试重点

本数据集实施时，至少覆盖：源超时、取消及业务进程退出后的续跑；尾页/恰好满页/完整unit交付，业务调度与源限频错误归属；业务重复键处理；缺列、错类型、错日期和合法 NULL/负指标；分步退出及续跑；目标冲突；发布后状态写失败；历史只更新指定股票、跨年范围、没有变化、新上市与旧股票缺前因子；股票集合相同但值变化、同样行数但主键不同；正常复权变化不会被错误拦截。

夹具来自已核对的源字段、Prod schema 和有界真实样本。预期结果用独立可人工核算样本，不能用被测函数生成 expected。真实接入验收须分别记录源返回、归一化、拒绝、目标行数，mock 通过不能代替真实边界。

组件既有隔离测试按其原验收记录保留，不在本数据集重新立项开发六种模式。新增回归重点是：源数据集名可登记/查找；独立 version 与内容变化仍影响比较及 unit 身份；同名重复登记仍拒绝；完整 261 字段及所用两种模式；固定 HTTP 登记及有界真实边界；假定分页的正常与失败终点。名称变更时同步全部受影响夹具和测试，不靠保留旧名别名通过。

存储边界还须证明：相同完整契约可由不同业务调用方选择本工程允许的正式目标和写入方式，无需改变下载配置；下载器不触碰正式数据库或文件。分别覆盖unit内部部分页成功但unit失败、完整unit已交付但业务未提交、全部下载结束但发布失败、提交后状态写失败和接收不明；业务失败停止后续下载而不触发源重试，已提交数据保留。合法NULL与负指标必须有可写入正例，不能只测试错误被拒绝。

历史流程新增接入回归还须覆盖：同一股票的多个窗口分次调用且范围不重不漏；同一任务重复 object_ranges 被拒绝；完整 unit 保存后可复用、只收到结果但未保存时重新下载；部分股票更新后的全市场行数按合并关系计算；日期 T 的基础数据和历史结果同键时没有重复行且只正式发布一次；最后一个下载进度 100% 但业务合并或发布失败时整批仍未完成。

### 12.3 可见信息和排障顺序

资产、check、job、sensor 均使用中文说明，讲明数据是什么、读取什么、何时可执行、会改哪些文件以及失败后如何处理。metadata 先展示 `summary`、`next_action`、结果、输入和过滤范围、诊断位置，再展示机器字段。

长任务展示阶段、当前日期/股票窗口、已完成/总量、页数、来源/目标行数、耗时和最后更新时间；业务将标准页/重试/unit通知接到现有任务观测，并在退出或异常后报告最终结果；下载器没有固定间隔心跳，不能承诺阻塞网络调用期间持续发回调。进度随已完成工作推进，不能伪造完成量，ETA 无依据时明确暂无法估算。

多个下载任务组成一个历史批次时，组件 total_units 和百分比只覆盖各自会话，不会自动累计成整批进度。业务依据已确定的股票×窗口范围及实际完成事实汇总批次状态，并分别展示下载、业务保存、合并和发布阶段；某个会话 100% 不能显示成整批完成。

| 运营看到的问题 | 首先查看及下一动作 |
| --- | --- |
| 未启动 | 查看交易日、源发布及 T/P 因子 readiness 的具体缺项，不手动反复触发。 |
| 源请求失败 | 查看 API、日期/股票、页号、重试次数、超时或配额原因，修复后续跑未完成单元。 |
| 行数/字段不一致 | 查看源/归一化/候选计数、原因和样本，不能跳过校验强行发布。 |
| 历史更新未完成 | 查看完整批次范围、已完成文件及剩余范围，继续同批次或在输入变化后重新评审。 |
| 文件冲突 | 查看预期与实际目标指纹、已有任务/维护窗口，确认范围后再执行，不覆盖未知结果。 |
| 文件完成、状态不完整 | 先按 checkpoint 和物理读回核验，再处理状态；不因 UI 不绿重跑全历史。 |
