一 / 总体关系

1. 数据基座在量化平台中的位置

本方案中的数据来源范围以 DG 及其维护的正式数据资产为起点。研究数据基座负责把上游明确提出的数据需求，转换为有边界的读取、程序可消费的数据及相应证据。它不接管研究任务，也不取代 DG 的数据生产与维护。

当前调用方主要是管理员自己控制的研究程序和智能体。首版不以公开数据分发、多租户或商业计费为建设目标。

参与方完整职责与数据基座的边界
DG 与数据生产侧采集、标准化、正式派生计算、生产检查、发布、修复与更新。决定正式数据事实及其生产合同；基座按获准范围只读消费，不通过查询请求触发补采、修复或 materialize。
研究数据基座目录与合同、受控读取、交付、质量覆盖报告、来源证据及访问运行治理。执行明确数据要求，不决定研究对象、策略、样本选择或研究有效性。
上游研究层定义研究问题、对象集合、评价区间、预热需求、特征、标签、样本规则、算法和评价方法。解释数据对研究是否足够、是否排除样本、是否继续运行；不得让基座隐式作出这些决定。
模型与研究程序模型组织研究、编写代码并审阅结果；程序消费数据明细、计算、验证和输出证据。模型主要读取说明、摘要和证据；大规模明细由程序消费。数据基座不承接任意研究代码的执行。

边界示例：上游要求 A、B、C 三只股票某日的行情。基座按请求读取，说明 B 缺少记录以及能确认的停牌事实，不静默剔除 B。是否排除 B、调整窗口或终止研究，由上游决定。

证券身份、上市退市、停复牌和板块成分是可供读取的数据事实。它们能支持上游定义研究对象，但“某天应该研究哪些股票”不是基座的职责。

2. 八项能力与五大方向的关系

八项能力是需求与验收清单，五大方向是设计职责分组。两者不是替代关系：能力编号保持固定，用于逐项追踪；方向将联系紧密的能力组织起来，形成内聚的输入、输出、执行规则与演进边界。五个方向并不预先等于五个服务、五个包或五张表。

能力应提供的内容主归属方向跨方向职责切分
C01 数据目录与合同身份、来源、字段、类型、单位、主键、频度和使用限制。D01 数据目录与合同管理D02 按合同读取；其他方向引用同一合同身份，不再各自定义字段含义。
C02 证券身份与基础事实代码、历史代码映射、上市退市、停复牌及成分等来源事实。D01 管理含义，D02 提供读取事实仍由正式上游资产维护；D03 只有取得对应事实后，才能给出有依据的缺失原因。研究对象选择属于上游。
C03 时间与版本信息来源实际具备的业务时间、发布时间、采集时间、修订信息及能力限制。D01 管理语义，D04 记录实际使用D02 执行明确的时间/版本读取要求。历史版本的生产与保留归数据生产和存储侧，不能悄悄转入查询基座。
C04 受控查询与数据关联按明确对象、字段、时间、过滤、排序及受支持关联条件读取。D02 数据读取与交付D01 提供可执行合同，D05 在执行前和执行中约束访问与成本。
C05 数据质量与覆盖报告实际覆盖、缺失、重复、NULL、合同检查及已确认原因。D03 质量与覆盖核验报告依据来自实际读取或适用的生产证据；不决定这些数据对某项研究是否足够。
C06 面向程序的数据交付稳定结构、排序、分页或批次读取、完整性与结束语义。D02 数据读取与交付与 C04 一起设计完整读取过程；临时文件、持久化或跨进程续读须另有明确合同与授权。
C07 读取追溯与输入证据请求与实际范围、来源、合同版本、时间、数量、可取得的输入身份与指纹。D04 来源与读取追溯关联 D02 实际执行和 D03 实际报告。指纹用于识别变化，不等于能恢复原版本。
C08 访问与资源治理权限、来源边界、并发、扫描量、内存、超时、取消、错误和运行观测。D05 访问与运行治理贯穿其他方向；管理读取执行，不决定研究方法或结论。

为什么这样归并

C04 与 C06 属于同一个读取过程。请求、读取计划、排序、批次、部分结果、取消和完成条件必须共同设计，否则容易出现“查询已成功，但交付是否完整没人负责”的空隙。

C02 与 C03 同时包含事实和元数据。事实的含义归合同管理，内容由读取能力交付，本次实际采用的时间/版本归追溯；不因此新建股票池选择器或研究时间策略。

C05 与 C07 分开。前者回答“检查了什么、数据实际怎样”，后者回答“这次实际用了什么、各项结果怎样对应”。一次失败读取也需要追溯记录，但不能把未完成的质量检查记成通过。

C08 是贯穿约束。权限与预算先于数据访问，运行限制和取消持续生效，资源释放与结果终态在结束时对齐；它不是链路末尾才执行的一步。

3. 横向职责与纵向完整链路

横向要求每个方向有一份完整设计；纵向要求这些设计能够共同完成一次读取。时间分期只限制当期支持范围，不能把异常、证据或边界留到后期再想。

明确请求上游指定数据、对象、时间、字段与规则。
→
D01 合同解析确认身份、字段含义与支持范围。
→
D02 读取计划确定来源、投影、过滤、关联和交付方式。
→
D02 + D03有界读取、适用核验和批次交付。
→
明确结束完整/部分/失败结果与证据相互对应。
D05 贯穿：权限检查 → 成本与资源准入 → 运行限制、取消与进度 → 资源释放。
D04 贯穿：关联请求与合同 → 实际来源与读取范围 → 批次、检查与最终证据。

质量检查可能发生在读取前、读取中或读取后。不能宣称所有检查都能在明细交付前完成。若采用流式交付，应在合同中定义：批次是否已完成所需检查、哪些检查尚未结束、最终失败时此前批次如何标识。上游不能把“收到一些数据”理解为“完整输入已通过全部检查”。

共同交付的四类内容

内容意义
数据合同说明读取的是什么、含义与限制是什么。
读取计划说明明确需求将怎样落到实际来源、读取范围和交付边界；计划本身不自动触发执行。
数据与交付结果说明实际返回了哪些字段、哪些范围、多少批次以及是否完整结束。
覆盖报告与读取证据说明检查的实际范围、已确认问题、未检查内容及本次输入来源。

上述内容是概念合同，不是已批准的 DTO、数据库表或独立状态机。具体字段、存储、生命周期与跨进程行为在 LLD 中确定。

二 / 五大方向 · D01

数据目录与合同管理

完整目标：上游和读取执行方能够依据同一份合同，识别数据、解释字段并确定可支持的读取要求。

职责与能力范围

  1. 组织发现入口。按数据主题、研究对象、来源、频度和数据性质查找候选数据；返回说明与匹配依据，不替上游选择研究数据。
  2. 建立稳定身份。区分逻辑数据集、Raw/Silver/Gold 表达、频度、来源与 serving 访问载体。相似名称不代表含义相同，查询副本不重复计为研究主题。
  3. 表达字段合同。覆盖字段名、类型、单位、精度或编码、NULL 含义、主键、时间语义、排序及支持的读取条件。缺失的定义需核实，不能从字段名猜测。
  4. 描述基础事实。说明证券身份、历史代码、上市退市、停复牌、成分等数据的含义与有效范围，使上游能够明确请求这些事实。
  5. 描述时间和版本能力。区分业务发生/所属时间、源端发布、平台采集及修订版本。只有来源实际支持的字段与历史读取能力，才能对外声明。
  6. 管理合同变化。明确合同身份与版本，区分字段新增、类型/单位/主键等含义变化，标识受影响的读取与消费者，避免静默改变解释。

输入：当前正式资产 registry、字段 schema、路径/分区合同、来源资料和经核验的消费者语义。

输出：可发现的数据说明、机器可读合同、来源与表达映射、支持/不支持/未知的能力说明及合同变化记录。

内部一致性与协作

DG 资产事实继续以现有 registry 及其引用合同为准。对上目录应通过经过审计的适配或发布方式引用这些事实，只补充缺失的发布语义；不手抄另一份字段清单成为竞争事实源。现行 catalog 是只读 registry，不因本方案自动变成 asset 生成器或运行时 planner。

D02 负责按合同执行读取；D03 解释检查范围和要求；D04 记录实际采用的合同版本；D05 据其声明能力执行访问和成本约束。

边界与异常

不决定股票池、研究对象或策略；不根据“更高层级”自动替换数据表达；不把 source 的可选参数直接变成研究输入；不从采集时间推测公开时间。

身份或表达存在歧义、字段含义冲突、所需版本不可提供时，明确报告冲突或不支持，不能静默使用另一个来源。登记合同存在不代表实现已注册、文件存在或覆盖已经核验。

方向的完整验收标准

  • 同一身份在不同入口中含义一致，支持范围可程序化判断。
  • 字段、类型、单位、时间和来源能追到独立依据；未知项明确可见。
  • 合同变化能定位受影响消费者，旧请求不会悄悄解释为新含义。
  • 事实源变化可复核，对上目录没有形成另一套手工资产事实表。
二 / 五大方向 · D02

数据读取与交付

完整目标：把上游明确的数据要求转换为受控、可核验、可完整消费的读取过程。

职责与能力范围

  1. 接收明确需求。数据集及表达、对象标识、时间范围、字段、过滤、排序和交付要求由上游指定。缺少条件时按合同判断是否允许，不能默认扩大为无界全量。
  2. 形成读取计划。解析实际来源、列投影、文件/分区或表过滤、排序、批次边界、预计成本与来源身份要求；将歧义和不支持项在执行前说明。
  3. 执行受控读取。依据实际物理布局裁剪，优先向量化、集合查询和批次消费，避免全量明细长期驻留内存以及重复扫描同一来源。
  4. 支持显式关联。只执行合同支持且上游明确指定的关联键、关联方式、时间条件及身份映射规则；关联前后数量和未匹配情况可见。
  5. 交付稳定数据。统一字段结构、类型、排序、分页或批次边界；定义最后一批、完整结束、部分结果、重复领取和消费中断的语义。
  6. 管理一次读取的生命周期。执行中响应取消、超时和来源变化；结束时关闭连接、释放句柄，并使交付结果与实际执行相符。

输入：明确的数据请求、D01 合同、D05 准入条件，以及上游显式选择的缺失处理和关联要求。

输出：读取计划、程序可消费的批次、实际交付摘要、明确的完成/部分/失败结果，并关联 D03、D04 的报告和证据。

整体过程

请求解析、计划、执行、交付和结束必须使用同一套身份、范围与错误规则。查询已返回记录，不等于调用方已经完整消费；此前返回过批次，也不等于后续异常可以被记为成功。

源读取一致性应逐类说明：数据库事务与多文件读取的保证可能不同。逐文件原子替换不能自动构成跨文件一致快照。要求无法满足时，不能用一个读取时间戳冒充一致性保证。

边界与异常

不计算研究特征、标签或策略；不自行扩展预热窗口、排除对象、改变复权基准、跨来源兜底、填值或删样本。上游需要额外窗口时必须显式请求。

数据交付不自动授权输入落盘、缓存或复制。现行 QTF 禁止持久化来源输入副本；若将来确需文件交付，须先明确保存方、路径、期限、权限及现行规则如何适用。不能先生成副本，再把它解释为“只是下载”。

中断后只允许在源身份与游标仍满足明确合同的情况下续读；否则返回不可续读或创建明确的新请求，不把两次变化后的输入拼成一份完整结果。

方向的完整验收标准

  • 实际来源、对象、时间和字段与请求/计划对齐；没有静默扩范围或改口径。
  • 分批读取可重建规定排序下的完整结果，重复、遗漏、截断和部分结果有明确表现。
  • 关联后的行数变化、未匹配及多对多扩张有说明，不能静默放大样本。
  • 超预算、取消、超时、来源变更和交付失败均有可核验结果，资源能够释放。
二 / 五大方向 · D03

质量与覆盖核验

完整目标：让上游知道所请求范围实际具备什么、检查了什么、缺了什么，以及哪些结论仍然未知。

职责与能力范围

  1. 明确检查依据。分别引用数据合同、请求范围、适用的生产检查和上游显式给出的核验要求。不能根据查询到什么，反推应该有什么。
  2. 报告结构与数值事实。schema、主键、重复、NULL 及来源合同已有的有效值要求，均需说明检查范围、结果与依据。
  3. 核对覆盖。按合同支持的对象、日期、频度、字段等维度核对请求与实际覆盖。只有取得预期集合的独立依据，才能声称缺失多少。
  4. 说明原因与不确定性。有明确事实时区分停牌、未上市、合法空日、尚未生产等原因；证据不足时保留未知，不能推测“无行情就是停牌”。
  5. 关联适用的生产检查。复用现有检查语义及结果时，确认其对应来源、分区、版本和有效范围。历史曾通过不等于当前输入已通过。
  6. 有界执行和解释。检查可以在读取前、中、后完成；列出已检查、失败、未检查与无法检查的部分，返回有界错误样本或可领取的明细。

输入：请求和实际读取范围、数据合同、适用的来源事实/检查证据，以及上游显式声明的预期集合或检查要求。

输出：覆盖与质量报告，包含检查依据、范围、时间、实际数量、缺失/异常和未知原因，并与具体读取绑定。

上游决策与数据合同校验的区别

基座可以拒绝非法请求、无法解释的结构冲突或不满足读取合同的数据。研究样本数量是否足够、是否排除停牌对象、是否调整区间，则由上游判断。对“缺失时拒绝交付”或“返回已有数据并附报告”等行为，应采用明确的已支持请求规则，不设置隐藏默认。

一次读取没有期望对象全集，就不能仅凭实际返回数量计算完整率。只有最大日期，也不能声称连续完整覆盖到该日。生产事件、文件存在、文件检查和研究可用性是不同结论。

边界与异常

不修复源数据，不为了检查通过而补零、去重或删行，不替研究制定样本剔除规则。检查无法在预算内完成时报告未完成，或按显式规则阻断，不降低检查语义。

避免为每次读取重新执行全量检查。优先评估适用的有界证据、批量核验及读取中统计，但不得把粗筛冒充正式完整检查。

方向的完整验收标准

  • 预期范围有独立依据，报告能解释请求、实际数据与检查范围之间的关系。
  • 缺失、合法空、未知、未检查和检查失败能够区分。
  • 生产检查的适用性与输入身份对应，旧检查不会被错误复用。
  • 报告不改变原数据、不偷偷改变研究对象，核验成本有边界。
二 / 五大方向 · D04

来源与读取追溯

完整目标：能说明一次读取实际使用了什么，并定位请求、来源、交付、检查和后续输入变化之间的关系。

职责与能力范围

  1. 建立关联身份。将一次请求、采用的合同、读取计划、实际来源、批次、质量报告和结束结果对应起来。引用身份不等于必须新增数据库实体。
  2. 记录实际输入。包括实际对象/时间/字段范围、来源与表达、合同版本、读取时间、实际数量及来源能够提供的版本身份。
  3. 获取必要指纹。依据读取方式选择内容、文件或发布身份等证据；区分来源声明的版本和本次实际内容指纹，说明覆盖范围与成本。
  4. 记录异常与证据缺口。部分交付、取消、检查未完成、追溯降级都应可见，不能把没有证据的环节记成已核验。
  5. 支持读取之间的比较。区分请求变化、合同变化、来源版本变化、内容变化和覆盖变化；不替研究判断结果变化是否有经济意义。
  6. 管理证据生命周期。证据的保存位置、期限、权限、敏感字段、失败策略和清理方式在 LLD 中明确，不默认建立另一套运行账本。

输入：D01 合同身份、D02 实际执行和交付事实、D03 实际检查报告，以及来源能够提供的身份信息。

输出：可关联、可比较的读取证据与差异说明；明确哪些部分只能检测变化，哪些来源确实支持原版本读取。

可追溯不等于可重放

保存内容指纹可以证明两次输入不同，不能恢复被覆盖的旧文件或旧表记录。即使合同版本相同，数据内容也可能变化；即使有读取时间，也不代表源端保留了那个时刻的历史版本。

历史版本的保留、修订发布与保留成本归数据生产/存储侧专项设计。基座只在来源真实支持的前提下执行指定版本读取，并记录实际采用的身份；不能在 QTF 中用复制输入绕过现行边界。

边界与异常

不承接研究结论管理、策略版本或实验结果评价；这些属于上游实验与研究层。证据状态也不替代 DG 的运行事实。

必须追溯的读取应在准入时明确要求。运行中证据写入失败的处置需有可见规则，不能伪造证据或回滚上游正式业务数据。审计存储不得未经设计就成为所有业务查询的隐式故障依赖。

计算指纹也要预算，优先评估在实际读取中增量计算或复用适用来源身份，避免为追溯无界重扫。

方向的完整验收标准

  • 能从读取结果追到实际来源、合同、范围和适用检查。
  • 能够识别输入变化，并清楚标识无法验证、无法原版本重读的情况。
  • 证据对应实际执行，取消、部分结果和追溯失败不被写成完整成功。
  • 证据不夹带凭证或无界明细，不产生来源数据持久化副本。
二 / 五大方向 · D05

访问与运行治理

完整目标：使数据访问在权限和成本边界内开始、持续执行并明确结束，能够观察、停止和解释。

职责与能力范围

  1. 访问准入。确认调用方、允许的数据来源、数据集、表达和字段范围。当前自有智能体场景采用最小必要能力，不默认引入新角色、多租户或公开访问体系。
  2. 成本准入。评估对象数、日期跨度、字段、扫描文件/分区、预计记录、返回体积与关联放大等因素；返回行数上限不能代替扫描成本上限。
  3. 资源控制。约束并发、内存、线程、临时空间和连接占用。研究读取与 DG 数据生产的资源关系需明确，不能直接套用生产计算的默认配置。
  4. 运行控制。执行前与批次边界响应取消，说明不可分步骤的最长占用和安全退出方式。交付过程考虑消费者读取慢或中断，避免无界缓冲。
  5. 可观测与错误反馈。区分已扫描、已读取、已返回、已检查和已消费的含义；总量未知时明确未知，不伪造进度或 ETA。
  6. 安全结束与演进。释放资源，处理超时、连接失败和源不可用；合同或配置变化需完成消费者、默认值、来源、生效方式及运维可见性审计。

输入：调用方与授权上下文、D01 支持范围、D02 读取成本和执行事实，以及已经批准的资源与失败策略。

输出：准入结果、明确限制、可见运行状态和错误、取消结果及资源占用证据。

治理贯穿整条链路

校验权限之后才能读取数据；根据读取计划判断预算之后才能执行重查询；读取中持续检查预算和取消；无论正常、失败还是取消都应释放资源。需要新增后台长任务时，必须先审计现有运行承载能力，不能由本方案直接另建状态机。

边界与异常

不以治理之名改变研究对象和策略，不自动调度 DG 修复、不擅自增加生产数据库来源、不把只读授权扩展为物化或写入权限。

只读需要在实际连接、路径和执行权限上落实。DuckDB 连接存在临时目录、spill 或显式文件写入能力，不能只凭“连接到内存库”或 helper 名称宣称无副作用。

本方案不新增具体配置项或默认阈值。每期 LLD 必须依据规模样本给出数值、来源和超限行为，完成配置审计后才能实施。

方向的完整验收标准

  • 越权和超预算请求在对应边界被拒绝，不以隐藏截断或换来源继续。
  • 并发、内存、连接与临时空间均有可测边界，读取不会无约束抢占 DG 生产资源。
  • 取消、超时和消费者中断能安全结束，已交付与未完成部分可区分。
  • 进度和错误表达实际工作，凭证及内部敏感内容不会泄露。

5. 用一条场景检验能力是否贯通

以下为需求示例，不选择具体首期数据集，也不表示当前已实现这些通用能力。

  1. 发现与理解：上游找到行情和停复牌数据，核对来源、字段、时间及价格口径，明确选择具体表达。
  2. 定义请求：上游给出 A、B、C 的明确代码、日期、字段、排序，以及缺失时返回已有数据并附报告的已支持规则；需要预热时明确给出额外读取区间。
  3. 计划与准入：平台说明实际来源和范围，评估读取成本，检查权限与预算；不支持的条件在执行前说明。
  4. 读取与核验：程序分批消费；平台报告实际覆盖。只有获得对应停牌事实时才把某项缺失解释为停牌，否则保留未知。
  5. 明确结束：程序得到完整或部分交付结果、检查报告与输入证据。上游自行决定是否排除 B、继续计算或修改研究要求。
  6. 结果解释：研究程序输出结果、样本情况和验证证据，模型据此分析。重读后内容不同，可先用读取证据定位输入差异。

这条链路同时经过五个方向。任一环节的责任缺失，都可能让上游错误理解输入：例如批次未结束却当作全量、检查未执行却当作通过，或最新数据被误当作历史时点版本。

6. MCP 与程序调用的位置

MCP、Python 程序入口和未来研究工作台是访问适配方式。它们不各自建立读取规则，也不代替五大方向的设计。研究程序应能直接调用统一的数据合同，不必经过模型才能读取明细。

describe_dataset取得编程所需含义、范围和限制。C01、C02、C03 / D01
get_data_availability了解指定范围的覆盖及证据。C05、C07、C08 / D03、D04、D05，并通过 D02 有界读取

四 / 三期开发节奏

7. 按完整使用场景分期

三个周期的交付对象是三种逐步扩展的完整使用场景。各方向先有贯穿全程的职责和设计，再按本期支持范围实施，不以“后期再补”为由推迟正确性、证据和失败语义。

这里给出相对节奏，不承诺周数或工时。开发前仍需完成本期方案、LLD、代码与消费者审计，给出实际预算、测试和验收条件，并取得相应确认。某一期通过不自动授权下一期。

第一期：完整的单数据集读取闭环

上游成果：能够找到并理解一份已发布合同的数据，提出精确请求，由程序有界消费，并取得实际覆盖和读取证据。

当期交付完整范围
目录与合同在明确发布范围内，身份、表达、字段、单位、时间、来源及限制齐备；身份和时间事实通过普通数据合同提供。
读取与交付单数据集字段投影、显式过滤、排序和批次读取；定义空结果、拒绝、完整/部分交付、取消和结束。
质量与追溯检查和报告范围明确；能报告实际数量与可核验覆盖，预期集合缺失时不伪造完整率；记录请求、实际来源、合同、范围和结束结果。
运行与入口落实只读、来源准入、扫描/返回/内存预算和超时；形成程序调用方式及薄 MCP 适配，二者数据语义一致。

明确不支持：任意跨数据集关联、任意 SQL、无界扫描、默认输入持久化，以及来源不具备的历史版本读取。

验收场景：同一明确请求在程序和 MCP 入口具有一致含义；正常、空结果、缺失、字段错误、超限、取消和来源不可用均能得到清楚结果；所有已交付范围都有相应证据。

需求覆盖：U01—U05、U07、U10—U12 的单数据集范围；U08 支持本次读取追溯，U09 必须明确声明实际支持或不支持。选用哪些数据集另行评审，不由本方案指定。

第二期：显式多数据协作与输入核验

上游成果：能够按明确身份、关联和时间规则组合多份数据，并解释组合后的覆盖、行数变化及不同读取之间的差异。

当期交付完整范围
多合同协作明确可关联数据、主外键或身份映射、时间条件、各来源表达和实际版本能力；不设置研究股票池或时间策略。
显式关联支持经过评审的关联方式，核对关联基数、未匹配及行数变化；字段来源和执行顺序可以解释。
覆盖与输入比较按明确预期集合和多个来源的事实诊断缺失；将各输入、关联过程和结果证据串联；比较两次请求、合同、覆盖和内容变化。
整体成本与错误评估组合读取总成本和关联放大；任一来源失败、检查未完成或版本不满足时，结果有明确语义。

明确不支持：自动决定研究对象、自动补值/扩窗口/换源、任意表达式关联，以及靠复制输入补出来源不支持的历史版本。

验收场景：上游指定多个数据和关联规则后，能核对关联前后数量、未匹配及时间要求；错误映射、重复键、多对多放大、混合版本和部分来源失败不会被静默掩盖；重读变化有相应证据。

需求重心：完整交付 U06，并扩展 U04、U05、U08、U09、U12；一期读取、交付和治理合同继续适用。

第三期：受控的大规模与并发数据服务

上游成果：在更大对象/日期范围和多个自有任务并发时，仍能预判成本、有界消费、观察进度、停止读取，并准确理解中断后的结果。

当期交付完整范围
可测成本与读取优化用代表性实际规模核验裁剪、集合读取、批次和关联规划，记录扫描文件/记录、耗时、内存与临时空间，拒绝不可接受量级。
并发与交付控制限制研究任务间和对 DG 生产的资源竞争；消费者变慢或中断时不无界缓冲；取消和异常能够释放资源。
一致性与续读边界校验来源在读取中的身份变化；跨进程续读仅在来源身份、读取顺序和游标合同可验证时实现，不满足则明确拒绝续读。
长期服务维护持续观测成本与失败，验证证据存储的规模边界；在合同变化时定位消费者并按迁移规则处理。

明确不支持：无限并发或读取量、自动新增缓存/快照/查询副本、无条件跨版本续读，以及未经批准的公开多租户服务。

验收场景：在获批容量样本和并发场景下，资源有可验证上限；超时、取消、消费者中断、源文件替换和合同升级都有清楚结果；不能把低效测量脚本造成的成本误判为必须新增状态系统。

需求重心：扩大 U03、U06、U07、U10、U11 的规模范围，强化 U08、U09、U12 的服务稳定性。历史版本保留仍须单独评审，不自动计入三期。

8. 五大方向 × 三期交付对照

按行可以看到一个方向贯穿三期的整体思路，按列可以检查一期能否完成上游使用场景。每一格表达当期可验收的支持范围，不是另建一套模块或合同。

方向与能力第一期：单数据集闭环第二期：多数据协作第三期：规模与持续运行
D01 目录与合同
C01、C02、C03		发布范围内身份、字段、时间和版本限制完整；可程序化发现与解释。声明显式关联键、身份映射和多来源时间/版本支持；合同变化可定位。检查更大消费范围的合同影响与迁移一致性；不改变合同管理的职责。
D02 读取与交付
C02、C04、C06		单来源精确读取、稳定批次与完整结束；明确取消、部分和失败。按明确规则关联多个输入，解释来源与行数变化，整体交付。规模化裁剪和批次、并发交付与来源变化控制；仅支持可验证的续读。
D03 质量与覆盖
C05		结构与覆盖报告有依据；未检查、未知和异常分开，禁止静默修复。关联前后覆盖和基数核验，依据多个明确事实解释缺失。在获批容量下批量核验，保证报告完整性与计算成本，不降低检查含义。
D04 来源与追溯
C03、C07		串联请求、实际输入、交付与检查；证据缺失和降级可见。串联多个来源和关联过程，比较请求、合同、覆盖及内容变化。核验长读取/并发下证据一致性、规模与保留边界，解释来源变化和不可重放。
D05 访问与治理
C08		权限、只读、来源与成本准入、超时、取消、资源释放均有规则。覆盖组合读取的权限、总成本、关联放大和整体失败。核验并发、资源隔离、背压、恢复条件和长期运行观测。

每个方向保持一份完整设计

方向的目标、输入输出、内部协作、异常、运行边界、演进和最终验收标准应在开发前整体说明。每期 LLD 引用并细化本方向设计，列清当期支持与不支持范围；不得为了阶段名称新建重复合同、第二套读取逻辑或兼容轨道。

9. 开工门禁与待确认事项

本文完成的是能力规划。进入任一期编码或正式执行前，应在本总体方案和对应 LLD 中完成以下内容，不能仅凭本页的节奏表开工。

  • 目标与范围：当期数据形态、调用方、受支持操作、禁止项和可独立使用的交付链路。
  • 代码与影响：实际实现位置、CodeGraph 调用/消费者分析、现有合同和测试依据、与当前代码的差异。
  • 合同与状态：精确请求、输出、错误、部分结果、取消、结束与必要续读规则；证据与源身份的关联方式。
  • 配置与读写：每项配置的名字、默认值、来源、消费者、生效与运维方式；明确数据库/Lake/临时目录/证据的访问及写入范围。
  • 成本与性能：对象、日期、分区、字段、文件、SQL/源请求、扫描/返回量、内存、并发、临时空间、耗时和超限策略；先有界样本再扩大。
  • 失败与恢复：取消检查点、源变化、进程退出、已返回数据、证据写失败及恢复条件；未支持的恢复明确拒绝。
  • 验收：独立依据的正反样本、静态门禁、有界真实只读核验、性能与取消验证；不得只用 mock 声称真实集成通过。
  • 确认与授权：按现行规则完成设计确认、契约批准和执行授权。只读审计、代码修改、正式运行和写入边界分别处理。

服务/模块归属、端口与装配方式DG 独立于生产 Web/Ops，QTF 只允许依赖自身与 Foundation；需要先审计依赖与消费者，不能把图中的方向直接变成跨包 import。

10. 当前实现起点与缺口

以下仅记录 2026-10-17 对当前工作区的静态核对结果，不代表正式环境、物理数据或运行状态已经重新验收，也不是对全仓通用能力的完整审计。

当前依据可复用的起点仍需设计或审计
LAKE_ASSET_CATALOG 与 LakeAssetCatalogEntry已有资产身份、数据集、层级、来源、schema、路径、分区、检查和策略登记。研究侧发布合同、语义缺口、适配与演进；不能直接把只读 registry 改成通用执行器。
ColumnContract 与各资产 schema字段名称、类型与说明有集中依据。单位、NULL、时间和版本等信息需逐项核实；文档中存在说明不代表全部字段已有结构化合同。
SectorInputSource / SectorInputRequest已有行业研究输入端口，以及明确时间范围、前后交易日数和源超时。它是特定行业场景的输入，不是全数据平台通用接口；不能直接推广其默认值和对象语义。
ProdSectorInputSource已有受限定合同的只读源读取与输入证据构造。当前有整段读取并组装内存对象的方式，不能据此认定已经支持通用大表流式交付；源权限也不能扩展为所有查询均可读 Prod。
DatasetEvidence 与输入预检已有字段、范围、数量、主键状态、缺失/重复和内容指纹等证据。通用查询证据、批次关联、关联结果覆盖及不同来源的适用性需设计，不能直接复用未经核实的业务预检规则。
QTF 执行器、App 接线与现有测试可以追到输入预检与运行读取的消费者；外部 IO 经端口注入，运行输入会重新核对合同。本规划不恢复旧 QTF M4 方向，不绕过现行里程碑；新数据基座和 QTF 的接入需另行全消费者审计。
统一 DuckDB 连接与性能规范已有资源参数和受限策略，可作为读取成本与副作用审计入口。managed 会创建临时目录，受限策略也不阻止显式 SQL 写文件；不直接照搬参数或声称天然只读。

本方案不修改依赖矩阵。DG、Foundation、QTF 和 App 的既有职责仍适用；没有将 DG 直接装入生产 Web，也没有允许 QTF 导入 orchestrator 内部实现。
