6. Raw Asset LLD

Asset raw_tushare_index_daily_by_code
Partitions cn_a_index_ts_codes
Resources lake_root、duckdb、tushare
Config IndexDailyRawByCodeConfig(trade_date, write_mode)
Output 一个 ts_code 对应一个 raw parquet 文件。

6.1 Config 类型

class IndexDailyRawByCodeConfig(dg.Config):
    trade_date: str
    write_mode: Literal["replace"]
  • trade_date 接受 YYYY-MM-DD，请求 Tushare 前转换为 YYYYMMDD。
  • asset 内部把 trade_date 映射为 start_date=end_date=trade_date。
  • 必须校验 trade_date >= 2000-01-01。
  • Sensor 日更默认传 write_mode="replace"。
  • 人工补数第一版也只允许 replace；merge 暂不实现。

6.2 Tushare 请求

api_name = "index_daily"
params = {
  "ts_code": context.partition_key,
  "start_date": "YYYYMMDD",  # derived from trade_date
  "end_date": "YYYYMMDD",    # derived from trade_date
  "limit": 8000,
  "offset": 0 / 8000 / ...
}
fields = INDEX_DAILY_RAW_COLUMNS

实现前必须按 AGENTS 门禁再次核验 docs/sources/tushare/** 与 tushareMcp 实测结果。 现有代码已使用 INDEX_DAILY_RAW_COLUMNS 常量，重构应复用字段常量，不重新发明字段契约。

6.3 写入算法

1. lake_root.ensure_available_for_run()
2. ts_code = context.partition_key
3. validate trade_date/write_mode and derive source start_date=end_date
4. fetch Tushare pages into staging parquet
5. read existing target parquet if exists
6. if write_mode == "replace":
     delete existing rows where trade_date in requested window
     append fetched rows
7. validate output has only raw contract columns
8. COPY rebuilt query TO target.tmp
9. os.replace(target.tmp, target)
10. return MaterializeResult metadata

replace 的替换范围是本次请求时间窗口，不是无条件删除整份 ts_code 文件。 这点要写进 asset description 和用户操作文档。

7. Silver Asset LLD

Asset silver_index_daily
Partitions cn_a_index_trade_days
Resources lake_root、duckdb
Input raw/tushare/index_daily_by_code/ts_code=*/part-000.parquet
Output silver/index_daily/trade_date=YYYY-MM-DD/part-000.parquet

7.1 读取代码集合

Silver 不能再读取 旧指数 active pool asset。 它应从正式 Dagster instance 中读取 cn_a_index_ts_codes，作为当前指数代码集合。 display_name、list_date 这类元信息不放在 partition key 里，后续如果 check 需要，应读取 silver_index_basic。

7.2 SQL 口径

SELECT
  ts_code,
  CAST(strptime(trade_date, '%Y%m%d') AS DATE) AS trade_date,
  CAST(open AS DOUBLE) AS open,
  CAST(high AS DOUBLE) AS high,
  CAST(low AS DOUBLE) AS low,
  CAST(close AS DOUBLE) AS close,
  CAST(pre_close AS DOUBLE) AS pre_close,
  CAST(change AS DOUBLE) AS change_amount,
  CAST(pct_chg AS DOUBLE) AS pct_chg,
  CAST(vol AS DOUBLE) AS vol,
  CAST(amount AS DOUBLE) AS amount
FROM read_parquet(raw_by_code_glob, hive_partitioning=false)
WHERE trade_date = '<YYYYMMDD>'
  AND ts_code IN (<registered cn_a_index_ts_codes>)
  • Raw 读取必须使用 hive_partitioning=false，避免目录名 ts_code=... 被误当成 parquet 内部字段。
  • Silver trade_date 必须是 DATE。
  • change 在 silver 中继续标准化为 change_amount。
  • 完全重复行可以 distinct，但必须输出 duplicate_removed_count 和样本。
  • 同一 ts_code + trade_date 出现内容冲突必须失败。

8. Checks LLD

8.1 Raw checks

Check Blocking 职责
raw_index_daily_by_code_file_exists 是 校验 raw_index_daily_by_code_path 存在。
raw_index_daily_by_code_required_columns 是 字段集合必须等于 INDEX_DAILY_RAW_COLUMNS。
raw_index_daily_by_code_partition_matches 是 文件内所有 ts_code 必须等于当前 partition key。
raw_index_daily_by_code_unique_ts_code_trade_date 是 ts_code + trade_date 唯一。
raw_index_daily_by_code_date_range_observed 否 输出 min/max trade_date、row_count、missing gap 样本，作为观测信息。

8.2 Silver checks

Check Blocking 职责
silver_index_daily_file_exists 是 目标交易日 silver 文件存在。
silver_index_daily_partition_date_matches 是 文件内 trade_date 全部等于 partition key。
silver_index_daily_required_columns_and_types 是 字段和类型符合 silver 契约，尤其 trade_date 为 DATE。
silver_index_daily_unique_ts_code_trade_date 是 ts_code + trade_date 唯一。
silver_index_daily_price_sanity 是 价格字段非负，high >= low，且 open/close 位于 high/low 范围内。
silver_index_daily_registered_code_coverage 是 基于目标交易日 raw 中实际存在的注册指数代码校验 silver 覆盖率、输出漏转和 extra 样本；raw-present code 漏转或 silver 多出非 raw-present code 时阻断 silver_index_daily ready。

Coverage check 不能继续叫 active pool coverage，也不能依赖 旧指数 active pool asset。 新口径是“目标交易日 raw-present 注册代码集合”的覆盖观测；它不再用 silver_index_basic.list_date 推断源端历史起点。

10.2 index_daily_sensor

@dg.sensor(
    job=index_daily_update_job,
    default_status=dg.DefaultSensorStatus.STOPPED,
    minimum_interval_seconds=600,
    required_resource_keys={"lake_root", "duckdb", "tushare"},
)
def index_daily_sensor(context):
    # 1. 读取指数交易日
    # 2. 只处理待更新 trade_date
    # 3. 16:00 后探测 Tushare index_daily ready
    # 4. 读取 cn_a_index_ts_codes
    # 5. 扫描 raw-by-code 是否已有目标 trade_date
    # 6. 为缺失的 ts_code 发 RunRequest
项目 口径
run key index_daily:<trade_date>:<ts_code>
run config trade_date=<目标交易日>、write_mode=replace
单 tick 限流 固定为 500；不能无限提交全部 codes。首次启用前必须 preview。验证阶段曾临时限制为 1，并已完成一次真实 raw run 触发验收。
SkipReason 必须中文清晰，例如“今天不是指数交易日”“Tushare 指数日线尚未 ready”“没有注册指数代码分区”。
cursor 使用 v1 cursor 顶层记录 target_date、decision、selected_count、blocked_count 和样本；next_pending_offset 只保存在 details。正确性仍来自 raw-by-code 文件中是否已有目标 trade_date；cursor 只用于代码数量超过单 tick 上限时推进同一个 sensor 的批次，避免每次都卡在同一批缺口。

10.3 silver_index_daily_sensor（Slice G 已实现）

当前代码已实现 silver_index_daily_sensor。该 sensor 的目标是补齐 index_daily_sensor 只触发 raw 后，silver 需要自动按最早缺口推进的问题。 它只触发 silver_index_daily_update_job，不调用 Tushare，不写 raw。 

@dg.sensor(
    job_name="silver_index_daily_update_job",
    default_status=dg.DefaultSensorStatus.STOPPED,
    minimum_interval_seconds=600,
    required_resource_keys={"lake_root", "duckdb"},
)
def silver_index_daily_sensor(context):
    # 1. 读取 cn_a_index_trade_days 与 cn_a_index_ts_codes
    # 2. 用 DuckDB gap audit 确认最近 60 个可运行交易日内 raw-by-code 无有效空洞
    # 3. 如果 silver 已生成但 checks 未全绿，跳过并等待人工处理
    # 4. 选择最早未 ready 的 silver trade_date
    # 5. 触发 silver_index_daily_update_job[trade_date]
项目 口径
输入状态 cn_a_index_trade_days、cn_a_index_ts_codes、目标交易日的 raw-by-code parquet 文件事实。
候选日期 只选已经注册且不晚于当前自然日的最近 60 个指数交易日。日常自动化按该窗口内 raw 最早有效空洞、silver 最早未 ready 的顺序推进；更早历史缺口继续使用审计报告和 UI/backfill。
raw 文件事实门禁 DuckDB raw 文件事实门禁分两层：最新目标日门禁检查未退市注册指数是否已有目标 trade_date；最近 60 个可运行交易日 local continuity 门禁只检查每个 raw 文件从本地首个已有 trade_date 之后是否存在中间空洞。 silver_index_basic.list_date 不再作为历史 expected start。 该门禁不读取 Dagster run tags/config，不扫描 raw asset materialization 或 check history。 注意：该口径不审源端历史前缀完整性。
质量检查边界 sensor 只做文件存在和目标日期存在的进门门禁；真正的去重、字段类型、行数、价格 sanity、 registered code coverage 和 silver 输出质量仍在 silver_index_daily asset 与 silver checks 中完成。
silver 已失败行为 如果 silver_index_daily[trade_date] 已 materialized 但 blocking checks 未全绿， sensor 不自动重跑，返回中文跳过原因，避免每 10 分钟重复提交失败 run。
RunRequest job_name="silver_index_daily_update_job"，partition_key=trade_date，run_key="silver_index_daily:<trade_date>"。
tags 不写项目自定义 run tags；只保留 Dagster 分区语义、partition_key=trade_date 和稳定 run_key。
SkipReason 必须中文清晰，例如“指数日线 raw-by-code 文件仍有缺失代码，暂不生成 silver”。
cursor 使用 v1 cursor 顶层记录 target_date、decision、selected_count、blocked_count 和少量缺失代码样本；registered_code_count、raw_ready_code_count、missing_raw_file_count、missing_raw_trade_date_count、no_raw_history_count、selected_trade_date 放入 details。cursor 只用于观测，不作为 ready 判断依据。
边界 不补 raw，不重跑失败 raw，不触发 index_daily_update_job，不读取 run tags/config，不扫描 raw check history，不处理历史多日批量。

10.3.1 本地 raw 连续性 gap audit LLD（已实现）

该小节只定义 index_daily raw-by-code 的本地连续性审计： 不从 index_basic.list_date 开始 expected，不维护源端首个可得日事实， 只检查每个代码从本地 raw 首个已有交易日开始，后续交易日是否存在空洞。 该审计不调用 Tushare，也不在 Python 中逐代码逐交易日枚举缺口。 当前实现落在 audit_index_daily_raw_gaps，日常最新日 raw presence 单独由 check_index_daily_raw_files_for_trade_date 承担。

项目 落地口径
审计输入 registered_codes、目标交易日窗口、silver_index_basic.exp_date 退市边界、raw-by-code parquet 文件。raw parquet 读取必须列裁剪到 ts_code、trade_date。
raw bounds DuckDB 先从 raw-by-code 计算每个代码的 raw_start。 raw_start 是本地连续性审计的起点； list_date 不参与历史 expected start。
expected pairs 对有 raw_start 的代码，expected 起点为 greatest(window_start, raw_start)；expected 终点为目标窗口结束日， 并按 exp_date 做退市后排除：trade_date < exp_date。 对没有 raw 历史的代码，不从 list_date 生成 expected pairs。
无 raw 历史 缺 raw 文件或 raw 文件无日期的代码输出 no_raw_history / missing_raw_file 计数和样本。它不是 local continuity gap； 最新目标日是否需要补 raw，由日常目标日门禁处理。
性能要求 raw_bounds、expected pairs、observed pairs、missing pairs 全部通过 DuckDB 集合运算完成。禁止 Python 双重循环计算 code * trade_date 矩阵。 禁止 SELECT * 读取 raw parquet。
10.3.1.1 性能预算与上线门槛
场景 规模预算 耗时门槛 处理策略
日常 sensor raw 门禁 registered_code_count <= 1200， trade_date_count=60， expected_pair_count <= 72000。 只读 DuckDB benchmark 目标 <= 3s； 超过 5s 禁止接入 sensor。 只能保留最近 60 个可运行交易日窗口；若现算 raw_bounds 过慢，必须改成预聚合或分批方案。
250 日 raw gap audit registered_code_count <= 1200， trade_date_count=250， expected_pair_count <= 300000。 benchmark 目标 <= 10s； 超过 20s 或发生 DuckDB spill 时，禁止作为常规 blocking audit。 只能作为人工/低频维护审计或显式 dry-run；不得注册为 silver_index_daily blocking asset check，不得进入 silver_index_daily_update_job 的 checks selection。 必须输出缺口与 no_raw_history 样本。
全历史 raw gap audit registered_code_count <= 1200， trade_date_count <= 7000， expected_pair_count <= 8400000。 benchmark 目标 <= 120s；超过该阈值、expected pairs 超过 10000000、raw 文件数超过 1500 或发生不可接受 spill 时，必须重设方案。 只允许显式人工/低频维护入口；禁止放进 sensor tick、UI 默认加载或日常 blocking check。 不得影响 silver_index_daily_update_job 更新最新分区。
日常最新日 raw 门禁 目标日只检查该日 raw 是否存在，不做历史展开。 必须快于连续性审计；若目标日缺 raw，应触发 raw 更新或阻断 silver。 用于生产补数；不替代历史连续性审计。

WITH registered_codes AS (...),
target_dates AS (...),
index_basic AS (...),
observed_raw_all AS (
  SELECT
    CAST(ts_code AS VARCHAR) AS ts_code,
    CAST(trade_date AS VARCHAR) AS compact_trade_date,
    strptime(CAST(trade_date AS VARCHAR), '%Y%m%d')::DATE AS trade_date_value
  FROM read_parquet([...], hive_partitioning=false, union_by_name=true)
),
raw_bounds AS (
  SELECT
    ts_code,
    min(trade_date_value) AS raw_start,
    max(trade_date_value) AS raw_end
  FROM observed_raw_all
  GROUP BY ts_code
),
no_raw_history AS (
  SELECT registered_codes.ts_code
  FROM registered_codes
  LEFT JOIN raw_bounds USING (ts_code)
  WHERE raw_bounds.ts_code IS NULL
),
effective_code_windows AS (
  SELECT
    registered_codes.ts_code,
    greatest(
      (SELECT min(trade_date_value) FROM target_dates),
      raw_bounds.raw_start
    ) AS expected_start,
    CAST(index_basic.exp_date AS DATE) AS exp_date
  FROM registered_codes
  INNER JOIN raw_bounds USING (ts_code)
  LEFT JOIN index_basic USING (ts_code)
),
expected_pairs AS (
  SELECT
    target_dates.trade_date,
    target_dates.compact_trade_date,
    effective_code_windows.ts_code
  FROM target_dates
  INNER JOIN effective_code_windows
    ON target_dates.trade_date_value >= effective_code_windows.expected_start
   AND (
     effective_code_windows.exp_date IS NULL
     OR target_dates.trade_date_value < effective_code_windows.exp_date
   )
),
observed_raw_window AS (
  SELECT ts_code, compact_trade_date
  FROM observed_raw_all
  WHERE compact_trade_date IN (
    SELECT compact_trade_date FROM target_dates
  )
)
SELECT ... FROM expected_pairs
LEFT JOIN observed_raw_window USING (ts_code, compact_trade_date);

10.3.2 silver_index_daily readiness 批量查询修复方案（已实现）

背景：2026-06-02 发现 silver_index_daily_sensor 在最近 60 个可运行交易日都已经 materialized 且 blocking checks 全绿时，逐日调用 readiness 会重复扫描 Dagster check history， 可能超过 Dagster sensor evaluation 60 秒时限。该问题发生在 Dagster event log readiness 查询， 不是 raw parquet gap audit；DuckDB 继续只用于 raw-by-code 文件事实审计。

项目 正式口径
事实源 只读取 Dagster instance 中 silver_index_daily 的 materialization event 与 silver_index_daily blocking asset check event。不得读取业务 parquet 内容来替代 readiness，不得读取 raw run tags/config，也不得扫描 raw asset check history。
窗口 输入仍是已经注册、不晚于当前自然日的最近 60 个指数交易日，顺序按交易日升序。 该窗口只服务日常自动触发，不替代历史 backfill 或长窗口 gap audit。
第一层剪枝 先读取 silver_index_daily 的 materialized partition 集合，找到窗口内第一个没有 materialization 的交易日 first_missing_materialization_date。 如果窗口第一天就缺 materialization，则直接返回该日期作为待触发目标，不扫描 check history。
不能直接返回 missing 的原因 如果 first_missing_materialization_date 之前已有 materialization 的日期中存在 failed/missing blocking check，真正的最早未 ready 日期是前面的 failed 日期，而不是后面的 missing 日期。因此必须先复核 missing 日期之前的已 materialized 前缀。
待复核前缀 若存在 first_missing_materialization_date，只复核它之前的 materialized prefix； 若不存在 missing materialization，则复核完整 60 日窗口。不得复核 missing 日期之后的分区， 因为它们不会影响“最早未 ready 日期”的选择。
latest materialization 绑定 对待复核前缀内每个交易日读取 latest materialization record，并以其 storage_id 作为唯一匹配键。旧 materialization 的 check 通过，不能证明最新 materialization ready。
blocking checks 批量查询 对 SILVER_INDEX_DAILY_BLOCKING_CHECKS 中每个 check name 最多查询一次 check execution history，再按 target_materialization_data.storage_id 匹配前缀内的 latest materialization。旧逐日方案最坏是 60 * 7 = 420 次 check history 查询； 新方案稳定态最多 7 次 check history 查询。
check 结果选择 同一个 check 与同一个 latest materialization 若存在多条 execution event，必须取最新 event。 实现不得依赖未确认的 API 返回顺序；必须基于可排序字段选择最新，或在实施前先确认 Dagster 1.13.6 的返回顺序并用测试固定。
fail closed check event 的 blocking 必须为 true，且 execution succeeded、evaluation passed 才算通过。历史 non-blocking check event 即使 passed 也不能算 ready。 如果 check history 在配置 limit 内找不到目标 latest materialization 的结果，必须返回 missing check，不得默认为 ready。
返回规则 按窗口升序返回第一个 not-ready 状态：前缀内 failed/missing check 优先； 前缀全 ready 且存在 first_missing_materialization_date 时，返回该 missing 日期； 完整窗口 materialized 且 checks 全绿时返回 all-ready skip。
触发规则 只有返回状态是未 materialized 时，sensor 才能提交 silver_index_daily_update_job[trade_date]。如果目标日期已 materialized 但 checks 未全绿，sensor 只返回中文 skip reason，等待人工处理，不自动重跑。
性能预算 日常 60 日窗口内，check history 查询数不得超过 blocking check 数量；若后续窗口扩大， 需要重新评估 partition_count * blocking_check_count 与 Dagster sensor evaluation 时限，不能把该 helper 直接扩展成历史批量审计工具。
测试门槛 必须覆盖：窗口第一天 missing 时不扫 check history；前面 failed check、后面 missing 时返回前面的 failed； 60 天全 ready 时 check history 只查 7 次；non-blocking 历史 event 不通过；同一 materialization 多条 check event 取最新；history limit 找不到目标 materialization 时 fail closed；sensor 对 failed-check 日期不提交 run。

10.4 silver_index_daily_sensor 踩坑记录

2026-05-26 发现 silver_index_daily_sensor tick 报 DagsterUserCodeUnreachableError / DEADLINE_EXCEEDED。 根因不是 silver asset 本身失败，而是 sensor evaluation 过重：旧实现先逐个指数代码读取 raw parquet 判断目标 trade_date 是否存在，再逐 code 查询 raw asset materialization 和多项 blocking check history。 这把“能否进门”的轻量判断做成了 N 个文件扫描加 N 组 Dagster event history 查询，容易超过 gRPC sensor evaluation 时限。

正式口径：sensor 只读 raw-by-code 文件事实，确认文件存在且包含目标日期；不再读取 raw run tags/config， 也不扫描 raw asset materialization 或 check history。去重、字段类型和 silver 输出质量继续由 silver_index_daily asset 与 checks 承担。后续 sensor 门禁不得再把 per-code check history 扫描放进 evaluation 函数；重检查应进入 run/check 层。
