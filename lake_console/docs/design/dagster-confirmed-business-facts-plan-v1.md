# DG 已确认业务事实登记方案

日期 2026-11-20 · ETF 复权因子覆盖规则已确认，待实施 · 首期案例为天弘上证180ETF（`530080.SH`）

配套[详细设计](dagster-confirmed-business-facts-low-level-design-v1.md)说明 SQL、接口、检查接入、历史复核及验收。

## 1. 目标和接入范围

在 DG 的 PostgreSQL 业务库 `goldenshare_lake_meta` 中建一张 `confirmed_business_facts` 表。运营依据公告登记一次，相关数据集按需使用。Tushare 每次同步照录来源值，DG 查询指定日期的业务状态时，把已确认事实一起考虑。

**接入由数据集主动选择。** 每个接入的数据集说明要读哪类事实、用于哪一步、如何按日期判断。只有这条调用路径会查询登记表。新增一个使用方可以复用已经登记的记录，例如以后基金净值有需要时，可以读取同一条清算事实，再按净值披露规则检查。

首期提供登记和查历史的维护入口、按日期查询基金状态，以及 ETF 复权因子覆盖检查的接入。实际条目先用 `530080.SH` 的清算公告验证。数据更正有版本，工作流保持低频人工维护。登记表直接由 PostgreSQL 提供读取。日后若批量读取确有性能需要，可另行评估程序生成的带版本只读 Parquet。

## 2. 为什么需要这张表

11 月 20 日对照 Tushare 和 DG 数据，`530080.SH` 在基金基础信息里仍是 `list_status = 'L'`。天弘基金的公告确认该基金于 **2026 年 11 月 16 日进入清算**。正式终止上市的日期以交易所公告为依据，届时是另一条事实。 [天弘基金决议公告（转载）](https://qcloud.fund.eastmoney.com/gonggao/530080%2CAN202611141831712627.html)

按这次只读审计，各日情况如下。Raw 缺这个代码表示当时的源镜像没有该记录。是否应该有复权因子，由 Silver 的覆盖规则判定。

| 交易日 | ETF 复权因子 Raw 中的 `530080.SH` | ETF 复权因子 Silver |
| --- | --- | --- |
| 11 月 16 日 | 有 | 有，覆盖检查通过 |
| 11 月 17 日 | 无 | 文件存在。按现有规则应有 1,721 只，实际 1,720 只，仅缺这只，检查失败 |
| 11 月 18 日 | 无 | 审计时尚无文件 |
| 11 月 19 日 | 无 | 审计时尚无文件 |

现有代码从冻结的基金基础信息快照中，筛出沪深交易所与代码一致、`list_status = 'L'`、上市日不晚于交易日的 ETF。覆盖检查用同一份名单识别「应有未有」和「多出来」的代码。11 月 17 日文件已经存在，检查失败使自动任务停在最早未通过的日期，后续日期随之停住。写入与源数据一致性检查还使用同一份基础信息筛选源行。现有规则和审计更正见原 ETF 方案。 [覆盖检查与源行筛选](../../orchestrator/src/orchestrator/defs/io/etf_daily_silver_writer.py) · [ETF 现行方案](dagster-etf-daily-data-onboarding-plan-v1.md)

已完成的股票停复牌链路有可参考的做法。源数据与已确认事实在一个地方形成业务判断，再供多个任务使用。本方案的首期使用方是 ETF 复权因子，现有股票停复牌治理由原专项管理。 [停复牌治理方案](dagster-stock-suspend-confirmed-facts-technical-plan-v1.md)

## 3. 数据库和表结构

业务库使用现有架构预留的 `goldenshare_lake_meta`。Dagster 运行与事件由 `goldenshare_dagster` 管理。早期资料记录业务库曾创建，当前编排代码尚未接入，实施前用只读方式核实库、角色和连接条件。 [DG 业务库分工](../architecture/大火箭.md) · [编排资源规则](../../orchestrator/AGENTS.md)

### 3.1 字段

一行存一件事的一个版本。更正或撤销时追加新行，原版本可查询。

| 字段 | PostgreSQL 类型 | 含义和用法 |
| --- | --- | --- |
| `fact_id` | `uuid` | 事实编号。登记生成，更正和撤销沿用。 |
| `revision` | `integer` | 版本号，首次为 1，每次更正或撤销加 1。 |
| `action` | `text` | 固定值 `confirm`、`correct`、`revoke`，分别表示确认、更正、撤销。 |
| `subject_type` | `text` | 对象类别，首期为 `etf`。 |
| `subject_key` | `text` | 对象标识，首期为带交易所后缀的 ETF 代码。 |
| `fact_type` | `text` | 固定事实编码。首期支持 `fund_liquidation_started`（进入清算）和 `fund_delisted`（正式退市）。 |
| `time_precision` | `text` | 公告时间精度。首期按日登记，系统填 `day`。将来如接入有盘中时刻的事实，再明确该类型的时间规则。 |
| `effective_from` | `timestamptz` | 生效起点，包含该时点。日级事实使用上海时间当天零点作为计算边界，运营看到的是日期。 |
| `effective_until` | `timestamptz`，可空 | 适用结束边界，到达该时点停止适用。公告无明确结束日期时留空。 |
| `evidence` | `jsonb` | 证据列表。每项包括发布机构、公告链接及可取得的公告编号。确认和更正至少附一项。撤销可附后续公告或其他凭据。 |
| `reason` | `text` | 登记、更正或撤销的说明，供查证。 |
| `recorded_by` | `text` | 由维护入口取得的经认证操作人。 |
| `recorded_at` | `timestamptz` | 数据库记下本次提交时间。查询业务日期时使用生效时间，查操作历史时使用录入时间。 |

`fact_id + revision` 是主键。按对象类别、对象标识和事实类型建查询索引。应用使用枚举校验对象类型和事实编码，数据库约束主键、版本、操作类型和时间区间。更正可修改时间、证据或说明。对象或事实类型填错时，先撤销原记录，再登记正确的事实。

### 3.2 这个案例实际怎么填

| 运营看到的内容 | 实际保存 |
| --- | --- |
| 对象 | `subject_type = etf`，`subject_key = 530080.SH` |
| 发生的事 | 在维护入口选择「进入清算」，保存 `fact_type = fund_liquidation_started` |
| 生效日期 | 2026-11-16，按上海日期保存，`time_precision = day` |
| 结束日期 | 空 |
| 公告与说明 | 天弘基金决议公告链接。说明为「公告确认 11 月 16 日起进入清算」。 |

提交后由系统填记录编号、操作人、录入时间和第 1 版。日常程序使用固定编码和时间范围进行判断，公告链接和说明供运营查证。若交易所之后公布正式退市日期，运营选择「正式退市」，新增一条 `fund_delisted`。两件事各有证据、日期和历史。

## 4. 维护与查询方法

首期使用一个 DG 维护入口。登记、更正和撤销调用同一处维护代码。登记后回显对象、事实编码、生效日期和版本。复核沿用 ETF 复权因子的现有任务入口，按明确的对象和日期执行。

| 方法 | 输入 | 结果 |
| --- | --- | --- |
| `register_fact` | 对象、事实编码、生效范围、证据、说明 | 事实已登记时返回现有记录，否则写入第 1 版。 |
| `correct_fact` | 记录编号、操作人看到的版本、修改内容、证据、说明 | 读取数据库当前状态，必要时追加一份完整的新版本。 |
| `revoke_fact` | 记录编号、操作人看到的版本、撤销理由、可用证据 | 事实已撤销时回显状态，否则校验版本后追加撤销记录。 |
| `list_fact_history` | 对象或记录编号、分页范围 | 查看版本、操作人、时间和证据。 |
| `find_effective_facts` | 一批对象、明确的事实类型和日期范围 | 批量返回适用记录和版本。先取每条事实的最新版本，再判断撤销和有效期。这样更正生效日期后，旧版本也不会重新出现在查询结果里。 |

维护操作在同一短事务内校验并追加记录。提交中断后重新执行同一项操作，每次以数据库当前记录为准。已完成的登记、更正或撤销回显现有结果，尚未写入的操作按当前状态办理，遇到不同内容或版本冲突时先核对。数据库读写权限分配给相应入口。DG 自动化用只读角色，维护入口用有登记权限的身份。连接方案拟使用预留的 `LAKE_META_POSTGRES_URL` 为只读入口供值，敏感值由本地运行环境提供。连接仅在已接入的任务需要读表时打开，配置与权限在编码前核实。 [Dagster 资源定义](https://docs.dagster.io/guides/build/external-resources/defining-resources)

## 5. ETF 复权因子怎么接

### 5.1 提取事实，按日期查状态

基金基础信息的 `list_status` 保存来源值。统一的 DG 基金状态查询接收代码、业务日期和基础信息快照，结合已确认事实给出业务状态和依据。以 11 月 17 日为例，来源值是 `L`，有效记录是 `fund_liquidation_started`，查询结果显示「清算中」。正式退市事实生效后，查询才根据该事实显示「退市」。 [现有 ETF Basic 快照选择](../../orchestrator/src/orchestrator/defs/asset_guards/etf_basic_readiness.py)

ETF 复权因子的现有正式覆盖检查和自动任务文件核验，各自在开始核验时批量读取本次日期范围内的清算事实。程序按 `subject_key` 和固定枚举 `fund_liquidation_started` 匹配，比较事实生效区间与交易日。正式覆盖检查记下用于追溯的事实编号和版本。两处入口共用原覆盖检查的规则实现，ETF 日线使用自己的现有规则。 [正式覆盖检查](../../orchestrator/src/orchestrator/defs/checks/etf_daily_checks.py) · [运行前文件核验](../../orchestrator/src/orchestrator/defs/asset_guards/etf_daily_lake_readiness.py)

### 5.2 ETF 复权因子覆盖规则（已确认）

2026 年 11 月 20 日管理员确认，**对有公告依据且清算事实已生效的 ETF，从清算生效日当天起允许复权因子缺省。源端提供的有效因子应按现有筛选、字段和源数据一致性规则入库，已保存的有效因子应保留。** 这是 DG 的覆盖规则，清算生效日期取自公告。仅有源端空结果时，覆盖检查仍按当天应有的名单判断。

对 `530080.SH`，因此适用日期从 11 月 16 日起。16 日已有的有效因子应保留，17 日缺少这只 ETF 的因子本身不再阻断覆盖检查。正式运行结果以规则实施后的实际复核为准。

覆盖检查用以下等价逻辑，正式实现沿用 DuckDB 批量 SQL。

```python
eligible_codes = select_eligible_etfs(basic_snapshot, trade_date)
liquidating_codes = {
    fact.subject_key
    for fact in effective_facts
    if fact.fact_type == FactType.FUND_LIQUIDATION_STARTED
}

required_codes = eligible_codes - liquidating_codes

missing_codes = required_codes - silver_codes
unexpected_codes = silver_codes - eligible_codes
```

`effective_facts` 已按该交易日筛好。缺失检查使用必有名单，超范围检查使用可入库名单。把清算基金直接从两份判断中都删掉，会误报 11 月 16 日的合法因子。源端给了合法记录而 Silver 漏写时，源数据一致性检查仍会指出缺失。 [现有行筛选与源数据一致性核验](../../orchestrator/src/orchestrator/defs/io/etf_daily_silver_writer.py)

### 5.3 运行、复核和恢复

1. 保留现有日常任务、重跑入口和每个日期的文件检查方式。每次覆盖核验使用该次适用的事实，正式检查结果记录所用事实的编号和版本，查询登记历史即可核对原内容。登记表读取失败时报告错误，查表成功且为空时按原有基础信息判断。
2. 本次手动补齐前，先暂停 ETF 复权因子 Silver 的 sensor，核对这条 sensor 已提交的相关作业都已结束。读回 11 月 16 日已有的有效因子，再对 17 日已有文件跑一次现有检查。17 日通过后按现有单日任务依次生成 18、19 日，各自检查并读回。完成后恢复这条 sensor 原有状态。
3. 本次单日任务失败后重新发起对应日期的任务。已落到正式位置且通过核验的文件保留，可按情况复用或补检查。失败作业的临时候选按作业编号、资产和日期列出，确认作业已结束、清理范围获准后定点清理，再启动新的同日任务。正式文件与候选有冲突时保留现场并报告。 [性能与文件安全规则](dagster-data-pipeline-performance-governance.md)

## 7. 实施顺序与验收

按已确认的复权因子覆盖规则完成 LLD、接入点与配置核验，再开发并进行隔离验证。开发和隔离验证完成后，单独交付第 8 节的接入使用说明。正式登记、任务触发、Lake 写入及检查结果发布按各步骤的明确授权执行，正式状态以实际执行和验收记录为准。

| 验收项 | 怎么证明通过 |
| --- | --- |
| 固定编码 | 选「进入清算」保存固定编码。无效编码被拒绝。修改公告备注后，状态判断仍按编码和日期计算。 |
| 更新后保留 | 正常同步 ETF Basic 后，用本次同步后经核验的快照查询同步当日的 `530080.SH` 状态，核对清算事实、公告和版本。11 月 17 日复权因子文件的复核使用原文件对应的 Basic 快照。 |
| 真实日期案例 | 16 日已有有效因子读回相同。17 日用获准规则复核现有文件。18、19 日正式文件通过覆盖及源数据一致性检查。 |
| 真缺数仍能拦截 | 用一只符合要求但确实缺失因子的 ETF 验证覆盖检查失败。用源有而 Silver 漏写的样本验证一致性检查失败。 |
| 更正、撤销和中断 | 更正或撤销后，后续核验按最新适用事实判断，旧检查可查到当时所用版本。维护操作中断后重做也只留一份业务结果。单日任务中断后，核对并清理其废弃候选，再重跑对应日期。 |
| 按需接入 | 在隔离测试里让登记库不可读。ETF 复权因子核验报明确错误，未接入的任务仍能依照自身输入完成。 |
| 正常清算日边界 | 用相互独立的测试预期验证生效日前、当天、之后，覆盖源端有记录和无记录两种情况。对正式退市另用交易所公告对应的日期验证状态。 |
