Dagster 股票分钟线连续性性能优化专项方案

本文档基于已完成的只读 profiling 重新定义优化方向：不新增 status manifest、summary asset、readiness asset、数据库表或其它新状态实体。 优化重点改为减少读取次数，使用 DuckDB 批量读取 lake 文件事实，并在需要放行或阻断时执行完整 blocking check 语义。

状态方案文档；尚未进入代码实现。
适用范围股票分钟线 raw / silver / qfq 日常 continuity sensor hot path。
不做事项不新增实体；不改 run key；不运行 Dagster；不写正式 lake。
核心原则先 batch，后判断；粗筛不冒充 ready；完整语义不能降级。

1. 结论

旧方案废弃： 不再把“新增 lake status manifest”作为本专项主方案，也不保留新增持久化状态实体的备选路线。 qfq / repair sensor 的性能问题纳入本专项，但只能通过 batch 读取、lake 文件事实、现有 metadata bounded read 和移除热路径无用字段解决。
新方案： 股票分钟线 sensor hot path 使用“两阶段 batch readiness”： 第一阶段用 DuckDB 粗筛 60 天窗口的文件存在、freq 覆盖和 row count，快速发现明显缺口； 第二阶段对粗筛通过的窗口执行 batch 完整 blocking check 语义。 不允许只看 row count 就认定 ready。

这次优化的目标不是缩短窗口，而是减少读取次数。只要读取模型正确，20 天和 60 天的粗筛成本都在 0.1 秒级； 如果读取模型错误，20 天也会慢到不可接受。 本专项窗口固定保留 60 天；第一阶段不启用 cursor frontier cache，避免隐藏完整 check 语义变化。

3. 问题根因

问题 错误理解 正确理解
窗口大小 60 天太大，改成 20 天就能解决。 窗口不是根因。读取方式正确时，20 和 60 的粗筛成本都很低；读取方式错误时，20 天也会超时。
Dagster metadata 只要 batch 读取 Dagster metadata 就够了。 batch metadata 仍要反序列化大量 event JSON，60 天 raw/silver 仍在 11 到 12 秒。
DuckDB 粗筛 文件存在且 row count 大于 0 就是 ready。 粗筛只能快速定位明显缺口；ready 必须由完整 blocking check 语义确认。
新增状态实体 性能慢就新增 status manifest。 新增实体会带来一致性、原子性、回补和退出成本；本轮禁止新增实体。

4. 目标方案

4.0 P0 口径收口结论

P0 已拍板： 本专项不只优化 sensor 读取性能，也纳入两个会影响连续性正确性的契约收口： silver 分钟线退出 silver_namechange / 未被计算使用的 silver_stock_basic 直接硬依赖； silver_stock_daily 从 current-listed-only 过滤口径改为历史股票生命周期口径。
审计点 当前事实 后续固定口径
silver 分钟线 sensor gate stock_mins_silver_trade_day_sensor 与 stock_mins_silver_sensor 当前都把 silver_namechange_ready_for_trade_date(...) 作为硬门禁。 后续从这两个分钟线 sensor 中移除 namechange 硬 gate； silver_namechange_ready_for_trade_date(...) 继续服务 namechange 自身和 identity map 链路。
silver 分钟线 asset deps / writer inputs 五个 silver_stk_mins_* asset 直接依赖 silver_namechange / silver_stock_basic； write_silver_stk_mins_partition(...) 也要求 silver_namechange_path / silver_stock_basic_path 存在。 但当前 silver 分钟线生成 SQL 实际消费的是 raw、identity map、stock daily、suspend 和 1m raw。 后续移除这两个未被计算使用的直接硬依赖； 保留 silver_stock_identity_map、silver_stock_daily、 silver_stock_suspend_daily 作为正式前置。
silver_stock_daily 股票池口径 silver_stock_daily_select(...) 当前用 current-listed-only 的 silver_stock_basic 过滤股票全集； silver_stock_daily_current_listed_only 也是正式 blocking/readiness 口径。 后续改为 raw_stock_basic 历史生命周期事实： ts_code + trade_date 必须落在 list_date 到 delist_date/null 生命周期内，并保留 CNY、上市日期、北交所开市日期等现有交易规则。 新增 blocking check 名称固定为 silver_stock_daily_stock_lifecycle_covered； 旧 silver_stock_daily_current_listed_only 退出正式阻断口径。

P0 只记录这些口径，不落代码。涉及 stock daily 的变更范围大于最初的分钟线 sensor 性能优化， 所以后续必须把 stock daily 生命周期改造拆成独立阶段，不能藏在 silver 分钟线 check 或 sensor 改造里顺手处理。

4.1 两阶段 Batch Readiness

sensor tick
  expected_dates = load from silver_trade_calendar
  registered_dates = dynamic partitions

  coarse_frontier = DuckDB batch coarse scan(expected_dates[-60:])
  if coarse_frontier.first_missing_or_obvious_not_ready:
      return SkipReason or RunRequest for that earliest actionable date

  full_frontier = DuckDB batch full blocking check scan(required window)
  if full_frontier.first_failed:
      return SkipReason; do not advance later dates

  target = first date whose target asset is not produced
  validate target with single-day full check when needed
  submit RunRequest only when all upstream gates are ready

第一阶段负责快，第二阶段负责正确。不能删除第二阶段，也不能把第一阶段结果写成 ready。

4.2 Raw Readiness

层级 粗筛 完整语义
raw 五频度文件存在，row count 大于 0，按 date/freq 聚合。 schema、freq matches asset、partition date、唯一键、price/volume sanity、partition registered。

4.3 Silver Readiness

层级 粗筛 完整语义
silver 五频度文件存在，row count 大于 0，按 date/freq 聚合。 schema、freq/date/trade_time、唯一键、价格、量额、exchange、stock_daily codes、full-day suspend、股票生命周期身份覆盖、名称时间线解释。

4.4 QFQ 与 Repair Status

qfq daily 与 qfq factor repair 已完成只读 profiling，必须纳入本专项一并处理。 当前 selector 因 2026-03-23 / 2026-05-22 的上游 not-ready 会很快短路，但这只是当前数据状态，不代表设计安全。 一旦早期缺口修复，qfq daily 会重新进入 60 天逐日 DG metadata 扫描，实测不短路 60 天为 38.27s。

qfq daily 方案：复用 raw/silver 的 batch lake readiness 思路，并扩展到 gold qfq 和 adj factor readiness； qfq factor repair 方案：gold qfq readiness 改为 batch 读取；repair status 热路径不得再计算或回填 event_storage_id， 只读取判断自动触发所需的 metadata，例如 ready、repair_required、upstream_batch_id、repair range、codes hash。 本轮不新增 qfq factor repair status manifest，不新增 MACD/KDJ completion manifest。
