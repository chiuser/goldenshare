Dagster Silver 上下游关系与触发门禁审计

更新时间：2026-06-07。适用范围：lake_console/orchestrator 当前 silver 生产链路、触发入口、raw ready 门禁和下游影响面。

1. 文档定位

本文不是 silver 资产数量台账，也不是字段 schema registry。本文只回答三个问题：

  1. 某条 silver 生产链路依赖哪些 raw、silver 或文件事实。
  2. 自动触发时，sensor 在提交 run 前到底检查了哪些 ready 门禁。
  3. 门禁缺口会影响哪些下游链路，应该按什么优先级修复。

本文记录静态代码审计结论与已确认的上线观察事实。不运行 Dagster job、sensor、backfill，不读取正式 Dagster instance，不读写 lake 数据。2026-06-07 用户已在 Dagster UI 打开 stock_daily 相关新 sensor，暂未观察到异常；该观察由用户操作反馈提供，不代表本文执行过正式环境验证。手动 Launchpad、CLI、runless 补录绕过 gate 的问题另设专项，不在本文中宣称已解决。

2. Ready 门禁口径

门禁口径 含义 可否作为下游触发依据 本文中的使用场景
event/check ready 上游 asset 已 materialized，且同一 materialization 的 blocking checks 全部通过。full snapshot 还要满足 freshness。 可以 分钟线 silver、身份映射、部分下游 gold 的触发门禁。
file-fact ready 通过本地文件事实和 DuckDB set-based SQL 证明输入文件、目标日期数据和连续性满足生产条件。 可以 silver_index_daily。raw 按指数代码分区，silver 按交易日分区，使用文件事实门禁比逐 code event 扫描更合适。
in-run raw write only raw 和 silver 在同一个 job selection 中，Dagster asset 依赖只能保证 raw asset 函数先于 silver asset 函数。 不可以视作严格 ready suspend_d、adj_factor、基础 full snapshot 当前仍存在该问题。stock_daily 自动链路已从此类移出。

4. 总修复模式

所有 in-run raw write only 链路按同一种模式修复：先把 raw 生产事实变成可审计的 ready，再让 silver 触发显式依赖这个 ready。不要在每条链路里临时补一个文件存在判断，也不要把 raw 与 silver 继续放在同一个自动生产 job 里。

步骤 统一口径 落地要求
统一命名 asset 使用已确认的正式 asset key；job 名称固定为 layer + asset name + mode；sensor 名称固定为 job name + sensor。check 命名规则只适用于新增 check：asset name + function + check。 stock_daily 拆分后 job 为 raw_stock_daily_update_job 与 silver_stock_daily_update_job，sensor 为 raw_stock_daily_update_job_sensor 与 silver_stock_daily_update_job_sensor。已存在 check 禁止为了命名规则改名。
拆生产边界 raw-only job 只选择 raw asset 和 raw blocking checks；silver-only job 只选择 silver asset 和 silver blocking checks。 job 文件只保留 asset selection，不承载业务逻辑。禁止继续存在同一个日常自动 job 同时选择 raw 与 silver。
定义 raw ready raw ready 必须是 raw materialization 与同一 materialization 的 raw blocking checks 全绿。若 raw checks 依赖支撑事实，sensor 提交 raw run 前也要检查这些支撑事实。 在 readiness.py 中维护 raw-only readiness spec/helper；已有下游最终 ready helper 不得被削弱。
拆触发入口 raw sensor 只处理源站 ready 与 raw 缺口；silver sensor 只处理 raw ready、支撑事实 ready 与 silver 缺口。 sensor 只提交满足门禁的分区。已 materialized 但 blocking checks 未全绿的分区默认 skip，不自动用 daily sensor 重跑。
保留合法文件事实 gate 若数据形态不适合逐 asset event 扫描，可使用 DuckDB 文件事实 gate，但必须能证明目标日期 presence、连续性或完整性。 silver_index_daily 继续保留 file-fact ready。该口径不是漏洞，不能被误改为低性能历史 event 深扫。
控制性能 daily sensor 只看小窗口和少量候选分区；不在 sensor 中做全历史扫描。 event/check ready 适合按分区小批量判断；历史深扫必须另走维护审计或 DuckDB set-based SQL。
测试门禁 正向证明 ready 后提交 run；负向证明 raw missing、raw check failed、supporting fact not ready、source not ready 时不提交 silver run。 必须有静态测试断言 job selection 不再混 raw+silver，并有 sensor 单测覆盖 skip/run 分支。

stock_daily 已按本模式落地：旧混合 job/sensor 被替换为 raw-only 与 silver-only 入口，silver sensor 显式等待 raw event/check ready。手动 Launchpad、CLI 或 runless 补录绕过 gate 是单独专项。本文的总修复模式先覆盖自动触发链路，不能在本文中声明手动入口已经被治理。

7. 后续新增链路登记要求

新增 silver 数据集或修改生产链路时，不再只登记资产名，而要登记触发关系：

登记项 必须说明
上游事实 raw assets、支撑 silver facts、文件事实、source readiness、full snapshot freshness。
触发入口 sensor、automation condition、schedule、manual-only job，以及 run key / cursor 口径。
提交 run 前门禁 明确是 event/check ready、file-fact ready，还是待整改的 in-run raw write only。
下游影响面 列清直接消费方、间接消费方和失败后会被阻断的链路。
性能预算 event log 查询次数、DuckDB 扫描规模、分区数、对象数和不可接受阈值。
测试门禁 ready 时提交 run；not-ready、failed check、scan error 时不提交；禁止扩大 job selection；禁止同 job 重新混入 raw+silver。
