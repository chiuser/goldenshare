# wealth 模块交付通用清单 v1

> 用途：把“市场客观总结”这轮实践沉淀为可复用检查清单。  
> 适用范围：`wealth` 所有后续模块（summary / indices / breadth / turnover / money-flow / leaderboard / limit-up / sectors）。

---

## 1. 使用方式

1. 每个模块开工前，先跑完本清单再编码。
2. 清单中的“否决项”任一不满足，必须停下来先修正文档或方案，不能带病开发。
3. 本清单与模块交付事实链配套使用，不替代 Figma/需求基线、implementation design、LLD 及其内嵌编码门禁。

---

## 2. 硬检查

## 2.1 交付事实链先行（否决项）

检查项：

1. 完整 Figma 已完成并评审通过；没有完整 Figma 或存在无法由 Figma 表达的需求时，已补独立 benchmark requirement。
2. implementation design 已完成并评审通过。
3. LLD 已完成并评审通过，且包含编码门禁矩阵、核心测试和例外白名单。

不通过动作：

1. 不允许进入编码。

---

## 2.2 后端事实归一（否决项）

检查项：

1. 模块核心事实字段全部由后端产出。
2. 前端不做事实拼装、排序口径改写、语义二次计算。
3. 示例响应能一眼看懂业务含义（避免 `2/10` 这类歧义表达）。

不通过动作：

1. 回到 implementation design 明确字段语义和来源映射。

---

## 2.3 模块状态机清晰（否决项）

检查项：

1. 至少定义 `loading / ready / error`（必要时扩展 `empty / delayed / partial`）。
2. 真实 API 未返回前，不得展示 mock 数据冒充 ready。
3. 超时阈值和超时文案已在文档写死（例如 5 秒超时）。

不通过动作：

1. 先补状态流设计，再改代码。

---

## 2.4 显示语义与数据语义绑定

检查项：

1. 红涨绿跌规则由结构化方向字段驱动，不靠文案猜测。
2. 值格式（如 `2:8`）与颜色、说明文案一致（如“上涨数量:下跌数量”）。
3. 不能出现展示样式和事实含义矛盾。

不通过动作：

1. 修正 DTO 字段和前端渲染映射。

---

## 2.5 测试覆盖“行为过程”

检查项：

1. 不只断言最终 JSON，还要覆盖状态过程（例如 loading -> ready、timeout -> error）。
2. 覆盖核心布局变体（如 5 卡 / 6 卡）。
3. 覆盖错误分支的用户可见文案。

不通过动作：

1. 补充行为测试后再合入。

---

## 2.6 文档与实现同轮同步（否决项）

检查项：

1. 代码改口径后，Figma/需求基线、implementation design、LLD 与门禁矩阵同轮更新。
2. 示例响应、字段定义、异常语义与当前代码一致。
3. 不留“文档旧、实现新”的错配状态。

不通过动作：

1. 先补文档一致性，再允许提交。

---

## 2.7 模块级渐进替换纪律

检查项：

1. 每轮只切一个目标模块，其余模块保持 mock 且不动。
2. 不做静默 mock 回退掩盖真实失败。
3. 有清晰回滚条件与回滚步骤。
4. 必须有模块级 source 开关记录（本轮前后值可追踪），能明确证明“只切了目标模块”。

不通过动作：

1. 按 [module-incremental-delivery-spec-v1.md](/Users/congming/github/goldenshare/wealth/docs/system/module-incremental-delivery-spec-v1.md) 回到上一状态。

---

## 2.8 契约先行与消费者对齐（否决项）

检查项：

1. 先冻结模块 DTO（字段名、可空策略、状态语义），再落后端与前端代码。
2. 后端返回结构与前端消费模型一一对应，不允许前端做“临时补字段/猜语义”。
3. 契约变更必须同步更新：implementation design/LLD + API 示例 + 对应 smoke 测试断言；涉及视觉交互时还必须同步 Figma。

不通过动作：

1. 回到 implementation design 先完成契约收敛，不允许继续编码。

---

## 2.9 图表坐标与说明文案约束

检查项：

1. 图表坐标轴必须符合业务语义约束（如“家数”类指标纵轴下限固定为 `0`，不得出现负值刻度）。
2. 需要固定刻度的模块，刻度值必须在 implementation design 或 LLD 中写死并与实现一致。
3. 说明性文案（如图下“横轴/纵轴提示”）默认不常驻展示；仅当评审通过的 Figma 或明确需求基线要求时才允许显示。

不通过动作：

1. 先回到 benchmark/implementation 文档补齐约束，再修改代码与测试。

---

## 2.10 统计计算与数据传输边界

检查项：

1. 中位数/分位数/聚合类统计优先在 SQL 侧计算，不允许先把大结果集拉到应用层再计算。
2. 涉及数据库特有函数（如 `percentile_disc`）时，必须提供测试环境兼容策略（例如 sqlite fallback）。
3. 模块切 real API 前，必须完成一次端到端耗时实测，并与前端超时阈值对齐（默认 5 秒）。

不通过动作：

1. 回到 implementation design 补齐“查询下推策略 + 兼容策略 + 性能验证口径”后再编码。

---

## 2.11 配置生效语义（策略中心模块）

检查项：

1. 模块文档必须明确配置文件路径、注册键（`moduleKey/market`）和生效时机。
2. 配置改动后是否需要重启、何时生效、校验失败行为，必须写入 implementation design/LLD 并进入门禁矩阵。
3. 任何“配置可改”能力都必须有结构化模型校验，禁止运行时隐式吞错。

不通过动作：

1. 先补齐配置生效语义文档和门禁，再允许提测或发布。

---

## 2.12 通用清单映射矩阵（否决项）

检查项：

1. 每个模块的 LLD 必须内嵌“编码门禁矩阵”，逐条标记：
   - 适用（并给出落地位置：字段/测试/组件）
   - 不适用（必须给出业务语义理由）
2. 未映射条目不得留空，不允许“默认继承”。
3. 映射矩阵未评审通过，不允许开工编码。

不通过动作：

1. 先补齐映射矩阵并完成评审，再进入实现。

---

## 2.13 模块例外白名单与语义断言（否决项）

检查项：

1. 偏离通用清单的规则，必须登记到模块级“例外白名单”，并写明：
   - 例外规则
   - 适用模块
   - 生效范围
   - 业务语义依据
2. 累计值图表（如累计成交额、累计净流入）默认纵轴下限为 `0`，不得出现负值刻度；若要放宽，必须先进入白名单并评审通过。
3. 坐标语义规则必须有可执行测试断言（至少一条），不能只写文档不落测试。

不通过动作：

1. 先补白名单与测试断言，再允许提交代码。

---

## 2.14 图表参数优先级与语义不可篡改（否决项）

检查项：

1. 当组件显式传入 `yMin/yMax/yTickValues` 时，图表渲染层必须“原值生效”，禁止再做二次抬高、压低或自动改写。
2. 图表实现不得把“自动范围逻辑”覆盖“业务硬约束”；若两者冲突，必须先改文档拍板，再改实现。
3. 对“显式坐标参数”至少有一条可执行断言（单测或集成测试），验证最终渲染语义与契约一致。

不通过动作：

1. 回到实现层修正参数优先级，再补测试断言后才能提交。

---

## 2.15 双图并排坐标区对齐与标签避让（否决项）

检查项：

1. 同模块内并排双图（如左“当日”右“历史”）若共用同一业务坐标语义，必须使用同一套 `y` 域与刻度策略。
2. 双图坐标格必须对齐，不能出现一侧基线漂移、刻度区高度不一致。
3. 坐标轴标签必须完成边界避让验收，禁止出现 `y` 轴数字与 `x` 轴日期重叠。
4. 需要支持“最长标签样本”验证（如 `10000亿`、`YYYY-MM-DD`），通过后才允许合入。

不通过动作：

1. 修正图表布局参数与标签排版后再提测。

---

## 2.16 指标卡片文案长度与单行约束（否决项）

检查项：

1. 若 benchmark 指定某行文案必须单行展示（例如“20日均值 25920亿”），实现层必须给出明确样式约束（字号/行高/不换行）。
2. 不允许通过“缩窄父容器”或“挤压其他卡片”来间接凑单行；必须定点修改目标卡片样式。
3. 卡片文案长度约束需要有至少一条页面级 smoke 断言或人工验收截图记录。

不通过动作：

1. 先补齐样式约束与验收证据，再允许提交。

---

## 2.17 核心测试 case（真实 API + 前端展示）覆盖（否决项）

检查项：

1. 每个模块必须定义“核心测试 case 字段清单”（页面关键展示字段 + 状态字段 + 异常字段）。
2. 后端必须有真实 API 集成测试覆盖核心字段（走真实路由，不 mock service/query）。
3. 前端必须有真实 API 展示校验覆盖核心要素（禁用 mock adapter 路径，验证页面展示与后端字段一致）。
4. LLD 编码门禁矩阵中必须写明核心 case 的执行命令与通过标准。
5. 仅 mock 测试不允许作为模块交付门禁通过依据。

不通过动作：

1. 先补齐核心 case 设计与测试，再允许提交。

---

## 2.18 跨模块抽象门禁原则（否决项）

> 用途：避免只记“某次事故细节”，把可复用规则固化为长期门禁。  
> 要求：每个模块的 `implementation design` 与 LLD 编码门禁矩阵必须逐条映射本节 8 条原则。

### 原则 1：事实源单一原则

检查项：

1. 页面展示事实只能来自后端契约字段，不允许页面或 adapter 二次拼装事实语义。
2. 同一事实不得在多个层次重复定义并各自演化。

参考 case：

1. 榜单字段缺失时不能由前端“猜值补值”，必须后端补齐契约字段并在真实 API 用例中断言。

### 原则 2：契约先行与冻结原则

检查项：

1. 字段名、可空策略、状态语义先冻结再编码。
2. 契约变更必须同轮更新 implementation design/LLD + API 示例 + 测试断言；涉及视觉交互时同步 Figma。

参考 case：

1. `cardKey/boardKey` 漂移会导致前端消费错位；必须靠冻结契约和测试阻断。

### 原则 3：配置一致性原则

检查项：

1. 配置模型、配置文件、代码读取、文档说明必须同源同名。
2. 配置变更必须有版本和生效语义说明。

参考 case：

1. 榜单 key 命名不一致（如 `amount/turnover` 口径混用）会直接导致模块行为偏移。

### 原则 4：默认行为显式原则

检查项：

1. 未传参、边界态、异常态行为必须显式定义（严格/降级/回退）。
2. 默认行为必须有可执行测试断言。

参考 case：

1. `strictHotDate=true` 时热榜空榜并标记 delayed，不能静默回退旧日数据。

### 原则 5：排序与筛选确定性原则

检查项：

1. 排序规则必须固定主次顺序，并定义异常值剔除规则。
2. 筛选条件必须来自文档+真实数据核验，不允许凭印象。

参考 case：

1. 热榜排序需固定为 `rank -> rank_time`，且 `rank/rank_time` 同时缺失行必须剔除。
2. 市场筛选值（如 `A股市场`）需与真实源数据值一致，否则会出现全空结果。

### 原则 6：性能预算前置原则

检查项：

1. 核心查询必须有性能预算与实现约束（SQL 下推、索引命中、超时阈值）。
2. 模块切 real API 前必须完成端到端耗时验证并与前端超时对齐。

参考 case：

1. 把大聚合放在应用层会导致接口稳定超时，必须前置下推 SQL 方案。

### 原则 7：可观测与异常标准化原则

检查项：

1. 异常码、严重级别、调试字段结构化统一。
2. 生产展示与 debug 展示分层，避免污染用户视图。

参考 case：

1. 异常必须走统一 exception registry，不允许模块内临时散落定义。

### 原则 8：测试以用户可见结果为中心原则

检查项：

1. 后端测试必须断言“前端实际消费字段”，不能只测状态码/结构存在。
2. 前端测试必须覆盖真实 API 驱动下的可见状态流转（loading/ready/error/delayed）。

参考 case：

1. 人气榜/飙升榜曾出现页面字段空洞，根因是测试未覆盖前端真实消费字段。

不通过动作：

1. 任一原则未映射或无测试落地，禁止进入编码和提测。

## 3. 提交前速查（One-pass）

1. 交付事实链是否全部通过评审？
2. 模块事实是否完全后端定义？
3. loading/ready/error 是否按文档实现？
4. 行情红绿语义是否由结构化字段驱动？
5. 行为测试是否覆盖状态过程与超时？
6. Figma/需求基线、implementation design 和 LLD 是否已同步最新实现？
7. 本轮是否只改了计划内模块？
8. 模块 source 开关是否可追踪且仅变更目标模块？
9. 前后端契约与 smoke 断言是否同轮更新？
10. 图表纵轴与刻度是否满足业务语义约束（例如家数类必须非负）？
11. 图下说明性文案是否仅在需求明确要求时展示？
12. 统计计算是否已下推 SQL，避免应用层拉取大结果集再聚合？
13. DB 特有函数是否提供测试环境兼容策略？
14. real API 接入前是否完成了端到端耗时实测，并与前端超时阈值对齐？
15. 配置文件路径、注册键、生效时机与失败行为是否已写入 implementation design/LLD 门禁？
16. 目标模块 LLD 是否包含“编码门禁矩阵”并已评审通过？
17. 目标模块是否存在未登记的规则例外（尤其累计值图表纵轴语义）？
18. 坐标语义与状态语义是否有对应可执行测试断言？
19. 显式坐标参数（`yMin/yMax/yTickValues`）是否被图表引擎原值生效（未被自动逻辑覆盖）？
20. 并排双图是否已验证“坐标格对齐 + 轴标签不重叠（最长标签样本）”？
21. 指定单行文案（如卡片副文案）是否具备定点样式约束与验收记录？
22. 是否完成该模块“真实 API 集成测试 + 真实 API 前端展示校验”双门禁？
23. 交付说明是否明确记录核心 case 的覆盖字段、命令与结果？
24. 是否已在 implementation design 与 LLD 门禁矩阵中映射“跨模块抽象门禁原则”8 条，并给出落地位置？
25. 是否存在“默认行为未定义”或“默认行为无测试断言”的路径？
26. 是否存在排序/筛选规则未固定、靠隐式 DB 顺序输出的路径？
27. 是否有配置 key 在文档、配置文件、代码中命名不一致的情况？
28. 是否有异常码未登记、debug 字段未结构化的情况？
29. 是否存在后端字段有值但前端展示链路断裂（或反之）的风险？
30. 性能预算（阈值、耗时、降级）是否在 implementation design/LLD 中可追踪？
31. 模块交付是否把“用户可见结果”作为测试主断言，而非仅结构断言？
