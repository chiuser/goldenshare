市场总览｜成交额总览分钟线快照方案 v1

本方案用于解决 /api/v1/wealth/market/turnover 当前直接扫描 raw_tushare.stk_mins 带来的结构性超时问题。目标不是把超时阈值勉强压进 5s，而是把页面读取链路彻底改成“读快照，不扫 raw”。

版本：v1 状态：待评审 范围：wealth 市场总览 / 成交额总览 建议落点：core_serving 文档格式：HTML 方案基线

1. 当前事实与为什么必须做长期方案

最新 30 分钟源时间探测
40.1s
单日 30 分钟市场聚合
5.4s
前端模块超时阈值
5.0s
问题点 当前实现 实测现象 结论
最新分钟线日期探测 max(trade_time) where freq=30 无写入任务时仍约 40s 全分区扫描，结构性不可接受
日内累计曲线 按日聚合 raw_tushare.stk_mins 有数据日约 5.4s 单月分区扫描，已经卡到页面超时边界
页面容错 5 秒后直接展示 error 模块稳定超时 不能靠“调大超时”解决

补充事实：raw_tushare.stk_mins_2026_04 单月分区约 31796570 行；2026-04-23 且 freq=30 的日内记录约 49572 行。

2. 设计目标与非目标

目标

  1. 让成交额总览页面完全脱离分钟 raw 表的在线聚合。
  2. 把“最新可用分钟日期探测”从全表扫描降为 O(1) 或近似 O(1)。
  3. 让页面读取链路稳定、可预测，并且不受分钟线导入任务影响。
  4. 保证重跑、补跑、覆盖写入时不会累加重复数据。
  5. 保持新架构边界：页面只读业务快照，不读 ops 状态表。

非目标

  1. 不在本方案内重做 TaskRun、审计模型、财富业务整页聚合接口。
  2. 不在本方案内重做分钟线原始表结构或历史分区布局。
  3. 不把页面 fallback 回 raw 查询作为兜底路径。
  4. 不为了短期通过 5 秒超时而做临时 patch。

3. 为什么“只加状态表”不够

方案 能解决什么 解决不了什么 结论
只加分钟线状态表 可以快速拿到最新日期、最新时间 盘中累计曲线仍要扫 raw_tushare.stk_mins 只能解决 40s 探测，不解决 5.4s 图表
分钟线市场汇总快照表 既解决最新日期探测，也解决图表读取 需要新增一个物化构建链路 推荐

结论：本次应该做“快照表”，而不是只做“状态表”。

4. 推荐表设计

4.1 表名建议

推荐表名：core_serving.wealth_market_turnover_snapshot

这是一个明确服务于“财富行情 / 市场总览 / 成交额总览”模块的业务快照，而不是通用 raw 状态表。

4.2 表结构

字段 类型 约束 说明
type varchar(16) PK 主体类型。首期固定 stock，后续可扩展 index、sector
market varchar(16) PK 市场标识，首期固定 CN_A
trade_date date PK 交易日
freq smallint PK 分钟周期，首期支持 1/5/15/30/60，后续再扩展
build_status varchar(16) not null READY / FAILED。PARTIAL 属于模块展示态，不进入单条快照构建态
latest_trade_time timestamp null 该切片内最新分钟点，存本地交易所时间；例如 2026-05-08 15:00:00
total_amount numeric(20,2) null 该交易日该频率下的全市场成交额总计，单位 thousand_yuan（千元）
total_vol bigint null 该交易日该频率下的全市场成交量总计，整数
security_count integer null 参与本切片汇总的证券数量
source_row_count bigint null 参与本次汇总的源分钟线行数，用于对账、定位失败构建、发现异常波动
points_json jsonb not null 该日该频率的全市场分钟点数组，按时间升序；页面图表直接读取这里，不再扫 raw
build_version varchar(32) not null 快照构建版本，例如 v1、v1.1-hotfix
built_at timestamptz not null 本行快照生成时间

4.3 points_json 建议结构

[
  {
    "tradeTime": "09:30",
    "tradeTimeTs": "2026-05-08 09:30:00",
    "amount": 1288000.52,
    "vol": 418229103,
    "securityCount": 5231
  },
  {
    "tradeTime": "10:00",
    "tradeTimeTs": "2026-05-08 10:00:00",
    "amount": 1632000.14,
    "vol": 509108321,
    "securityCount": 5240

存“该频率下的完整分钟点数组”，不要只存前端固定 5 个点。amount 是该分钟点成交额，单位 thousand_yuan（千元），累计值由查询层生成。

4.4 DDL 草案

CREATE TABLE core_serving.wealth_market_turnover_snapshot (
  type              varchar(16)  NOT NULL,
  market            varchar(16)  NOT NULL,
  trade_date        date         NOT NULL,
  freq              smallint     NOT NULL,
  build_status      varchar(16)  NOT NULL,
  latest_trade_time timestamp    NOT NULL,
  total_amount      numeric(20,2) NOT NULL,
  total_vol         bigint       NOT NULL,
  security_count    integer      NOT NULL,
  source_row_count  bigint       NOT NULL,
  points_json       jsonb        NOT NULL DEFAULT '[]'::jsonb,
  build_version     varchar(32)  NOT NULL DEFAULT 'v1',
  built_at          timestamptz  NOT NULL DEFAULT now(),
  build_note        text,
  PRIMARY KEY (type, market, trade_date, freq),
  CONSTRAINT ck_wealth_market_turnover_snapshot_type
    CHECK (type IN ('stock', 'index', 'sector')),
  CONSTRAINT ck_wealth_market_turnover_snapshot_market
    CHECK (market = 'CN_A'),
  CONSTRAINT ck_wealth_market_turnover_snapshot_freq
    CHECK (freq IN (1, 5, 15, 30, 60)),
  CONSTRAINT ck_wealth_market_turnover_snapshot_status
    CHECK (build_status IN ('READY', 'FAILED'))
);

CREATE INDEX idx_wealth_market_turnover_snapshot_lookup
  ON core_serving.wealth_market_turnover_snapshot (type, market, freq, build_status, trade_date DESC);

当前真实分钟线样本已核实：freq=30 在库里的分钟点形态是 09:30 / 10:00 / 10:30 / 11:00 / 11:30 / 13:30 / 14:00 / 14:30 / 15:00， 所以 latest_trade_time 的常见终值就是 15:00:00。

5. 生成链路设计

建议：分钟线同步成功后触发切片级 snapshot materialize。失败不回滚 raw 数据，只让 snapshot 保持旧值并记录失败。

5.1 触发时机

  1. stk_mins 某个 trade_date + freq 的业务数据提交成功。
  2. 进入一个独立的 snapshot materialize 步骤。
  3. 按该日该频率重建一行快照，使用 UPSERT 覆盖。

5.2 为什么不用“边写 raw 边增量累加”

  1. 分钟线任务可能重跑、补跑、局部覆盖，边写边累加最容易重复。
  2. 快照行很小，单日重算成本可控，幂等性更强。
  3. 把“原始写入”和“业务快照产出”拆开，排障更清楚。

6. 页面读取链路如何改

6.1 具体读取口径

  1. 日级四卡与历史曲线：继续读 core_serving.equity_daily_bar。
  2. 分钟曲线：改读 snapshot 行的 points_json。
  3. 最新分钟线可用日期：改读 snapshot 中 build_status='READY' 的最新交易日。
  4. 页面不再执行 max(trade_time) 或 raw 分钟聚合。
  5. 明确不保留 raw fallback。snapshot 不可用时，模块直接按 delayed / empty / error 语义暴露。

7. 幂等、恢复与回补规则

场景 处理方式 原因
同一天同频率重跑 按主键 UPSERT 整行覆盖 避免增量累加污染
分钟线局部重写 重新物化该 trade_date + freq 切片 快照必须和 raw 保持同一切片一致
物化失败 不回滚 raw；snapshot 保持旧值并记录失败 观测失败不能污染业务数据
历史回补 支持按日期范围重建 snapshot 便于补历史分钟线后统一修复页面事实源

8. 对现有 API 与模块的影响

  1. /api/v1/wealth/market/turnover 的外部契约可以保持不变。
  2. 内部查询实现需要改：分钟曲线与 observed minute date 从 snapshot 读取。
  3. pageStatus / moduleStatus 仍按原语义输出，不需要前端改字段。
  4. 这次不需要改 TaskRun 模型、不需要改审计模型、不需要改 wealth API 命名空间。

9. 主要风险

工程风险

  1. 如果 snapshot 产出链路没有和分钟线同步成功点绑定，会出现 raw 已新、snapshot 未新的短暂不一致。
  2. 如果仍保留 raw fallback，会让系统重新回到“有时快、有时超时”的不稳定态。
  3. points_json 结构一旦定下，后续改动要控制版本。

缓解策略

  1. 明确 snapshot 是唯一分钟页面事实源，不允许 raw fallback。
  2. 物化任务采用“切片级覆盖”而不是“边写边加”。
  3. 保留 build_version 字段，后续 schema 演进可控。

10. 已确认决策

D1. 表名

已确认：core_serving.wealth_market_turnover_snapshot

D2. points_json 存储粒度

已确认：存该频率下完整的日内点序列，不只存页面当前固定点。

D3. 首期支持的频率

已确认：首期物化 1/5/15/30/60；90/120 暂不纳入，后续按配置扩展。

D4. 物化触发方式

已确认：首期只支持手动命令触发，不接自动触发。

D5. 快照主体类型维度

已确认：增加 type 字段，并纳入主键。首期固定写入 type=stock；后续可扩展到 index、 sector 等主体。

D6. raw fallback

已确认：不保留 raw fallback。页面只读取 snapshot。

D7. source_row_count

已确认：保留。该字段不参与页面展示，只用于物化结果对账、 排障和重建验证。

11. 建议落地顺序

  1. 补一份编码前门禁文档，限定“只改 turnover minute snapshot，不碰其他模块”。
  2. 先建表与手动物化命令，再补切片级重建与验证链路。
  3. 再改 turnover 查询链路，彻底切到 snapshot 读取。
  4. 最后做页面回归，确认彻底去掉 raw 分钟在线聚合。
