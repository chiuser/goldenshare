# 上证指数详情页日线接入方案 v1

> 状态：待评审 · 2026-11-05
>
> 范围：上证指数（`000001.SH`）普通日K、七条MA及BOLL、MACD、KDJ、同页九转和趋势通道，以及股票和指数普通日线图表请求量统一。
>
> 本文记录接入设计。代码级细节见[指数详情 LLD §27](index-detail-low-level-design-v1.md#sse-daily-kline-integration)。所有开发开始前，先完成 Figma 并核对实际节点，定稿日K分页和趋势日期范围的接口合同。

## 1. 目标与当前实现

股票和指数详情页的普通日线图表请求统一显式传500根，包括日K、日线九转和日线趋势通道。分钟线相关请求当前已是500根。已确认的历史缓存规则继续使用。后端指标接入仅限上证日K，从原行情行生成价格和量额，只把MA、BOLL、MACD、KDJ的16个字段换成内核结果。上证九转和趋势通道按当页实际日期取数。

| 环节 | 已核实的当前实现 | 本方案的接入位置 |
|---|---|---|
| 普通日K首屏 | 先请求 `page-init`，取 `asOfTradeDate`，再请求 `kline`。股票页面传300，指数页面传1000。 | 普通页面显式请求500，沿用原路由和回包结构。共享接口边界见第8节。 |
| 日K数据和随附指标 | 当前工作区的日K流程有本地DG和数据库两条读取分支，都会先取得行情和已保存的指标。 | 复用取数逻辑，由后端校验当页日期和四价，内核结果填入原指标字段。 |
| 九转与趋势 | 九转接受起止日期。上证趋势通道接口目前接受截止日期和上限。 | 首屏沿用原触发时机，只改请求量为500。历史日K成功后，用实际首末日期请求同页图层，趋势接口补起始日期。 |
| 图表 | 数据数组改变会重新创建日K、MACD、成交量和KDJ四张图。当前拖动到最早位置后，可见范围会被固定在边界。 | 历史左插在原图实例上更新，按交易日期保持可见范围。重试取自用户真实拖动，即使已经拖不动。 |
| 计算内核 | 现有服务通过 `PriceSource` 接收输入，现有 Lake 读取实现没有指数日线。 | 增加上证指数日线输入，直接复用当页K线。需要预热时，内核只向本环境补读缺少的前置K线。 |

代码依据见 [首屏控制器](../../../src/features/index-detail/controller/useIndexDetailController.ts#L63)、[指数日K路由](../../../../src/biz/api/wealth/market/index_detail.py#L132)、[日K两条读取分支](../../../../src/biz/queries/wealth/market/index_detail/index_detail_kline_query_service.py#L86)、[图表更新](../../../src/shared/charts/detail-workspace/DetailChartWorkspace.tsx#L654)和[内核当前取数规则](../../../../src/foundation/clients/local_lake/technical_indicator_contracts.py#L51)。

## 2. 产品交互

### 2.1 首屏与继续查看历史

1. 点进上证指数详情页后，沿用当前日期选择逻辑。通常由 `page-init` 给出最新有行情的交易日。从指定日期进入时，仍使用该入口确定的 `asOfTradeDate`。从这天往前最多取500根。若 `page-init` 已明确无行情，则直接沿用首屏空状态。
2. 用户向右拖动图表，查看更早的行情。以最左侧可见的交易日为准，从这根数到缓存最早一根，两端都计入。**剩100根或更少时**，提前请求下一页。缓存有500根时，最新为第1根，第401根是首次触发位置；接成1000根后，对应第901根。一次快速拖动跨过阈值，也只请求当前下一页。
3. 下一页只取更早日期，例如首屏第1～500根、下一页第501～1000根。已加载的数据继续保留。用户在缓存覆盖范围内查看时，直接使用缓存；仍有更早历史时，只有用户拖入新的预取范围才发起下一页。图表因接入新数据而调整自身位置，也只更新显示。
4. 旧页在请求途中，用户若已拖回较新的日期，回包只存进缓存，画面保持原样。再次向历史拖动，进入当前图表左端剩100根的范围时，先用已有缓存补图。比如缓存已有第1～1000根，图上仍只有第1～500根，拖回第401根时只从缓存补图，拖到第901根才请求下一页。用户若还在历史一侧，接上旧页时保持回包当下正在看的交易日期和缩放，让同一次拖动可以继续。

### 2.2 左端与异常

| 情况 | 用户看到什么 | 页面动作 |
|---|---|---|
| 下一页在后台加载，用户还未拖到最早一根 | 图表照常 | 等待当前请求。 |
| 下一页尚未回来，已拖到最早一根 | 最早K线左侧显示「加载中」 | 停在当前左端。数据到达时撤下提示，接入左侧。 |
| 历史页失败 | 到左端时显示「加载失败」。若已拖回较新日期，保留当时的视图；当前请求的后端日期或四价错误仍弹出具体提示。 | 保留原图和缓存。下一次继续向右拖、试图越过左端时，用原日期重试；每次新手势最多触发一次，无回弹动效。 |
| 历史页成功，返回1～499根 | 接上本页已有数据 | 标记已到最早，后续拖动使用本地数据。 |
| 历史页成功，返回0根 | 原图照常 | 撤下等待提示，标记已到最早，原图无需重绘。 |
| 首屏成功，返回0根 | 使用现有「暂无指数日线数据」页面状态 | 结束加载。首屏查询失败则走现有页面错误状态，后端报告日期或四价异常时同时提示具体原因。 |
| 切换指数、日期，或离开页面 | 以当前页面状态为准 | 取消旧请求；迟到的成功、失败和收尾回调均丢弃。 |

首屏和历史页成功返回不足500根即到头。判断依据是后端成功返回的 `bars` 根数。恰好500根且后端给出下一页截止交易日时，下一次用户拖到阈值才正常请求更早一页。如果下一页返回0根，就结束加载。

## 3. 请求与上下游合同

### 3.1 普通日K

| 请求 | 参数 | 回包和衔接 |
|---|---|---|
| 首屏 | 现有 `GET /api/v1/wealth/market/index-detail/kline`，带 `tsCode=000001.SH`、`period=day`、`endDate=page-init.asOfTradeDate`、`limit=500` | 日期从早到晚。实际首末日期取自 `bars`，`meta.endDate` 仍表示本次请求的截止日期。 |
| 更早一页 | 同一指数和周期，`limit=500`；`endDate` 使用上次成功回包给出的下一页截止交易日 | 后端用同环境交易日历，给出本页最早一根之前的上一交易日。最早一根若是周一且上周五开市，下一页直接传周五。 |
| 重试 | 沿用失败请求的指数、周期、截止日和上限 | 仍是当前最早日期之前的同一页。成功后才推进缓存边界。 |

一个页面同时只发一个日K历史页请求。股票、指数的普通日线请求都显式使用同一个500根页大小，预取阈值为100根。指标计算分支由标准化的指数代码和内核单次容量确定，见第8节。股票既有日线九转、趋势的触发条件和缓存沿用原流程，本次统一其请求量。 [股票接入方案 §9.3](../../../../docs/architecture/technical-indicator-kernel-stock-daily-api-integration-plan-v1.html#stock-daily-frontend)

回包入缓存前核对指数代码和日线周期，并与发请求时记录的页面编号、首屏截止日、当前请求编号和本页截止日对应。历史页的 `meta.endDate` 对应的是该历史请求。用户从上证切到沪深300再切回上证，第一次打开上证时发出的回包也属于旧页面。页面取消是为了尽早停止请求，编号检查用于挡住已经在路上的旧回包。

### 3.2 后端负责日期和四价完整性

- 日K服务在返回成功前统一核对同一指数的日期范围、日期唯一性和顺序，以及开盘、最高、最低、收盘是否为可用的有限数值。发现异常时整页失败，错误信息带指数代码、出错交易日期和具体原因，例如「000001.SH 2026-10-15 收盘价缺失」。建议沿用现有 `ID_QUERY_FAILED` 和错误消息传递方式，页面直接弹出消息。后端记录同一请求的诊断信息，供按错误日期追查。
- 日期核对要覆盖整根缺失。例如周三应有行情，但数据漏了，查询又用更早一天补满500根，后端仍要指出周三缺失。优先复用当前请求已有的交易日和行情信息，区分休市、确实没有更早历史和行情缺失。LLD 写明日期依据和检查位置。
- 上证普通页面使用交易日作为截止日。仍传入休市日的直接调用，按截止日及之前最近的交易日判断数据状态，原请求日期保留在 `meta.endDate`。分页所需的上一交易日与 `pageContext.prevTradeDate` 分开，字段及短页规则见 LLD §27.2。
- 成功回包保持当前 `bars` 及指标字段，合法的指标空值保留。前端只做回包归属检查并处理成功或错误，行情日期和四价的完整性由后端承担。历史回包只补图表缓存，首屏的行情日期、右栏摘要和页面状态仍来自首屏。

参考 [指数日K合同](index-detail-api-contract-v1.md)、[错误码登记](../../system/exception-code-registry.md)、[前端错误读取](../../../src/features/index-detail/api/indexDetailApiClient.ts#L85)和[当前指数API回归样本](../../../../tests/web/test_wealth_index_detail_api.py#L40)。

### 3.3 九转与趋势通道

首屏沿用现有时机。趋势在 `page-init` 后照常发起，九转按当前页面逻辑触发，两路只把请求上限改为500。趋势先回来时暂存在首屏状态，日K回来后按实际K线日期绘制。首屏结果由主图和右栏共用。

历史日K成功且有K线后，两路图层以该页 `bars` 的实际首末日期并行请求。比如最后一页有200根，两路仍传500作为上限，日期范围覆盖实际的200根。

| 图层 | 查询规则 | 页面使用 |
|---|---|---|
| 九转 | 现有 `GET /api/v1/wealth/market/index-detail/nine-turn`。首屏只改 `limit=500`，历史页传同页 `startDate`、`endDate` 及 `limit=500`。 | 按日期放置标记，只有出现计数的交易日才有标记。首屏最新九转摘要复用首屏响应，旧页标记只补图。 |
| 趋势通道 | 现有 `GET /api/v1/quote/detail/trend-channel` 增加可选 `start_date`。首屏只改 `limit=500`，历史页用包含首末日期的范围和 `limit=500` 截取现有计算结果。显式起始日晚于显式截止日返回 HTTP 400。省略起始日期时沿用现有调用行为。 | 按日期接入趋势点，缺点的日期留空。追加历史趋势时保留用户选择的叠加项和首屏趋势摘要。 |

日K的成功回包用于判断到头。历史空页不触发图层。历史图层按页面、日期范围和图层登记，在途和成功的请求由对应显示位置复用。九转或趋势单独失败时，在对应图层提示并重试原请求，已成功的日K和图层继续显示。

参考 [九转查询](../../../../src/biz/queries/wealth/market/index_nine_turn/index_nine_turn_query.py#L23)、[趋势通道接口](../../../../src/biz/api/quote.py#L123)和[趋势通道计算与截取](../../../../src/biz/services/quote_trend_channel_query_service.py#L181)。

## 4. 缓存和图表如何衔接

- 同一次打开只保留一份业务缓存，以交易日期存日K、随附指标和辅助图层。图表记录当前显示区间、缩放和正在拖动的位置。旧页回包时若用户已拖回较新位置，只更新缓存；之后拖回历史侧时才更新图表。
- 左插时保留原四张图实例，在已有数据序列上调用 `setData`。以更新前实际可见的交易日期和缩放恢复四图的共同范围。左插会改变数组下标，所以正在进行的拖动也要按更新后的日期位置接续。趋势追加时保留当前 MA、BOLL 或趋势的选择。
- 浏览器在上证页面分别验收用户仍在向历史拖动时回包和已经拖回较新日期后回包，观察可见交易日、缩放、十字线和拖动是否跳变。
- 当前图表在到达边界后会固定可见范围。左端失败重试应读取新的真实拖动手势，以识别继续向右拖的意图。单次手势内即使收到多次移动事件，也只重试一次。

参考 [拖动边界](../../../src/shared/charts/detail-workspace/DetailChartWorkspace.tsx#L552)、[四图更新](../../../src/shared/charts/detail-workspace/DetailChartWorkspace.tsx#L654)和[主图叠加项](../../../src/features/index-detail/chart/IndexChartWorkspace.tsx#L41)。

## 5. 上证日线接入计算内核

1. **当页直接复用。** `IndexDetailKlineQueryService.build_kline()` 复用原行情读取并校验。合法空页直接返回。有行情时，App 为本请求创建 `PriceSource`，把现成的交易日、最高、最低和收盘交给内核。同一页一次提交MA5、10、20、30、60、90、250，以及BOLL、MACD、KDJ。用不复权的指数点位计算，结果只覆盖当页日期。
2. **预热由内核补读。** 通过现有 `PriceSource` 接入上证日线。内核先确定需要多少前置历史，已在请求内的数据直接用，只补读缺少的、更早的K线。后端本地运行时读DG，生产运行时读Prod PostgreSQL。补读沿用该环境现有的上证日K读取方式和价格口径，只取交易日和高、低、收。历史确实到起点时按现有初始化规则处理，缺数据或读取失败按错误处理。每次请求使用自己的输入和读取位置。
3. **回填后走原检查和原映射。** 先逐日核对内核结果和 `rows`，再把16个结果写回原行中对应的指标字段。MACD的 `hist` 写入 `macd_bfq`，KDJ的 `j` 写入 `kdj_bfq`。回填完成后，继续调用现有缺项检查和 `build_kline_bar()`。均线缺项检查需要的前置有效收盘根数复用本次输入。价格、量额、涨跌等字段用原行生成。内核原有 `price` 输出能力保留，本次业务只使用四组指标结果。日期对不上、结果字段不齐或计算失败时，整页报错。
4. **指标数值验收采用新旧对照。** 用上证的同一批交易日，把原路径读到的16个指标值和内核结果逐日、逐字段对照。两边按同一规则舍入到小数点后两位，结果必须一致。日期、字段、根数及空值位置也必须一致。两位精度只用于验收，实际计算及API输出沿用各自现有精度。发现差异时记录交易日、指标、旧值和新值。

参考 [日K取数与缺项检查](../../../../src/biz/queries/wealth/market/index_detail/index_detail_kline_query_service.py#L86)、[内核确定预热需求](../../../../src/foundation/technical_indicators/service.py#L135)、[数据交接接口](../../../../src/foundation/technical_indicators/sources/contracts.py#L138)和[日K字段映射](../../../../src/biz/services/wealth/market/index_detail/index_detail_field_mapper.py#L113)。

## 6. Figma 需要补齐的内容

沿用现有指数详情 Loaded 图表区 `417:42`、交互说明 `425:178` 和首屏 Empty `499:579`。首屏 Loading、Error 和其他完整页面状态沿用已有稿。新增或标注以下内容，确定后把新节点链接补到 LLD。

| 设计稿或交互说明 | 要画清楚的内容 |
|---|---|
| 日K左端「加载中」 | 用户已经拖到最早一根、旧页未到的画面。标出提示在最早一根左侧的位置，以及K线、横轴和其余三张图如何保持。后台预取而用户未到左端时，沿用正常画面。 |
| 日K左端「加载失败」及重试 | 保留已有K线，标明失败提示位置。用连续画面标注再次向右拖的触发方式、切换回「加载中」以及成功接入；无回弹。 |
| 行情校验错误提示 | 画出带指数代码、交易日期、原因的提示，以及历史页出错时仍显示原图的效果。首屏沿用完整错误版式，并给具体原因留出显示位置。确认长错误文案的换行及在较窄布局中的位置。 |
| 历史页接入前后 | 标注相同可见日期和缩放的对照。分别说明等待在左端时接入，以及用户已拖回较新日期时只更新缓存。 |
| 空结果、到头、辅助图层 | 首屏0根沿用既有无数据稿，历史0根维持原图。短页接完后停止加载。九转或趋势单独失败时在对应图层提示和重试，主图和已成功图层继续显示。 |

以原设计稿为视觉基准，并核对当前支持的较窄布局。已知节点来自 [指数详情页标杆需求](index-detail-benchmark-requirement-v1.md#L45)及[原页面实施方案](index-detail-implementation-design-v1.md#L95)。

## 7. 开发顺序与验收

| 步骤 | 内容 | 完成条件 |
|---|---|---|
| 1. 完成 Figma 与接口合同 | 按 LLD §27 补齐图表状态，定稿日K下一页截止交易日及趋势起始日期，并确定有界验收样本和读取上限。 | Figma 和接口合同均定稿，有界验收样本和读取上限已确定，然后开始后端或前端编码。 |
| 2. 后端接入 | 上证日K复用当页K线并调用内核，按原字段回填并校验。趋势补起始日期，九转复用已有范围参数。 | 核对当页只读一次，预热只补早于首根的数据。校验缺整根和缺四价。用原路径指标对照内核，逐字段两位小数一致。 |
| 3. 前端缓存与图表 | 普通股票及指数页面的日K、日线九转和日线趋势统一传500。接入上证日K首屏、续页和两路同页图层，按日期保持视口，处理等待、失败、重试和迟到回包。 | 核对两类页面实际请求量，验证上证500/100边界、缓存命中、短页和空页、两页日期衔接、图层独立重试及旧回包丢弃。 |
| 4. 首期验收 | 用上证真实 API 核对首屏与续页，并用慢回包场景检查图表和交互。 | 上证四组指标实际走内核，原行情与指标结构正确，图层按日期对齐，回包接入后可继续拖动。 |

当前调用链由 CodeGraph 的 `codegraph_explore` 和源码核对，覆盖日K路由、取数、指标输入及回包。一次有数据的上证日K页最多发三次日线业务请求，即日K、日线九转和趋势。首屏另有原 `page-init`，重试单独计。验收记录实际返回根数、复用的K线数和补读的预热根数。编码前依据实际查询及有界样本核定读取和耗时预算，纳入失败、续跑和最终验收。

## 8. 页面页大小和接口边界

股票及指数普通日线页面显式传 `limit=500`。股票日K API 仍按现行默认500、范围1～500处理。指数日K API 仍按现行默认300、范围1～2000处理。标准化后的 `tsCode=000001.SH` 且 `limit≤500` 时，非空日K页一次调用内核。直接请求上证501～2000根或请求其它指数时，从入口按现有查询处理。已经进入内核计算的请求如遇失败，按原错误合同返回。
