### 1.1 账务计算与数据运营平台的边界（用户已确认）

**交易助手自己负责账务校验、持仓与收益计算、每日账户快照以及历史重算；这些不是数据运营平台的数据集同步任务。**

1. 本期账务链路不创建、不依赖 Ops `TaskRun`、`task_run_node` 或 `task_run_issue`，不接入其 dispatcher、worker、任务队列、维护 action 或状态投影；不再保留“可选 Ops 观测 / 接入”的设计口子。
2. 用户账户、持仓、交易、资金、费用、闭环与收益快照是交易助手私有业务记录，不注册为 `DatasetDefinition` / `DatasetExecutionPlan`，不创建数据运营平台的数据集、同步计划或维护任务。需要业务表落库，不等于需要注册运营数据集。
3. 行情价格、交易日等外部事实通过已有数据服务只读消费；其上游数据生产与账户记账分开。不能因账务计算缺少行情而在记账请求中创建运营同步任务，更不能将个人账务写入公共行情表。
4. 必要的待重算状态、版本、进度和恢复记录由交易助手业务层管理，页面通过自己的业务 API 读取。后台计算不等于 TaskRun；保留恢复能力也不意味着要在交易助手内部再造一套通用任务平台。
5. App 只负责认证、会话、行情读取与交易助手执行能力的装配，核算规则仍在 Biz；不改变仓库依赖矩阵。执行方式按实际工作量选择最小方案，不因此新增独立微服务、worker lane、systemd 服务或消息队列。本次确认边界，不提前选定新的运行基础设施。
6. 后文涉及市场物化、Ops worker 的代码审计仅作为历史比较与“不直接复用”的证据，不是后续接入待办。日志 / 指标失败不得影响业务提交；业务重算状态本身的持久化失败仍按业务事务处理，不能被当作可忽略的日志失败。

本节取代修订 6—12 中“可选 Ops 观测”和“向现有 TaskRun 入口接线”的探索方向；未来若确需改变此边界，必须另行明确申请，不能借“继续技术方案”自行恢复。收益公式、产品功能和已批准 Figma 不因此改变。

## 4. 核算设计中已经可以确定的部分

1. 原始事实只有初始化、逐笔买卖、资金流水等用户有效输入；佣金与印花税均自动计算，不接受手工覆盖。账户费率独立版本化，更正保留审计关系，不无痕删除后续结果的依据。
2. 每个账户按日期处理，同日按股票汇总买卖数量与金额，同时保留每一笔明细。成本和资金核算不借助录入时间猜测真实成交先后。
3. 当日卖出成本按日初未分摊含费成本比例分配；再把当日买入含费成本加入未分摊池。动态摊薄成本单独使用累计买入投入减累计卖出净回款，不能替换未分摊成本池。
4. 当日结束数量为零才结束轮次；日内卖出又买回而日末仍持有不拆轮。历史修改后从最早受影响日期重算，不能混用新旧快照和闭环结果。
5. 期间收益金额按各轮期末费用后累计收益减期初对应值计算；初始化按其基线截断；期内已结束轮次保留终值。该金额与同版本日增量加总对账，不额外再加闭环利润。
6. 当前累计、单笔闭环、整轮、期间收益分别命名，不能共用一个没有范围含义的 `profitRate` 在各处自行解释。
7. 转出本身不产生盈亏，不因转出而删除本期已经参与的本金。转出后账户真实可用现金非负校验按已通过的 §9.4 执行；后续买入可用的复用额度按 PRD §12.1.1 第 19 项及本方案第 6 节计算。

### 4.2 账户账务逻辑模型与唯一性

下表明确要保存的事实、关系和约束；对象名是方案用语，最终表名、SQL 类型和索引 DDL 留给 LLD。本轮先展开账户账务，计划、提醒及机器人仅明确归属关系，不声称其完整模型已完成。

| 对象 | 必须保存的信息及关系 | 唯一性 / 修改边界 |
| --- | --- | --- |
| 交易账户 | 账户 ID、所属用户、账户名、券商名、初始化日期、当前期初版本、当前费用版本、已接纳事实版本、计算目标版本、已发布结果版本 | 账户 ID 是身份；不以券商、账户名或未采集的资金账号做身份。不新增账户数量限制或“全部账户”实体；事实版本与计算目标的区别见 §4.6.1 |
| 期初资产版本 | 账户、版本、初始化日期、初始现金、修订来源；下挂期初股票明细 | 一个账户每一版本只有一个现金基线；修改创建新版本并保留旧版，不伪造入金流水 |
| 期初股票明细 | 期初版本、股票代码、总持仓股数、初始可卖股数、含费成本价；含费投入由数量乘成本确定 | 同一期初版本、同一股票一条合并持仓事实；重复股票不得静默重复计入；不是逐笔历史成交。不持久化另一个可由差额得到的“初始不可卖量”输入 |
| 账户费用版本 | 账户、版本、佣金率、最低佣金、印花税率、创建时间与生效记录顺序 | 不可变；账户只切换当前版本。两项费率均按新交易首次接纳时选定，不按成交日期倒查；修改不更新旧流水或其历史派生结果 |
| 账务流水修订 | 稳定流水 ID、修订号、账户、接纳事实版本、类型、业务日期、有效 / 作废状态、备注、来源修订及录入时间 | 一个逻辑流水可有多个不可变修订；当前查询只选该事实版本下最新修订，再排除作废。不能先按股票 / 日期筛选再挑最新修订，否则改股票或日期会让旧记录“复活” |
| 买卖专属字段 | 股票、方向、价格、股数、成交金额；首次接纳的账户费用版本与三项配置快照；系统计算的佣金和印花税 | 两项费用均无手工覆盖值、手工来源或人工确认字段；买入税额为 0，仍保存当时税率依据。客户端不能提交费用或逐笔费率；资金流水无股票费用字段 |
| 资金专属字段 | 转入 / 转出类型、日期、正金额；账户关系来自流水 | 不建账户转账配对、来源账户或去向账户；入金不生成收益，出金不扣减收益 |
| 记账操作回执 | 当前用户、请求标识、操作类型、目标对象、规范化请求摘要、受理结果、产生的流水 / 版本标识 | 用户 + 请求标识唯一；同请求同内容返回原结果，同请求不同内容拒绝。不同请求的相同成交允许独立保存；不是按成交内容自动去重 |
| 账务派生版本 | 账户、计算目标版本、源事实版本、计算规则版本、状态、计算范围、发布标识；涉及估值时另记行情依据、截止时点与费用依据 | 事实接纳与派生发布分开；只有完整校验后的版本可作为当前结果。失败不能指向未完成版本；分批及发布见 §4.6 |
| 持仓轮次 / 数量成本结果 | 账户、股票、轮次、所属派生版本、开始 / 结束日期、余量、未分摊含费买入成本、累计买入投入、累计卖出净回款 | 同一版本中一只股票最多一轮未结束持仓；保存可重建的数量成本状态，不保存单股当前 / 每日收益率。日内卖出又买回、日末仍有仓按 §4 第 4 项不拆轮 |
| 逐笔闭环结果 | 所属派生版本、来源卖出流水及修订、轮次、卖出股数、分摊成本、净回款、收益金额 / 收益率 | 每个有效卖出在一个完整派生版本中恰好一条；同日两笔卖出必须两条。不独立编辑；更正后旧结果仍可追溯，但不混入当前结果 |
| 每日账户快照 | 账户、业务日期、所属派生版本、估值依据与状态，以及 PRD §12.2 的账户级汇总 | 一个账户、一个日期最多一个当前有效版本；不新增单股收益率表和周 / 月结果表。当前累计与当天新增收益分别保存，不能共用含糊字段 |

采用“结构化流水 + 不可变修订 + 可重建结果”，不引入通用事件溯源框架。买卖与资金可以共用流水标识、版本和审计机制，但必须有互斥的类型校验；不能用一个任意 JSON 载荷绕开股数、日期、金额和费用约束。业务日期用于核算；录入时间、修订号仅用于审计和稳定展示，不能代表真实成交先后。

§4.6 补充业务重算需求、批次游标 / 执行权、日封存结果及完整日期清单等执行记录。它们服务于上述派生版本，不是新的原始账务、用户配置或收益口径；一代查询可经清单复用兼容的旧日结果，不要求复制每条旧闭环。物理引用必须能追到结果的原计算代次与当前发布上下文，不能将“当前派生版本”误实现为每张表单独取最大版本号。

关系边界：交易计划归属具体账户和用户，独立提醒归属用户；条件版本下挂检查 / 触发证据，发送记录关联触发和实际使用的机器人配置版本。机器人候选、已确认配置、测试记录按 §7 分开。它们不成为账户流水的子类型，不持有“自动生成交易”入口；配置变更对未触发计划的引用策略、发送状态与完整唯一键仍待通知专题设计，不在此静默选定。

### 4.3 写入、并发与失败处理合同

#### 4.3.1 版本读取与短事务提交

每次变更分为“核验候选内容”和“接纳事实”两步。不能边修改当前有效流水边试算，失败后再靠补写修复。

1. 从认证上下文取得用户身份，验证具体账户所有权；流水、更正目标、费用版本和期初版本均须属于该账户。“全部账户”标识不得进入写命令。
2. 读取账户的已接纳事实版本与不可变输入，形成候选变更。按日期和股票做日级核算，验证受影响日期及其后的现金、数量、T+1；改动日期时从新旧日期较早者开始，改动股票时覆盖新旧股票，但现金始终在整个账户范围验证。只用已登记事实，不预支未来补录。
3. 核算不持有长期账户行锁；读取固定事实版本，不能一边翻页一边混入后来接纳的修订。完成候选验证后，进入短写事务，锁定所属账户并复核事实版本、目标修订与费用版本；若已变化，候选失效，不能继续写入旧余额或旧费用结果。账户版本变化后重新核验最新事实，若现金已不足，仍按金额字段错误返回；目标流水修订已变化则拒绝覆盖。重验次数与请求时间预算须在性能章落定，不能无限重试。
4. 同一事务保存本次有效事实修订、必要的费用快照、账户事实版本推进、重算需求以及操作回执；这几项要么全部接纳，要么全部回滚。这里的重算需求是保证账务结果可恢复的交易助手业务状态，不创建 Ops/TaskRun 记录。当前派生结果保留原版本并标记待重算，不能因事实写成功就标记收益已就绪。
5. 提交前生成并校验确认响应，只返回已接纳的标识、事实版本与结果状态。提交后不再靠可能失败的补查来决定这次记账是否成功；完整页面查询是独立读取。网络响应丢失后的处理见 4.3.3。
6. 重算完成后才发布完整派生版本；发布时复核源事实版本，落后的任务不得覆盖更新结果。失败保留已接纳事实和旧完整结果的追溯依据，用户看到重算中或失败，而不是混合新旧账。派生重算的分批、恢复和发布合同见 §4.6，接纳前候选校验见 §4.7；不在 Web 请求中持有覆盖全历史的大事务，不能用后台重算替代合法性校验。

只有候选验证与接纳完成才算该次账务保存成功；行情缺数只影响估值与收益就绪，不能伪造行情补齐。现金、数量校验无需估值价，但 T+1 的交易日依据必须可靠；无法确定交易日时不能以自然日代替。行情与交易日可用性仍须专项核验。

#### 4.3.2 各操作的持久化边界

| 操作 | 接纳前必须核验 | 一次接纳保存什么 / 后续动作 |
| --- | --- | --- |
| 三步初始化完成 | 账户名、券商名、费率、最低佣金、现金与每只初始股票全部合法；同股票不能重复计入 | 一个账户、第一版费用、期初资产及股票、操作回执一次提交；没有历史成交或初始化佣金。界面填到中间一步不创建有效账户 |
| 新买入 / 卖出 | 日期、价格、数量、同账户有效事实的现金与 T+1；锁后确定本次新交易采用的费用版本 | 一笔新的逻辑流水及第一修订、逐笔费用快照、事实版本与回执；派生重算每笔卖出一条闭环，不合并同日明细 |
| 资金转入 / 转出 | 正金额；转出按当前已登记现金和受影响历史日期复验，不能让账户为负 | 一笔独立资金流水；无股票、无费用、无另一账户配对；重新核算现金与期间本金但不新增收益 |
| 更正 / 作废原始流水 | 目标所属账户与预期修订未变化；替换或排除旧修订后重新验证后续现金与 T+1 | 同一逻辑流水新增修订，保留来源和已有备注信息；只接纳合法候选，失败保留原有效版本；更正不生成第二笔有效成交，不新增用户必填的作废原因字段 |
| 修改账户税费配置 | 当前用户、账户与预期版本匹配；佣金率、最低佣金、印花税率合法 | 有变化才新增费用版本并切换当前引用；同事务保存配置回执，不推进历史账务重算目标。旧流水、现金、闭环及历史快照不动；当前估值按独立估值依据处理，不回写旧快照 |
| 更正初始化 | 新期初版本合法，并验证初始化之后全部受影响事实 | 原子切换到新期初版本、推进事实版本并记录重算需求；失败不改变原基线，不静默修复超卖 |

佣金与印花税共用“首次接纳新交易”的费用版本选定顺序，不按成交日期匹配另一费率。相同请求重试沿用原已接纳交易快照；配置保存后补录较早日期的新交易也使用新版本。历史成交信息更正保留首次接纳的两项费率与最低佣金，对更正后的金额和方向自动计算；账户仅改费率不改变旧交易费用。买入税额为 0，卖出按原快照税率计算，不增加人工费用确认分支。

**税费输入与生效门禁：**买卖录入、更正、详情中的佣金和印花税均只读，不设计费用修正命令；请求如携带佣金 / 税额覆盖值或逐笔税率必须拒绝，不能静默忽略。账户配置由同一短锁 / 版本校验确定与交易接纳的先后顺序；新交易候选配置过期则重验现金，旧请求重试不升级费用版本。设置保存失败或取消不能切换版本。当前持仓的预计卖出税费继续使用估值时固定的账户配置，不是旧交易费用；不回写历史成交或历史快照。

#### 4.3.3 幂等与提交结果不确定

- 客户端为一次明确提交生成请求标识；请求未完成期间重复点击不生成新标识。同一用户、同一标识携带相同规范化请求时，服务端返回同一操作结果；不同内容复用同一标识时拒绝，不覆盖旧请求。
- 幂等键不能是“股票 + 日期 + 价格 + 数量”。用户确实录入两次相同成交时使用不同请求标识，应形成两笔流水、分别收取费用，卖出分别形成闭环。
- 创建账户尚无账户锁时，用用户与请求标识的唯一约束确保同次初始化只生成一个账户；不把同名账户自动当成重复提交。已有账户的写入使用账户行锁及版本复核，不跨账户抵扣现金或数量。
- 确认未提交的失败不产生有效账务修订；失败审计或请求回执不是交易。提交时断连、超时或成功响应无法解析，客户端只能判为待核验，不能声称失败、清空表单或换新标识盲目再记一笔。
- 服务端以相同请求标识读取或重放原请求，已存在成功回执时返回原结果；未发现回执也不能仅凭一次查询就断言失败，因为原事务可能仍在提交。再次接纳仍需经过同一唯一约束与账户版本检查，最终只能有一个成功结果。
- 更新同一流水的两个不同请求必须带预期修订；后到者若目标已经更正，应提示内容已变化，不能无提示覆盖前一更正。明确错误、处理中和结果待核验的精确 API 码及用户状态映射在接口章节冻结，不直接新增一套未经评审的页面。

#### 4.3.4 读取与外部副作用

原始明细读取最新已接纳事实，派生值读取同一已发布结果版本，两者的版本差异必须显式成为重算状态。持仓列表、条形图、饼图、盈亏地图共用同一结果上下文；账户摘要、曲线、日历和下钻不得将旧闭环与新快照拼成 Ready。多账户读取保留各账户版本集合和共同估值截止，任一账户缺数或重算不能被汇总掩盖。

#### 4.5.1 闭环成本分币分配与剩余成本承接

计算范围固定为“账户 + 股票 + 交易日期 + 有效事实版本”。先由 T+1 校验确定合法卖出数量；当日新买入既不补充可卖量，也不进入当日卖出的日初成本。所有输入费用先按逐笔规则确定，再进行成本分配。

**计算步骤（使用整数分及整数股，避免循环小数误差）：**

1. 设日初未分摊成本为 `P` 分，日初持仓 `Q` 股，当日各笔合法卖出股数为 `q_i`，合计 `S`。要求 `0 < S <= 可卖数量 <= Q`、`P >= 0`；没有卖出则跳过分配，不执行除法。
2. 当日应分摊成本目标 `T = HALF_UP(P × S / Q)`，单位为分；取商与余数比较实现半入，不先生成两位单位成本。若当日卖完全部日初持仓，`S = Q`，因此 `T = P`，不会留下成本尾数。
3. 每笔先取其精确比例的整数分部分：`base_i = (P × q_i) // Q`，保留余数 `rem_i = (P × q_i) % Q`。待分配分数 `R = T - Σbase_i`，必须为 0 到卖出笔数之间的整数。
4. 按 `rem_i` 从大到小排序，余数相等时按来源流水的稳定逻辑标识升序；前 `R` 笔各加 1 分，其他不加。结果为最终闭环分摊成本 `cost_i`。该排序仅用于分币破平，不代表真实成交顺序，不使用前端排列、请求遍历顺序、修订生成时间或重算生成的闭环 ID。
5. 同一有效事实集合和稳定来源标识，不论读取批次或输入排列如何，`cost_i` 映射必须一致。来源事实新增、作废、股数或成本变化则重新计算整个受影响日组，不能只改一个闭环行；金额完全相同的两筆真实卖出仍各有独立来源标识和闭环，不为去尾差合并成交。
6. 各笔已实现利润 `profit_i = sellNet_i - cost_i`；闭环收益率以该最终 `cost_i` 作分母。日末未分摊成本 `P_next = P - T + 当日买入含费成本之和`，日末持仓 `Q_next = Q - S + 当日买入数量之和`。次日使用这份已经对账的剩余成本，不再从两位单位成本反推；同日卖完旧仓又买回时，成本池只承接新买入投入，持仓轮次仍按日末是否归零确定。

必须同时证明：`Σcost_i = T`、未分摊成本非负、每笔最终分配与精确比例相差不到 1 分、清仓后成本池为 0、整轮全部闭环成本合计等于含费买入投入、整轮全部闭环利润合计等于累计卖出净回款减累计买入投入。每笔相对“独立 HALF_UP 理论成本”的调整至多 1 分，可能为 -1、0 或 +1 分；不能总把尾差全部堆给某一笔而失去比例边界。

**保存与使用：**在日级成本分配依据中保留所属版本、日初成本 / 数量、卖出总量、目标分摊成本及分配规则版本；各闭环关联其来源流水，保存最终分摊成本和相对独立舍入值的分币调整。精确理论比例可由这些事实重建，不创建任意精度浮点事实源。物理字段和索引在 LLD 固定，前端只消费后端最终成本、利润与收益率；不新增用户尾差设置或手工调整流水。

该分币调整只重新分配已经存在的买入成本，不改真实现金、逐笔自动费用、轮次累计买入投入或卖出回款，不产生额外收益。跨期剩余持仓成本按 `P_next` 承接，当前持仓动态摊薄成本仍为累计买入投入减累计卖出净回款，不能改用本成本池。所有派生金额须使用同一规则版本重建，不能把旧闭环成本与新成本池拼在一起。

### 4.6 每日账户快照与历史重算（修订 11）

本节承接 PRD §6.3、§7.7、§12.1.1—12.4、§14 及本文 §4.2—4.5.1，展开**已经合法接纳的事实如何形成可查询结果**。不改变收益分子、单股 / 全仓分母、费用或 T+1；不增加用户操作、账户限制、后台管理页面或自动交易。接纳前校验仍遵守 §4.3，不能先保存非法账务，再寄望重算纠正。

#### 4.6.1 输入、触发与重算范围

一次计算固定以下依据：账户及所有者、已接纳事实版本、期初版本、计算规则版本、计算起止日，以及逐日估值所需的行情 / 交易日 / 费用依据。金额和状态必须能由这些依据重建；**只存 hash、不保留可读回的数据或不可变版本引用，不算输入冻结**。无历史版本能力的行情适配器须把本次实际使用的值、日期、来源及状态保存为估值依据，再计算；不能恢复时悄悄改读最新行情。

| 触发 | 最早受影响日与处理范围 | 不允许的处理 |
| --- | --- | --- |
| 首次初始化 | 从初始化基线起计算；初始化以前不生成账户收益历史 | 把已有持仓虚构为历史买入，或把初始化之前浮盈记为当天新增收益 |
| 新买卖、资金流水、更正 / 作废 | 从受影响日到本次固定截止日；日期更正取新旧日期较早者，股票更正覆盖新旧股票，现金与汇总覆盖整个账户 | 只重算改动股票当天，遗漏后续现金、轮次、成本分币、期间本金或已清仓闭环 |
| 初始化更正 | 从初始化基线重新验证和重建后续全部结果 | 沿用旧初始成本 / 可卖量检查点 |
| 新交易日数据就绪 | 从最后完整日之后推进；当天无买卖但仍持仓，也要估值并计算当天新增收益 | 仅有交易才生成快照，或把无买卖的持仓日计为没有收益 |
| 历史行情被修正 | 从最早受影响估值日重建，包含后续增量所依赖的前值；来源与新旧估值依据可追溯 | 覆盖底层价格却保留旧日收益，导致相邻日期累计差与日收益加总不一致 |
| 当前账户税费配置改变 | 更新当前估值的预计卖出费用依据；历史实际成交费用和历史估值当时采用的费用依据不套用新配置 | 因修改当前费率重新给过去每笔成交收费，或悄悄重写所有历史快照的预计费用 |

只有行情完整性与交易日依据满足对应日计算要求，才能形成正式日终快照，不以“已到收盘时间”代替数据就绪。当前交易日估算与正式日终快照分开标识；未完成周 / 月只计算到实际截止，不生成未来快照。缺数及停牌等具体估值取价仍须在行情章节核验，本节不擅自规定用前收盘价补齐。

初始化基线独立于日终快照保存；初始化发生在休市日期时，不把该日期伪造成交易日。日期清单覆盖已确定的有效快照日期，非交易日的日历格继续按 PRD §12.4 表达；不因它显示“待计算”就调度一个永远无法完成的交易日重算任务。

每个账户保存一个递增的**计算目标版本**：已接纳事实变化、有效估值依据变化或计算截止推进，都更新目标并持久化重算需求。它不同于账务事实版本，解决“流水没变但行情已经更正”的旧任务覆盖问题。该版本是技术一致性标识，不是用户配置。连续变更时，最早待重算日取所有尚未被当前完整结果覆盖的变更日期的最小值；不能以最后一次修改日期覆盖较早的待办范围。

#### 4.6.2 分批保存与日级检查点

业务封存单位是 `账户 + 计算代次 + 交易日`；代次记录固定输入、目标版本、范围、状态、完成日数、最后封存日和失败依据。同一目标只保留一个可推进的有效代次；失败后原输入仍适用则续跑，不制造另一套同时发布的结果。计算目标变更后旧代次退出发布候选，新代次重新确定范围。

代次状态依次为待领取、准备输入、计算中、核验中、待发布、已发布；等待数据、失败、已取消保留中断阶段及检查点，满足恢复条件后回到该阶段。目标过期进入已被替代，不得重新发布。状态转换与检查点同属业务持久化；这些是内部执行状态，不要求页面逐项新增同名状态或按钮。

**一个交易日不是无上限的大内存批次。**按以下阶段分页，并在每批前后检查取消和执行权：

1. **准备输入：**使用固定事实版本，先选每个逻辑流水的有效修订，再按日期 / 股票筛选，按稳定键翻页，不用 offset 扫描可变集合。逐批保存本代次使用的估值依据及同日股票买卖汇总、资金汇总；禁止将整段历史或全部逐笔记录一次载入内存。
2. **计算股票：**逐股票读取前一封存日的数量、未分摊成本、轮次累计投入 / 回款和初始化限制；当前日期的完整买卖汇总准备完毕后，才计算成本分配目标。大额明细页分批生成闭环，先保存 §4.5.1 的基础分摊与余数，再按余数及稳定流水 ID 排序分配尾差；不能每页各自四舍五入后拼合。没有买卖但仍持有的股票也参与估值。
3. **汇总账户：**股票计算批次全部完成后，分页汇总现金、持仓、闭环和估值依据，生成 PRD §12.2 的账户快照。跨期已结束轮次不丢失，日增量不重复加闭环利润；全仓日本金单独按 §6.4 的日窗口重置计算。
4. **封存当日：**读回确认输入页完整、每笔有效卖出有且只有一个闭环、股数 / 成本 / 现金守恒、费用与快照汇总可解释。通过后用短事务封存当日和推进检查点；下一交易日只能读取已封存的前日状态，不能读取半日计算结果。

每批的候选结果、累计器和游标在**同一个短业务事务**提交。批次唯一键包含代次、日期、阶段、股票（适用时）及稳定页边界；重复领取已完成批次须读回核对，不重复加汇总。部分写入失败整批回滚，已提交前批保留。恢复只从数据库已提交游标继续，不能从内存进度或 TaskRun 的“已完成数量”推断账务事实。

数量 / 成本 / 轮次检查点是重算依据，不持久化单股日收益率，不另建周收益表、月收益表。周 / 月及单股查询按固定版本读取所需事实和边界状态后计算；不能加总每日分母、平均日收益率或用期末是否持仓决定是否有收益。

**有界执行要求：**输入页、闭环写入页、股票状态页和读回核验页都必须有行数与字节上限；SQL、远程读取及批次必须有可中断的时间预算。峰值内存随一批记录及固定累计器增长，不随全历史流水或全部持仓数增长；同日余数排序交给持久化候选查询分页，不在内存汇集所有卖出。修订 14 的 §4.8.4 已列设计初值、唯一来源、消费者及生效方式，仍须经性能验证后冻结；不能在各服务散落另一套常量，不能以设计初值代替实测。

#### 4.6.3 完整结果发布与一致读取

从最早受影响日前最后一个**输入仍兼容的完整检查点**开始；不存在则从初始化重放。复用条件包括期初、核算规则及此前有效事实 / 估值一致，不能仅凭日期较早就认定可复用。

一个发布代次包含从初始化到固定截止日的完整**日期结果清单**，每个日期明确指向一个封存结果及其核算依据。未受影响的前缀可引用已验证兼容的旧日结果，其余日期全部指向新封存结果；清单直接引用日结果，不形成“旧代次再找更旧代次”的递归查询链。物理复用不等于混用两套口径：兼容性证明及整份清单才确定这一代的可见结果，不能查询时逐表挑最新行。

日期清单可分批保存，但全部日期、检查点、闭环、快照及估值依据完成读回核验后，代次才进入待发布状态。发布仅做一个短事务：锁定账户，复核当前计算目标、输入版本及执行权仍匹配，确认候选已完整封存，原子切换账户的已发布代次指针并记录发布回执。任一条件变化均拒绝旧任务发布；不能按表分别发布持仓、闭环和快照。

- 正式查询先获取一次结果上下文，携带账户、已接纳事实版本、计算目标、已发布代次、估值截止和结果状态。各图表、摘要、分页及下钻固定使用该上下文；新请求返回另一代时，前端整组更新或保持处理中，不单独替换某张卡片造成混合 Ready。
- 原始交易可展示已接纳事实，但其派生闭环和收益未追上时明确待重算，不用旧利润装成该新交易的正式结果。旧完整值仅可作为注明版本 / 时间的旧结果，不是当前有效值；PRD §14 的 Recalculating / Delayed / Partial / Error 按原因映射，精确 DTO 和组件承接留给接口章。
- 多账户保留逐账户的完整结果上下文和共同截止。不能把一个账户的新收益与它的旧本金混合；不同账户不要求同一个代次编号，但不得隐去某账户缺数或重算。周 / 月分子和分母在各账户独立算完再汇总，不跨账户复用现金。
- 正式每日快照的“唯一”是一个账户、一个日期只有一个**当前有效结果**，不是抹掉旧结果。更正后旧代次保留审计引用，未完成候选不进入正式查询；本轮不新增历史清理或删除策略。

#### 4.6.4 失败、接管、进度与运行边界

| 事件 | 必须保存 / 恢复的行为 | 页面及账务边界 |
| --- | --- | --- |
| 接纳事实后执行器尚未启动、进程退出 | 原事务保存的业务重算需求仍在，运行入口重新领取；不是靠提交后一次内存回调保证不丢任务 | 原事实仍已保存，相关派生结果待重算；不得要求用户重复记账 |
| 批次中断 / 重试 | 同目标、同输入、同批键续跑；已提交批次先读回，未提交批次重做 | 没有半批可见结果，也不重复闭环或费用 |
| 执行器被接管后旧进程恢复 | 每次领取有递增执行权标识；候选写入、封存和发布均在短事务内验证标识，旧持有者不能继续提交 | 不是只在启动时加一把锁，避免两个进程交错改候选结果 |
| 输入或核算对账失败 | 保存具体日期、阶段、失败原因与缺失依据；保留已提交候选及旧完整结果；只有输入不变且错误已排除才能续跑 | 不填 0、不假装未触发、不发布部分账户结果；计划检查状态不由此改写 |
| 必需行情未就绪 | 标记等待数据及缺失范围，等待就绪信号或有界检查后续跑；输入变化则更新目标 | 不无限紧循环、不以定时器到点当成数据完整 |
| 取消执行 | 每批前后检查；已提交批保留，不再领取新批，未发布仍不可见；恢复仍须校验原输入和目标 | 取消计算不撤销已经成功保存的交易。本轮不新增用户取消按钮，运营执行控制接线另行核验 |
| 发布提交时断连 | 读账户指针与同代次发布回执确定结果；已发布则幂等完成，不能无条件再发布 | 与账务保存的未知结果区分，不重复接纳交易 |
| 重算中又有更早日期变更 | 推进计算目标，合并最早待重算日；旧代次退出候选，已发布版本不倒退 | 旧任务即使算完也不得覆盖新目标；不能丢掉第一次历史更正的影响范围 |
| 日志 / 指标上报失败 | 业务批次、封存、发布事务照常独立提交；业务进度仍以已提交记录为准 | 不创建 Ops 状态投影；不能因日志异常回滚账务，业务状态保存失败则不能忽略 |

进度事实至少包括代次 / 目标、阶段、当前日期及股票或页游标、已封存日期数、固定总日期数、已提交批次数、最后业务提交时间、等待 / 失败原因。恢复同一代次的已完成量不倒退；新目标使用新代次并显式区分，不能混在同一个百分比里。日期完成率只表达已封存日数，不冒充所有阶段耗时比例；未知总页数或 ETA 时明确未知。长阶段必须分批并有可见状态更新，不能连续 30 秒无更新；心跳只证明存活，不能增加业务完成量。页面字段如何承接现有处理中状态须在 API / 组件对账中落定，不自行扩展 Figma。

核算服务、待重算状态和恢复记录位于 Biz 的交易助手私有领域，由 App 装配其执行能力与行情读取。按 §1.1，不接入 Ops/TaskRun、公共数据集或市场物化 action。执行唤醒、接管、退避与取消须在交易助手自身方案中明确，不能将“现有运行壳接线”解释为接入数据运营平台；不新增通用任务框架、消息队列或独立调度系统。

| SNAP-10 | 单日大量卖出、很多持仓、长历史 | 测量每批行数 / 字节 / 时间及峰值内存；成本分币跨页结果一致；取消响应和更新间隔满足预算，无覆盖全历史事务 |
| SNAP-11 | 当前估算转日终、改变账户税费配置、复用未受影响前缀 | 估算不冒充正式快照；不改历史成交费用或历史估值依据；复用前缀有输入兼容证据，每个账户日期仅一个当前结果 |

本节没有发现需要新产品选择的冲突，因此无需再向用户重问已确认的收益口径。验证边界是当前代码阅读和文档合同审计，**尚未运行上述 SNAP 功能测试、真实数据库故障注入或性能测量**。接纳前长历史校验已在修订 12 的 §4.7 展开；运行接线、行情证据、性能 / 配置预算及精确 API 仍须补齐，不能将本节写完表述为全部重算能力已通过验收。

### 4.7 保存前的账务合法性校验与执行衔接（修订 12）

#### 4.7.1 硬约束与最小计算范围

依据 PRD §7.2、§7.7、§9.4—9.4.1、INIT-06，以及本文 §4.3。**点击保存不等于账务已经接纳；校验通过也不等于提交成功；提交成功又不等于收益快照已经就绪。**三个阶段必须分别确认，不能复用一个含义不明的“完成”。

保存前只判断候选事实是否合法，不执行 §4.6 的估值、收益、闭环生成、分币分配或计划检查。校验读取用户有效流水、已确定的逐笔费用、期初数量 / 现金和可靠交易日依据；收盘行情晚到不妨碍现金、数量校验，但交易日无法确认不能假定通过。无账务变动日期不用逐日查行情或生成快照，T+1 仍按真实交易日和初始化日判定，不改成自然日计时。

| 校验内容 | 输入与计算 | 拒绝反例 / 后续测试 |
| --- | --- | --- |
| 当前转出余额 | 从固定有效事实算当前现金，不读取落后的持仓摘要；更正已有转出时先移除原修订的现金影响，再放入候选，不把新旧转出各扣一次 | 当前现金 1000、新转出 2000 拒绝；原现金 2000、已转出 2000，改为转出 1500 应形成现金 500，而非按旧余额 0 拒绝；VAL-01、08 |
| 历史现金 | 期初现金加按日期累计的转入、卖出净回款，减转出、买入含费金额；检查每个有资金变化日的日末值非负 | 周一入金 1000、周二买入花 900，将入金改到周三或作废后，周二为负，不能只看今天现金通过；VAL-02 |
| 股票数量 / T+1 | 每日先检查全部有效卖出量不超过当日可卖基数，再计算日末总量；初始化日使用初始可卖量，其后使用上个交易日末数量，同日买入不补可卖量 | 同日买入 100 再卖 100、初始化可卖 600 却卖 700 都拒绝；VAL-03 |
| 跨股票与日期更正 | 候选替换原逻辑流水；数量校验覆盖新旧股票，现金覆盖整个账户，从新旧日期较早者向后检查 | A 的买入改为 B 后，不能遗留 A 后续卖出；只查新股票不合格；VAL-04 |
| 并发与重复提交 | 固定事实版本验证；提交时在账户短锁下复核版本 / 目标修订 / 费用依据 / 请求回执 | 现金 1000 两个请求各转出 700，只能一个成功；同请求重试只接纳一次；VAL-05 |

“当前转出余额”和“历史现金非负”是两道校验，不相互替代。更正时的替换只发生在候选视图中，原流水在成功提交前保持有效；前端不能自行加回原转出推算可用现金。相同有效事实的日级结果与录入顺序无关，不等于允许尚未登记的后续回款预先支撑当前保存。

#### 4.7.2 固定候选、分页核验与可复用依据

1. **固定候选：**校验记录绑定用户、账户（已存在时）、同次提交请求标识、规范化输入摘要、基础事实版本、预期目标修订、期初版本、账务校验规则及所用费用 / 交易日依据。首次初始化尚无账户时以用户与请求标识隔离候选，期初和费用依据取本次输入。候选输入只作为待核验内容持久化，不属于有效流水、费用、账户资产或重算需求，也不占用现金和可卖数量。
2. **正确替换：**在基础事实版本下，先按稳定流水 ID 选有效修订，再排除被替换 / 作废的目标，最后叠加一次候选。之后才按股票、日期和类型过滤。读取范围不能先筛掉被改日期 / 股票的旧修订，避免同一逻辑流水出现两个有效事实。
3. **恢复起点：**只复用最早受影响日之前、与基础事实 / 期初 / 校验规则兼容的现金和数量检查点；不存在则从初始化计算。行情变化本身不使现金 / 数量检查点失效；账务或交易日依据变化则必须重验。不能要求收益快照先 Ready 才允许记账，也不能为提高速度直接信任旧派生余额。
4. **现金扫描：**账户有效现金事实按业务日期、稳定流水 ID 分页，用一个现金累计值和当前日累计变动检查日末非负。保存的是原始逐笔费用后的现金影响，不涉及本期复用本金桶。日期跨页时先合完该日期再判定日末，不能把一页暂时负值当作整日负值。
5. **数量扫描：**按受影响股票逐只扫描有效买卖日期，维护上日末数量、当日买入量 / 卖出量及初始化可卖基数；不在内存装入全部股票历史。新旧股票均检查到基础版本下最后已有相关事实，不能更正当天通过就省略后续卖出。初始化更正按股票分页覆盖全部受影响初始持仓及后续交易。
6. **分页持久化：**单位为候选 + 校验尝试 + 阶段 + 股票（适用时）+ 稳定页边界。每批只保存游标、当前日期累计器、已验证范围、依据摘要和错误定位，不生成正式闭环或收益。结果与游标同一短事务提交，未完成半日不能当完整检查点；页行数、字节和 SQL 执行时间均须受性能预算约束。
7. **完成证明：**保存已遍历范围、有效事实数量、输入摘要、最后日期及全部校验结论，不能以“没有抛异常”代表读到结尾。只有现金扫描与全部受影响股票检查完成，才允许进入 §4.3 的短提交；候选检查点始终不作为正式查询结果。

不做覆盖全历史的大事务，不新增通用事件框架或专用“校验队列”。这一方案减少的是校验所需字段和日期，不限制用户历史长度；页大小、请求预算和锁等待尚须在性能章测量冻结。若代表性长历史无法满足已批准的保存交互预算，必须停下讨论处理中的交互，不能偷偷改成“先保存成功，后台再判断是否合法”。

#### 4.7.3 中断、超时与并发重验

本期设计继续以用户的保存请求驱动接纳，不新增“关闭页面后后台自动审核并记账”流程。单次请求内分批核验；短暂中断保留隔离的候选检查点，同一请求、相同输入再次明确提交时，在重新鉴权及核对依据后续验。**状态查询只读，不因查询、刷新或后台恢复就接纳候选。**对合法原请求的网络重试仍采用 §4.3.3 的相同请求标识，不创建第二笔账。

| 情况 | 服务端必须怎样处理 | 对用户结果的限制 |
| --- | --- | --- |
| 校验得到明确非法结果 | 保存失败原因和字段 / 股票 / 受影响日期定位，不推进事实版本、不生成重算需求 | 保留表单；当前余额不足使用 PRD 原红字；历史关联错误须明确日期及原因，不误称服务器故障 |
| 提交前触发已知校验期限 / 取消 | 在短事务中封存本次尝试为已中断，并撤销它进入接纳事务的执行权；只有确认该尝试没有提交后，才能返回“未保存” | 不能将“未算完”说成输入非法；不清空输入。具体超时文案及重试状态待 API / 正式组件映射，不自行新增弹窗 |
| 同请求同时重试或接管旧尝试 | 同一请求只有一个可推进尝试；检查点复用前核对输入和全部依据，旧执行者每批及提交前均复核执行权 | 不会两个请求分别保存一次，也不能旧请求在返回未保存后迟到提交 |
| 账户被另一请求更新 | 旧完成证明失效；在单次请求预算内以新基础版本重新验证；目标流水已被他人改动则按预期修订冲突拒绝覆盖 | 不拿旧余额放行，不无限重试；保留用户输入，不擅自覆盖他人更正 |
| 校验时 / 提交前账户税费配置变化 | 新交易必须重新用待接纳时的费用配置核算现金，并复核其版本；更正历史交易沿用该流水已有费用依据 | 不在锁内悄悄换费用后沿用旧现金证明；成功请求重试仍返回原费用快照 |
| 客户端断连，服务端尚未确认停止或已进入提交 | 客户端只能判为结果待核验；原请求回执 / 同标识重试完成核对；数据库提交结果不确定按 §4.3.3 处理 | 浏览器 abort 不等于服务端撤销；不能断言未保存或立即换新标识 |
| 已经提交成功，之后快照执行失败 | 交易、费用、事实版本和业务重算需求都保留；只处理派生任务恢复 | 不将快照失败变为记账失败，不自动撤销交易或让用户重新录入 |

接纳前最终短事务核对所有者、基础事实版本、目标修订、费用依据、校验规则 / 交易日依据和当前尝试执行权，核对幂等回执，然后一次提交有效修订、费用、版本、重算需求与成功回执。版本不符不能只重算最后一步现金；读到当前交易日数据和其他行情不属于此事务。初始化成功前仍不产生有效账户；未成功候选通过用户与请求标识隔离，不能为校验方便先建立半个账户。

中断候选不是“后台待记账订单”。用户修改表单产生不同输入时，不得覆盖原摘要并复用旧证明；原请求若结果不确定，先核对原结果。隔离候选的保留 / 清理周期、确切状态字段和 API 错误码在配置及接口章统一审计，本轮不设隐含 TTL、不清理任何数据、不添加用户配置项。

### 4.8 交易助手自己的后台计算（修订 14，待整体评审）

这不是当前已有能力：本轮检查 `src/app/web/lifespan.py::web_lifespan`，目前只负责启动 / 停止日志；`src/app/web/app.py` 已将它注册为应用生命周期。拟由 App 在这一生命周期装配交易助手计算服务，业务循环、待办领取与核算留在 `src/biz/services/wealth/market/trading_assistant/`。该循环只服务本模块，不抽象成第二套通用任务平台。

#### 4.8.1 从保存到账目更新

1. **保存：**§4.7 校验通过后，交易修订、费用、账户版本、待重算状态和保存回执在同一事务提交。一个账户保留一个当前待办，后续更正合并最早受影响日期、推进目标版本，不为每次点击创建独立待执行交易。保存未成功的候选不进入待办查询。
2. **发现：**后台循环周期性检查到期的待办，不依赖保存后的内存通知。保存进程在 commit 后立刻退出也不会丢工作；不要求用户再点“重新计算”，关闭页面也不影响已经保存的账目更新。数据库为空时只做有界的待办检查，不扫描公共行情全市场。
3. **领取：**使用短事务选一个可执行账户，检查 `next_attempt_at` 与执行权有效期，以行锁跳过其他进程正在领取的账户；更新所有者、执行权序号和到期时间后提交。后续计算不一直持有领取锁，不把待办全表锁住。唯一性仍以账户和目标为准，不以股票或页面作为隔离单位。
4. **计算一批：**按 §4.6 的固定输入与已提交游标处理一批，提交候选结果和检查点，然后归还执行机会。待办按“到期时间、上次获得执行机会时间、账户 ID”稳定排序；尚未完成的账户重新排队，不能一个长历史账户连续独占全部时间。一次只从数据库领取实际准备处理的工作，不提前塞满内存队列。
5. **核对并发布：**全部日期结果完成读回对账后，按 §4.6.3 原子切换已发布代次。清除待办必须带匹配的目标版本条件；清除时发现用户已提交新修改，则保留更新目标，不能抹掉新的待办。
6. **页面读取：**保存回执表示交易已保存；收益未追上时使用既定重算状态。页面通过交易助手业务 API 获取进度与结果上下文，只在整组版本一致时更新正式值。轮询频率和具体组件状态留给 API / Figma 对账，不新增进度管理页、任务列表或取消按钮。

待办延续 §4.6 的业务状态，补齐领取必需的 `next_attempt_at`、上次执行时间、所有者、执行权序号、有效期及连续暂时失败次数。它们属于账户业务执行记录，不是原始交易，也不是新增 TaskRun 表；物理字段 / 索引在 LLD 明确，索引需支持到期待办查找及账户唯一性。

#### 4.8.2 不阻塞网页与多进程安全

App 生命周期启动一个异步协调循环；同步数据库读取与核算放入**本进程专用、并发数为 1 的线程执行资源**，每次只提交一个有界计算批次并等待其结束，不占用 HTTP 事件循环，也不复用请求线程池无限排队。采用现有 Python 标准库能力，不新增依赖或后台进程。数据库 `Session` 在执行该批的线程中创建、关闭，不能把请求 Session 或 ORM 实例跨线程传入。

这个线程不是 CPU / 数据库资源的完全隔离。持续重算仍可能增加 Web 服务负担，须做真实页面并发性能验收；没有证据不能承诺“完全不影响页面”。每批在行数、字节和时间任一预算到达后保存进度并让出执行机会，不在单次线程调用里把多年历史算完。

每个真正运行应用生命周期的 Web 进程最多有一个此类计算槽。若部署启动 N 个 Web 进程，就最多有 N 个槽，不能误称整个部署只有一个；本轮读取的 `src/app/web/run.py::main` 未显式传入 workers 数，不据此推断生产进程数量。进程扩容前必须重验连接池、CPU 和任务领取竞争，不能另用全局内存变量保证账户互斥。

每个写批、日封存和发布事务都验证账户 / 目标 / 执行权序号，时间依据使用数据库时间。过期被其他进程接管后，旧进程即使恢复也不能继续提交。新更正推进目标版本时，旧目标计算只能停止，不能沿用旧目标清掉待办或发布旧结果。业务行锁可能短暂竞争，锁等待必须受预算约束；“跳过已锁行”不等于其他所有事务都不会等待。

#### 4.8.3 启停、重试与日终发现

| 场景 | 首期设计 |
| --- | --- |
| 服务启动 / 重启 | 完成模块装配后扫描未完成且到期的业务待办；仍在有效期内的其他进程工作不抢占，过期工作按新执行权续跑。不会重新接纳交易或补写虚构流水 |
| 服务正常停止 | 先停止领取、发出协作停止信号，等待在途有界批次提交或回滚后再关闭执行资源；只在确认线程退出后释放本进程持有的执行权。不能取消一个异步等待就假装底层线程已停 |
| 进程被强制终止 | 已提交批次保留，未提交事务由数据库回滚；执行权过期后恢复。若提交结果不确定，按批次键与发布回执读回，不重复累计 |
| 暂时性数据库连接 / 锁超时 | 只对已分类的暂时故障延后重试，失败次数保存在业务待办中，重启不清零。若连失败状态也无法写入，则靠执行权过期与数据库恢复后重新读回，不能谎报已安排重试 |
| 行情尚未完整 | 按等待数据状态延后检查，不占着计算槽等待；数据未变不反复推进目标或从头重算。缺失股票 / 日期可解释，不计算成零收益 |
| 守恒失败、非法输入、规则 / schema 不匹配 | 停止这一目标自动重试，记录可定位原因、保留原始交易和旧完整结果；经修复核验后恢复，不把任何异常都当暂时网络故障重试 |
| 普通日志 / 指标输出失败 | 不阻断批次提交或发布。业务进度写入失败则按业务批次失败处理，两类失败不能混为一谈 |
| Web 服务整体停机 | 不承诺停机期间仍计算；服务恢复后从持久化日期游标与待办补算缺口，不只计算恢复当天。不能因此启用 Ops 或偷偷加独立服务 |

日终快照不能只靠用户记账触发。后台另有**有界的日终发现步骤**：保存已检查的行情依据 / 日期和账户分页游标，通过注入的行情与交易日读取能力确认有效日期的数据状态，再按账户分页生成或合并待办。一次只检查一页；无买卖但持续持仓的账户、刚清仓账户及现金账户的账户级快照按 PRD §12.2 处理，不以有成交作为扫描资格。非交易日不伪造成有行情的交易日，资金变动仍来自用户事实。

日终发现与账务重算交替获得执行机会，不能扫描完全部账户才开始算，也不能一直处理用户更正而漏掉每日快照。发现结果、目标推进与账户扫描游标在同一短事务提交；重新检查相同有效输入不重复建目标。历史行情更正的发现必须有来源版本 / 变更日期证据或经过预算验证的回查策略；来源尚未核验时不能宣称已支持自动发现全部历史更正。此输入适配证据留在行情专题补齐，不在记账链路内请求运营同步。

等待数据与正在计算分开：等待期间保存缺失原因和下次检查时间，不增加完成量；§4.6 的运行中更新要求不能被拿来要求每 30 秒虚构进度。进入计算后仍须按批次更新业务进展，后台无进展或退出须如实表现为停滞 / 异常，不得靠独立心跳长期伪装正在计算。

以下为**待评审的保守设计初值，不是实测结论**。采用单一不可变 `TradingAssistantExecutionPolicyV1`（拟放本模块的 `execution_policy.py`），由 App 在启动时注入循环、待办查询及分批计算服务；不新增 env、Settings、数据库配置或用户输入，不读取 Ops 的同名参数。首次固定为版本化工程策略，后续确需可调才另做配置变更审计。代码尚未创建，不得把此处默认值当成已生效。

| --- | --- | --- |
| `local_concurrency` | 每个 Web 进程 1 | App 执行资源与后台协调循环；禁止无界提交线程任务 |
| `idle_poll_seconds` | 1 秒 | 没有到期工作时的可中断等待；有工作则每批让出调度后继续，不额外逐批睡 1 秒 |

统一来源、默认值、作用、消费者及生效方式以上表为准；策略修改随代码评审 / 发布、进程重启生效，不热更新、不改变收益核算规则版本。启动日志输出非敏感策略版本和值，模块业务健康信息记录最近批次时间、积压最早时间、失败原因和实际进度；不得记录 Webhook、安全密钥或整份用户账本。缺少配置 / 性能自动化测试前不进入实现发布，不把本表复制到前端作为另外一套控制参数。

预算验收包括：代表性单账户长历史、多账户积压、多个 Web 进程，以及同时进行正常页面查询 / 保存时的 P95、连接等待、峰值内存、最长无进展时间与恢复时间。500 行 / 2 秒不意味着整账户两秒完成；若这些设计初值达不到现有页面体验或资源预算，先调整分批和查询，再评估是否需要新基础设施。未实测前不承诺固定完成秒数。

## 6. 已确认：混合现金转出后的本期复用本金

### 6.1 问题背景与确认记录

PRD §12.1.1 第 13—17 项要求：闲置现金不计本金、同一期资金复用不重复计本金、真正新增参与的资金才增加本金，不要求用户标明资金来源。同时，账户实际现金可以同时包含“本期还没用来买股票的现金”和“本期卖出回款”。

此前 A—I 案例没有混合现金转出这一步，未明确分配顺序。2026-09-09 用户已选择第一种处理：优先扣本期未参与交易的闲置现金。产品文档已补充第 19 项、案例 J 和 T52，本节不再是待拍板项；不涉及改变转出合法性或让用户填写资金来源。

### 6.2 同一份流水的具体差异

假设同一账户、同一个完整自然周，忽略费用，仅用于说明本金。A、B 均隔日卖出，满足 T+1；周初没有持仓。

| 日期 | 记录 | 操作后现金 |
| --- | --- | ---: |
| 周初 | 现金 20000.00 | 20000.00 |
| 周一 | 买 A，花 10000.00 | 10000.00 |
| 周二 | 卖 A，收到 11000.00，赚 1000.00 | 21000.00 |
| 周三 | 转出 10000.00 | 11000.00 |
| 周四 | 用余下 11000.00 买 B | 0.00 |
| 周五 | 卖 B，收到 12000.00，再赚 1000.00 | 12000.00 |

两种分配下，本周收益均为 `2000.00`，转出合法，所有现金和持仓都一致；不同的只是“本周曾经参与的去重本金”：

| 决策结果 | 如何解释周三转出及周四再买 | 本周本金 | 本周收益率 |
| --- | --- | ---: | ---: |
| 已采纳：优先转出本期未参与交易的闲置现金 | 转出的 10000.00 是一直没买过股票的现金；留下的 11000.00 全部属于本周卖出回款，买 B 不新增本金 | 10000.00 | 20.00% |
| 未采纳：优先转出本期卖出回款 | 卖出回款被转走 10000.00，只剩 1000.00；买 B 的另外 10000.00 是原闲置资金首次参与 | 20000.00 | 10.00% |

第二行仅保留为被否决的反例，不是可选配置或并存算法；实现和验收只能采用第一行。

### 6.3 已确认的规则边界

采用“优先转出本期未参与交易的闲置现金”：本例本周显示 **20.00%**。不因为转出一笔原本就闲置的钱，把本可复用的资金重复计入本金，也不新增录入字段。

每个统计窗口独立识别闲置与复用额度；转出先减少闲置部分，超出的部分才减少仍可用于后续买入的复用额度；已经计入本期的历史参与本金不因转出而删除。后续转入只增加现金，尚未实际买入时不增加本金；若原可复用回款已被转走，不能把后来的新入金凭空视为那笔回款仍留在账户。

原 A—I 及已通过资金转出交互保持不变。下面是规则的技术展开及有限算术验证，不将用户对产品边界的确认扩大为全部算法实现已验收。

### 6.4 单账户全仓期间本金计算步骤

计算范围先固定为“一个具体账户 + 一个日 / 周 / 月窗口”。窗口开始时重新建立三个计算值，均不是新增真实资金账户，也不是收益率持久化明细：

| 计算值 | 含义 | 窗口起点 |
| --- | --- | --- |
| `idleCash` | 本窗口尚未用于股票的闲置现金 | 期初真实现金；不追查窗口之前现金的来源 |
| `reusableCash` | 本窗口卖出所得、仍留在账户且可用于后续买入的回款 | 0；跨期已是现金的部分不携带上期复用标记 |
| `participatingPrincipal` | 本窗口已经参与过的去重成本本金 | 期初仍持有数量对应的未分摊含费买入成本合计；不取市值、动态摊薄成本或已卖出数量的历史投入 |

按业务日期升序读取有效事实。同一日期先汇总资金转入、资金转出、买入含费支出和卖出净回款；每笔费用仍按原始流水保存值求和，不能先合并交易再算最低佣金。以下顺序是固定的日级计算步骤，不是真实成交先后的推断，也不改变 T+1 可卖校验：

1. 当日转入加入 `idleCash`，不改变 `participatingPrincipal`。
2. 当日卖出净回款加入 `reusableCash`，不再增加本金。若极端费用使合计卖出净回款为负，先扣可复用现金，不足部分扣闲置现金；该费用支出不冒充新买入本金。真实余额不足仍须由账户校验阻止，不允许把负现金强行归零。
3. 当日买入含费支出优先消耗 `reusableCash`；不足部分消耗 `idleCash`，且只有这部分增加 `participatingPrincipal`。
4. 当日转出优先消耗步骤 3 后的 `idleCash`，不足部分才消耗 `reusableCash`；不减少 `participatingPrincipal`。
5. 每日核对两类现金均非负，且 `idleCash + reusableCash = 同版本真实账户现金`。下一日承接这两个余额及已参与本金。对有效事实，只改变同日录入排列不得改变结果。

当日有足够真实现金时，“买入优先用复用回款”和“转出优先用闲置现金”分别优先消耗不同部分，不应靠录入先后来选择分母。真实转出能否提交继续按 PRD §9.4 的当前已登记余额检查；这个期间重算器不得绕过该检查，也不能借未登记回款让转出成功。

窗口结束后：`期间收益率 = 同窗口新增收益金额 / participatingPrincipal`。无交易无持仓且本金为 0 是无期间股票收益，不除以 0；存在有效持仓却本金异常为 0 是核算错误，不伪装为空值。日 / 周 / 月分别重放对应窗口，不能从日快照分母直接相加得到周月分母。

“全部账户 + 全仓”分别运行账户计算，再汇总分子、分母。本节不能套用于单股筛选，也不能把单股分母相加冒充账户分母。用户已明确单股按自身期间总收益 / 总成本计算，使用 §6.6，不跟踪其他股票占用其回款。修订 7 曾提出的两种单股资金追踪解释均不再是待选方案；历史原因及关闭记录见 §8.2。用户已明确采用本节全仓日级步骤，剩余工程细化不再作为本金规则待拍板。

### 6.6 单股期间与全仓期间的范围承接（修订 8）

依据为 PRD v1.20 §12.1.1 第 20—21 项，不是另增一种可配置收益算法。

1. 先固定当前用户、账户范围、股票范围和日 / 周 / 月窗口、事实与估值版本；同一收益查询必须显式知道是全仓还是单股。两者的分子都只取本期新增收益，期内结束轮次不能删除，跨期仍持有轮次按期末累计减期初累计，初始化按原基线截断。
2. 对每个具体账户的单股，分母 `stockPeriodCost = openingUnallocatedBuyCost + sum(periodBuyGrossAmount + periodBuyCommission)`。期初成本只承接期初尚未卖出数量的未分摊含费成本；本期每笔买入按有效事实累计。本期卖出不减少已参与成本，也不生成可复用本金抵扣；不查询其他股票的买卖来决定该分母。成交信息及其自动费用修订须选择同一有效事实版本，不把被替换旧交易再加一次。
3. 单股收益率为 `stockPeriodProfit / stockPeriodCost`。分子是净收益，不减 1；费用仍逐笔扣计，零负动态摊薄成本不作分母。持仓累计查询仍按该轮累计买入投入计算，不从单股期间分母反推当前成本价。
4. 全仓分母只运行 §6.4；多账户先独立算相应范围的分子、分母，再分别求和后相除。不存在跨账户共享现金、平均收益率或从单股成本简单求和得到全仓去重本金。即使账户里仅交易一只股票，选“全仓”与“单股”时分母仍可能不同，见案例 L；不能由股票数量自动切换算法。
5. 单股期间成本是后端查询计算中间值，不新增单股收益率表；日账户快照保存全仓期间指标。日 / 周 / 月各自计算期初承接和期间输入，不叠加日分母冒充周月分母。查询与缓存若后续采用，键必须包含账户、股票范围、窗口与事实 / 估值版本，不能让两种范围共用一个数值结果；不在本轮新增缓存实现。

待实施测试：K 必须同时验证单股 2000 / 20000 与全仓 2000 / 20000，并证明删除 B 的买入只改变全仓去重分配、不改变 A 自身总成本（其余有效 A 事实相同）；L 必须验证单股 2000 / 21000 = 9.52%、全仓 2000 / 10000 = 20.00%。补充跨期部分卖出仅承接剩余买入成本、单股两账户加权汇总、同日输入排列、成交信息更正后的费用计算、同代码清仓重建仓等正反例。具体 API 字段、真实路由 / 前端状态与测试符号仍待后续方案和 LLD 映射，本轮未创建测试代码。

最近一轮方案解释已在内存以整数分验证 8 组全仓样本：案例 K、盈利回款复用、亏损后补钱、J 闲置现金先转出、全部转出后新入金买入、跨期期初剩余成本、极端费用导致负净回款、入金未买入；全部符合 §6.4 的本金与现金恒等式。该记录仅为算术证据，不是数据库、真实 API、行情或功能验收；完整精度 / 重算验证仍未完成。

### 8.1 后续核验发现：初始化当日可卖数量（规则与交互已确认并合入）

本项是在上述完整性审计提交后，继续核验账户模型时发现的新边界；不是恢复已经关闭的收益或机器人问题。修订 3 曾暂停并请用户确认；2026-09-10 用户答复“同意”，随后明确 R8 交互评审通过并要求合入。下面保留发现原因，当前业务和交互确认均已关闭。

**发现问题时的历史依据（修订 3，初始化旧稿现已由 R8 替代）：**

1. PRD §6.3 要求录入初始化时的当前持仓数量和含费成本，不要求补录之前交易；§7.2 和 §17.1 要求严格 T+1，当日新买数量不能卖出。
2. 2026-09-10 只读核对正式 Figma 第 20 页 `1441:130`（`Onboarding / Step 3`）：初始现金、初始持仓、股票、数量、成本及添加 / 移除入口齐全，但没有可卖数量或当天新买数量；第 19 页也没有另一套初始化输入。现有 T+1 拦截 `1442:111` 针对已知当日买入的场景，不解决初始化输入的缺失。
3. 样例中的“期初可用持仓”说明针对固定演示账本，不能推广为“任何用户初始化时录入的总持仓都可在当天卖出”。

**为什么影响实现：**

| 初始化时真实情况 | 修正前表单能收到的信息 | 当天最多可卖 |
| --- | --- | ---: |
| 1000 股全部在之前交易日买入，当前含费成本 10.00 | 股票、1000 股、成本 10.00 | 1000 股 |
| 600 股之前买入，400 股今天新买，当前含费成本同为 10.00 | 股票、1000 股、成本 10.00 | 600 股 |

两组输入完全相同，卖出 800 股却应一组允许、一组拒绝。系统不能从总数量和成本倒推出真实可卖量：一律可卖会放过第二组，一律锁到下一交易日又会错误拦住第一组。

**已确认规则：**只在首次初始化的每只股票中增加“当前可卖数量”，由用户照券商显示填写，必填、允许 0，不得超过总持仓；总持仓与可卖量的差额作为初始化时当日不可卖部分，下一个交易日解除该项 T+1 限制。它只补齐初始数量状态，不补造历史买卖、不新增历史佣金，不改变现有含费成本基线。字段默认留空，不能把未填等同于 0 或默认全部可卖。

**正式交互承接：**PRD v1.19 的 §6.3、§7.2、§17.1.1 规则不变。已将 R8-A 原位应用到第 20 页正式 `1441:130`，保留第二步到第三步入口及上一步、完成连接。正式未填写、超额、零可卖状态分别为 `1756:4922`、`1756:4964`、`1756:5006`，说明为 `1757:1705`；复用现有表单、错误样式和等宽按钮。第 21 页四张 R8 稿保留为已通过 / 已应用记录，不再是待评审基线。固定示例只表达状态，错误态不跳转完成页，任意输入校验和添加 / 移除行为仍须真实实现；完成页沿用独立示例账本，不代表初始化值已经计算。已检查节点边界、按钮尺寸及前后链接目标；本轮不新增业务字段实现或数据库迁移。

**模型与校验承接要求（现已映射到 §4.2—4.4，仍不是最终 DTO / DDL）：**

1. 按账户、股票保留初始化日期、期初总持仓、期初可卖数量及含费成本。可卖量是必须持久化的初始事实，不能从总持仓、价格或缺失的历史成交推算；暂不可卖量由二者相减得到，不新增第二个用户输入。整数和上下界校验在前后端一致执行，0 与未提供必须区分。
2. 对初始化日 `d0`，校验该股票该日有效卖出数量之和不得超过期初可卖量；录入下一笔卖出时，可用余额为期初可卖量减去该日已有有效卖出。同日新增买入不增加余额。更正或撤销交易时按更正后的有效集合重算，不能把被替换的旧卖出重复扣减。
3. 对 `d0` 之后的交易日，用上一交易日结束的持仓数量减去当日有效卖出数量。初始化不可卖差额在下一交易日按此规则纳入，不使用 24 小时计时或自然日解锁，也不依赖重启后的内存状态。按所查询 / 更正的交易日期回算，不能因为今天已经解锁，就放过初始化日的历史超卖；交易日来源仍须在完整行情与日历方案中核验。

**冲突依据：**PRD §14.2 第 5 项要求最终业务结果统一四舍五入到两位；§9.2 要求同日各笔使用同一完整单位成本分摊，并要求一轮清仓后全部闭环盈亏之和等于整轮收益；§14.2 第 6 项要求闭环合计、摘要和下钻相互对账。若“最终业务结果”包含各笔闭环分摊成本独立舍入后的金额，这些要求不能在所有分币场景同时严格成立。不是 Decimal 精度不足，也不是原始金额录入错误。

**可发生的样本：**买入 300 股，价格 33.32，买入佣金 4.00，含费成本合计 `9996 + 4 = 10000.00`。下一交易日分三笔各卖 100 股，全部清仓，符合 T+1。每笔精确分摊成本为 `10000 × 100 / 300 = 3333.333…`，独立四舍五入均为 `3333.33`，三笔合计却是 `9999.99`，少分摊 `0.01`。

为核对利润，以每笔卖价 34.00、佣金 4.00、印花税 1.70 作固定算术输入（税率只作为既有 PRD 样本规则，不是本轮税法核验）：每笔净回款 `3394.30`，按独立舍入成本得到利润 `60.97`，三笔合计 `182.91`；实际整轮利润则是 `3394.30 × 3 - 10000 = 182.90`。费用逐笔一致，差异完全来自成本分摊舍入，不能篡改现金或再加一笔费用来消掉。

**已采纳的原则，尚未实现业务代码：**以总成本与整轮利润准确对账为优先，允许按固定、可重建的规则对闭环分摊成本做分币尾差调整。此例金额集合为 `3333.33、3333.33、3333.34`，相应利润集合为 `60.97、60.97、60.96`，合计恰为 `182.90`。调整的是成本分摊的最后一分钱，不改用户输入、实际成交费用或现金，不新增手工配置项。§4.5.1 已固定余数优先、稳定来源标识破平的分配顺序及依据；原例“第三笔”仅用于展示，不将无精确成交时间的最后录入当成真实最后成交。

PRD §14.2 已明确“费用仍逐笔四舍五入；闭环成本分摊允许为合计对账进行分币调整”的例外。不采用“每笔独立舍入、允许合计差一分”的另一方案，也不新增可选算法。现有 Figma 布局不变，真实页面字段与数据的验收仍由后续 API / 状态映射承接。

**验证与当前状态：**修订 9 的 Decimal / 精确分数反例保留；修订 10 补 §4.5.1 的整数分算法、3000 组样本和乱序重放验证。本项已关闭；修订 11 已继续展开 §4.6 的派生快照 / 历史重算合同，运行接线、预算与真实验收尚未完成。原 §8.2 的单股 / 全仓本金规则保持已关闭，不因分币问题重新讨论。
